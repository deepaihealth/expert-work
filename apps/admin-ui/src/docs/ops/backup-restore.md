面向平台运维（system_admin）——本篇范围是**用户工作区**的归档与恢复（其他数据域的备份不在这里）。核心是记住一件事：恢复的操作顺序不能颠倒，顺序错了会导致刚恢复的数据被下一轮清扫任务覆盖冲掉。

## 归档从哪来

参见《用户维度运维》——清除用户数据之后，后台清扫任务（janitor）会把该用户的工作区打包归档到对象存储，再清空原始目录，原地留一个永久墓碑标记挡住这个用户以后再申领沙箱。

## 90 天窗口

归档对象自清除完成起保留 **90 天**，到期后由一个定时任务把归档对象和对应的数据库记录一起物理删除。对象存储本身还配了一条独立的生命周期规则做同样的事（到期自动清理），作为应用层这个定时任务万一失效时的兜底——两条路径殊途同归，不是两个不同的保留期。

也就是说：误清除的用户，只要在 90 天之内发现，数据都还能拿回来。

## 恢复顺序——先清墓碑，再解包，最后复位

90 天窗口内需要恢复某个用户的工作区时，按下面这个顺序做，**不能打乱**：

1. **先清掉墓碑标记。** 这是最容易被忽略、但顺序错了后果最严重的一步。墓碑标记还在的时候，janitor 每一轮（约 30 分钟一次）都会把这个用户当成“还在等待归档”——如果这时候已经把文件解包放回了原来的目录，janitor 下一轮会把这个刚放回去的目录当成“复活”了，重新打包上传（覆盖掉刚恢复的完整归档）、再删一遍目录，恢复等于白做。清掉墓碑标记本身也会重新放开“这个用户可以申领新沙箱”的闸门，所以这一步和后面几步要连着做，不要清完标记就搁置。
2. **把归档文件解包恢复到原来的位置。**
3. **把数据库里这条工作区记录的状态复位成“未删除、未归档”。**

三步都做完之前，不要让这个用户去申领新沙箱或触发新的写入——顺序颠倒或中途被打断，都可能让 janitor 在还没恢复完成的目录上抢跑。

不需要手动补用量统计——下一轮 janitor 的全量扫描（约 30 分钟内）会自动把这个用户的已用空间重新算准。

**如果怀疑归档本身是不完整的**（比如打包上传中途失败过、或者看到过 janitor 报错）：归档对象的存储位置是按用户确定性算出来的一个固定位置，同一个用户始终对应同一个位置——这意味着“半成品”也可能覆盖过一份完整归档。恢复前先把归档内容下载下来核对一遍，不要假设它一定是最后一次完整打包的结果。

## 第二层反悔垫：文件服务器回收站

janitor 每轮归档完成后会清空原始目录——这一类删除操作会先进文件服务器自带的**回收站**，保留 **7 天**。这是比 90 天对象归档更短、但更靠前的一层安全网：如果归档这一步本身出了问题（比如上传到一半就被打断），原始文件在回收站里还有一周的抢救窗口，不需要走上面那套“先清墓碑”的完整恢复流程——直接从回收站找回原目录即可。

## 什么时候找谁

工作区恢复不是 admin-ui 界面上能自助完成的操作（下载归档、解包、改数据库状态都是运维侧的操作），需要恢复某个用户的数据时，找平台运维处理。
