面向平台运维（system_admin）——什么时候要发布、发布脚本做了什么、smoke 检查两种常见假摔、发布记录的惯例。本篇不涉及集群连接方式与内部地址——那部分只在运维内部手册里，不适合写进应用内文档。

## 三条独立的发布线

平台由三个可以独立发布的东西组成，谁改了就发谁，不用每次都三个一起发：

- **control-plane**（后端 API）：业务逻辑、数据库迁移、接口改动。
- **admin-ui**（前端控制台）：这个应用本身。
- **沙箱镜像**：Agent 执行代码时用的那个容器镜像——只有沙箱运行时/工具链改动才需要发它，发布路径与前两个完全独立，不在同一条流水线上，是单独的手动步骤。

大多数改动只涉及 control-plane 和/或 admin-ui，这两个可以合在一次发布里一起走（也可以只发其中一个）。沙箱镜像的改动通常单独发；但如果一次改动同时触及了 control-plane 的沙箱对接逻辑和沙箱镜像本身，两条线之间**谁先谁后是有讲究的**——顺序错了会让“沙箱工具暂时不可用”的窗口被拉长，具体顺序按变更内容跟负责发布的工程师确认，不是本篇要展开的细节。涉及沙箱镜像的变更，镜像要在 control-plane / admin-ui 发布之前先行到位——反过来会把沙箱工具不可用的窗口拉长到镜像就绪为止。

## 一条命令的语义

control-plane / admin-ui 这条线用一个脚本一次性走完，按固定顺序做五件事：

1. **构建 + 推送镜像**——为改动到的组件各构建一个新镜像，打上一个新 tag（默认取当前代码提交的短哈希；每次发布都用一个从没用过的新 tag，不复用旧 tag——镜像分发那一层是按 tag 缓存的，不会重新比对内容是否变化，复用旧 tag 有可能拿到的还是旧内容）。
2. **钉版本**——把编排配置里各组件的镜像 tag 改成刚构建出的新 tag。这一步的改动**故意不提交**，留到发布验证通过之后再补一个专门的记录提交（见下文）。
3. **应用配置 + 跑数据库迁移**——把新版本的配置推给运行环境，并跑一遍数据库迁移（迁移只做向前兼容的加法，不做破坏性变更——这样即使这次发布出问题要回滚，旧版本代码也还能在新的库结构上正常跑）。
4. **等所有实例滚动完成**——每个组件都等到新版本的实例全部就绪才算这一步结束。
5. **跑 smoke 检查**——一套只读、可重复跑的健康检查（见下一节）。

脚本支持一个“演练”模式，只打印每一步会做什么，不真正执行——发布前想确认一下命令对不对时用。

## smoke 检查与两种已知假摔

smoke 检查覆盖：所有实例是否都处于正常运行状态、后端健康探针、公开入口的可达性与鉴权网关是否生效、可观测性组件是否可达、指标采集目标是否全部在线。全绿才算通过。

发布之后紧跟着跑 smoke，有两类失败是**已知的瞬态假摔**，重跑一次通常就变绿，不代表发布出了问题：

- **旧实例还在“收尾退出”阶段**——滚动更新切到新版本之后，旧实例不是立刻消失，而是有一个收尾退出的过程；这段时间里它可能被状态检查误判为“没就绪”。等它彻底退出（通常几秒到几十秒）重跑即可。
- **新实例还没被指标采集到**——刚起来的新实例要等采集系统的下一个采集周期才会被记上“在线”状态；在被第一次采集到之前，它的健康态是“未知”而不是“下线”，指标检查会看到类似“总数的几分之几在线”这种暂时性的不齐，跑过一个采集周期后自然补齐。

这两类之外的 smoke 失败（比如同一个目标连续多轮都没恢复、或者健康探针本身返回错误）按真实故障处理，不要无脑重跑掩盖。更多故障排查关键字见《常见故障排查》。

## 发布记录的惯例

第 2 步“钉版本”的改动是故意不提交的——等发布跑完、smoke 确认通过之后，把这个版本号改动单独提交成一个“发布记录”提交，commit message 里写清楚这次发布带上了哪些改动、验证结果（比如 smoke 通过的检查项数）。这样每次线上实际跑的是哪个版本、什么时候发的、验证过什么，都能从提交历史里查到，不用去猜。
