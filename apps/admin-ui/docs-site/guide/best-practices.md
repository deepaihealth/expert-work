# 最佳实践

本篇是几条容易踩坑的对接建议——服务端怎么调用、`user_id` 怎么取、key 怎么保管、流式怎么处理断线。

## 只在服务端调用,别把 key 塞进前端

API Key 是持有者凭证,谁拿到就能以你的服务账号身份发起调用、铸造终端用户、消耗你的配额。**永远不要把 key 打包进浏览器 JS、移动端 App,或任何终端用户能反编译 / 抓包拿到的地方**——只在你自己的后端服务里持有和使用它。

顺带说一句:control-plane 目前没有为浏览器跨域访问开 CORS allowlist,这个开放 API 设计上就不是给浏览器直接调用的——就算开了 CORS,也解决不了"key 泄露给终端用户"这个问题,CORS 管的是浏览器要不要放行跨域请求,不是密钥保密。你的架构应该是终端用户 → 你的后端 → Expert-Work API,而不是终端用户的浏览器 / App 直连。

## `user_id` 怎么取

`user_id` 是你自己业务里终端用户的标识,首次出现会被自动铸造成一个新的终端用户,长期记忆 / 工作区 / 按用户的 token 计费都挂在它上面(见 [调用 Agent](./run-agent))。取值要满足:

- **稳定**——同一个终端用户每次调用都传同一个 `user_id`,别用会变的值(比如一次性 session token、每次登录都换的 id)。传了个新值等于给这个用户重新铸造了一个"新人",之前的记忆 / 会话历史全接不上。
- **每个终端用户唯一**——不要把多个真实用户共用一个 `user_id`(比如图省事全用 `"default"`),否则他们的记忆、工作区文件会串在一起。
- 用你系统里本来就唯一且不变的标识就行——内部用户 id、稳定的第三方账号 id 都可以,不需要是真实姓名 / 邮箱这类 PII。

## Key 的保管与轮换

- 明文只在创建 / 轮换时返回一次——存进你自己的密钥管理系统(环境变量 / secret manager),不要写进代码仓库、日志、错误上报。
- 给外部对接方的 key 只给 `write`(需要轮询就加 `read`),不要给 `admin`(见 [认证](./auth))。
- 设置 `expires_at`,别留永久 key;到期前用轮换换一把新的,宽限期内新旧 key 都能用,不用停机切换。
- 一旦怀疑 key 泄露,别等轮换的宽限期——直接吊销,再创建一把新的。

## Stream 断线怎么处理

流式调用(`mode: "stream"`)是一条长连接,中间可能因为网络抖动 / 代理超时断掉。处理方式(细节见 [SSE 事件格式](./sse-events)):

1. 连接一建立就把 `X-Expert-Work-Session-Id` / `X-Expert-Work-Run-Id`(或第一条 `metadata` 帧里的 `run_id` / `thread_id`)存下来。
2. 断线后不要重新发起一次新的 `/runs` 调用(那会开启新的一轮 run)——用 `GET /v1/sessions/{thread_id}/runs/{run_id}/events` 接回这次 run 的事件流。
3. `token` 预览帧断线后拿不回来,这是预期行为;界面状态以最近一条 `updates` / `metadata` 帧为准,不用还原逐 token 的打字机效果。
4. 给读流加超时:正常情况下大约每 15 秒会有一条心跳注释帧,超过这个间隔什么都没收到,就判断连接已死,按上面第 2 步重连。
