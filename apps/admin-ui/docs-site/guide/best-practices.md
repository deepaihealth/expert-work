# 7 对接注意事项与 FAQ

本篇是几条容易踩坑的对接建议、常见问题,以及上线前的联调自测清单。

## 7.1 只在服务端调用,别把 key 塞进前端

API Key 是持有者凭证,谁拿到就能以你的服务账号身份发起调用、铸造终端用户、消耗你的配额。**永远不要把 key 打包进浏览器 JS、移动端 App,或任何终端用户能反编译 / 抓包拿到的地方**——只在你自己的后端服务里持有和使用它。

顺带说一句:Expert-Work 后端目前没有为浏览器跨域访问开 CORS allowlist,这个开放 API 设计上就不是给浏览器直接调用的——就算开了 CORS,也解决不了"key 泄露给终端用户"这个问题,CORS 管的是浏览器要不要放行跨域请求,不是密钥保密。你的架构应该是终端用户 → 你的后端 → Expert-Work API,而不是终端用户的浏览器 / App 直连。

## 7.2 `user_id` 怎么取

`user_id` 是你自己业务里终端用户的标识,首次出现会被自动铸造成一个新的终端用户,长期记忆 / 工作区 / 按用户的 token 计费都挂在它上面(见 [调用 Agent](./run-agent))。取值要满足:

- **稳定**——同一个终端用户每次调用都传同一个 `user_id`,别用会变的值(比如一次性 session token、每次登录都换的 id)。传了个新值等于给这个用户重新铸造了一个"新人",之前的记忆 / 会话历史全接不上。
- **每个终端用户唯一**——不要把多个真实用户共用一个 `user_id`(比如图省事全用 `"default"`),否则他们的记忆、工作区文件会串在一起。
- 用你系统里本来就唯一且不变的标识就行——内部用户 id、稳定的第三方账号 id 都可以,不需要是真实姓名 / 邮箱这类 PII。

## 7.3 Key 的保管与轮换

- 明文只在创建 / 轮换时返回一次——存进你自己的密钥管理系统(环境变量 / secret manager),不要写进代码仓库、日志、错误上报。
- 给外部对接方的 key 只给 `write`(含只读轮询能力;纯只读集成给 `read`),不要给 `admin`(见 [认证](./auth))。
- 设置 `expires_at`,别留永久 key;到期前用轮换换一把新的,宽限期内新旧 key 都能用,不用停机切换。
- 一旦怀疑 key 泄露,别等轮换的宽限期——直接吊销,再创建一把新的。

## 7.4 Stream 断线怎么处理

流式调用(`mode: "stream"`)是一条长连接,中间可能因为网络抖动 / 代理超时断掉。完整的重连策略——怎么找回 `run_id`、怎么用事件回放接口续上、多久没收到数据就该判定连接已死——见 [SSE 事件格式](./sse-events)。

## 7.5 常见问题

**`agent_code` 从哪拿?**

`agent_code` 是租户管理员在管理控制台创建 / 发布 Agent 时定的名字,不能靠 API 查询——`GET /v1/agents`(Agent 列表接口)只对租户管理员登录后的凭证开放,API Key 调用一律 403。需要由你的租户管理员直接告诉你要对接哪个 `agent_code`。

**key 轮换期间,旧 key 还能用多久?**

由发起轮换请求时的 `grace_period_s` 决定,默认 300 秒,最长 3600 秒;宽限期内新旧 key 都能验证通过,一过立刻 401。细节见 [认证](./auth) 的「轮换与吊销」一节。

**`session_id` 从哪来?不传会怎样?**

请求时不传 `session_id` 就是开一段全新会话;传了但不属于这个 `user_id` / `agent_code`,返回 404(见 [错误码与限流](./errors))。拿到 `session_id` 的方式**按 `mode` 不同,别混用**:

- `mode: "stream"`——响应头 `X-Expert-Work-Session-Id`(见 [通用约定](./conventions) 的「公共请求头」一节)。
- `mode: "queue"`——**没有响应头**,202 响应体的 `data.thread_id` 字段就是这次绑定/续接到的会话 id(字段名叫 `thread_id`,不是 `session_id`——两个名字指的是同一个值,下次请求续接时仍然填进请求体的 `session_id` 字段)。

会话绑定(`POST /v1/agents/{agent_code}/sessions`)和上传接口(`POST /v1/agents/{agent_code}/uploads`)这两个端点则是在响应体的 `data.session_id` 字段里给,字段名又不一样——原样按各自接口的参数表读,别假设所有端点用同一个字段名或者都走响应头。

## 7.6 联调自测清单

上线前照这份清单逐项跑一遍,而不是只测"发起 run 能拿到回答"这一条:

- [ ] 拿到一把带 `write` scope 的 key —— [认证](./auth)
- [ ] 发起一次 `stream` 模式的 run,读到完整的 SSE 事件流 —— [调用 Agent](./run-agent)、[SSE 事件格式](./sse-events)
- [ ] 发起一次 `queue` 模式的 run,轮询到终态 —— [调用 Agent](./run-agent)
- [ ] 上传一个文件(图片或文档),拿到 `upload_id` 后发起一次带附件的 run —— [调用 Agent](./run-agent)
- [ ] 用上一次响应给的 `session_id` 续接同一段会话 —— [调用 Agent](./run-agent)
- [ ] 模拟一次断线,用事件回放接口接回同一个 run —— [SSE 事件格式](./sse-events)
- [ ] 取消一次正在执行的 run —— [取消 run 与审批决策](./run-control)
- [ ] 对一个待审批的 run 下达决策(至少覆盖 `approve` 与 `reject`)—— [取消 run 与审批决策](./run-control)
- [ ] 拉取会话列表与某段会话的历史消息 —— [调用 Agent](./run-agent)
- [ ] 列出并下载工作区里的一个文件 —— [调用 Agent](./run-agent)
- [ ] 用一个错误的 `user_id` / `session_id` 组合确认拿到的是不透明 404,而不是你自己代码里判错 —— [错误码与限流](./errors)
