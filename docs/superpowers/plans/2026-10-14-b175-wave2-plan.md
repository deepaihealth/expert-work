## 0. 先摆清楚的事实(10-14 核对,决定下面怎么做)

1. **分词器与长期记忆共用**:`tokenize_for_search`(`persistence/knowledge/text_search.py:17-25`)是 jieba 默认模式(不是 `cut_for_search`),无停用词、无词典,标点也成词。写入侧 `replace_chunks` 用它建 `content_tsv`(`sql.py:1048-1050`),查询侧 `keyword_search_scored` 用它再 `plainto_tsquery('simple', …)`(`sql.py:1190-1194`)。**记忆模块同用这个函数**(`memory/sql.py:167/285/433/539/733`、`memory/memory.py:38/43`)。→ **PR1 不改这个函数**,只在知识库查询侧另起一个查询构造;改了它等于连记忆一起改。
2. **关键词路全 AND,虚词与编号都被拆成必中词**:实测 `动物双歧杆菌乳亚种BGI-N3的专利号是多少？` → `动物 双歧 杆菌 乳 亚种 bgi - n3 的 专利号 是 多少 ？`,`plainto_tsquery` 要求每个词都在同一段里。这就是关键词路 31 道零命中(跨文档 14、表格 8、编号 7、FAQ 2)和编号题排不上的原因。
3. **内存版与 SQL 版语义不同**:内存版是「任一词重叠计数」(`persistence/knowledge/memory.py:657-682`),SQL 版全 AND。→ PR1 的行为测试必须连 SQL 跑(testcontainers),只在内存版上测会假绿;PR1 合入后两边要同义。
4. **向量路**:`search_scored` 按余弦距离排序取 `limit`(`sql.py:1135-1165`),没有任何 `SET LOCAL hnsw.ef_search` / `iterative_scan`;HNSW 索引 `knowledge_chunk_embedding_idx` 用默认参数(迁移 `0021_knowledge_base.py:135-138`)。生产召回深度 `recall_limit = 20`(`orchestrator/tools/knowledge.py:51`,`runtime.py:1876` 不覆盖)。
5. **融合丢掉了所有子分数**:关键词的 `ts_rank` 不留(`tools/knowledge.py:220-222`),RRF 分也不留(`:224`);`RetrievedChunk` 只有向量相似度 `score` 与 `recall_source`(`:77-102`),没有 chunk_id、关键词分、融合分、重排分。记忆侧也用 `rrf_fuse_scored`(`memory/sql.py:334`、`memory/memory.py:189`),**PR2 不改这个函数**,知识库另写加权版本。
6. **重排**:`Reranker` 协议只返回下标(`tools/knowledge.py:60-74`);`DashScopeReranker` 传 `top_n=top_k`、丢掉 `relevance_score`(`llm/rerank.py:97-127`);`HTTPDashScopeRerankClient` 的 HTTP 错误**不兜底**,一路冒到工具层(变成工具报错)和控制台检索测试(未处理的 500);重排返回空列表会被当成「没找到」。`LLMReranker` 吞掉所有异常、退回融合序(`tools/knowledge.py:140-145`)。
7. **平台只有一份重排配置,知识库与记忆共用同一个实例**:`DynamicResolvingReranker`(`runtime.py:1296-1367`)每次读 `effective_rerank_config()`;同一实例传给知识检索(`app.py:1756`)与记忆召回(`app.py:1831` → `graph_builder/memory.py:357`)。配置表只有一对 `rerank_provider / rerank_model`(迁移 `0051`)。→ PR3 的「按用途拆分」是必需的,否则给知识库调重排会顺带改记忆。
8. **阈值只过滤向量路**:`retrieval_score_threshold` 是「最低向量相似度」(`protocol/knowledge.py:166-171`),只作用于向量命中(`tools/knowledge.py:197-208`),关键词命中绕过它 → 混合模式下无答案题永远有结果,这是拒答 0/10 的直接原因。
9. **「检索出错」与「没找到」不分**:库名解析不到、融合为空、重排返回空,都返回 `[]`,工具统一回 `[no relevant knowledge found for the query]`(`tools/knowledge.py:344-348`)。
10. **MMR 已有现成实现**:`expert_work/common/search/mmr.py:28`(`mmr_select`,λ=0.7),目前只有记忆召回在用(`graph_builder/memory.py:378-406`)。
11. **控制台检索测试**:`POST /v1/knowledge/bases/{name}/test`(`api/knowledge.py:840-918`),无 response model、不计量、不记日志;管理端 `RetrievalTestTab.tsx` 每张卡片只显示来源、召回路、向量分、标题路径、正文。**没有任何检索日志表**;最新迁移是 `0165_knowledge_model_v2`。
12. **评测判对规则**:文档命中 = 文件名在手列的期望文档里(`tools/eval/kb_metrics.py:117-120`);段命中 = 同文档且锚文本是 `retrieval_text` 的子串(`:145-150`)。产品 FAQ 题 148 道都只列了 3 份文档(汇总表、FAQ-2025、产品知识库),**内容高度重复的 FAQ-2026 没列**;其中 33 道排第一的正是 FAQ-2026,被算成第一名没命中,整体 MRR 约低估 0.05。
13. **评测的重排开关走的是聊天模型排序**(`kb_eval.py:1034-1058` 只建 `LLMReranker`),与生产的 `qwen3-vl-rerank` 不是一回事。`qwen3-vl-rerank` 限制:单次请求最多 100 份文本、单份 ≤ 8,000 token、整个请求 ≤ 12 万 token;支持 `instruct` 参数(任务说明,默认按问答检索排序)。
14. **与波 2 无关、但要记下的潜在问题**:0165 加了分段 `enabled` 列,但两条检索路都不过滤它(`sql.py`、`memory.py` 均未用),停用的分段照样能被检索到。P3 做「停用分段」之前必须补上;已记入 P3 前置。

## PR0 评测地基(只动 `tools/eval/`)

### T0.1 锚文本判对
- **规则**:一条期望 `{document, anchor}` 命中的文档 = 手列文档 ∪ 入库后任一段 `retrieval_text` 含该锚文本的文档。段命中同理:命中段属于上述文档之一且含锚文本。
- **做法**:`check_anchors`(`kb_eval.py:574-613`)已经逐段扫锚文本,扩成同时产出「锚文本 → 含它的文档集合」;`score_case`(`kb_metrics.py:253-307`)接收扩展后的期望文档集合,原有 `any` / `all` 两级语义不变(`all` = 每条期望各自命中扩展集合里的任一文档)。
- **防误伤**:锚文本过短会匹配到大量无关文档。对扩展后文档数 > 5 的期望单列告警,不自动扩展;报告里列出被扩展的 case 数与扩展前后差异。
- **测试先行**:内存库 + 假嵌入下造「两份文档含同一锚文本、只列一份」的 case,断言另一份排第一时 MRR = 1;锚文本过短的告警;`all` 语义不被放宽。

### T0.2 接上生产同款重排

## PR1 中文关键词(目标 1 2 3)

- **知识库专用查询构造**(新函数,`text_search.py` 内,不改 `tokenize_for_search`):
  1. 去掉虚词与标点成词(「的 是 多少 吗 哪些 什么 ？ ，」等,停用表放代码里,短小、可审);
  2. 识别字母数字编号(如 `BGI-N3`、`TF08-1`、`ZL202011248842.0`):按写入侧同一分词把编号切开后,用短语查询(`<->`)整体匹配,不再要求散开的碎片各自命中;
  3. 其余词用 `|` 组成「任一词命中」,用 `to_tsquery('simple', …)`(查询串由我们拼,词先过 `quote` 处理,防注入);
  4. 排序改 `ts_rank_cd`;命中编号短语的段加权(作为一个可调常数,不是硬编码魔法数)。
- **写入侧不变**:`content_tsv` 不重建,不需要回填。
- **内存版同义**:`InMemoryKnowledgeStore.keyword_search_scored` 用同一个查询构造(任一词 + 编号短语 + 同样的去虚词),两边谓词一致。
- **记忆不受影响**:加锁定测试——记忆的关键词召回结果在本 PR 前后不变。

## PR2b 文档名进检索文本(给 5 打底;10-15 拍板加入)

**为什么做**(10-15 实数):
- 评测召回结果里抽到 24 份产品说明书的 268 段,**132 段(49%)正文不写自己是哪个产品**。问句点名产品时,这些段在关键词路上匹配不到产品名,向量也只能靠内容相似。
- 重排模型同样看不到文档名:`_rerank` 送的是 `chunk.retrieval_text`(`orchestrator/tools/knowledge.py:256`),文件名要到之后的 `_attribute` 才查(`:273`)。智能体拿到的结果带 `[文件名#序号]`(`:405`),重排模型拿不到。
- 业界依据(10-15 调研,原文已读):DAPR(UKP/Cohere,arXiv 2305.13915)零样本给段落前加文档标题,nDCG@10 平均 +1.4~2.4,「要知道出自哪篇文档才答得出」的题 0 → 34~40;Anthropic Contextual Retrieval 用模型写的上下文句,前 20 未命中率 −35%(仅向量)/ −49%(加关键词);2026-10 的对照实验(arXiv 2610.10170)证明真标题胜过随机标题,但幅度小(+0.01)。RAGFlow 默认把文件名放进关键词(权重 10,正文 2)并按 0.1 混入向量;LlamaIndex 默认把文件路径放进向量与关键词。
- **反例**:标题长且杂会伤(DAPR 基因组数据集 −8~−12);同一文档所有段带同一前缀会更难区分彼此;没见过标题格式的模型可能略降。→ 下面的做法与闸门都针对这几条。

**做法**:
- `chunk_retrieval_text` 增加文档名:格式 `[Document: <名>]` 放在 `[Section: …]` 前。名字只做通用清洗:去扩展名、`_` 与多余空白归一、超长截断(上限做成常数);不放目录路径,不做针对某家资料的规则。
- **向量路**:嵌入文本 = 上述检索文本(DAPR 做法)。需要重新嵌入。
- **关键词路**:文档名作为 tsvector 里单独加权的一段(`setweight(…, 'A')`,正文仍是 D),不和正文混成一段;PR1 的覆盖率 / IDF 计分如何吃这个权重,在 PR 里按评测定,要和 PR1 对齐(PR1 现在把整列压成 D)。
- **重排**:送 `retrieval_text`,自然带上文档名,不用另改。
- **存量**:旧段没有文档名照常检索(行为同今天);重新入库后才带上。文档改名后检索文本过期,要重新入库,文档里写明。
- **同批的入库统一**(10-15 拍板并入,PR1 遗留;都要重建索引,和文档名一起重建只做一次):
  1. **写入侧做与查询侧相同的归一**(NFKC + 破折号归一,只用于知识库的关键词索引,`tokenize_for_search` 与记忆不动):PR1 只在查询侧做,半角问句查不到全角原文(`2型` 查不到 `２型`)。归一后 PR1 查询侧「原样形 OR 归一形」可以收回成只用归一形。
  2. **编号里的空格**:原文 `ZL 2018 1 1514219.8`、用户输入 `ZL201811514219.8` 时编号短语对不上(先实测确认)。写入侧对「字母数字编号」做同一套去空格规则,查询侧同规则。
  3. **标题不单独成段**:说明书里「问题标题」单独切成一段、答案在下一段,PR1 的整句加分会把只有问句的那段顶到第一(主评测集 2 道,重排后已回到第 1)。切块时只有标题、没有正文的块并入下一块。
  - 三项与文档名**分开记数**:评测按「改前 → 只加入库统一 → 再加文档名」逐组跑,各自都要证明不退、有提升;只重建关键词索引不花钱,文档名改动检索文本要重嵌入。

**评测与合入闸门**(主评测集 + 真实问法集,召回层 + 最终排序都跑):
1. 三组对照:改前 / 真文档名 / **随机换名**(把文档名在文档间打乱,长度与格式不变)。
2. 补一个题目切片:答案段正文没写产品名、问句点名产品的题(约 15 道,只读产品资料出题)。
3. 闸门:两套题整体与各来源不变差(目标 6 7 的口径);真文档名在 MRR 上明显好过随机换名;新切片有提升;说明书 Q&A(同一文档里找某一段)不退。任一条不过就不合,结论写回本计划。
4. 费用:每组重新嵌入评测库约 9 元(10-14 全量嵌入实测 ¥9.19),两组约 18 元;带重排再加每组约 1 元。开跑前报估算。

**测试先行**:检索文本格式与清洗规则(扩展名、下划线、超长截断、空名退回无前缀);全角 / 半角四种组合都能互查;带空格与不带空格的编号互查;只有标题的块被并入下一块(标题仍进 `heading_path`);写入侧向量与关键词都用新文本;关键词路文档名权重生效(只在文档名里出现的词也能命中,且排在正文命中之后或之前,按定下的计分);重排收到的文本带文档名;旧段无前缀不变。

## PR3 专用重排 + 阈值 + 去重(目标 4 5)

- **重排按用途拆分**:平台配置加「知识库重排」一对 `(provider, model)`(迁移加两列,可空);为空时继承现有那一份,记忆一律用现有那一份 → **记忆行为不变**(锁定测试)。`DynamicResolvingReranker` 按用途取配置;控制台平台配置页与 API 同步加字段。
- **`Reranker` 协议返回 `(index, score)`**;`DashScopeReranker` 的 `top_n` = 候选总数,保留 `relevance_score`;`LLMReranker` 无分数时返回 None(阈值对它不生效,文档写明)。
- **候选**:PR2 的召回深度(≤ 100);可选 `instruct` 参数(默认不传,评测里对比一次再定)。**请求总量上限**:`qwen3-vl-rerank` 整个请求 ≤ 12 万 token、单份 ≤ 8,000 token(§0 第 13 条),100 个大段可能超限 → 候选按 token 预算截断(从排名靠后的丢),不能让超限变成整次重排失败(10-14 PR2 审查遗留)。
- **阈值**:库配置加 `rerank_score_threshold`(可空,默认空 = 不拒答,保持现行为);重排分低于阈值的段丢弃,全丢 = 拒答。原 `retrieval_score_threshold`(向量相似度)保留原语义。阈值只用主评测集校准,目标 4 的误拒上限(≤ 6 / 293)是硬约束。
- **MMR**:用现成 `mmr_select` 对重排后的结果去冗余(λ 可配,默认 0.7);主要针对重复文档(两版 FAQ)。
- **失败 ≠ 没找到**:重排 HTTP 错误在知识库路径兜底为「退回融合序 + 标记 degraded」,不再冒成工具报错 / 控制台 500;库名解析失败、嵌入失败与「零命中」在工具输出里分开(给模型的文字说清是检索出错,不是库里没有)。
- **测试先行**:用途拆分后记忆仍拿旧配置;分数透传;阈值边界;全丢即拒答;MMR 对两份同文去重;重排 500 时降级而不报错;四种「空」各自的工具输出。
- **重排对精确编号不友好**(10-15 PR1 评测):hard_exact 召回层 MRR 0.611,开重排后 0.538。方向:编号短语完整命中的段不让重排挤出前几位,或给重排传 `instruct`;评测里对比再定。
- **评测**:最终排序 hybrid 改前 / 改后;目标 4 5 在此 PR 验收(5 若差一点,要在 PR 里摆出是哪类题拉的分)。
