# 智能体异步 program(异步长任务 + 运行中插话)

> 2026-11-12 立项整理。**本文件是这条主线的唯一排期入口**,ROADMAP 里 B-144 / B-304 / B-305 三行只写状态,先后顺序和范围以本文件为准。
> 来源:用户 11-12「借助这个机制,实现智能体的异步长任务、插话等功能」;业界参照见 §2。
> 本文件是总图,不是设计稿。每个阶段开工前单独出设计稿,先摆场景让用户拍板(§7),再开 PR。

## 1. 要解决的场景

| # | 场景(用户视角) | 今天的样子 | 想要的样子 |
|---|---|---|---|
| S1 | **长任务交出去就走**:让智能体做一份要跑 40 分钟的健康方案 / 调研报告,用户关掉页面 | run 能跑完(队列模式 + 断线可重放),但做完没人通知;用户得自己回来翻 | 做完主动通知(对接方收 webhook、控制台有提示),回到对话就能看到结果 |
| S2 | **跑着的时候插一句**:智能体在做表,用户插一句「改成按月汇总」 | 这句话排在后面,等这一轮整个跑完才处理(B-139 排队);前面的活按旧要求做完、白做 | 当前这一步做完、下一次调用模型之前,把这句话塞进去,智能体当场改方向 |
| S3 | **叫停重来**:用户发现方向错了,说「停,换个做法」 | 只能先取消(`:cancel`),再重新发 | 一条消息完成「停掉当前这轮 + 带着新要求重开」 |
| S4 | **边做边聊**:长任务在后台跑,用户同时问一个不相关的小问题 | 小问题排在长任务后面,要等几十分钟 | 长任务交给后台子智能体,主智能体空出来马上答;长任务做完自己回报 |
| S5 | **管理后台任务**:同时开了两个后台任务,想看进度、给其中一个追加要求、取消另一个 | 子智能体(`spawn_worker` / `subagent`)跑完才返回,中途不能看、不能改、不能单独取消 | 主智能体能列出、查看、追加指令、取消每个后台任务 |

S2 / S3 = 插话;S1 / S4 / S5 = 异步长任务。两者共用同一个底座(§4)。

## 2. 业界做法(11-12 读原文)

- **LangChain Deep Agents 异步子智能体**(2026-11-05,beta;[博客](https://www.langchain.com/blog/agents-are-going-async)、[文档](https://docs.langchain.com/oss/python/deepagents/async-subagents)、[参考实现](https://github.com/langchain-ai/async-deep-agents)):
  - 主智能体 5 个工具:`start_async_task`(立即返回任务编号)/ `check_async_task` / `update_async_task` / `cancel_async_task` / `list_async_tasks`。
  - 追加指令两种:`interrupt`(默认,停掉当前这次、带着新指令重来)/ `enqueue`(等当前这次跑完再接着做)。
  - **完成通知不靠模型去查**:主智能体忙时,每次调用模型前查一遍未完成任务(每个任务一次、总共最多 5 秒),结果当作一条带元数据的消息塞进来;主智能体空闲时,子智能体完成就叫醒它开新一轮;主智能体停在审批上时不打扰,等用户答完再给。
  - 子智能体要审批时显示「等待中」,用户在子智能体自己的会话上答,不打断主智能体。
  - 任务清单放在单独的 state 通道(不放消息历史),压缩后也不丢;任务编号用整串 UUID,不用 `thread::run` 这种带分隔符的格式(模型会拆开传)。
  - 启动方式:`isolated`(只给任务描述,默认)/ `fork`(带一份主对话快照,实验性,基本吃不到前缀缓存)。
  - 已知坑(官方文档写的):模型开完任务马上反复去查状态、把异步又变回同步;报旧状态;截断任务编号。
- **Claude Code 后台 agent**:同一模式,本仓库开发就在用(派后台 agent → 完成通知 → 继续派活 / 发消息续跑)。默认让后台 agent 共用工作目录,我们实际用 worktree 隔开写冲突。
- **OpenAI 异步工具调用**([指南](https://developers.openai.com/api/docs/guides/async-tool-calling)):工具定义加 `async: true`,模型发出调用后不等结果先往下答,结果在后面的请求里按原 `call_id` 补回;另配一个应用自己实现的 `wait_for_tasks` 工具。**这是 OpenAI 接口独有的**,GLM / DeepSeek / Qwen 没有,我们只能在平台这一层做(与 LangChain 同路)。
- **插话**(B-144 立项时调研,10-02):五家主流产品都支持运行中插话或中断;openclaw 默认插话模式(当前工具跑完后、下一次模型决策前注入,未开始的调用给合成结果);hermes 区分插话与改道(改道只取消在途的模型请求,不杀工具)。

## 4. 核心机制:统一收件箱(两条线共用)

所有「要送进一个正在跑(或停着)的智能体」的东西走同一个收件箱,而不是插话、后台回报、定时结果各造一套:

- **来源**:用户插话 / 后台任务回报(完成、失败、等待审批)/ 定时任务结果 /(以后)异步工具结果。
- **落库**:按会话持久化(多副本、重启不丢),每条只送进检查点一次(B-151 那类「并行写丢消息」不能再犯)。
- **什么时候送进去**:
  - 智能体在跑 → 当前这批工具跑完之后、下一次调用模型之前(openclaw、LangChain 同一时点);
  - 停在审批上 → 不送,等审批有结果后再送;
  - 空闲 → 视来源决定:用户插话 = 正常开新一轮;后台回报 = 叫醒智能体开新一轮(可按智能体关掉,改成只发 webhook)。
- **模型看到什么**:用户插话就是一条用户消息;后台回报是带来源标记的平台消息。**要注意 B-162 的教训**:GLM 的对话模板里「工具结果后面跟一条 user 消息」= 新一轮开始,平台内容曾因此被当成用户原话 —— 设计稿要实测几家模型对「中途插入的用户消息」和「平台回报」各怎么理解。
- **对外**:新事件(例如「插话已送进第 N 步」「后台任务完成并已回报」),对接方可通过 webhook 或在跑的 SSE 收到;控制台对话页能看到插话落在哪一步。

## 6. 开工前先数(阶段 0 第一件事,只读查询,不花模型钱)

- 运行时长分布:近 30 天生产 / 测试 run 里超过 5 / 10 / 30 分钟的各占多少(决定 S1 / S4 值不值得做)。
- 用户在 run 还在跑时又发消息的频率:`queued_behind` 非空的 run 数、排队等了多久(决定 S2 的价值和默认行为)。
- 发完消息又取消重发的次数(`:cancel` 后 60 秒内同会话新 run)—— S3 的需求量。
- `spawn_worker` / `subagent` 的调用量与单次时长(8 月统计真实流量自动委派 = 0;要看现在是否仍如此)。
- 对接方(深护智康)是否已经接了 webhook、能否接收「对话里多了一条消息」这类主动推送。

## 7. 要用户拍板的事(各阶段设计稿里再细化,这里先列)

1. **插话的默认行为**:继续排队(今天)/ 默认插话 / 由对接方每次指定(推荐:默认仍排队,对接方和控制台可选插话,先不改默认)。
2. **插话时在跑的工具**:让它做完再插(推荐,最安全)/ 立即停掉。
3. **后台任务能不能改正式产出**:能写工作区但不能登记交付件 / 和主智能体一样(推荐前者,沿用「子智能体只做事不拍板」)。
4. **用户不在时的钱**:后台任务单独的预算与时限上限,到线就停并回报(推荐),还是沿用整轮的。
5. **空闲时后台回报要不要叫醒智能体自己开一轮**:要(会多花一轮模型调用)/ 只通知、等用户回来再说。
6. **对接方契约**:新增事件和 `if_busy` 参数都是可选的,老对接方不改也照常(推荐);深护智康是否同步接入。

## 8. 风险与已有教训

- **两轮交错写同一份检查点**(B-75 / B-139 / B-151):收件箱投递、打断重来都要在会话锁里做,先写设计再写代码。
- **模型反复查状态**:LangChain 文档点名的坑;平台必须主动送达回报,工具描述里写明「不用查」。
- **模型抄错长串**:任务编号用整串、不带分隔符;能不让模型抄就不让(参照 `memory: llm-retypes-opaque-strings`)。
- **内部记账外发**:新 state 通道一律进 `_INTERNAL_STATE_KEYS`(B-302 #2084 刚修过一次)。
- **共享工作区写冲突**:LangChain 默认共享沙箱没处理;我们至少要做到后台任务之间、后台与主智能体之间不互相覆盖。
- **审批**:子智能体今天遇审批是软拒回父;后台化之后要能真的停下等用户,且不挡主智能体。
