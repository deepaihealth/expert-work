## 0. 先摆清楚的事实(调查结论,决定下面怎么做)

1. **现有 RAG 评测没走真实链路**:`tools/eval/rag.py` 从 YAML 读预切好的段、用假嵌入、写进 `InMemoryKnowledgeStore`(`rag.py:109-177`);没有 CLI、没有 MRR / nDCG、没有页码。它仍是 M0 闸门的一部分(`run_baseline.py:182-184`,`eval_engine.py:76` 会 import),**不动它**,另起 `kb_eval.py`。
2. **真实入库链路一个函数就能调**:`ingest_document_bytes(*, store, embedder, tenant_id, document_id, kb_id, filename, raw, chunk_max_tokens, chunk_overlap_tokens) -> int`(`knowledge/ingestion.py:38`),只要 `KnowledgeStore` + `Embedder`,不要 settings、不要 control-plane。调用前要自己 `create_base` + `upsert_document`。
3. **关键词路 SQL 与内存两套语义不同**:SQL 是 `plainto_tsquery` 全 AND(`sql.py:785-815`),内存是任一词重叠打分(`memory.py:452-477`)。**基线必须用 `SqlKnowledgeStore` 跑**,否则量不到设计 §2 缺陷 1。
4. **语义切块会多一遍嵌入**(`chunk_markdown_semantic` 先嵌每个 block,`chunking.py:95`),真嵌入跑评测要上 `longmem/embedders.CachedEmbedder`(sqlite 内容哈希缓存)。
5. **没有页码**:解析丢掉页边界(`parsing.py` 不传 `page_chunks`),`KnowledgeChunk` / `RetrievedChunk` 都没有页或偏移字段。评测集的「期望位置」先用**文档名 + 锚文本**(期望段落里一段原文子串),页码等 P5 加了 `source_locator` 再补。
6. **检索器行为**:`KnowledgeRetriever.search(..., method, score_threshold, rerank)`(`orchestrator/tools/knowledge.py:149`);两路各取 `recall_limit=20` 再 RRF;**阈值只过滤向量路**(`:183-194`),混合模式下关键词命中总会进融合 → 「无答案」判定用 `method=VECTOR` + 阈值,或在运行器里自己按分数截。
7. **入库可靠性的实况**(全部已核到行):
   - `_to_document` 不拷 `attempts`(`sql.py:88-99`),所有 SQL 端点返回 `attempts: 0`。
   - `status='processing' AND attempts >= max` 的行永远不再被认领(`_claimable`,`sql.py:49-64`),崩在第 5 次就永远卡住;`test_exhausted_attempts_not_reclaimed` 还把这当成期望。
   - 状态 / 分段写回只按 `(tenant_id, id)` 过滤(`set_document_status :587`、`replace_chunks :649`、`mark_document_failed_terminal :554`),无代际 / 租约围栏:重传或重入库会 `attempts=0` + 立刻删分段(`upsert_document :362-412`),旧任务随后写回旧分段并置 READY。
   - 恢复 worker 一次认领 20 个、300 秒租约、**串行处理**(`recovery.py:101-133`),批次超 300 秒后面的租约先过期,其它副本再认领一次,白耗 attempts。
   - 快速通道任何异常都终态 FAILED(`ingestion.py:232`),嵌入 429 / 超时不重试;`OpenAICompatibleEmbedder` 按 10 条一批**串行**发(`embedder.py:116-141`)。
   - 上传 `await file.read()` 无上限(`api/knowledge.py:459`);`settings.document_max_bytes`(25 MiB)只管 `api/uploads.py`。
   - `list_documents` 不分页(`api/knowledge.py:505`);控制台写操作零审计。
8. **管理端实况**:`DocumentsTab.tsx` 的 `Upload.Dragger` 已 `multiple`,但逐个串行、单个 `uploading` 布尔、无进度 / 大小检查 / 文件夹(`:105-127, :270-280`);`uploadDocument` 无 `onUploadProgress` / `AbortSignal`(`api/knowledge.ts:209-218`);文档表 `pagination={false}` 且入库中每 5 秒全量重拉(`:38, :87-103`);全仓没有多文件队列组件,`src/hooks/` 只有 `useStatusPolling.ts`。i18n 是 TS 文件,新键要在 `en.ts` 接口、`en.ts` 值、`zh-CN.ts` 三处加,漏一处 typecheck 红。
9. **评测语料**:`~/kb-eval/huada/manifest.csv`(仓库外),A 层 649 份有文字层文档(含 `D-A` 31 份)、B 层 331 份扫描件;金标准 221 条(产品 FAQ 表 149 + `FAQ-2026.xlsx` 156 + 说明书 Q&A 129,归一化去重)。**原文档不进仓库;CI 不碰真文档**。

## L2 入库可靠性 + 数据模型(原 P0-PR1 + P3-PR1,拆 3 个 PR)

### L2-PR1 切块乱码(单独小 PR,最先合)
- **文件**:`control_plane/knowledge/chunking.py`(`_tail_text :281-288`、`_split_by_tokens :272-278`)、`tests/test_knowledge_chunking.py`。
- **做法**:两处都改成「先 `decode_bytes` 再**截到完整 UTF-8 字符边界**」,再把 `_tail_text` 的起点**向前推到语义边界**(段落 `\n\n` > 换行 > 句末标点 `。！？.!?`),找不到边界才退回字符边界;`_split_by_tokens` 两端同样处理。`_hard_split` 拼接改 `"\n"`(原来用 `" "`,中文句间多出空格)—— 这一条顺手但要单独一条断言。
- **测试先行**:构造 39 种中文 / emoji / 表格尾切(10-10 实测 13 种含 U+FFFD)→ 断言任一分段 `"�" not in chunk`;重叠起点落在句边界;重叠不跨标题(已有 `test_overlap_not_carried_across_a_heading_change` 保持绿);**自证**:把边界修正注掉,红。

### L2-PR2 入库可靠性(代际守卫 · 终态巡检 · 并发恢复 · 退避 · 上限 · 审计)
- **迁移 `0164_knowledge_ingest_generation`**:`knowledge_document.ingest_generation bigint NOT NULL DEFAULT 0`;`down_revision="0163_writeback_job_dedup"`。
- **协议**:`ClaimedIngestion` 加 `generation: int`;`KnowledgeDocument` 加 `ingest_generation`;新 `DocumentStatus` 取值预留 `blocked` / `disabled`(B-179 用,本 PR 不写入)。
- **store ABC / 内存 / SQL 同步改**(谓词同义,契约测试参数化跑两套):
  1. `upsert_document`:存在则 `ingest_generation += 1`、状态 pending、**不再删分段**、`attempts=0`;若 `content_sha256` 相同且 `status='ready'` → 不改状态,返回 `(doc, unchanged=True)`(调用方据此不提交任务;API 返回 200 + `unchanged: true`,原来是 202)。
  2. `claim_document` / `claim_documents_for_ingest`:RETURNING 带 `ingest_generation`;`_claimable` 不变。
  3. `set_document_status` / `replace_chunks` / `mark_document_failed_terminal`:新增关键字参数 `generation: int | None`;给了就加谓词 `status='processing' AND ingest_generation=:gen`,不匹配返回 False / 不写;`replace_chunks` 在**同一事务**里删旧插新(本来就是),只是多了围栏。
  4. 新方法 `sweep_terminal(*, now, max_attempts) -> int`:`status='processing' AND attempts >= max AND lease_until < now` → `failed`,`error='ingest attempts exhausted'`(修「第 5 次崩溃永久卡住」);`test_exhausted_attempts_not_reclaimed` 改成「不再被认领,但被巡检置 failed」。
  5. 新方法 `renew_lease(*, tenant_id, document_id, generation, now, lease_seconds) -> bool`。
  6. `_to_document` 拷 `attempts`(顺手修,一条断言)。
  7. `list_documents(*, tenant_id, kb_id, limit, offset) -> (items, total)`;`list_bases` 同形;默认 `limit=50`,上限 200。
- **`parsing.py`**:`parse_document` 输出做一次 UTF-8 清洗(10-13 真语料实测:docx 里半个 emoji 解析成孤立代理项 `\ud83d`,之后任何 UTF-8 编码 —— 写库、写缓存 —— 都抛 `UnicodeEncodeError`,整份文档入库失败且报错看不出原因);测试:含孤立代理项的解析结果 → 分段正文可 `encode("utf-8")`。
- **`ingestion.py`**:`_run` 用 claim 返回的 generation 写回;嵌入调用包一层 `_embed_with_backoff`(429 / 5xx / 超时:指数退避 1s·2s·4s,最多 3 次,只在 ingestion 侧,不动 `orchestrator/llm/embedder.py`,记忆侧行为不变);快速通道加全局 `asyncio.Semaphore(settings.knowledge_ingest_concurrency, 默认 4)`;处理中按 `lease_seconds/3` 续约。
- **`recovery.py`**:`run_once` 先 `sweep_terminal`,再认领 `limit=concurrency`,`asyncio.gather` 并发处理(每个在自己的租户 RLS 上下文里),续约同上。
- **`api/knowledge.py`**:上传改流式读入 + 上限 `settings.knowledge_document_max_bytes`(默认 50 MiB,可配)→ 超限 **413** `{"error": "file_too_large", "limit_bytes": …}`;`list_documents` / `list_bases` 加 `limit` / `offset` / `total`(默认值保证老客户端不传参也得到前 50 条 + `total`,管理端 L3 第二个小 PR 切过去);所有写操作 `emit` 审计:`knowledge:base_create / base_update / base_delete / base_reindex / document_upload / document_delete / document_reingest`,`resource_type="knowledge_base"|"knowledge_document"`。
- **测试先行**(按条目一一对应):
  - 两个并发 worker 复现「旧覆盖新」:worker A 认领 gen=1 → 重传使 gen=2 → worker B 认领 gen=2 并写回 → A 再写回 `replace_chunks(generation=1)` **不生效**,文档 READY 且分段是 B 的(内存 + SQL integration 各一条;SQL 用 `asyncio.gather`,照 `test_claim_documents_concurrent_exactly_once` 的写法)。
  - 第 5 次尝试崩溃后 `sweep_terminal` 置 failed,再认领为空。
  - 同哈希重传:状态不变、不删分段、API 200 `unchanged`。
  - 重传期间**旧分段仍在**(直到新分段整体替换)。
  - 恢复:25 个 pending、concurrency=4 → 单次 `run_once` 只认领 4 个且并发;租约在处理中被续约(mock 时钟)。
  - 嵌入 429 两次后成功 → READY;三次都 429 → FAILED 且 error 含 `429`。
  - 上传 50 MiB + 1 字节 → 413;49 MiB → 202。
