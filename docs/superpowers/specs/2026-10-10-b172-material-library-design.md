## 1. 场景与范围

**场景**:根据客户的语义或意图,搜出合适的商品、视频等物料。例:客户说「晚上老睡不着,别太贵」→ 返回改善睡眠的商品卡片 + 一条讲睡眠调理的科普视频。

**用户 2026-10-10 给出的约束**:

| 问题 | 回答 | 对设计的影响 |
|---|---|---|
| 物料数据在哪 | 可能是零散文件,也可能在别的系统 | 零散文件走本方案的导入与抽取;**别的系统用 MCP 对接,不在本方案范围** |
| 结果给谁看 | 员工和客户都有 | 需要「对员工」与「对客户」两种模式,对客户更严 |
| 有哪些硬规则 | 不确定,不同类型可能不同 | 规则不能写死,作为「物料类型」的字段声明;平台给通用默认 |
| 视频是什么样 | 都有可能(有无标题介绍、各种题材) | 有现成元数据就用;只有文件就从口播与画面生成 |

**不在范围**:对接外部商品系统(走 MCP);下单、支付、库存实时扣减。

## 2. 为什么不能直接用现在的文档检索

| | 文档检索 | 物料搜索 |
|---|---|---|
| 搜索单位 | 一段文字 | 一条物料记录(一个商品 / 一条视频) |
| 返回 | 文字片段 | 物料卡片:ID、类型、名称、价格、封面、链接、推荐依据 |
| 条件 | 无 | 价格、品类、适用人群、禁忌、地区、上下架等 |
| 难点 | 找到相关段落 | 把客户口语翻译成需求,对上物料;且不能推荐不该推的 |

把商品写成文档也能搜到(测试环境的产品条目就能命中),但返回的是片段、无法筛选、一个商品可能被切成几段、视频进不来、客户说法与商品描述对不上。

## 3. 设计原则

1. **物料是一条记录**,搜索结果以物料为单位去重返回,前端按 ID 渲染卡片;模型只能引用工具返回的真实 ID,**无法编造不存在的物料**。
2. **安全规则由平台代码执行,不交给模型判断**:禁忌、对客可见性、上下架、有效期等硬条件在 SQL 层过滤。
3. **对客模式由平台判定,不由模型选择**:模型不能把自己切到「对员工」模式绕过限制。
4. **平台默认可用,扩展可配**:预置几种通用物料类型和字段,不配置也能用;租户只在需要时追加字段或规则([[platform-defaults-over-configuration]])。
5. **平台文本零租户内容**:类型模板、需求画像提示词、示例全部泛化。
6. **先量再做**:先建「客户说法 → 期望物料」的评测集,硬规则违反数与对客泄露数必须为 0。

## 4. 数据模型

物料库作为知识库的一种类型(`knowledge_base.type = 'material'`,推荐;待拍板),复用 B-171 的检索与索引设施。

### 4.1 物料类型(字段与规则的声明)

平台预置通用类型,租户可追加字段:

| 预置类型 | 通用字段 |
|---|---|
| 商品 | 名称、介绍、价格、品类、规格、适用人群、禁忌人群、使用方法、链接、封面 |
| 视频 | 标题、介绍、时长、题材、口播文字稿、关键画面描述、链接、封面 |
| 图文 / 文章 | 标题、摘要、正文链接、封面 |
| 服务 / 课程 | 名称、介绍、价格、适用人群、周期 |

每个字段带四个属性:

| 属性 | 含义 |
|---|---|
| `filterable` | 可作为搜索条件(价格上限、品类…) |
| `rule` | `none` / `hard_exclude`(命中即排除,如禁忌人群、限售地区)/ `soft_boost`(排序加权,如主推、新品) |
| `customer_visible` | 对客模式是否可展示(成本价、内部话术不可) |
| `required` | 缺失时进入待补全列表 |

规则因此「跟着类型走」:不同类型可以有不同的硬规则,租户不确定时用平台默认(只对「禁忌人群」「上下架」「有效期」三项默认执行硬过滤)。

### 4.2 表

```sql
CREATE TABLE material_type (id, tenant_id NULL /* NULL=平台预置 */, key, name, fields jsonb /* 字段声明 */, version);
CREATE TABLE material (
  id, tenant_id, kb_id, type_id, seq /* 租户内短编号 M{seq} */,
  title, summary, attributes jsonb /* 按类型字段存值 */, need_profile jsonb /* §5.2 */,
  status /* draft|confirmed|offline */, customer_visible boolean, valid_from, valid_to,
  media jsonb /* 封面、视频、图片在 OSS 的地址与哈希 */, source_refs jsonb /* 来自哪份文件哪段 / 哪行 */,
  version, last_edit_source /* pipeline|import|user */, created_at, updated_at);
CREATE TABLE material_rule_check (material_id, field, value, status /* candidate|confirmed */);  -- 模型抽取的禁忌等候选,确认后生效
```

检索索引复用 `knowledge_chunk`(B-171 §5.6 的 `chunk_type` / `parent_chunk_id`):

- 每条物料一行 `chunk_type='material'`:文本 = 名称 + 摘要 + 需求画像 + 关键字段;
- 每条「客户可能的说法」一行 `chunk_type='material_phrase'`,`parent_chunk_id` 指向物料行,命中后折叠回物料(同 FAQ 相似问做法)。

全部带 `tenant_id` + RLS;短编号 `M{seq}` 不含空格,穿过输出围栏不被改写。

## 5. 入库

### 5.1 四条入口

| 入口 | 做法 |
|---|---|
| 表格导入 | Excel / CSV,列映射到类型字段;按内容哈希幂等(append / replace) |
| 手工录入 | 控制台表单,按类型字段渲染 |
| **从零散文件抽取** | 复用 B-171 批 4 的整理流水线:按物料类型模板抽取候选 → 逐字段标出处 → 去重合并 → 缺字段 / 字段矛盾进待确认 → 人工确认后发布 |
| 视频文件 | §5.3 |

### 5.2 需求画像(解决「客户说法和物料描述对不上」)

每条物料一次模型调用,只根据物料自身字段生成(字段里没有的留空,不推断):

- `solves`:解决什么问题 / 满足什么需求;
- `suits`:适合什么样的人、什么场景;
- `not_suits_candidates`:可能不适合的人群(**只作候选,进 `material_rule_check`,人工确认后才成为硬规则**);
- `phrases`:客户可能怎么说(5~10 条口语化说法);
- `tags`:主题标签。

物料内容或类型变更时重算;人工改过的画像锁定,只提修改建议。

### 5.3 视频

1. 有标题 / 介绍:作为主要信息。
2. 抽音轨 → 语音转文字得到口播文字稿(**平台目前没有语音识别能力,需新接供应商,型号与价格待核**)。
3. `ffmpeg` 按场景切换抽 5~10 张关键帧(沙箱镜像已有 `ffmpeg`)→ 视觉模型写画面描述。
4. 汇总生成视频摘要 + 需求画像,建索引;返回时给视频链接、封面、时长,可附「相关片段的时间点」(以文字稿时间戳定位,二期)。
5. 原视频存 OSS;按文件哈希缓存转写与描述,重跑不重复花钱;限制单条时长与每库总量。

## 6. 搜索

### 6.1 智能体工具

```
material_search(need: str, types?: [str], filters?: {price_max, category, tags, ...}, customer_conditions?: [str], limit?: int)
```

- `need`:智能体把客户的话理解成一句需求描述(说明里要求写完整需求,不写关键词列表)。
- `filters`:只接受类型里声明为 `filterable` 的字段,其余报错并列出可用字段。
- `customer_conditions`:客户的情况(孕期、正在服用某类药、过敏…),用于禁忌过滤。
- **没有 `audience` 参数**:对员工 / 对客户由平台从智能体配置或调用渠道判定(待拍板具体来源)。

另配 `material_get(id)` 读单条物料详情(按模式过滤字段)。

### 6.2 流程

1. 混合召回:关键词 + 向量,作用在物料行与说法行上;说法行折叠回物料。
2. 硬过滤(SQL):`status`、上下架、有效期;对客模式只留 `confirmed` 且 `customer_visible`;`hard_exclude` 字段与 `customer_conditions` 命中则排除。
3. 专用重排(同 B-171 §5.2),再按 `soft_boost` 字段加权。
4. 多样性:同类物料去重,类型之间留配额(例如商品与视频各给几条)。
5. 返回物料卡片:`M{seq}`、类型、名称、按模式过滤后的字段、匹配依据(命中了哪条需求画像或说法)、链接、封面。
6. 辅助信息走 `ToolResult.notice`:被规则排除的条数、**未提供客户情况、禁忌未校验**这类提示。

### 6.3 推荐话术

模型只依据卡片字段写推荐理由;对客模式下不得出现卡片外的功效描述。卡片的前端渲染与对外 API 投递形态(会话条目里新增卡片类事件)单独设计。

## 7. 对客模式与合规

| | 对员工 | 对客户 |
|---|---|---|
| 可返回物料 | `draft` 带「未确认」标记 + `confirmed` | 仅 `confirmed` 且 `customer_visible` |
| 字段 | 全部 | 仅 `customer_visible` 字段 |
| 禁忌候选(未确认) | 展示并警示 | 待拍板:按严格执行(先排除),还是确认后才生效 |
| 话术 | 可参考内部话术字段 | 不含内部字段 |

## 8. 评测

- 每种物料类型准备一批「客户说法 → 期望物料」样例,覆盖口语、模糊需求、带硬条件、带禁忌情况。
- 指标:recall@5、MRR;**硬规则违反数 = 0、对客泄露(返回不可对客物料或字段)= 0** 作为必过门槛。
- 视频单独评测「只靠口播 / 画面能否被搜到」。

## 10. 待拍板

1. 物料库作为知识库的一种类型(推荐),还是独立模块。
2. 对客 / 对员工模式的判定来源:智能体配置、调用渠道(对外 API / 企微),还是二者组合。
3. 模型抽取的禁忌候选在确认前是否先按严格执行。
4. 语音识别供应商与成本上限(每条视频时长、每库总量)。
5. 平台预置哪几种物料类型及其默认硬规则。
6. 推荐卡片的对外 API 形态(是否进对话条目协议)。

## 11. 风险

- **客户情况漏传**:模型没把禁忌相关的客户情况传进工具 → 禁忌过滤失效。缓解:对客模式下工具在 notice 明示「禁忌未校验」;提示词规则「推荐前先确认客户情况」;评测集覆盖该场景。是否需要平台侧从对话中自动提取客户情况,作为后续评估项。
- **需求画像编造**:只依据物料字段生成,字段缺失留空;对客模式只用已确认物料。
- **视频成本**:转写 + 多帧视觉调用;按哈希缓存、限时长、限总量。
- **规则配置门槛**:租户不确定规则时依赖平台默认,默认只对禁忌、上下架、有效期硬过滤,其余不限制。
