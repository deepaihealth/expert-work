## 0. 一页看懂

**租户的问题**:改了切块参数、换了模型、上传或删了文档、改了智能体提示词之后,知识库问答是变好还是变坏?今天只能在「命中测试」页一题一题手点,或者凭感觉。

**我们给的东西**:一个「题集 + 一键测评 + 逐题看结果 + 两次对比」的功能。

| | 第一期(P1) | 第二期(P2) | 第三期(P3) |
|---|---|---|---|
| 题从哪来 | 手写、表格导入 | 线上沉淀(检索没命中的问题、差评、对话里「加入题集」)、在分段预览里划一句话出题 | 模型自动出题(人审后才能用) |
| 测什么 | 只测检索;或端到端(指定智能体的某个版本答题) | 一次跑两个对象对比(草稿 vs 已发布、两组检索参数) | 发布智能体前自动跑 |
| 看什么 | 头条数字、逐题明细、错因、人工改判、两次运行对比、导出 | 趋势图 | 开放 API |

**几条关键取舍**:

1. **证据按原文锚定,不按段落编号**。重新切块后段落编号全变,按编号标的答案会失效(RAGFlow Issue #15033);按「文档 + 原文片段」锚定,切块怎么变都找得到。
2. **测租户真实的库和真实的智能体**,不像 WeKnora 那样另建临时库。
3. **判分复用 B-206 的分级尺子**:把回答拆成一条条结论逐条核依据,编造分「与原文矛盾」「张冠李戴」「结论没依据」;3 票多数。
4. **分数带样本量和区间,对比按逐题变好 / 变坏数给结论**。不报「准确率 83.27%」这种假精度。
5. **花钱先预估、用户确认、到上限就停**,和入库同一套规矩。
6. **测评答题不进会话列表、不写长期记忆、用量单独记一种类型**。

## 1. 租户能用它做什么

### 1.1 真实场景

| # | 场景 | 用法 | 期 |
|---|---|---|---|
| S1 | 改了知识库的切块参数,重新入库 | 改前跑一次「只测检索」存为基线,改完再跑,看证据命中数变了几题 | P1 |
| S2 | 上传一批新文档 / 删了旧版本 | 同一题集再跑,看老问题有没有被新文档挤掉;删掉的文档对应的题会标「证据已失效」 | P1 |
| S3 | 改了智能体提示词、换了答题模型 | 端到端测:同一题集分别对「已发布版」和「草稿」各跑一次,对比答对 / 编造 / 误拒 | P1(两次运行手动对比);P2 一次跑完 |
| S4 | 智能体上线前回归 | 准备 30~100 道题,含「资料没写」的题,确认不会乱编 | P1 |
| S5 | 线上有人点了差评、或者检索零命中 | 一键转成题,补上标准答案和证据,下次测评就盯着它 | P2 |
| S6 | 刚建库,一道题都没有 | 模型按文档出题,人审过的才进题集 | P3 |
| S7 | 每次发布前自动跑 | 发布草稿时自动对比当前发布版,退步就提示 | P3 |

### 1.2 对五类资料是否同样成立

| 资料类型 | 典型问题(合成) | 成立吗 | 限制 / 要特别处理的 |
|---|---|---|---|
| 营养健康资料 | 「示例燕麦片每 100 克含多少蛋白质」「孕期能不能喝示例饮品」 | 成立 | 判断类问题多(「能不能」),资料常只有相邻事实 → 要有「部分写了」题型和 B 式作答(§5.5)。判分里「通用安全提示」不算编造,但措辞不能写成健康行业专用 |
| 合同 | 「示例供货合同的违约金比例是多少」 | 成立 | 模板合同大量条款逐字相同 → 证据原文出现在很多文档里,必须同时指定文档,「太常见」的锚要提示(§5.2.4) |
| 制度 | 「出差住宿标准是多少」 | 成立 | 新旧版本并存 → 证据指向旧版时要标「已过时」;同名重传会让旧证据失效(§5.2.5) |
| 产品说明书 | 「示例净水器滤芯多久换一次」 | 成立 | 答案常在表格里 → 证据核对要做表格和数字归一化(B-206 尺子 v2 已有) |
| 会议纪要 | 「3 月 5 日例会定的上线日期是哪天」 | 成立,但出题要求高 | 多份纪要措辞相近,问题必须带日期 / 会议名,否则题本身有歧义;自动出题对它效果最差(§5.3.3) |

### 1.3 不解决什么

- 不判断资料本身对不对:测评只看「回答和资料是否一致」。
- 不自动调参数:只告诉租户哪里丢分、建议查什么。
- 不评长期记忆、联网搜索、外部工具的效果(§5.1)。

### 2.2 缺口

- 没有任何东西把「题集 → 跑 → 判分 → 看结果」连起来给租户用。`eval_run` 是平台自己的回归门,`tools/eval` 只能在开发机上跑,依赖内存库、假嵌入、本地语料和 `EXPERT_WORK_EVAL_*` 凭据,答题用的是自写循环,不是生产智能体。
- 没有一处存「问题 + 回答 + 段落原文」的逐题明细。
- 现有 live 评测可能根本不记用量(§6)。

### 3.3 我们自己的教训(B-206,11-10)

| 教训 | 对本功能的要求 |
|---|---|
| 造「资料没写」的题时只删了锚句,30 道里 26 道的答案仍以别的说法留在库里 | 「资料没写」的题要复核:拿生产检索取前 20 段,让判分模型确认答不了(§5.3.4) |
| 一句没标明的推断就判整题编造,误伤常识、安全提示、算术、复述 | 用分级判分:「与原文矛盾」「张冠李戴」单列,旁支推断只记「夹带推断」(§5.5) |
| 引文和表格单元格格式对不上就判「找不到」 | 判「找不到」前先做文本和数字归一化(复用 `kb_text_norm.py`) |
| 3 票多数仍会有约 1 题 / 组误判;句级判分噪声大,系统级排名稳定(调研给出 TREC 2024:人与 GPT-4o 句级一致率 56%,系统排名 Kendall τ>0.79) | 逐题结果标「仅供参考」,结论看总数和逐题翻转数;判分分歧的题单列让人看(§5.4.3) |
| 75 题 × 3 票判分约 ¥35–45,答题约 ¥8–9 | 判分是大头,必须先预估、确认;票数可选 |

### 3.4 由此定的原则

1. **测真实的东西**:真实库、真实智能体版本、生产的检索和工具输出渲染。
2. **证据按原文,不按编号**;证据失效要能看出来,不能悄悄算错。
3. **分数诚实**:带题数、带区间;判分规则版本不同不比较。
4. **不花用户没确认的钱**。
5. **测评不污染线上**:不进会话列表、不写记忆、不混进检索记录统计、用量分开记。

## 5. 设计

### 5.1 两种测法

| | 只测检索 | 端到端 |
|---|---|---|
| 对象 | 1 个或几个知识库,用库当前的检索参数 | 一个智能体的某个版本(已发布 / 草稿 / `agent_spec_revision` 里的历史版本),用它绑定的库 |
| 每题做什么 | 调与命中测试同一条检索(`KnowledgeRetriever.search`),再用 `knowledge_search` 工具同一段渲染代码算出「交给模型的文本」 | 智能体按自己的模型、提示词、平台提示段、知识库工具答题,记下每次检索 / 读文档的结果和最终回答;再判分 |
| 需要的题字段 | 证据必填(没证据的题只报「最高分」,不进命中率) | 都可选;证据和标准答案越全,能判的越多(§5.4) |
| 花费 | 查询嵌入 + 重排,很便宜(我们开发集约 ¥0.01–0.02 / 题,随模型变) | 答题 + 判分,判分是大头(我们实测约 ¥0.6–0.7 / 题,3 票) |
| 能回答的问题 | 证据有没有被找到、排第几、有没有交给模型 | 加上:答对没有、编造没有、该拒拒了没有 |

**端到端时的外部工具**:智能体的联网搜索、MCP、http、沙箱执行、委派子智能体这类会访问外部或有副作用的工具,P1 一律关掉,结果页标明「测评时以下工具已关闭」。理由:测评要批量跑几十上百题,真实调用外部系统可能下单、发消息、改数据;联网结果每次不同,也会让对比不可复现。代价:绑了知识库又能上网的智能体,测评时「先查库还是先上网」(B-267)测不到。要不要做「替身工具」放进待拍板(§10 第 6 条)。

**参考**:Bedrock 两种测法分开(采纳);Dify 只测检索(只采纳一半,因为租户最终关心的是回答)。

**五类资料**:都成立。会议纪要类问题依赖日期的多,端到端测时智能体可能需要多次检索,答题费偏高。

### 5.2 题集

#### 5.2.1 字段

| 字段 | 必填 | 说明 |
|---|---|---|
| 问题 | 是 | ≤ 2,000 字(与检索记录的查询上限一致) |
| 题型 | 否,默认按证据推 | `可答`(answerable)/ `资料没写`(no_answer)/ `部分写了`(partial),与 `kb_dataset.py:48` 同义。不填时有证据 = 可答,无证据 = 资料没写 |
| 标准答案 | 否 | 有了才能判「答偏」(回答有依据但不是问的那件事) |
| 证据 | 可答题建议填 | 0~5 条,每条 = 文档(按文档名选,存文档 id + 当时的文档名)+ 原文片段(≥ 8 字,与 `kb_dataset.py:37` 一致);`部分写了` 的题填的是「相关事实」的原文 |
| 判定方式 | 否,默认「任一」 | `任一`:任一条证据被找到就算命中;`全部`:要全部找到(「找全」类问题,如「列出所有…」) |
| 标签 | 否 | 自由标签,结果按标签分组 |
| 来源 | 系统填 | 手写 / 导入 / 线上沉淀(带来源会话、检索记录 id)/ 自动生成 |
| 状态 | 系统填 | 可用 / 草稿(证据没对上,或自动生成待审)/ 证据失效 |

**参考**:Dify「问题 + 证据文本 + 标签,导入时匹配段落、对不上存草稿」(采纳);Bedrock「标准答案必填」(不采纳:冷启动门槛高,而且「资料没写」的题本来就没有标准答案);RAGFlow #15033、WeKnora `29c52b034`(证据按文本不按编号)。

**改了什么**:证据锚定在「文档 + 原文片段」,不锚在段落上;文档按 id 存,文档名只做显示和导入匹配 —— 文档改名不影响。

#### 5.2.2 导入导出

- **格式**:XLSX(给业务人员)、CSV、JSONL(给开发)。XLSX 模板一行一题,列:`问题 / 题型 / 标准答案 / 判定方式 / 标签 / 证据1文档 / 证据1原文 / … / 证据5文档 / 证据5原文`。JSONL 一行一个对象,字段同上,证据是数组。模板和示例里只放合成内容。
- **上限**:单个题集 500 题(Bedrock / FastGPT 1,000、扣子 5,000)。理由:端到端 500 题按我们的实测约 ¥300–350(3 票),再大一次跑不起;要更多就分题集。做成平台设置,不写死。
- **导入时**:逐行校验;证据文档按文档名在指定库里找,找不到或原文片段对不上的那一题存为草稿、在导入报告里列出行号和原因,其余照常导入(Dify 做法)。
- **导出**:与导入同格式,能原样导回。

#### 5.2.3 版本

- 每题有稳定的题号和内容指纹(问题 + 题型 + 标准答案 + 证据 + 判定方式)。改任一项指纹就变。
- 题集每次被修改,版本号 +1;**每次运行冻结当时的题目快照**,运行结果引用快照,题集之后怎么改都不影响已有结果。
- 两次运行对比时只比指纹相同的题;改过的题列在「题目改过,不参与对比」。

**参考**:百炼新版、扣子、Langfuse 都有带版本的评测集(采纳);我们不做分支、不做命名版本 —— 租户要的是「这两次比得了吗」,指纹就能回答。

#### 5.2.4 证据检查

- **什么时候查**:导入时、编辑时、每次运行开始时。
- **怎么查**:证据文档还在、处于可用状态,且原文片段归一化后落在该文档**检索能返回的某一段**里(父段;与 `tools/eval` 的「锚文本存活检查」同口径,README §B-175)。归一化用 `kb_metrics.anchor_key`(NFKC、去 HTML、小写)加 B-206 v2 的表格与数字归一。
- **太常见的片段**:同一片段出现在 5 份以上文档里时提示「这句话太常见,请换一句更有区分度的」(`tools/eval` `--doc-match anchor` 的阈值)。合同模板、制度通用条款最容易碰上。
- **片段跨了段边界**:落不进任何一段时提示「这句话被切在两段之间」,这本身就是切块的信号,在结果页也单列。

#### 5.2.5 证据失效

| 情况 | 标记 | 运行时怎么算 |
|---|---|---|
| 文档被删 | 证据失效:文档已删 | 这条证据不参与命中计算;一题所有证据都失效 → 这题从检索指标的分母里拿掉,单列 |
| 文档被同名重传或修订,原文片段找不到了 | 证据失效:原文已变 | 同上;提示用户更新证据或删题 |
| 文档停用 | 暂停 | 同上(Dify 的「禁用则暂停」) |
| 文档还在,但片段现在落在两段之间 | 证据可用,标「跨段」 | 照常算,结果页提示 |

失效的题**不自动删**:它往往正说明「资料更新后这个问题的答案变了」,让人决定改题还是删题。

**参考**:Dify「原文删除标已过时」(采纳并细分原因)。

#### 5.2.6 和 `eval_dataset` 的关系:新建,不复用

| 方案 | 好处 | 问题 |
|---|---|---|
| A 复用 `eval_dataset`(一行一题,`input / expected` 放 JSON) | 少一张表;CRUD 现成 | ① 按 `agent_name` 归属,而「只测检索」没有智能体;② 没有题集、版本概念,`(tenant, agent_name, name)` 也没唯一约束;③ `source` 的 CHECK 只有三个值;④ **技能进化回放会读 `source in (golden, regression)` 的行**,知识库题混进去会被当成技能的留出集;⑤ 智能体彻底删除时一起删,但只测检索的题不属于任何智能体;⑥ 每租户 1000 行上限是给策展用的 |
| B 扩展 `eval_dataset` 加列 | 同上 | 问题 ①④⑤ 都还在,还要给老消费者加过滤 |
| **C 新建题集表(推荐)** | 归属到租户 + 题集;有版本、有证据状态;删除和留存规则可以按测评的需要定 | 多两张表 |

推荐 C。P2 做「从待审池转题」时,从 `curation_candidate` 直接转进新表,不经过 `eval_dataset`。

### 5.3 题从哪来

#### 5.3.1 手写和导入(P1)

见 §5.2.2。另外在空题集页给一份「怎么写好一道题」的说明:问题要带上能区分对象的名字和日期;每个题集里放一些「资料没写」的题;证据挑最能直接回答问题的那一句。

#### 5.3.2 线上沉淀(P2)

| 入口 | 题源 | 带过来什么 | 还要人补什么 |
|---|---|---|---|
| 检索记录页「转为测评题」 | `knowledge_retrieval_log` 里零命中或分数低的查询 | 查询原文、当时的结果(文档和段落位置) | 题型、证据、标准答案 |
| 待审池(P-2 的 👎) | `curation_candidate` | 用户问题、被踩的那一轮、用户评论 | 同上 |
| 对话详情页每轮「加入题集」 | 会话原文 | 用户问题、智能体当时的回答、当时检索到的段落 | 同上 |
| 分段预览里划一句话出题 | 文档分段 | 这句话自动成为证据 | 问题 |

- 沉淀来的题一律进**草稿**,补齐并通过证据检查后才可用。
- 真实用户的问题可能带个人信息:转题时提示「请删去个人信息」;题记下来源会话的用户,**用户被清除时一起删**(与 `eval_dataset` 在用户清除时被删的现有行为一致)。
- 入口需要能看会话原文的权限(`session:read`),与检索记录页一致。

**参考**:扣子 Trace 回流、Dify「线上问题一键转参考问题」、Glean「从不满意的会话挖题」、LangSmith 线上回流(采纳);**改了什么**:扣子会把低分 Trace 自动回流,我们不自动 —— 线上的问题没有证据和答案,自动进题集只会堆一堆判不了的题。

#### 5.3.3 自动出题(P3)

- **做法**:按文档分批,让模型从一段原文出题,要求同时给出问题、答案和**原文里逐字存在的证据片段**;代码核对片段确实在原文里,对不上的丢掉。题型覆盖单点事实、跨段、比较、数值。
- **出题前筛段落**(DeepEval):目录、页眉页脚、纯表头、过短的段不出题。
- **质量控制**:
  - 全部进草稿,**必须人审**后才能用;审题页一次一题,通过 / 改 / 丢。
  - 一个题集里自动生成的题占比和人审通过率在结果页显示。
- **对五类资料**:说明书、制度效果最好(事实明确);合同出题容易变成法律判断题,要标成「部分写了」;会议纪要问题必须带日期 / 会议名,否则同一问题对多份纪要都成立 —— 出题提示词要求「问题里写明能唯一定位的名称、日期或编号」,措辞不提任何行业。
- **花费**:按文档字数预估,同样要确认。

**参考**:百炼旧版(按知识库出题,可编辑)、Ragas(知识图谱出题)、DeepEval(先筛上下文)、Azure Simulator。**反面证据**:百炼新版文档里已经没有自动出题;Ragas 一类出的题偏「从原文抄一句改成问句」,和真实用户问法差得远(我们开发集里「真实问法集」的检索分一直明显低于按原文出的「主集」,见知识库优化总计划 §3)。所以自动出题只用来冷启动,不能代替线上沉淀。

#### 5.3.4 「资料没写」的题怎么造才不失真

在产品里**不能**像 B-206 难负例那样删租户的资料,只能出「看起来相关、其实库里没写」的题:

1. **出题**:取库里真实出现的对象(产品名、制度名),问一个文档没写的属性;或问一个库里没有、但与库里对象同类的对象。
2. **复核(必做)**:用**生产同一条检索**取前 20 段,让判分模型判「这些段落能不能答出这题」,3 票多数;判为能答的丢掉。这是 B-206 `kb_agent_recheck.py` 的做法(参考 CRUMQs,arXiv 2510.11956)。
3. **人审**:复核过的仍进草稿;审题页把前 5 段给人看。
4. **残余风险照实说**:复核只看前 20 段;答案以别的说法藏在更后面时仍会漏。结果页对「资料没写」题的编造给出「请人工确认」入口。

手写的「资料没写」题同样可以一键跑第 2 步复核(便宜,按次预估)。

### 5.4 指标

#### 5.4.1 检索侧

| 指标 | 含义(给租户看的说法) | 算法 | 出处 |
|---|---|---|---|
| 证据命中 | 前 k 条结果里有没有含证据原文的段落 | `kb_metrics.hit_at_k`,k 默认 = 智能体实际看到的条数,另报 k = 10 | `tools/eval`,Dify 证据命中率 |
| 证据覆盖 | 多条证据时找到了几成 | `coverage_at_k` | `tools/eval` |
| 第一条证据的名次 | 排第几 | 只显示名次;MRR 只在汇总里给开发看 | — |
| **证据交给了模型** | 证据原文是否真的出现在模型拿到的文本里(被条数或字数预算截掉的不算) | `kb_metrics.context_hit`:只测检索时用工具同一段渲染算;端到端时看这一题所有检索和读文档的真实输出 | 我们自己的(B-206),别家没有 |

- 「资料没写」的题没有检索指标,只报「最高分」,用来帮租户看重排分数下限设得合不合适。
- 不报 Precision、MAP:WeKnora 的教训是这类数在只看证据的口径下没有信息量。

#### 5.4.2 回答侧(端到端)

按题型给类别,与 B-206 尺子 v2 一致:

| 题型 | 类别 |
|---|---|
| 可答 | 答对 / 夹带推断 / 误拒 / 编造 / 答偏 |
| 资料没写 | 正确说没写 / 夹带推断 / 编造 / 其它 |
| 部分写了 | B 式作答 / 夹带推断 / 只说没写 / 编造 / 其它 |
| 都可能 | 判分失败、判分分歧(单列,不进分母) |

「编造」再分三种原因,结果页可筛:**与原文矛盾**、**张冠李戴**(别的对象的事实说成这个对象)、**结论没依据**。

头条只放四个数:可答题答对率、可答题误拒率、资料没写题的编造题数、部分写了题的 B 式作答率;再加检索侧的「证据交给了模型」。

| 题上有什么 | 能判什么 |
|---|---|
| 只有问题 | 编造 / 误拒 / 正确说没写(只看回答和它看到的段落是否一致,TruLens 式) |
| + 证据 | 加:检索命中、交给模型、错因归到哪一层 |
| + 标准答案 | 加:答偏 |

#### 5.4.3 怎么呈现才不虚假

- **率都带题数**:「答对 41 / 50」,不写「82.00%」;百分比只保留整数。
- **带区间**:题数 < 100 时显示 95% 区间(Wilson),并提示「题少,差几题属于正常波动」。ARES 用至少 50 条人工标注做区间校准 —— 我们不做校准,但用区间让人别把 3 题的差当真。
- **对比按逐题翻转**:「变好 5 题、变坏 2 题、不变 43 题」,再用符号检验给一句「差异在噪声范围内 / 不在」(我们内部评测一直这样判,见知识库优化总计划 §3.5)。
- **逐题标判分一致度**:3 票里 3 票一致 / 2 票一致;2 票一致的题标「建议人工看一眼」。
- **判分分歧、判分失败的题单列**,不进任何分母。
- 结果页固定一句说明:「单题判分会有误判,看总数和前后对比更可靠。」

### 5.5 判分

| 项 | P1 | 理由 / 参考 |
|---|---|---|
| 判法 | B-206 尺子 v2:把回答拆成结论,逐条标依据(原文写了 / 标明了的推断 / 标明了的常识 / 不需要出处 / 没标明的推断 / 资料里没有 / 与资料矛盾 / 张冠李戴),再标是不是结论本身;编造由代码按规则算,不靠判分模型整体拍板 | 我们 11-05 实测旧口径同一回答 7 次判 2 次编造;分级参考 Google FACTS Grounding、DeepEval、FActScore / Ragas(B-206 v2 注释) |
| 原文核对 | 判分模型说「原文写了」必须附原文,代码核对在智能体看到的资料里;核对前做文本、表格、数字归一 | §3.3 第 3 条教训 |
| 票数 | 1 票(快速)或 3 票(默认,待拍板 §10 第 4 条) | 3 票仍有约 1 题 / 组误判;5 票费用太高、收益没测过 |
| 判分模型 | P1 平台定一个、经验证的模型;P2 开放在验证过的名单里选(§10 第 2 条) | 判分提示词只在一个模型上验证过;换模型要重新验证一致率 |
| 答题模型 = 判分模型时 | 提示「答题和判分用了同一个模型,可能偏宽」 | Glean 用多模型 jury 降低自评偏差;我们 P1 不做 jury(成本翻倍),只提示 |
| 尺子版本 | 每次运行记下判分规则版本 + 判分模型 + 票数;这三样不同的两次运行不给对比结论 | WeKnora 文档自己承认跨版本不可比 |
| 提示词 | 从 `tools/eval/kb_agent_judge.py` 抽出,**改写成平台文本**:不出现任何行业例子(现在的「不需要出处」例子是健康类免责语)、英文书写、要求判分理由用问题的语言 | 平台文本铁律 |

**人工改判**:每题可改类别并写理由;改判绑定在「这一题的这一个回答」上,复跑时回答没变就沿用。汇总里显示「人工改判 N 题」,改判前后的数都能看。腾讯 ADP、百炼新版、LangSmith 都有人工标注(采纳)。

**反面证据**:句级判分噪声大(§3.3);判分模型对「推断有没有标明」的理解跨模型不一致(B-206 11-05 抖动)。所以判分规则版本必须可追溯,且不承诺单题判分准确。

### 5.6 逐题错因

**按信号用规则判,不调模型**。顺序参考 RAGFlow 的排错顺序,类别参考百炼旧版五类(模型理解有误、重排不佳、检索无效、切片不完整、未获取知识):

| 顺序 | 错因 | 判据(都是已有信号) | 建议查什么 |
|---|---|---|---|
| 1 | 题目本身有问题 | 证据失效;判分分歧;题型和证据矛盾(标了「资料没写」却填了证据) | 改题 |
| 2 | 资料没入库 / 解析坏了 | 证据文档不在可用状态,或片段落不进任何段 | 文档状态、分段预览(解析结果) |
| 3 | 没检索到 | 证据有效,但这题所有检索的结果里都没有含证据的段 | 换问法试命中测试;切块参数;检索方式与分数下限 |
| 4 | 检索到了但没交给模型 | 结果里有,但 `context_hit` = 0(条数或字数预算截掉) | 返回条数、重排分数下限 |
| 5 | 交给了模型却答错 | `context_hit` = 1,且类别是编造 / 答偏 / 误拒 | 模型、提示词 |
| 6 | 资料没写却编造 | 题型 = 资料没写,类别 = 编造 | 模型、提示词;回答规则 |
| — | 无证据,看不出在哪层错 | 可答题没填证据且答错 | 补证据 |

- **改了什么**:百炼旧版用模型给每题归因;我们只用确定的信号,同一份结果每次归因相同。代价是归不到「模型理解有误」这种细类。
- **反面证据**:百炼新版已经不提自动归因。我们的归因只说「在哪一层出的问题」,建议只指向查哪个页面,不承诺自动调优。
- **对五类资料**:都成立。第 2 类(解析坏了)在产品说明书的表格、扫描件上最常见。

### 5.7 运行

#### 5.7.1 执行器:另做,照入库执行器的样子

| | 扩展现有 `EvalWorker` | **另做 `KbEvalRunner`(推荐)** |
|---|---|---|
| 取任务 | 300 秒轮询一次,最长等 5 分钟才开始 | 入队即提交,与入库执行器一样 |
| 并发 | 串行跑完一个套件再下一个 | 有并发上限;一次运行内多题并行(默认 4) |
| 进度 | 跑完一次性写入 | 每题写完即落库,页面看得到 |
| 卡死 | 没有回收 | 租约 + 定期续约,pod 被杀后由别的副本接着跑**没做完的题** |
| 取消 / 继续 | 没有 | 每题开始前查取消标记;「继续」= 只跑没完成的题 |
| 引擎接口 | `run(suite)`,租户靠上下文变量 | 按运行行带租户、题集快照、对象 |
| 改动面 | 要改状态机、表、接口、前端,老的 3 个平台套件还在用它 | 新表、新执行器,不碰平台回归门 |

`KnowledgeIngestionRunner`(`knowledge/ingestion.py:1412`)已在生产上验证了 CAS 认领、租约 300 秒、按 1/3 租约续约、并发上限、代次栅栏(`:14-19,133`),直接照这个做。

#### 5.7.2 状态和控制

- 运行状态:`估算中 → 待确认 → 排队 → 运行中 → 已完成 / 已停止 / 因费用上限停止 / 出错`;待确认 7 天不确认自动作废(同 B-222)。
- **停止**:当前正在跑的题跑完(或到超时)就停;已完成的题保留,汇总按已完成的题算并标「未跑完」。
- **继续**:对已停止的运行再确认一次剩余部分的预估,只跑没完成的题。这就是「暂停 / 继续」(ADP),不另做暂停状态。
- **单题重试**:模型限流、超时、5xx 自动重试最多 2 次;仍失败的题记「运行失败」并写原因,不让整轮失败(WeKnora 的反面)。
- **超时**:答题每题 5 分钟、每次判分 2 分钟(可配置)。
- **每租户并发**:同一租户同时只跑 1 个运行(FastGPT 同样限制),其余排队;平台全局另有上限。理由:测评调真实模型,并发大了会挤占这个租户线上对话的限流额度。

#### 5.7.3 后台调真实智能体答题,怎么不污染线上

| 要求 | 怎么做 | 依据 |
|---|---|---|
| 不进会话列表 | 进程内构建 + `graph.ainvoke`,不调 `POST /v1/sessions` / `runs`,不建 `thread_meta` | `thread_meta` 没有来源字段(`models/thread_meta.py:20-59`),走 run 接口一定进列表 |
| 不写长期记忆 | 调用时不传 `user_id`:记忆召回和写回在没有 `user_id` 时都跳过(`graph_builder/memory.py:16,698-699`) | 代价:开了长期记忆的智能体,测评测不到记忆的作用 —— 结果页注明 |
| 用量单独记 | 用不带缓存的构建 `agent_builder(spec, tenant_id=…, token_usage_kind=<测评类型>)`;**不能走 `get_agent` 缓存**(`runtime.py:542-570` 不收用量类型,会记成 `conversation`);configurable 里必须带 `tenant_id`,否则用量静默不记(§6) | 技能进化回放已这样用(`runtime.py:194-199`);重排等平台调用跟随构建类型(`usage_metering.py:250-256`) |
| 检索记录分开 | 检索记录加来源 `evaluation`(改 `0177` 的 CHECK),检索记录页默认不显示 | 否则测评的几百次检索会冲掉租户看线上检索的视图 |
| 用哪个版本 | 从 `agent_spec` 当前发布版、草稿列或 `agent_spec_revision` 取 spec 构建 | `0072`、`0150` |
| 外部工具 | 构建前从 spec 里去掉外部工具(§5.1) | — |
| 观测 | trace 打上测评标记 | — |

待核:进程内 `ainvoke` 用的检查点存储是否会把测评的 thread 落库、怎么清;知识库工具写检索记录时 `source` 从哪来(§11)。

#### 5.7.4 测评期间知识库变了怎么办

- 运行开始时记下涉及的库里每份文档的 id 和内容版本(入库代次)。
- 运行结束时再取一次;有变化就在结果页顶部标「运行期间资料有变动」,并列出证据文档变了的题。
- **不锁库**:租户随时能上传、删除。ADP 只是「建议别改」;我们把变化记下来,比只建议更有用。
- 开始时库里还有「入库中 / 待确认」的文档:提示「有 N 份文档还没入完,结果不含它们」,不拦。

### 5.8 花费

#### 5.8.1 预估、确认、硬上限

- 沿用 B-222 的规矩:**无论金额多少都要用户确认才开始**;预估本身不调模型。
- **怎么估**(按平台价目表 `model_rate_card`,`knowledge/pricing.py`):
  - 只测检索:题数 × 查询嵌入 token + 题数 × 重排候选数 × 平均段长。
  - 端到端答题:按这个智能体历史上每题平均检索次数(从检索记录取,没有就按 3 次)× 每步输入 token(系统提示 + 工具说明 + 平均每次交给模型的字数)估「预计」,再按智能体自己的步数上限估「最多」。
  - 判分:每票输入 ≈ 问题 + 这题看到的段落 + 回答 + 判分提示词;× 票数。
  - 平台承担的部分(若有)不列给租户(B-222 做法)。
- **确认时显示**:题数、预计金额、**最多金额**;用户确认的是最多金额。
- **硬上限**:执行器每题结束累计实际花费,下一题的预计花费会超过已确认的最多金额就停,状态「因费用上限停止」(百炼「最大值即硬上限」;离线尺子 `BudgetGate` 同理)。
- 百炼是先试跑 1 题再估;我们不试跑,因为历史检索次数已经能给出不错的估计,而且试跑本身要花钱、要再确认一次。

#### 5.8.2 记在谁头上

- 新增用量类型 `kb_evaluation`,答题、重排、判分都记这一种;判分调用在智能体之外,照 `quality_monitor_worker.py:324` 的方式直接写用量行。
- 计费给租户还是平台承担,见 §10 第 1 条。
- 用量页按用途单列「知识库测评」,对外对话用量(只取 `conversation`,`api/_run_usage.py:33`)不受影响。

#### 5.8.3 凭据登记

判分模型用平台凭据,新增 `kb_eval_judge_provider / kb_eval_judge_model` 两个配置,在 `platform_provider_uses.py` 登记一行 `feature="kb_eval_judge"`;自审测试会盯住漏登记。答题用智能体自己的模型,已经算在智能体的引用里。

## 6. 顺带要修:现有 live 评测不记用量(已读代码确认,未真跑)

**结论:属实。** 控制台「评测运行」里 `adversarial` / `trace_eval` 两个套件真实调用模型,却不会写任何 `token_usage` 行,也不进 Prometheus 计数。

- `LiveEvalHarness._run` 调 `graph.ainvoke` 时只传了 `{"configurable": {"thread_id": …}}`(`eval_engine_live.py:262-274`);`tenant_id` 只用来构建(`:265`),没进 configurable。
- 智能体节点从 configurable 取 `tenant_id`(`orchestrator/graph_builder/builder.py:1105-1106`),放进调用前后中间件的 payload(`:1237`、`:1648-1652`)。
- 用量中间件在 `tenant_id` 不是 UUID 时直接返回(`runtime/middleware/token_usage.py:209-212`),计数器和落库都不做。
- 同时 `user_id` 也没传,所以不写记忆这一点是对的。

**修法**:configurable 加上 `tenant_id`;构建时传 `token_usage_kind`(与本功能用同一个测评类型,或单独一个平台回归类型,随 §10 第 1 条一起定)。补一条测试:跑一次 harness 后用量 store 里有行且类型正确;按仓库规矩先把修复改回去确认测试会红。放在 P1 的 PR0,很小,可单独先合。

**顺带发现,不在本次修**(登记即可):

1. `POST /v1/eval-runs` 入队不记审计(`api/eval_runs.py:136-157`)。
2. `eval_run` / `eval_case_result` 不在任何留存清理或彻底删除里(`git grep` 在 `retention-cleanup-job` 与清除代码里零命中)。

## 8. 风险

| 风险 | 后果 | 应对 |
|---|---|---|
| 租户把单题判分当真 | 为一两道误判的题改配置,越改越乱 | §5.4.3 的呈现方式;改判入口;说明文字 |

| 题集太小(< 30 题) | 对比结论几乎都是「在噪声内」 | 显示区间并提示题数;建议每类至少 10 题 |
| 端到端关掉外部工具 | 测的不是线上完全相同的行为 | 结果页写明;§10 第 6 条 |
| 沉淀题带个人信息 | 隐私 | 转题时提示删除;用户清除时连带删 |
| 测评挤占线上限流 | 线上对话变慢或报错 | 每租户同时 1 个运行,运行内并发 4;遇限流退避 |
| 证据锚定在英文或其它语言资料上 | 8 字下限对拼音文字太短,容易「太常见」 | 下限按字符计且在提示里说明;太常见提示会兜住 |
| 会议纪要、合同这类相似文档多的资料 | 证据片段在多份文档里重复,命中算宽 | 证据必须带文档;太常见提示;对比只看同一题 |

## 9. 不做(带理由)

| 不做 | 理由 |
|---|---|
| 像 WeKnora 那样另建临时库测 | 测不到租户真实的切块和文档 |
| 按段落编号标证据 | 重新切块后全部失效(RAGFlow #15033) |
| 1~5 分打分 | 「3 分」和「4 分」说不清差在哪;类别 + 编造原因更能指导改什么 |
| 用模型做错因归类 | 每次结果不同;百炼新版已不提;规则已能分到层 |
| 线上问题自动进题集 | 没证据、没答案的题判不了,只会堆积 |
| 知识同步后自动复测(Dify) | 会自动花钱,违反「用户确认才花钱」;P3 的发布闸门是用户主动设置的 |
| P1 做多模型 jury | 判分成本翻倍,收益没测过 |
| ARES 式置信区间校准 | 要至少 50 条人工标注,租户负担重;先用 Wilson 区间 |
