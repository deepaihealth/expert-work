# B-129 旧的只读查询结果可"再查一次"收起 —— 设计

- 日期:2026-09-29
- 状态:待用户审
- 前置:B-126(跨轮清理,已合 main)、B-128(只留最新系统提示词,已合 main)
- 班车:不赶 10-08;测试环境验收通过后另排

## 1. 要解决的问题

同一段 ai-health-plan 真实 7 轮对话(测试环境重放 `d91e8b61`,49 次模型调用)按类别拆输入 token:

| 组成 | 占输入 |
|---|---|
| **业务系统 MCP 查询结果** | **27%** |
| 工具说明 + 其他注入 | 18% |
| 系统提示词 | 11% |
| 写文件参数 | 11% |
| bash 结果 | 7% |
| 其余 | 26% |

业务系统查询结果(`form_get_latest_field_values` / `form_get_field_detail` / `health_plan_get_customer_plan` / `form_list_by_project` …)在第 1 轮查回来、用来写方案;第 2~7 轮用户说的是"字大一点""饮食改表格""出 PDF",基本用不到这些原始数据,但它们**每次调用都原样重发**。

B-126 已经在新一轮开头把旧结果收成一行引用,但**只收有副本的**(工具调用时 ≥4000 字才存副本);业务系统结果大多 1000~4000 字,没副本,于是一直原样带着。

## 2. 做法

### 2.1 一句话

**能重新查的只读工具**,旧结果在新一轮开头收成一行"调过什么、多少字、需要请再调一次";**不能重跑的**(bash / 执行代码等)保持 B-126 现状 —— 有副本才收。

### 2.2 为什么这样选(与备选的比较)

| 方案 | 做法 | 为什么没选 |
|---|---|---|
| A. 降存副本门槛到约 1000 字 | 小结果也存副本,再按 B-126 收 | 行业没有"给小结果存副本再清"的先例;副本多了会放大 §2.7 的串客户搜索问题 |
| B. 照搬 hermes / openclaw 原样配置 | 按窗口百分比触发 | glm-5.3 窗口 100 万,hermes 50 万 / openclaw 30 万才触发,我们最大 9 万 → 永不触发 |
| **C. 本设计** | 只读工具清成"再查一次",触发时机沿用 B-126 每轮开头 | —— |

C 的依据:Anthropic context editing、JetBrains《The Complexity Trap》(有质量数据:成本降一半以上,解题率不降)、hermes-agent 都是"旧结果清成占位 / 一行摘要,需要时再调工具",**不存副本**。我们与它们的差别只在触发时机(它们等窗口快满,我们每轮开头),这一点 B-126 已上线实测(每轮开头断缓存只 1~2 千 token)。

### 2.3 找回途径的优先级(每条旧结果按顺序取第一个)

1. **已有无损引用**(B-126 现状,不变):技能引用 / 副本路径 / 外置 footer。
2. **再查一次**(本设计新增):工具在"可重新查询名单"里 → 收成再查提示。
3. 都没有 → 不动(bash / exec_python 等无副本的输出维持原样)。

有副本时优先用副本:读文件比再调一次 MCP 便宜,拿到的也是当时的原文。

### 2.4 "可重新查询名单"怎么来

- **内置工具**:`ToolSpec.is_read_only is True` 的(`read_file` / `list_dir` / `search_files` / `read_document` / `read_page` / `skill_view` / `knowledge_search` / `web_search` …)。
- **MCP 工具**:服务器 `list_tools` 标注 `readOnlyHint: true` 的(B-122 已读取这个标注;ai-health-plan 现有的 9 个 MCP 工具全部标了只读(09-27 B-122 验收时 11 个 `kept=11 dropped_write=0`,09-29 删了 2 个))。没标或标 `false` 的一律不算。
- **排除**:只有 `ask_image`(已在 `_NEVER_PRUNE_TOOLS`,看图结论不清,不变)。
- **`web_search` 在名单里**(用户 09-29 拍板):重查拿到的是最新结果,这正是它该有的行为;内置后端是自建 SearXNG,重查不产生费用;要回看之前某条结果对应的网页,历史里留着链接,可直接 `read_page`。初稿曾以"结果会变 + 有费用"排除它,费用一条核实为错。
- **不改 `ToolSpec.is_read_only`**:它还决定失败自动重试(`error_classifier`)与并行调度(`scheduling`),把 MCP 工具标成只读会顺带改这两处行为。名单在构建 Agent 时单独算出来,传给 `ToolResultPruner`。

### 2.5 收起后的样子

沿用 B-126 的 `<tool-result-pruned>` 标签与参数提示(≤120 字),正文换成再查提示,例如:

```
<tool-result-pruned>
[mcp__srv__form_get_latest_field_values] {"customer_code": "…"} — 2,873 chars from an earlier turn, elided.
Read-only lookup: call the same tool again with the same arguments to get the data back (it returns current data, which may have changed since).
</tool-result-pruned>
```

- 文字面向全平台,**不含任何租户 / 客户内容**,英文与现有 stub 一致。
- 调用参数仍完整留在历史里那条 AI 消息上(本设计不动调用参数),模型照抄即可重调。

### 2.6 门槛与保护(除新增一项外全部沿用 B-126)

| 项 | 值 | 来源 |
|---|---|---|
| 何时动手 | 新一轮开头;同一轮内逐字不变 | B-126 |
| 最近几条不动 | 最近 4 条旧结果 | B-126 |
| 上下文太小不动 | < 3 万 token | B-126 |
| 省得太少不动 | 一次合计 < 5000 token | B-126 |
| 失败的结果 | 不动 | B-126 |
| **单条最小长度(新增)** | **500 字** | 提示本身约 200~300 字,更短的收了几乎不省;hermes 用 200,我们取稍保守 |

### 2.7 顺带修:`search_files` 跳过 `.tool_results`

现状问题(与本设计无关,**现在就存在**):员工工作区按"员工 + Agent"分、不按客户分,`.tool_results/` 下是这位员工所有对话的超长结果副本;`search_files` 按内容搜索时会搜进去,给客户 B 做方案时可能搜出客户 A 的数据。

修法:`search_files` 遍历时跳过 `.tool_results` 子树(`name_glob` 与 `content` 两种都跳)。模型拿副本走的是引用里的确切路径 + `read_file`,不经过搜索,不受影响。**先于本设计单独合入**。

`list_dir` 只列一层,根目录会看到 `.tool_results` 这个目录名,不涉及内容,不改。

### 2.8 开关

- Agent 配置 `policies.tool_result_prune.requery: bool`,**默认开**,可按 Agent 关;默认值不落库(存量配置指纹不变,沿用 B-126 `_B126OmitDefaultsMixin` 的做法)。
- `cross_turn: false` 时本功能一并不生效(它是跨轮清理的一部分)。
- 回滚纪律同 B-126:改过默认值的配置旧镜像读不了,回滚镜像前先恢复默认。

### 2.9 观测

- span 属性:`cm.cross_turn.requery_stubbed`(本次收成再查提示的条数)。
- 计数器:`expert_work_cm_requery_stub_total`(按工具名不打标签,避免基数问题)。
- 验收时另从检查点统计"被收起的工具又被重新调用"的次数(不上线为指标)。

## 3. 不做什么

- 不改存副本门槛(`PERSIST_MIN_CHARS` 仍 4000)—— 本设计做完看数据再议。
- 不动调用参数(写文件内容的存根 = 另一件事,证据较弱,排在后面)。
- 不在本轮内清理(断缓存,省的不够补)。
- 不做 LLM 摘要。

## 4. 风险

| 风险 | 表现 | 怎么发现 / 兜住 |
|---|---|---|
| 模型不重查、凭印象写 | 后续轮改方案时数据写错 | 验收专设"要用第 1 轮原始数据"的轮次,核对交付件数字出处 |
| 重查拿到的是新数据 | 与第 1 轮不一致 | 提示里写明"返回当前数据";对方数据本来就会变,方案按最新数据改是合理行为 |
| 重查多了反而更贵 | 多次 MCP 调用 + 结果重新进上下文 | 验收统计重查次数与成本;超出就按 Agent 关掉 |
| 对方 MCP 标注错(写工具标了只读) | 重调产生副作用 | 名单只认 `readOnlyHint: true`;B-122 已依赖同一标注给子智能体放行,风险同源 |
| 强模型反受损(arXiv 2606.00408 倒 U 形) | 质量下降 | 对照重放比交付件 |

## 5. 验收(测试环境,ai-health-plan,glm-5.3)

1. **对照重放**:同一段 7 轮对话,`requery` 开 / 关各跑 **3 次**(单次波动 ±5~10%,一次看不出)。
2. **加一轮"要用原始数据"的追问**(放在第 5 轮后):例如"把第一次查到的空腹血糖历史记录列一下,并据此调整监测频率"。检验模型会不会重查而不是凭印象写。
3. **判据**:
   - 成本:开比关的中位数低(目标 ≥10%);
   - 质量:两组交付件都过技能校验;章节、数字出处比对无退化;追问轮的数字与原始数据一致;
   - 行为:统计重查次数;凭印象写错 = 0;
   - 7 轮全部 success。
4. `search_files` 修复:单测覆盖两种搜索都不返回 `.tool_results/` 下的文件;测试环境造一个含标记字符串的副本,真跑确认搜不到。
