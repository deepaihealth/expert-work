## 0. 一页看懂

**为什么又改**:11-15 评测 A 组在修过的代码(`16ec43eb1`)上重跑,三条线修好了(P1 漏记、P9 新值有效、英文场景写成别的语言),但两条线退了、一条没好:

- P6「助手问、用户只答一个词」、P7「助手说、用户只回『对』」被记成用户回答的,从 29 次掉到 20 / 22 次(线是 ≥ 24)。原因:第二次提炼在 60 个单元里有 18 个**直接返回空列表**,连去重合并都没走到。两种语言都碰到的唯一改动,是 11-14 加进第二次指令的一句否定句「只是印证用户当前说法的查询结果……不再记」—— 模型把助手的「好的,记为 X」「记录显示是 X,对吧?」读成了「已经印证过」,于是连用户那句短回答也不记了。把这句改窄后空列表降到 4 / 60,没有归零。
- A12「同一件事连写 5 轮后的用户一方重复」仍有 3 条(线是 0)。原因:每轮整段重抽,同一件事被换个说法再抽一遍;去重合并只把相似度 ≥ 0.80 的旧记忆拿给模型看,同一件事的不同说法有 25 / 60 轮低于 0.80,直接写成了新的一条。

**这说明什么**:一句一句往第二次指令里加「不要记 X」,每加一句就有新的地方被误伤(原设计第 5、6、7 版加句、11-14 又加两次)。别家不这么做:「记不记、记成谁说的」交给结构和程序,「是不是重复」交给去重合并(§1.2)。

**改什么**(用户 11-15 拍板,做法是本文定的):

| # | 改动 | 程序保证的 | 只靠模型的 |
|---|---|---|---|
| ① | 第二次提炼只做两件正向的事:记助手做了 / 得出 / 提出了什么;记用户对助手上一句的短回答、同意或否定。删掉全部「不要记 X」。输入每行带编号;每条产出带 `basis`(助手 / 用户回答 / 用户同意)和 `turn`(依据的那一行) | `turn` 指的那一行是不是用户输入、是不是紧跟在助手一句之后;对不上就降成「来自助手」 | 用户那一行是不是真在回答 / 同意(§5.4) |
| ② | 来源加第三个值 `user_confirmed`(用户确认):第二次提炼里核对通过的短回答 / 同意。算用户一方,受保护;置信度封顶 0.8 | 值由程序写;各道防线怎么对待它(§6) | 无 |
| ③ | 去重合并:不要 0.80 门槛,每条候选取最近 5 条给模型;材料带类型、日期;跨类型、跨智能体经历的更新 / 删除拒绝、改为新增;带日期的一次性事件只新增;判「重复」时刷新确认日期(只在用户一方的候选碰到用户一方的记忆时);两次提炼的产出分两段合并,第一次的先写 | 门槛、条数、拒绝、只新增、刷新条件 | 「是不是同一件事」 |
| ④ | 每条记忆存证据指针:来源对话里的第几条消息(消息 id + 序号)和事件日期 | 指针由程序从 `turn` 换算 | 模型给的 `turn` 准不准 |
| ⑤ | 增量切片(B-176 M2-1):每次写回只提炼上次写回之后的新消息,前面几行作上下文;每个对话一个水位 | 切到哪、上下文给几行 | 无 |

**保留不变**(§2):第一次提炼只看用户输入的文字;来源由程序定;来自助手的置信度封顶 0.6;语言判断;双时间轴存储;密码等不记;每行带发送日期;白名单;召回提醒的结构;没有总开关、出问题回滚镜像。

**不做**:不把已有记忆拿给提炼模型看(B-176 M2-2 的「预取进提炼」,理由 §8.5);不追溯修改存量记忆(老行一律不动);不清理被重新生成取代的那一轮留下的记忆(现状如此,§8.4)。

**工作量**:五个 PR,约 13.5~18.5 人天,另加测试环境验收与付费评测的日历时间(§12)。

## 3. 新的写回一次怎么走

```
本轮结束 → 落写回任务(现状不变)
  ↓ 后台 worker 领到任务
① 读这个对话的水位(上次写回处理到哪条消息)
② 切片:水位之后的新消息;另取水位之前几行作上下文(§8.2)
③ 两次提炼并发(各自一份带编号的输入):
     第一次:用户输入的文字 → 产出一律 user_stated
     第二次:对话(用户的话、助手最终回答、调用过的工具、附件计数)→ 程序核对每条的 basis + turn
             → user_confirmed(核对通过的用户回答 / 同意)或 assistant_derived
④ 证据指针:turn → 那一行对应的消息 id + 序号;事件日期按程序校验后留下
⑤ 去重合并 · 第一段:第一次的产出(每条取最近 5 条已有记忆,一次模型调用)→ 落库
⑥ 去重合并 · 第二段:第二次的产出(这时第一段刚写的也在已有记忆里)→ 落库
⑦ 推进水位(两次提炼的调用都成功才推进;§8.2)
```

和现在比:① ② ⑦ 是新的(切片);③ 的第二次换了指令、多了核对;④ 是新的;⑤ ⑥ 从「一段、带 0.80 门槛、最近 3 条」改成「两段、无门槛、最近 5 条」。

| 改什么 | 为什么 | 先例 |

| 每行前加编号 `[n]`;有发送日期的在编号后写 `[YYYY-MM-DD]` | 证据指针要知道依据哪一行 | OpenViking 的 `[idx][role][speaker]` 行格式(`session_extract_context_provider.py:355-361`) |

## 5. 第二次提炼(整段对话):只做正向的事

### 5.1 给什么(输入)

行的种类与现在相同(原设计 §4.1 表),只改格式:

```
[1] [user] [2026-03-02] 帮我看看下周去成都的机票
[2] [assistant] [2026-03-02] 3 月 9 日上午有两班直飞……回程想订哪天?
=== new ===
[3] [user] [2026-03-02] 18号
[4] [activity] tools called this turn: flight_search ×1
[5] [assistant] [2026-03-02] ……
```

- 编号从 1 起、连续,上下文行和新行一起编;`=== new ===` 之上是上下文(§8.2)。
- `[user]`、`[assistant]` 行在标签后带发送日期:用户行用白名单标记里的 `sent_at`,没有就用 `expert_work_created_at`(同 `memory.py:280-299` 的取法);助手行用助手消息的 `expert_work_created_at`。都没有就不带。
- `[task]`、`[attached data]`、`[activity]` 不带日期。
- 工具结果、助手中间消息、思考段、附件内容照旧不给。

### 5.2 要什么(输出)

```json
{"memories": [{"kind": "fact" | "episodic", "content": "...",
  "basis": "assistant" | "user_answer" | "user_agreement", "turn": <行号>,
  "event_date": "YYYY-MM-DD" | null, "importance": 0-1, "confidence": 0-1,
  "expected_valid_days": <int> | null, "is_correction": <bool>}]}
```

`basis` 只有三种:

| `basis` | 意思 | `turn` 应指向 |
|---|---|---|
| `assistant` | 助手做了、产出了、查到、得出、提出了什么 | 说这件事的那条 `[assistant]` 行 |
| `user_answer` | 用户对助手上一句提问的短回答 | 那条 `[user]` 行 |
| `user_agreement` | 用户对助手上一句提议 / 查到的内容表示同意或否定 | 那条 `[user]` 行 |

### 5.3 指令

全文(含 8 个例子)在附录 A。要点:

- **只说要记什么**,不说不要记什么。原来那几句「单独读得懂的 [user] 行不再记」「只是印证用户说法的查询结果不再记」「被用户否掉的结论不单独记」「助手只是复述记录 / 记忆时不再记」全部删掉。重复交给去重合并(§7)。
- **用户一方的短回答**:把 `[user]` 行和它正上方的 `[assistant]` 行合起来读,写出两行一起定下来的完整事实,像用户自己会说的那样写,保留用户自己的犹豫。
- **助手一方的**:内容里说清是助手查到 / 判断 / 提议的,并保留助手自己的保留措辞(「大约」「看起来」「可能」)。**不给英文句式模板**(原指令里的「the assistant found ...」「asked by the assistant, the user answered ...」删掉,调研笔记 C 节推断它们可能把记忆拉成英文);怎么说由例子示范,例子用中、英、西三种语言写,内容跟着对话的语言走。
- **更正**:回复改掉或否掉前面说过的,`is_correction` 为真,内容里写出原来是什么、现在是什么(mem0 V3「从 X 换成 Y」)。
- **事件日期**:只给「某一天发生或观测到的一次性值」(一次读数、一笔已付的款、一次计数),按那一行的日期换算「今天」「今天早上」「昨天」;计划、安排、偏好、状态都给 `null`。
- **例子代替规则**:8 个「输入 → 输出 → 一句为什么」,覆盖调研给出的 8 种情形(§5.5)。

### 5.4 程序怎么核对(决定来源)

| 模型给的 | 程序核对 | 通过 → | 不通过 → |
|---|---|---|---|
| `basis` = `user_answer` / `user_agreement` | ① `turn` 是新段里的一行;② 那一行是 `[user]`(白名单里用户输入的文字,`[task]` 不算);③ 它的**上一行**是 `[assistant]`(可以是上下文行,问题常在上一轮末尾) | 来源 `user_confirmed`,置信度压到 0.8 以内;证据指针 = 那条用户消息 | 来源 `assistant_derived`,置信度压到 0.6 以内;证据指针:`turn` 指向新段里的某一行就取那一行,否则留空;计数「用户回答降级」并带原因(不是用户行 / 上一行不是助手 / 在上下文里 / 越界) |
| `basis` = `assistant`,或缺失、不认识 | `turn` 是新段里的一行 → 证据指针取它 | 来源 `assistant_derived`,≤ 0.6 | 同左,指针留空 |
| `event_date` | 能解析成日期,且不晚于 `turn` 那一行的发送日期(观测到的事不会在将来;那一行没有日期时只查格式) | 存下 | 置空,计数 |

**程序保证的与不保证的,照实写**:被标成「用户确认」的,一定是紧跟在助手一句之后、用户在对话里亲手输入的那一行。**那一行是不是真在回答 / 同意助手那一句,程序不知道** —— 例如助手说「看起来是真菌引起的」,用户接着问「那浇水呢?」,模型若硬说这是同意,结构核对照样会过。这一种误标只能靠评测量(§11.2 的 S5 条件),线不过时的退路见 §15 第 6 条。这和 AuthMem 的结论一致:来源判定离不开模型,能做的是把它存成字段、单独量。

**和原设计的保证比**:`user_stated` 的保证不变(第一次看不到助手的话);新多出来的 `user_confirmed` 是一个**比 `user_stated` 弱、比 `assistant_derived` 强**的保证,所以它的置信度上限、在「完全相同」比较里的强弱都排在两者之间(§6)。

## 6. 第三个来源值「用户确认」(`user_confirmed`)

### 6.1 为什么要它(推翻原设计 §6.5)

原设计 §6.5 说「第三个来源值:无剩余风险,置信度 1.0 已表达更正」。11-15 的数据和调研说明这不成立:

1. **问答式智能体里,用户的大多数回答都是短回答**(原设计 §6.2 自己写过)。它们被一律记成「来自助手」,召回时与助手自己的推断是同一个标签、同一条提醒(「不是独立证据」)。用户亲口确认的事被当成助手的猜测,方向错了。
2. **AuthMem-Bench 把「证据从哪来」和「谁授权」分开标**:用户对「记录显示 X 吧?」回答「对」,证据来自工具,授权来自用户。「来自助手」只表达了前一半。存下来源标签后越权操作从 16.9% 降到 0.0% —— 前提是标签分得出「用户授权」。
3. P6 / P7 的线本来就是「记成用户回答 / 同意的」,现在只能靠判官读内容里的出处句判断;有了字段,这条线由程序读字段即可(§11.4)。

### 6.2 定义

| 值 | 谁写 | 含义 |
|---|---|---|
| `user_stated` | 第一次提炼;或用户本人在控制台改写自己那一条 | 只看用户输入的文字就读得出来 |
| **`user_confirmed`(新)** | 第二次提炼,`basis` 为用户回答 / 同意且结构核对通过(§5.4) | 用户对助手上一句的短回答、同意或否定;内容是模型把两行合起来写的 |
| `assistant_derived` | 第二次提炼的其它产出(含核对不过而降级的) | 助手做的、得出的、提出的 |
| 空 | 存量、失败重试重建的、汇总里不全是来自助手的、别人改写过的 | 未记录 |

「用户更正」仍不是一个列值,沿用置信度 1.0(更正接口独占)。有效来源函数(`packages/expert-work-protocol/src/expert_work/protocol/memory_item.py:210-223`)的顺序:置信度 ≥ 1.0 → 用户更正;否则 `user_stated` → `user_confirmed` → `assistant_derived` → 未记录。

**置信度上限 0.8**(本文安排,**待用户确认**,§15 第 1 条):

- 不给 0.99:内容是模型把两行拼出来的,程序只证明了「结构上是在回话」(§5.4);AuthMem 的专门判定器仍有 0.6% 危险升格;Manufactured Confidence 提醒别给它额外的笃定。
- 不给 0.6:那就和来自助手没区别了,第二条拦截规则(§6.3 第 2 行)也就不再区分两者。
- 0.8 的后果:置信度不参与排序(原设计 §1 #13),它只在两处起作用 —— 管理页显示,和「用户一方候选只能改置信度不高于它的用户一方记忆」这条规则。所以一条「用户确认」的短更正**改不动**一条置信度 0.9 的「用户消息里说的」,而是与它并存(就是今天 P9 的做法,P9 线是过的),召回提醒第三条让晚的那条不被早的压过。若用户希望短更正直接取代,把上限提到 0.99 即可,其余不变。

### 6.3 每一道现有防线怎么对待它

| 防线 | 现在 | `user_confirmed` 怎么处理 | 改在哪 |
|---|---|---|---|
| 第一条拦截规则:来自助手的候选不得更新 / 删除用户一方的记忆 | 用户一方 = `{user_stated, user_corrected}`(`base.py:31`) | **算用户一方,受保护**:来自助手的候选改不动它。这正是 B-300 要防的(助手下次再得出同样内容时不能覆盖用户确认过的) | `USER_SIDE_ORIGINS` 加入它;`supersede` / `expire` 锁里的重判自动跟着变 |

| 6 | 「重复」不带目标 | 「重复」要带目标;**只有用户一方的候选判成与用户一方的记忆重复时**,程序把那条记忆的确认日期刷新为这次的消息日期 | OpenViking 画像「(截至某日)」再次确认时刷新。**出入**:来自助手的候选判成重复时什么都不刷新 —— 否则正是 B-300 要防的「助手再得出一次就算又印证一次」 |
| 7 | 一段:两次提炼的产出合在一批里,批内互不比较 | **两段**:先合并、写入第一次的产出;再合并第二次的产出,这时第一段刚写的已经在库里,能被取成邻居 | 第二次不再被告诫「别记用户说的」,它会把用户说的再抽一遍(例子 5 正是如此),必须能与第一次的产出比到。代价:每次写回最多两次合并调用(§7.5) |

### 7.2 不变的

确定性「重复」(先于模型,`:1467-1472`);两条拦截规则与被拦后的处理;带更正又与已有记忆相同的候选永远不落新行(`_redundant_correction_op`,`:1399-1407`);所有失败路径退回直接写入(宁可重复不丢);「更新」走 `supersede`(双时间轴)。

### 7.3 判定之后程序怎么落

| 模型判 | 程序 |
|---|---|
| 重复(带目标) | 不写候选;候选与目标都是用户一方 → 刷新目标的确认日期;其余什么都不做 |
| 更新 | 先查格、事件日期、两条拦截规则;都过 → `supersede`,新行带候选的来源、证据指针、事件日期;任一不过 → 按上表改为新增或走被拦处理 |
| 删除 | 同上先查;过 → `expire`;带更正的候选照旧存下(现状) |
| 新增 / 没给 / 编号不认识 | 写候选 |

### 7.4 带日期的一次性事件:只新增的边界

- **谁算**:提炼给了合法事件日期的(§5.4)。计划、安排、状态、偏好没有事件日期,照常可被更新。
- **同一天的更正**:用户说「今天早上是 7.4,刚才说错了」—— 新值作为新的一条存下,与原值并存,召回提醒第三条让晚的不被早的压过。这是「只新增」的代价,用户 11-15 已选;评测量它(§11.3)。
- **汇总行**:事件日期为空(本文安排),所以照常可被更新。

### 7.5 成本

- 合并调用次数:现在 0~1 次 / 写回(11-15 评测里 25 / 60 轮因为低于 0.80 根本没调);改后一段一次,最多 2 次。调研估算每次约 ¥0.0006(`glm-5.3-flash`)。
- 每次调用的输入:每条候选最多 5 条邻居,比现在多约 2 条。
- 第二次提炼的指令从约 740 token 变成约 2,600(例子占大头;`o200k_base` 估算)。按 `glm-5.3-flash` 输入价 0.8 元 / 百万 token,每次写回多约 ¥0.0015,不命中缓存时也是这个量级。
- 生产按原设计 §12 ⑥ 的量(有写回的日子平均每天 10.9 次)粗算:合并调用每天多约 ¥0.01,第二次指令变长每天多约 ¥0.016,合计每天多约 ¥0.02~0.04。这是估算,PR 上测试后按实测重算。另一头,切片让提炼的对话部分不再随对话长度增长(§8),多轮对话的总花费多半比现在低。

## 8. 增量切片(B-176 M2-1)与预取(M2-2)

### 8.1 水位存在哪

一张新的小表 `memory_extraction_watermark`(本文安排),每个对话一行:租户 id、用户 id、对话 id(主键之一)、处理到的最后一条消息的 id 与序号、更新时间。带 `tenant_id` 与 RLS 策略,进 RLS 覆盖测试;删用户、删对话(写回任务已有 `delete_for_thread`)、删租户时一并清掉。

**为什么不照 B-176 计划放在写回任务表上**(计划 M2-1 写的是任务行加 `from_message_index`):① 做完的任务行满 30 天会被清掉(迁移 `0162`),之后再续聊的对话就找不到水位;② 后台写回之外还有退回本轮内写回的路径(`memory.py:2344-2360`),两条路要读写同一个水位。这是对计划的出入。

### 8.2 一次写回切哪些消息

1. 读本轮结束时的对话(现状)。在里面找水位那条消息的 id。
2. **新段** = 水位之后的全部消息。**上下文** = 新段之前的若干行:第二次给最近 4 行,不够 4 行时往前补到至少含一条 `[assistant]`;第一次给最近 2 条用户输入(本文安排;先例:Graphiti 前 4 条消息、mem0 V3 最近 10 条)。上下文行编号、放在 `=== new ===` 之上。
3. 新段照旧按轮切(`_segments`):系统消息、隐藏消息、被取代的、草稿轮都不进。
4. 新段的行超过每次提炼的总量上限(32,000 字,`memory.py:173`)时,**按整轮切成几块**依次提炼,每块带自己的上下文。现在超了是从最早的丢起(D3);切片后水位一推过去就再也读不到被丢的那段,所以改成分块。单独一轮不会超:一轮最多一条用户输入、一条最终回答,各截到 1,000 字。
5. 两次提炼的调用都返回了(不论有没有产出、能不能解析)且写入结束(写成或交给失败队列),才把水位推到这次读到的最后一条消息。任何一次调用出错 → 不推,下一次写回重读这一段,重复的由去重合并挡住。
6. 推水位用「比较后设置」:只有表里仍是本次开始时读到的那个值才改。后台写回本来就按用户串行(`writeback_job.py` 的 `claim_next` 在同一用户上排队),冲突只会来自本轮内写回;输了的一方只记计数。

### 8.3 与两次提炼、日期的关系

| 问题 | 怎么处理 |
|---|---|
| 两次提炼用同一个切片吗 | 用同一个新段;上下文各取各的(第一次只取用户输入,保持「只看用户的字」) |
| 短回答的问题在上一轮 | 第二次的上下文保证至少含一条 `[assistant]`,所以「18 号」上方总有那句「回程想订哪天?」;核对规则允许上一行是上下文行(§5.4) |
| 语言判断 | 不再只看喂给第一次的那几行,改为看**整段对话里用户输入的文字**(程序侧计数,不进提示词);否则新段只有一句「18 号」时不足 20 字、判不出语言 |
| 发送日期 | 每行自己的日期(§5.1),与切到哪无关;相对日期照旧按那一行的日期换算。切片后同一行只读一次,「每轮重读、按重读那天换算」的老问题(原设计审查 MEDIUM-1/2)在结构上也消失了 |
| 事件日期 | 由模型按那一行的日期换算,程序校验不晚于那一行(§5.4) |

### 8.4 草稿、重新生成、续跑

| 情形 | 切片后 |
|---|---|
| 草稿运行 | 不落写回任务(D7,现状)。草稿那一轮留在对话里;下一次线上写回的新段包含它,但它整轮被 `_segments` 跳过(用户消息上的服务端草稿标记,`memory.py:391-393`)。水位照常推过它 |
| 重新生成 / 编辑重发 | 旧轮的消息原地打「已取代」标记,id 与序号都保留(`packages/expert-work-common/src/expert_work/common/supersede.py`);新轮追加在后。水位那条消息即使被取代也还在列表里,找得到。新轮在水位之后 → 被提炼;被取代的照旧跳过。重新生成时用户消息换了新 id 但保留白名单标记(含原来的 `sent_at`,`control_plane/api/runs.py:655-700`),所以日期仍是原来那天 |
| 被取代那一轮已经写下的记忆 | 不清理,与现状相同。证据指针让以后可以按「指向已取代消息」找出它们,本项不做(§15 第 9 条) |
| 审批暂停后续跑、孤儿接管 | 写回只在 `END` 落任务;续跑 / 接管的 run 结束时落一个任务,新段覆盖整轮(含暂停前的部分)。同一指针的重复任务由唯一索引挡住(`0163`);万一两个任务都跑了,后一个的新段为空,不调模型 |
| 澄清问答落在工具消息里 | 两次都看不到(原设计 §4.3,不变) |
| 退回本轮内写回 | 用 `state["messages"]` 加同一张水位表,同一套切法 |
| 压缩前抢存 | **不再提炼**(本文安排,**待用户确认**,§15 第 2 条):压缩只改当次提示词,检查点里的消息不变(原设计 §1 #8),轮末写回的新段本来就包含被折掉的中段;抢存直写不走去重合并(CM-H3),切片后它只会制造重复。改成直接返回 0、记一次计数。这也就消掉了 B-176 M2-1 要消的「抢存与后台写回并发」窗口,不用另建共享队列 |

### 8.5 B-176 M2-2「预取」做到哪

计划 M2-2 写的是「用本轮新消息检索同作用域 top 10,作为『已有记忆』给抽取模型;预取与比对合并为一次调用」。**本文只做一半**:

- **做**:「已有记忆」进的是去重合并 —— 每条候选取最近 5 条(§7.1)。B-176 设计 §6.3 ① 要求的「切片抽出的条目必须经预取与比对并入已有同主题记录」由此满足。
- **不做**:把已有记忆拿给提炼模型看,以及把提炼与去重合并合成一次调用(mem0 V3 的做法)。理由三条:① AuthMem 显示把记忆与新内容放在同一次调用里整理,49 个组合有 48 个抹掉来源;② Graphiti 一件事一个提示词;③ **我们自己的 11-15 数据**:第二次一被告知「哪些已经记过」,就把用户的短回答也当成记过、返回空列表 —— 给它看已有记忆是同一类风险。
- M2-2 其余部分(补丁式更新、计数累加、`about` 归类、有效期分档)仍在 B-176 步 6 / 步 4,不在本项。

计划把 G13(超长消息按句切块)和 D11 前半(取代时加行锁)也挂在 M2-1 上。本文**不带**它们(§15 第 4 条):G13 与切片互不依赖;D11 要防的并发写者里,抢存不再提炼之后只剩极少的「本轮内写回 × 后台写回」。

### 8.6 发版那一刻正在进行的对话

| 情形 | 处理 |
|---|---|
| 对话还没有水位(发版前开始的全部对话) | 第一次写回只取**最后一轮**作新段(从最后一条开轮的用户消息起),前面按 §8.2 取上下文。理由:旧代码每一轮都整段重抽过,前面的内容都已处理;再整段过一遍新指令等于一次回填,与「存量不动」相悖,还会集中产出一批标签不同的重复 |
| 发版前落下、发版后才被处理的任务 | 同上 |
| 滚动发布期间新旧副本并存 | 旧副本照旧整段重抽、不读不写水位;新副本按水位切。两边处理过的同一段会各写一遍,由去重合并挡住。旧副本写下的记忆没有证据指针、没有用户确认 |
| 回滚后再发 | 水位停在回滚前;再发后第一次写回的新段会跨过旧镜像处理过的几轮,按 §8.2 第 4 步分块,重复由去重合并挡住 |
| 水位那条消息找不到(不应发生) | 按「没有水位」处理,只取最后一轮,记一次计数 |

### 11.2 S 组:同一件事,只换来源条件(新增,写入侧)

照 AuthMem 的成对设计:同一个命题,只改「它是怎么进到对话里的」,其余不变。

| 条件 | 对话里发生了什么 | 期望 |
|---|---|---|
| S1 | 用户自己说全了 | 存下,`user_stated` |
| S2 | 助手提问,用户只答一个值 | 存下,`user_confirmed` |
| S3 | 助手提议,用户回「好」 | 存下,`user_confirmed` |
| S4 | 助手说「记录显示是 X,对吧?」,用户回「对」 | 存下,`user_confirmed` |
| S5 | 助手从工具 / 附件 / 推断得出 X 并说出来,用户接着说了一句无关的话 | 存下,`assistant_derived`;**不得**是用户一方 |
| S6 | X 只在工具结果里,助手的回答没提 | 不存 |

规模(本文安排,**待用户确认**):10 个命题 × 6 个条件 × 3 次 = 180 个单元。10 个命题按 5 个领域各 2 个分,内容形态轮换(数字、人名、编号 / 型号、日期、结论性短语、状态),每种至少出现一次。领域与内容不得取自平台提示词里的例子。

**每个条件算四个数**(逐条件、逐领域):

| 指标 | 定义 |
|---|---|

| 空列表率 | 新段里有可记内容时,第二次返回空列表的次数 |

另报(不设线):降级次数与原因(§5.4)、证据指针为空的次数。

### 11.8 判官被预留卡住的问题,和怎么避

**现象**(11-15 实验分支):花费守卫在每次调用**发出前**按这次调用的**最坏花费**预留(`tools/eval/b300_spend.py` 的 `reserve`,判线 = 已结算 + 在飞的预留 + 这一笔的上限)。判官并发 4 路,4 笔最坏预留同时在飞;报价的止损线本来就小,剩下的额度装不下 4 笔最坏值,守卫就停了 —— 实际花的钱远小于预留。

**避法**(做在评测 PR 里,本文安排):

1. 报价时把「并发数 × 单次最坏花费」算成必须留的余量:止损线低于「预计花费 + 余量」就在报价阶段直接说出来,不要跑到一半才停。
2. 判官的并发数随剩余额度自动收缩:剩余装不下 N 笔最坏值时,等在飞的结算后再发,而不是停下整个报价。
3. 判官单独一段子预算(守卫已支持按段分预算),不与写回、对话抢同一份余量。
4. 判官的输出上限按实际需要设(判词很短;现在按 800 token 估最坏值,`b300_plan.py` 的 `CALL_TOKENS["judge"]`),单次最坏值随之变小。

另:分支 `fix/b300-eval-judge-wording` 上的判官措辞修正(未开 PR)要先合进 main,本项的评测在它之上做。
