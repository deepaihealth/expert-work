## 0. 一页看懂

**出了什么事**:用户上传一张体重秤液晶屏照片(4032×3024,画面顺时针横了 90 度,照片不带方向标记),实际 69.1。看图工具整张快看读成 0.0;`region="auto"` 把图切成横条,横条把躺着的数字拦腰切开,退回整张读成 68.1;工具给了「建议再看这个区域」,但没有任何一方真的去看。

**根因一句话**:平台只按照片自带的方向标记转正,没有标记就原样给模型;而看图模型**能看出**图是横的,却**读不对**横着的数字。

**改四件事**(前三件在看图工具里,原图不动;第四件不调付费模型):

| 序 | 改什么 | 程序保证的 | 靠模型的 | PR |
|---|---|---|---|---|
| ① 先问方向 | 看图前先问看图模型一句「主要文字 / 显示屏是正的吗」;说不正,就把图转 90 / 180 / 270 度各问一次,用它说「正」的那一张来读 | 转图、选哪张、缓存、记进轨迹、每张图最多多 4 次调用 | 「正不正」的回答(实测两家各 28/28) | 1 |
| ② 如实说 | 转过图、判不出方向、两次读数对不上 —— 都在工具结果里写明 | 什么时候写、写什么 | 主模型看到后是否照做 | 1、3 |
| ③ 自己重看 | 横条报「被切开」时,工具自己把那一段裁出来再看一次,不再只留一句建议;两次一致也**仍标不确定** | 重看这个动作 | 重看读得对不对 | 3 |
| ④ 文档页 | 知识库入库的扫描页、对话里的文档页:用方向分类小模型,把握 ≥ 0.9 才转(§7) | 转不转、转多少、记下来 | 小模型的判断(文档上实测 100%) | 4、5 |

按看图模型逐个开:只有实测「能答对正不正」的模型才开(§6);答不了的模型(例如 glm-4.6v,永远答「正」)保持今天的行为。

**做完之后还剩什么**(详见 §8):

1. **淡笔段读错不修**。屏幕上没点亮的淡笔段是另一个独立原因(豆包把 72.4 读成 2.4,图是正的),转正帮不上。
2. **主模型自己能看图的智能体不覆盖**(测试环境 14 个):图不经过看图工具。
3. **已经入库的横置扫描件不会自动变好**:要重新入库才生效,转过的页要重新识别(§7.5)。
4. **豆包 260628 版本没测过**:测试环境 31 个走看图工具的智能体里 30 个用它;实测的是 260915。在 260628 过线、或这 30 个智能体换型号之前,本设计在测试环境**只覆盖 1/31**(事故那个)。
5. 「读到健康数值先跟用户确认再记录」不是平台行为,由各智能体自己的提示词负责(§12)。

## 3. 已定的方向与本文的收窄

用户已同意:(a) 文档 / 扫描件用方向分类小模型,把握 ≥ 0.9 才动;(b) 其它照片问看图模型「正不正」,不正就试几个方向,按模型逐个开;(c) 工具自己重看它建议的区域;(d) 工具结果如实写不确定;(e) 转了多少度记进轨迹。「先跟用户确认再记录」归各智能体提示词,平台不改已有智能体。

本文在这个范围内做了三处收窄,理由是「先修量到的问题」:

1. **在看图工具里做,不在上传时做**。上传时没有 run、不知道是哪个智能体的看图模型,轨迹也无处可记;更要紧的是在上传时转 = 改掉用户的原图,模型判错一次,之后每次看都是错的。工具里做只生成一张转正的副本,原图不动,判错了影响限于这一次 run。代价:主模型自己看图的那条路覆盖不到(§8.1)。这是最大的一个取舍,用户已定在工具里做。
2. **按来源分流,不猜图的类型**。用户上传的图、工作区里的图片文件 → 走 (b)。平台渲染出来的文档页、知识库扫描页 → 才是 (a) 的对象。不做「先判断这张上传图是文档还是照片」:小模型在自然照片上误转 22.6%,猜错类型的代价太高。
3. **(a) 本批就做**(用户 11-11 定,§7)。我原先建议先数再立项;「数」保留为不花钱的第 0 步,用来定验收集和报告收益,不再是立项门槛。

## 4. 设计

### 4.1 先问方向(PR 1)

**对谁做**:`ask_image` 看的**上传图**和**工作区图片文件**。不做的:文档页(`path` + `unit`,平台自己渲的)、已经是裁图的引用、看图模型没开这项能力的(§6)、没接工作区的构建(副本没地方放 —— 与今天 `region` 的前提相同,`vision.py:946-953`)。

**流程**(每张图每次 run 只做一次):

```
1. 出一张「0 度候选」:整张图缩到约 150 万像素的副本;图片自带方向标记的先按标记转正。
   问它:「主要文字或显示屏是正的吗?」
   - yes / none(图里没有文字或显示屏)→ 结论「正」,和今天一样往下走。
   - no → 第 2 步。
   - 答非所问 / 调用失败 / 超时 → 结论「没问成」:按 0 度往下走,只记轨迹,不对主模型说什么。
2. 在 0 度候选上顺时针转 90 / 180 / 270 度,三张副本并行各问一次同一句话。
   - 三次都答成了,且恰好一张答 yes → 结论「已转 N 度」。
   - 其余一切情况(没有 yes、不止一张 yes、任何一次超时 / 失败 / 答非所问)
     → 结论「判不出」:按 0 度读,结果里如实写(§4.3)。不采纳部分结果。
3. 结论(含「没问成」)写进缓存文件。这次 run 里之后对这张图的每一次看
   (整张、横条、指定区域)都按缓存的角度做 —— 同一次 run 里坐标系不会中途变。
```

**问的那句话**(平台英文,通用;第 0 步先测,§9.0):

> Look only at orientation. Is the main text or numeric display in this image upright, that is, readable without turning the image? Answer with exactly one word: yes, no, or none (there is no text or display).

解析:去掉思考标签、markdown 符号和标点,转小写,取第一个词;不是这三个词之一就算「答非所问」,次数进计数器。已测过的问法只有 yes / no、只说「显示屏」;放宽到「文字或显示屏」并加 `none` 是没测过的改动,所以排在开工前先测。

**怎么转**:不新写旋转代码。裁图函数本来就能「按一个方向值把裁下来的块转正」(`region_zoom.py:347-362`,为方向标记写的);给它加一个「再顺时针转多少度」的入参,与图片自带的标记合成一个方向值。于是:

- 候选副本 = 对整张图(框 `[0,0,1000,1000]`)带角度裁一次,自动缩到约 150 万像素(`region_zoom.py:380-396`)。
- 结论是「正」且图片没有方向标记(上传图都没有,上传时已去掉):整张看仍把原图交给模型,**与今天逐字节相同**。其余情况(转过,或带标记)整张看用对应的候选副本 —— 分辨率比原图低,由 §9.2 的小字横图检验。
- 横条和指定区域照旧从**原像素**裁,坐标换算到转正后的画面;横条规划用转正后的宽高(事故那张转正后 3024×4032,按 §1.3 #10 是 8 条,数字横排)。

要改的调用点是数出来的:把原图引用直接交给模型的 4 处(`vision.py:452,548,574,672`)、读尺寸 1 处(`:713`)、宿主裁图 1 处(`:793-813`)。

**文件与缓存**:都在本次 run 的裁图目录 `.tool_results/<run>/crops/<原图哈希>/` 下(`vision.py:794-801`)。今天裁图文件名只由框决定、已存在就复用(`vision.py:802,811-812`),不同角度会撞名 —— 所以转过的裁图和候选副本放进子目录 `r<角度>/`,0 度沿用现有位置。缓存文件记结论、角度、四个回答。并行的两次 `ask_image` 看同一张图时排队,沿用现有目录锁(`vision.py:809`)。只在一次 run 内有效,跨 run 重问。

**能力怎么传**:工具上加一个布尔字段,装配处(`tools/assembly.py:557`)按「模型目录能力位 且 总开关」填。评测脚本直接构造工具、把这个字段设为真,不依赖发布出去的镜像里目录怎么写(§10)。

**调用路线、限时、计费**:问方向固定走快看那条链,被厂商拒时**不**再走「退回正常看图」的二次路由(`vision.py:866-876`)—— 拒了就算没问成。每次限时 30 秒(普通快看测试环境 30 天最长 28 秒,`vision.py:143-144`),超时算没问成;**看图绝不因为问方向而失败**。每次调用照常扣 token 池、记账(`vision.py:516-523`),并占切块调用的名额(`vision.py:182`)。

### 4.2 工具自己重看(PR 3,最后做)

只管一种情况:`region="auto"` 里有横条报 `partial`。今天是退回整张读并留一句建议(§1.3 #11、#12);改成工具把报 `partial` 的那几条的并集框裁出来,用原问题再快看**一次**,然后:

- 两次读数一致 → 仍给整张读的值,**保留「小字可能不可靠」的不确定措辞**,只把「请用这个区域再问一次」换成「已重看过接缝,同值」。不把「一致」说成「可信」:实测同一模型对同一张横图两次都是 68.1,裁出显示屏也不解决横置(§2)。
- 不一致,或重看没读到 → 两个读数都列出,明说不确定。**不投票、不挑一个**(与现有横条汇总的原则相同,`tile_reading.py:11-13`)。

作用只有一个:省掉主模型「再问一次」那一轮,并且保证真的有人看过。横条之间「冲突」没有单一区域可看,保持今天的报告方式。每次 `auto` 最多多 1 次调用。它对所有看图模型生效(不看能力位),所以措辞只许比今天更保守,并排在 PR 2 之后:事故靠 PR 1 就能修。

### 4.3 如实说

沿用工具结果末尾加括号说明的现有写法(例:`vision.py:553-556`)。平台英文、通用:

| 情况 | 追加的话(初稿) | PR |
|---|---|---|
| 转过图 | `(The image was stored turned; it was rotated N degrees clockwise before reading. Any region refers to the rotated image.)` | 1 |
| 判不出方向 | `(The text or display in this image does not look upright and its orientation could not be determined, so this reading may be wrong. Say the value is uncertain.)` | 1 |
| 接缝重看,同值 | 现有「whole-image reading; small print may be unreliable」原样保留,后半句换成 `the seam between bands was looked at again and gave the same value.` | 3 |
| 接缝重看,不同 | `(Two looks at this value disagree: A / B. Say the value is uncertain.)` | 3 |

**不做**:

- 不靠「同一个模型再读一遍、两次一致」表示可信(理由同 §4.2)。
- 不改看图模型系统提示词里的 "do not add caveats"(`vision.py:130-134`)。它确实不鼓励模型说「图是横的」,但改它影响所有看图回答,没测过;方向改由平台单独问。
- 不在平台文字里写「请用户确认」「健康读数」之类 —— 那是智能体的事(§12)。

### 4.4 记进轨迹(PR 1)

工具结果的 meta 本来就进事件流(`vision.py:456-464`)。新增一个 `orientation` 字段:结论(正 / 无文字 / 已转 / 判不出 / 没问成)、角度、四个方向各自的回答、回答的是哪个模型、是否来自缓存、多花了几次调用。另加一个计数器,按结论和角度分。候选副本留在 run 的裁图目录里,排查时可以直接打开看。

## 5. 多花多少钱、多慢多少

**次数**(程序保证的上限;这是「逻辑调用」数):

| 情况 | 每张图每次 run 多出的调用 |
|---|---|
| 模型没开这项能力 | 0 |
| 图是正的(绝大多数) | 1 |
| 第 1 步答 no(横 / 倒 / 判不出) | 4(1 + 3) |
| `auto` 里有横条被切开(PR 3) | 每次 `auto` 再 +1 |

一次逻辑调用在主看图模型失败时会顺着备用链往下试,所以**发给厂商的请求数上限 = 4 × 链长**(链长 = 主看图模型 + 配置的备用模型数;没配备用就是 4)。最坏的一次 `ask_image`(大图第一次用 `auto`、横图、有接缝):4 + 8 条 + 1 整张 + 1 重看 = 14 次逻辑调用,今天最多 9 次。费用**只随「图片张数 × run 数」增长**,与对话长度、问了几个问题无关。

**单价假设**(占位;价格在数据库费率表里,本文没有读,未验证):问方向的一次调用 = 一张约 150 万像素的图 + 一句话输入、一个词输出;假设折合约 2,000 个输入 token、输入价 ¥3 / 百万 token → **每次约 ¥0.006**。按这个假设:正图每张 +¥0.006,横图每张 +¥0.024。各家对图片的计 token 方式不同,误差可能到 2~3 倍。

**延迟**:问方向排在读数之前,正图多等 1 次调用,横图多等 2 轮(第 2 轮三次并行)。只输出一个词,应当比普通快看快(普通快看 p95 15 秒、最长 28 秒),但**没有量过**(未验证)。限时 30 秒意味着慢的那一小部分会静默按原图读 —— 这个比例是验收项(§9.2 L6)。「问方向与读数并行、正图零等待」先不做:横图会白读一次,量完再说。 有多少图会用到还不知道(只有 1 个实例),用户已定先数(§9.0 第 3 项)。

## 7. 文档页与知识库扫描页:方向分类小模型(PR 4、5,本批就做)

### 7.1 用哪个模型、用在哪

PP-LCNet_x1_0_doc_ori(四分类:0 / 90 / 180 / 270 度)。11-11 实测:文档 100%;显示屏照片只有 62~79%;正放的自然照片有 22.6% 被判成要转。所以:

- **只用在按来源就知道是文档的图上**:知识库入库时判为「要识别」的 PDF 页,和对话里平台渲出来的文档页。
- **绝不用在用户上传的照片、工作区图片文件上** —— 那里五张正图就可能转错一张;它们走 §4.1 的问模型。
- **把握 ≥ 0.9 且角度不是 0 才转**;其余一律不动,和今天逐字节相同。

### 7.2 现状(读代码确认)

**知识库入库**

| # | 事实 | 出处(`services/control-plane/src/control_plane/` 下) |
|---|---|---|
| 1 | 知识库只收 10 种文件,没有图片;扫描页只来自 PDF | `knowledge/parsing.py:34-36` |
| 2 | PDF 逐页判定;判为「要识别」的页才渲成图。自带隐藏文字层(≥ 50 字)的扫描页不识别、直接用文字层 | `knowledge/recognition/pages.py:222-247` |
| 3 | 渲染:200 DPI、长边 ≤ 2000 像素、JPEG;在**解析进程池**里跑;页图只在内存里,不落盘 | `pages.py:205-211,324-334`;`recognition/ingest_parse.py:281-282`;`knowledge/ingestion.py:305-311` |
| 4 | 页图交给识别模型;识别结果按「**页图字节的哈希** + 模型 + 渲染参数」缓存 | `recognition/recognizer.py:591-598,366-369` |
| 5 | 扫描页上的插图:识别模型给出相对页图的框,之后在**图片进程池**里把这一页**重新渲一次**再裁 | `recognizer.py:903-929`;`recognition/figure_scan.py:27-50` |
| 6 | 重新入库已有单篇入口,走费用预估 | `api/knowledge.py:1079-1097` |

**对话里的文档页**:在沙箱里用 `pdftoppm` 渲,整页 100 DPI,局部另渲高分辨率;编排侧经工作区引用读到页图(`services/orchestrator/src/orchestrator/tools/read_page.py:228,845,1006`;`tools/vision.py:762-782`)。

### 7.3 推理怎么跑

| 选项 | 新增的东西 | 结论 |
|---|---|---|
| A. paddlepaddle + paddleocr / paddlex 整套 | 一整套新的推理框架进镜像(体积和内存都是几百 MB 量级,未在本仓库量过) | **否**:为一个 7 MB 级的小模型不值;控制面内存放不下(见下) |
| B. 模型导出成 ONNX,用 onnxruntime 在**解析进程池的 worker 里**跑 | 控制面:**0 个新包** —— onnxruntime 1.20.1 已经随 markitdown → magika 在锁文件和控制面依赖里(`uv.lock:2156-2162,2223-2231,2645`;`services/control-plane/pyproject.toml:61`);只多一个模型文件 | **选它** |
| C. 放在控制面主进程里 | 同 B | **否**:主进程正是内存算满的那一块 |
| D. 单独起一个服务 | 新的部署、新的资源配额、多一跳网络 | **否**:B 在第 0 步量出来放不下时的退路 |
| E. 用识别厂商接口自带的方向纠正 | 无 | **否**:各家不一样,绑定厂商(WeKnora 调 PaddleOCR-VL 时把这项关着,`WeKnora/internal/infrastructure/docparser/paddleocr_vl_converter.go:97`) |

**内存放不放得下(硬约束)**。控制面 pod 限额 4 GiB,预算公式是「主进程 1,366 + 解析 worker(上限 2,400 − 650)+ 图片 worker(上限 1,536 − 654)= 3,998 MiB」,只剩 98 MiB(`tools/deploy/test_parse_worker_memory_budget.py` 文件头与 `worst_case_mib`)。回答:

- **pod 的预算不变**。公式里 worker 是按它的**地址空间上限**计的,不是按实际用量;小模型只在解析 worker 里加载(主进程不 import、图片 worker 也不加载),上限不改,公式的每一项都不变,98 MiB 不被动用。公式里的 650 是「峰值时不在内存里的那部分」:多加载一个库只会让它变大或不变,不会变小。
- **代价转移到 worker 自己身上**:worker 在 2,400 MiB 上限之内多了一个常驻的库和模型,离上限更近,原本勉强能解析的超大文档会更早失败(那一份文档解析失败,不影响别的)。多占多少**没量过** —— 第 0 步量(§7.6);magika 若已在 worker 里把 onnxruntime 载入,增量可能接近 0。
- 线程数固定为 1、关掉内存池预分配,按现有部署的线程约束来。

**对话文档页那一半(PR 5)没有这个便利**:编排服务的依赖里今天没有 onnxruntime(`services/orchestrator/pyproject.toml` 只有 Pillow,`:45`),要给编排镜像加一个包(linux x86_64 的安装包约 13 MB,`uv.lock:2659`;numpy 是否已在其中未核对),并且在编排进程里常驻。编排 pod 的内存余量没有核对。所以 PR 5 排在 PR 4 之后,第 0 步量过再开工;是否本批做列为待用户再定的问题 1(交付说明)。

### 7.4 做法

**知识库(PR 4)**。只改渲染这一步(§7.2 #3),在识别之前:

1. 对每个「要识别」的页,先渲一张小图(短边约 256 像素)给小模型,得到角度和把握。
2. 角度不是 0 且把握 ≥ 0.9 → 正式渲染时带上旋转(PyMuPDF 渲染矩阵直接旋转,不是渲完再转图,无额外损失);否则正式渲染与今天相同。
3. 渲染结果带回角度和把握。角度记进这一页的识别记录和计数器(落在哪个现有字段,PR 4 里定;未核对,§11)。
4. 插图裁剪(§7.2 #5)重渲这一页时用**同一个角度**(由服务端传进去,图片 worker 不加载模型),否则框和画面对不上。
5. 小模型加载失败或推理出错 → 按不转处理,计数,不让入库失败。

缓存不用改:转过的页字节变了,自然不命中旧缓存;没转的页字节不变,照常命中。**不改渲染参数串**(`pages.py:89-93`)—— 改它会让全部已缓存的页失效、全部重新付费识别。

**对话里的文档页(PR 5)**。`ask_image` 用 `path` + `unit` 看文档页时,对那张 100 DPI 的页图跑同一个小模型;要转的话,整页看用 §4.1 的同一套「带角度出副本」,局部和横条把框换算回原页坐标交给沙箱渲、拿回来的块再转正。角度写进同一个 `orientation` 轨迹字段(来源标成小模型)。不问看图模型,不看 §6 的能力位。

**开关**:两处各一个平台级环境变量,**默认开**(与第 7 条拍板一致;把握线和「只对文档」已经把误转压住,出问题一处关掉)。

### 7.5 已经入库的扫描件

不会自动变好,也不自动重跑:重新入库要重新识别转过的页、重新做向量,是花租户钱的动作,必须走现有的预估与确认。

- 做法:第 0 步的计数脚本(§7.6 第 4 项)顺带输出「含横置扫描页的文档 id 和页数」(只有 id 和数字)。平台把名单交给知识库的负责人,由对方用现有的单篇重新入库(§7.2 #6)。
- 费用:只有**转过的页**重新付识别费(没转的页命中缓存);整篇的向量是否全部重算以现有重新入库的行为为准(未核对,§11)。谁出这笔钱列为待用户再定的问题 2(交付说明)。
- 不把这些文档批量标成「过期」:标了就等于催所有人重跑。

### 7.6 第 0 步里不花钱的四项(开工前;协调人安排,本文作者没有装任何包)

1. **模型文件与许可证**:在一次性的环境里把模型导出成 ONNX(不进任何产品镜像);核对模型的许可证;记下文件大小和哈希。导出后的 ONNX 在 11-11 那批测试图上必须给出与 Paddle 原版相同的角度(逐张比)。预处理(缩放、裁剪、归一化)和「90 度指顺时针还是逆时针」用合成图钉死。
2. **内存与耗时**:在控制面镜像里,解析 worker 加载模型前后的地址空间和常驻内存各多少;单页推理的 CPU 耗时。过线:加载后 worker 仍能在 2,400 MiB 上限内解析预算测试用的那几份最大的文档;单页推理 ≤ 200 毫秒。不过线 → 退到选项 D,回来找用户。
3. **把握 ≥ 0.9 时的误转**:22.6% 是不设把握线还是设了线的数没有核对。用合成的「照片风格的 PDF 页」(整页照片、封面、整页图表)30 张重测;0 张被转才按 0.9 上,否则提高把握线再测。
4. **数一数**:测试环境知识库里判为「要识别」的 PDF 页,随机取最多 500 页,跑小模型,报四个数(取了几页、判横置几页、人工抽查确认几页、从判为正的里抽 100 页漏判几页),外加 §7.5 要的文档 id 名单。只读、只出数字和 id;人工抽查在本机做、不外传。生产同一脚本由用户跑。**这些数只用来定验收集和报告收益,不是立项门槛。**

### 7.7 代价(如实)

- 控制面多一个模型文件(预计 10 MB 以内,未核对);**没有新包**。编排镜像(PR 5)多一个 onnxruntime。
- 解析 worker 更接近自己的内存上限;入库每个扫描页多一次小图渲染 + 一次推理。一个新的、要有人维护的模型:它出错的方式是「把正的文档页转歪」,转歪之后那一页识别出来是乱的,而且要等有人读到才会发现。靠把握线、§9.4 的对照集和开关兜住。
- 夹在 PDF 里的照片页有被误转的风险(§7.6 第 3 项专门量)。

## 8. 这个设计修什么、不修什么

| 问题 | 修不修 | 说明 |
|---|---|---|
| 横 / 倒的照片被读错(事故本身) | **修**,对开了能力位的看图模型 | 实测:转正后 qwen 真实照片读对;豆包正放 12/14 对比转过 6/42 |
| 四个方向都不被认为是正的 | 不猜 | 用原图读,结果里写明可能读错(§4.3) |
| 横条把数字切开后没人再看 | **修**(PR 3) | 工具自己重看一次;重看一致也仍标不确定 |
| 同一张图跨 run | 不缓存 | 每次 run 重问一次方向;两次 run 判得不同,上一次的区域坐标就对不上(少见,接受) |
| 淡笔段(没点亮的笔段)被当成点亮 | **不修** | 与方向无关;豆包正放也错。本设计对它唯一的作用是:若它恰好让两次读数不一致,会被如实标出;两次一致的错(如稳定读成 2.4)标不出来。兜底只有智能体提示词里的「先确认」(§12) |
| 看图模型没开能力位(如 glm-4.6v) | 不修 | 行为与今天相同 |
| 文档页、知识库扫描页横置 | **修**(PR 4、5) | 方向小模型,把握 ≥ 0.9 才转;已入库的要重新入库(§7) |
| 读错的数被记进长期记忆 | 不在本文 | B-300 |

### 8.1 主模型自己看图的智能体(测试环境 14 个)

**不在本批范围内**。原因:图直接进主模型的消息(§1.2 #4),不经过看图工具;它们用的模型(deepseek-flash、glm-5.3-flash、glm-5.3-flashx)「能不能答对正不正」**一次都没测过**。

要覆盖它们,做法是:在 run 开始、图第一次进消息之前,用主模型(关思考)问同样的一句话,必要时把消息里的图换成转正副本。这要动 run 输入的组装(`runs.py:468-527` 在控制面,转图在编排侧),比 PR 1 大,而且每张图都要多一次**主模型**调用。建议顺序:先花一次小测量(§9.3 报价里单列)看这三个模型答不答得对;答得对再单独立项;答不对就只能靠 §12 的提示词。用户已定:这次不做,先测(< ¥2),能答对再单独立项。

## 9. 验收

### 9.0 第 0 步:开工前的小测量

用户已定现在跑。前两项约 90 次调用、< ¥1,都只用合成图,qwen3.8-max-0902 与 doubao-…-260915 各跑一遍:

1. **新问法**(§4.1 那句):28 张集 + 4 张无文字图,各问 1 次 = 每模型 32 次。过线:28 张答对 ≥ 27,无文字 4 张全部答 `none` 或 `yes`。不过线就退回已测过的问法(只问显示屏、只答 yes / no),无文字的图交给 L4 去量。

## 12. 哪些智能体要改提示词(平台不代改)

平台只负责读得更准、读不准时如实说。「把读到的数记下来之前先跟用户确认」是业务决定,写在各智能体自己的提示词里,由智能体的负责人改。

**挑选标准**(三条都满足的优先改):

1. **能看图**:走看图工具(有 `vision` 块且主模型不能看图),或主模型自己看图。
2. **会把看到的东西留下来**:开了长期记忆写回,或带有会写入外部系统的工具。
3. **看的是数值**:业务上会让用户拍读数、单据、仪表。这一条程序判断不了,也**不要去搜提示词或对话内容**,由负责人看名单后自己判断。

主模型自己看图的那一类(§8.1)平台这次不修方向,更需要这句提示词。

**测试环境查询**(只读;只输出名字、版本、模型名和是 / 否,不输出提示词、不输出任何对话或客户文字):

```sql
SELECT name, version, status,
       jsonb_typeof(spec_json->'spec'->'vision') = 'object'
         AND NOT COALESCE((spec_json->'spec'->'model'->>'supports_vision')::bool, false)
                                                        AS uses_ask_image,
       COALESCE((spec_json->'spec'->'model'->>'supports_vision')::bool, false)
                                                        AS main_model_sees_images,
       spec_json->'spec'->'vision'->'model'->>'name'    AS vision_model,
       spec_json->'spec'->'model'->>'name'              AS main_model,
       jsonb_typeof(spec_json->'spec'->'memory'->'long_term') = 'object'
         AND COALESCE((spec_json->'spec'->'memory'->'long_term'->>'write_back')::bool, true)
                                                        AS writes_memory
FROM agent_spec
WHERE (jsonb_typeof(spec_json->'spec'->'vision') = 'object'
       OR COALESCE((spec_json->'spec'->'model'->>'supports_vision')::bool, false))
  -- AND status = 'active'   -- 自检通过后再加这一行,只看在用的
ORDER BY writes_memory DESC, uses_ask_image DESC, name, version;
```

为什么用 `jsonb_typeof`:没配的块落库时存成 JSON 的 null(`packages/expert-work-persistence/src/expert_work/persistence/agent_spec/sql.py:162,328`,`model_dump` 不去掉空值),`IS NOT NULL` 对它恒为真,会把不看图的也算进来。

自检(口径与 §2 相同:全部行,不加状态条件):`uses_ask_image` 为真 31 行、`main_model_sees_images` 为真 14 行,合计 45 行;对不上先停下。之后加上 `status = 'active'`(取值见 `packages/expert-work-protocol/src/expert_work/protocol/agent_spec.py:1878-1881`)得到要看的名单。字段路径取自同文件 `:1537-1566`(`AgentSpecBody`),表定义 `packages/expert-work-persistence/src/expert_work/persistence/models/agent_spec.py:20-32`。「带写入外部系统的工具」没有写进查询:工具清单里哪些会写入要人看,第一轮先按记忆写回筛。

**生产**:同一条 SQL,由用户用只读账号执行;我不连生产。把结果里的行数和 `name / version` 两列发回即可,其余列按需。连接方式用现有的只读连接,**不要把连接串打到终端或粘贴出来**。

**建议的提示词措辞**(通用,各智能体按自己的口吻改写,加在自己的提示词里):

> 从图片里读到的数值(读数、金额、日期、编号等),在写入记录、记入记忆或用于计算之前,先把读到的值原样告诉用户,请对方确认或更正。看图工具提示「不确定」或给出两个不同读数时,如实告诉用户看不清,请对方确认或重新拍一张正放、清晰的照片,不要自己挑一个。用户确认之前,不要把这个数当作已知事实。
