## 0. 一页看懂

**问题**:图片里的内容横着或倒着、而图片又不带方向标记时,平台原样交给看图模型,模型读错。**实例**(测试环境):一张体重秤液晶屏照片(4032×3024,顺时针横了 90 度),实际 69.1;整张快看读成 0.0;`region="auto"` 的横条把躺着的数字拦腰切开,退回整张读成 68.1;工具给了「建议再看这个区域」,没有任何一方去看。

**根因**:平台只按图片自带的方向标记转正;看图模型**看得出**图是横的,却**读不对**。

**改四件事**(前三件在看图工具里,原图不动;第四件不调付费模型):

| 序 | 改什么 | 程序保证的 | 靠模型的 | PR |
|---|---|---|---|---|
| ① 先问方向 | 看图前先问看图模型一句「主要文字是正的吗」;说不正,就转 90 / 180 / 270 度各问一次,用它说「正」的那一张来看。**底层能力,所有看图模型默认都做**;只留一个运维紧急开关(用户 11-12 改定,§6) | 转图、选哪张、缓存、记进轨迹、每张图最多多 4 次调用 | 「正不正」的回答 | 1 |
| ② 如实说 | 转过图、判不出方向、两次看的结果对不上 —— 都在工具结果里写明 | 什么时候写、写什么 | 主模型看到后是否照做 | 1、3 |
| ③ 自己重看 | 横条报「被切开」时,工具自己把那一段裁出来再看一次;两次一致也**仍标不确定** | 重看这个动作 | 重看读得对不对 | 3 |
| ④ 扫描页 | 知识库**新入库**的扫描页:方向分类小模型,把握 ≥ 0.9 才转(§7) | 转不转、转多少、记下来、费用预估同步 | 小模型的判断 | 4 |

①对所有看图模型都做,不按模型开(用户 11-12 改定,§6)。答不了的(例如 glm-4.6v,永远答「正」)等于每张图多问 1 次、其余与今天相同;上生产前对在用的看图模型做一次体检(§9.2;生产只用豆包 260628,默认测两个豆包,通义可选)。

**证据有多宽(如实)**:判方向这一步在合成图和 5 张真实照片上没有误判;在测试环境的真实上传图上第一次看到出错:同一张横图问 3 次,doubao 有 1 次答成「正」(漏转,不是转错;§2)。「横着就读错、转正就读对」**几乎只在数字显示屏上量到过**,而且因模型而异:doubao 收益明确;qwen 至今只有事故那 1 张照片横着读错,其余合成图和 5 张真实照片上转不转都一样。横着的印刷文字、表格、手写、标签没有数据。所以 §9.2 的评测跨 11 类内容,按类报告「有收益 / 无收益 / 变差」。11-12 用户改定后它不再决定开不开(所有看图模型都做),而是上生产前的体检:重点看正放的图有没有被转歪(§9.2、§13)。

**做完之后还剩什么**(详见 §8):

1. 与方向无关的读错不修(例:液晶屏没点亮的淡笔段被当成点亮,正放也错)。
2. 没有文字、但有明确上下的图(表盘、曲线图、人像)不会被转:问的是「文字正不正」。
3. 主模型自己能看图的智能体不覆盖(测试环境 14 个);知识库文档里内嵌的横置图片不覆盖。
4. **已经入库的横置扫描件不处理**(用户定):只对新入库生效。对话里的文档页这一批不做(用户定,§7.8)。
5. 豆包 260628 的「正不正」没测过,而测试环境 31 个走看图工具的智能体里 30 个用它。①对它默认就做(11-12 改定),所以上生产前的体检(§9.2)必须包括它。
6. 「从图片读到的关键信息先跟用户确认再使用」不是平台行为,由各智能体自己的提示词负责(§12)。

## 3. 已定的方向与本文的收窄

用户已同意:(a) 文档 / 扫描件用方向分类小模型,把握 ≥ 0.9 才动;(b) 其它照片问看图模型「正不正」,不正就试几个方向,按模型逐个开;(c) 工具自己重看它建议的区域;(d) 工具结果如实写不确定;(e) 转了多少度记进轨迹。「先跟用户确认再记录」归各智能体提示词,平台不改已有智能体。

本文在这个范围内做了三处收窄,理由是「先修量到的问题」:

1. **在看图工具里做,不在上传时做**。上传时没有 run、不知道是哪个智能体的看图模型,轨迹也无处可记;更要紧的是在上传时转 = 改掉用户的原图,模型判错一次,之后每次看都是错的。工具里做只生成一张转正的副本,原图不动,判错了影响限于这一次 run。代价:主模型自己看图的那条路覆盖不到(§8.1)。这是最大的一个取舍,用户已定在工具里做。
2. **按来源分流,不猜图的类型**。用户上传的图、工作区里的图片文件 → 走 (b)。平台渲染出来的文档页、知识库扫描页 → 才是 (a) 的对象。不做「先判断这张上传图是文档还是照片」:小模型在自然照片上误转 22.6%,猜错类型的代价太高。
3. **(a) 本批就做**(用户 11-11 定,§7)。我原先建议先数再立项;「数」保留为不花钱的第 0 步,用来定验收集和报告收益,不再是立项门槛。

## 4. 设计

### 4.1 先问方向(PR 1)

**对谁做**:`ask_image` 看的**上传图**和**工作区图片文件**。不做的:文档页(`path` + `unit`,平台自己渲的)、已经是裁图的引用、运维紧急开关关掉时(§6)、没接工作区的构建(副本没地方放 —— 与今天 `region` 的前提相同,`vision.py:946-953`)。

**流程**(每张图每次 run 只做一次):

```
1. 出一张「0 度候选」:整张图缩到约 150 万像素的副本;图片自带方向标记的先按标记转正。
   问它:「主要文字是正的吗?」
   - yes / none(图里没有可读的文字)→ 结论「正」,和今天一样往下走。
   - no → 第 2 步。
   - 答非所问 / 调用失败 / 超时 → 结论「没问成」:按 0 度往下走,只记轨迹,不对主模型说什么。
2. 在 0 度候选上顺时针转 90 / 180 / 270 度,三张副本并行各问一次同一句话。
   - 三次都答成了,且恰好一张答 yes → 结论「已转 N 度」。
   - 其余一切情况(没有 yes、不止一张 yes、任何一次超时 / 失败 / 答非所问)
     → 结论「判不出」:按 0 度读,结果里如实写(§4.3)。不采纳部分结果。
3. 结论(含「没问成」)写进缓存文件。这次 run 里之后对这张图的每一次看
   (整张、横条、指定区域)都按缓存的角度做 —— 同一次 run 里坐标系不会中途变。
```

**问的那句话**(平台英文,通用;第 0 步先测,§9.0):

> Look only at orientation. Is the main text in this image upright, that is, readable without turning the image? Answer with exactly one word: yes, no, or none (the image has no readable text).

解析:去掉思考标签、markdown 符号和标点,转小写,取第一个词;不是这三个词之一就算「答非所问」,次数进计数器。第 0 步测过的是带 "text or numeric display" 的那一句(§2);平台文字不带场景词,所以这里去掉了 display —— 屏幕上的数字本来就是文字。去掉之后要补测(§9.0);补测若答对率下降,记为该模型开能力位的条件,**不把场景词写回平台文字**。

**怎么转**:不新写旋转代码。裁图函数本来就能「按一个方向值把裁下来的块转正」(`region_zoom.py:347-362`,为方向标记写的);给它加一个「再顺时针转多少度」的入参,与图片自带的标记合成一个方向值。于是:

- 候选副本 = 对整张图(框 `[0,0,1000,1000]`)带角度裁一次,自动缩到约 150 万像素(`region_zoom.py:380-396`)。
- 结论是「正」且图片没有方向标记(上传图都没有,上传时已去掉):整张看仍把原图交给模型,**与今天逐字节相同**。其余情况(转过,或带标记)整张看用对应的候选副本 —— 分辨率比原图低,由 §9.2 的小字横图检验。
- 横条和指定区域照旧从**原像素**裁,坐标换算到转正后的画面;横条规划用转正后的宽高(事故那张转正后 3024×4032,按 §1.3 #10 是 8 条,数字横排)。

要改的调用点是数出来的:把原图引用直接交给模型的 4 处(`vision.py:452,548,574,672`)、读尺寸 1 处(`:713`)、宿主裁图 1 处(`:793-813`)。

**文件与缓存**:都在本次 run 的裁图目录 `.tool_results/<run>/crops/<原图哈希>/` 下(`vision.py:794-801`)。今天裁图文件名只由框决定、已存在就复用(`vision.py:802,811-812`),不同角度会撞名 —— 所以转过的裁图和候选副本放进子目录 `r<角度>/`,0 度沿用现有位置。缓存文件记结论、角度、四个回答。并行的两次 `ask_image` 看同一张图时排队,沿用现有目录锁(`vision.py:809`)。只在一次 run 内有效,跨 run 重问。

**能力怎么传**(用户 11-12 改定):工具上加一个布尔字段 `ask_orientation`,装配处(`tools/assembly.py` 的 `_register_ask_image`)**只按运维紧急开关**填(环境变量 `EXPERT_WORK_ASK_IMAGE_ORIENTATION`,默认开)。不看模型目录、不看智能体配置,模型目录里不加能力位。评测脚本直接构造工具、把这个字段设为真。

**调用路线、限时、计费**:问方向固定走快看那条链,被厂商拒时**不**再走「退回正常看图」的二次路由(`vision.py:866-876`)—— 拒了就算没问成。每次限时 30 秒(普通快看测试环境 30 天最长 28 秒,`vision.py:143-144`),超时算没问成;**看图绝不因为问方向而失败**。每次调用照常扣 token 池、记账(`vision.py:516-523`),并占切块调用的名额(`vision.py:182`)。**用量记在哪**:与今天 `ask_image` 的看图调用完全相同 —— 同一个记账回调,用量种类就是这次构建的种类(与主循环同口径,`agent_factory.py:785-790,853-860`),记在租户名下;不新增用量种类或桶。对接方看到的变化只有:同一个种类下的调用次数和 token 数变多(§5)。

### 4.2 工具自己重看(PR 3,最后做)

只管一种情况:`region="auto"` 里有横条报 `partial`。今天是退回整张读并留一句建议(§1.3 #11、#12);改成工具把报 `partial` 的那几条的并集框裁出来,用原问题再快看**一次**,然后:

- 两次读数一致 → 仍给整张读的值,**保留「小字可能不可靠」的不确定措辞**,只把「请用这个区域再问一次」换成「已重看过接缝,同值」。不把「一致」说成「可信」:实测同一模型对同一张横图两次都是 68.1,裁出显示屏也不解决横置(§2)。
- 不一致,或重看没读到 → 两个读数都列出,明说不确定。**不投票、不挑一个**(与现有横条汇总的原则相同,`tile_reading.py:11-13`)。

作用只有一个:省掉主模型「再问一次」那一轮,并且保证真的有人看过。横条之间「冲突」没有单一区域可看,保持今天的报告方式。每次 `auto` 最多多 1 次调用。它对所有看图模型生效(不受 PR 1 的运维紧急开关管),所以措辞只许比今天更保守,并排在 PR 2 之后:事故靠 PR 1 就能修。

## 5. 多花多少钱、多慢多少

**次数**(程序保证的上限;这是「逻辑调用」数):

| 情况 | 每张图每次 run 多出的调用 |
|---|---|
| 运维紧急开关关掉 | 0 |
| 图是正的(绝大多数) | 1 |
| 第 1 步答 no(横 / 倒 / 判不出) | 4(1 + 3) |
| `auto` 里有横条被切开(PR 3) | 每次 `auto` 再 +1 |

一次逻辑调用在主看图模型失败时会顺着备用链往下试,所以**发给厂商的请求数上限 = 4 × 链长**(链长 = 主看图模型 + 配置的备用模型数)。最坏的一次 `ask_image`(大图第一次用 `auto`、横图、有接缝):4 + 8 条 + 1 整张 + 1 重看 = 14 次逻辑调用,今天最多 9 次。费用**只随「图片张数 × run 数」增长**,与对话长度、问了几个问题无关。

**单价**(第 0 步实测,qwen3.8-max):问一次方向(150 万像素副本,1,525 输入 token)≈ **¥0.018**。正图每张每次 run +¥0.018,横图 +¥0.072。豆包同尺寸的 token 数约为一半,单价未给(未验证)。第 1~2 版假设的 ¥0.006 偏低,作废。

**延迟**:问方向排在读之前,正图多等 1 次调用,横图多等 2 轮(第 2 轮三次并行)。耗时**没有单独量过**(未验证);限时 30 秒意味着慢的那一小部分会静默按原图读 —— 这个比例是验收项(§9.2 L6)。「问方向与读并行、正图零等待」先不做:横图会白读一次,量完再说。有多少图会用到:测试环境 32 张不同的上传图里 2 张横置(约 6%,样本小且不代表真实用户,§2);生产没数。

## 6. 对谁开:所有看图模型(用户 11-12 改定)

**做法**:问方向是 `ask_image` 的底层能力,**所有看图模型默认都做**。模型目录里**不加**能力位,不按模型开;也**不给**智能体配置或控制台任何开关。只留一个**运维紧急开关**:平台环境变量 `EXPERT_WORK_ASK_IMAGE_ORIENTATION`(布尔,默认开;`0` / `false` / `off` / `no` 为关),出问题时一处关掉、全部回到今天的行为。装配时工具上的布尔字段只按它填(§4.1「能力怎么传」)。

**为什么不按模型开**(用户的理由):

1. 这和平台上任何一个能力弱的模型是同一类问题 —— 某个看图模型答不准「正不正」,会在排查读错时被发现,然后换掉这个模型,与换掉一个读图本身就弱的模型一样;不为这一件事单独维护一张按模型的开关表。
2. 判错是看得见的:每次判断都记进轨迹(§4.4 的 `orientation` 字段:结论、角度、四个方向各自的回答、回答的模型),转过图时工具结果里明写「转了 N 度」(§4.3),判不出时明写「读不可靠」。所以「被转歪」不会静默发生。
3. 永远答「正」的模型(实测 glm-4.6v)无害:每张图多 1 次调用,其余与今天相同(单元测试钉住:只多 1 次调用和 meta 里的 `orientation`,读的引用、回答、其余 meta 全都一样)。

**已知风险(如实)**:真正有害的是把**正放**的图判成「不正」、又恰好在某个转角上答 yes —— 那会把正图转歪去读。至今没见过(§2),但测试环境在用的 doubao-seed-2-1-pro-260628 没测过。所以上生产前做一次体检(§9.2),重点就是正放的图 0 张被转。

已有的实测(仍然有用,作为体检的参照):

| 看图模型 | 「正不正」实测 | 说明 |
|---|---|---|
| qwen3.8-max-0902 / qwen3.8-max(别名) | 28/28 | 事故智能体在用 |
| doubao-seed-2-1-pro-260915 | 28/28 | #2075 新增 |
| doubao-seed-2-1-pro-260628 | **没测** | 测试环境 31 个走看图工具的智能体里 30 个在用 |

**重测条件**:问方向那句话改了措辞,或在用的看图模型换了 / 别名指向的快照换了 —— 对受影响的模型重跑一次体检(§9.2);体检不过就先关运维开关,再定换模型还是改问法。

## 7. 知识库扫描页:方向分类小模型(PR 4)

### 7.1 用哪个模型、用在哪

PP-LCNet_x1_0_doc_ori(四分类:0 / 90 / 180 / 270 度)。11-11 实测:文档 100%;显示屏照片 62~79%;正放的自然照片 22.6% 被判成要转(是在什么把握线下量的没有核对)。

- **只用在一处**:知识库入库时 PDF 里判为「要识别」的页。对话里的文档页这一批不做(§7.8)。
- **这些页不全是文字文档**:「要识别」包括字少且有图的页、图片块很多的页、整页图、乱码页(`pages.py:236-247`)—— 照片页、幻灯片、图纸、图表都在里面,正是小模型会误转的那类。靠三样压住:把握 ≥ 0.9 才转;§9.4 的 D3(≥ 200 张这类页,0 张被转);真实扫描件的确认率线(§7.6 第 4 项)。
- **绝不用在用户上传的照片、工作区图片文件上**(22.6% 的那个数);它们走 §4.1。
- 角度为 0 或把握 < 0.9 的页一律不动,和今天逐字节相同。

### 7.2 现状(读代码确认;路径在 `services/control-plane/src/control_plane/` 下)

### 7.3 推理怎么跑

| 选项 | 结论 |
|---|---|
| A. paddlepaddle + paddleocr / paddlex 整套 | **否**:为一个小模型引入一整套推理框架(体积、内存没在本仓库量过) |
| B. 导出成 ONNX,用 onnxruntime 跑 | **选它**。**不加新包**:onnxruntime 1.20.1 和 numpy 已随 markitdown → magika 在控制面镜像里(`uv.lock:2156-2163,2222-2231,2645`;`services/control-plane/pyproject.toml:61`);只多一个模型文件 |
| C. 单独起一个服务 | **否**:新部署、新配额、多一跳;B 放不下时的退路 |
| D. 用识别厂商接口自带的方向纠正 | **否**:各家不一样,绑定厂商(WeKnora 调 PaddleOCR-VL 时把它关着,`WeKnora/internal/infrastructure/docparser/paddleocr_vl_converter.go:97`) |

**内存(硬约束)**。pod 限额 4 GiB,预算是「主进程 1,366(实测)+ 解析 worker(上限 2,400 − 650)+ 图片 worker(上限 1,536 − 654)= 3,998 MiB」,剩 98 MiB(`tools/deploy/test_parse_worker_memory_budget.py:73-77` 与文件头)。

- **PR 4(知识库)放得下,预算不变**。推理会话**只在解析 worker 里、第一次用到时创建**(onnxruntime 这个模块今天已被 magika 带进各进程,要管住的是会话);每个 worker 一辈子只建一次。公式按 worker 的上限计,上限不改,98 MiB 不被动用;多加载一个模型只会让「峰值时不常驻的部分」不变或变大。代价在 worker 自己:离 2,400 MiB 上限更近,超大文档会更早失败。**硬要求**:会话显式设单线程(算子内、算子间都是 1)、关掉内存池预分配 —— 部署里的四个线程环境变量管不到 onnxruntime。过线见 §7.6 第 2 项。

### 7.4 做法

**知识库(PR 4)**:

1. **逐页判定时就判方向**(§7.2 #2 那一步,入库和预估都走它):对「要识别」的页渲一张小图(短边约 256 像素)给小模型;角度和把握记在这一页的判定结果里,之后一路带着走,**不再重新推理**。
2. 正式渲染:要转的页用渲染矩阵直接旋转(不是渲完再转图);不转的页与今天逐字节相同。**不改渲染参数串**(`pages.py:89-93`),否则全部缓存失效。
3. **预估与入库对齐**(§7.2 #5):转过的页,读法摘要加「角度 + 小模型文件哈希」后缀,缓存写入和预估查询都用它;没转的页摘要不变。这样旧缓存里按横着读的那一条不会被预估当成「已缓存、免费」。
4. 插图裁剪重渲这一页时用带回来的同一个角度。
5. 角度和把握记进这一页已有的识别缓存记录和计数器。**不需要数据库迁移**:那条记录的内容本来就是一个 JSON 字段,页码、来源哈希、读法摘要都是里面的键(`recognizer.py:384-391`;`packages/expert-work-persistence/src/expert_work/persistence/models/knowledge.py:329-354`),角度再加两个键即可;预估的查询按这些键过滤(`persistence/knowledge/sql.py:2473-2496`),读法摘要加后缀只是换了键值。
6. **失败不静默**:镜像构建时加一步「加载模型并推理一张图,失败则构建失败」(仿 Dockerfile 里分词表的做法,`services/control-plane/Dockerfile:81-92`);运行期加载或推理失败按不转处理、入库照常,但记告警级计数。

**开关**:一个平台级环境变量 `EXPERT_WORK_KNOWLEDGE_SCAN_PAGE_ORIENTATION`(`Settings.knowledge_scan_page_orientation`),**默认开**(用户 11-12 定,§13 第 12 条)。合进去后新入库(含重新入库、补识别、费用预估)的扫描页立即生效,不用任何人操作;出问题时设成 `false` 即关,只影响之后新判定的页。把握线 0.9 是代码里的常量,不按租户 / 智能体配。

| 问题 | 修不修 | 说明 |

| 读错的数被记进长期记忆 | 不在本文 | B-300 |

## 12. 哪些智能体要改提示词(平台不代改)

平台只负责读得更准、读不准时如实说。「把读到的数记下来之前先跟用户确认」是业务决定,写在各智能体自己的提示词里,由智能体的负责人改。

**挑选标准**(三条都满足的优先改):

1. **能看图**:走看图工具(有 `vision` 块且主模型不能看图),或主模型自己看图。
2. **会把看到的东西留下来**:开了长期记忆写回,或带有会写入外部系统的工具。
3. **会把从图片里读到的内容当作事实使用**(写入记录、记入记忆、用于计算或决定)。这一条程序判断不了,也**不要去搜提示词或对话内容**,由负责人看名单后自己判断。

主模型自己看图的那一类(§8.1)平台这次不修方向,更需要这句提示词。

**测试环境查询**(只读;只输出名字、版本、模型名和是 / 否,不输出提示词、不输出任何对话或客户文字):

```sql
SELECT name, version, status,
       jsonb_typeof(spec_json->'spec'->'vision') = 'object'
         AND NOT COALESCE((spec_json->'spec'->'model'->>'supports_vision')::bool, false)
                                                        AS uses_ask_image,
       COALESCE((spec_json->'spec'->'model'->>'supports_vision')::bool, false)
                                                        AS main_model_sees_images,
       spec_json->'spec'->'vision'->'model'->>'name'    AS vision_model,
       spec_json->'spec'->'model'->>'name'              AS main_model,
       jsonb_typeof(spec_json->'spec'->'memory'->'long_term') = 'object'
         AND COALESCE((spec_json->'spec'->'memory'->'long_term'->>'write_back')::bool, true)
                                                        AS writes_memory
FROM agent_spec
WHERE (jsonb_typeof(spec_json->'spec'->'vision') = 'object'
       OR COALESCE((spec_json->'spec'->'model'->>'supports_vision')::bool, false))
  -- AND status = 'active'   -- 自检通过后再加这一行,只看在用的
ORDER BY writes_memory DESC, uses_ask_image DESC, name, version;
```

为什么用 `jsonb_typeof`:没配的块落库时存成 JSON 的 null(`packages/expert-work-persistence/src/expert_work/persistence/agent_spec/sql.py:162,328`,`model_dump` 不去掉空值),`IS NOT NULL` 对它恒为真,会把不看图的也算进来。

自检(口径与 §2 相同:全部行,不加状态条件):`uses_ask_image` 为真 31 行、`main_model_sees_images` 为真 14 行,合计 45 行;对不上先停下。之后加上 `status = 'active'`(取值见 `packages/expert-work-protocol/src/expert_work/protocol/agent_spec.py:1878-1881`)得到要看的名单。字段路径取自同文件 `:1537-1566`(`AgentSpecBody`),表定义 `packages/expert-work-persistence/src/expert_work/persistence/models/agent_spec.py:20-32`。「带写入外部系统的工具」没有写进查询:工具清单里哪些会写入要人看,第一轮先按记忆写回筛。

**生产**:同一条 SQL,由用户用只读账号执行;我不连生产。把结果里的行数和 `name / version` 两列发回即可,其余列按需。连接方式用现有的只读连接,**不要把连接串打到终端或粘贴出来**。

**建议的提示词措辞**(通用,各智能体按自己的口吻改写,加在自己的提示词里):

> 从图片里读到、并且要写入记录、记入记忆或用于后续操作的关键信息(数值、名称、日期、编号、勾选项等),在使用之前先原样告诉用户,请对方确认或更正。看图工具提示「不确定」「读不可靠」或给出两个不同结果时,如实告诉用户看不清,请对方确认或重新提供一张正放、清晰的图,不要自己挑一个。用户确认之前,不要把它当作已知事实。
