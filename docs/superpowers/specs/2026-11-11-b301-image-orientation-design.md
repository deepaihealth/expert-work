## 0. 一页看懂

**出了什么事**:用户上传一张体重秤液晶屏照片(4032×3024,画面顺时针横了 90 度,照片不带方向标记),实际 69.1。看图工具整张快看读成 0.0;`region="auto"` 把图切成横条,横条把躺着的数字拦腰切开,退回整张读成 68.1;工具给了「建议再看这个区域」,但没有任何一方真的去看。

**根因一句话**:平台只按照片自带的方向标记转正,没有标记就原样给模型;而看图模型**能看出**图是横的,却**读不对**横着的数字。

**改三件事**(都在看图工具里,原图不动):

| 序 | 改什么 | 程序保证的 | 靠模型的 | PR |
|---|---|---|---|---|
| ① 先问方向 | 看图前先问看图模型一句「主要文字 / 显示屏是正的吗」;说不正,就把图转 90 / 180 / 270 度各问一次,用它说「正」的那一张来读 | 转图、选哪张、缓存、记进轨迹、每张图最多多 4 次调用 | 「正不正」的回答(实测两家各 28/28) | 1 |
| ② 如实说 | 转过图、判不出方向、两次读数对不上 —— 都在工具结果里写明 | 什么时候写、写什么 | 主模型看到后是否照做 | 1、3 |
| ③ 自己重看 | 横条报「被切开」时,工具自己把那一段裁出来再看一次,不再只留一句建议;两次一致也**仍标不确定** | 重看这个动作 | 重看读得对不对 | 3(最后做) |

按看图模型逐个开:只有实测「能答对正不正」的模型才开(§6);答不了的模型(例如 glm-4.6v,永远答「正」)保持今天的行为。

**做完之后还剩什么**(详见 §8):

1. **淡笔段读错不修**。屏幕上没点亮的淡笔段是另一个独立原因(豆包把 72.4 读成 2.4,图是正的),转正帮不上。
2. **主模型自己能看图的智能体不覆盖**(测试环境 14 个):图不经过看图工具。
3. **文档 / 扫描件、知识库入库不在前三个 PR 里**:先数有多少横着的,再决定做不做(§7)。
4. **豆包 260628 版本没测过**:测试环境 31 个走看图工具的智能体里 30 个用它;实测的是 260915。在 260628 过线、或这 30 个智能体换型号之前,本设计在测试环境**只覆盖 1/31**(事故那个)。
5. 「读到健康数值先跟用户确认再记录」不是平台行为,由各智能体自己的提示词负责(§12)。

## 3. 已定的方向与本文的收窄

用户已同意:(a) 文档 / 扫描件用方向分类小模型,把握 ≥ 0.9 才动;(b) 其它照片问看图模型「正不正」,不正就试几个方向,按模型逐个开;(c) 工具自己重看它建议的区域;(d) 工具结果如实写不确定;(e) 转了多少度记进轨迹。「先跟用户确认再记录」归各智能体提示词,平台不改已有智能体。

本文在这个范围内做了三处收窄,理由是「先修量到的问题」:

1. **在看图工具里做,不在上传时做**。上传时没有 run、不知道是哪个智能体的看图模型,轨迹也无处可记;更要紧的是在上传时转 = 改掉用户的原图,模型判错一次,之后每次看都是错的。工具里做只生成一张转正的副本,原图不动,判错了影响限于这一次 run。代价:主模型自己看图的那条路覆盖不到(§8.1)。这是最大的一个取舍,列为待拍板 #1。
2. **按来源分流,不猜图的类型**。用户上传的图、工作区里的图片文件 → 走 (b)。平台渲染出来的文档页、知识库扫描页 → 才是 (a) 的对象。不做「先判断这张上传图是文档还是照片」:小模型在自然照片上误转 22.6%,猜错类型的代价太高。
3. **(a) 排在最后、先数再做**(§7)。事故与实测都是照片;文档页横置有多少还没有数字,而 (a) 要给平台引入一个新的推理依赖(仓库里今天没有 Paddle,§1.1 的搜索 0 命中)。

## 4. 设计

### 4.1 先问方向(PR 1)

**对谁做**:`ask_image` 看的**上传图**和**工作区图片文件**。不做的:文档页(`path` + `unit`,平台自己渲的)、已经是裁图的引用、看图模型没开这项能力的(§6)、没接工作区的构建(副本没地方放 —— 与今天 `region` 的前提相同,`vision.py:946-953`)。

**流程**(每张图每次 run 只做一次):

```
1. 出一张「0 度候选」:整张图缩到约 150 万像素的副本;图片自带方向标记的先按标记转正。
   问它:「主要文字或显示屏是正的吗?」
   - yes / none(图里没有文字或显示屏)→ 结论「正」,和今天一样往下走。
   - no → 第 2 步。
   - 答非所问 / 调用失败 / 超时 → 结论「没问成」:按 0 度往下走,只记轨迹,不对主模型说什么。
2. 在 0 度候选上顺时针转 90 / 180 / 270 度,三张副本并行各问一次同一句话。
   - 三次都答成了,且恰好一张答 yes → 结论「已转 N 度」。
   - 其余一切情况(没有 yes、不止一张 yes、任何一次超时 / 失败 / 答非所问)
     → 结论「判不出」:按 0 度读,结果里如实写(§4.3)。不采纳部分结果。
3. 结论(含「没问成」)写进缓存文件。这次 run 里之后对这张图的每一次看
   (整张、横条、指定区域)都按缓存的角度做 —— 同一次 run 里坐标系不会中途变。
```

**问的那句话**(平台英文,通用;第 0 步先测,§9.0):

> Look only at orientation. Is the main text or numeric display in this image upright, that is, readable without turning the image? Answer with exactly one word: yes, no, or none (there is no text or display).

解析:去掉思考标签、markdown 符号和标点,转小写,取第一个词;不是这三个词之一就算「答非所问」,次数进计数器。已测过的问法只有 yes / no、只说「显示屏」;放宽到「文字或显示屏」并加 `none` 是没测过的改动,所以排在开工前先测。

**怎么转**:不新写旋转代码。裁图函数本来就能「按一个方向值把裁下来的块转正」(`region_zoom.py:347-362`,为方向标记写的);给它加一个「再顺时针转多少度」的入参,与图片自带的标记合成一个方向值。于是:

- 候选副本 = 对整张图(框 `[0,0,1000,1000]`)带角度裁一次,自动缩到约 150 万像素(`region_zoom.py:380-396`)。
- 结论是「正」且图片没有方向标记(上传图都没有,上传时已去掉):整张看仍把原图交给模型,**与今天逐字节相同**。其余情况(转过,或带标记)整张看用对应的候选副本 —— 分辨率比原图低,由 §9.2 的小字横图检验。
- 横条和指定区域照旧从**原像素**裁,坐标换算到转正后的画面;横条规划用转正后的宽高(事故那张转正后 3024×4032,按 §1.3 #10 是 8 条,数字横排)。

要改的调用点是数出来的:把原图引用直接交给模型的 4 处(`vision.py:452,548,574,672`)、读尺寸 1 处(`:713`)、宿主裁图 1 处(`:793-813`)。

**文件与缓存**:都在本次 run 的裁图目录 `.tool_results/<run>/crops/<原图哈希>/` 下(`vision.py:794-801`)。今天裁图文件名只由框决定、已存在就复用(`vision.py:802,811-812`),不同角度会撞名 —— 所以转过的裁图和候选副本放进子目录 `r<角度>/`,0 度沿用现有位置。缓存文件记结论、角度、四个回答。并行的两次 `ask_image` 看同一张图时排队,沿用现有目录锁(`vision.py:809`)。只在一次 run 内有效,跨 run 重问。

**能力怎么传**:工具上加一个布尔字段,装配处(`tools/assembly.py:557`)按「模型目录能力位 且 总开关」填。评测脚本直接构造工具、把这个字段设为真,不依赖发布出去的镜像里目录怎么写(§10)。

**调用路线、限时、计费**:问方向固定走快看那条链,被厂商拒时**不**再走「退回正常看图」的二次路由(`vision.py:866-876`)—— 拒了就算没问成。每次限时 30 秒(普通快看测试环境 30 天最长 28 秒,`vision.py:143-144`),超时算没问成;**看图绝不因为问方向而失败**。每次调用照常扣 token 池、记账(`vision.py:516-523`),并占切块调用的名额(`vision.py:182`)。

### 4.2 工具自己重看(PR 3,最后做)

只管一种情况:`region="auto"` 里有横条报 `partial`。今天是退回整张读并留一句建议(§1.3 #11、#12);改成工具把报 `partial` 的那几条的并集框裁出来,用原问题再快看**一次**,然后:

- 两次读数一致 → 仍给整张读的值,**保留「小字可能不可靠」的不确定措辞**,只把「请用这个区域再问一次」换成「已重看过接缝,同值」。不把「一致」说成「可信」:实测同一模型对同一张横图两次都是 68.1,裁出显示屏也不解决横置(§2)。
- 不一致,或重看没读到 → 两个读数都列出,明说不确定。**不投票、不挑一个**(与现有横条汇总的原则相同,`tile_reading.py:11-13`)。

作用只有一个:省掉主模型「再问一次」那一轮,并且保证真的有人看过。横条之间「冲突」没有单一区域可看,保持今天的报告方式。每次 `auto` 最多多 1 次调用。它对所有看图模型生效(不看能力位),所以措辞只许比今天更保守,并排在 PR 2 之后:事故靠 PR 1 就能修。

### 4.3 如实说

沿用工具结果末尾加括号说明的现有写法(例:`vision.py:553-556`)。平台英文、通用:

| 情况 | 追加的话(初稿) | PR |

| 转过图 | `(The image was stored turned; it was rotated N degrees clockwise before reading. Any region refers to the rotated image.)` | 1 |
| 判不出方向 | `(The text or display in this image does not look upright and its orientation could not be determined, so this reading may be wrong. Say the value is uncertain.)` | 1 |

**不做**:

## 5. 多花多少钱、多慢多少

**次数**(程序保证的上限;这是「逻辑调用」数):

| 情况 | 每张图每次 run 多出的调用 |
|---|---|
| 模型没开这项能力 | 0 |
| 图是正的(绝大多数) | 1 |
| 第 1 步答 no(横 / 倒 / 判不出) | 4(1 + 3) |
| `auto` 里有横条被切开(PR 3) | 每次 `auto` 再 +1 |

一次逻辑调用在主看图模型失败时会顺着备用链往下试,所以**发给厂商的请求数上限 = 4 × 链长**(链长 = 主看图模型 + 配置的备用模型数;没配备用就是 4)。最坏的一次 `ask_image`(大图第一次用 `auto`、横图、有接缝):4 + 8 条 + 1 整张 + 1 重看 = 14 次逻辑调用,今天最多 9 次。费用**只随「图片张数 × run 数」增长**,与对话长度、问了几个问题无关。

**单价假设**(占位;价格在数据库费率表里,本文没有读,未验证):问方向的一次调用 = 一张约 150 万像素的图 + 一句话输入、一个词输出;假设折合约 2,000 个输入 token、输入价 ¥3 / 百万 token → **每次约 ¥0.006**。按这个假设:正图每张 +¥0.006,横图每张 +¥0.024。各家对图片的计 token 方式不同,误差可能到 2~3 倍。

**延迟**:问方向排在读数之前,正图多等 1 次调用,横图多等 2 轮(第 2 轮三次并行)。只输出一个词,应当比普通快看快(普通快看 p95 15 秒、最长 28 秒),但**没有量过**(未验证)。限时 30 秒意味着慢的那一小部分会静默按原图读 —— 这个比例是验收项(§9.2 L6)。「问方向与读数并行、正图零等待」先不做:横图会白读一次,量完再说。

**有多少图会用到**:不知道,目前只有 1 个实例。见待拍板 #3。

## 7. 文档 / 扫描件与知识库:先数,再决定(不在 PR 1~3)

(a) 的做法本身已定(方向分类小模型,把握 ≥ 0.9 才转,转了记下来)。没定的是**值不值得现在做**:它要引入新的推理依赖,而横置的文档页有多少没有数字。先数,方法如下,全部只读、只打印数字:

1. **取样**:测试环境里,(i) 知识库的扫描页图片,(ii) 对话里由平台渲出来给看图工具看的文档页。各随机取最多 500 张;不足就全取。取样脚本只输出张数,不输出文件名、文本或任何内容。存放位置以 B-209 的实现为准,本文没有核对(未验证)。
2. **判**:在本机用同一个分类小模型离线跑(CPU,免费,不调任何付费接口),统计「判为非 0 度且把握 ≥ 0.9」的张数。
3. **抽查**:被判为横置的全部人工看(上限 50 张),再从判为正的里随机看 100 张,得到误转和漏判两个数。人工看在本机做,不外传。
4. **报**:四个数 —— 总张数、判横置张数、抽查确认的张数、漏判张数。
5. **生产**:同一个脚本交给用户在生产跑,同样只出数字。

**做不做的线**(预先写下):横置占比 ≥ 1% 或绝对数 ≥ 20 张,就立项做 PR 4;否则不做,记录数字后关掉这一条。知识库入库的那一半另行设计(入库是批处理,转错了会影响检索,回滚方式不同),本文不展开。

## 9. 验收

### 9.0 第 0 步:开工前的小测量(约 90 次调用,< ¥1;等用户说「跑」)

两件事,都只用合成图,qwen3.8-max-0902 与 doubao-…-260915 各跑一遍:

1. **新问法**(§4.1 那句):28 张集 + 4 张无文字图,各问 1 次 = 每模型 32 次。过线:28 张答对 ≥ 27,无文字 4 张全部答 `none` 或 `yes`。不过线就退回已测过的问法(只问显示屏、只答 yes / no),无文字的图交给 L4 去量。
2. **「像真照片」的合成图能不能复现错读**:做 3 个数值的合成图(透视、反光、背景、手持模糊),各转 90 和 270 度 = 6 张,各读 2 次 = 每模型 12 次。记下 qwen 读错几次 —— 这决定 L3 和 qwen 的对照怎么写(见下)。

### 9.1 不花钱的(单元测试,CI 里跑)

用假的看图模型:只在收到「转了 N 度的合成图」时答 yes,只在收到正放的合成图时读出正确的数(靠合成图里的像素标记分辨)。

- 工具选中 N、读出正确的数、meta 里记了 N —— N = 0 / 90 / 180 / 270 各一条。
- **必须变红的对照**:能力字段为假(或总开关关),同一张 90 度的图读出的是错数,断言失败。这条先于实现写好并确认是红的。
- 四个方向都答 no / 两张都答 yes / 三次里有一次超时或答非所问 → 都按 0 度读 + 「判不出」那句话。
- 第 1 步超时 / 报错 → 看图照常成功,meta 记「没问成」;同一 run 再看这张图不再问,角度不变。
- 同一 run 第二次看同一张图 → 问方向的调用数为 0。
- 同一个框先按 0 度裁、再按 90 度裁 → 两个文件,互不复用。
- 带方向标记的工作区图片、画面再横 90 度 → 第 1 步问的是按标记转正的副本;最终结果与「先按标记转正再转 90 度」逐像素相同。
- 结论「正」且无标记的图 → 交给模型的引用与改动前相同。
- PR 3:有横条报 `partial` → 多且只多 1 次调用;同值时不确定措辞仍在;不同值时两个都列出。

## 12. 哪些智能体要改提示词(平台不代改)

平台只负责读得更准、读不准时如实说。「把读到的数记下来之前先跟用户确认」是业务决定,写在各智能体自己的提示词里,由智能体的负责人改。

**挑选标准**(三条都满足的优先改):

1. **能看图**:走看图工具(有 `vision` 块且主模型不能看图),或主模型自己看图。
2. **会把看到的东西留下来**:开了长期记忆写回,或带有会写入外部系统的工具。
3. **看的是数值**:业务上会让用户拍读数、单据、仪表。这一条程序判断不了,也**不要去搜提示词或对话内容**,由负责人看名单后自己判断。

主模型自己看图的那一类(§8.1)平台这次不修方向,更需要这句提示词。
