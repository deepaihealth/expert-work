## 0. 一页看懂

**出了什么事**:用户上传一张体重秤液晶屏照片(4032×3024,画面顺时针横了 90 度,照片不带方向标记),实际 69.1。看图工具整张快看读成 0.0;`region="auto"` 把图切成横条,横条把躺着的数字拦腰切开,退回整张读成 68.1;工具给了「建议再看这个区域」,但没有任何一方真的去看。

**根因一句话**:平台只按照片自带的方向标记转正,没有标记就原样给模型;而看图模型**能看出**图是横的,却**读不对**横着的数字。

**改三件事**(都在看图工具里,原图不动):

| 序 | 改什么 | 程序保证的 | 靠模型的 | PR |
|---|---|---|---|---|
| ① 先问方向 | 看图前先问看图模型一句「主要文字 / 显示屏是正的吗」;说不正,就把图转 90 / 180 / 270 度各问一次,用它说「正」的那一张来读 | 转图、选哪张、缓存、记进轨迹、每张图最多多 4 次调用 | 「正不正」的回答(实测两家各 28/28) | 1 |
| ② 如实说 | 转过图、判不出方向、两次读数对不上 —— 都在工具结果里写明 | 什么时候写、写什么 | 主模型看到后是否照做 | 1、2 |
| ③ 自己重看 | 横条报「被切开」时,工具自己把那一段裁出来再看一次,不再只留一句建议 | 重看这个动作 | 重看读得对不对 | 2 |

按看图模型逐个开:只有实测「能答对正不正」的模型才开(§6);答不了的模型(例如 glm-4.6v,永远答「正」)保持今天的行为。

**做完之后还剩什么**(详见 §8):

1. **淡笔段读错不修**。屏幕上没点亮的淡笔段是另一个独立原因(豆包把 72.4 读成 2.4,图是正的),转正帮不上。
2. **主模型自己能看图的智能体不覆盖**(测试环境 14 个):图不经过看图工具。
3. **文档 / 扫描件、知识库入库不在前三个 PR 里**:先数有多少横着的,再决定做不做(§7)。
4. **豆包 260628 版本没测过**:测试环境 31 个走看图工具的智能体里 30 个用它;实测的是 260915。开之前要补测(§9)。
5. 「读到健康数值先跟用户确认再记录」不是平台行为,由各智能体自己的提示词负责(§12)。

### 1.4 把事故对回代码

1. 上传:照片没有方向标记 → 表 #1,原样存下(横的)。
2. 主模型(glm-5.3,不能看图)调 `ask_image` 整张快看 → 表 #8,看图模型看到横图,读成 0.0。
3. 图是 4032×3024 = 1219 万像素 ≥ 400 万 → 表 #9,追加了 `region='auto'` 的提示,主模型照做。
4. 按表 #10 的公式手算:宽:高 = 1.33,切横条;ceil(1219 / 150) = 9,夹到 8;8 条时每条约 4032×422(长:短 9.5 > 8)、7 条 8.4 > 8、6 条 7.2 → **切 6 条横条 + 1 次整张 = 7 次调用**。数字是躺着的(沿竖直方向排开),整宽横条正好把它拦腰切开。
5. 有横条报 `partial` → 表 #11,退回整张读的 68.1,附「再问一次或说不确定」。
6. 表 #13:没有人再看。主模型把 68.1 当成了答案。

「横条实际报了什么」来自 ROADMAP B-301 行(两条各读到一半),本文没有重新取那次 run 的轨迹(未验证,§11)。

## 3. 已定的方向与本文的收窄

用户已同意:(a) 文档 / 扫描件用方向分类小模型,把握 ≥ 0.9 才动;(b) 其它照片问看图模型「正不正」,不正就试几个方向,按模型逐个开;(c) 工具自己重看它建议的区域;(d) 工具结果如实写不确定;(e) 转了多少度记进轨迹。「先跟用户确认再记录」归各智能体提示词,平台不改已有智能体。

本文在这个范围内做了三处收窄,理由是「先修量到的问题」:

1. **在看图工具里做,不在上传时做**。上传时没有 run、不知道是哪个智能体的看图模型,轨迹也无处可记;更要紧的是在上传时转 = 改掉用户的原图,模型判错一次,之后每次看都是错的。工具里做只生成一张转正的副本,原图不动,判错了影响限于这一次 run。代价:主模型自己看图的那条路覆盖不到(§8.1)。这是最大的一个取舍,列为待拍板 #1。
2. **按来源分流,不猜图的类型**。用户上传的图、工作区里的图片文件 → 走 (b)。平台渲染出来的文档页、知识库扫描页 → 才是 (a) 的对象。不做「先判断这张上传图是文档还是照片」:小模型在自然照片上误转 22.6%,猜错类型的代价太高。
3. **(a) 排在最后、先数再做**(§7)。事故与实测都是照片;文档页横置有多少还没有数字,而 (a) 要给平台引入一个新的推理依赖(仓库里今天没有 Paddle,§1.1 的搜索 0 命中)。

## 4. 设计

### 4.1 先问方向(PR 1)

**对谁做**:`ask_image` 看的**上传图**和**工作区图片文件**。不做的:文档页(`path` + `unit`,平台自己渲的)、已经是裁图的引用、看图模型没开这项能力的(§6)、没接工作区的构建(转正副本没地方放 —— 与今天 `region` 的前提相同,`vision.py:946-953`)。

**流程**(每张图每次 run 只做一次,结果缓存):

```
1. 问原图:「主要文字或显示屏是正的吗?」
   - yes / none(图里没有文字或显示屏)→ 用原图,和今天一样往下走。
   - no → 第 2 步。
   - 答非所问 / 调用失败 / 超时 → 用原图往下走,只在轨迹里记「没问成」,不对主模型说什么。
2. 把图顺时针转 90 / 180 / 270 度,各出一张缩小的副本,并行各问一次同一句话。
   - 恰好一张答 yes → 用这个角度。之后这次 run 里对这张图的每一次看
     (整张看、横条、指定区域)都在转正后的画面上做。
   - 没有一张答 yes,或不止一张答 yes → 判不出方向:用原图,结果里如实写(§4.3)。
```

**问的那句话**(平台英文,通用,初稿;最终措辞以 §9 的评测为准):

> Look only at orientation. Is the main text or numeric display in this image upright, that is, readable without turning the image? Answer with exactly one word: yes, no, or none (there is no text or display).

解析:去掉思考标签后取第一个词;不是这三个词之一就算「答非所问」。实测用的问法只有 yes / no 两个答案、只说「显示屏」;这里放宽到「文字或显示屏」并加了 `none`,是**没测过的改动**(未验证,§11),所以 §9 用最终措辞重测,并加没有文字的合成对照图。

**怎么转**:不新写旋转代码。裁图函数本来就支持「按一个方向值把裁下来的块转正」(`region_zoom.py:347-362`,为方向标记写的);给它加一个「画面要顺时针转多少度」的入参,与图片自带的方向标记合成一个方向值即可。于是:

- 判方向用的三张副本 = 对整张图(框 `[0,0,1000,1000]`)带角度裁一次,自动缩到约 150 万像素(`region_zoom.py:380-396`)。
- 选定角度后,整张看用同一张缩小的转正副本;横条和指定区域照旧从**原像素**裁,只是坐标换算到转正后的画面 —— 分辨率不损失。
- 横条规划用转正后的宽高。事故那张图转正后是 3024×4032,按 §1.3 #10 的公式是 8 条横条,数字是横排的。

要改的调用点是数出来的:把原图引用直接交给模型的 4 处(`vision.py:452,548,574,672`)、读尺寸 1 处(`:713`)、宿主裁图 1 处(`:793-813`)。

**缓存**:结果写成一个小文件,放在本次 run 的裁图目录里(`.tool_results/<run>/crops/<原图哈希>/`,与现有裁图同一处,`vision.py:794-801`),同一次 run 里再看这张图直接用。范围是「一次 run」:跨 run 会重问一次。并行的两次 `ask_image` 看同一张图时排队,沿用现有的目录锁(`vision.py:809`)。

**坐标**:主模型看不到图,它手里的区域坐标都来自看图模型的回答;转正后看图模型看到的是转正的画面,所以整个 run 里坐标统一按转正后的画面解释。跨 run 如果两次判出的方向不同,上一次的坐标就对不上 —— 少见,接受,写在 §8。

**超时与失败**:每次「问方向」的调用单独限时(初定 20 秒,PR 1 里按实测调整),超时按「没问成」处理,**绝不让看图因为问方向而失败**。计费、扣 token 池与现有每次看图调用一样逐次记(`vision.py:516-523`)。

### 4.2 工具自己重看(PR 2)

只管一种情况:`region="auto"` 里有横条报 `partial`。今天是退回整张读并留一句建议(§1.3 #11、#12);改成工具把报 `partial` 的那几条的并集框裁出来,用原问题再快看**一次**:

- 重看的读数与整张读一致 → 给这个值,注明「接缝处重看过,一致」。
- 不一致,或重看也没读到 → 两个读数都列出来,明说不确定。**不投票、不挑一个**(与现有横条汇总的原则相同,`tile_reading.py:11-13`)。

不管的:横条之间「冲突」的情况没有单一的区域可看,保持今天的报告方式。每次 `auto` 最多多 1 次调用。

### 4.3 如实说(PR 1 写方向两条,PR 2 写重看一条)

沿用工具结果末尾加括号说明的现有写法(例:`vision.py:553-556`)。新增三种,平台英文、通用:

| 情况 | 追加的话(初稿) |
|---|---|
| 转过图 | `(The image was stored turned; it was rotated N degrees clockwise before reading. Any region refers to the rotated image.)` |
| 判不出方向 | `(The text or display in this image does not look upright, and no rotation made it upright, so this reading may be wrong. Say the value is uncertain.)` |
| 重看与整张读不一致 | `(Two looks at this value disagree: A / B. Say the value is uncertain.)` |

同时在工具结果的 meta 里放一个 `uncertain` 列表(原因代码),供评测和 B-300 以后使用;本文不规定 B-300 怎么用。

**不做**:

- 不靠「同一个模型再读一遍、两次一致」来表示可信 —— 实测横图两次都是 68.1(§2)。
- 不改看图模型系统提示词里的 "do not add caveats"(`vision.py:130-134`)。它确实不鼓励模型说「图是横的」,但改它会影响所有看图回答,没有测过;方向这件事改由平台单独问。
- 不在平台文字里写「请用户确认」「健康读数」之类 —— 那是智能体的事(§12)。

### 4.4 记进轨迹(PR 1)

工具结果的 meta 本来就进事件流(`vision.py:456-464`)。新增一个 `orientation` 字段:结论(正 / 无文字 / 已转 / 判不出 / 没问成)、转了多少度、四个方向各自的回答、回答的是哪个模型、是否来自缓存、多花了几次调用。另加一个计数器,按结论和角度分。转正副本本身留在 run 的裁图目录里,排查时可以直接打开看。

## 5. 多花多少钱、多慢多少

**次数**(程序保证的上限):

| 情况 | 每张图每次 run 多出的调用 |
|---|---|
| 模型没开这项能力 | 0 |
| 图是正的(绝大多数) | 1 |
| 图是横的 / 倒的,或判不出 | 4(1 + 3) |
| `auto` 里有横条被切开(PR 2) | 每次 `auto` 再 +1 |

最坏的一次 `ask_image`(大图第一次用 `auto`,横图,有接缝):4 + 8 条 + 1 整张 + 1 重看 = 14 次,今天最多 9 次。费用**只随「图片张数 × run 数」增长**,与对话长度、问了几个问题无关(同一 run 里有缓存)。

**单价假设**(占位,开工前用费率表里的真实价格替换;价格在数据库费率表里,本文没有读,未验证):问方向的一次调用 = 一张约 150 万像素的图 + 一句话输入、一个词输出;假设折合约 2,000 个输入 token、输入价 ¥3 / 百万 token → **每次约 ¥0.006**。按这个假设:正图每张 +¥0.006,横图每张 +¥0.024。厂商对图片的计 token 方式各不相同,误差可能到 2~3 倍。

**延迟**:问方向排在读数之前,正图多等 1 次快看的时间,横图多等 2 轮(第 2 轮三次并行)。问方向只输出一个词,应当比普通快看快(普通快看测试环境 30 天 p95 为 15 秒,`vision.py:143-144`),但**实际多少没有量过**(未验证);PR 1 的真栈验收里报中位数和 p95。「问方向与读数并行、正图零等待」可以做,但横图会白读一次,先不做,量完再说。

**有多少图会用到**:不知道。目前只有 1 个实例。见待拍板 #3(先数再开工)。

## 7. 文档 / 扫描件与知识库:先数,再决定(不在 PR 1~3)

## 8. 这个设计修什么、不修什么

| 问题 | 修不修 | 说明 |

## 9. 验收

### 9.1 不花钱的(每个 PR 的单元测试,CI 里跑)

用假的看图模型:它只在收到「转了 N 度的那张合成图」时答 yes,只在收到正放的合成图时读出正确的数(靠合成图里的像素标记分辨)。

## 12. 哪些智能体要改提示词(平台不代改)

平台只负责读得更准、读不准时如实说。「把读到的数记下来之前先跟用户确认」是业务决定,写在各智能体自己的提示词里,由智能体的负责人改。

**挑选标准**(三条都满足的优先改):

1. **能看图**:走看图工具(有 `vision` 块且主模型不能看图),或主模型自己看图。
2. **会把看到的东西留下来**:开了长期记忆写回,或带有会写入外部系统的工具。
3. **看的是数值**:业务上会让用户拍读数、单据、仪表。这一条程序判断不了,也**不要去搜提示词或对话内容**,由负责人看名单后自己判断。

主模型自己看图的那一类(§8.1)平台这次不修方向,更需要这句提示词。

**测试环境查询**(只读;只输出名字、版本、模型名和是 / 否,不输出提示词、不输出任何对话或客户文字):

```sql
-- 先确认「在用」的状态值:SELECT status, count(*) FROM agent_spec GROUP BY status;
SELECT name, version,
       (spec_json->'spec'->'vision') IS NOT NULL
         AND NOT COALESCE((spec_json->'spec'->'model'->>'supports_vision')::bool, false)
                                                        AS uses_ask_image,
       COALESCE((spec_json->'spec'->'model'->>'supports_vision')::bool, false)
                                                        AS main_model_sees_images,
       spec_json->'spec'->'vision'->'model'->>'name'    AS vision_model,
       spec_json->'spec'->'model'->>'name'              AS main_model,
       (spec_json->'spec'->'memory'->'long_term') IS NOT NULL
         AND COALESCE((spec_json->'spec'->'memory'->'long_term'->>'write_back')::bool, true)
                                                        AS writes_memory
FROM agent_spec
WHERE status = '<在用的状态值>'
  AND ((spec_json->'spec'->'vision') IS NOT NULL
       OR COALESCE((spec_json->'spec'->'model'->>'supports_vision')::bool, false))
ORDER BY writes_memory DESC, uses_ask_image DESC, name, version;
```

自检:测试环境里 `uses_ask_image` 为真的应是 31 行、`main_model_sees_images` 为真的应是 14 行(§2 的数);对不上说明查询或表结构理解有误,先停下。字段路径取自 `agent_spec.py:1537-1566`(`AgentSpecBody`)与表定义 `packages/expert-work-persistence/src/expert_work/persistence/models/agent_spec.py:20-32`。「带写入外部系统的工具」没有写进查询:工具清单里哪些会写入要人看,第一轮先按记忆写回筛。

**生产**:同一条 SQL,由用户用只读账号执行;我不连生产。把结果里的行数和 `name / version` 两列发回即可,其余列按需。连接方式用现有的只读连接,**不要把连接串打到终端或粘贴出来**。

**建议的提示词措辞**(通用,各智能体按自己的口吻改写,加在自己的提示词里):

> 从图片里读到的数值(读数、金额、日期、编号等),在写入记录、记入记忆或用于计算之前,先把读到的值原样告诉用户,请对方确认或更正。看图工具提示「不确定」或给出两个不同读数时,如实告诉用户看不清,请对方确认或重新拍一张正放、清晰的照片,不要自己挑一个。用户确认之前,不要把这个数当作已知事实。
