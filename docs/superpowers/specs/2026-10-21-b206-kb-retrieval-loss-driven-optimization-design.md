## 2. 诊断结论

### 2.1 头号原因:切块太碎,答案在相邻块里没交给模型

- 89 题正确文档共 4,253 段:**中位 264 字符**(p25 183、p75 396),30% 不到 200 字符;而切块上限是 512 token(英文约 2,000 字符)。
- 答错 / 不全的题里,正确文档平均每段不足 500 字符的占比:C 59%、B 84%、D 59%;**全对的 201 题只有 31%**。正确文档本身并不更长(中位 6.4 KB vs 5.5 KB)。全库 21% 的文档占了 48% 的段。
- 例子:一份 33 KB 会议记录切成 145 段;1.5 KB 的故障复盘切成 9 段(其中一段只有「P1」);1.4 KB 的客户记录切成 3 段。
- 后果:检索命中的常是摘要 / 标题那一小段,答案在旁边那段;模型要么说「资料里没写」,要么拿相似文档凑。**C 类「说资料没写」的 8 题,全部是答案所在的那段没被返回**,不是拒答提示的问题。
- **通用性已核**:测试环境唯一的中文知识库(1 篇、41 段)中位 134 字、83% 不到 200 字,上限 1,024 token——同样碎(样本小,开工时在华大开发集上复核)。
- 代码原因:`chunking.py:97` `MIN_SEMANTIC_CHUNK_TOKENS = 32`,语义断点只要缓冲区够 32 token 就切;B-175 设计 §5 定的目标是 300~500 token、同一父标题下相邻短节合并,实现没达到。

### 2.2 C / B / D 逐题分类(按修复落在哪一层)

| 组 | 检索排序 | 结果呈现(碎片 / 缺上下文 / 缺元数据) | 评测提示词(只评测有) | 判分 | 合计 |
|---|---|---|---|---|---|
| C 找到了仍答错 | 11 | 10 | 6 | 3 | 30 |
| B 只找到部分 | 8 | 4 | 0 | 1 | 13 |
| D 判对但不全 | 14 | 7 | 6 | 19 | 46 |

按原因:选了相似的干扰文档 21、说资料没写 9、列举不全 12、答案段没返回 12、漏检某篇 8、读错 / 版本混 4、判分存疑 23。

### 2.3 判分噪声

D 组 46 题里 19 题我方答案其实写了被判缺的内容(有的近乎逐字);C 组 3 题、B 组 1 题是与标准答案的争议。对别家同样严,**排名对比不受影响,绝对分偏低**。另:qst_0413 标准答案文档重复且对应两份内容冲突的文件;qst_0450 标准答案「8 篇」与语料不符;0061 / 0222 / 0287 / 0082 / 0128 / 0447 有近乎相同的干扰文档,标准答案本身有歧义。

### 2.4 检索重放:A / B 类正确文档丢在哪一步

10-21 按评测时的代码(wt-b198)重建同一个库(104,966 篇 / 855,880 段,嵌入全部命中缓存),重放 82 题里模型当时的 369 次检索,再用题目原文各搜一次;80 / 82 题重放结果与评测时逐篇一致(差的 2 题正是评测时重排被限流的那 2 题),花费 ¥1.24。按(题, 正确文档)计 203 对,取模型所有查询里走得最远的一步:

| 正确文档最远走到 | 模型的查询 | 题目原文 | 含义 |
|---|---|---|---|
| 两路前 50 都没有 | **57(28%)** | 111 | 真正的召回失败;24 题所有正确文档都在这一档 |
| 进了某一路,合并后掉出前 50 | 21(10%) | 16 | 合并名次全在 52~94(向量路 14、关键词路 7) |
| 进了前 50,被重排挤出前 20 | 13(6%) | 4 | 重排池名次 4~48,全部是被「带标题视图」的前 20 截掉 |
| 重排后在前 20,但排在模型要的条数之后 | **37(18%)** | 25 | 369 次检索里 279 次(76%)用的是默认 5 条 |
| 已显示给模型 | 75(37%) | 47 | |

结论:
- **条数太少是最便宜的一块**:37 对卡在「排得进前 20、但只给 5 条」。按文档分组后取前 10 篇,37 对里 20 对会显示;按段取前 15 条会显示 30 对 → 直接支持 K-4。
- **重排环节漏掉 34 对**:合并后掉出前 50 的 21 对,合并名次都在 100 以内 → 重排候选从 50 加到 100 能全部收进来;被带标题视图截掉的 13 对里有 3 对在重排池前 16 → 支持 K-14(两项都做对比)。
- **真正召回失败 57 对(28%)**:题目原文直接搜更差(111 对),说明「怎么问」影响很大;这些正确文档段数偏少(中位 9 段 vs 已显示的 13 段),检索入口少。这一块要靠查询侧(K-5、K-10)或索引侧(K-3、K-11 / K-12、K-9)补,重放分不出哪个更有效 → 在华大开发集上对比决定。

### 2.5 评测工具本身的限制(不算产品问题)

- 评测脚本每题最多 5 次检索:89 题(25%)用满,这些题平均 29.4 分、其余 84.4 分;用满的题里 40 题从头到尾没找到正确文档——**用满多半是找不到的症状**。另有几题模型只搜 2 次就停(0341 / 0364 / 0376)。
- 评测时 85.5 万段单次检索中位 11.8 秒、P90 25.4 秒:这是评测脚本**故意用精确扫描**保证可复现;生产走 HNSW 近似索引(迁移 0021),不能据此推断生产延迟。

## 4. 设计原则

1. **通用**:每条写明对真实租户资料(中文营养资料、合同、操作规程、会议纪要、销售对话)是否成立;只对评测资料管用的不做(§7)。
2. **只改平台层**:检索、切块、知识库工具及其说明;评测脚本的提示词不算。
3. **评测集只诊断**:开发阶段在华大开发集(303 题)上前后对比;评测集最后复测一次当留出集。
4. **先量再做**:有外部实测数字的优先;没有的先做对比试验;收益是假设的能力以评测结果决定开不开(同 B-175 原则 6)。
5. **默认开启**:新能力默认就开,不让租户自己去配。
6. **前端同步**:凡是改变了模型拿到什么,分段预览 / 检索测试 / 轨迹面板三处同步改(§6)。

## 5. 方案清单

每条:改什么 / 治哪类 / 依据 / 通用性 / 代价 / 验证判据。工作量 S = 1~2 天,M = 3~5 天,L = 1~2 周。

### 5.1 第一梯队:便宜、直接对症

**K-1 父子块(自动带上下文)** —— M
- 改:命中小段后自动带上前后各 1 段(同一标题内);短文档(约 6 KB 以内)直接给整篇;同一篇命中多段时合并去重;单次结果设总字数上限;用上 `parent_chunk_id`。
- 治:诊断里「正确文档已显示、答案在没返回的段里」约 22 题(C 11、B 4、D 7,逐题见诊断记录)。
- 依据:Dify 父子块模式(父段交给模型)、RAGFlow「用子块检索」、FastGPT「分块大小 / 索引大小」分离;Onyx 合并同文档相邻段、按需扩到 ±5 段。
- 通用:高。代价:每次结果字数上升,用总字数上限压住。
- 判据:华大开发集答对率不降、「说资料没写」的错答下降;单次结果平均字数在上限内。

**K-2 「读文档」工具(模型自己决定读多少)** —— M
- 改:新增 `knowledge_read(文档, 范围)`:读某段的相邻段 / 某一节 / 整篇(长文档分页);B-175 P4 设计过。
- 治:同 K-1,加「找全」题。
- 依据:Mixedbread 在 BrowseComp-Plus 上让 agent 能读整篇后 80.00 → 90.48;LlamaIndex 自测「自动合并」单独用与基线差不多——**提分来自模型按需读,不是系统自动塞**,所以 K-1 只带 ±1 段,K-1 与 K-2 在开发集上对比。
- 通用:高。代价:多一两次工具调用。
- 判据:开发集答对率上升;工具调用次数增幅可接受。

**K-3 修切块大小,达到 B-175 设计目标** —— M,要重新入库
- 改:最小断点从 32 token 提到约 200;标题切换时短节向同级合并到上限;对话 / 会议纪要不按每人一句切;切块参数变更按 B-175「新版本」规矩建好再切换。
- 治:根因,A / B / C / D 都有。
- 依据:§2.1 数据(答错题的碎片占比 59~84% vs 全对题 31%);B-175 设计目标 300~500 token。
- 通用:高(中文库同样碎,§2.1)。代价:所有知识库重新嵌入(生产 10-13 查时 0 个知识库,开工前再核)。
- 判据:开发集答对率不降;段长中位落在 300~500 token;召回不降。

**K-4 结果按文档分组 + 显示文档信息并交给重排** —— S
- 改:同一文档最多 2~3 段、相邻段合并;默认条数 5 → 10 左右(总字数上限内);每条带文档标题、日期 / 版本 / 生效日期(有就显示)、来源;这些信息也拼进送重排的文本。
- 治:找全、相似文档混淆、项目关联;重放里「排得进前 20、但只给 5 条」的 37 对(18%),按文档分组取前 10 篇可显示其中 20 对(§2.4)。
- 依据:Onyx 每节最多 3 段、结果按文档分组并带标题 / 更新时间 / 作者 / 来源;Cohere 重排最佳实践建议文档带 Title / Date;metor「钉住能区分相似文档的属性」;Anthropic:前 20 比前 10 / 前 5 好。
- 通用:高(合同、制度、SOP 都有版本和生效日期)。代价:结果 token 增加 2~3 倍,用总字数上限压。
- 判据:开发集「找全 / 相似文档」类题答对率上升。

**K-5 查询向量声明「这是问题」** —— S,不用重新入库
- 改:嵌入改走 DashScope 原生接口,查询带 `text_type=query`(英文可加 `instruct`),入库仍是默认 document。
- 治:A 类向量那一路。
- 依据:阿里云 text-embedding-v4 文档建议短查询检索长文本时区分 query / document;`instruct` 厂商自称提升 1%~5%;OpenAI 兼容接口不支持这两个参数。
- 通用:高(中文优先的模型)。代价:几乎为 0。可能要重标定知识库的向量分数阈值。
- 判据:开发集召回上升;阈值重标定后拒答率不变。

**K-6 搜索工具说明加两句** —— S
- 改:平台 `knowledge_search` 工具说明里加:① 下结论前逐条核对问题里的条件,依据要出自读到的原文;② 「找全 / 列出所有」类问题换词继续搜,直到搜不出新文档为止。写在工具说明里——没挂知识库的智能体看不到(平台提示词跟着能力走)。
- 治:C 里漏条件 / 读错;B 里搜两次就停。
- 依据:metor「agent 读到了再下结论」;Onyx 论文多轮探索在「找全」上召回 59.0(单次关键词 46.5);Azure agentic retrieval 一问拆约 3 个子查询。
- 通用:高。代价:每题可能多搜一两次。
- 判据:开发集编造数不升、找全类召回上升。

### 5.2 稳定性(随第一梯队做)

**K-7 重排限流** —— S
- 改:纯文本知识库改用纯文本重排模型;客户端按速率排队;429 / 过载 / 5xx 按带随机抖动的指数退避重试若干次,仍失败才退回融合序,保留「已降级」标记。
- 依据:阿里云限流表:`qwen3-vl-rerank` 600 次 / 分钟,`qwen3-rerank` 5,400、`gte-rerank-v2` 5,040;我们双视图每次检索调两次;阿里云错误码文档建议匀速 + 退避 + 排队。评测第二轮实际出现 4 次 429、3 题受影响。

**K-8 嵌入报错** —— S
- 改:入库时 `InternalError` 类 400 重试一次;检索时嵌入失败改走纯关键词并标记降级,不再无声失败。
- 依据:评测预热时实际遇到 400 `InternalError.Algo.Embedding_pipeline_Error`;Onyx 嵌入带退避重试。

### 5.3 第二梯队:等重放 / 对比结果再定

**K-9 关键词路改成 BM25(对比试验)** —— M
- 依据:Onyx 论文在 ERB 上 BM25 基线 68.8 正确率 vs 向量 51.4,语义改写题上 BM25 也更好;《BM25 Wins at Scale》全量 BM25 50.5 vs 向量 29.9。ParadeDB 有 jieba BM25,但是 AGPL 且 RDS 装不了扩展 → 在现有 tsvector 上补词频饱和与长度归一。
- 通用:高。判据:开发集对比现有计分,召回 / 答对率择优。

**K-10 多路查询** —— M
- 改:原问题一路 + 一路「关键词查询」(要求保留专有名词、不扩写生僻词)+ 一路「换说法」,加权 RRF;重复检索时跳过扩写。
- 依据:Onyx 现成做法(换说法权重 1.3、关键词 1.0、模型原查询 0.7、原问题 0.5);query2doc 对 BM25 提升 3%~15%;模型扩写对陌生术语会失效 → 必须留原问题一路。
- 通用:中高。代价:每次检索多一次小模型调用(0.5~2 秒,可与第一路并行)。

**K-11 入库时给每段写一句说明(上下文化切块)** —— L,要重新入库

- 通用:高(与语言无关)。代价:每段一次便宜模型调用(按文档缓存)。与 K-12 二选一。

**K-12 每段配几个「可能的问题」** —— L,要重新入库
- 依据:Doc2Query-- 效果 +16%、索引 −33%;RAGFlow 自动生成问题 / 关键词,FastGPT 多索引;B-175 计划过(`chunk_type=question` 折叠回主段)。
- 通用:高(把用户的说法放进索引)。代价:每段一次模型调用 + 索引行增多。

**K-13 「列出所有相关文档」工具** —— M
- 改:`knowledge_list_documents(关键词, 过滤)`:在现有 tsvector 上按文档聚合,穷举列出命中文档(带标题 / 日期 / 命中次数),供「找全」逐篇读。

**K-14 重排环节调参(候选池 + 标题视图)** —— S
- 改:① 重排候选从合并后前 50 加到前 100;② 「带标题视图」先截前 20 再给正文视图,改成两个视图都在整池上打分,或调低 `_TITLED_VIEW_WEIGHT = 0.7`(0.3~0.5);两项分别在开发集对比。

**第二梯队取舍(重放后定)**:

## 7. 不做(带理由)

| 做法 | 理由 |
|---|---|
| 知识图谱 / GraphRAG / LightRAG / 全库地图(AtlasNav) | 建库成本高;《BM25 Wins at Scale》显示大规模企业资料上图方法低于 BM25;AtlasNav 在找全(66.98)和项目题(59.09)上仍弱 |
| RAPTOR 分层摘要 | 收益在单篇长文综合(QuALITY +20%),不是我们丢分的地方;建库成本高 |
| 迟分块(late chunking) | 要逐词向量,DashScope 不提供 |
| 文档摘要索引 | Anthropic:通用摘要「收益很有限」、摘要索引「效果低」 |
| 按时间自动降权 / 新版覆盖旧版 | 全国版与地区版政策可以并存;改成显示日期让模型判断(K-4) |
| 激进的相似文档去重 | 会藏掉有冲突的版本;只去字节完全相同的 |
| 不留原问题的纯扩写 / HyDE | 对内部术语失效(K-10 必须留原问题一路) |
| 按 ERB「语义改写」题风格调提示词 | 那类题是故意压低关键词重合度生成的,属于过拟合 |
| 修字面 `\n` 转义的单行文本 | 评测语料特有格式(9,518 篇),租户资料罕见 |
| 按来源 / 连接器划范围、按目录树导航 | 租户是上传文件,没有 Slack / Jira 连接器与有意义的目录 |
| 照搬榜单前几名的答题模型 | 不是检索问题 |
