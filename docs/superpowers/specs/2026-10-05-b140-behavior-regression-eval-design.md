# B-140 行为回归评测集第一版 —— 设计稿

> ROADMAP B-140(C 档,波次 1)。专项计划 `docs/superpowers/plans/2026-10-02-harness-quality-program.md`。
> 2026-10-05 起草。用户规矩(10-02):设计与开发直接做,不逐项等批准;合并等用户说「合并」。

## 1. 要解决什么

提示词、工具、模型、执行层的改动,目前靠「临时重放一段真实对话 + 一次金丝雀」放行(B-126 / B-128 /
B-129 / B-131 / B-136 / B-137 / B-149 都是这样验的)。问题:

- 每次重放都是现写的探针,换一个人、换一项改动就重写一遍,结果不能横向比;
- 只看「这一项修好没有」,看不到「别的地方有没有被带坏」—— B-129 就是重放才发现修改轮变差、整单关掉;
- `tools/eval` 里的 golden / regression 目录从 2026-05-18 起是空的,`m0_baseline` 只测纯函数,**没有任何一个评测会把任务交给真的智能体跑一遍**(现状摸底见 §11)。

**目标**:一套固定的合成任务,能在测试环境上对「改动前 / 改动后」各跑一遍,出一张对照表 —— 哪些任务从过变成不过、哪些反过来、token 与耗时涨落多少。B-136 之后的每一项改动(含 B-141 / B-143 / B-148)都用它证明有效、没带坏别的。

**算成功**:

1. 一条命令跑完整套(24 个任务 × 每个 3 次),在测试环境 40 分钟内出结果;
2. 一条命令对比两次结果,出 Markdown 对照表;
3. **能红**:故意做一个已知的坏改动(见 §9 自证),对照表必须把受影响的任务标成退步;
4. 客户数据零接触:任务、虚构客户、判据全部是合成的,全程不读生产、不读对接方租户。

## 2. 用户拍板(2026-10-05)

| 问题 | 拍板 |
|---|---|
| 任务数据从哪来 | **纯合成**。按线上失败的**形态**自己编任务和虚构客户;客户对话原文一个字都不进仓库 |
| 第一版围绕哪个智能体 | **通用 + ai-health-plan**:一半用通用测试智能体,一半模仿 ai-health-plan 的形态 |

失败形态不用再去生产统计:ROADMAP B-122 ~ B-151 各行已有波次 0 / 复盘的实测数字(§7 每个任务都标了出处)。

## 3. 不做什么

- **不做 LLM 打分**。第一版判据全部是代码可判的(结束方式、产物、文件内容、工具调用形状);LLM 判分有方差、要额外的钱和凭据,判「做没做完」也正是 B-148 的范围,等那时再加。
- **不进 CI**。真跑要模型、沙箱和测试环境,CI 只跑框架自己的单元测试(Mock 传输层)。
- **不碰生产、不碰对接方租户**(§8)。
- **不接 `eval_dataset` 表 / 差评回流(B-46)**。B-46 的形状是「真实差评 → 数据集」,与纯合成的拍板相反,本条不并入,ROADMAP 里另行排期。
- **不复用控制台的评测页(EvalRuns)**。那套是 `eval_worker` 在 control-plane 进程里跑无工具的 harness,跑不了带沙箱、带技能的多轮任务;第一版结果落本机文件。

## 4. 方案比较

| 方案 | 做法 | 优点 | 致命问题 |
|---|---|---|---|
| **A 在测试环境真跑(采用)** | 本机脚本走对外 API:建会话 → 发一轮或多轮 → 读流 → 下载产物 → 判分 | 跑的就是线上那条路径:真模型、真沙箱、真技能、真 B-126 剪裁、真队列 | 慢(分钟级)、要钱、有方差 → 用重复 3 次与统计规则兜(§6) |
| B 进程内脚本化模型 | 照 `trace_eval` 用 `_ScriptedLLM` 驱动真图 | 确定、免费、能进 CI | 模型的回复是写死的,**测不到模型行为** —— 而 B-136 / B-137 / B-149 / B-131 全是「改了以后模型会不会换种做法」 |
| C 进程内真模型 + 假沙箱 | 本机起图、真调模型、文件操作打到内存假沙箱 | 比 A 快 | 假沙箱与线上分叉(B-124、W2-BUG-1 都是真沙箱才有的问题);技能脚本跑不了;要在本机拿模型密钥 |

方案 A 的方差问题有现成答案(重复 + 只认稳定翻转),B / C 的问题是结构性的(测不到要测的东西)。

## 5. 架构

```
tools/eval/                    沿用该目录的平铺约定(无包、conftest 把目录放进 sys.path)
  behavior_schema.py           用例 / 运行记录 / 结果的 pydantic 模型 + 加载 + 结果读写
  behavior_extract.py          从产物取文本(docx / pptx 用标准库读 zip 里的 XML,不加依赖)
  behavior_checks.py           判据,纯函数:输入一次运行的记录与取回的文件,输出逐条判定
  behavior_client.py           对外平面客户端(httpx;上传、流式一轮、取产物 / 工作区文件、归档)
  behavior_runner.py           CLI:跑整套 → 写结果 JSONL
  behavior_compare.py          CLI:两份结果 → Markdown 对照表 + 有稳定退步时退出码 1
  test_behavior_*.py           单元测试(MockTransport / 纯函数)
  datasets/behavior/
    agents/                    两个评测智能体的 manifest(入库,随用例版本走)
    cases/                     用例,一个文件一个任务(YAML,文件名 = id)
    fixtures/                  开局要上传的合成文件 + 生成脚本
```

**数据流**(每个任务的每一次重复):

1. 新的 `user_id`(`b140-<run-label>-<case>-<rep>`)→ 工作区天然是空的(工作区按「用户 × 智能体」划分,复用 user_id 会把上一次的 `PLAN.md` 带进来,B-133 那类任务就测不准);
2. 有开局文件就先 `POST /v1/agents/{code}/uploads`,拿 `upl_` id;
3. 按用例逐轮 `POST /v1/agents/{code}/runs`(流式),多轮用同一个会话;
4. 从流里收:工具调用序列(名字 + 关键参数)、最终文本、结束帧的 `status` / `completed` / `exit_reason` / `artifacts`;每轮结束后 `GET /v1/agents/{code}/runs/{run_id}/usage` 拿 token 数;记墙钟;
5. 取用例点名要检查的文件:产物走 `GET /v1/agents/{code}/artifacts/download`,工作区文件走 `GET /v1/agents/{code}/workspace/file`(被改的文件不必要求模型另存产物,直接读工作区);
6. `checks.py` 判分;一行结果写进 JSONL(只存判定、计数、指标与产物的**摘要**,不存全文);
7. 归档会话(`DELETE /v1/agents/{code}/sessions/{session_id}`,软归档)。

**只用对外平面**(`/v1/agents/{code}/...`):API key 打控制台平面(`/v1/sessions/...`)会被 `console_only()` 直接 403。上面七步用到的接口对外平面都有,与第三方对接方走的是同一条路。

**并发**:默认 4 路(每个任务自己的会话与用户,不撞 B-139 的同会话排队);可调。
**失败处理**:网络错误 / 5xx 重试 2 次;仍失败记为 `infra_error`(**不计入**过 / 不过,对照表单列,避免把环境抖动算成退步 —— 「发布闸门红了可能是受害者」那条教训)。

## 6. 用例格式、判据与对照规则

### 用例(YAML)

```yaml
id: g02-edit-three-places
agent: eval-general          # eval-general | eval-ahp
shape: B-137                 # 来自哪条失败形态(ROADMAP 编号)
fixtures: [report-300-lines.md]
turns:
  - prompt: |
      工作区里的 report-300-lines.md 有三处数字过时了:……(具体三处,实现计划里写死)。只改这三处。
checks:
  - {type: completed}                          # completed == true 且 exit_reason == text_response
  - {type: workspace_file_contains, path: report-300-lines.md, all: ["2026 年 9 月", "1,234"]}
  - {type: workspace_file_unchanged_lines, path: report-300-lines.md, fixture: report-300-lines.md, except_lines: [12, 140, 288]}
  - {type: tool_used, tool: edit_file}
  - {type: tool_not_used_on, tool: write_file, path: report-300-lines.md}
metrics: [tokens_in, tokens_out, tool_calls, wall_s]
```

### 判据类型(第一版全部代码可判)

| 类型 | 判什么 |
|---|---|
| `completed` | 每一轮结束帧 `status == "success"`、`completed == true` 且 `exit_reason == "text_response"`。**由用例显式列出**,不默认加:「诚实报不能完成」类任务(g12 / h10)读不存在的文件本身就是一次工具失败,`completed` 按定义就是 false |
| `exit_reason` | 指定结束方式(诚实报不能完成的任务要 `text_response` + 文本判据) |
| `final_text_contains` / `final_text_regex` / `final_text_not_contains` | 最后一轮回复 |
| `artifact_exists` | 产物按名字(或 glob)存在 |
| `artifact_contains` / `artifact_not_contains` | 产物文本(`.docx` / `.pptx` / `.pdf` 本机抽文本后判) |
| `artifact_unchanged_lines` | 与开局文件逐行比,除指定行外不变(抓「整篇重写顺手改坏别处」) |
| `workspace_file_contains` / `workspace_file_unchanged_lines` | 同上两条,但读工作区里的文件(改已有文件的任务不要求另存产物) |
| `tool_used` / `tool_not_used` / `tool_count_max` | 工具调用形状 |
| `tool_not_used_on` | 某工具没有用在某路径上(抓「改已有文件却整篇 write_file」) |
| `turn_tokens_max` | 某一轮输入 token 上限(B-126 / B-128 那类「越聊越贵」) |

判据只认**行为的结果**,不认措辞。每条新判据在单元测试里必须能红(先构造一份「坏记录」证明它会判不过)。

### 重复与对照规则

- 每个任务跑 **3 次**,记过了几次(0 ~ 3);
- **稳定退步**:改动前 ≥2/3 过、改动后 ≤1/3 过;**稳定进步**反之;其余变化记「抖动」,对照表单列但不下结论;
- 指标(输入 / 输出 token、工具调用数、墙钟)比**中位数**,涨跌超过 20% 标出;
- `compare.py` 有稳定退步时退出码 1,方便放进发版前的检查步骤;
- 对照表另附一段「每个任务每次的判定明细」,定位到哪条判据翻了。

### 三种对照方式

| 改了什么 | 怎么对照 |
|---|---|
| 平台代码(执行层、工具、剪裁…) | 先在测试环境当前版本上跑一遍存基线,`release.sh test` 发候选,再跑一遍,`compare` |
| 提示词 / 工具清单 / 模型 | 不用发版:建一个改过的评测智能体副本(另一个 agent code,如 `eval-ahp-b`),`runner --agent-map eval-ahp=eval-ahp-b` 跑一遍,与原版对照。对外 API 只认 agent code、总是跑当前生效版本,所以用两个 code 而不是两个版本号 |
| 只想看现状 | 跑一遍,与上一次存档的结果比 |

每份结果文件头记:标签、时间、目标地址、`--note`(写测试环境镜像 tag 等,对外 API 拿不到 `agent_spec_sha256`)、agent code 替换表、用例集版本(用例与 fixtures 的内容哈希)、重复次数。对照时这几项不同会写在表头,用例集不同直接拒绝对比。

## 8. 运行在哪、凭据、清理、成本

- **测试环境、对接方租户(用户 10-05 拍板,不新开租户)**。原方案是独立评测租户;但平台没有「切到别的租户」的能力,新租户要先建首位管理员账号才能建服务账号与 key,用户定直接用对接方租户 + 现成的 canary key(Secret `canary-credentials`)。代价:每次运行在对接方租户里新建一批 `b140-…` 用户(会话跑完归档,用户条目留着)。评测智能体由用户的控制台登录态导入同一租户(新建智能体只能走控制台平面)。
- **凭据**:runner 从环境变量 `EXPERT_WORK_API_TOKEN` 读 key(沿用 `verify_live` 的约定),key 只经 `kubectl get secret … | base64 -d` 进变量,不进命令行参数、不落文件、不打印。
- **清理**:每个会话跑完即归档;`b140-` 用户条目留在对接方租户里(平台没有删用户的接口)。自证用的 `eval-general-broken` 用完即删。
- **成本**:24 × 3 = 72 次运行、约 110 轮。耗时按 4 路并发估 30 ~ 40 分钟。token 第一次跑完实测后写进 ROADMAP;评测智能体 manifest 里设单 run token 上限,防一个任务失控。

## 9. 怎么证明它能红(自证)

1. **判据层**:`checks.py` 每种判据配「好记录过 / 坏记录不过」两条单元测试,坏记录照真实失败形态构造;
2. **端到端层**:第一次上线时跑两遍 ——
   - 基线:`eval-general`;
   - 坏候选:另建 `eval-general-broken`,**只改系统提示词**:要求「修改已有文件一律 read_file 读全文、write_file 整篇写回」,模拟 B-137 修之前「改文件只能整篇重写」,`--agent-map eval-general=eval-general-broken`。**不能靠在 manifest 里删工具**:`exec_python` / `bash` / 读写改文件等是平台基础能力(`BASE_CAPABILITY_BUILTINS`),每个智能体都有、与 manifest 的 `tools` 无关(10-05 smoke 实测:删了照样调用);
   - 判据:`compare` 必须把 g02 / g03 / g04 / h06 至少三个标成稳定退步、退出码 1;其余任务不该出现稳定退步(否则说明噪声太大,先调重复次数或阈值)。
3. **重复性**:基线自己跑两遍对比,稳定退步必须为 0(同一版本对自己不该「退步」)。

三步都过才算 B-140 交付。

## 10. 风险

| 风险 | 处置 |
|---|---|
