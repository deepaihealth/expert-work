## 1. 现状(2026-10-07 读代码 + 测试环境实数)

**什么时候压缩**(B-126 起,不是旧的「窗口 70%」):
- 新一轮开头先做跨轮清理(不看窗口):本轮开始估算 ≥ 3 万 token 且能省 ≥ 5 千,把更早轮次的大块工具结果换成可重读的引用。
- 每次调模型前三道闸,门槛都是 `min(窗口 × 0.7, 20 万)`:① 收起旧工具结果 → ② 工作窗口(只留第一轮 + 最近 20 轮)→ ③ **模型写摘要**(本设计只动这一道)。
- 摘要写回检查点,下一轮复用(B-126 PR2)。

**摘要这一步现在怎么做**(`orchestrator/context/compressor.py`):
- 保留开头 4 条、末尾 6 条,中间全部交给摘要模型。
- 中间每条消息截到 2,000 字符(头 2/3 + 尾 1/3);整段拼起来再截到 **24,000 字符(约 6 千 token)**,同样是头 2/3 + 尾 1/3。
- 门槛 20 万 token 时,中段可达十几万 token(约 60 万字符量级),摘要模型**只看到约 4%**;而且整段按头尾截,**中段的中间部分整块看不到** —— 恰好是「做到哪一步」最可能在的地方。
- 摘要格式固定三段 `## Facts / ## Decisions / ## Pending`,规则里写着「不要推测后续步骤」—— 没有一段专门记「做到哪一步、下一步是什么」。
- 摘要用 Agent 主模型(`agent_factory.py` 传的是 `metered_default`)。

**实际触发情况**:测试环境 08-14 以来 1606 个 run,`run_event` 里 `compaction` 事件 0 条;生产流量更低。这一步几乎从不触发,所以**改它的风险低、价值也要靠专门造的用例才看得出来**(不能等真实数据)。

**依据**(ROADMAP B-141 行):三篇预印本显示压缩的主要伤害是模型丢失「做到哪一步」,且集中在少数几次压缩上。

## 2. 目标与不做

做:
1. **B-141-a 读得更全**:摘要输入从约 6 千 token 放到约 4 万 token,截断改成「先砍旧工具结果、不砍用户和助手的话」,不再整块丢掉中段的中间。
2. **B-141-b 固定保留进度**:摘要加一段 `## Progress`(已完成的步骤和结果、正在做的一步、紧接着的一步),更新模式下这一段**整段替换为最新状态**,不与旧的合并。
3. **B-143 摘要改用便宜模型**:默认用主模型**同一家**的便宜型号(智谱 `glm-5.3` → `glm-5.3-flash`);没有对应型号的厂商照旧用主模型;便宜模型调用失败时当次退回主模型。

不做:重做压缩机制、改门槛、改头尾保留条数、把计划(`update_plan`)塞进摘要(计划本来每次调用都单独注入,CM-0)、B-148 的完成判定。

## 3. 设计

### 3.1 B-141-a 摘要输入预算

- 总预算 `_SUMMARY_INPUT_CHAR_BUDGET`:24,000 → **160,000 字符**(约 4 万 token)。摘要模型窗口最小的是 20 万 token 级别,4 万占 20%,留足输出与系统提示的余量。
- 每条消息按角色设上限,取代统一的 2,000:
  - 用户消息 6,000(用户说的话最贵,几乎不截);
  - 助手消息 4,000(推理与决定);
  - 工具结果 1,500(头 + 尾,保留调用意图与结果)。
- 拼完仍超预算时,**从最旧的工具结果开始**依次压成一行 `tool: <工具名>(省略 N 字符)`;工具结果都压完还超,再从最旧的助手消息开始同样处理;最后才用原来的头尾截断兜底(防御性,正常到不了)。
- 更新模式(中段里已有上一份摘要)照旧对半分:上一份摘要 8 万、新事件 8 万。

为什么不按 token 精确算:摘要输入的作用是「别让摘要调用自己溢出」,字符数按 4 字符 / token 的粗估足够;中文按 1~2 字符 / token,16 万字符最多约 10 万 token,仍在 20 万窗口内。

### 3.2 B-141-b 摘要里的进度段

摘要结构从三段改成四段:`## Facts` / `## Decisions` / `## Progress` / `## Pending`。

`## Progress` 的规则(写进摘要提示词):
- 列出已完成的步骤,每步一行,带**具体结果**(文件路径、数字、产物名),原样保留;
- 写明**正在进行的那一步**做到了哪里;
- 写明**紧接着的一步**,只写对话里明确出现过的,不许自己推测;
- 更新模式:`## Progress` 以新事件为准**整段重写**;其余三段照旧合并。

同时删掉旧规则里「不要推测后续步骤」这一句的歧义:改为「Pending / 下一步只写对话里明确出现过的」。

兼容:检查点里的旧摘要是三段,更新模式读到旧摘要照常合并、补出第四段;回滚到旧镜像读到四段摘要只是文本,不报错。

### 3.3 B-143 摘要模型

沿用现成的「按步骤换模型」(`routing.rules`,`build_step_routers`,现有 `planning` / `reflection` 两类),不新加配置字段:

- `routing.rules[].when` 增加一个取值 `compression`。写了这条规则就用规则里的模型(要退回主模型,规则里写主模型即可)。
- **没写规则时(默认)**:查一张「同厂商便宜型号」映射表 —— 先只有 `glm-5.3` / `glm-5.2` → `glm-5.3-flash`;查到就用「主模型的同一份 `ModelSpec`、只换型号名、`fallback` 挂主模型本身」,查不到就用主模型(与现在一样)。
  - 便宜型号报错 → 路由器现成的备用链自动转主模型,不用另写退回逻辑;仍失败照旧走 RT-ADR-6(跳过本轮、连续三次才失败)。
  - **只在同一家内切换**,凭据、地域与主模型一致:不把一个租户的对话发给它没选的厂商。
- 记账:压缩调用的记账器按这条路由的整条链分桶(`_step_meter`,B-42 / B-104 口径),便宜型号记在自己的 provider·model 名下。**生产价目表必须有 `glm-5.3-flash`(用户核)**。
- `glm-5.3-flash` 始终思考(`always_thinking`),摘要调用按最低思考档发。
- 回滚兼容:默认路径不改 manifest;只有显式写了 `when: compression` 的 manifest 在回滚窗口里会被旧镜像拒(`extra="forbid"` + Literal),所以生产上不写这条规则,只在测试环境的评测智能体上写。

## 4. 验证(B-140 扩展)

### 4.1 评测框架
- 客户端多数一种帧:每轮记录 `compaction` 帧次数,写进轮指标。
- 用例可声明 `requires_compaction: true`:**一次都没压缩的那次运行判「不可判」**,不算过也不算不过(在不可能失败的条件下验证等于没验证)。
- 新判据 `workspace_file_line_count`(文件里匹配某正则的行数等于 N),用来抓「重做一步」(行重复)和「漏一步」(行缺失)。

### 4.2 评测智能体
- 新增 `eval-compress`:与 `eval-general` 相同,但 ① 关掉收起旧工具结果(`tool_result_prune.enabled: false`,跨轮清理一并关)和工作窗口,让**摘要成为唯一一道闸**;② 压缩门槛 `absolute_cap_tokens: 30000`。
- 新增 `eval-compress-main`:同上,另加一条 `routing.rules: [{when: compression, model: <主模型>}]`(B-143 对照用;要等 B-143 合入后才能导入)。
- **两个都要用户在控制台导入一次**(新建智能体只能走控制台平面),或用户 codegen 登录一次、我用登录态无头导入。
