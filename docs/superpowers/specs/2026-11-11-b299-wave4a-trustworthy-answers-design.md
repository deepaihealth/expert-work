### 2.2 读下来最该记住的三点

1. **「编号存在」和「编号可引用」是两回事**(WeKnora)。目录里出现过的、历史里出现过的、标题清单里的,都有编号但不能当依据。T3 的标题清单正是这种:给文档号让模型能去读,但它不在可引用集合里。
2. **流式预览不是权威**(RAGFlow)。我们的对外文档本来就要求客户端拿到 `updates` 后整段覆盖预览(`apps/admin-ui/docs-site/guide/sse-events.md:346-350`),所以核对放在整条消息上做,预览只管「别把半截编号漏出去」。
3. **两家都没有防「编号是真的、说的却是别的东西」**。WeKnora 用一句提示词管(每个编号只代表自己那段),没有程序核对。这是 T4 才能治的,T1 治不了,验收时要单独数(§5.2 的「引对了」)。

#### 3.1.2 方案:编号、核对、展开

**编号就是结果标头里那个**。模型在一句话后面写 `[D12#7]`,和它在结果里看到的一模一样。

> 取舍一:用现有编号,还是每轮另编 1、2、3?
> - 支持用现有的:模型已经在看它、`knowledge_read` 已经在用它;旧结果压成的引用行里列的也是它(`knowledge_reference.py:150`);`meta["refs"]` 已经在记「显示过哪些」;少一张对照表、少一处会错的地方。
> - 反对:它是长期有效的编号,模型可能凭记忆写、或者顺手改个数字(WeKnora 用请求内临时编号就是为了让「凭记忆写」必然失效)。→ 用核对来挡:只认本轮结果真显示过的。
> - 反对:比 `[1]` 长。实测 `[D12#7]`、`[D128#43]` 都是 5 个 token(o200k_base),可以接受。
> - 是否验证过:编号被模型原样抄回的比例**未验证**,进评测(§5.2「假编号」)。

**认哪些写法**(宽进):半角或全角方括号;一个括号里用逗号或顿号写多个;编号里的 `#` 可以是全角;读文档结果的区间写法 `[D12#7-9,41]`。规范化之后一律写成一个编号一个 `[…]`。裸写在句子里、没有括号的 `D12#7` 不算出处,原样留着。圆括号不认(容易误伤正文)。

**什么算「本轮给过」**:从本轮起点到当前这一步,所有成功的知识库工具结果的元数据里登记的段:

| 来源 | 登记内容 |
|---|---|
| `knowledge_search` | 每条显示出来的结果:标头里的编号 + 该结果命中的子段号 |
| `knowledge_read` | 每个显示出来的段:它的编号(含区间写法)+ 段号列表里的每一个 |
| `spawn_worker`(子智能体) | 子智能体那次运行里登记过的全部段(新增,见下) |

回答里的编号,文档号 + 段号都落在这个集合里才算认得。只写文档号(`[D12]`)一律不认 —— 这样 T3 标题清单里的文档号天然不能当出处。

**不认得的怎么办**:删掉这个编号,句子不动(D1)。分两类计数:「本轮和历史都没给过」(疑似编的)和「上一轮给过、本轮没给」(过期的)。两类都删,计数分开是为了评测和排查。

**认得的怎么展开**:展开用的资料在工具返回时就备好,放进工具元数据(不发给模型、不占上下文),核对时不再查库:

```json
{
  "ref": "D12#7",
  "document_id": "…", "doc_seq": 12, "kb": "库名",
  "title": "文档标题", "filename": "原文件名",
  "chunk_id": "…", "chunk_index": 7,
  "heading_path": ["第三章", "3.2 退货"],
  "locator": [{"type": "pdf", "page": 14}]
}
```

`locator` 没有就整个键不出现(与对外文档「取不到值的键不出现」一致,`sse-events.md:1814`)。

**放在哪一步做**:`agent_node` 里、脱敏之后、写入状态之前,和现有三道改写同一处(`builder.py:1594-1692`)。它是一个不做 IO 的纯函数(输入:回答文本 + 本轮消息;输出:改过的文本 + 出处清单 + 两个计数),评测脚本可以像现在取答前核对那样直接取产品函数(`tools/eval/kb_agent_prod_prompt.py:1-13`)。每一条有正文的助手消息都过一遍,不只最后一条。

> 与响应缓存的先后:改写放在缓存写入之前还是之后,**未验证**。两种顺序结果应当一样(提示词相同 ⇒ 本轮显示过的段相同),但要在实现时用测试钉住。

**门控**:只有构建里有 `knowledge_search` 才启用;另设一个平台开关(同 `kb_first_routing` 的做法,`knowledge.py:139-144`),关掉时文本与行为和今天逐字节相同,用于回滚和评测对照。

**子智能体**:子智能体自己的图里照常核对(它也有知识库工具)。它的回答以文本回到父级时,父级状态里没有那些段的工具结果,父级照抄的编号会全被当成不认得。所以 `spawn_worker` 的结果元数据里新增 `knowledge_sources`(子智能体那次运行登记过的段,最多 50 条),父级核对时把它并进「本轮给过」。

> 顺带发现:`spawn_worker` 给父级模型看的说明还写着子智能体「no knowledge-base search」(`tools/spawn_worker.py:70-80`),而实际默认继承。这是在对模型说假话,建议随子智能体那个 PR 一起改;因为是提示词文本,要过评测(§7.2 第 6 条)。

**多轮**:只认本轮(拍板口径,WeKnora 同)。上一轮的段被压成引用行后编号仍然可见,模型要引就得用 `knowledge_read` 重新读一遍。代价:不重新检索、直接凭上一轮内容回答的追问,出处会被全部删掉、整段被淡标成「未标出处」。这是如实的(这一轮它确实没看原文),但追问场景会多几次读文档调用。用多轮指代评测集盯这个数(§5.2)。

**结构化输出**:配了输出格式的智能体,编号可能落在 JSON 字符串里。删编号不会破坏 JSON;若正文被改过,已解析的结构要像脱敏那样作废重算(`builder.py:1625-1626` 的先例)。**未验证**,实现时补测试。

#### 3.1.3 数据模型 / 协议变更

**存储**(不加表、不加列):

- 助手消息正文:带规范化后的有效编号。
- `AIMessage.additional_kwargs["citations"]`:

```json
{"version": 1,
 "sources": [ {…上面那个对象…} ],          // 按正文里第一次出现的顺序,不重复
 "dropped": {"unknown": 0, "earlier_turn": 0}}
```

一条消息没有任何有效出处、也没有删过编号时,这个键不出现。它跟着 `updates` 帧进检查点和 `run_event`,历史回放直接有,不需要重新核对。

- `knowledge_search` / `knowledge_read` 的工具元数据新增 `sources`(同上对象的列表);`spawn_worker` 新增 `knowledge_sources`。

**流式预览**:`token` 帧里把编号去掉。做法是在现有扣留器前面加一道:遇到 `[` 或 `【` 开始扣,最多扣 48 个字符,等到右括号;是编号就丢,不是就原样放出去;流结束时没写完的原样放出去。每步结束的 `updates` 帧带着编号和 `citations` 到达,客户端本来就整段覆盖。没有知识库工具的构建不加这一道(保持现有直通快路径)。

> 取舍二:预览里显示编号,还是去掉?
> - 去掉的好处:不用在预览阶段做核对(预览里先显示、结束时又被删,比不显示更糟);对外默认「无编号」在预览和权威帧上天然一致;实现只有一个状态机。
> - 去掉的代价:控制台里角标要等这一步结束才出现。现在控制台本来就在这一刻把纯文本换成 Markdown 渲染(`AnswerBubble.tsx:144-149`),多一次重排可以接受。
> - 参考:RAGFlow 以最后一帧为准;WeKnora 在流里实时改写。未做用户测试。

**对外(API key 平面)**:

| 位置 | 默认 | 请求里带 `citations=inline` 时 |
|---|---|---|
| `updates` 帧里助手消息的 `content` | **去掉编号**(与今天一致) | 保留 `[D12#7]` |
| `updates` 帧 `additional_kwargs.citations` | 有(新增可选字段) | 有 |
| items 模式 `assistant_message` | `content` 去掉编号;新增可选字段 `citations`(同结构) | `content` 保留编号 |
| `GET …/sessions/{id}/items`、`…/messages` | 同上,查询参数 `citations=inline` 打开 | — |
| `token` 帧 | 永远没有编号 | 永远没有编号(文档写明:内联编号以 `updates` / `item.done` 为准) |
| `tool_result.artifact` | 多出 `sources`(新增可选字段) | 同左 |

- 不新增事件种类(沿用「不新增对外事件」的拍板)。
- 去编号是一个无状态的小函数,只去掉这条消息自己 `citations.sources` 里列着的编号(连同前面的一个空格),放在公共包里,对外的四个出口共用:实时流、事件回放、items、messages。老消息和没有出处的消息一个字都不会被动。
- 按 `changelog.md` 的分类,以上全部是「新增可选字段」,默认行为不变,不需要提前通知;发布时记在更新记录里。
- 控制台(员工登录)永远拿带编号的正文。

> 取舍三:对外默认去掉,还是默认带上?
> - 支持默认去掉:已上线的对接方把 `content` 直接显示给终端用户,正文里突然多出 `[D12#7]` 是可见的退步;按我们自己的对外约定属于「行为变化」要提前通知。
> - 反对:多一个开关;默认拿不到「哪句话对应哪个出处」(只有清单,没有位置)。
> - 这是需要用户定的(§7.2 第 1 条),本文按「默认去掉」设计。

#### 3.1.4 页码 / 位置

现状决定了能做到哪一步:解析器不给位置,切段器不留偏移,逐页记录没有文字。**总计划里「页码用已有逐页记录」不成立**(§3.1.1 后八行)。

方案分两层:

| 层 | 给什么 | 怎么来 | 什么时候有 |
|---|---|---|---|
| 0 | 文档 + 标题路径 + 段号 | 现成(`heading_path`;表格文件的工作表名本来就在标题路径里) | T1 一上线就有,所有文件类型 |
| 1 | PDF 页码 | **把段落文字对回每页文字**(见下) | 新入库的文档自动有;已有文档跑一次补算 |

**对文字的办法**(只做 PDF):

1. 取每页的纯文字:文字页用 PyMuPDF 逐页取(现在为了数字数已经在取);扫描页用该页识别后清理过的文字(入库当时手上就有)。
2. 每个段取开头和结尾各一小截(规范化:去空白、全半角归一,复用评测里已有的投影思路),在页文字里**按顺序**找:一个段的位置不能早于上一个段。
3. 截取的文字在可搜索范围内只出现一次才算数(页眉页脚、重复条款会出现多次 → 不算)。
4. 开头和结尾各定位到一页,得到页码或页码范围,写进 `source_locator`:`[{"type":"pdf","page":14}]`(跨页就写多个);父段取子段的并集。
5. **对不上就留空**。原则:错的页码比没有页码更糟。

- 入库时:在切段之后、写库之前做,不改变段落文字,所以不触发重新嵌入、不改变检索结果。
- 已有文档:后台补算任务,从留存的原文件字节重新取每页文字再对。只用 CPU,不调模型、不重新入库。扫描页在补算时只有缓存里的模型原始回复(未清理,且识别缓存按图片去重,页号可能是另一张相同图片的),对不上的比例会高,留空即可。
- 不做:其它文件类型的位置(Word 没有固定页;表格行号在解析时已经丢了;幻灯片页号是否留在正文里**未验证**)、页内坐标高亮、点开原文件定位到页(管理端现在没有原文件预览)。

> 取舍四:对文字,还是改解析器让它带位置?
> - 改解析器(WeKnora 的做法)是精确的,但要改纯文字 PDF 的解析方式(从整篇一次改成逐页),输出的 Markdown 会变 → 切段变 → 全量重新嵌入,还要重新过检索闸门。
> - 对文字不动任何现有产物,可以补算;代价是近似,会有留空。
> - **命中率未验证**:开工第一步是在合成的多页 PDF 上数「对上了多少、对错了多少」;对错必须为 0 才算过(§5.2)。命中率太低就只上层 0,页码另排(§7.2 第 2 条)。

#### 3.1.5 界面

**角标**:回答里的 `[D12#7]` 渲染成小角标,显示序号(按 `citations.sources` 的顺序,同一来源同一个号)。悬停:文档标题、标题路径、页码(有才显示)。点击:右侧抽屉显示这一段的原文(复用分段预览抽屉,加一个「定位到第几段」的入参)。回答下方一行「来源」,列出本条回答引用过的文档。

- 渲染方式:送进 Markdown 之前,把这条消息 `citations.sources` 里列着的编号换成一个内部链接写法,再用链接的自定义渲染画成角标。只换清单里有的,所以老对话、代码块里碰巧长得像编号的文字不受影响。
- 原文按文档 + 段 id 现取;段已经被重新入库替换或文档已删,显示消息里存的那份快照(标题、路径、页码)并提示「原文已变更」。
- 权限:看原文需要知识库读权限(与检索记录里看段落原文同一口径);没有权限的人只看到快照里的标题和位置。

**没有出处的段落(D1)**:只标不删。

- 单位是 Markdown 的块(段落、列表项、表格行),不拆句子 —— 拆句要分语言,做不到中立。
- 只在「这一轮知识库结果显示过段落」的回答上标;标题、代码块、12 个字以内的短块不标。
- 样式:块左侧一条淡色细线,悬停提示「这段没有标出处,可能是推断或通用说明」。不用红色、不用警告图标 —— 寒暄、「资料没写」、标了「我推测」的句子本来就不该有出处,不能让它们看起来像出错。
- 整条回答一个出处都没有时,不逐块标,只在回答下方一行「本回答没有标出处」。
- 调试台里另外显示被删掉的编号个数(两类分开)。
- 界面判断不了一句话是不是「事实句」(那需要再调一次模型)。所以这里标的是「没有出处的段落」,不是「没有出处的事实句」。这个差别要让用户知道(§7.2 第 4 条)。

**轨迹面板**:知识库工具调用那一行今天只显示结果原文。本期不改;后续可以把「被回答引用过的段」标出来。

#### 3.1.6 边界情况

| 情况 | 处理 |
|---|---|
| 模型写了本轮没给过的编号 | 删编号,计入 `unknown` 或 `earlier_turn` |
| 模型把编号改了一位(给过 `D12#7`,写了 `D12#8`) | 不认得 → 删。`D12#8` 即使是同一个大段里的另一个子段也不认(只认显示过的) |
| 一句话后面写了多个编号 | 各自核对,留下认得的 |
| 编号写在句子前面、或全堆在回答最后 | 照常核对和展开;位置不纠正。「堆在最后」的比例进评测 |
| 没有文档号的旧文档(标头是 `[文件名#段号]`) | 不能引用(编号里带租户文字,不进平台文本)。占比**未验证**,上线前数一次 |
| 检索结果因为字数预算只显示了命中的子段(标了「已截断」) | 照常可引;展开指向同一段 |
| 一次检索有库没搜成 | 不影响:只登记显示出来的段 |
| 输出筛查把回答换成了拒答文案 | 没有编号,`citations` 不出现 |
| 判官开着(不流式) | 只有权威帧,照常核对 |
| 回答被用户中途停止 | 没写完的那条消息照常核对已有文本 |
| 重新生成 / 编辑后重答 | 是新的一次运行,重新核对 |
| 文档事后被改名、重新入库、删除 | 消息里存的是回答当时的快照;界面按 §3.1.5 提示 |
| 智能体没绑知识库却写了 `[D12#7]` | 不处理(门控关着),原样显示 |
| 厂商模型把方括号写成全角、或把多个编号合进一个括号 | 规范化后核对(§3.1.2) |

#### 3.1.7 不做什么

- 不按相似度事后补出处(§2.1)。
- 不删、不改没有出处的句子(D1)。
- 不核对「编号指向的段是否真的支持这句话」—— 那是 T4。
- 不给对外默认内联编号的位置信息(字符偏移)。要位置的对接方用 `citations=inline`。
- 不做页内坐标高亮、不做 PDF 以外的精确位置。
- 不新增 SSE 事件。
- 不做「每个智能体自己开关出处」的配置项。只有一个平台开关用于回滚。

> - 「in the user's language … the equivalent of "I infer"」:平台文本不能出现某一种语言的固定说法。这样写英文提示词里没有任何中文,模型按用户的语言自己选词。各厂商模型是否稳定照做**未验证**(§5.2 分模型冒烟)。
> - 「资料说的是谁就只算谁」:支持 —— 判分的 `misattributed` 类 10 → 3 题说明这类错误真实存在;WeKnora 有同样一句(`citations.go:32-34`)。它在 `7ad5521ac` 里写好但从未单独评测,**未测**。

#### 3.2.3 协议变更

无。只改三个常量和它们的测试。评测脚本直接取产品常量,自动跟着变。

#### 3.2.4 边界情况

- 用户明确要看法(「你觉得呢」):允许推断,仍要单独成句、第一人称开头。
- 资料写了一部分:写了的照答并带出处;没写的那部分按上面处理。
- 没搜到任何东西:走已有的「没找到」提示,不涉及这三段。
- 子智能体:拿到同样的工具说明和答前核对,行为一致。

#### 3.2.5 不做什么

- 不把「我推测」之类的中文写进平台文本。
- 不要求固定的回答版式(小标题、固定句式)。
- 不改 `_RESULTS_NOTICE`(检索结果后面那段,`knowledge.py:207-214`):它每次检索都付费,已经说了「没明说的不算有依据」。
- 不合并 `feat/b206-entity-scope`:它的有效部分已在上面的文本里,分支作废。

#### 3.3.2 方案

**① 默认值放在模型目录里,不放在库上。** 下限本来就绑定重排模型,所以平台默认值是「某个重排模型的默认下限」:`RerankCaps` 加一个可选字段 `default_score_floor`。只给分数是绝对刻度(`normalized` / `sigmoid`)的模型填;没填的模型没有默认门槛。平台换重排模型时,默认值跟着模型走,不存在「暂停」。

**② 库上的设置变成三种状态**(不加列):

| 库上的值 | 今天的意思 | 改后的意思 |
|---|---|---|
| 留空(`None`) | 不过滤 | **跟随平台默认**(当前重排模型的 `default_score_floor`;模型没有默认值就不过滤) |
| `0` | 不过滤(等价) | **明确关闭** |
| 大于 0 | 自定义,绑定模型 | 不变;因换模型而暂停时,退回平台默认(今天是退回不过滤) |

> 已有的库怎么办:**一起拿到默认值**(留空的含义变了)。
> - 支持:今天所有库都是留空,不是租户主动选的「关」;只给新库开,等于最需要它的老库永远没有;与「平台缺口先改默认,别让人去配」一致。
> - 反对:已有库的行为在发布那一刻变了 —— 原来会返回低分段落的检索,现在可能返回「没找到」。
> - 缓解:默认值按「有答案题一道都不误挡」标定(见 ④);全不过线先降一次;平台开关可一键关;发布说明写明「想保持原样就填 0」。
> - 上线前必须去数:测试 / 生产各有多少库已经填了非空下限、平台当前重排模型是哪个。**未数**。
> - 这是行为变化,要用户确认(§7.2 第 3 条)。

**③ 降一次(D2)。** 一次检索里所有有分数的候选都被各自库的下限挡掉时,把每个库的下限乘一个系数再过滤一次(同一批分数,不重新调重排)。还是一条不剩 → `below_threshold`。只降这一次;**不做**「只留最好的一条」。检索结果里记 `floor_degraded`,检索记录页能看到。命中测试里手填的临时下限不降(那是在标定)。系数和默认值一起标定,起点取 0.7(WeKnora `rerank.go:33`;我们 B-175 设计 `2026-10-10-b175-knowledge-base-v2-design.md:265` 当时写的也是 0.7)。

> 10-22 不做降级的理由是「资料确实没写时会把低分段落塞回去」。这个风险仍在,所以:只降一次;离题题集上要同时报「降之前挡住几题、降之后还挡住几题」(§5.3)。

**④ 默认值怎么定:标定,不拍数。** 步骤(只跑检索,不跑智能体):

1. 用现有检索评测在开发集(主集 + 真实问法集)上回放,拿到每个问题每个候选的重排分(生产默认的双视图加权分)。重排有缓存,老问题基本不花钱。
2. 对每道有答案题,取「含答案的段里分数最高的那个」的分数 `s_gold`。
3. 新造一批明显离题的问题(§5.3),取每题最高分 `s_off`。
4. 候选下限 F 的约束:降一次之后(F × 系数),**有答案题里没有一道**因为门槛丢掉全部含答案的段。满足约束的最大 F 记为 F_max。
5. 默认值取 F_max 再留余量(乘 0.9),报告三样:这个值下离题题被挡住的比例;有答案题被误挡的题数(应为 0);`s_gold` 和 `s_off` 两个分布的重叠情况。
6. 如果离题题挡住的比例很低(两个分布分不开),如实报告,默认值照样可以上(无害),但要说清它几乎不起作用。
7. 每换一个平台默认重排模型,重做一次;没标定的模型不填默认值。

界面上现有的 0.70 是 B-175 波 2 时的参考值,口径和这里不同(没有「降一次」),**不直接沿用**。

**⑤ 单独的「没找到」结果。** `below_threshold` 时工具返回:

围栏内(可以有租户文字 —— 标题):

```text
[no passage was relevant enough to the query: 37 passages were retrieved and none passed the relevance floor]
Nearest documents (titles only):
- D12 示例产品手册
- D7 示例售后政策
```

围栏外的提示(固定文本,92 token;今天的通用提示是 41):

```text
[knowledge_search: no passage passed the relevance floor, so no passage text is shown.
The titles listed are metadata that says which documents exist: a title states no
fact, supports no claim and is not a reference. knowledge_read with a document's
number shows its text. Documents may word a fact differently from the query, so a
search in their terms can find what this one missed; if that finds nothing either,
the knowledge base does not cover this.]
```

- 标题取被挡掉的候选里排名最靠前的不同文档,最多 5 个;只给文档号和标题,不给任何正文。
- 文档号让模型能去 `knowledge_read`;但它不带段号、也不在「本轮给过」的集合里,所以**不能当出处**(§3.1.2)。真去读了,读到的段才可引。
- 这条结果不算「显示过段落」,不触发答前核对(`answer_check.py:68-81` 按 `hits` 判,这里是 0)。
- 用 `bases` 缩小范围后全不过线:沿用现有的「只搜了选中的库」提示(`knowledge.py:1235-1258`),同样附标题清单。
- 有检索路径失败时:沿用「这次检索不完整」的提示,不说「知识库不覆盖」。

> 给不给标题清单?
> - 支持:WeKnora 这么做;模型能告诉用户「库里有这几份可能相关的文档」,也能自己去读。
> - 反对:11-05 的追踪里,模型曾经凭文件名、标题下结论(`knowledge_read_reader.py:92-95` 的注释)。标题会诱发这种推断。
> - 缓解:提示里明说标题不是事实;标题不可引,凭标题说的话在界面上是「未标出处」;`GROUNDING_NOTICE` 已经管标题。
> - **未测**:离题题集上数「凭标题下结论」的题数(§5.3)。数出来不为 0 就去掉清单,只留一句话。

#### 3.3.3 数据模型 / 协议变更

- `RerankCaps.default_score_floor: float | None`(模型目录,新增可选字段)。
- `KnowledgeBase.rerank_score_threshold` 字段不变、取值范围不变(0~1),含义按 ② 改;字段说明重写(顺手删掉过时的「留 3 条」)。不需要数据库迁移。
- 库详情接口 `retrieval_config` 多三个只读字段:`rerank_floor_effective`(这次实际会用的值)、`rerank_floor_source`(`default` / `custom` / `off` / `none`)、`rerank_floor_default`(当前模型的默认值)。
- 检索结果 / 命中测试 / 检索记录多 `floor_degraded`;`below_threshold` 的工具元数据多 `titles`(个数)。检索记录的 `params` / `flags` 是 JSON 列,不用迁移。
- 界面:下限输入框占位文字改成「留空 = 跟随平台默认(当前 X);填 0 = 不过滤」;说明文字同步改。
- 平台开关一个(关 = 今天的行为:留空不过滤、不降、没找到时不附标题)。

#### 3.3.4 边界情况

| 情况 | 处理 |
|---|---|
| 库关了重排 / 平台没配重排模型 / 凭据取不到 / 模型不支持 | 没有分数 → 没有门槛(现有逻辑,不变) |
| 重排调用失败、限流、超时 | 用融合顺序,没有门槛(不变) |
| 双视图只成了一半(只有带标题那一路) | 不带分数 → 没有门槛(不变;那一路的分数偏高,不能拿来比) |
| 聊天模型当重排 | 没有分数 → 没有门槛 |
| 重排模型的分数是请求内相对分 / 原始 logit | 目录里不填默认值 → 没有默认门槛 |
| 一次搜多个库,下限各不相同 | 各按各的过滤(不变);全部被挡才算全不过线,降的时候各自乘系数 |
| 多个库里有一个明确关了门槛(0) | 那个库的候选都留下,这次检索就不会「全不过线」 |
| 重排只判了前 100 个候选 | 没被判的没有分数,不被门槛挡(现有逻辑 `knowledge_threshold.py:55-62`) |
| 命中测试手填了下限 | 用手填的,不降;结果里标明来源是 `override` |
| 自定义下限因换模型暂停 | 退回新模型的默认值;界面照旧提示重新标定 |

**必须写明的一条**:这个门槛**挡不住「相关但没回答问题」的段落** —— 资料没写的 27 题搜到的全是这一类,它们的重排分和真正含答案的段分不开(界面说明今天就这么写,`zh-CN.ts:822`)。T3 的验收只看离题题,不看那 27 题。

#### 3.3.5 不做什么

- 不做「只留最好的一条」(WeKnora 的第三级)。
- 不做按库自动标定、不做界面上的标定向导(属于 B-298 测评的范围)。
- 不在全不过线时直接结束对话或回固定话术(RAGFlow 的做法):我们的使用者是智能体,它还能换说法再搜。
- 不给向量相似度阈值(`retrieval_score_threshold`)加默认值。
- 不为这件事另调一次模型。

### 3.4 T4 答后独立核对(只留草图,**暂缓**)

**做不做的条件**:T1~T3 评测后,资料没写的题仍有编造,或「引对了」的比例明显低于「带出处」的比例(编号是真的、说的却是别的东西),才做。

| 项 | 草图 |
|---|---|
| 什么时候触发 | 本轮知识库结果显示过段落,且这一步是最终回答(没有工具调用)。省钱的收窄:只在回答里有带出处的句子时才核(没有出处的回答界面已经标了) |
| 核什么 | ① 答的是不是问的那件事(对象对、属性对、版本 / 时间对);② 带出处的句子里,每个数字、名称在它引的那段里有没有。②先用不花钱的文字比对(数字带单位),比不出来的才交给模型 |
| 怎么核 | 另调一次模型,只给:问题 + 回答 + 回答引用的那几段原文(T1 的编号正好用来取段)。不给对话历史 |
| 不过怎么办 | 把核对理由作为平台段贴上,重答一次;只重答一次,不循环 |
| 流式 | 第一版回答已经在逐字预览。要么这类轮次不出预览(像现在开了判官那样,`streaming_redact.py:305-310`),要么照常预览、以权威帧覆盖(对外文档已经这么要求)。倾向后者 |
| 费用 / 时延 | 每个有出处的回答多一次模型调用:输入约为「问题 + 回答 + 被引用的段」(上限是一次检索的 1 万字预算),输出很短;被打回时再加一次完整作答。具体数等评测里量 |
| 核对模型答非所问时 | 按「通过」处理并记日志(RAGFlow 的取舍:误打回比误放行贵,`agent.go:1086-1090`) |

**为什么是先答再核,而不是答之前先判「资料够不够」**:

- RAGFlow 量过并否决了后者:「Judging the page BEFORE answering was measured and rejected: with no answer to commit to, the model answered "is the page enough?" too harshly, refusing five questions whose facts were all on the page」(`internal/agentic_rag/agent.go:940-945`);「Verification runs AFTER the answer, not before it … it can look for the failure that actually happens here: the right subject, the wrong fact」(`agent.go:1139-1146`)。
- 我们的数据方向一致:27 题全都正确地说了「没写」(模型知道资料不够),错在后面追加的内容。「够不够」的判断不是瓶颈,追加的内容才是 —— 那只有看到回答才能核。
- 我们自己的答前核对(`answer_check.py:21-27`)当初选「搭在已有步骤上、不多调一次」正是为了避开这笔费用;T4 是它留的位置(`answer_check.py:40-43`)。

### 3.5 T5 默认返回条数

#### 3.5.1 现状

- 库设置 `retrieval_top_k`:默认 5,范围 1~50(`protocol/knowledge.py:355-360`;接口 `api/knowledge.py:115,136`)。
- 读它的只有命中测试(`api/knowledge.py:1431`)。
- 智能体工具:默认常量 5、上限 20(`knowledge.py:95-96`),模型不传 `limit` 就是 5(`knowledge.py:1309-1312`);参数说明写死「default 5」(`knowledge.py:1116-1121`)。
- 界面说明:「knowledge_search 默认返回多少条结果。」(`zh-CN.ts:809`;英文 `en.ts:4646`)—— 与实际不符。
- 一次检索实际能显示多少条还受 1 万字符预算限制(`tools/knowledge_results.py:27`)。

#### 3.5.2 方案(D3:让设置生效)

优先级,从高到低:

1. 模型这次调用传的 `limit`(夹在 1~20)。
2. 库设置(多个库取**最大值**),夹到 20。
3. 都没有 → 5。

- 「多个库」指这次实际搜的库(用了 `bases` 缩小范围就只看选中的)。取最大值的理由:条数是这次检索的总条数,把某个库调大的人是想多看;别的库多半还是默认 5,取最小值会让调大永远不生效。
- 实现位置:条数在检索器里、解析出库之后才定(今天是工具在调用检索器之前就定了)。召回深度随之按最终条数算。
- 工具参数说明改成不带数字:`Max results (default: the knowledge base's setting, at most 20).` —— 工具说明在构建时生成,读不到库设置,也不该为此多一次查库。
- 实际用的条数和它的来源(`model` / `base` / `platform`)记进工具元数据和检索记录。

界面说明改为:

> 智能体每次检索默认返回多少条结果。智能体可以在单次检索里自己指定(最多 20 条);这里填的超过 20 时,智能体按 20 算。命中测试不填条数时也用这个值(最多 50)。实际显示条数还受单次结果的字数上限限制。

#### 3.5.3 协议变更

无新字段。`retrieval_top_k` 的字段说明更新;工具元数据多 `limit_source`。已有库默认都是 5,不改设置的库行为不变。

#### 3.5.4 边界情况

- 库设成 50:智能体按 20;命中测试仍可到 50。
- 设置调大后 token 变多:由 1 万字符预算封顶;超出的结果按现有规则先显示命中的子段、再不够就截掉靠后的。
- 改过这个设置的已有库:发布后才真正生效,行为会变。上线前数一次有多少库不是 5(**未数**),发布说明写明。
- 子智能体:同一个工具,同样生效。

#### 3.5.5 不做什么

- 不把上限从 20 提到 50。
- 不按智能体单独设条数。
- 不改命中测试的行为。

| `token` 预览 | 不变 | 编号在预览里被去掉 |
| 回答的说法(T2) | 会变 | 资料没写时不再主动给结论;这是模型行为,不是接口变化,但要在更新记录里写一句 |
| 检索更容易返回「没找到」(T3) | 可能 | 只影响明显离题的问题;发布说明写明如何关(填 0) |
| 改过「返回条数」的库(T5) | 会变 | 设置开始生效 |

深护智康的对接不需要改代码(默认行为不变)。要显示来源,读 `citations` 即可。

### 4.2 已存的对话

- 老消息没有 `citations` 键:界面不画角标、不做淡标,和今天一样。
- 老回答里碰巧有 `[D12#7]` 字样:不处理(只处理本条消息出处清单里列着的编号)。
- 检查点和事件记录的格式不变(多一个可选键),不需要迁移,回滚后老版本读到多出来的键会忽略(**未验证**:老版本前端遇到带编号的正文会原样显示编号,回滚时要知道)。

### 4.3 每轮多花多少 token

按 o200k_base 实算,厂商分词有出入:

| 位置 | 现在 | 改后(T2) | 再加 T1 | 什么时候付 |
|---|---|---|---|---|
| 工具说明里的作答规则 | 75 | 148 | 205 | 有知识库的智能体的**每次**模型调用;在可缓存的前缀里 |
| 答前核对 | 66 | 82 | 107 | 本轮显示过段落之后的每一步 |
| 读文档结果后的提示 | 76 | 82 | 82 | 每次读文档 |
| 「没找到」的提示 | 41 | 92 | 92 | 只在全不过线时;另加最多 5 个标题 |
| 工具元数据里的 `sources` | — | — | 0 | 不发给模型 |
| 回答里的编号 | — | — | 每个约 5(输出) | 每处引用 |

举例:一轮三步(检索 → 读文档 → 作答),输入多 3 × 130 + 2 × 41 + 6 = **约 480 token**,其中 390 在可缓存的前缀里;一条带 6 处出处的回答,输出多约 30 token。没绑知识库的智能体:0。

T5 把条数调大的库会多显示段落,那是租户自己的选择,由 1 万字符预算封顶。T3 让离题的检索少返回段落,是省的。

### 4.4 时延

- 核对是纯内存的正则 + 查表,可忽略。
- 流式:只有碰到 `[` / `【` 才扣,最多 48 个字符;普通文字不受影响。
- T3:不多调重排;降一次是对同一批分数再过滤。
- 页码补算:后台任务,不在请求路径上。

## 5. 评测与验收

### 5.1 用什么

沿用 `tools/eval/kb_agent_*`(真模型答题 + 3 票判分 + 按断言判,`kb_agent_judge.py:1-28`)。评测的答题循环不是完整的生产图,它直接取产品的工具说明和答前核对(`kb_agent_eval.py:6-9`、`kb_agent_prod_prompt.py:1-13`);T1 的核对函数做成纯函数,用同样的方式取。

### 5.2 新指标

**不花判分钱、统计脚本直接算的**(结果行里新增:原始回答、核对后的回答、`citations`):

| 指标 | 定义 | 分母 |
|---|---|---|
| 带出处比例 | 回答里至少有一个有效出处的题 | 有答案 45 题(总计划的验收项) |
| 出处指向含答案段的比例 | 被引用的段里至少有一段含本题的标准答案原文片段(用现有的文字投影比对) | 有答案题;另报「只在带出处的题里」的比例 |
| 假编号 | 被删掉的编号个数、涉及的题数;「从没给过」与「上一轮给过」分开 | 全部题 |
| 写法不规范 | 靠规范化才认出来的编号个数(全角、合并写) | 全部编号;分模型 |
| 出处堆在最后 | 全部编号都在回答最后一个块里的题数 | 带出处的题 |

**要改判分模板的**(模板改了,判分缓存作废,要重新花判分钱):

| 指标 | 怎么得到 |
|---|---|
| 引对了 | 判分模型本来就给每条「原文写了」的结论抄一句原文;新增让它同时抄下这条结论后面跟着的编号。统计脚本核对「那句原文是不是在被引的那段里」:在 = 引对了;在别的段里 = 引错段;没编号 = 没引 |
| 没有出处的事实结论 | 判为事实性(不含「不需要出处」「标明了的推断」)却没有编号的结论数 |
| 推断是否第一人称标明 | 现有的「标明了的推断」/「没标明的推断」两类,口径不变 |

**原有三个数照旧盯**:资料没写题的编造、夹带推断、有答案题的误拒(总计划 §2.3)。

**每题跑两次**(同题两次约一半会变);报告按题次合计,并给逐题配对的变好 / 变坏数。

**多轮**:用现有多轮指代评测集另报「因为是上一轮的编号而被删」的题数,以及追问时多出来的读文档次数。

**分模型冒烟**(GLM / DeepSeek / Qwen 各跑同样 20 题,只看格式类指标:带出处比例、假编号、写法不规范、推断有没有第一人称标明),不做质量结论。

**页码**:合成的多页 PDF(纯文字、扫描、带重复页眉页脚、跨页段落各若干),已知每段在哪页。数:对上的比例、**对错的个数(必须为 0)**、留空的比例。不花模型钱(扫描页用已有的识别缓存或合成文字层)。

### 5.3 T3 的离题题集

新造 20 题,全部是和资料库明显无关的通用问题(合成,不用任何客户内容),进 `tools/eval/datasets/kb/`。看:

- 检索层:默认下限下,这 20 题里多少题拿不到任何段落(降之前 / 降之后各报一次)。
- 智能体层:拿不到段落之后,回答有没有凭标题下结论、有没有如实说没找到。
- 对照:有答案 45 题里,因为门槛拿不到含答案段的题数(应为 0)、误拒数(不升)。
- 标定本身(§3.3.2 ④)用整个开发集,只跑检索。

### 5.4 验收

| 项 | 判据 |
|---|---|
| T1 单测 | 没给过的编号被删、句子保留;给过的编号展开出文档与位置;上一轮的编号被删并单独计数;流式预览里任何切法都不漏出半截编号;没绑知识库的构建输出与改动前逐字节相同;对外默认正文不含编号 |
| T1 评测 | 报带出处比例、出处指向含答案段的比例、引对了的比例、假编号。**门槛不在这里拍**:先看数,由用户定(§7.2 第 5 条) |
| T2 评测 | 资料没写 27 题 × 2 次:编造题次下降,且逐题配对的变好数多于变坏数;若差别在噪声内(1~2 题),如实记为「未证实」 |

### 5.5 花费怎么估(只给算法,开跑前按当时的记录出报价)

- 单价沿用总计划的 11-10 实测:**每题次约 ¥0.96**(答题 + 判分 + 重排)。
- 主评测:72 题 × 2 次 × 臂数。两臂(改动前 / 全部改动后)= 288 题次 × ¥0.96 ≈ 总计划写的 ¥275。若要把 T2 和 T1 的效果分开看,加一臂(只有 T2)= 再加 144 题次。
- 离题 20 题 × 2 次 × 臂数,按同一单价是上限(这类题检索内容少,实际更低)。
- 分模型冒烟:20 题 × 3 个模型,答题单价按各模型价目另算,判分只跑格式统计、不调判分模型。
- 判分模板改了,老结果要重判才能和新结果比同一把尺子:用 `kb_agent_estimate.py` 的重判估算出数。
- 标定:只跑检索,老问题的重排在缓存里;新增花费 = 离题题的嵌入 + 重排调用。
- 以上都在开跑前用 `tools/eval/kb_agent_estimate.py` 出报价,用户说「跑」再跑。
