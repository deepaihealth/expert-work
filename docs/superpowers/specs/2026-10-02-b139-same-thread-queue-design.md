# B-139 设计:同一会话的多轮串行执行(排队)

> 专项:执行层质量(B-135),独立计划 `docs/superpowers/plans/2026-10-02-harness-quality-program.md`。
> 策略已拍板(2026-10-02):上一轮没结束时再发一轮 → **排队**,不拒绝、不并发。B-144(运行中插话)以本项为前置。
> 状态:设计稿(2026-10-02)。用户授权直接设计开发;合并等「合并」;不单独发测试。

## 1. 现在的问题

### 1.1 现象

同一会话上一轮还在跑,用户(或对接方程序)再发一轮,两轮会**同时**跑。

测试环境近 30 天:590 个 run 里有 2 对真的重叠,分别重叠 104 秒和 243 秒。生产 110 个 run 里 0 对。罕见,但一旦发生:

- 两轮各自从同一个检查点出发,各写各的分支,后写完的那一轮成为「最新」。另一轮的对话从会话历史里**消失**,不报错、不提示。
- 两轮同时往同一个工作区写文件、同时调同一个沙箱。
- 这正是 B-75「交错的两轮留下悬空工具调用」的来源。
- 对外文档 `run-control.md` 现在写的就是这个行为:「两轮在同一会话里同时执行,输出顺序不确定」。

### 1.2 代码层面为什么拦不住(摸底结果)

| 事实 | 位置 |
|---|---|
| 普通的一轮(控制台、对外接口)**没有任何**「会话忙不忙」的检查 | `spawn_run`(`control_plane/api/runs.py`) |
| 只有「重新生成 / 编辑重发」会查,忙就 409 `THREAD_BUSY` | `supersede.py` |
| `RunManager.has_inflight` 没有任何生产调用点,而且只看本进程内存、看不到排队中的 run 和别的副本 | `runtime/runs/manager.py` |
| 后台队列只按创建时间全局先进先出,不按会话排;同一会话的两条排队 run 可能被两个副本同时领走 | `SqlRunStore.list_queued` / `claim_queued` |
| 多副本之间只有数据库是共享的;流式输出的通道在每个进程的内存里 | `InMemoryStreamBridge` |
| **逐字输出的 token 帧不落库**,只能在执行这一轮的副本上实时推 | `orchestrator/sse.py` |
| LangGraph 检查点没有任何按会话的锁 | `runtime/checkpointer` |

## 2. 用户看到的行为

| 场景 | 改之后 |
|---|---|
| 会话空闲时发一轮 | **和现在完全一样**,不多一毫秒等待(只多拿一次会话锁) |
| 上一轮在跑时再发一轮(流式) | 连接立即建立,先收到一个 `queued` 帧(前面还有几轮);上一轮结束后,这一轮自动开始,照常收到 `metadata`、逐字输出直到 `end` |
| 上一轮在跑时再发一轮(`mode=queue`) | 照旧立即返回 202 `status: queued`,但现在真的会**等上一轮结束**才开始 |
| 排队时取消这一轮 | 和取消别的 run 一样;排队中的这一轮直接结束为 `interrupted`,不会再执行 |
| 控制台:排队时关掉页面 | 控制台的规矩是「断开即取消」,排队中的这一轮一起取消(今天这条规矩管不到排队状态,顺带补上) |
| 对外接口:排队时断开连接 | 对外的规矩是「断开继续跑」,这一轮照样排队、照样执行,结果用 `/events` 或查询接口取 |
| 上一轮停在等审批 | **视为空闲**,新一轮马上开始,并按现有规矩作废那条待审批(「新一轮作废之前的待审批」是已拍板的规则,不变) |
| 同一会话已经排了 3 轮还在等 | 第 4 轮直接 409 `THREAD_QUEUE_FULL`(防止程序死循环把一个会话堆满) |
| 重新生成 / 编辑重发时会话忙 | **不变**,仍 409 `THREAD_BUSY`。它们改的是上一轮的历史,排在后面没有意义 |

「忙」的定义:会话里有任何一个 run 处于 `pending` / `queued` / `running`。与重新生成用的 `SUPERSEDE_BUSY_STATUSES`、会话列表的 `running` 字段是同一个口径。

## 3. 做法

### 3.1 接单时:按会话加锁,判断要不要排队

所有新一轮都走 `spawn_run` 这一个入口(控制台、对外创建、重新生成 / 编辑)。今天它只在「重新生成 / 编辑」时拿会话锁。

改为:**每一轮都拿同一把会话锁**(复用现有的 `SUPERSEDE` 锁,classid 8620,键是会话 id),在锁里:

1. 从数据库查这个会话有没有忙的 run。这一步不能用进程内存,要能看到别的副本和排队中的 run。
2. **空闲** → 走今天的路,一点不变。
3. **忙** → 已排队的 ≥ 3 轮就 409 `THREAD_QUEUE_FULL`;否则这一轮按排队写库(`status=queued`,带 `enqueued_input`)。

为什么复用 8620,不新开一把锁:重新生成本来就在这个锁里查「忙不忙」,两件事必须互斥。用同一把锁,不会出现两把锁互相等的死锁。登记表里的说明改成「会话接单锁」,值不变。按登记表规矩,正在用的锁不改号。

两个请求同时打到一个空闲会话:锁保证只有一个看到「空闲」,另一个看到第一个刚写入的行,就去排队。

### 3.2 谁来执行排在后面的那一轮

关键约束:**逐字输出不落库**。所以流式请求排的那一轮,最好由收到这个请求、拿着这条连接的副本自己执行,用户才能看到逐字输出。

做法是给排队的行**加预订**:

- 流式请求排队时,把行的 `claimed_by` 写成本副本、`lease_until` 写成「现在 + 30 秒」。这两列今天只在执行中用;排队行上本来是空的。
- 本副本起一个等待任务,每秒查一次「这个会话里比我早的 run 是否都已经不忙」,同时每 10 秒续一次预订。
- 轮到了 → 本副本用现有的 `claim_queued` CAS 领走,在本进程执行,把输出推给这条连接。
- **本副本挂了或在关机**:预订 30 秒内过期,任何副本的后台队列都能领走它照常执行(对外接口的「断开继续跑」语义因此成立)。关机交接时主动清掉预订,不用等过期。

`mode=queue` 的排队行不加预订,和今天一样由后台队列执行。

### 3.3 后台队列:按会话排队

`list_queued` / `claim_queued` 加两个条件,SQL 与内存版两份实现必须同义:

1. 同一会话里**没有更早的**、处于 `pending` / `queued` / `running` 的 run(严格按会话串行)。
2. 没有有效预订(`claimed_by IS NULL OR lease_until < now()`)。

条件 1 写在 `claim_queued` 的那条 UPDATE 里,与领取在同一个原子操作,不留竞态。

查询要一个索引。现有的 `ix_agent_run_thread_inflight` 不含 `queued`,新增部分索引 `(thread_id, created_at) WHERE status IN ('pending','queued','running')`(一个迁移)。

### 3.4 上一轮结束得多快能接上

| 情况 | 接上的延迟 |
|---|---|
| 预订副本在等 | ≤ 1 秒(每秒查一次) |
| 后台队列执行 | ≤ 2 秒(队列本来就每 2 秒扫一次) |
| 预订副本挂了 | ≤ 30 秒预订过期 + 2 秒 |
| 上一轮所在的副本挂了 | 上一轮先由孤儿重收接着跑完(现有机制),排着的这一轮再接上 |

### 3.5 流式协议:新增 `queued` 帧

排队时立即发一帧:

```
event: queued
data: {"run_id": "...", "thread_id": "...", "ahead": 1}
```

之后照常每 15 秒一个心跳,开始执行后是今天的 `metadata` … `end`。

- 这是**新增**事件。对接方的客户端按白名单收事件,不认识的会忽略,所以不会坏。文档要写明:收到 `queued` 表示排队,可以提示用户「上一轮结束后开始」。
- `end.status` 的取值不变。
- `/events` 接口对排队中的 run:今天写的是「排队且永不执行时连接不会返回」。改后它一定会执行,文档同步改。

### 3.6 控制台

调试台与对话页收到 `queued` 帧时,在这一轮的位置显示「排队中,上一轮结束后开始」,带取消按钮。对话页的会话状态把排队算作「进行中」(与对外 `running` 字段同口径)。

### 3.7 进入点逐个过一遍

| 进入点 | 处理 |
|---|---|
| 控制台发消息、对外创建 run(流式 / 排队) | §3.1 ~ §3.3 |
| 重新生成 / 编辑重发 | 不变(忙就 409),但现在和普通一轮在同一把锁下互斥 |
| 审批通过后的续跑 | 它就是那一轮自己的后半程,不排队。今天已有保护:有更新的一轮时审批会被作废,续跑不会发生 |
| 审批超时扫描 | 同上 |
| 孤儿重收 | 接着跑的是同一个 run,它本来就是「忙」的那一个,不排队 |
| 定时触发 | 每次都开新会话,不涉及。**但**它把结果送回原会话时(`trigger_delivery`)不检查原会话是否有 run 在跑,是另一个交错点,本项不改,登记为 B-151 |

## 4. 不做的

- 不做「运行中插话」(B-144),那要能把消息塞进正在跑的这一轮。本项只保证串行。
- 不改重新生成 / 编辑重发的 409。
- 排队上限不做成配置,是平台常量(3)。理由:真实数据里两轮重叠都罕见,排到第 4 轮几乎只可能是程序出错。
- 不改审批规则(新一轮作废待审批)。

## 5. 风险

| 风险 | 应对 |
|---|---|
| 每一轮多拿一次数据库锁 + 一次查询 | 锁按会话,只与同一会话的请求互斥;查询走新索引。合并前在本地 testcontainers 上量单次耗时,写进 PR |
| 预订等待任务漏处理(本副本还活着,但等待任务出了异常) | 预订照样过期,后台队列接手执行;这条连接收不到逐字输出,但能收到完整结果(连接切到落库事件的实时跟读)。测试覆盖 |
| 上一轮卡住不结束 | 不新增超时:上一轮现有的步数 / 时长上限与孤儿重收保证它终会结束;用户也可以取消上一轮 |
| SQL 与内存版谓词不一致 | 两份实现跑同一组用例(本仓库教训:谓词必须逐字同义) |
| 对外行为变化 | 今天文档写的就是「同时执行、顺序不确定」,改成串行属于修正;新增 `queued` 帧、`THREAD_QUEUE_FULL` 两处契约新增,文档同 PR 改,并告知对接方 |

## 6. 验证

### 6.1 单测与集成测(本地,每条变异自证)

- 空闲会话:行为与今天逐字段相同,不发 `queued` 帧。
- 忙会话:
  - 第二轮写成 `queued`,带预订。
  - 上一轮结束后由本副本领走执行。
  - 输出帧顺序是 `queued` → `metadata` → … → `end`。
- 并发接单:两个请求同时打到空闲会话,只有一个直接执行(真 Postgres,testcontainers)。
- 后台队列:
  - 同一会话两条排队,后一条在前一条结束前领不到。
  - 有效预订领不到,过期预订领得到。
- 排队上限:第 4 轮 409 `THREAD_QUEUE_FULL`。
- 取消:
  - 排队中取消,不再执行。
  - 控制台断开连接会取消排队中的这一轮。
  - 对外断开连接不取消。
- 上一轮停在等审批:新一轮立即开始,审批被作废。
- 重新生成在忙会话:仍 409 `THREAD_BUSY`,且与普通一轮互斥。
- 关机交接:预订被清掉,其他副本可领。

### 6.2 统一发测试后的真栈用例

写进 `docs/runbooks/pending-test-release-acceptance.md`,本项开发 PR 同 PR 加:

- 控制台连发两条消息:第二条显示「排队中」,第一条结束后自动开始;会话历史里两轮都在、顺序正确。**没修好时**:两轮同时跑,其中一轮从历史里消失。
- 对外接口连续两个流式请求:第二个先收到 `queued` 帧,再完整收到第二轮的输出。
- `mode=queue` 连续两个请求:第二个在第一个结束之后才开始(看两行的 `started_at` / `finished_at`)。
- 排队中取消第二轮:它结束为 `interrupted`,从未开始执行。
- 第一轮跑的时候删掉执行它的 pod:第一轮由孤儿重收接着跑完,第二轮随后执行。
- 连发 4 轮:第 4 轮 409 `THREAD_QUEUE_FULL`。
- 金丝雀 PASS。
