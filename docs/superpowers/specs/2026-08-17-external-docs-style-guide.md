# 对外 API 文档写作规范

适用范围:`apps/admin-ui/docs-site/guide/` 下全部页面。任何对这些页面的改动,提交前按本文末尾的清单自检;评审按同一清单验收。

## 1. 读者与目的

- 读者是**第三方的开发工程师**,可能是前端也可能是后端。他们要把自己的产品接到平台上,关心的是:接口什么时候返回什么、字段是什么意思、拿到之后该怎么处理、出错了怎么办。
- 读者**不了解也不需要了解**平台的内部实现:没有「编排引擎」「图」「节点」「写入」「落库」「游标」这些概念,也不关心平台内部的评审、验收、版本迭代过程。
- 这是**企业级对外文档**,不是内部技术文档。它代表产品的专业程度。

## 2. 语气

- 正式、克制、准确。陈述事实,不渲染情绪。
- 不用口语和俏皮话:「第一天就会踩到的坑」「别赌这一点」「免得你以为自己漏读了」「这玩意」「一律」「反正」「说白了」。
- 不引用内部过程:「真栈实测」「三个场景」「B 场景」「上一轮」「审计」「终审」「P2-a」「Task N」。事实直接陈述,不说来源。
- 不以「我们」谈实现;必要时用「平台」「服务端」。
- 尽量不用第二人称;需要指代对方时用「客户端」(对方的程序)或「调用方」(对方的系统 / 团队)。
- 不用感叹号;不用「!!」「!!!」;不用表情。

## 3. 词表(左边禁用,右边替换)

| 禁用 | 用 |
|---|---|
| 图、节点、图里的节点 | 步骤、「这一步由谁完成」 |
| 节点写入、写入 | 这一步的产出 |
| 落库、入库 | 服务端记录 |
| 游标 | 续传位置(`since_seq`) |
| 回放(未定义就用) | 首次出现时写「续传:断线重连后服务端把未收到的事件重新发送(见 3.6)」;此后可用「续传」 |
| 帧 | 事件 |
| 平台注入 | 由平台附加 |
| 铸造、mint | 自动创建 |
| 闸、门禁 | 校验、限制 |
| 终态 | 最终状态 |
| 裸 `detail`、裸 404 | 只有 `detail` 字段的错误响应 |
| 不透明 404 | 统一的 404(不区分原因) |
| 落地、接线、口径、载荷 | 生效、接入、说法、请求体 / 响应体 |
| 通路 | 按含义写实:「按文档 / 按图片处理」或「存储」 |
| 编排、graph、LangGraph、checkpoint、supervisor | 不出现 |

## 4. 结构

- 每个接口小节固定顺序:一句话说明用途 → 请求(方法 + 路径 + 参数表)→ 响应(状态码 + 字段表)→ 示例(请求 / 响应成对)→ 错误(只列这个接口特有的)。
- 每个 SSE 事件小节固定四段:**什么时候发** → **data 字段** → **示例** → **客户端怎么处理**。
- 每个概念的首段必须回答:谁发起 → 发给谁 / 什么时候 / 客户端该做什么。
- 一个概念依赖另一个概念时,**首次出现处给一句话定义 + 指向详解的链接**,不能让读者先跳走再回来。
- 相同的事实只在一处完整讲述,其它地方一句话 + 链接。

## 5. 表格

- 最多 4 列。表头是名词短语,不含条件语(「除 X 外还有」)、不含问句形式(「什么时候出现」「客户端要做什么」→ 写成「出现时机」「客户端处理」「由谁完成」);首格不能为空(行标签列也要有表头,如「类别」)。小节标题不受此条约束(「什么时候发」「客户端怎么处理」这类小节名可用)。
- 请求参数表统一三列:**参数 / 必填 / 说明**(类型写在说明首句,如「string,长度 1–255 字符」);响应字段表统一三列:**字段 / 类型 / 说明**。取值写在说明里,格式:「取值:`a`(含义)/ `b`(含义)」;开放取值写「开放取值,当前常见:…;遇到未知值时 …」。错误表表头用「错误码」,不用 `error.code`(有的错误码在 `detail.code` 里)。
- 某一列在多数行取值相同时,删掉这一列,把它写成表前的一句话。
- 每格说明不超过两句;需要长解释的放到表后正文。
- 按条目逐行,不按类别归并;同类条目很多且说明相同时,反过来合并成一行(如「带 `id:` 的事件」一行列出全部名字)。

## 6. 标题

- 不含任何标点(顿号、逗号、冒号、破折号、问号、括号);行内代码后不接标点。
- `##` 带章节编号(如「3.2 事件的格式」),`###`/`####` 不带编号。
- 修改标题会改变锚点:改前全站搜索引用,改后同步侧栏与所有链接。

## 7. 强调与提示框

- 一段最多一处加粗,只用于「必须 / 不要」级别的规则或读者最容易做错的判断。表格里不加粗。
- `::: warning`:只用于「照直觉写会出错」的陷阱;一框一个话题;标题是陈述句,不带标点。
- `::: danger`:只用于数据丢失、安全、不可逆的后果。
- `::: tip`:建议值、可选优化。
- 提示框内不超过三段;不放表格。

## 8. 代码块

- 每个代码块都有标题,标题是名词短语:「请求」「响应 200」(响应一律「响应 + 状态码」,不在标题里再写错误码)「事件流片段」「示例代码」「data 的结构」;标题里不含 `[` `]`,不用「·」分隔。
- 注释简短、正式;不写「别赌」「反正」类口吻。
- 示例载荷完整可复制,但裁剪到能说明问题的最小;固定示例值全站一致(`user_id: "u-123"`,文档 `upl_3f2c9a1e-…`,图片 `upl_9b7d2c40-…`)。
- 请求 / 响应成对出现,用 `####` 小节分隔,不用 `::: code-group` 拆到不同标签页里。

## 9. 主语与指代

- 「值」「它」「这个」「那个」必须能指回上一句里明确的主语;拿不准就重复主语(「`data` 里某个键对应的值」)。
- 占位符统一花括号 `{user_id}`,行内代码里不夹中文。

## 10. 长度

- 段落不超过三句;一条 bullet 只说一件事;一个列表只装一类事。
- 长解释拆成小节,不拆成加粗句。

## 11. 术语表(全站同一词)

run · 会话(`session_id`,与 `thread_id` 同值)· 事件 · 步骤 · 工具调用 · 审批 · 附件(调用方上传的)· 工作区文件(Agent 写出的)· 产物(Agent 登记为成果的)· 后台清理作业 · 子任务(worker)· 续传 · 心跳

- [ ] 词表里的禁用词为零(`rg` 一遍)。
- [ ] 内部过程用语为零(真栈 / 场景 / 审计 / 上一轮 / Task)。
- [ ] 标题无标点;新标题已同步侧栏与链接。
- [ ] 每张表 ≤ 4 列、表头名词短语、请求参数表 参数/必填/说明、响应字段表 字段/类型/说明。
- [ ] 正文标点全角(，：；（）),代码块内保持 ASCII;可用 `scratchpad/fullwidth.py` 一类脚本处理,处理后核对代码块字节未变。
- [ ] 每个概念首段答「谁→谁 / 何时 / 客户端做什么」;依赖概念首次出现有一句话定义 + 链接。
- [ ] 每段 ≤ 1 处加粗;提示框一框一话题。
- [ ] 每个「值 / 它 / 这个」有明确主语。
- [ ] 代码块都有标题;示例值与全站一致。
- [ ] 构建通过、死链脚本零死链、公开文档红线扫描为空。
