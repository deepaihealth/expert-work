# 跨轮上下文降本设计(B-126)

- 状态:方向与四节设计已拍板(2026-09-28),本文待审
- 关联:CM-12 旧工具结果清理(`orchestrator/context/tool_result_prune.py`)、CM-2 历史窗口(`context/working_window.py`)、L2 对话压缩(`context/compressor.py`)、工具结果外置(`tools/overflow.py`)、B-84(入均 5~11 万 token 的上下文是慢与贵的主因)
- 原则拍板人:项目负责人(2026-09-28 会话)

## 一、问题

### 1.1 实证

测试环境 2026-09-28,ai-health-plan 重放张女士对话(thread `d3016385`,glm-5.3,7 轮):

| 轮次 | 调用次数 | 每次输入 token(首次 → 末次) | 首次调用缓存命中 | 成本(元) |
|---|---|---|---|---|
| 1 出方案 | 32 | 1.4 万 → 5.5 万 | — | 3.74 |
| 3 问答 | 1 | 7.3 万 | 25% | 0.54 |
| 6 改样式 | 9 | 9.0 万 → 9.7 万 | 36% | 2.19 |
| 合计 7 轮 | | | | 12.63 |

同一轮内每次调用缓存命中约 95%,钱主要花在「每次调用都把越来越长的历史再读一遍」上。
跨轮时用户间隔回话,缓存大多已冷,而上一轮的全部工具原始返回(客户数据约 2 万 token、技能文档约 0.8 万 token、校验回执……)原样带进新一轮的每一次调用。

### 1.2 根因:所有收缩门槛按窗口百分比,大窗口模型实际从不触发

平台现有三道从轻到重的收缩:CM-12 清旧工具结果 → CM-2 丢整轮 → L2 写摘要。门槛都是 `context_window × 0.7`。
glm-5.3 的目录窗口是 100 万(`model_catalog.py`),门槛 = 70 万 token;实测 5~10 万,三道一道都没触发。
另有两个结构问题:

1. **CM-12 一旦触发就逐次重算**:「最近 4 条」窗口随调用滑动,每次都改写一条更早的消息,缓存前缀每次都断。
2. **L2 摘要不写回检查点**(`compressor.py` 注释原文「压缩结果不落检查点,下一步从完整历史重来」):过门槛后每一步都重新调模型写一次摘要,下一轮又从完整历史开始。门槛高时碰不到,门槛一降就会变成成本炸弹。

### 1.3 行业对照(本地源码 + 官方文档)

| | 保留原样 | 触发 | 清法 |
|---|---|---|---|
| Anthropic context editing(`clear_tool_uses_20250919`) | 最近 3 次工具调用 | 输入超绝对 token 数(默认 10 万,文档示例 3 万)+ `clear_at_least` | 旧结果换占位符;可排除指定工具 |
| openclaw(`pi-hooks/context-pruning`) | 最近 3 条助手消息 | **只在缓存已过期时**;占窗口 ≥30% 软削、≥50% 且可清 ≥5 万字硬清 | >4000 字削成首尾各 1500 字,再不够整条清空 |
| hermes-agent(`context_compressor.py`,主动清理默认关) | 最近 20 条消息 | 手设 token 数,至少省 4096 token | ≥8000 字的旧结果改一行摘要 |

共识:同一轮内不清(保缓存);按绝对量而非窗口百分比决定;只清工具原始返回,模型自己的话不动;清掉的要能找回。
openclaw / hermes 的压缩门槛也按百分比,在 100 万窗口上同样撞不到,这一点不照抄;只有 Anthropic 给了大窗口的答案(绝对 token)。

## 二、决定

| # | 决定 | 理由 |
|---|---|---|
| D1 | 平台级,默认开启,所有 Agent 生效;可在 Agent 配置里关 | 平台缺口改默认,不做成要人去配的开关 |
| D2 | 只改发给模型的视图,检查点里的历史不动 | 对话页 / 调试台 / 审计仍见完整记录;沿用 CM-12 现有「Prompt-view only」 |
| D3 | 同一轮内不清;清理决定在新一轮开头做一次,本轮所有调用沿用 | 缓存前缀稳定;跨轮首调缓存本就大多已冷(实测 25%~36%) |
| D4 | **不做「清理前让 Agent 记笔记」** | 工作区按员工不按客户,笔记会串到另一位客户的对话(用户指出);清掉的内容本就能找回(D6) |
| D5 | 触发条件看绝对量,不看窗口百分比 | 大窗口模型百分比门槛等于从不触发 |
| D6 | 只清「能无损找回」的结果:有工作区副本的(≥4000 字,平台写入时已存),或技能正文(可 `skill_view` 重读) | 被清掉的每一条都能找回,一个字不真正丢 |
| D7 | 副本文件按对话隔开;清理后的占位只引用本对话的副本 | 防止换客户时引用到上一位客户的存档 |
| D8 | L2 摘要按「覆盖到哪条消息」缓存进检查点,历史未变就复用 | 修 1.2-2,否则门槛一降成本反升 |
| D9 | 深护智康 MCP `form_get_field_detail` 精简模式由调用方显式开启,**不设默认** | 对方其他地方在用完整返回(用户拍板) |

## 三、设计

### 3.1 新一轮的判定

- 当前轮 = 最后一条**真实用户消息**之后的全部消息;之前的为旧轮次。
  平台注入的隐藏消息(本轮输入块、计划、工作区摘要、看图块等)不算真实用户消息,实施时按 `thread_message.hidden` / 消息元数据区分,计划里须列出全部注入点逐一核对。
- 审批通过后续跑、孤儿重收续跑不是新一轮(没有新的用户消息)。
- 清理结果只取决于旧轮次的内容 → 同一轮内每次调用算出的清理视图逐字相同,无需额外保存状态。

### 3.2 无损清理(改造 CM-12)

**触发**(新一轮第一次调用时判一次,三条同时满足):

1. 本次视图预估总量 ≥ `min_context_tokens`(默认 **30,000**);
2. 按 3.3 可清理的旧结果合计 ≥ `min_reclaim_tokens`(默认 **5,000**);
3. 该 Agent 未关闭跨轮清理。

不满足则整轮不动;满足则一次清完,本轮沿用。

### 3.3 清哪些

同时满足才清:

1. 属于旧轮次;
2. 不在按本轮开始时计数的最近 `recent_tool_results_kept` 条(默认 **4**,沿用现值)之内;
3. 有无损找回途径:工作区副本路径(`artifact` 里的持久化路径或外置 footer,≥4000 字的结果写入时已存),或成功的 `skill_view` 正文。

一律不清:模型自己的消息;当前轮全部工具结果;4000 字以下、无副本的结果;被安全拦截 / 漂移 / 已归档等占位(安全提示不改写成「可重读」,沿用现有规则);看图的文字结论。
完全相同的重复结果只留最新一份(沿用现有去重)。

### 3.4 清理后的占位

一行,写明:工具名 + 主要参数摘要(如 `form_get_field_detail form_customer_basic_info`)、原结果大小、找回方式(读某副本文件 / 重新 `skill_view`)。
复用现有 footer / skill reference 格式,补上参数摘要。

### 3.5 副本文件按对话隔开

外置副本当前写在 `.tool_results/<run_id>/…`。改为按对话分目录(如 `.tool_results/<thread>/<run>/…`),占位只引用本对话目录下的路径。
计划里须核对:`list_dir` / `search_files` 是否会把 `.tool_results` 列给模型,若会,默认列表排除该目录。

### 3.6 有损步骤的门槛

CM-2 丢整轮、L2 写摘要、以及同一轮内逐次清理的兜底,门槛统一改为:

```
min(context_window × threshold_pct, absolute_cap_tokens)   # absolute_cap_tokens 默认 200,000
```

顺序不变(轻 → 重)。20 万取自行业常见 20 万窗口的实际压缩位置,仍远低于 hermes / openclaw 在 100 万窗口下的 50 万~98 万。
正常出方案一轮约 5 万 token,碰不到有损步骤。

### 3.7 摘要缓存(修 1.2-2)

- 摘要连同「覆盖到的最后一条消息 id」写进 Agent 状态的一个新通道,随检查点保存。
- 下一次需要摘要时:被覆盖的那段历史未变 → 直接复用;有新增 → 只把新增部分与旧摘要合并重写(或按现有 `max_passes` 规则整体重写,计划里定)。
- 开头 `head_keep` 条、最近 `tail_keep` 条原样保留,沿用现有做法。

### 3.8 配置项

放进现有 `policies.tool_result_prune`(跨轮清理)与各有损步骤的策略块,默认值即上文数字:

| 字段 | 默认 |
|---|---|
| `tool_result_prune.cross_turn`(开关) | `true` |
| `tool_result_prune.recent_tool_results_kept` | 4(已有) |
| `tool_result_prune.min_context_tokens` | 30000 |
| `tool_result_prune.min_reclaim_tokens` | 5000 |
| `*.absolute_cap_tokens`(CM-2 / L2 / 兜底) | 200000 |

新字段均带默认值;注意 manifest 模型 `extra="forbid"` 的回滚纪律(旧版本读到新字段会校验失败):回滚窗口内不在生产配这些新字段,真要回滚先清掉。

### 3.9 可观测

每次调用写一条运行事件:本次是否跨轮清理、清了几条、省了多少 token、摘要是否复用。调试台可见,供上线后算账。

## 四、测试与验收

### 4.1 单元(每条新断言先在旧代码上红,再在新代码上绿)

- 同一份历史在本轮第 1 次与第 N 次调用算出的清理视图逐字相同。
- 门槛:总量 < 3 万或可清 < 5000 token 时一字不动;刚过线即清。
- 不清的一律不清:当前轮、最近 4 条、<4000 字无副本、安全占位、模型自己的消息。
- 每条被清的都有找回途径;无副本的不清。
- 摘要:被覆盖历史未变时不调模型。
- 副本按对话分目录,两段对话互不引用。

### 4.2 集成(真实执行图 + 记录型假模型)

- 连跑 3 轮带工具的对话:第 2 轮起旧结果变一行占位;同一轮内各次调用前缀逐字相同;检查点历史完整。
- 同一员工两段对话、两位客户:第二段发出的内容不含第一位客户的任何数据或副本路径。

### 4.3 测试环境真栈

张女士对话同输入重放两次(关闭 / 开启跨轮清理):

| 指标 | 通过标准 |
|---|---|
| 第 3 轮起每轮首次调用输入 token | 明显下降(预计 7~9 万 → 3~4 万) |
| 7 轮总成本 | 降 30% 以上 |
| 同一轮内缓存命中率 | 不低于对照组 |
| 成品 | 质检全过,内容与对照组一致 |
| 找回次数 | 统计重读副本 / 重调工具次数,不得把省下的吃回去 |

另:串客户专项(同一员工先张女士、再新对话另一测试客户,后者对话与交付件无张女士信息);金丝雀 + 一个 sop2 类 Agent 回归。

### 4.4 上线与回退

默认开启随常规发版;生产发布由用户操作。异常时在 Agent 配置里关 `cross_turn` 即恢复旧行为,不必回滚代码。上线后一周看 3.9 的事件统计。

## 五、附:给深护智康 MCP 团队的改进说明(D9)

**实测**(2026-09-28,ai-health-plan 一次出方案):`form_get_field_detail` 调 6 次,返回共 26,644 字(约 1 万 token),而模型实际用得上的(字段名、编码、类型/单位、填写说明)约 7,200 字,**有用约 27%**。

| 表单 | 字段数 | 返回字数 |
|---|---|---|
| form_customer_basic_info | 34 | 14,337 |
| form_blood_glucose_log | 20 | 8,228 |
| form_weight_log | 4 | 1,678 |
| form_pressure_log | 4 | 1,567 |
| form_nutritional_profile | 1 | 417 |
| form_sports_archive | 1 | 417 |

每个字段固定 15 个属性,冗余来自:名称三份(`custom_field_name` / `custom_name` / `global_field_name`)、编码两份(`field_code` / `global_field_code`)、后端专用配置(`validation_rules` / `calculation_expression` / `calculation_type` / `default_value` / `field_order` / `is_required`)、约四分之一的空值,以及每行重复 15 个属性名的 JSON 开销。

**请求**:新增可选参数(如 `detail_level`),**不传时行为与现在完全一致**;传 `brief` 时每字段只返回名称、编码、类型、单位、填写说明,空值不返回,以表格式文本输出(属性名只写一次)。预计该工具返回缩到约四分之一。
ai-health-plan 侧在对方上线后显式传 `brief`,单独重放量收益。本设计的平台改动不依赖此项,可先行交付。
