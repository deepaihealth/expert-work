# B-158 一次回答撑满输出上限:丢弃并让模型拆小重做一次

> 2026-10-06。ROADMAP B-158。B-140 首次 3× 基线带出(#1742)。

## 1. 问题

B-105 起,模型回答被输出上限截断、且答案不可用(正文为空,或带着工具调用 —— 最后一个调用的参数必然被截)时,agent 节点抛 `OutputTruncatedError`,整轮以错误结束,什么都不交付。

- **B-140 实测**:eval-ahp(上限 40960,与生产 ai-health-plan 相同)51 次运行中 4 次。h08「Word + PDF 一起交付」、h11「读长体检报告出方案」、h10 各中过。形态都一样:读完技能说明后,想在**一次回答里**把整份方案和生成脚本连同思考一起写出来。同一用例的另一次分 14 步写完就过了。
- **真实智能体上还没见到**:生产 ai-health-plan 近 30 天 515 次调用,单次输出最高 30,832,到顶 0 次。测试环境 2,842 次,最高 22,210。
- **10-08 起风险变了**:B-105 随 10-08 上生产后,截断不再是「悄悄残缺」,而是「整轮报错」。

这一格不是模型做不到,是一次写太多。直接判死,丢掉的是一轮完全可以完成的任务。

## 2. 同行怎么做(10-06 读源码)

| | 截断的工具调用 | 截断的纯文本 | 调高上限 |
|---|---|---|---|
| hermes-agent `agent/turn_truncation.py` | 丢弃这条回复,原样重发,最多 4 次;不加提示 | 保留片段,加「从断处接着写」提示,最多续 4 次 | 是,每次翻倍(不超过模型上限) |
| openclaw `run/attempt-recovery.ts` | 不执行;记一条隐藏提示「工具调用在输出上限处被截断、没执行,把剩下的工作拆成更小的调用、参数写短」,然后接着跑 | 保留片段并给用户看「已截断」提示,不续写 | 否 |

## 3. 做法

照 openclaw 的路子:**不执行、丢弃、加一条拆小提示、再试一次**。

1. 截断且不可用时,先照旧计量(这次调用照样计费,B-105 已有),然后看本轮是否已经重试过。
2. **没重试过**:被截的回答**不进历史**(里面的工具调用一个都不执行);写入一条隐藏提示(`HumanMessage`,`expert_work_hide_from_ui`,与 recovery advisory 同一形态),路由回 agent 再调一次。提示内容:
   - 上一条回复撑满了单次输出上限(N tokens,含思考),已作废,其中的工具调用都没有执行;
   - 把这一步拆小重做:大文件分几个文件写,或先写骨架再用 `edit_file` 补;工具参数写短;思考简短。
3. **已重试过**(本轮输入的最后一条就是这条提示)、仍然截断:照旧抛 `OutputTruncatedError`。
4. 重试占一步 `step_count`,受 `max_steps` 约束。上限 1 次是常量,不开配置。

**判「已重试过」不新增 state 通道**:提示消息带 `additional_kwargs["expert_work_truncation_retry"]`,节点开头看 `state["messages"][-1]` 是不是它。路由 `_should_continue` 遇到最后一条是这条提示,就回 `agent`。

## 4. 不做什么

- **不调高上限**:上限是租户在模型配置里设的,也是成本闸。悄悄翻倍等于替租户改配置(hermes 这么做,但它没有租户)。报错文案里「请调大输出上限」保留。
- **不续写纯文本**:正文可用的截断 B-105 已照常交付并计数,不在本条范围。
- **不重试多次**:没有数据支持第二次比第一次更有效,每次失败的重试要多花最多一整个上限的输出 token。先 1 次,用 B-140 量效果再说。

## 5. 流式预览

被作废那次调用的 `token` 帧已经发出去了(预览)。对外协议规定预览是临时的,以同一步的 `updates` 帧为准(`docs/api/streaming-events.md`)。重试这一步的 `updates` 只带一条隐藏提示,客户端会在下一步的预览开始时换掉旧的预览。这和「输出被安全拦截、预览被拒答替换」是同一类行为,不新增帧类型。已知小瑕疵:被作废调用若已发出 `tool_args` 预览卡片,它的 `call_id` 不会出现在任何 `updates` 里。协议本来就要求按 `call_id` 配对、未配上的预览卡片丢弃(「a dropped incomplete call」同一情形)。

## 6. 验证

- **单测**(真图):
  - 截断后第二次正常 → run 成功,被截的回答与它的工具调用都不在历史里、工具没被调用,提示在历史里且隐藏;
  - 两次都截断 → 照旧 `OutputTruncatedError`,工具 0 次;
  - 截断计数器照旧每次都计;
  - 正文可用的截断不受影响。
- **B-140 对照**:h08 / h10 / h11 × 3,修前截断 4/15 次,修后 0 次判「未完成」(截断计数器可以 > 0)。
