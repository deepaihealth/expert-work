## 0. 一页看懂

### 0.1 做什么

| 项 | 一句话 |
|---|---|
| 形态 | 新增一种知识库类型「FAQ 库」(`kind = faq`)。库里不放文档,放**条目**:一个标准问 + 一个答案 + 若干相似问法 + 可选分类 + 启停开关 |
| 检索单位 | 一条 = 一个整体,不切段。每个问法单独进索引,命中任何一个问法都返回整条(标准问 + 答案) |
| 给模型看的 | 和文档段落同一种结果格式,标头是 `[D12#34]`:`D12` 是这个 FAQ 库的编号,`34` 是条目号(建了就不变)。4a 的出处编号直接用它 |
| 回答 | 仍然由模型作答,**不绕过模型直接吐答案**;作答规则、答前核对、出处核对一律不变 |
| 管理 | 控制台:列表 / 搜索 / 筛选、新建 / 编辑 / 删除、逐条与批量启停、命中测试能看到「命中了哪个问法」;Excel / CSV 批量导入(先免费校验 → 报价 → 确认 → 后台执行 → 可下载失败行)、导出 |
| 费用 | 只有向量化花钱,记在租户名下(与现有入库同一口径)。批量导入必须先估价再确认;改一条只重算改过的问法 |
| 开关 | 一个平台开关,**默认关**;关着时建不了 FAQ 库,现有库和智能体完全不受影响 |

### 0.3 这一版治不了的

- **「问得像、其实不是同一件事」**(近似问题):检索总会把最接近的条目拿回来,拦它靠的是模型读了之后判断「这条答的不是这个问题」,以及 4a 的作答规则。本版不做反例问(D5)。能做的是把这一类单独量出来(§8.3 的近似题)。
- **FAQ 库是否比「把同一张问答表当文档上传」检索得更准:现在没有证据。** 管理能力(逐条启停、相似问、稳定编号、不被切碎)是确定的收益;检索准确率的收益要靠 §8.3 的对照量出来,量不出来就如实报告。

## 2. 产品形态:新库类型,还是普通库里的一种条目

| | 甲:新库类型(本文选) | 乙:普通库里可以混放文档和 FAQ 条目 |
|---|---|---|
| 租户怎么理解 | 「这个库是问答库」;建库时选类型,之后不能改 | 一个库里既有文件又有问答条目;界面要在同一个库里并排两套管理 |
| 数据模型 | `kind` 列现成(§1.2);新表挂在库上 | 条目挂在库上或挂在「一份 FAQ 文档」上;库级设置(切段参数、「按新参数重新入库」)对条目没有意义,要逐项说明「对条目不生效」 |
| 界面 | 库详情页按类型换一组页签(条目 / 命中测试 / 检索记录 / 设置) | 文档页签里混一种特殊行,或再加一个页签;批量操作、估价横幅、过期文档提示都要区分两类 |
| 文档 + FAQ 一起搜 | 智能体绑两个库。多库融合是现成的(§1.3);门槛、检索方式可以各设各的 | 同一个库内融合;门槛、检索方式只有一份,问答和文档共用 |
| 对已有库的影响 | 没有。分支只看 `kind`,现有库全是 `document` | 每个库都可能有条目,所有文档级路由都要按行判断 |
| 发布 / 回退 | 开关关着就建不出 FAQ 库,影响面 = 0 个库 | 开关只能挡入口,代码分支在每个库上都走 |
| 与早先设计 | B-175 设计的数据模型就是按库分类型(`2026-10-10-b175-…:178`);总计划 E3 写「新库类型,不影响已有库」 | 要改已拍板文字 |
| 参考实现 | WeKnora:库类型 `faq`,有专属配置(`internal/types/knowledgebase.go:857-914`);MaxKB:问题表独立、挂到段落(`apps/knowledge/models/knowledge.py:272-294`) | RAGFlow:问答是一种**切段模板**,用在普通库上(`internal/ingestion/pipeline/template/ingestion_pipeline_qa.json`;`internal/ingestion/component/chunker/qa.go:17-28`);FastGPT:每条数据本身就是 q + a(`packages/service/core/dataset/data/schema.ts:39-57`) |
| 缺点 | 同时有文档和问答的租户要建两个库、智能体绑两个;目录里多一行 | 见上 |

**选甲。** 理由三条:① 已拍板文字和现成的 `kind` 列都是这个方向;② 分支点只有一个(库的类型),不影响任何已有库,开关关着时影响面是零;③ 库级设置对问答和文档的含义不同,放在一个库里每一项都要解释。乙的唯一明显好处(少建一个库)换不回这些。

**反对甲的证据也要摆出来**:RAGFlow、FastGPT 都没有单独的库类型,说明「混放」是行得通的产品形态;如果以后客户普遍抱怨「要绑两个库」,可以在甲之上加「把 FAQ 库挂到文档库下一起绑定」的快捷方式,不需要推翻数据模型。

**对租户来说,和今天上传问答表的区别**:

| | 今天:问答表当文档上传 | FAQ 库 |
|---|---|---|
| 一个结果是什么 | 一大段,里面好几行问答 | 正好一条问答 |
| 用户换个说法问 | 靠向量碰运气 | 可以给一条挂多个相似问法,每个问法单独进索引 |
| 某一条过期了 | 改文件重传,或把整段关掉(连带同段其它行) | 关掉这一条,立即生效 |
| 改一条答案 | 改文件重传(整份重新估价、重新切段,段号重排) | 改这一条,只有变了的问法重新向量化,条目号不变 |
| 回答的出处指到哪 | 一大段 | 这一条 |
| 维护 | 在 Excel 里 | 在控制台里逐条改,或导出 → 改 → 导入 |

1. **没有一家在高分时绕过模型,除了 MaxKB 的可选项。** WeKnora 的「0.9 直接回答」其实只是一个提示标记。
2. **「索引什么」各家默认不一样**(WeKnora 问 + 答拼一条;Dify 只索引问题;RAGFlow 问 + 答一段;MaxKB 问题单独成行)。没有共识,就不能拍,要量。
3. **每问法一条索引会让同一条目占掉多个名额**,WeKnora 为此专门加了一轮补搜。

## 4. 数据模型与索引

### 4.1 条目

新表 `knowledge_faq_item`(条目的唯一事实来源;索引行由它派生,§4.3):

| 列 | 类型 / 约束 | 说明 |
|---|---|---|
| `id` | UUID 主键 | 内部 id,不出现在任何给模型或对接方的文本里 |
| `tenant_id`、`kb_id` | UUID 非空 | 租户隔离(§4.6);`kb_id` 必须是 `kind = faq` 的库 |
| `item_seq` | 整数,`(kb_id, item_seq)` 唯一 | **条目号**:库内只增不减、删了不复用。出处编号 `D12#34` 里的 34 |
| `question` | 文本,1~256 字符 | 标准问 |
| `answer` | 文本,1~4,000 字符 | 一个答案(§4.2)。纯文本 / Markdown,不解析图片 |
| `similar_questions` | JSON 数组,最多 20 个,每个 1~256 字符 | 相似问法,有顺序 |
| `category` | 文本,可空,最长 64 字符 | 可选的单个分类(§4.2) |
| `enabled` | 布尔,默认真 | 逐条启停 |
| `revision` | 整数,从 1 起 | 每次改文字加 1;编辑时带上读到的版本号,对不上回 409(同分段编辑,`cp/api/knowledge_passages.py:286-287`) |
| `created_by`、`updated_by` | 文本 | 操作人的 subject id |
| `created_at`、`updated_at` | 时间 | |

另加一条长度约束:**整条(分类 + 标准问 + 答案)不超过 2,048 token**(按切段用的分词器数,`cp/knowledge/chunking.py:229-231`)。这是现有「一个分段手工编辑的上限」(`cp/api/knowledge_passages.py:87` = 2 × 1024),取同一个数,保证一条一定放得进一次检索结果的 1 万字符预算、也放得进重排的 3000 字符上限的大部分。

**每个库的条目上限:10,000 条**(建议值,§9.2 第 2 条)。

> 上限这些数从哪来:256 来自 MaxKB 的问题列;2,048 token 来自我们自己的分段编辑上限;20 个相似问、4,000 字符、10,000 条是我给的起点,**没有实测依据**。最坏情况一个库的索引行 = 10,000 ×(20 + 1 + 1)= 22 万行,都在一张段表里;现有的「单文档 4 万段」上限(`cp/settings.py:552`)是为入库时的内存设的(B-214),FAQ 的写入是一条一条 / 一批一批的,不走那条路,也**不受那个设置约束** —— 所以条目上限必须自己设,不能指望它。22 万行对向量索引和关键词检索的影响**未验证**(§9.3 U4)。

### 4.2 三个取舍

> **取舍一:一个答案,还是像 WeKnora 那样多个答案 + 策略?**
> - WeKnora 的多答案是给「随机挑一个回复」用的(`faq.go:251-258`),前提是答案原样发给用户。我们的答案一定经过模型改写,「随机一个」没有意义;「全部返回」等于把几段写进同一个答案框。
> - 多答案 + 随机会让同一个问题两次检索拿到不同的文字:出处指纹(4a)对不上、评测不可重复。
> - 反对:从 WeKnora 之类系统导出的数据可能一条有多个答案。→ 导入模板只有一个答案列;多答案的数据由租户自己并成一个。
> - 结论:v1 一个答案。是否验证过:没有客户提过多答案的需求(**未调研**,只查了仓库和计划文档)。

> **取舍二:分类,还是标签?**
> - 现有标签表是「库内标签 ↔ 文档」多对多(`persistence/models/knowledge.py:516-566`),复用它要再建一张「标签 ↔ 条目」表和一套标签管理界面。
> - v1 的需求只是「列表里能按类筛、导入表里能带一列」。一个可选文本列够用,也正好对上问答表里常见的「分类」列。
> - 分类还有一个现成的去处:作为这一条的「章节路径」(§4.3),模型看到的结果里会带上它,读文档工具可以按它读一组。
> - 结论:v1 单个可选分类。多标签以后要做时,分类列可以原样保留。

> **取舍三:条目另建表,还是全部塞进现有段表?**
>
> | | 另建条目表,段表只放派生的索引行(本文选) | 只用段表(大段行 = 条目,子段行 = 问法) |
> |---|---|---|
> | 列表 / 搜索 / 筛选 / 分页 | 一张表上的普通查询 | 要把大段行和它的子段行拼起来,按问法搜要连表;没有 `updated_at`、操作人、分类列 |
> | 唯一性 | 可以建唯一约束(§4.5) | 段表上建不了只针对 FAQ 的唯一约束而不影响其它文档 |
> | 索引方式以后要换 | 从条目表重建索引行即可,条目不动 | 条目和索引是同一批行,换方式 = 改数据 |
> | 与现有「分段」功能的界线 | 清楚:FAQ 的行不允许走分段编辑接口 | 模糊:大段行会被当成可编辑的分段 |
> | 代价 | 多三张表;条目和索引行要在同一个事务里一起写,否则会不一致 | 不加表 |
>
> 选左边。代价用两条规则兜住:**写条目和写它的索引行永远在同一个数据库事务里**;提供一个「按条目表重建本库索引行」的内部函数(换嵌入模型的重建、修数据都用它),并有一条契约测试断言重建前后检索结果相同。

### 4.3 条目怎么落到现有的段表上

每个 FAQ 库有**一份系统文档**(建库时自动建,`source_type = faq`,文件名 = 库名,状态恒为 `ready`,没有原文件)。它的作用只有三个:给这个库一个文档编号 `D12`;让「文档级启停」「按文档读」这些现成机制对 FAQ 库成立;让段行有 `document_id` 可挂。库名不能改(`cp/api/knowledge.py:121-128`),所以文件名稳定。

一条条目派生出三种行(都在这份系统文档下):

| 行 | 段类型 | 段号 | 正文 | 章节路径 | 向量 | 关键词索引 | 作用 |
|---|---|---|---|---|---|---|---|
| 整条 | `parent` | `item_seq` | `标准问` + 空行 + `答案` | `[分类]`(没有分类则空) | 无(约束要求,§1.2) | 无 | **显示给模型的那一段**;读文档工具读的也是它 |
| 问法(标准问 1 行 + 每个相似问 1 行) | `faq_question` | `item_seq × 32 + 位置`(标准问 0,相似问 1~20) | 这个问法的原文 | 空 | 有 | 有 | 问法对问法的匹配 |
| 问答合并 | `faq` | `item_seq` | `标准问` + 换行 + `答案` | 空 | 有 | 有 | 让只出现在答案里的词(型号、数字、专名)也搜得到 |

- 三种行的 `parent_chunk_id` 关系:问法行、问答合并行都指向「整条」行。于是现有的「按 `parent_chunk_id` 折叠、返回大段」(§1.2)原样成立:命中任何一个问法,结果都是整条。
- 段号的规则只是为了满足 `(文档, 段类型, 段号)` 唯一;**对外只出现条目号**(§5.4)。
- 索引行不带文档标题(`doc_title` 留空):文档标题会被拼进检索文本(`protocol/knowledge.py:301-317`),对 FAQ 来说是每一行都重复一遍库名,只会稀释问法。
- 正文不带「问:」「答:」之类的前缀:那是固定某种语言的说法。**模型能不能稳定分清哪句是问、哪句是答,未验证**(§9.3 U6);分不清的话再评估加语言中立的标记。
- 「问答合并」这一行要不要、问法行要不要带答案,**由 §4.4 的对比决定**;上表是默认候选(方式 B)。
- 启停:条目关掉 = 它的全部派生行 `enabled = false`,同一个事务。召回只取启用的行(§1.2),所以关掉的条目**在结构上**搜不到:搜不到问法行和合并行,就没有任何路径能走到那条「整条」行。整库停用 = 停用系统文档(现成的文档启停,`cp/api/knowledge_maintenance.py:148-176`)。

### 4.4 索引什么:不拍,先比

三种候选:

| 方式 | 进索引的行 | 每条的向量数(n = 相似问个数) | 谁这么做 |
|---|---|---|---|
| A 只索引问法 | 每个问法一行 | 1 + n | Dify(旧副本);WeKnora 的「只问题 + 分开」 |
| **B 问法 + 一行问答合并(默认候选)** | 每个问法一行,另加一行「标准问 + 答案」 | 2 + n | 无完全相同的先例;最接近 MaxKB(问题行 + 段落本身) |
| C 全部拼成一行 | 「标准问 + 全部相似问 + 答案」一行 | 1 | WeKnora 默认(`knowledgebase.go:900-913`);RAGFlow(问 + 答一段,没有相似问) |

- 支持 A / B(每问法一个向量):用户的问题是短句,和问法是「短句对短句」;把十个问法和一大段答案拼在一起(C),向量是它们的平均,任何一个问法都被稀释。总计划的 E1(给每段生成问题单独入索引)赌的是同一件事。
- 反对 A:答案里才有的词(型号、价格、条款号)搜不到。B 用多一行补这个洞。
- 支持 C:最省(一条一个向量);WeKnora 把它做成默认,至少说明它在他们的场景里够用。
- **我们自己没有任何数字。** E1 的假设也还没量(总计划 §2.3:目标 0.822 → 0.848,状态「待设计」)。所以按下面的规则定:

**离线对比(在 F0 里做,只跑检索,不跑智能体;通过线现在就定死)**:

- 数据:§8.2 的合成 FAQ 集的**开发半**(100 条目)。三种方式各建一遍索引。
- 同时比重排文本的两种取法(§5.3):R1 = 命中的那一行自己的文本;R2 = 整条(标准问 + 答案)。共 3 × 2 = 6 组。
- 每组量四个数:
  1. 换说法题(题目不是任何一个已登记的问法)**条目命中 @1**、**@3**;
  2. 答案关键词题(题目里的关键词只出现在答案里)**@3**;
  3. 原样题(题目就是某个已登记的问法)**@1**;
  4. 近似题最高分与换说法题最高分的重叠(只报告,给 §5.6 的门槛用)。
- **合格** ⇔ 换说法 @1 ≥ 85% 且 @3 ≥ 95%;答案关键词 @3 ≥ 90%;原样题 @1 = 100%。
- **选哪组**:合格的组里,选每条向量数最少的方式;同一方式下 R1、R2 都合格选 R1(不用多读一次库)。并列再看换说法 @1。
- **一组都不合格**:不上线,把六组的数报给用户,另议(不是自动选最好的那组)。
- 四个百分比是我事先定的起点,**不来自数据**;要改请在跑之前改(§9.2 第 4 条)。
- 花费:6 组 × 100 条目的嵌入 + 约 130 道题的查询嵌入与重排调用。量很小,跑前照例用评测的估价脚本报价。
- 这次对比用的是开发半;验收用留出半(§8.4)。**标定和验收不用同一批题。**

### 4.5 唯一与重复

- **规则**:同一个库里,任何两个问法(不论是标准问还是相似问、不论属于哪一条、不论启用与否)规范化后不能相同。一个问法指向两条答案 = 检索结果取决于运气。
- **规范化**:NFKC、转小写、空白折叠成一个空格、去掉首尾空白和结尾的问号 / 句号(全角半角都算)。只做字面归一,不做同义判断。
- **怎么保证**:新表 `knowledge_faq_question_key(tenant_id, kb_id, question_key, item_id)`,主键 `(kb_id, question_key)`,`question_key` 是规范化文本的 SHA-256。条目的写入事务里同步维护;撞了主键 = 重复,接口回 409 并指出和哪一条(条目号)撞了。靠数据库约束而不是「写之前先查一下」,并发导入和手工编辑同时发生时也成立。
- **同一条内部**:相似问与标准问相同、相似问之间相同 → 保存时直接去掉重复的,不报错。
- **不做**:语义近似的重复检测(两条问法意思一样但字面不同)。v1 靠命中测试人工发现;导入报告里**不**做相似度比对(那要嵌入,就不是免费校验了)。

### 4.6 修订历史、迁移、租户隔离

**修订历史**:新表 `knowledge_faq_item_revision(id, tenant_id, kb_id, item_id → 级联删除, revision, snapshot JSONB, edited_by, created_at)`,`(item_id, revision)` 唯一。`snapshot` 是那一版的标准问、相似问、答案、分类。每次改文字写一行;可以查看历史、把某一版写回(写回 = 一次新的编辑,产生新版本、重新走向量复用)。

> 为什么不复用现有的分段修订表:它每行只有「正文 + 章节路径」两列,而且带着分段特有的语义 —— 重新入库后「对不上的修改」「继承的停用」「孤儿 30 天后清理」(`persistence/models/knowledge.py:462-513`)。FAQ 条目没有「重新入库」这回事。硬塞进去要么把整条序列化进 `content`,要么让那些字段对 FAQ 行永远是空的。复用的是**做法**(版本号乐观锁、历史列表、写回、操作人显示名,`cp/api/knowledge_passages.py:17-20,520-610`),不是那张表。

**迁移**(一个,只加不改;编号以合并时为准,当前最新是 0186):

| 对象 | 内容 |
|---|---|
| `knowledge_faq_item` | §4.1;索引 `(tenant_id, kb_id, item_seq)` 唯一、`(tenant_id, kb_id, enabled)`、`(tenant_id, kb_id, category)` |
| `knowledge_faq_question_key` | §4.5 |
| `knowledge_faq_item_revision` | 上文 |
| `knowledge_base.faq_last_seq` | 可空大整数。条目号计数器:在条目的写入事务里 `UPDATE … SET faq_last_seq = COALESCE(faq_last_seq, 0) + n … RETURNING`,库行的行锁把并发串起来(同文档编号计数器的思路,`persistence/knowledge/sql.py:1713-1727`) |
| `knowledge_task.status` 的取值约束 | 加一个 `awaiting_confirmation`(§6.3)。这张表今天没有任何写入方(§1.2),过期清理只删三种收尾状态(`retention-cleanup-job/…/settings.py:101-105`),新状态不会被误删;**清理语句本身没有逐行核**(§9.3 U9) |

- 三张新表都带 `tenant_id`,都按 `0165` 的写法开行级安全策略。
- **但运行期的连接今天不受行级安全约束**(项目既有结论:应用以超级用户连接,策略不生效;RLS 项目在第 0 阶段后搁置)。所以隔离的真正保证是:每条 SQL 都带 `tenant_id` 条件 + SQL 与内存两套存储实现用同一组参数化契约测试,其中必须有「用租户甲的身份读 / 改 / 删租户乙的条目 → 一律当作不存在」的用例。行级安全策略是第二道,不能当第一道写进验收。
- 回滚:只换回旧镜像即可,新表和新列旧代码不读。旧镜像下已经建好的 FAQ 库会被当成普通库(§8.5)。

### 5.1 一张表看改哪里、不改哪里

| 环节 | 现在 | FAQ 库 | 改不改代码 |
|---|---|---|---|
| 召回 SQL(向量、关键词) | 取启用的、可检索类型的行 | 同;`faq` / `faq_question` 已在可检索集合里(§1.2) | **不改** |
| 每路召回深度 | 条数 × 2,夹 50~100 | 取 3 倍再按条目折叠(§5.2) | 改(只对 `kind = faq` 的库) |
| 融合 | 所有库所有路加权 RRF | 同;FAQ 库的每一路先按条目折叠,一条 = 一票 | 改(同上) |
| 重排文本 | 子段的标题 + 章节 + 正文 | 由 §4.4 的对比定:命中行自己的文本,或整条 | 可能改 |
| 重排分下限 | 按库各自过滤 | 同;FAQ 库的默认值见 §5.6 | 小改 |
| 折叠成结果 | 子段 → 大段 | 问法行 / 合并行 → 整条 | **不改** |
| 去重 | 章节 + 正文相同只留一条 | 同(不同条目的正文不同,不会误并) | **不改** |
| 条数、字数预算 | 5 条(4a 后读库设置)、1 万字符 | 同;一条算一个结果 | **不改** |
| 结果文本 | `[D12#7] 文件名` + 大段文字 | `[D12#34] 库名` + 整条文字;放不下时不退回只显示问法 | 改(§5.4) |
| 工具说明、作答规则、答前核对 | — | 一个字不改 | **不改** |

### 5.2 召回与融合

- **问题**:一条有 20 个相似问时,它在向量那一路可能占掉前 20 个名额;别的条目被挤出召回深度,重排的 100 个名额也被同一条的不同问法占掉。WeKnora 遇到的就是这个(§3)。
- **做法**(只对 `kind = faq` 的库,在 `tools/knowledge.py:613-655` 那个按库循环里):
  1. 这个库的每一路向存储要 `深度 × 3` 行(上限 300)。
  2. 按「整条」折叠:同一条只留排名最高的那一行,截到 `深度` 条。
  3. 同一条在向量路和关键词路可能是不同的行(比如向量命中某个相似问,关键词命中合并行)。两路统一用**同一个代表**参与融合,这样一条在两路都命中时能拿到 RRF 的两票,而不是被当成两个互不相干的候选。每一路实际命中的是哪一行另外记下来,给命中测试和检索记录用。
- 「3 倍」是起点,**未验证**:§4.4 的对比顺带报「折叠后不足 `深度` 条的查询占多少」;占比高就调大。不做 WeKnora 那种「不够再搜一轮」的循环 —— 多一次往返,先看 3 倍够不够。
- 文档库的召回路径一行不动。

### 5.3 重排

- 重排模型是按「问题 ↔ 段落」训练的。拿「用户的问题」对「一个问法」打分(R1)是「问题 ↔ 问题」,它打得准不准**没有证据**;拿「用户的问题」对「标准问 + 答案」打分(R2)更接近它的训练方式,但要在重排之前先把候选的「整条」行读出来(一次批量读,最多 100 行;读到的行后面出结果时复用,同去重已有的做法,`tools/knowledge.py:668-675`)。→ 两种都放进 §4.4 的对比。
- FAQ 候选没有文档标题,所以「带标题」和「只看正文」两个视图是同一段文字,加权后的分 = 单次的分,和文档候选的加权分在同一个刻度上(`tools/knowledge.py:1034-1044` 对「全部候选两视图相同」的情况已有处理;**混合候选时 FAQ 的那几个会被原样多打一次分**,多出的重排调用量和它记在谁账上**未验证**,§9.3 U7)。
- **不给 FAQ 加权**(WeKnora 乘 1.2)。理由:① 乘过之后的分不在重排模型的刻度上,4a 的门槛(按模型标定)对它就没有意义了;② 「FAQ 一定比文档更该信」是一个产品假设,不是事实 —— 文档可能更新、FAQ 可能过期;③ 没量过混排时 FAQ 是不是真的吃亏。先量(§8.3 混绑题),吃亏再议。

### 5.4 结果长什么样、编号是什么

给模型看的一条(围栏内,租户文字):

```text
[D12#34] 示例售后问答库
[Section: 退换货]

怎么申请退货?

登录后进入「我的订单」,在订单详情里选择「申请退货」并填写原因;审核通过后按页面提示寄回。
```

- 第一行标头:`D12` = 这个 FAQ 库的系统文档编号;`34` = **条目号**。后面是库名(就是系统文档的文件名)。
- 标头之后是「整条」行的文字:分类(有才有,沿用现成的章节路径写法)、标准问、空行、答案。
- **不显示**命中的是哪个相似问:模型需要的是标准问和答案;命中的问法只进工具元数据。

**一个编号 = 整条**(与 4a 设计 §3.1.2 同一口径:一个编号 = 显示给模型的那一段文字):

| | 文档段落(4a) | FAQ 条目 |
|---|---|---|
| 显示的是什么 | 一个大段 | 整条 |
| 标头里的号 | 排名最高的子段的号 | 条目号 |
| 这一段登记哪些号 | 同一大段里上榜的子段号 | 只有条目号 |
| 号稳不稳定 | 重新入库会重排(靠指纹识别) | 建了就不变、删了不复用(仍然算指纹,用来识别「答案改过」) |

- 实现上只有**两处**把子段号换成条目号:检索结果成形处(`tools/knowledge.py:1261-1296` 的 `_retrieved`:候选是 FAQ 类型的行时,结果的段号和「上榜的子段号」都取所属整条行的段号)和读文档的视图(`tools/knowledge_read.py:430-438` 的 `_view`:子段全是 FAQ 类型时,这一段的号 = 整条行的段号)。下游的标头、`meta["refs"]`、旧结果压成的引用行、读文档的区间标头、4a 的出处登记,读的都是这两个字段,**不用各自分支**。
- **放不下时**:现有逻辑是退回「只显示命中的子段」(`tools/knowledge_results.py:108-118`)。FAQ 的子段是问法,只显示问法 = 不给答案,比不显示更糟。所以 FAQ 结果不提供「命中子段」这个备选:排在后面的放不下就到此为止;排第一的放不下(只可能在别的工具把预算改小时发生,正常一条 ≤ 2,048 token 一定放得下)按现有规则截断并标「已截断」,模型可以用 `knowledge_read D12#34` 读全。
- 工具元数据(不发给模型)多两样:`matched`(这一条在各路实际命中的行是标准问、第几个相似问、还是合并行;只有位置,没有文字)、`exact_phrase`(查询规范化后与某个问法完全相同,布尔)。命中测试接口另外把命中问法的原文带给界面(§6.2);它本来就返回命中子段的正文(`cp/api/knowledge.py:1467`),界面也已经在显示(`admin-ui/pages/knowledge_detail/RetrievalTestTab.tsx:105-106`)。

**与 4a 出处对象的对接**(F3b,等 4a 的 A0 / A1a):

```json
{"ref": "D12#34", "doc_seq": 12, "chunk_indexes": [34],
 "title": "示例售后问答库", "filename": "示例售后问答库",
 "heading_path": ["退换货"],
 "fingerprint": "5b1e0c9d2a7f4e31",
 "kind": "faq", "question": "怎么申请退货?"}
```

- 只多两个**可选**键:`kind`(没有就是文档段落)和 `question`(标准问,给界面的悬停提示用)。不带任何内部 id、不带条目的数据库 id。
- `fingerprint` 的算法和 4a 完全一样(章节路径 + 这一段正文的 SHA-256 前 16 位):因为「整条」行的正文就是标准问 + 答案,所以标准问、答案、分类任何一个改了,指纹就变。**相似问的增删不改指纹** —— 它们不是显示给模型的文字。
- 原文抽屉(4a 的 A3 给取段接口加「按文档号 + 段号定位」):对 FAQ 库,段号按条目号去找「整条」行;条目已删 → 取不到 → 显示快照 +「原文已变更」;答案改过 → 指纹对不上 → 同样处理。条目被停用但没删:抽屉照常显示原文并标「已停用」。
- 4a 没上线时:FAQ 结果照常返回、模型照常作答,只是没有出处对象。

### 5.5 高分命中要不要变行为:不变

**不绕过模型。** 理由:

1. 我们的产品是智能体,不是问答机器人:回答要过角色设定、输出筛查、输出判官、脱敏(4a 设计 §3.1.1 列过这三道改写,`graph_builder/builder.py:1594-1692`),可能配了输出格式,用户的一条消息可能问了两件事、或者还要调别的工具。直接吐 FAQ 答案会绕过所有这些。
2. 「高分」没有稳定的含义:目录里四个重排模型没有一个声明了跨请求可比的 0~1 分数(4a 设计 §3.3.1);向量相似度随嵌入模型变。WeKnora 的 0.9、MaxKB 的 0.9 都是绑定各自模型的经验值。
3. 检索的查询串是**模型写的**(`tools/knowledge.py:181-186`),不是用户原话。它和某个问法字面相同,不等于用户问的就是这一条。
4. 两个参考实现里,WeKnora 也没有绕过(§3)。MaxKB 的直接返回是给「对外检索」用的 —— 我们如果要,它属于开放 API(R1),B-175 设计当时也是这么放的(`2026-10-10-b175-…:106`)。

**也不给模型看「精确匹配」标记、不把 FAQ 结果排到文档前面。** WeKnora 做了这两样。不做的理由:标记会被模型读成「可以照抄、不用看用户还问了什么」;排前面等于 §5.3 说的加权。两样都没有证据说明利大于弊。`exact_phrase` 只记在工具元数据和检索记录里,供排查用。

**作答规则原样适用。** 工具说明里的作答规则、结果后面的提示、答前核对(`tools/knowledge.py:174-180,207-214`)说的是「段落有没有明确写出被问的事实」,对 FAQ 条目同样成立:条目答的不是用户问的那件事,就该说资料没写。**这些文字一个字不改** —— 所以没绑 FAQ 库的智能体多花 0 个 token 是结构上保证的(§5.9)。

### 5.6 相关度门槛(4a 的 T3)

- 机制不变:FAQ 库也是一个库,有自己的重排分下限,按库过滤、全不过线时降一次、还不过就返回「没找到」+ 最近的文档标题清单(对 FAQ 库,清单里就是 `D12 库名` 一行;模型可以 `knowledge_read D12` 翻看条目)。
- **默认值不直接套用。** 4a 的平台默认下限是在文档段落上标定的。FAQ 候选的打分文本(问法,或标准问 + 答案)不一样,分数分布可能不同 —— 尤其是近似题:问法很像、答的不是一回事,分数多半很高。
- 规则:`RerankCaps` 的默认下限对 FAQ 库是否生效,取决于一次检查 —— 用那个默认值在 **FAQ 留出集**上数「换说法题里,正确条目被挡掉的题数」。为 0 → FAQ 库留空 = 跟随平台默认;不为 0、或者还没量 → FAQ 库留空 = 不过滤。自定义下限、填 0 的含义与 4a 相同。这是与 4a 文字的一处出入(§0.2 第 6 条),要用户确认(§9.2 第 6 条)。
- 近似题在门槛上分不分得开,只报告、不设红线(同 4a 对「同领域但库里没有」那一档的处理)。

### 5.9 「没绑 FAQ 库就没有任何变化」靠什么保证

- 提示词、工具说明、结果提示:**没有新增或改动任何一句**。FAQ 只改结果正文的内容(围栏内)和目录里 FAQ 库那一行。
- 检索路径:所有新分支的条件都是「这个库的 `kind` 是 `faq`」或「这一行的段类型是 FAQ 类型」。开关关着时建不出这样的库,这样的行也就不存在。
- 验收里有一条单测:只绑文档库的智能体,构建出的系统提示词、工具定义、以及对同一份固定数据的检索结果文本,与改动前**逐字节相同**。
- 绑了 FAQ 库的智能体多出来的:FAQ 库每一路多取 2 倍的行(数据库读,不调模型);若选了 R2,重排前多一次批量读;不多调任何模型。回答所用的 token 取决于返回的条目文字,不比同样内容放在文档里多。

## 6. 管理界面与接口(v1 只对控制台)

### 6.1 接口

全部挂在 `/v1/knowledge/bases/{name}/faq/…` 下,`console_only`;对 `kind` 不是 `faq` 的库一律 400。跨租户只读(平台人员切换租户)沿用现有读范围的做法(`cp/api/knowledge.py:1397-1407`):看得到,按钮点不了。

| 接口 | 权限 | 说明 |
|---|---|---|
| `POST /v1/knowledge/bases`(现有)多收一个 `kind` | `manifest:write` | 默认 `document`;`faq` 只在平台开关开着时接受。建 FAQ 库时同一个事务里建系统文档。类型建后不可改。返回体加 `kind`;FAQ 库的 `stats` 给条目数 / 启用数 |
| `GET …/faq/items` | `manifest:read` | 分页(默认 50,最多 200);筛选:关键字(在标准问、相似问、答案里做子串匹配)、分类、启用状态;排序:条目号 / 更新时间 |
| `GET …/faq/items/{item_seq}` | `manifest:read` | 单条,含相似问 |
| `POST …/faq/items` | `manifest:write` | 新建。校验 → 查重 → 嵌入(只嵌入新文本)→ 一个事务写条目 + 索引行 + 查重键 + 修订 |
| `PATCH …/faq/items/{item_seq}` | `manifest:write` | 改文字(必须带读到的 `revision`)和 / 或 `enabled`。只改 `enabled` 不产生新版本、不调模型 |

| `GET …/faq/items/{item_seq}/revisions`、`POST …/restore` | 读 / `manifest:write` | 历史与写回 |
| `POST …/faq/imports` | `manifest:write` | 上传文件 + 列映射 + 模式;返回任务 id。只做免费校验(§6.3) |

**审计**:新动作 `knowledge:faq_item_create / _edit / _toggle / _delete / _restore / _batch`、`knowledge:faq_import / _import_confirm / _import_cancel`、`knowledge:faq_export`(导出是整库内容的批量读取,记一笔)。资源类型加 `knowledge_faq_item`(现有只有库和文档两种,`cp/api/knowledge.py:195-212`)。审计详情只放库名、条目号、数量、任务 id、模式,**不放问题和答案的文字**。

**错误**:409 `revision_conflict`(带当前内容)、409 `duplicate_question`(带撞上的条目号和是哪个问法)、422 `question_too_long` / `answer_too_long` / `item_too_long` / `too_many_similar_questions`、409 `item_limit_reached`、409 `import_in_progress`(一个库同时只允许一个导入任务)、503(没配嵌入模型,同现有文案)。

**单条新建 / 编辑的费用**:沿用「手工改分段」的现有做法 —— 直接嵌入变了的文本、记租户账,**不弹估价确认**(§1.2)。保存按钮旁写明「保存会对新增或改动的问法做向量化,按用量计费」。这和「无论金额大小都要确认」的字面有出入,但与已上线的分段编辑一致;要用户确认(§9.2 第 3 条)。

**只重算改过的问法**:保存时按新内容生成全部索引行的检索文本,算内容哈希;哈希在这份系统文档里已有、且是当前嵌入模型做的 → 复用向量(现成机制,§1.2);其余的才调嵌入。所以:只改答案 → 只重算「问答合并」那一行;加一个相似问 → 只算那一个;只改分类或启停 → 一个都不算。**这是靠哈希复用在结构上成立的,不是靠调用方自觉**;单测用一个会计数的假嵌入器钉住每种编辑各调了几次。

### 6.2 界面(`admin-ui/pages/knowledge_detail/`)

- **建库**:向导里多一步选类型(文档 / FAQ),注明「建后不可改」。开关关着时不显示这一步。
- **FAQ 库的详情页**:页签换成「条目 / 命中测试 / 检索记录 / 设置」(文档库的是「文档 / 命中测试 / 检索记录 / 设置」,`admin-ui/pages/KnowledgeDetail.tsx:222-226`)。
- **条目页签**:表格列 = 条目号、标准问、相似问个数、分类、启用开关、更新时间、更新人;上方搜索框 + 分类筛选 + 启用筛选;多选后「启用 / 停用 / 删除」;右上「新建」「导入」「导出」。
- **编辑抽屉**:标准问、答案(多行,显示字数与 token 数、离上限还有多少)、相似问(一行一个,可增删、可拖动排序)、分类、启用;「历史」页签看各版本并写回。保存冲突时显示对方改成了什么。
- **命中测试**:结果卡片显示条目号、标准问、答案、分数明细(现成),另加一行「命中的问法:第 2 个相似问『……』」或「标准问」或「答案内容」。这是调相似问的主要工具:搜一个用户的真实问法,看有没有命中、命中的是哪个问法、排第几。
- **设置**:FAQ 库不显示切段参数、「按新参数重新入库」;检索方式、返回条数、相似度阈值、重排开关与下限照常。
- **文案**:中英两套,新键放在自己的键组里(`knowledge_faq.*`),不动现有键。

### 6.3 批量导入

**文件**:`.xlsx` 或 `.csv`;最大 10 MiB、最多 10,000 行(建议值)。`.xlsx` 只读第一个工作表(或在映射步骤选一个);单元格按显示值读,合并单元格向下填充(与现有表格解析同一套规则,`cp/knowledge/office_xlsx.py:14-28`);公式取缓存值。`.csv` 按 UTF-8(带不带 BOM 都行)读,读不出来就报错并提示另存为 UTF-8,不猜别的编码。

**列映射**:

- 模板的表头是固定的英文键:`question`、`answer`、`similar_questions`、`category`、`enabled`。表头正好是这些键时自动映射。
- 表头是别的(比如客户自己的问答表):界面上让用户逐列指定「这一列是什么」,前 5 行预览。服务端**不按任何语言的常见叫法去猜**(那是把某种语言的词写进平台代码)。
- 相似问:一个单元格里用换行分隔多个;也可以把多列都映射成「相似问」。
- `enabled` 列可省(默认启用);认 `TRUE` / `FALSE` / `1` / `0`。

**两种模式**:

| 模式 | 做什么 | 已存在的标准问 |
|---|---|---|
| 追加(默认) | 只新增 | 两个选项:**跳过**(默认)/ **用文件里的覆盖**(答案、相似问、分类以文件为准;条目号不变) |
| 替换全部 | 让库里的条目变成和文件一样 | 按规范化后的标准问逐条对比:没变的不动(条目号、向量都保留);变了的更新;文件里没有的**删除**;新的新增 |

「替换全部」不是「清空再灌」:清空再灌会让全部条目号重编、全部向量重算、所有旧出处失效。按差异做,只有真变了的才花钱,没变的条目旧出处照样有效。它会删条目,所以确认时要 `manifest:delete`,并且确认框里写明「将删除 N 条、更新 M 条、新增 K 条」,要用户输入库名才能点确认。

**流程**(状态记在 `knowledge_task` 一行里;`task_type = faq_import`):

| 阶段 | 任务状态 | 做什么 | 花钱吗 |
|---|---|---|---|
| ① 校验 | `running`(`stats.phase = validating`) | 解析文件;逐行检查(下表);与库里现有条目比对,算出每行的去向(新增 / 更新 / 跳过 / 失败)和要删的条目数;数出要新嵌入的文本及其 token | 不花:不调任何模型 |
| ② 待确认 | `awaiting_confirmation` | 给出校验报告 + 估价(向量化一项;平台开着「先查知识库」时另有画像刷新一项,同 B-222 / B-267 的分项)。最长保留 7 天(B-222 §14 的拍板),过期自动撤回 | 不花 |
| ③ 执行 | `running`(`stats.phase = applying`) | 每批 200 条:嵌入这一批的新文本 → 一个事务写这一批。每批之前检查是否被取消;进度 = 已处理 / 总数 | 花(只有新文本) |
| ④ 结束 | `succeeded` / `failed` / `cancelled` | 结果统计(新增、更新、跳过、删除、失败各几条)+ 实际花费;「替换全部」的删除放在最后一步,前面任何一批失败就不删 | — |

- 金额为 ¥0.00(比如全部是没变的行)也要点确认 —— B-222 的规则。
- 确认后、真正开始前再校验一遍(库在待确认期间可能被人改过):去向和要嵌入的文本对不上了,就退回待确认并更新报告(同 B-222「确认后真花钱前再估一次」)。
- 中途失败或取消:已经写入的批次**保留**(每批自己是完整的),报告里写清处理到第几行。重新导入同一个文件是幂等的:已写入的行会被判为「没变,跳过」,向量按哈希复用。
- 后台执行与多副本:任务由控制面的后台工作者认领,沿用文档入库的「认领 + 租约 + 兜底巡检」做法(B-222 设计 §1 描述的快路径与 `cp/knowledge/recovery.py` 的兜底;**这个文件我没有打开**,以 B-222 设计的描述为准)。**这部分要在真栈上验**(§8.6)。
- 上传的文件在任务结束或撤回后删除;存放位置(对象存储,还是任务表旁边加一列)在 F4 开工时定,**未验证**(§9.3 U11)。

**逐行检查**(都是免费的):

| 检查 | 结果 |
|---|---|
| 标准问或答案为空 | 失败 |
| 标准问 / 相似问 / 答案 / 整条超长;相似问超过 20 个 | 失败,原因里写是哪一项、超了多少 |
| 同一个文件里标准问重复 | 第一条之后的都失败,指出与第几行重复 |
| 相似问与本文件里别的行的任何问法重复,或与库里**别的**条目的问法重复 | 这一行失败(不是只丢掉那个相似问 —— 悄悄丢掉会让用户以为导进去了) |
| 同一行内相似问重复、或与本行标准问相同 | 自动去掉,不算失败,报告里计数 |
| 追加后会超过库的条目上限 | 整个任务校验不过 |
| 行数或文件大小超限 | 上传时直接拒绝 |

**校验报告**:各种去向的行数;前 100 条失败行(行号 + 原因);「下载全部失败行」。失败行文件是用户自己的数据加一列原因,改完可以直接再导入。

### 7.1 已经传进普通库的问答表,怎么变成 FAQ 条目

**建议:v1 不做专门的转换工具,给操作指引。**

- 指引:在 FAQ 库的「导入」里上传**同一个原文件**,在列映射里指定哪列是问题、哪列是答案;导入完成后,到原来的文档库里把那份文档停用或删除。
- 为什么不做工具:① 导入已经能吃同一个文件,转换工具做的事 = 导入 + 停用旧文档,只省了「再选一次文件」;② 从已入库的段落反推问答对是不可靠的 —— 表格被切成了「几行一段、长行被切开、表头重复」(§1.1),要转只能回去读原文件,而原文件那一列可以为空(4a 设计 §3.1.4 核过);③ 自动转换意味着替用户判断「哪张表是问答表、哪列是问题」,判断错了就是把一张价格表变成一堆乱七八糟的条目。
- 不这么做的风险:用户导入了 FAQ 却忘了停用旧文档,两个库都绑着,同一条答案会从两处各返回一次(去重只认「章节 + 正文完全相同」,问答表的段和 FAQ 条目的文字不同,**去不掉**)。缓解:导入完成页固定提示一句「如果这些问答也作为文档存在于别的库,请停用那份文档」。
- 以后若要加:最小的一步是导入时按文件内容的 SHA-256 在本租户的文档里查同一份文件,查到就在提示里点名是哪个库的哪份文档。v1 不做(要加一个跨库查询)。

### 8.2 合成 FAQ 集

全部合成,三个虚构领域(网店售后、软件账号与订阅、家用设备使用),不含任何客户内容,入库前人工过一遍。

| 部分 | 数量 | 说明 |
|---|---|---|
| 条目 | 200(每个领域约 67) | 每条 0~5 个相似问;约三分之一的答案里有只在答案出现的专名 / 型号 / 数字;有 20 组「主题相近、答案不同」的条目(比如同一件事的两种情形) |
| 换说法题 | 150 | 问的是某一条,但说法**不在**该条已登记的任何问法里 |
| 原样题 | 30 | 题目就是某个已登记的问法(一半是相似问) |
| 答案关键词题 | 30 | 题目里的关键词只出现在答案里 |
| 近似题 | 60 | 和某一条主题相同,但问的是库里**没有答案**的另一件事(换了对象、条件或数量)。标注「最像的是哪一条」和「正确的做法是说资料没写」 |
| 离题题 | 20 | 沿用 4a 的通用离题题 |
| 混绑题 | 30 | 另配一个合成文档库(约 20 份短文档)。10 题答案只在 FAQ、10 题只在文档、10 题两边都有且**说法不同**(其中 5 题两边内容冲突) |
| 停用对照 | 20 条 | 从上面的条目里指定 20 条,在「停用」那一臂里关掉 |

- 按条目分成**开发半 / 留出半**(各 100 条目,题目跟着条目走;近似题、混绑题对半分)。开发半用于 §4.4 的对比、调多取倍数、看门槛;留出半只在验收时跑一次。
- 换说法题和近似题由我们写(可以用模型起草,人工逐条审),**写的人不看条目的相似问列表以外的检索结果**,避免照着系统能搜到的写。
- 现有开发集里来自问答表的 158 题**不用来验收 FAQ**:它们的题目就是表里的问题原文(`README.md:105-106`),属于「原样题」,量不出换说法的效果;而且那是客户内容,不能灌进一个新造的 FAQ 库去跑对照。

### 8.3 指标、通过线、必须变红的对照

**检索层**(不调对话模型;统计脚本直接算):

| 指标 | 定义 | 通过线(留出半) |
|---|---|---|
| 换说法 @1 / @3 | 正确条目排第 1 / 前 3 的题占比 | ≥ 85% / ≥ 95% |
| 原样 @1 | 同上,原样题 | **100%**(硬线:登记过的问法搜不到自己那一条就是缺陷) |
| 答案关键词 @3 | 同上 | ≥ 90% |
| **停用的条目被返回** | 「停用」臂里,20 条停用条目出现在任何一次检索结果里的次数 | **0**(硬线) |
| 混绑:FAQ 题 @3 | 同时绑 FAQ 库和文档库,答案只在 FAQ 的题 | ≥ 95% |
| 混绑:文档题不被挤掉 | 答案只在文档的题,正确文档进前 5 的题数,与「只绑文档库」相比 | 少不超过 1 题 |
| 相对「表格上传」基线 | 把同样 200 条做成一张问答表传进普通库,同一批题 | FAQ 库的换说法 @3、答案关键词 @3 **都不低于**基线(硬线);高多少如实报告,不设线 |
| 近似题分数重叠 | 近似题最高分与换说法题正确条目分数的分布 | 只报告 |
| 折叠后不够数 | 多取 3 倍后,折叠出的条目数仍小于召回深度、而库里还有更多条目的查询占比 | 只报告;高于 5% 就调倍数重跑 |

**智能体层**(真模型答题,沿用 `tools/eval/kb_agent_*` 的答题与 3 票判分;每题跑两次):

| 指标 | 定义 | 通过线 |
|---|---|---|
| 换说法题答对 | 回答与该条答案一致 | ≥ 90% 题次 |
| 换说法题误拒 | 说「资料没写」 | ≤ 2 题次 |
| **近似题采纳了错的条目** | 把最像的那一条的答案当成这个问题的答案给了用户(没有说明「资料里只有另一种情形」) | ≤ 10% 题次(起点值;没有基线) |
| 近似题正确处理 | 说明资料没写这件事(可以提到相近的那一条并说明它讲的是另一种情形) | 只报告 |
| 混绑冲突题 | 两边内容冲突的 5 题:是否把冲突说出来了,而不是只挑一边 | 只报告(题太少,不设线) |
| 出处(4a 开着时) | 带出处比例、引对了(指到的是答案所在的那一条) | 沿用 4a 的线:≥ 80% / ≥ 90% |

**必须变红的对照**(证明指标咬得住;不红则本轮结果作废、先修指标):

| 对照 | 做法 | 必须看到 |
|---|---|---|
| 关掉启停过滤 | 评测脚本里用一个不看 `enabled` 的召回(只在评测里) | 「停用的条目被返回」> 0,且 20 条里至少一半出现过。证明这个 0 不是因为那 20 条本来就搜不到 |
| 停用正确条目 | 把每道换说法题的正确条目停用 | 这些题的 @3 降到 5% 以下 |
| 打乱标准答案 | 把每题的「正确条目」换成随机另一条 | 换说法 @1 降到 5% 以下 |
| 拿掉相似问索引 | 只留标准问那一行 | 「题目 = 某个相似问」的那 15 道原样题,@1 明显下降(从 100% 降到不足 90%);不降说明这批相似问写得和标准问太像,数据要重写 |
| 植入错条目答案 | 取近似题,把「最像那一条的答案」原样当作回答交给判分 | 「采纳了错的条目」判出 100%;判不出来说明判分模板不咬 |
| 假编号(4a) | 沿用 4a 设计 §5.3 | 同 4a |

通过线里的百分比**没有基线可依**,是起点值;可以改,但要在看留出半的结果之前定下来(§9.2 第 10 条)。

### 8.5 开关与发布窗口

| 开关 | 默认 | 关着时 | 开着时 |
|---|---|---|---|
| 平台开关「FAQ 库」(环境变量,启动时读一次,同 `kb_first_routing` 的做法,`cp/settings.py:199-204`) | **关**(测试、生产都是) | 建库接口不接受 `kind = faq`;FAQ 路由 404;界面不显示类型选择。已经存在的 FAQ 库**继续能被搜到、能被管理接口以外的路径读到**(数据在,不能因为关开关让绑了它的智能体突然搜不到) | 全部可用 |
| 4a 的出处开关、门槛开关 | 按 4a(默认关) | FAQ 结果没有出处对象;门槛按今天的行为 | F3b 的出处部分生效 |

- **迁移**(F1)只加不改,合进主干即随班车发到测试 / 生产,此时开关关着,没有任何可见变化。
- **测试环境**:F2、F3a、F5 都合完并各自过了真栈用例之后才打开;F4 没合之前可以开(只是没有导入)。
- **生产**:F0~F5 全部合完、留出半验收过线、用户说「开」之后才开。F3b 可以晚于生产打开(那时 FAQ 结果先没有出处对象)。
- **回退**:关开关 = 不能再建 FAQ 库、管理界面不可用,已有的 FAQ 库照常被检索。要彻底停掉某个 FAQ 库:停用它的系统文档(现成的文档启停),或从智能体上解绑。
- **换回旧镜像时**:旧代码不认识 `kind`,会把 FAQ 库当成普通库 —— 检索仍能返回条目(索引行本来就是可检索类型),只是标头里的号变成问法行的内部段号;旧界面会把它显示成「只有一份文档的库」,并允许往里上传文档。所以回滚说明里要写:旧镜像期间不要在控制台操作 FAQ 库。

### 8.7 花费怎么估(只给算法,开跑前按当时的价目出报价)

- **检索层**:六组 × 100 条目的索引嵌入(每条约 2~7 段短文本)+ 每组约 160 道题的查询嵌入与重排;留出半再跑一遍选中的那一组 + 基线 + 各对照臂。全是嵌入和重排调用,量级远小于一次智能体评测;用评测的只读嵌入缓存后重复跑不再计费。具体金额**未算**,跑前用 `tools/eval/kb_agent_estimate.py` 同一套价目出数。
- **智能体层**:留出半的换说法 75 + 近似 30 + 混绑 15 = 120 题,每题两次 = 240 题次;加「表格上传」基线臂只跑换说法 75 题 × 2 = 150 题次;合计 390 题次。按总计划 11-10 实测的每题次约 ¥0.96 是**上限**(FAQ 的检索内容比文档短),约 ¥374。判分另计(3 票),同样跑前报价。
- 对照臂:关掉启停过滤、停用正确条目、打乱答案、拿掉相似问 —— 只重跑检索;「植入错条目答案」只调判分(30 题)。
- 用户说「跑」再跑;每题两次。

## 9. 风险、待拍板与未验证

### 9.1 风险

| # | 风险 | 依据 | 应对 |
|---|---|---|---|
| R1 | FAQ 库的检索并不比「问答表当文档上传」准 | 没有任何数字;各家索引方式没有共识 | §8.3 设了「不低于基线」的硬线并如实报告差多少;管理能力的收益不依赖它 |
| R2 | 近似问题拿到最像的条目,模型照着答 | 检索总会返回最接近的;本版没有反例问 | 作答规则与答前核对照常生效;§8.3 单独数;高了再排反例问或答后核对(T4) |
| R3 | 一条挂很多相似问,挤掉别的条目 | WeKnora 为此加了补搜 | 多取 + 按条目折叠;报告「折叠后不够数」的占比 |
| R4 | 条目表和索引行不一致(一个改了另一个没改) | §4.2 取舍三的代价 | 同一事务写;提供重建;契约测试;现有的文档 / 分段入口全部对 FAQ 拒绝(§5.8) |
| R5 | 混绑时 FAQ 和文档的重排分不在一个水平上,一类系统性压过另一类 | 打分文本形态不同;没量过 | 混绑题两条线(FAQ 题 @3、文档题不被挤掉);不做加权 |
| R6 | 重排模型对「问题 ↔ 问法」打分不可靠 | 模型按「问题 ↔ 段落」训练 | R1 / R2 两种文本都进对比 |
| R7 | 4a 的默认门槛误挡 FAQ 条目 | 默认值在文档上标定 | FAQ 库验过之前留空 = 不过滤 |
| R8 | 用户导入 FAQ 后没停用原来的问答表文档,同一答案返回两次 | 去重只认完全相同的文字 | 导入完成页提示;以后可按文件哈希点名 |
| R9 | 一个库 22 万索引行时召回变慢 | 上限是拍的 | 上线前在测试库造满一个库量一次(只量时延,不花模型钱) |
| R10 | 旧镜像把 FAQ 库当普通库,有人往里传文档或改分段 | §8.5 | 回滚说明写明;开关默认关,生产打开之前不存在 FAQ 库 |
| R11 | 导入任务在多副本下被重复执行或重复计费 | `knowledge_task` 从没被用过,没有现成的认领代码 | 沿用文档入库的认领 + 租约;每批幂等(按哈希复用向量、按查重键拒绝重复);真栈用例 F4-⑥ |
| R12 | 「替换全部」误删 | 会删文件里没有的条目 | 按差异做、要删除权限、确认框写明条数并要输入库名;删除放最后一步 |
| R13 | 正文不带「问 / 答」标记,模型分不清 | 未验证 | 智能体层评测能看出来;分不清再评估语言中立的标记 |
| R14 | 行级安全策略被当成隔离的保证 | 运行期连接不受它约束 | 每条 SQL 带租户条件 + 跨租户契约测试 + 真栈探针 |
