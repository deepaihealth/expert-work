## 0. 一页看懂

### 0.1 做什么

| 项 | 一句话 |
|---|---|
| 形态 | 新增一种知识库类型「FAQ 库」(`kind = faq`)。库里不放文档,放**条目**:一个标准问 + 一个答案 + 最多 10 个相似问法 + 启停开关 |
| 检索单位 | 一条 = 一个整体,不切段。每个问法单独进索引,命中任何一个问法都返回整条(标准问 + 答案) |
| 给模型看的 | 和文档段落同一种结果格式,标头是 `[D12#34]`:`D12` 是这个 FAQ 库的编号,`34` 是条目号(建了就不变)。4a 的出处编号直接用它 |
| 回答 | 仍然由模型作答,**不绕过模型直接吐答案**;作答规则、答前核对、出处核对一律不变 |
| 管理 | 控制台:列表 / 搜索、新建 / 编辑 / 删除、逐条与批量启停、命中测试能看到「命中了哪个问法」;按模板的 Excel / CSV 批量导入(先免费校验 → 报价 → 确认 → 后台执行 → 可下载失败行)、导出 |
| 费用 | 只有向量化花钱,记在租户名下。批量导入必须先估价再确认;改一条只重算改过的问法 |
| 开关 | 一个平台开关,**默认关**;关着时建不了 FAQ 库,现有库和智能体完全不受影响 |

### 0.3 这一版治不了的

- **「问得像、其实不是同一件事」**(近似问题):检索总会把最接近的条目拿回来,拦它靠模型读了之后判断「这条答的不是这个问题」。本版不做反例问(D5)。能做的是把这一类单独量出来(§8.3)。
- **FAQ 库是否比「把同一张问答表当文档上传」答得更准:现在没有证据。** 管理能力(逐条启停、相似问、稳定编号、不被切碎)是确定的收益;准确率的收益要靠 §8.3 的对照量出来,量不出来就如实报告。

## 2. 产品形态:新库类型,还是普通库里的一种条目

| | 甲:新库类型(本文选) | 乙:普通库里可以混放文档和 FAQ 条目 |
|---|---|---|
| 租户怎么理解 | 「这个库是问答库」;建库时选类型,之后不能改 | 一个库里既有文件又有问答条目 |
| 数据模型 | `kind` 列现成;新表挂在库上 | 库级设置(切段参数、「按新参数重新入库」)对条目没有意义,要逐项说明 |
| 界面 | 库详情页按类型换一组页签 | 文档页签里混一种特殊行;批量操作、估价横幅、过期文档提示都要区分两类 |
| 文档 + FAQ 一起搜 | 智能体绑两个库。多库融合是现成的(§1.3) | 同一个库内融合;门槛、检索方式问答和文档共用 |
| 对已有库的影响 | 没有 | 每个库都可能有条目,所有文档级路由都要按行判断 |
| 发布 / 回退 | 开关关着就建不出 FAQ 库,影响面 = 0 个库 | 开关只能挡入口 |
| 与早先设计 | B-175 设计按库分类型(`2026-10-10-b175-…:178`);总计划 E3 写「新库类型,不影响已有库」 | 要改已拍板文字 |
| 参考实现 | WeKnora:库类型 `faq`(`internal/types/knowledgebase.go:857-914`);MaxKB:问题表独立(`apps/knowledge/models/knowledge.py:272-294`) | RAGFlow:问答是一种**切段模板**,用在普通库上(`internal/ingestion/component/chunker/qa.go:17-28`);FastGPT:每条数据本身就是 q + a(`packages/service/core/dataset/data/schema.ts:39-57`) |
| 缺点 | 同时有文档和问答的租户要建两个库、智能体绑两个 | 见上 |

**选甲。** 理由:① 已拍板文字和现成的 `kind` 列都是这个方向;② 不影响任何已有库,开关关着时影响面是零;③ 库级设置对问答和文档含义不同。

**反对甲的证据**:RAGFlow、FastGPT 都没有单独的库类型,「混放」是行得通的。还有一条更便宜的路没被排除 —— **不加库类型,只把今天的表格切段改成「一行一段」**:它给不了逐条启停、相似问、稳定编号,但如果检索上的收益全部来自「一条一段」,那新库类型在检索上就没有额外贡献。§8.3 为此专门加了一个「一行一段」对照臂,把这两种收益分开量。

**对租户来说,和今天上传问答表的区别**:

| | 今天:问答表当文档上传 | FAQ 库 |
|---|---|---|
| 一个结果是什么 | 一大段,里面好几行问答 | 正好一条问答 |
| 用户换个说法问 | 靠向量碰运气 | 可以给一条挂多个相似问法,每个问法单独进索引 |
| 某一条过期了 | 改文件重传,或把整段关掉(连带同段其它行) | 关掉这一条,立即生效 |
| 改一条答案 | 改文件重传(整份重新估价、重新切段,段号重排) | 改这一条,只有变了的问法重新向量化,条目号不变 |
| 回答的出处指到哪 | 一大段 | 这一条 |

## 4. 数据模型与索引

### 4.1 条目

两张新表。`knowledge_faq_item`(条目):

| 列 | 类型 / 约束 | 说明 |
|---|---|---|
| `id` | UUID 主键 | 内部 id,不出现在任何给模型或对接方的文本里 |
| `tenant_id`、`kb_id` | UUID 非空 | 租户隔离(§4.6);`kb_id` 必须是 `kind = faq` 的库 |
| `item_seq` | 整数,`(kb_id, item_seq)` 唯一 | **条目号**:库内只增不减、删了不复用。出处编号 `D12#34` 里的 34 |
| `question` | 文本,1~256 字符 | 标准问 |
| `answer` | 文本,1~1,500 字符 | 一个答案(§4.2)。纯文本 / Markdown,不解析图片 |
| `enabled` | 布尔,默认真 | 逐条启停 |
| `revision` | 整数,从 1 起 | 只用于并发保护:编辑时带上读到的版本号,对不上回 409(同分段编辑,`cp/api/knowledge_passages.py:286-287`)。**不存历史版本**(§7.2) |
| `created_by`、`updated_by`、`created_at`、`updated_at` | | 操作人与时间 |

`knowledge_faq_question`(问法;**相似问只存在这里**,同时承担查重):

| 列 | 说明 |
|---|---|
| `tenant_id`、`kb_id`、`item_id`(删条目时级联删) | |
| `position` | 0 = 标准问;1~10 = 相似问,有顺序 |
| `text` | 问法原文,1~256 字符 |
| `question_key` | 规范化文本(§4.5)的 SHA-256;**主键 `(kb_id, question_key)`** —— 同一个库里问法不能重复,靠数据库约束保证 |

**上限**:

| 上限 | 值 | 来源 |
|---|---|---|
| 标准问、相似问各自长度 | 256 字符 | MaxKB 的问题列 |
| 每条相似问个数 | 10 | 起点值,没有实测依据 |
| 答案长度 | 1,500 字符 | 算出来的:一次结果预算 1 万字符、默认返回 5 条;每条 = 标头(库名最长 128)+ 标准问 256 + 答案 1,500 ≈ 1,900,5 条加分隔符 ≈ 9,550,放得下。再长的内容应该放文档库 |
| **一个库的全部行(每条的「整条」行 + 问法行 + 问答合并行)** | **不超过单文档段数上限**(现有设置,默认 40,000) | §1.2:一份文档的段会被整份读进内存;FAQ 库只有一份系统文档,所以整库受同一个上限约束。写入(单条和导入)时检查,超了回 409。折算:每条都挂满 10 个相似问时约 3,000 条;都不挂相似问时约 13,000 条 |

### 4.2 两个取舍

> **取舍一:一个答案,还是像 WeKnora 那样多个答案 + 策略?**
> - WeKnora 的多答案是给「随机挑一个回复」用的(`faq.go:251-258`),前提是答案原样发给用户。我们的答案一定经过模型改写。
> - 多答案 + 随机会让同一个问题两次检索拿到不同的文字:出处指纹对不上、评测不可重复。
> - 反对:从别的系统导出的数据可能一条有多个答案。→ 由租户自己并成一个。
> - 结论:v1 一个答案。有没有客户需要多答案**未调研**。

> **取舍二:条目另建表,还是全部塞进现有段表?**
>
> | | 另建两张表,段表只放派生的索引行(本文选) | 只用段表(大段行 = 条目,子段行 = 问法) |
> |---|---|---|
> | 列表 / 搜索 / 分页 | 普通查询 | 要把大段行和子段行拼起来;没有 `updated_at`、操作人 |
> | 问法不重复 | 主键约束 | 段表上建不了只针对 FAQ 的唯一约束 |
> | 与「分段」功能的界线 | 清楚:FAQ 的行不允许走分段编辑接口 | 模糊 |
> | 代价 | 多两张表;条目和索引行要在同一个事务里一起写 | 不加表 |
>
> 选左边。代价用一条规则兜住:**写条目和写它的索引行永远在同一个数据库事务里**,并有契约测试。v1 **不提供**「按条目表重建索引行」的函数(第 1 版有):换嵌入模型走现有的重建入口,它按段行重新嵌入、整库在 4 万行以内;以后要换索引方式时再写重建。

### 4.3 条目怎么落到现有的段表上

每个 FAQ 库有**一份系统文档**(建库时自动建,`source_type = faq`,文件名 = 库名,状态恒为 `ready`,没有原文件)。它的作用:给这个库一个文档编号 `D12`;让「文档级启停」「按文档读」这些现成机制对 FAQ 库成立;让段行有 `document_id` 可挂。

一条条目派生出三种行(都在这份系统文档下,章节路径都为空,都不带文档标题):

| 行 | 段类型 | 段号 | 正文 | 向量 / 关键词索引 | 作用 |
|---|---|---|---|---|---|
| 整条 | `parent` | `item_seq` | `标准问` + 空行 + `答案` | 无(约束要求) | **显示给模型的那一段**;读文档工具读的也是它 |
| 问法(标准问 1 行 + 每个相似问 1 行) | `faq_question` | `1,000,000,000 + item_seq × 16 + 位置` | 这个问法的原文 | 有 | 问法对问法的匹配 |
| 问答合并 | `faq` | `item_seq` | `标准问` + 换行 + `答案` | 有 | 让只出现在答案里的词(型号、数字、专名)也搜得到 |

- 问法行、问答合并行的 `parent_chunk_id` 都指向「整条」行,于是现有的「按 `parent_chunk_id` 折叠、返回大段」原样成立。
- **段号为什么要错开**:现有代码在大段行读不到时会退回子段自己、用子段的段号(§1.2)。如果问法行的段号和条目号落在同一个区间(第 1 版是 `item_seq × 32 + 位置`,第 1 条的第 2 个相似问 = 34 = 第 34 条的条目号),一次竞态或一次镜像回滚就会把出处指到别的条目上。现在问法行的段号从 10 亿起,永远不会和条目号相同(**约束:条目号不超过 7,000 万**,保证段号不溢出 32 位整数;计数器到顶就拒绝新建);问答合并行的段号就是条目号,退回它也指向正确的条目。另外 §5.4 规定:FAQ 类型的候选读不到「整条」行时,**这个结果直接丢弃**,不退回。
- 不带文档标题:文档标题会被拼进检索文本(`protocol/knowledge.py:301-317`),对 FAQ 是每一行都重复一遍库名。
- 正文不带「问:」「答:」之类的前缀:那是固定某种语言的说法。模型能不能稳定分清哪句是问、哪句是答,**未验证**(§9.3 U6)。
- 「问答合并」这一行要不要,由 §4.4 的对比决定;上表是默认候选(方式 B)。
- 启停:条目关掉 = 它的全部派生行 `enabled = false`,同一个事务。召回只取启用的行,所以关掉的条目**在结构上**搜不到。整库停用 = 停用系统文档(现成的文档启停,`cp/api/knowledge_maintenance.py:148-176`)。

### 4.4 索引什么:不拍,先比

| 方式 | 进索引的行 | 每条的向量数(n = 相似问个数) | 谁这么做 |
|---|---|---|---|
| A 只索引问法 | 每个问法一行 | 1 + n | Dify(旧副本);WeKnora 的「只问题 + 分开」 |
| **B 问法 + 一行问答合并(默认候选)** | 每个问法一行,另加一行「标准问 + 答案」 | 2 + n | 最接近 MaxKB(问题行 + 段落本身) |
| C 全部拼成一行(**只作参照,不参选**) | 「标准问 + 全部相似问 + 答案」一行 | 1 | WeKnora 默认 |

- C 不参选的原因:本设计的几样东西都要求「每个问法一行」—— 命中测试显示命中的是哪个问法、加一个相似问只重算那一个、§5.2 的按条目折叠。选了 C 这些都没有了。C 留在对比里只为回答「每问法一行到底有没有用」;如果 C 明显更好,结论是「回来重新设计」,不是自动选它。
- 支持 A / B:用户的问题是短句,和问法是「短句对短句」。反对 A:答案里才有的词搜不到。**我们自己没有任何数字。**

**离线对比(F0;只跑检索,不跑智能体;通过线现在定死)**:

- **库**:§8.2 合成集开发半的 100 条目 + **3,000 条合成干扰条目**。不加干扰的话,每路召回深度 50~100 再乘 3(§5.2),100 条的库几乎全进重排,三种方式分不出高下,比的只是重排文本。
- 同时比重排文本的两种取法(§5.3):R1 = 代表行自己的文本;R2 = 整条。A、B 各两种 = **4 组**;C 只跑一组作参照。
- **干扰条目要真的起干扰作用**:开发半换说法 100 题里,前 3 个结果中出现过干扰条目的题不到 30 道 → 判干扰无效(模板生成的东西字面上一眼可分),重做干扰条目后再比。这条在看各组命中率之前先查。
- F0 的脚本**自己建索引行**(产品代码这时还没有)。所以这次对比只用来选型;**验收不用它**(§8.4)。
- 每组在开发半的题上量(换说法 100、原样 30、答案关键词 30、近似 30,共 190 题),命中率按**排版后模型实际看到的结果**算(§5.4):
  1. 换说法题条目命中 @1、@3;2. 答案关键词题 @3;3. 原样题 @1;4. 近似题最高分与换说法题正确条目分数的重叠(只报告)。
- **合格** ⇔ 换说法 @1 ≥ 85 题、@3 ≥ 95 题(共 100);答案关键词 @3 ≥ 27 题(共 30);原样 @1 = 30 题(共 30)。
- **选哪组**:A、B 里合格的,选向量少的(A);同一方式下 R1、R2 都合格选 R1(不用多读一次库)。
- **A、B 都不合格**:不上线,把各组的数报给用户,另议。
- 这些数是我事先定的起点,不来自数据;要改请在跑之前改(§9.2 第 5 条)。

### 4.5 唯一与重复

- **规则**:同一个库里,任何两个问法(标准问或相似问、不论属于哪一条、**不论启用与否**)规范化后不能相同。
- **规范化**:NFKC、`casefold`、空白折叠成一个空格、去掉首尾的空白与标点(按 Unicode 类别判断是不是标点,不维护某种语言的标点表)。只做字面归一。
- **停用的条目仍然占着它的问法**:想把一个问法挪给另一条,要先从原来那条删掉它(或删掉原来那条),光停用不行。界面在 409 里指出撞的是哪一条、它是否停用。
- **同一条内部**重复的相似问:保存时去掉,不报错。
- **不做**语义近似的重复检测。

### 4.6 迁移、租户隔离

**迁移**(一个;编号以合并时为准,当前最新 0186):

| 对象 | 内容 | 性质 |
|---|---|---|
| `knowledge_faq_item`、`knowledge_faq_question` | §4.1 | 新表 |
| `knowledge_base.faq_last_seq` | 可空大整数,条目号计数器:写入事务里 `UPDATE … SET faq_last_seq = COALESCE(faq_last_seq, 0) + n … RETURNING`,库行的行锁把并发串起来(同文档编号计数器的思路) | 加列 |
| `knowledge_task` 加 `lease_until`、`attempts`、`confirm_by`、`confirmed_at` | 导入任务的认领、重试、待确认期限(§6.3) | 加列 |
| `knowledge_task` 部分唯一索引:`(kb_id)`,条件 `task_type = 'faq_import' AND status IN ('queued', 'running')` | 一个库同时只有一个进行中的导入 | 加索引 |
| `knowledge_task` 部分索引:`(confirm_by)`,条件 `status = 'queued' AND confirmed_at IS NULL` | 过期撤回的扫描 | 加索引 |

- **不新增状态值、不改任何已有约束**。「待确认」用现有的 `queued` + `confirmed_at` 为空表示(§6.3)。
- 两张新表都带 `tenant_id`,都按 `0165` 的写法开行级安全策略。**但运行期的连接今天不受行级安全约束**(项目既有结论:应用以超级用户连接,RLS 项目在第 0 阶段后搁置)。隔离的真正保证是:每条 SQL 都带 `tenant_id` 条件 + SQL 与内存两套存储实现共用一组参数化契约测试,其中必须有「用租户甲的身份读 / 改 / 删租户乙的条目 → 一律当作不存在」的用例。
- 回滚:换回旧镜像即可,新表新列旧代码不读。旧镜像下的 FAQ 库见 §8.5。

### 5.2 召回与融合

- **问题**:一条有 10 个相似问时,它可能占掉某一路的前 10 个名额,重排的 100 个名额也被同一条的不同问法占掉。
- **做法**:
  1. FAQ 库的每一路向存储要 `深度 × 3` 行(上限 300)。
  2. 把 **FAQ 类型的行**(`faq_question`、`faq`)按所属的「整条」折叠:同一条只留这一路里排名最高的那一行,截到 `深度` 条。
  3. 两路用**同一个代表行**参与融合,这样一条在两路都命中时拿到 RRF 的两票。**代表行的取法写死**:这一条在向量路里出现过 → 取它在向量路里排名最高的那一行;只在关键词路出现 → 取它在关键词路里排名最高的那一行。每一路实际命中的是哪一行另外记下来(给命中测试和检索记录)。
- **分支条件是「行的类型」**:折叠只作用于 FAQ 类型的行(`faq_question`、`faq`);「多取 3 倍」只作用于 `kind = faq` 的库。
- 「3 倍」是起点,**未验证**:§4.4 顺带报「折叠后不足 `深度` 条、而库里还有更多条目的查询占多少」;高于 5% 就调大重跑。
- 文档库的召回路径一行不动。

> **取舍:问法行要不要和 4c(E1)共用它的问题表?** 4c 设计(`7b409a691` §3.1.2~§3.1.3)给「每段生成的问题」另建了 `knowledge_chunk_question` 表,明确不往段表写,并把「E3 要不要共用」留给本文定(它的 U8)。
>
> | | 不共用:FAQ 问法行写在段表里(本文选) | 共用 4c 的问题表 |
> |---|---|---|
> | 关键词检索 | 有(段表的行自带关键词索引);问法里的型号、专名要靠它 | 4c 的表只有向量,没有关键词索引,要给它加 |
> | 停用 | 召回条件里现成的「行启用」,结构上搜不到 | 4c 是召回后再过滤,要另验 |
> | 4c 另建表的理由对 FAQ 成不成立 | 不成立:它怕的是问题行混在**文档的段**里,被分段列表、段数、关键词总段数、重建当成段落。FAQ 的行关在一份独立的系统文档里,这些读者已逐个处理(§5.8),重建把它们当段落正是想要的 | — |

### 5.3 重排

- 重排模型是按「问题 ↔ 段落」训练的。拿用户的问题对一个问法打分(R1)是「问题 ↔ 问题」,准不准**没有证据**;对「标准问 + 答案」打分(R2)更接近训练方式,但重排前要先把候选的「整条」行读出来(一次批量读,最多 100 行,后面出结果时复用,同去重已有的做法 `tools/knowledge.py:668-675`)。两种都进 §4.4 的对比。
- FAQ 候选没有文档标题,「带标题」和「只看正文」两个视图是同一段文字,加权后的分 = 单次的分,和文档候选在同一个刻度上。混合候选时 FAQ 的那几个会被原样多打一次分;多出的重排调用量和记账**未验证**(§9.3 U7)。
- **不给 FAQ 加权**(WeKnora 乘 1.2)。理由:① 乘过的分不在重排模型的刻度上,门槛对它没有意义;② 「FAQ 一定比文档更该信」是假设不是事实;③ 没量过混排时 FAQ 是不是吃亏。先量(§8.3 混绑题)。

### 5.4 结果长什么样、编号是什么

给模型看的一条(围栏内,租户文字):

```text
[D12#34] 示例售后问答库
怎么申请退货?

登录后进入「我的订单」,在订单详情里选择「申请退货」并填写原因;审核通过后按页面提示寄回。
```

- 标头:`D12` = 这个 FAQ 库的系统文档编号;`34` = **条目号**;后面是库名(系统文档的文件名)。
- 不显示命中的是哪个相似问;那只进工具元数据。

**一个编号 = 整条**(与 4a 设计 §3.1.2 同一口径):

| | 文档段落(4a) | FAQ 条目 |
|---|---|---|
| 显示的是什么 | 一个大段 | 整条 |
| 标头里的号 | 排名最高的子段的号 | 条目号 |
| 这一段登记哪些号 | 同一大段里上榜的子段号 | 只有条目号 |
| 号稳不稳定 | 重新入库会重排(靠指纹) | 建了就不变、删了不复用(仍算指纹,识别「答案改过」) |

- 只有**两处**把子段号换成条目号:检索结果成形处(`tools/knowledge.py:1261-1296` 的 `_retrieved`:候选是 FAQ 类型的行时,结果的段号和「上榜的子段号」都取「整条」行的段号;**「整条」行读不到 → 不出这个结果**)和读文档的视图(`tools/knowledge_read.py:430-438` 的 `_view`:子段是 FAQ 类型时,这一段的号 = 整条行的段号)。下游的标头、`meta["refs"]`、旧结果压成的引用行、读文档的标头、4a 的出处登记,读的都是这两个字段。
- **放不下时**:现有逻辑是退回「只显示命中的子段」(`tools/knowledge_results.py:108-118`)。FAQ 的子段是问法,只显示问法 = 不给答案。所以 FAQ 结果不提供这个备选:后面的放不下就到此为止。按 §4.1 的上限,默认 5 条一定放得下;模型自己要 20 条时会被预算截到放得下的那几条。
- **命中率怎么算**:评测里的 @k 一律按排版之后模型实际看到的条目算,不按检索器返回的列表算。
- 「各路实际命中的是哪一行」(`matched`:标准问、第几个相似问、还是合并行)**只在命中测试接口的返回里**,不进工具元数据 —— 工具元数据会出现在对外的 `updates` 帧里,没必要让对接方看到它。检索记录本来就存命中行的 id,详情页据此显示。
- 命中测试接口把命中问法的原文带给界面:它本来就返回命中子段的正文(`cp/api/knowledge.py:1467`),界面也已经在显示(`admin-ui/pages/knowledge_detail/RetrievalTestTab.tsx:105-106`)。

**与 4a 出处对象的对接**(F3b,等 4a):

```json
{"ref": "D12#34", "doc_seq": 12, "chunk_indexes": [34],
 "fingerprint": "5b1e0c9d2a7f4e31",
 "kind": "faq", "question": "怎么申请退货?"}
```

- **不带 `title` / `filename`**(对 FAQ 它们就是库名,4a 规定不带库名),没有 `heading_path`。多两个可选键:`kind`、`question`(标准问,给界面悬停用)。不带任何内部 id。
- `fingerprint` 算法和 4a 完全一样(这一段正文的 SHA-256 前 16 位):标准问或答案改了,指纹就变;相似问的增删不改指纹。
- 没有知识库读权限的人(4a A3:只见标题和位置):对 FAQ 出处显示 `question`;这是 4a 侧要补的一句,记在 F3b。对外检索(4b 的 R1)搜到 FAQ 库时,出处对象就是上面这个形状,原样带出(4b 设计 §4.6 已对齐)。
- 原文抽屉(4a 的 A3):对 FAQ 库,段号按条目号去找「整条」行。条目已删 → 显示快照 +「原文已变更」;答案改过 → 指纹对不上 → 同样;停用但没删 → 照常显示并标「已停用」。
- 4a 没上线时:FAQ 结果照常返回、模型照常作答,只是没有出处对象。

### 5.5 高分命中要不要变行为:不变

**不绕过模型。** 理由:

1. 我们的产品是智能体:回答要过角色设定、输出筛查、输出判官、脱敏(4a 设计 §3.1.1),可能配了输出格式,用户的一条消息可能问了两件事。直接吐 FAQ 答案会绕过这些。
2. 「高分」没有稳定的含义:目录里四个重排模型没有一个声明了跨请求可比的 0~1 分数(4a 设计 §3.3.1)。
3. 检索的查询串是**模型写的**(`tools/knowledge.py:181-186`),不是用户原话。
4. WeKnora 也没有绕过(§3)。MaxKB 的直接返回若要做,属于开放 API(R1)。

**也不给模型看「精确匹配」标记、不把 FAQ 结果排到文档前面。** 标记会被读成「可以照抄」;排前面等于加权。

**作答规则原样适用**:工具说明里的作答规则、结果后面的提示、答前核对(`tools/knowledge.py:174-180,207-214`)说的是「段落有没有明确写出被问的事实」,对 FAQ 条目同样成立。**这些文字一个字不改。**

### 5.6 相关度门槛(4a 的 T3)

- FAQ 库有自己的重排分下限,自定义值、填 0 的含义与 4a 相同;全不过线时「降一次」和单独的「没找到」结果照常(标题清单里对 FAQ 库就是 `D12 库名` 一行)。
- **v1 里 FAQ 库留空 = 不过滤**,不跟随 4a 的平台默认。第 1 版设计了「在 FAQ 题上验过零误挡才跟随」:那需要存一个验证结论、把它绑定到重排模型、换模型时让它失效,还要一批专门的题 —— 为一个还没证明有用的默认值造一套机制。砍掉。代价:明显离题的问题在 FAQ 库上不会被默认门槛挡住(和今天所有库的行为一样);租户可以自己填下限。等 4a 的默认值上线、FAQ 有了真实数据再评估。

**审计**:`knowledge:faq_item_create / _edit / _toggle / _delete / _batch`、`knowledge:faq_import / _import_confirm / _import_cancel`、`knowledge:faq_export`。资源类型加 `knowledge_faq_item`(现有只有库和文档两种,`cp/api/knowledge.py:195-212`)。详情只放库名、条目号、数量、任务 id,**不放问题和答案的文字**。

**错误**:409 `revision_conflict`、409 `duplicate_question`(带撞上的条目号、是否停用)、422 各种超长、409 `base_full`(整库行数到上限)、409 `import_in_progress`、503(没配嵌入模型)。

**手工新建 / 编辑的费用(§0.2 第 4 条的偏离)**:直接嵌入变了的文本、记租户账,不弹估价确认。保存按钮旁写明「保存会对新增或改动的问法做向量化,按用量计费」。

一次保存的量在结构上有界:最多嵌入 11 个问法(各 ≤ 256 字符)+ 1 行问答合并(≤ 约 1,760 字符)。

**只重算改过的问法**:保存时按新内容生成全部索引行的检索文本,算内容哈希;哈希在这份系统文档里已有、且是当前嵌入模型做的 → 复用向量(现成机制)。只改答案 → 只重算「问答合并」那一行;加一个相似问 → 只算那一个;只改启停 → 一个都不算。靠哈希复用在结构上成立;单测用一个会计数的假嵌入器钉住每种编辑各调了几次。

**导入执行期间,手工写入被拒**(409 `import_in_progress`):单条写入和导入的每一批都先锁库行,单条写入在锁内检查「这个库有没有**已确认、还没结束**的导入任务」(`status = 'running'` 且 `confirmed_at` 不为空;租约过期、等着被接手的也算)。校验中和待确认的任务不挡手工写入。整库行数上限也在拿到库行锁之后、同一个事务里数。这样导入校验时看到的库状态在执行时不会被别人改掉。

### 6.2 界面(`admin-ui/pages/knowledge_detail/`)

- **建库**:向导里多一步选类型(文档 / FAQ),注明「建后不可改」。开关关着时不显示。
- **FAQ 库的详情页**:页签是「条目 / 命中测试 / 检索记录 / 设置」(文档库的是「文档 / …」,`admin-ui/pages/KnowledgeDetail.tsx:222-226`)。
- **条目页签**:表格列 = 条目号、标准问、相似问个数、启用开关、更新时间、更新人;搜索框 + 启用筛选;多选后「启用 / 停用 / 删除」;「新建」「导入」「导出」;「下载模板」是界面里的一个静态文件,不是接口。
- **编辑抽屉**:标准问、答案(显示字数和上限)、相似问(一行一个,可增删)、启用。保存冲突时显示对方改成了什么。
- **命中测试**:结果卡片另加一行「命中的问法:第 2 个相似问『……』」/「标准问」/「答案内容」。这是调相似问的主要工具。
- **设置**:FAQ 库不显示切段参数、「按新参数重新入库」;重排下限的占位文字写「留空 = 不过滤」。
- **文案**:中英两套,新键放在自己的键组里(`knowledge_faq.*`)。

### 6.3 批量导入

**文件**:`.xlsx`(第一个工作表)或 `.csv`(UTF-8,带不带 BOM 都行;读不出来就报错并提示另存为 UTF-8);最大 5 MiB、最多 5,000 行。**按单元格原值读**(openpyxl 直接取值),不走现有的「表格转 Markdown」解析 —— 那条路会把单元格里的换行折成空格、转义 `|`(`cp/knowledge/office_xlsx.py:24,137-138`),相似问就拆不开了。

**列**:表头必须是模板的固定英文键,**v1 没有列映射界面**(§7.2):

| 列 | 必填 | 说明 |
|---|---|---|
| `question` | 是 | 标准问 |
| `answer` | 是 | 答案 |
| `similar_questions` | 否 | 一个单元格里用换行分隔多个 |
| `enabled` | 否 | `TRUE` / `FALSE` / `1` / `0`;省略 = 启用 |
| `item_no` | 否 | 条目号。导出的文件带这一列 |
| `base` | 否 | 库名。导出的文件带这一列。**有这一列且不等于当前库名 → 整个文件的 `item_no` 一律不认**(改按标准问对),报告里说明。防的是把甲库导出的文件覆盖导进乙库、按号改掉不相干的条目 |

多余的列忽略,并在报告里列出被忽略的列名。

**只有追加一种模式**(「替换全部」v1 不做,§7.2)。已存在的条目怎么办,二选一:**跳过**(默认)/ **用文件里的覆盖**(答案、相似问以文件为准;条目号不变)。

**怎么判断「已存在」**:这一行有 `item_no` → 按条目号找(找不到这个号 = 这一行失败,不新建);没有 `item_no` → 按规范化后的标准问找。所以「导出 → 把某条的标准问改个说法 → 覆盖导入」改的是原来那一条,条目号不变、旧出处仍然指得到它(指纹会提示内容变了)。

**流程**(状态记在 `knowledge_task` 一行里,`task_type = faq_import`;不新增状态值):

| 阶段 | 任务行 | 做什么 | 花钱吗 |
|---|---|---|---|
| ① 校验 | `running`,`confirmed_at` 为空,**带租约** | 解析文件;逐行检查;对照库里**当前**的条目,算出每行的去向(新增 / 覆盖 / 跳过 / 失败)和要新嵌入的文本及 token | 不花 |
| ② 待确认 | `queued`,`confirmed_at` 为空,无租约,`confirm_by` = 7 天后(B-222 §14 的期限) | 给出校验报告 + 估价(只有向量化一项) | 不花 |
| ③ 执行 | 确认时写入 `confirmed_at`;后台认领 → `running`,带租约 | 每批 200 行:嵌入这一批的新文本 → 一个事务写这一批,**每一行一个保存点** | 花 |
| ④ 结束 | `succeeded` / `failed` / `cancelled` | 结果统计 + 实际花费 | — |

- **一个库同时只有一个进行中的导入**:部分唯一索引(§4.6)保证。**待确认的任务不会占住库 7 天**:对同一个库再上传一个文件时,如果现有任务还在待确认,就在同一个事务里把它撤回、换成新的(和文档「重传顶掉待确认的旧版本」同一个思路);只有正在校验或执行的任务会让新上传得到 409。
- **过期撤回**:控制面现有的兜底巡检每一轮多做一件事 —— 把 `confirm_by` 已过、还没确认的导入任务置为 `cancelled`(走 §4.6 那个部分索引)。
- **认领、租约、接手**(照文档入库的做法写,`cp/knowledge/recovery.py:89-100,164-175`;那套代码只认文档表,**导入要自己实现一份**,在 F4 的范围里):
  - 校验和执行都拿租约、定期续租。认领 = 把「已确认的 `queued`」或「租约过期的 `running`」改成 `running` 并 `attempts + 1`。
  - **接手时看 `confirmed_at`**:为空 → 这是校验做到一半,**从头重做校验**(免费),绝不进入执行;不为空 → 从 `stats` 记的「已处理到第几行」继续执行。没确认过的任务在任何路径上都不会开始花钱。
  - 校验中副本挂了:租约到期后被兜底巡检接手重做;在那之前这个库的新上传得到 409(最长一个租约期),不会永久卡住。
  - `attempts` 超过上限:由兜底巡检在每轮开头置 `failed`(文档那边也是巡检扫,`recovery.py:164-166`)。
  - **取消执行中的任务**:接口在任务行上记「要求取消」;活着的工作者在下一批之前看到,置 `cancelled`。工作者已经死了:巡检接手时先看这个标记,有就直接置 `cancelled`,不再执行。
- **校验对照的是库的当前状态**;执行期间手工写入被拒(§6.1),所以校验时算出的去向在执行时仍然成立。待确认期间库可能被人改:确认后、开始执行前**重新校验一遍**,去向或要嵌入的文本变了就退回待确认并更新报告(同 B-222)。
- **一行失败不连累一批**:每行一个保存点;某一行撞了问法唯一约束(理论上重新校验后不该发生)→ 只回滚这一行,记进失败行。
- **重复计费的上界**:嵌入发生在事务之前。副本在「嵌入完、事务没提交」时挂掉,接手的副本会把这一批重新嵌入一次 —— **最多一批(200 行)的嵌入费付两次**;已经提交的批次按内容哈希复用,不会再付。不会重复写条目。
- 中途失败或取消:已写入的批次保留,报告里写清处理到第几行。重新导入同一个文件是幂等的。
- 金额为 ¥0.00 也要点确认(B-222)。
- 上传的文件在任务结束或撤回后删除;存放位置在 F4 开工时定,**未验证**(§9.3 U11)。

**逐行检查**(都是免费的):

| 检查 | 结果 |
|---|---|
| 标准问或答案为空;任何一项超长;相似问超过 10 个 | 失败,写明哪一项 |
| 同一个文件里两行的任何问法规范化后相同 | 后出现的那一行失败,指出与第几行重复 |
| 问法与库里**别的**条目的问法重复(覆盖模式下,被覆盖的那一条自己不算) | 这一行失败,指出条目号。想在一次导入里把一个相似问从甲条挪到乙条是做不到的:先导一次把它从甲条去掉,再导一次加到乙条 |
| 同一行内相似问重复、或与本行标准问相同 | 自动去掉,报告里计数 |
| `item_no` 在库里不存在;同一个 `item_no` 在文件里出现两次 | 失败 |
| 导入后整库行数会超上限 | 整个任务校验不过 |
| 表头缺 `question` 或 `answer`;行数或文件大小超限 | 上传时直接拒绝 |

**校验报告**:各种去向的行数;前 100 条失败行;「下载全部失败行」(用户自己的数据加一列原因,改完可以直接再导入)。

## 7. 不做的,和砍掉的

### 7.1 这一版不做(第 1 版起就不做)

| 不做 | 为什么 / 以后怎么办 |
|---|---|
| 反例问法 | D5 已定后放。参考实现里它只在查询与反例字面完全相同时生效 |
| 多个答案、答案策略、「推荐」标记 | §4.2 |
| 高分直接返回答案 / FAQ 加权 / FAQ 排在文档前 / 「精确匹配」标记 | §5.3、§5.5 |
| 模型自动生成相似问 | 它要调对话模型,是按条目数增长的费用,必须走估价确认;4c 的「给每段生成问题」要做的正是「生成 + 估价」这一套。**建议等它做完再排**,做成付费可选、逐条人工确认采纳 |
| FAQ 管理的开放 API | 归 R1 的二期;v1 全部 `console_only` |
| 「没答上来的问题」分析、条目命中次数 | 检索记录页已能筛出「没搜到」的查询 |
| 把普通库里已有的问答表自动转成 FAQ | 见下 |
| 语义近似的重复检测、答案里的图片(归 E2)、多标签、条目有效期、审核流、改库类型 | 没有需求来源 |

**已经传进普通库的问答表怎么变成 FAQ 条目**:不做转换工具。指引:把原表的问题列、答案列复制进模板,在 FAQ 库导入;完成后到原来的文档库把那份文档停用或删除。不做工具的理由:① 从已入库的段落反推问答对不可靠(表格被切成了「几行一段、长行被切开」),要转只能回去读原文件,而原文件不一定还留着;② 自动转换要替用户判断哪列是问题。风险:用户导入后忘了停用旧文档,同一条答案会从两处各返回一次(去重只认完全相同的文字,去不掉)—— 导入完成页固定提示一句。

### 7.2 审查后砍掉的,和砍掉的代价

D5 定的范围是「问题 + 答案 + 相似问法 + 批量导入 + 逐条启停」。第 1 版在这之外加了不少,审查后按「能砍就砍」处理:

| 砍掉的 | 省掉什么 | 代价 | 以后加回来的难度 |
|---|---|---|---|
| **修订历史与写回** | 一张表、两个接口、一个页签 | 改错了看不到原来写的是什么、不能一键改回;只有审计记录知道谁在什么时候改了哪一条。缓解:大改之前先导出一份 | 低:加表即可,不影响现有数据(只是没有加之前的历史) |
| **「替换全部」导入模式** | 删除顺序、查重键先放后占、要删除权限的确认流程;以及审查指出的「改标准问会被当成删一条加一条」的坑 | 想让库「变成和文件一模一样」做不到:文件里没有的旧条目要在界面上筛出来分批删(一次 200 条),或删库重建(条目号全部重来) | 中:按条目号对比的规则已经有了,主要是删除那一半 |
| **分类** | 一列、一个筛选、读文档的章节分支、画像按分类取样 | 列表只能靠关键字搜;原表里的「分类」列导不进来(要保留只能写进答案或标准问);模型看到的结果里没有分类这一层 | 低:加一列,并把它填进「整条」行的章节路径。**五样里它最可能被要回来** —— 现有切段代码的注释都提到问答表常有分类列(`cp/knowledge/chunking.py:1540`) |
| **列映射界面** | 导入向导的一步、服务端的映射参数 | 客户自己的问答表不能直接传,要先把列复制进模板(改表头也行) | 低 |
| **模板下载接口** | 一个接口 | 无(模板是界面里的静态文件) | — |
| **FAQ 库的画像与校准** | 画像摘要的 FAQ 分支、导入估价里的画像一项、手工建的库怎么触发的问题 | 库目录里 FAQ 库没有自动生成的概述,只有管理员写的名称和描述;每轮探测对 FAQ 库只走关键词那一路。多库智能体选库时对 FAQ 库的了解少一些 | 中 |
| **「验过才跟随平台默认门槛」** | 一个验证结论的存储、与重排模型的绑定和失效、一批专门的题 | FAQ 库默认不挡明显离题的问题(和今天所有库一样) | 低:等 4a 的默认值上线后再看 |
| **「按条目表重建索引」函数** | 一个函数和它的契约测试 | 以后换索引方式(比如从 B 换成 A)时要现写;条目表和索引行万一不一致,没有现成的修复命令 | 低 |
| **更大的库**(第 1 版 10,000 条 × 20 个相似问) | 给读文档、重建、按词找各做一套分页 | 一个 FAQ 库约 3,000~13,000 条封顶;每条最多 10 个相似问;答案最多 1,500 字符 | 高:三条路径都要改 |

**保留、但超出 D5 字面的**:批量启停 / 批量删除(几千条的库里没有批量,「逐条启停」不可用;砍了「替换全部」之后它也是清理旧条目的唯一办法);导出(没有修订历史之后唯一的备份手段,也是「导出 → 改 → 覆盖导入」的前一半);入库前估价 + 确认(B-222 的既定规则);命中测试显示命中的问法(调相似问全靠它,接口本来就返回这个字段)。

### 8.3 指标、通过线、必须变红的对照

**检索层**(留出半;命中率按排版后模型实际看到的结果算;线一律写成题数):

| 指标 | 定义 | 通过线 |
|---|---|---|
| 换说法 @1 / @3 | 正确条目排第 1 / 前 3 的题数(共 100) | ≥ 85 / ≥ 95 |
| 原样 @1 | 共 30 | **30**(硬线:登记过的问法搜不到自己那一条就是缺陷) |
| 答案关键词 @3 | 共 30 | ≥ 27 |
| **停用的条目被返回** | 「停用」臂里,20 条停用条目出现在任何一次检索结果里的次数 | **0**(硬线) |
| 混绑:答案只在 FAQ 的 10 题 | 正确条目进前 3 | 最多 1 题没进 |
| 混绑:答案只在文档的 10 题 | 正确文档进前 5 的题数,与「只绑文档库」相比 | 最多少 1 题 |
| 与两个对照臂比(只报告,不设线) | 「正确条目的答案原文出现在模型看到的结果里」的题数,在**相同字符预算**下比:前 2,000 字符内、整个 1 万字符内各数一次 | 只报告。不能直接比 @3:基线的一个结果是一大段、里面十几行问答,「前 3 个结果」覆盖三十来条,和 FAQ 的「前 3 条」不是一个单位 |
| 近似题分数重叠、折叠后不够数的查询占比 | — | 只报告;后者高于 5% 就调倍数重跑 |

**智能体层**(真模型答题,沿用 `tools/eval/kb_agent_*` 的答题与 3 票判分;每题跑两次;换说法题取留出半里的 50 道):

| 指标 | 定义 | 通过线 |
|---|---|---|
| 换说法题答对 | 50 题 × 2 = 100 题次 | ≥ 90 题次 |
| 换说法题误拒 | 说「资料没写」 | ≤ 2 题次 |
| 近似题采纳了错的条目 | 30 题 × 2 = 60 题次;把最像的那一条的答案当成这个问题的答案给了用户 | 不设绝对线(没有基线),只看下一行的配对比较;题次如实报 |
| **相对表格上传基线(硬线,按题配对)** | 基线臂跑同样的换说法 50 题 + 近似 30 题,各两次。**「FAQ 更差的题」** = 基线两次都对、FAQ 两次都不对(近似题:基线两次都没被带偏、FAQ 两次都被带偏) | 换说法:这样的题 ≤ 2 道(共 50);近似:≤ 2 道(共 30)。单次的翻转不计。反方向(FAQ 更好的题)和两臂的题次总数如实报 |
| 混绑冲突题 | 5 题:是否把冲突说出来了 | 只报告 |
| 出处(4a 开着时) | 带出处、引对了 | 沿用 4a 的线 |

> 为什么按题配对、不比题次总数:同题两次结果约一半会变(总计划 §2.3),两臂各 100 题次时题次之差的噪声就有四题上下,「不少超过 2」在两臂水平相同时也有相当的概率判不过。「两次都对 → 两次都不对」才是稳定的退步;4b 的护栏用的是同一个定义(4b 设计第 710 行)。
>
> 近似题为什么也要跑基线臂:这是 FAQ **可能更差**的地方。基线的一大段里,相邻的两种情形是并排显示的,模型看得到「还有另一种情形」;FAQ 只给最像的那一条。如果 FAQ 臂在这里明显更差,要如实报告,并作为排反例问 / 答后核对的依据。

**必须变红的对照**(证明指标咬得住;不红则这个指标的结果作废、先修指标):

| 对照 | 做法 | 必须看到 |
|---|---|---|
| 关掉启停过滤 | 评测里用一个不看 `enabled` 的召回 | 「停用的条目被返回」> 0,且 20 条里至少 10 条出现过 |
| 停用正确条目 | 把每道换说法题的正确条目停用(走产品的停用写入) | 这些题的 @3 降到 5 题以下(共 100) |
| 打乱标准答案 | 把每题的「正确条目」换成随机另一条 | 换说法 @1 降到 5 题以下 |
| 植入错条目答案 | 取近似题,把「最像那一条的答案」原样当作回答交给判分 | 「采纳了错的条目」30 题全部判出 |
| 假编号(4a) | 沿用 4a 设计 §5.3 | 同 4a |

**一个不算对照、只是如实报告的项**:拿掉相似问的索引行(只留标准问),看留出半里「题目 = 某个相似问」的 15 道原样题 @1 掉多少。掉了,说明相似问索引在起作用;**没掉,就照实写「在这批题上相似问索引没有可见作用」**(可能是相似问和标准问太像,也可能是向量本来就够)。不因此改数据重跑 —— 改到它有用为止,就是在调数据凑结论。

通过线里的数**没有基线可依**,是起点值;可以改,但要在看留出半的结果之前定下来(§9.2 第 6 条)。

### 9.1 风险

| # | 风险 | 依据 | 应对 |

| R1 | FAQ 库答得并不比「问答表当文档上传」准 | 没有任何数字 | §8.3 的回答层硬线 + 「一行一段」对照臂;管理能力的收益不依赖它 |
