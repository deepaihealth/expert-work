## 0. 一页看懂

**问题**:主模型自己能看图(`supports_vision: true`,下称 Path A)时,图片原样进主模型。今天实测 qwen4-max 直接看:**横着 / 倒着的仪表照片 54 次读对 33 次,错的 21 次全是笃定的错**(血压 95 每次都读成 99);同一批图经看图工具(Path B:`ask_image` 先按 B-301 问方向,看图模型也是 qwen4-max)36/36 全对。Path A 没有「先转正」,也没有「放大局部 / 逐条读 / 如实说没看到」。

**做两件事,两个 PR**:

| PR | 做什么 |
|---|---|
| ① 先转正 | 用户这一轮发来的图,进主模型之前先用**主模型自己**按 B-301 的问法问「主要文字是正的吗」;明确横 / 倒的,**只在发给模型的那一份里**换成转正的图,并告诉模型「已顺时针转 N 度」。用户的原图、聊天记录、对话历史都不动;转正的图只在内存里临时生成,不落盘 |
| ② 看近一点 | 新工具 `zoom_image`:模型给一个框 → 从原像素裁出来,下一步附给它自己看;`region='auto'` → 平台按 B-266 切横条、每条单独读、如实报没看到 / 被切开 / 不确定、接缝自动重看。也让 Path A 第一次能看工作区里的图片文件 |

**用户会感觉到的变化**(按今天的数;各模型价钱见 §4.1.10):

| 项 | 变化 |
|---|---|
| 等待 | **带图的那一轮,第一句回复前多等**:正放的图约 +2~5 秒;横着的图约 +5~15 秒;一轮最多 8 张图并行,最坏封顶 30 秒(到点没判完的图这一轮按原样发,下一轮开头再判一次)。之后的步骤与轮次**不再调模型**;横着的图每次发送前要用到转正图,平时在内存里现成,换了副本、或被挤出缓存时要在发送前重算一次(每张约 0.3~1 秒,未实测;§4.1.5) |
| 费用 | 每张新图多 1 次主模型调用(横的多 4 次)。按「思考关不掉的模型输出按 1,000 token 的上限算」这一个口径:qwen4-max 约 ¥0.016 / 次;Claude Opus 5.5 约 ¥0.19、Fable 5.2 约 ¥0.38 / 次;glm / deepseek 约 ¥0.003~0.01。只在图第一次出现那一轮花(没判完的下一轮再花一次),历史图不重复花。各模型见 §4.1.10 |
| 隐私 / 数据去向 | 图只发给智能体本来就在用的主模型那一家,不新增厂商。PR ① 不写任何新文件。PR ② 裁出来的局部图与今天 `ask_image` 一样写在本对话的临时目录里(沙箱读得到,闲置满保留期才清;用户删了原图,裁图不会立刻跟着删)—— 见 §7 与 §8 第 13 条 |
| 打开范围 | 只对**核实过的主模型**打开:模型目录里一个标记 `orientation_verified`,有 §6.2 E 组的体检证据才在代码里设上;没设的模型(包括新加的)照今天的样子,不转。不用各环境另配名单。运维开关只是紧急关停 |

**不修的**:与方向无关的读错(淡笔段、模糊)、没有文字但有上下的图(表盘、人像)、豆包读错、上线前就在历史里的图(只管之后新来的图,§8 第 10 条)。Path B 的三件事另立 B-323 / B-324 / B-325。

**上线**:先测试环境;上生产排在 B-301 上生产之后(B-301 还没上生产,随 B-300 同一班,§7)。

**两个看图事实,决定了本设计的取舍**:

1. **qwen4-max 不缩图**:约每 1,024 像素 1 个 token,单图封顶约 12.3k token。所以它直接看密集化验单也 60/60 —— 对它来说「放大」的价值主要是转正与聚焦。
2. **别家会缩图**:B-266 实测豆包不论图多大都压到约 1,400 token,整页快看小字只读对 10%,切块后 92~98%。对这类模型,「放大」决定读不读得对。

**B-301 问方向的代价**:看图模型 qwen4-max:正放多 1 次调用、横的多 4 次,问方向这一段中位约 4~5 秒;豆包 260628 体检:中位 2.08 秒、p95 4.0 秒、超时 0(B-301 §9.5)。

**主模型能不能答「正不正」—— 证据只到第 1 步**:B-301 §8.1 小测量对 deepseek-flash、glm-5.3-flash、glm-5.3-flashx 每张图**只问了一次**(正放 33 + 转过 33 + 无文字 4,B-301 设计第 399、493 行):正放答 yes、转过答 no、无文字答 none,前两个全对,flashx 转过答 no 32/33。**第 2 步(三个角度各问、恰好一个 yes 才转)在这三个模型上从没测过**,而测试环境 14 个 Path A 智能体里 13 个用它们(B-301 第 116 行,11-11 的数);glm 两个关不了思考,耗时与输出 token 没量。qwen4-max 今天两步都测过(48/48)。所以 §6.2 E 组要补全两步,生产只对测过的模型打开(§8 第 2 条)。

## 2. 目标与不做

### 2.1 目标

1. Path A 不比 Path B 弱:横 / 倒的图先转正(①);放大局部、`auto` 逐条读、如实说没看到 / 不确定、接缝重看(②)。
2. **正放的图一张都不许被转,转过的图一张都不许转错角度**(B-301 体检里豆包 260628 转错过 1/99,`vt-1@180`;此时「已顺时针转 N 度」那句话就是笃定的错话)。
3. 原图永远不动;换图只发生在每一步临时组装的提示词视图里。
4. 发给模型的字节**不比原图大**(PNG 例外:不超过 min(原图 × 1.1, 4,900,000 字节),§4.1.5)—— 不能因为转正让本来能发的图被厂商拒。
5. 对所有厂商一套做法;只按「体检过没有」决定生产是否打开(§8 第 2 条)。

### 2.2 不做(各一句)

- **豆包读错**:用户定先不管。
- **B-323 Path B 不告诉模型它看不见图**、**B-324 超过 10 MiB 的图被拒而不是缩小**、**B-325 Anthropic 缓存写了不命中**:各自另立项。
- 与方向无关的读错、没有文字的图的方向、知识库文档里内嵌的横图:同 B-301 §8。
- 上线前就在对话历史里的图:不回头判(§4.1.1,§8 第 10 条)。
- 压缩器按 1,300 token 估一张图,对 qwen4-max 低估约 9 倍:与本设计无关,记在 §10。
- 调试台显示「这一步发给模型的是转过的图」的界面:本单只把数据记下(§4.1.8),界面另做。

## 4. 设计

### 4.1 PR ①:图进主模型之前先转正

#### 4.1.1 在哪一步做、管哪些图

```
A. 压缩之后、挂工作区快照与渲染页段之前(builder.py 压缩段 :1093-1199 之后、:1245 之前):
   1. 找要判的图,两类,按图字节哈希去重:
```

**再核一次是谁答的**(第三轮审查 L1):回答落进结论之前,看每个回答实际是哪个模型给的。注意 B-301 记的只是**模型名**:`_served_model` 取解析器返回的第二项(`vision.py:1219-1223`),解析器返回 `(provider, model, 上限)`(`llm/truncation.py:86-88`)。PR ① 这一侧改记完整的 `provider/name`(B-301 不动),与目录条目的键同形(`catalog_entry(provider, name)`,`model_catalog.py:1066`),不然对不上、所有判断都被作废、功能悄悄不工作。规则:**只采信核实过的模型给的回答**;其余回答当作没答成。于是:第 1 步由核实模型答了 no → 后面没核实的回答都当没答成 → `pending`;第 1 步就不是核实模型答的 → `unjudged`。计 `answer_from_unverified_model`。**这一道是事后的补充,真正的保证在建路由时的剪枝**(第四轮审查 L1):响应上没有盖「谁答的」章时,解析器一律报配置的主模型(`usage_metering.py:139-146`),而盖章层只在接了用量存储时才挂(`agent_factory.py:731-735` 的 `step_llm_chain`)—— 没盖章时这道检查永远通过,核不出备用模型。所以:① 问方向路由与主循环一样挂盖章层(同 `step_llm_chain` 的写法:有用量存储就 `with_served_by`);② 加一条**构建期测试**:问方向路由整棵备用树的每个节点都是核实且未撤销的模型,保证即使没盖章,答的也只可能是核实模型。

**问法与判定**:原样用 B-301 —— 同一句问题(`image_orientation.py:21-25`)、同一张约 150 万像素的候选图、同一个两步判定(`:91-108`)、被厂商拒不退回。**不改一个字**,B-301 的体检口径直接适用。

#### 4.1.3 结论记在哪

对话状态里加三个通道(`state.py`,与 `viewed_figures` 同类,`state.py:385-397`):

| 通道 | 内容 | 什么时候写 | 合并方式 | 上限与淘汰 |
|---|---|---|---|---|
| `conversation_images` | 图编号(`img_` + 图哈希前 8 位)→ 原图 ref、像素尺寸、第一次出现的那一轮 | 只在出现新图时追加 | 按键并集(同键值不变) | 不淘汰(每轮最多 8 张,每条约 150 字节;1,000 张图约 150 KB) |
| `image_orientations` | 键 = 图哈希前 16 位 + 问法版本 → 结论、角度、四个方向的回答、尝试过几轮、上一次尝试的那一轮;**判断时配置的主模型**与**实际应答的模型**只作记录,不进键 | 有新结论、或结论从「待再判」变成定论时写 | 按键并集,同键新值覆盖旧值 | **不淘汰**(第二轮审查 N5:每条约 300 字节;淘汰会让历史图在对话中途翻回横的) |
| `shown_image_angles` | 本步每个图编号显示的角度 | 每一步整份替换 | 默认(后写的覆盖) | 只有本步的图 |

**结论有哪几种**(第二轮审查 N1):

| 结论 | 怎么来 | 显示 | 说明 | 以后 |
|---|---|---|---|---|
| upright / no_text | 第 1 步 yes / none | 原样 | 无 | 定论 |
| rotated | 第 2 步恰好一个 yes | 转 N 度 | 「已转 N 度」 | 定论 |
| undetermined | **三个角度都答成了**(yes / no / none),但没有唯一的 yes;或 pending 再判一次后仍判不出 | 原样 | 「看起来不正,判不出方向」 | 定论 |
| **pending** | 第 1 步答 no,第 2 步**有任何一个角度没答成**(超时、出错、答非所问、候选图没生成出来、时间不够) | 原样 | 「看起来不正,还没判出方向」 | 之后某一轮第一步再判一次第 2 步(第 1 步不重问);再判后三个都答成 → rotated / undetermined,仍有没答成的 → undetermined |
| **unjudged** | 第 1 步就没答成(超时、出错、被拒、答非所问);或判它的模型被明确撤销(§4.1.9) | 原样 | 无 | 之后某一轮第一步再从头判一次;仍没答成就停在这里,不再试 |

**这张表只在 PR ① 这一侧用**(第三轮审查 M1):B-301 的判定在第 2 步「没全答成」时一律给 undetermined(`image_orientation.py:102-108`),候选图写失败也给 undetermined(`vision.py:1171-1173`),三个角度共用一个时限、超时记 `"timeout"`(`vision.py:1176-1181,1208-1209`)。照搬的话,§4.1.4 说的高负载情形会把图永久判成 undetermined、再也不重判。所以 PR ① 不看 B-301 给的结论字段,而是按回答重新归类:第 0 度是 no、90 / 180 / 270 里有任何一个不在 yes / no / none 里(或根本没问到)→ pending;三个都在 → 照 B-301 的「恰好一个 yes」规则。`ask_image` 的行为不变。

pending / unjudged 也写进状态(不再只放进程内):这样它们在下一轮还在、说明不会悄悄消失;代价是「待再判」那张图在再判的那一轮从「看起来不正」变成「已转 N 度」,历史消息的字节变一次,厂商的前缀缓存破一次 —— 每张图最多一次,接受。

**为什么键里不放模型**:方向是图自己的属性。放了模型,换主模型会让历史图的显示角度翻转、模型之前给过的框对不上;子代也继承不了父代的结论。判断模型(`provider/name`)照样记下;问法一改(问法版本变),所有图重问。

**显示哪些结论**(第三轮审查 L2、第四轮 M-A):每条结论在判的时候记下判它的模型(`provider/name`)以及「判的时候它是核实的」(只有核实模型的回答被采信,所以这一项总为真,但写进记录,不靠事后去目录里查)。显示时:

- **只有明确撤销才收回**:给出这条结论的某个模型在撤销清单 `ORIENTATION_REVOKED_MODELS` 里(§4.1.9)→ 这条结论**按 unjudged 对待**:这一步起按原样显示、不加说明;之后某一轮第一步、图还在视野里、而且**这时的主模型是核实且没被撤销的**,才重判一次。**说白了:撤销的正是这个智能体自己的主模型时,没有谁会来重判 —— 一直按原样显示,直到这个智能体换成一个核实过的主模型**(第五轮审查 1)。「按 unjudged 对待」是每一步显示时现算的(查清单),不靠把状态改写回去;重判出新结论时才覆盖状态里那一条。
- **目录里查不到不算撤销**:模型条目被删、被改名(这是常事,例如 deepseek-flash 换成 V4.1、B-320 那样成批改目录),结论照旧显示。
- 撤销那一刻这些图的显示角度变一次(前缀缓存破一次,旧角度的局部图按 §4.2.3 退役);撤销是少见、有意的动作,接受。
- 主模型换成没核实的模型、或子代用没核实的模型时:已有结论照样显示,只是不判新图。

**三处特殊出口也带上**(第一轮审查 M1):输出截断重试、空回复重试这两个提前返回(`builder.py:1595-1603,1655-1661`)也把本步的新结论与 `shown_image_angles` 并进返回值;模型调用出错、整步从检查点重跑时(`:1527-1529`),结论还没落检查点,靠**进程内记录**兜住 —— 键为 (一轮的首段 run id, 图哈希, 问法版本),与 B-301 的 `_remember` 同形(`vision.py:1225-1238`),重跑不重问。

**子代**(第二轮审查 N6、第三轮 L3):建子代时,把父代对 `turn_image_refs` 里那几张图的**定论**(upright / no_text / rotated / undetermined)种进子代的初始状态 `child_input["image_orientations"]`,与 `turn_image_refs` 同一个做法(`_child_run.py:252-265`);子代再派孙代时照此往下传。**pending / unjudged 不往下种**:否则 5 个子代会同时各自重判同一张图,还可能与父代判得不一样;子代遇到这种图就当没结论,自己判或按原样(取决于它的模型有没有核实)。父代的结论经工具上下文到 `_child_run`:`ToolContext` 加 `image_orientations`,由 `_build_tool_context` 从状态填(`builder.py:2161-2166` 那一处)。子代自己问到的结论只记在子代的对话状态里。

#### 4.1.4 并行与限时

- 第 1 步:最多 8 张同时问。第 2 步只给第 1 步答 no 的图,每张 3 次。
- 每次调用占进程内看图名额(与 `ask_image` 切块共用 12 个,`vision.py:213-243`)—— 保护厂商限流,代价是同一进程里同时有很多带图对话时要排队。
- 候选图在内存里生成(§4.1.5),占宿主解图名额(共用 2 个,`region_zoom.py:277`),不新增解图并发,所以不加大主进程内存峰值的上限。
- **整步限时 30 秒**(沿用 `ORIENTATION_TIMEOUT_S`,`image_orientation.py:27`),含排队;run 剩不到 60 秒就不问(同接缝重看那条线,`seam_relook.py:49`)。

**耗时估算**(单个对话、调用本身按 qwen4-max 2~5 秒一轮、候选图生成按每张 0.3~1 秒 —— 后者没量):

| 情形 | 估计 |
|---|---|
| 1~2 张正放的图(最常见) | 1 轮,约 2~5 秒 |
| 1 张横的图 | 2 轮 + 3 张候选,约 5~12 秒 |
| 8 张都横着(最坏) | 第 1 轮 8 次并行约 5 秒;24 张候选经 2 个解图名额约 4~12 秒;第 2 轮 24 次分两批(名额 12)约 10 秒 → **约 20~27 秒,贴着 30 秒线** |
| 同一进程 N 个对话同时传图 | 名额共享:N 个对话各 1 张正放图,N ≤ 12 不排队;N 个对话各 8 张横图,N ≥ 2 就会有图到 30 秒还没判完 |

**到点没判完的图**:第 1 步就没答成 → 记 unjudged,按原样发,不加说明;**第 1 步答了 no、第 2 步没来得及** → 记 pending,按原样发,加「看起来不正,还没判出方向」(§4.1.6),不让它悄悄横着进去。两种都写进状态,**下一轮第一步各再判一次**(§4.1.3 结论表),之后就是定论。表里「两个对话各 8 张横图」那种挤兑,因此只让这些图晚一轮转正,不会整段对话一直横着。

#### 4.1.5 转正的图怎么生成、多大

**不落盘,发送时在内存里生成**(审查 M2 / M8):

- 提示词视图里换上的块形如 `{"type": "image_ref", "ref": <原图 ref>, "view": {"degrees": 90, "variant": "full"}}` —— ref 仍是原图,只多一个「按多少度显示、用全分辨率还是小副本(`full` / `low`)」。适配器按 `variant` 取对应那一份,用了小副本的 run 里不会退回去读全分辨率那份(第五轮审查 3)。
- **在 `agent_node` 里先算好,适配器只读**(第二轮审查 N2):适配器解析图片发生在 `_prepare_request` 里(`openai.py:566,642`),那一段算在路由的首 token 超时里(`router.py:872-874`);在那里现算 12 MP 的转正图,慢的时候会被误判成首 token 超时、切到备用模型。所以 §4.1.1 A 段定下显示角度之后,`agent_node` 就在调模型**之前**把这一步要用的转正图算好,放进一个进程内缓存,键 = (图哈希, 角度)。
- **钉住的范围**(第三轮审查 M2):钉住是包住**整个 `agent_node` 这一步**的 try / finally,从进入这一步到返回、出错或被取消。这一步里所有会重新解析图片的调用都在里面:路由的每一次备用尝试(每次都重跑 `_prepare_request`,`openai.py:566`)、思考升档那一次(`builder.py:1379-1383`)、结构化输出的重发(`_finalize_structured_response`,`builder.py:1702-1715`)。
- **钉住的也算在上限里**:放新条目时先挤掉没钉住的;缓存**永远不超过上限**。参考:10 个对话同时在跑、各有 3 张横图,约 10 × 3 × 3.5 MB ≈ 105 MB,比全 pod 约 98 MiB 的余量还大(`test_parse_worker_memory_budget.py:66` 那套预算)—— 所以上限是硬的。
- **挤光了还放不下时,角度不变**(第四轮审查 M-B):原先「这一步按原样发、下一步再试」会让同一张图在一个 run 里横、正来回翻,每翻一次前缀缓存破一次、局部图退役又恢复,而且偏偏在最忙的时候。改为三级,都在 `agent_node` 里、不算进首 token 时间:
  1. **等**:最多等 5 秒,等别的步骤结束、钉住解除腾出地方;
  2. **小副本**:还是放不下,就生成一张约 150 万像素的转正图(与问方向的候选同尺寸,约 0.3~0.5 MB),放进单独留出的 4 MiB 小副本区;**角度不变**,只是这张图这个 run 里清晰度降一档,块上标 `variant: "low"`,计 `low_res_copy`。这个 run 之后的步骤一直用这张小副本(字节稳定);下一轮重新按原分辨率试。**小副本区的条目归属于 run**(第五轮审查 3):过期时间 = 这个 run 的截止时刻;run 结束时(`sse.run_agent` 的结束收尾,`services/orchestrator/src/orchestrator/sse.py:431`;正常结束、出错、被取消都走)一并释放,不等过期;
  3. **按原样发**(小副本区也满,极端情况):这张图**在这个 run 剩下的步骤里一直按原样**,不来回翻;这一步的 `shown_image_angles` 记 0,不加「已转 N 度」那句,改加一句只陈述事实的说明 `Image {i} of {n} in this message is shown as stored in this step, not turned upright.`(第五轮审查 4);`zoom_image` 因此按 0 度裁;计 `pin_over_cap`。下一轮重新试。
  两个区加起来的上限(32 + 4 MiB)仍是硬的。**一步要用的条目一次拿齐**(第五轮审查 3):这一步所有要钉住的条目(全分辨率与小副本)要么全部拿到、要么一个都不拿再等,不会两个步骤各拿一半、互相等满 5 秒。
- 两个适配器取图时(`openai.py:750-774`、`anthropic.py:1028-1061` 经 `multimodal.resolve_message_images`)认 `view` 字段:先照旧取原图字节(取不到照旧换成提示文字,B-283 不变),再按 (图哈希, 角度) 从缓存里**读**。万一没读到(只有钉住失效之类的异常情况),适配器当场算一次并计 `expert_work_main_model_image_view_cache_total{outcome="adapter_miss"}`,不让这一步失败。`ask_image` 发出的消息从来不带这个字段,所以 Path B 不受影响、不会转两次。
- **缓存多大**:按「同时活跃的带横图对话数」定。按测试环境约 6% 的图是横的、每轮最多 8 张,一个活跃对话平均不到 1 张转正图;单张 12 MP 转正图约 3~4 MB。上限先定 32 MiB(约 8~10 张),按最近使用淘汰;被挤掉的下一步在 `agent_node` 里重算(在首 token 计时之外)。实际命中率、重算次数、`pin_over_cap` 次数在 §6.1 的 pod 实测里量,不够再调。多副本部署时换了副本也要重算一次。
- **同一张图每次算出的字节必须完全一样**:厂商的前缀缓存按字节比,重算一次字节变了,缓存就破一次。编码参数固定(固定质量与子采样、不写时间戳等元数据);加单元测试「同一输入算两次,字节相同」。**前提**(第三轮审查 L7):同一张原图、同一版 Pillow(及它带的 libjpeg / zlib)。各副本跑同一个镜像时成立;滚动升级换了 Pillow 版本,新旧副本算出的字节可能不同,厂商的前缀缓存因此破一次,之后恢复。
- 不写 NAS、不经沙箱;计算占已有的 2 个解图名额(`region_zoom.py:277`;闸在 `vision.py:221-234`),与 `ask_image` / `auto` 裁图共用 —— 不新增解图并发,不加大内存峰值上限;代价是两边同时忙时互相排队,但排队发生在 `agent_node` 里,不算进首 token 时间。
- 问方向用的 150 万像素候选图同样在内存里生成(`crop_image(data, [(0,0,1000,1000)], degrees, 150 万)`,与 B-301 写到盘上的那张像素相同),不缓存。

| 选项 | 结论 |
|---|---|
| **A. 内存里临时生成** | **推荐**:沙箱看不到;用户删了原图,下一次取原图就失败,转正图自然没了;不占 NAS、不用接留存清理 |
| B. 按对话存一份(按内容命名,接留存清理与删原图联动) | 否:要改留存作业的不变式(README:79-83 只许删登记过的东西)、要和删除联动,收益只是省一点 CPU |
| C. 存对象存储 | 否:同 B,还要新键空间与清理 |

**分辨率与字节**(审查 H2):

- 像素:原像素转,**不缩**:转正只换方向,像素与原图一样多,而原图今天就是这么大发给厂商的(适配器原样发原图字节,§1.2 #4;进对象存储之前已过上传那一侧的解码上限 6,000 万像素与 10 MiB 字节上限)。4032×3024 的手机照片转 90 度就是 3024×4032。不再另设长边 4,000 / 1,200 万像素的上限(§8.1 第 5 条细化,2026-11-20;原先那样 4032×3024 会被缩到 4000×3000,这 1% 的缩放让峰值内存多约 2.5 倍,审查 H1)。只有字节规则(下一条)会缩像素。
- 格式:跟原图走 —— PNG 转完仍是 PNG(无损,字节与原图相近),JPEG 质量 92、WebP 90(与上传转码同档)。
- **字节不超过原图**:JPEG / WebP 超了就按质量 85、75 再存(同上传那一侧的退法),仍超就每次把像素缩到 0.8 倍再试,最低到 150 万像素;还超(实际上碰不到)就**放弃转正、按原样发**并计数。原图今天能被厂商收下,不超过原图字节的转正图也收得下(厂商单图字节上限如 Anthropic 5 MB 是审查给的数,§10)。
- **PNG 例外**(第二轮审查 N9):PNG 转正是无损的,字节只会因压缩顺序略有出入;缩像素会让截图里的小字发糊。所以 PNG 先按最高压缩重存;仍比原图大时,**不超过 min(原图字节 × 1.1, 4,900,000 字节)** 就照发,不缩像素;超出才走上面的缩像素。4,900,000 字节是十进制的 4.9 MB,低于 Anthropic 的 5 MB(5 MiB = 5,242,880 字节会超过它,第三轮审查 L6)。单元测试:一张约 9 像素高小字的合成 PNG 截图转正后不被缩、字节在线内。
- **内存**(审查 H1,本机实测见修订记录 5.2):解开的原图转完立刻放掉,不需要转时不复制,WebP 模式已对时不转换;一张全分辨率转正图**占 2 个解图名额**(`ask_image` 裁图今天就用这 2 个名额,所以同一时刻最多一张全分辨率转正图在算,不会与别的解图叠加),适配器当场重算(`adapter_miss`)也走名额、在线程里,不占事件循环;问方向借出的候选图算在全分辨率区的上限里。本机实测 12 MP JPEG 单次峰值约 +55 MiB、48.8 MP 约 +110 MiB。开发时仍要在 pod 里实测峰值与常驻增量,有增量就改 `test_parse_worker_memory_budget.py:66` 的主进程常数(§6.1)。

#### 4.1.6 给主模型的说明

每段说明包进 `<platform-context>`(`platform_context.py:99-101`),追加在那张图所在消息的末尾,在用户字样转义之后(§4.1.1 B)。防冒充的程度**与 B-162 平台段相同**:只转义标签的原样拼写(`platform_context.py:93-96,130-133`),别的写法(大小写、加空格)挡不住,与今天的平台段一样。

系统提示词说「最新的平台段取代之前的」(`platform_context.py:77`),而这些说明挂在各自那条历史消息上、比尾部的平台段旧。为了不让模型以为它们被取代了,每段说明末尾固定加一句「这条说明对这张图在整段对话里一直有效」(第二轮审查 N4)。不改系统提示词:那会让所有智能体的系统提示词字节变一次。

适配器把文字放前、图放后,所以按「这条消息里的第几张」说。平台英文、只陈述事实;rotated / undetermined 末尾带 `This note about the image stays valid for the rest of the conversation.`,pending 末尾带 `This note stays valid until the platform replaces it.`(它下一轮会被定论替换):

| 结论 | 说明 |
|---|---|
| upright / no_text / unjudged | 不加 |
| rotated | `Image {i} of {n} in this message was stored turned; it is shown rotated {N} degrees clockwise. The user's file is unchanged.` |
| undetermined | `The text in image {i} of {n} in this message does not look upright and its orientation could not be determined, so values read from it may be wrong.` |
| pending | `The text in image {i} of {n} in this message does not look upright; its orientation has not been determined yet, so values read from it may be wrong.` |

「已转」那句只说事实,不说「所以文字是正的」:转错角度时(§2.1 第 2 条)这句话仍然为真。

#### 4.1.9 开关与「核实过的模型」

**两样东西,作用不同**(第三轮审查 L5):

- **核实标记(决定对谁打开)**:模型目录的 `ModelEntry`(`packages/expert-work-protocol/src/expert_work/protocol/model_catalog.py:242`)加两个布尔字段,默认都是假:
  - `orientation_verified`:跑过 §6.2 E 组、过了 §6.3 的 E 线,才在代码里设为真,注释写体检日期与结果出处(与目录里其它「实测过」的注释同一个写法)。只有它为真、且下一项为假的模型才判新图。
  - **撤销清单 `ORIENTATION_REVOKED_MODELS`**(第四轮审查 M-A、第五轮 2):不是目录条目上的字段,而是同一个模块里的一个**只增不减的代码常量**(`provider/name` 的集合),这样删掉或改名目录条目不会顺带「撤销撤销」。发现某个模型会转错(例如生产计数里转错角度),把它加进清单:它不再判新图,它判过的结论在显示时按 unjudged 对待(§4.1.3)。只增不减由一条测试钉住:测试里另记一份清单,常量里少了任何一个名字就红。**把 `orientation_verified` 改回假、删掉条目、改名都不算撤销**,只影响以后判不判新图,已有结论照旧显示。如果撤销的正是某个智能体的主模型,它的图在换成核实过的主模型之前都按原样显示、没有重判。
  - 按 `provider/name` 查(`catalog_entry`,`:1066`),所以不存在拼写对不上的问题。不需要任何环境配置:**没有核实的模型,哪个环境都不判**。新加一个主模型或备用模型 = 它在 E 组过线后一个代码改动。
- **运维紧急开关(只用来关)**:`EXPERT_WORK_MAIN_MODEL_IMAGE_ORIENTATION`(布尔,默认开,`0 / false / off / no` 为关,与 B-301 同一套解析,`image_orientation.py:37-38,213-216`)。不复用 B-301 的开关:那个关掉的是 `ask_image` 的问方向,两边出问题的方式不同(§8 第 3 条)。

| 开(默认) | 核实了 | 判(备用链只留核实且未撤销的节点) | 显示;判它的模型被明确撤销的除外(那些改成 unjudged) |
| 开 | 没核实 | 不判(计 `model_not_verified`) | 显示(同上) |
| 关 | 不管 | 不判 | **不显示**,一切与今天逐字节相同 |

所以**默认等于对没核实的模型关着**;开关只是出事时的一键关停。PR ① 合并时目录里预计只有 qwen4-max 有今天的证据(还要按 E 组补全),其它模型都要先过 E 组。另一种做法(各环境配一张名单)见 §8 第 2 条。

## 5. 否掉的做法(理由对着代码核过)

### 5.1 只改提示词

用户已否。证据:今天 qwen4-max 直接看转过的仪表,21 次错全是笃定的错 —— 模型不觉得图是横的,「横着的图请小心」它不知道对哪张小心;B-301 §2:「不问的话,模型几乎从不主动说图是横的」。提示词也转不了像素。B-323 的测评里,智能体提示词写着「客户发来的图片你能直接看」,模型就照着编了内容。

### 5.2 让 Path A 也能调 `ask_image`

- 根本问题在 `ask_image` 被调**之前**:主模型已经看到了横着的原图,可能直接作答 —— 今天 21 次笃定的错就是这样来的。转正只在 `ask_image` 里做,保护不到这一步;PR ① 正是补这一步。(`ask_image` 的看图模型本可以换成主模型的关思考路由 —— PR ② 的 `auto` 就是这么借用的 —— 所以「要再配一个模型」不是否掉它的理由。)
- 离线模拟:24 次里 22 次调了 `ask_image`,5 次 4 步内没回复 —— 主模型看得见图还要绕一圈,多一步延迟。
- 代码特意做成互斥(`agent_factory.py:707-716`);`read_page` 的回执按「三选一」说话(`assembly.py:529-539`,`read_page.py:1406-1410`),同时存在要另起说法。

### 5.3 上传时就转正

- 上传时没有 run、不知道哪个模型,轨迹无处可记(B-301 §3);上传那一步只按方向标记转(`_image_sanitize.py:15-17`;调用点 `api/uploads.py:812`)。
- 转的是用户原图:判错一次,之后每次看(包括 Path B 智能体、人在聊天记录里看)都是歪的,回不去。
- 业界没有人在上传时按内容转(§3)。

### 5.4 用方向分类小模型

- PP-LCNet_x1_0_doc_ori:正放的自然照片 22.6% 被判要转,显示屏照片只对 62~79%(B-301 §2);B-301 已定它绝不用在用户上传的照片上(§7.1)。
- 对话在控制面主进程里跑,主进程内存算满(全 pod 只剩约 98 MiB,B-301 §7.3 / §7.8)。
