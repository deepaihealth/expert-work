## 1. 目标与范围

### 1.1 要解决的问题

1. **记不住**:LoCoMo 全量 1,540 题端到端只有 23.1%,**70% 的回答是「记忆里没有」** —— 瓶颈在抽取丢信息,不在检索(B-167 ⑥)。
2. **记错地方**:记忆只按「用户」存。员工用同一个账号服务很多位客户时,客户 A 的病情 / 偏好会在服务客户 B 时被召回;健康类智能体因此至今不能开长期记忆(B-167 ①)。
3. **几处已核实的正确性缺陷**:写入比对会改到别的智能体的记录、失败重试丢元数据、让模型抄 UUID 抄错就新旧并存、关键词检索实际失效(§2)。
4. **智能体用不上**:模型不能主动查 / 记 / 忘;已有的 `remember` 工具写的是技能组件,不进记忆表,平台上实际有两套「长期记忆」。
5. **可治理性不够**:人工更正原地覆盖丢历史、自动写入无审计、管理页把旧版本和当前版本混着列、删除语义说不准、第三方的终端用户无法查看 / 删除自己的记忆。
6. **成本与延迟**:每轮把整段对话重抽一遍;回答前最多 3 次额外模型调用(改写 / 重排 / 复核)。

### 1.2 范围

| 块 | 含义 |
|---|---|
| **后端** | 作用域模型、记忆类型、写入流水线(抽取 / 比对 / 落库)、召回、智能体工具、整理与遗忘、评测、审计 / 权限 / 安全 |
| **Web 管理端** | `apps/admin-ui` 记忆相关页面(`MemoryAdmin`、用户档案的记忆面板)与智能体配置里的记忆设置 |
| **开放 API** | 给第三方的终端用户记忆接口(查看、删除;二期写入 / 更正),含鉴权粒度与文档站 |

**不在范围**:知识图谱 / 时序图数据库(§3.5 说明为何不做);参数化记忆(LoRA / KV-cache);自训练模型;外部业务系统里的客户档案同步(走 MCP)。

| 指标 | 现状 | 目标 |

## 3. 参照结论

### 3.1 行业基线(多数项目 / 云厂商都有 —— 必须达到)

| 做法 | 谁在做 | 我们 |
|---|---|---|
| 默认后台抽取,先答后写 | AgentCore、Memory Bank、ChatGPT、LangMem、Letta 睡眠期智能体 | ✅ B-168 |
| 另给模型一个主动「记住 / 忘掉 / 查」的工具 | Claude 记忆工具、Letta、LangMem、OpenViking MCP | ❌(#11) |
| 写入时与同作用域相似记录比对(新增 / 更新 / 跳过 / 作废) | AgentCore、Memory Bank、mem0 v1、OpenViking | ✅ 有缺陷(#4 #5) |
| 不覆盖,作废并留时间(双时态 / 版本) | Zep / Graphiti、Memory Bank revisions | ✅ 人工路径例外(#12) |
| 抽取时把相对时间落成绝对日期 | mem0、LongMemEval 建议 | ❌(#2) |
| 分层作用域,在存储层强制 | AgentCore namespace(`/actor/{actorId}/session/{sessionId}`)、Memory Bank scope、OpenViking peers | 缺「客户」层(#10) |
| 常驻小画像 + 按需检索长尾,控 token | ChatGPT、Memobase、OpenViking、Claude Code | 只有长尾 |
| 混合检索(向量 + 中文正确分词的关键词)+ 融合 + 可选重排 | mem0、Graphiti、ReMe、OpenViking | 关键词路失效(#7) |
| 写入是注入面:标来源、过滤、不让工具 / 网页内容直接成为用户事实 | OWASP Agentic、MINJA、OpenViking(工具结果不进用户记忆) | 部分(有威胁扫描,无来源区分) |
| 用户可看 / 改 / 删 / 关闭,删原始对话连带派生记忆 | ChatGPT、Claude、Copilot、Azure | 控制台有;终端用户没有(#17) |
| 按类型设保留期(TTL)与修订历史 | AgentCore(7–365 天)、Memory Bank(默认 365 天) | 只有预测有效期 |
| 用自己领域的数据评测,始终对照「全文进上下文」 | 所有严肃评测 | 只有英文 LoCoMo |

### 3.2 进阶做法(有数据支撑、按需采纳)

- **抽取提示词质量规则**(mem0 v3):每条自成一句(代词替换成实体)、15–80 字带上下文而非原子碎片、显式记录状态变化(「从 A 改成 B」)、观测日期 vs 当前日期、区分用户说的 / 助手说的、宁多勿漏。
- **短编号代替 UUID**(mem0 旧版 `_resolve_mapped_id`):给模型看 `0..9`,回来再映射,未知编号丢弃。对应本仓库教训「模型手抄长串必错」。
- **先读后改**(OpenViking):改已有记忆前必须给模型看到原文;「相似 ≠ 同一件事,拿不准就分开存」的合并安全规则;每次抽取落一份 diff(增 / 改 / 删 / 跳过 + 原因码)供审计与调试。
- **按类型的合并规则**(OpenViking):画像 = 当前状态 + 「截至日期」;事件 = 只追加;偏好 = 每主题一条;计数类累加。
- **上下文组装**(OpenViking):按类别配额 + 先广后深(摘要 → 全文)+ 跨轮去重账本(同一条不重复注入)+ 其它服务对象的记忆降权。
- **分阶段评测**(HaluMem):多数错误产生在抽取和更新阶段并向下游传播 —— 抽取 / 更新 / 检索 / 端到端分开打分。
- **按用途的任务成功评测**(DolphinBench 思路):有记忆能完成、没记忆完不成的任务。
- **经验记忆**(ReasoningBank、ReMe、AgentCore episodic reflection、OpenViking experiences):从成功和失败轨迹里提炼「情境 / 做法 / 禁忌」,带效用统计、低效用剪枝。

### 3.3 mem0 本地源码结论(2.2.1)

- **算法已大改**:2026-04(`a488e190`)起改为**单次 LLM 只新增**,开源版删除了增删改判定与图记忆;OpenMemory 与评测目录也已移出主仓。README 的 LoCoMo 92 / LongMemEval 94 是**托管平台专有优化**,开源版拿不到。
- **可借**:抽取提示词规则(§3.2);短编号映射(注意 v3 自己的 `uuid_mapping` 建了不用,`mem0/memory/main.py:937`);融合打分(过采样 + 按查询长度 sigmoid 归一的关键词分 + 实体加权 + 语义阈值先门控);身份键剥离防越权写;OpenMemory 的状态机(活跃 / 暂停 / 归档 / 删除 + 状态历史表)与按应用的访问控制。
- **不借**:只新增不处理矛盾(与我们的双时态和「知识更新」题型冲突);英文 spaCy 实体 / 词形还原与 `'simple'` 分词(中文下关键词与实体加权实际失效);历史存 SQLite;写入无锁有竞态;JSONB 过滤无索引;遥测默认开。

### 3.4 OpenViking 本地源码结论(AGPL,只借思路)

- **可借**:peers(员工下挂服务对象的记忆空间 + 按服务对象过滤 + 其它对象降权)—— 正对我们的 #10;记忆类型由配置定义(目录 / 主键 / 字段合并规则 / 只追加或更新);先读后改 + 补丁式编辑;两阶段提交(同步归档 + 持久队列异步抽取,我们 B-168 已具备);抽取时**工具调用 / 结果不进用户记忆**;上下文组装器;经验演化链与「经验被读 → 后续结果」的谱系统计。
- **不借**:每次提交 2–6 次以上模型调用;非严格模式下抽取异常静默返回空;文件与向量双存储写入不一致;仅路径前缀隔离;README 与代码不一致(目录递归检索已删)。

### 3.5 有争议 / 暂不做

- **知识图谱**:Zep 时序图最严谨,但要图数据库、写入调用重;mem0 开源版已删图;Letta 仅用文件 + grep 在 LoCoMo 拿到 74%。**不做**,用「实体字段 + 关系表」的轻量方案留口子(按需)。
- **写入时增删改 vs 只新增**:mem0 转向只新增、读时消解;AgentCore / Memory Bank 仍写时比对;HaluMem 显示写时更新本身引入错误。**我们保留写时比对**(有双时态承接,管理端可解释),但用 M1 的「更新正确率」指标盯住,见 §9 必拍 #2。
- **读路径放多少模型调用**:Zep 读路径零模型调用;我们复核默认开。默认值以评测定(§9 后定 #3)。
- **跨用户经验学习的安全性**:2026 年有研究报告无攻击者情况下跨用户污染率 57–71%;只在脱敏 + 审核前提下做,放最后(M9)。

## 4. 设计原则

1. **先测量再改**:任何影响抽取 / 召回的改动,PR 里贴评测前后数字;没有基线不动默认值。
2. **作用域在存储层强制**:租户 / 用户 / 服务对象 / 智能体的过滤由平台 SQL 加,不来自模型,不来自提示词;所有读写路径(召回、比对、整理、清除、导出)走同一个作用域对象。
3. **不覆盖**:自动和人工的每次变更都走版本链(supersede / expire),旧值可回看。
4. **模型只给短编号**:任何让模型引用已有记录的地方用 `0..N`,平台映射回 ID。
5. **来源可追**:每条记忆带来源会话 / run / 消息位置 / 说话方(用户 / 助手 / 工具);工具和网页内容默认不直接成为用户事实。
6. **一套记忆**:模型主动写的、自动抽取的、人工录入的,都进同一张表、同一套作用域与审计。
7. **平台默认可用,开关只做收窄**:新能力默认在合理档位开启,不让每个租户去配(本仓库教训「平台缺口先改默认」)。
8. **平台文本零租户内容**:提示词、工具说明里的示例不得出现具体客户业务。
9. **与知识库共用地基**:中文关键词、重排按用途拆分、评测工具链与 B-175 共用实现。
10. **健康数据按敏感个人信息对待**:服务对象记忆可整体关闭、可按对象删除、保留期有上限。

## 5. 总体架构

```
            ┌──────────── 写入 ────────────┐                 ┌──────────── 读取 ────────────┐
 一轮结束 → │ 写回任务(B-168,持久队列)    │                 │ 召回节点(每 run 一次)        │

            │  ③ 抽取(新提示词,观测日期)  │                 │  ③ 长尾:向量 + 中文关键词     │
            │  ④ 比对(短编号,同作用域)    │                 │     → RRF → 衰减/频次/重要度  │
            │  ⑤ 落库 + 版本链 + 审计 diff  │                 │     → 重排(记忆用途配置)     │
            └───────────────┬──────────────┘                 │     → MMR → 复核(按评测定)   │
 模型工具 memory_save/forget ┘                                 │  ④ 预算组装 + 跨轮去重         │
 人工 / 开放 API 更正 ────────┘                                └──────────────────────────────┘
                     ┌──────────────── memory_item(单表,作用域 = 租户 × 用户 × 服务对象 × 智能体)──────────────┐
                     └──────── 后台整理:聚类汇总 · 到期复核(带新证据) · 归档 · 保留期清理 · 画像重建 ────────┘
```

## 6. 后端设计

### 6.1 作用域模型(解决 #10;待拍板 #1)

新增**服务对象**(subject)维度,完整作用域 = `租户 × 用户 × 服务对象 × 智能体`:

| 记忆归属 | `subject_ref` | `agent_name` | 例子 | 谁能召回 |
|---|---|---|---|---|
| 用户本人事实 / 偏好 | 空 | 空 | 「这位员工习惯周报按自然月」 | 该用户的全部智能体 |
| 服务对象事实 | `subject_ref` | 空 | 「客户 X 对青霉素过敏」 | 该用户在服务**同一对象**时 |
| 经历 | 可空 | 智能体 | 「上次为客户 X 出了三月方案」 | 同一智能体(+ 同一对象) |

- **`subject_ref` 从哪来**:run 级参数,由调用方给,不由模型推断。
  - 对外 API:`POST /v1/agents/{code}/runs` 新增可选字段 `memory_subject`(字符串,≤255;与 `user_id` 同样做 NUL / 控制字符拒绝)。
  - 控制台 / 触发器:智能体配置 `memory.long_term.subject_from: inputs.<key>`,从本轮注入变量取值(B-61 注入变量已是结构化输入)。
  - 平台存 `subject_ref` 的 SHA-256 摘要 + 调用方原值(管理端展示用),索引用摘要。
- **没给 `subject_ref` 时**:行为与现在完全一致(兼容现有对接方)。
- **智能体可声明「必须有服务对象」**:`memory.long_term.subject: required`。声明后,没给对象的 run **不写服务对象类事实**(只写用户本人类),召回也不带任何对象记忆 —— 宁可少记不可串记。健康类智能体开记忆的前置条件是声明为 `required`。
- **抽取时归类**:抽取提示词输出 `about: "user" | "subject"`,平台按本轮作用域落列;本轮没有对象时 `about: subject` 的条目丢弃并计数。
- **比对、整理、到期复核、清除、导出全部按完整作用域进行**(修 #5 的同一处入口)。
- **索引**:`(tenant_id, user_id, subject_hash, agent_name)` 复合 btree;HNSW 过滤召回开 `hnsw.iterative_scan = relaxed_order` 并设 `ef_search`(pgvector 0.8 已支持),避免对象过滤后召回不足。
- **备选方案(必拍 #1 的另一侧)**:不加维度,健康类智能体只记员工工作偏好,客户事实以对接方业务系统为准(经 MCP 读)。代价:平台对「客户」完全无记忆;好处:零迁移、零隐私面扩大。

### 6.2 记忆类型

| 类型 | `kind` | 写入方式 | 合并规则 | 召回方式 |
|---|---|---|---|---|
| 事实 | `fact`(现有) | 抽取 / 工具 / 人工 | 同作用域比对 → 新增 / 新版本 / 作废 / 跳过 | 长尾检索 |
| 经历 | `episodic`(现有) | 抽取 | 只追加;整理时聚类汇总 | 长尾检索 |
| 画像 | `profile`(新) | 后台由事实重建,不由模型直接写 | 每个(用户或对象)一份「当前状态」清单,每行带「截至日期」与来源事实 ID | **常驻注入**,预算内全量 |
| 经验 | `experience`(新,M9 条件) | 从轨迹提炼 + 人工审核 | 情境 / 做法 / 禁忌;`supersedes`;效用统计 | 按任务相似度召回 |

- 画像是**派生物**:由当前有效的事实重建(整理任务里做),事实被作废 / 删除时画像随下一轮重建更新;删除对象时画像同删。好处是画像永远可解释(每行能点回来源事实)。
- `status` 补上 `archived` 的实现(§6.6)。

### 6.3 写入流水线(解决 #1–#6、#13)

1. **增量切片**(#3):写回任务带上一次成功写回的消息水位(检查点里已有消息序号,`memory_writeback_job` 增一列 `from_message_index`),只抽「水位之后的新消息 + 前 N 条作上下文」;压缩前抢存(CM-3)共用同一水位,消掉 B-168 遗留的「上一轮后台写回与下一轮抢存并发」窗口(同一会话的两者合并为同一串行队列)。
2. **预取**:用本轮新消息的用户侧文本做一次同作用域检索,取 top 10 作「已有记忆」上下文给抽取模型(mem0 / OpenViking 做法),让模型少抽重复、能写「从 A 改成 B」。
3. **抽取提示词重写**(#2):
   - 输入:观测日期(本轮时间,租户时区)、本轮作用域说明(有无服务对象)、已有记忆(短编号)、新消息;
   - 规则:自成一句(代词换成具体称呼)、可带必要上下文(上限约 80 字)、记录变化、相对日期落成绝对日期、**沿用对话语言**、标 `about`(用户 / 对象)与 `said_by`(用户 / 助手)、宁多勿漏但不记寒暄;
   - **工具调用与工具结果不作为用户事实来源**(只可作经历的依据),网页 / 文件内容同理 —— 防记忆投毒;
   - 输出仍为 JSON,字段在现有基础上加 `about`、`said_by`、`valid_at`(绝对日期,可空)。
4. **比对**(#4 #5):
   - 邻居检索带完整作用域(用户 × 对象 × 智能体规则同召回);
   - 给模型的已有记录一律短编号 `0..N`,回来映射,未知编号计 `degraded` 并按新增处理(保持「不丢记忆」);
   - 合并安全规则:相似不等于同一件事,拿不准就分开存;
   - 预取阶段已命中的相似记录与比对邻居合并为一次模型调用(省一次)。
5. **落库**:沿用 `ON CONFLICT DO NOTHING` + 版本链;每次写回落一行**写入记录**(`memory_write_log`:任务 ID、作用域、增 / 改 / 删 / 跳过逐条与原因码、模型、token),即 OpenViking 的 `memory_diff`,同时满足 B-167 ④ 的审计诉求(审计表只记汇总行,明细在写入记录里,避免撑爆审计)。
6. **失败重试**(#6):失败队列改存完整的 `MemoryItem` 载荷(含 `agent_name`、`subject`、分数、有效期、`said_by`),重试走与首写相同的比对 + 落库函数;旧格式行兼容读取。
7. **人工路径**(#12):控制台编辑 / 更正 / 开放 API 更正一律走 `supersede`(新行 `confidence=1.0`,旧行 `invalid_at`),不再原地 `update_content`。
8. **模型工具写入**(§6.5):`memory_save` 产生的条目直接走第 4–5 步(比对 + 落库),`said_by=user`(用户明确要求记)或 `assistant`。
9. **抽取频率**(B-168 遗留):M2 先做增量切片(成本与对话长度脱钩);是否进一步降到「每 N 轮 / 空闲时 / 会话结束」,以 M1 评测的召回不回退为前提再定(§9 后定 #1)。

### 6.4 召回(解决 #7–#9、#18)

1. **中文关键词**(#7):与 B-175 共用同一实现 —— 查询端改 OR 语义 + `ts_rank_cd`(或 B-175 必拍 #5 选定的扩展路线),记忆与知识库同一个工具函数;索引端无需重建(jieba 搜索模式切词是精确模式的超集,已在知识库侧核实)。
2. **查询构造**(#8):默认用「最近 2 轮用户消息 + 本轮」拼成查询(不调模型);仅当本轮是指代 / 省略句(长度短且含指代词,规则判定)时才走已有的改写(`rewrite_reads`)。
3. **画像块常驻**:召回节点先取当前作用域的画像(用户 + 本轮对象),预算内整块注入;长尾检索结果排在其后、去掉已被画像覆盖的事实。
4. **重排按用途配置**(#18):B-175 P2 把平台重排配置拆为 `knowledge` / `memory` 两个用途(同一基座实现,模型 / 阈值 / 候选数分开);记忆侧默认候选 20、取 5,阈值按 M1 校准。
5. **读路径模型调用按需**(#9):复核(`verify_reads`)默认值由 M1 的「有 / 无复核」对照定;无论开关,复核与重排并行(都只依赖候选集),不串行。
6. **注入位置**:沿用 `per_session` 在 `messages[1]` 带缓存锚点;画像块与长尾分两段,画像段在一次会话内稳定以保住提示缓存。`per_turn` 尾部注入的问题由 B-162 处理,本方案不重复改。
7. **跨轮去重**:同一会话内已注入过且未变化的记忆不重复注入(账本存会话元数据),省 token。

### 6.5 智能体工具(解决 #11)

| 工具 | 作用 | 说明 |
|---|---|---|
| `memory_search(query, limit)` | 主动查记忆 | 与召回同一检索服务、同一作用域;返回短编号 + 内容 + 日期 |
| `memory_save(content, about)` | 主动记一条 | 走写入流水线第 4–5 步;用户明确说「记住」时用 |
| `memory_forget(ref)` | 作废一条 | `ref` 为本会话内 `memory_search` / 注入块里出现过的短编号(会话级映射),不收 UUID;走 `expire` |

- 开记忆的智能体默认带这三个工具(平台默认可用,原则 7);工具说明为平台通用措辞。
- **`remember` 的去向(待拍板 #3)**:推荐保留 `remember` 只用于「智能体级工作约定」(技能组件,属程序性记忆,本就该走草稿审核),改名 `propose_agent_note` 并改说明,避免与 `memory_save` 混淆;关于用户 / 客户的事实一律进记忆表。备选:直接下线 `remember`,已激活的 `memory_entry` 迁入记忆表。

### 6.6 整理与遗忘(解决 #14、#16、#19)

- **按完整作用域聚类**:整理只在同一(用户 × 对象 × 智能体规则)内聚类,杜绝跨对象汇总。
- **到期复核带新证据**:复核时附上该作用域内比这条记忆更新的相关记忆 / 近期对话摘要;没有新证据时只降权不作废。
- **归档**(`archived` 实现):长期未用 + 低重要度 → 归档(默认不召回,管理端可查、可恢复),替代现在 30 天未用直接清理的一刀切;清理只针对归档满保留期的。
- **按类型保留期**:租户配置每类记忆的保留上限(服务对象类默认上限待拍板,健康数据建议有限期);到期软删 → 90 天物理删(现有 retention)。
- **删除语义写准**(B-167 ③):注释与对外文档统一为「软删,90 天后物理删除」;补租户删除、按对象删除、按会话删除的连带清理(含画像、写入记录里的内容字段、失败队列、待写回任务)。
- **画像重建**:作为整理任务的一个子步骤,按作用域增量重建。
- **整理模型配置**:修 #19,按智能体的 `aux_model` 生效或删掉该配置项(二选一,计划里定)。

### 6.7 评测(解决 #1 的度量)

- **LoCoMo 全量重跑**:当前代码 + 平台实际模型;同时跑两组对照 ——「不抽取、直接按原文检索」与「全文进上下文」。
- **中文领域评测集**(待拍板 #5:数据来源):覆盖 LongMemEval 五项能力(信息抽取、跨会话推理、时间推理、知识更新、拒答),场景为健康管理 / 销售 / 客服;每题标注作用域(含「另一位客户的记忆不得出现」的串记忆题)。
- **分阶段打分**:抽取召回与精确率(人工标注的应记事实)、更新正确率(该作废的有没有作废、不该改的有没有被改)、检索召回 @5、端到端判分;**同时记成本(token)与回答前记忆耗时**。
- **判分可靠性**:判分模型抽样人工复核(LoCoMo 判分被报告会接受大量错误答案)。
- 工具链放 `tools/eval/`,与 B-175 的检索评测共用运行器与报告格式。

### 6.8 权限、审计、安全

- 控制台 `/v1/memory` 维持 `console_only`;新增「按服务对象」筛选与操作沿用现有 RBAC。
- 审计:人工操作照旧;自动写入落汇总审计行 + 写入记录明细(§6.3 ⑤)。
- 投毒防护:写入威胁扫描保留;工具 / 网页 / 文件内容不直接成为用户事实;注入时继续标注为不可信;经验类(M9)必须人工审核后才可被召回。
- 隐私:服务对象记忆的整体开关(租户级)、按对象一键删除、导出;对外 API 删除入口见 §8。
- RLS:现有策略按 租户 × 用户;`subject` 不进 RLS(由应用层强制 + 测试锁定),RLS 真正 enforce 前改写回 worker 的扫描方式(B-168 遗留)。

## 8. 开放 API 设计

### 8.1 定位(待拍板 #4)

原定位(08-13)是「第三方只给 agent run」。终端用户的**查看与删除权**是 PIPL / GDPR 层面的硬需求,而终端用户只存在于第三方系统里 —— 只有第三方能代他们发起。推荐**一期只开「列出 + 删除」**(只读 + 删除,不开写),二期按需开「更正 / 写入」。这是定位变更,需拍板。

### 8.2 鉴权

- 沿用服务账号 key;新增能力 `memory:read` / `memory:delete`(二期 `memory:write`),**默认不授予**;作用范围 = 该 key 所属租户下、经对外 API 产生的终端用户(`subject_type=user` 且 `subject_id` 以 `ext:` 开头),不能触达员工账号的记忆。
- 能力模型与 B-175 的 key 授权方案(必拍 #4)统一设计,不各搞一套。

### 8.3 路由与约定

- **前缀不能以 `/v1/memory` 或 `/v1/users` 开头**:控制台锁定检查按字符串前缀匹配(`services/control-plane/tests/test_console_lockdown.py:158-188, 525`),`/v1/memories` 也会被 `/v1/memory` 前缀吃掉。推荐 `/v1/end-users/{user_id}/memories`。
- 按现有对外约定:`external_only()`、`tags=["external"]`、路径参数 NUL 拒绝、`{success, data, error}` 信封、limit / offset / total 分页;登记到 gate 与 lockdown 两张表。

### 8.4 端点(以推荐前缀示意)

| 方法 | 路径 | 期 | 说明 |
|---|---|---|---|
| GET | `/v1/end-users/{user_id}/memories` | 一 | 列出当前有效记忆;可按 `memory_subject`、`agent_code`、`kind` 过滤 |
| DELETE | `/v1/end-users/{user_id}/memories/{memory_id}` | 一 | 删除一条(软删 + 90 天物理删) |
| DELETE | `/v1/end-users/{user_id}/memories?memory_subject=…` | 一 | 删除该终端用户(或其某一服务对象)的全部记忆,含画像与待写回任务;返回异步任务 ID |
| POST | `/v1/end-users/{user_id}/memories/{memory_id}:correct` | 二 | 更正(走 supersede) |
| POST | `/v1/end-users/{user_id}/memories` | 二 | 写入一条(走比对 + 落库) |

- run 请求新增 `memory_subject`(§6.1),属于现有 runs 端点的字段扩展,与一期同发。
- 文档站:按风格指南新增「终端用户记忆」页,更新 `auth.md`(能力表)、`errors.md`、run 请求字段表。

5. 服务对象类记忆的默认保留上限 —— M6 前,结合合规意见。
6. 整理任务按智能体模型配置:修好还是删掉(#19)。
7. 经验记忆(M9)做不做、与技能自进化如何合并。
8. 实体字段 / 轻量关系表是否需要(只在评测显示多跳题明显吃亏时)。
9. 开放 API 二期(更正 / 写入)何时开。
10. 生产库实查后,哪些已开记忆的智能体需要迁移 / 回填作用域。

## 10. 风险

| 风险 | 缓解 |
|---|---|
| 新抽取提示词「宁多勿漏」导致噪音上升、召回变差 | M1 分阶段指标同时看精确率;整理与归档兜底;灰度到少数智能体先跑 |
| 作用域加维度后,老数据(无对象)与新数据混合 | 老数据视为「用户本人类」,行为不变;不做自动回填;健康类本来 0 条 |
| 调用方传错 / 漏传 `memory_subject` 导致串记忆 | `required` 模式下漏传不写对象类;对外文档醒目说明;串记忆回归用例为必过门槛 |
| 增量切片丢掉跨轮才完整的信息 | 切片带前 N 条上下文;M1 对照「整段重抽」与「增量」召回 |
| 读路径去掉模型调用后误注入增加 | 以评测定默认;复核与重排并行而非直接取消 |
| 健康数据的合规要求变化 | 对象记忆总开关 + 保留期上限 + 一键删除;开放 API 删除入口 |
| 与 B-175 公共件的先后依赖 | 计划 §0 约定:谁先开工谁建公共件,另一方复用;接口先定 |
| 评测成本 | LoCoMo 全量约 20–140 元(按模型,B-167 估算未实测),中文集规模可控;每批只跑受影响的子集 |
