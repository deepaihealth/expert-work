#### 3.1.2 方案

**名词**:**小段** = `knowledge_chunk` 里 `chunk_type='text'` 的一行(被嵌入、被检索的单位);**大段** = 它所属的父段(显示给模型的单位);**问题行** = 新表的一行(一个问题 + 它的向量 + 它的关键词索引 + 所属小段 id);**每千段** = 每 1,000 个实际发起了一次生成调用的小段。

**① 给哪些小段生成**

| 情况 | 处理 |
|---|---|
| 普通文字小段、图片描述段 | 生成 |
| 表格切出来的小段 | **生成**。真实问法集答案涉及表格的题 83 / 172(总计划 §3.4);评测单独报表格题 |
| 正文不到 30 token 的小段 | 跳过并计数。这条会跳过短的键值行、表单项、短问答行、幻灯片标题页 —— 小测和全量生成都**按内容类型报跳过了多少**,某一类被跳掉大半就回来改这条线 |
| 被人工停用的小段 | 跳过并计数 |
| 同一文档里文本完全相同的小段 | 只调一次(缓存键相同) |
| 大段(父段行) | 不生成 |

**② 怎么调**

- 每段最多 3 个问题;一段一次调用。K-11 首版一次写 60 段,29.4% 写成英文、重复 2.2%;约 15 家实现没有一家一次写多段(B-206 设计 `…b206-kb-retrieval-loss-driven-optimization-design.md:331,336`)。
- 输入只有:文档标题、标题路径、这一段的正文。**不带前后段。** 这样「文本没变的段不重付」是确定的:缓存键 = sha256(这段的检索文本哈希 + 提示词版本 + 模型 + 调用参数),不受邻居变动影响。
- 关思考、温度 0.2、输出上限 256 token。**关不掉思考的模型不用来生成**(输出费不可控):选到这种模型时直接报「不可用」。

**③ 提示词**(通用、零租户内容;质量小测后定稿,之后**不再按检索结果改**)

**语言怎么定**(现成的 `document_language` 只分中 / 英:有汉字或拉丁字母不足 50 个就算中文,`cp/knowledge/recognition/figure_describe.py:123-133` —— 日文、韩文、泰文、俄文都会被判成中文,不能用):

| 这段正文里占比最大的文字系统 | 提示词最后一句 |
|---|---|
| 有假名 | `Write every question in Japanese.` |
| 谚文 | `Write every question in Korean.` |
| 汉字(没有假名) | 用中文版提示词 |
| 其它(拉丁、西里尔、泰文、阿拉伯文…)或判不出 | `Write every question in the same language as <passage>; do not translate.` |

原则与 B-300 记忆设计一致:程序只在「一种文字对应一种语言」时点名语言,否则让模型跟随原文、不翻译。拉丁字母对应几十种语言,所以**不点名英文**。纯用标准库按字符的 Unicode 区段数,不加依赖。

英文版:

```text
You write search questions for one passage of a document. Write the questions a person
would type when they need exactly what <passage> states.

Rules:
- Each question must be answerable from <passage> alone.
- Each question stands on its own: name the thing asked about with the exact names and
  identifiers <passage> uses; no pronouns, no "this document", no "the passage".
- Phrase them the way people ask, not the way the document is written.
- No two questions with the same meaning.
- At most {count} questions, one per line, no numbering. Fewer is fine. If <passage> states
  nothing a person would ask about, output nothing.

Document: {title}
Section: {heading_path}
<passage>{body}</passage>

{language_rule}
```

中文版(汉字为主的段用):

```text
你为一份文档里的一段话写检索用的问题:一个人正好需要 <passage> 里写的内容时,会怎么问。

规则:
- 每个问题只靠 <passage> 就能回答。
- 每个问题单独看也看得懂:问的是谁、是什么,照 <passage> 里的名称和编号原样写出来;不用「它」「这个」「该文档」「上文」这类指代。
- 用人平时提问的说法,不要照抄文档的写法。
- 问题之间意思不重复。
- 最多 {count} 个问题,一行一个,不要编号。可以更少;<passage> 里没有值得问的内容就什么都不输出。

文档:{title}
章节:{heading_path}
<passage>{body}</passage>

全部用 <passage> 所用的中文(简体或繁体与原文一致)书写。
```

逐行检查(不合格的行丢掉,不重问;一行都不剩记失败):问题的主要文字系统与这段正文不同(这只查得出「写成了另一种文字」,同一种文字里的语言错靠小测人工看);短于 6 个字符或长于 200 个字符(按字符数,对中文偏松、对英文约 30 个词);以代词开头 —— **只有中文、英文有词表**,别的语言不做这项检查;与同段另一行规范化后相同。

**④ 存储与问题路的查询**

- 新表 `knowledge_chunk_question`(§3.1.3)。问题行对小段有外键、级联删除:小段被整批换掉、被人工改写、文档或库被删,问题行自动跟着没。
- 段落的 `content`、`embedding`、`content_tsv`、`content_hash` 都不改 —— 生成问题的代码路径不写 `knowledge_chunk`,这是结构保证。
- 每个库多**两路**召回:问题向量路、问题关键词路。向量路的查询形状:

```sql
-- 第 1 步:按距离取问题行(走问题表自己的 HNSW;LIMIT 按行算)
SELECT chunk_id, embedding <=> :q AS distance
FROM knowledge_chunk_question
WHERE tenant_id = :t AND kb_id = :kb AND embedding_model = :model
ORDER BY distance LIMIT :depth * 4;
-- 第 2 步:折回小段(每个 chunk_id 留最近的一条),再取小段行并过滤
SELECT … FROM knowledge_chunk
WHERE id = ANY(:chunk_ids) AND enabled AND document_id NOT IN (<停用的文档>);
```

  - 倍数 4:每段最多 3 个问题,要拿到 `depth` 个不同的小段至少要 3 倍行,再留余量。`hnsw.ef_search` 跟着 `LIMIT` 走(现有逻辑,封顶 1,000;`depth` 最小 50 → 200 行,在范围内)。
  - 「所属小段 / 文档被停用」是第 2 步的事后过滤,所以这一路拿到的小段可能不足 `depth` 个 —— 接受,记日志,不补取。
  - 折回后得到一个小段 id 的排名表,作为新的一路加进现有的加权 RRF(`orch/tools/knowledge.py:636,658`),权重 1.0。
  - 库设置的「向量相似度下限」同样用在这一路上。
- **问题关键词路**(用户 11-11 定:首版就要):
  - **索引与段落表今天的做法完全一样**:应用侧分词(jieba)后写 `tsvector`(`simple` 配置)+ GIN;打分是我们自己在 SQL 里算的「查询词覆盖率 × 逆文档频率」(`pers/knowledge/sql.py:139,648-663,3200-3258`)。段落表今天**没有用**任何 BM25 扩展(K-9 挂起后 `pg_textsearch` 没接进来),所以 PG 16 与 PG 17 上行为相同,问题表也不依赖扩展。
  - **只对中文、英文的问题建关键词索引。** 现有分词是 jieba(`pers/knowledge/text_search.py:18-28`),只对中文和纯 ASCII 英文切得对:假名、谚文、泰文、西里尔字母会被拆成单字,带变音符号的拉丁词会被拆断,停用词表只有中文(后两句是审计结论,未逐行核)。问题只有十几个字,单字命中算出来的分基本是噪声。所以写入时判一下:问题里的字母全是汉字或 ASCII 拉丁字母才写 `content_tsv`,否则留空 —— 留空的行关键词路自然查不到,向量路照常。这是存量分词的限制,4c 不把它复制到新的一路上;分词本身另立项(§3.1.6)。
  - 问题行的关键词列只含问题文字,不含文档标题(没有「标题命中打半价」那一档)。
  - **要动的那段 SQL**:现在的匹配与打分(`sql.py:666-726` 的 `_kb_hits`、`:3187-3289` 的 `keyword_search_scored`)直接写死 `KnowledgeChunkRow` 的 `id` / `content_tsv`。改成把「查哪张表的哪两列 + 范围条件」作为参数传进去,段落表是默认值;覆盖率、逆文档频率、短语加分、5 秒语句超时、强制自定义计划全部原样复用。问题路的「总行数」和「含这个词的行数」在**问题表自己的范围**里数,不与段落混算 —— 段落路的打分因此一个数都不变。
  - 取数与向量路相同:取 `depth × 4` 行问题 → 折回小段(同一小段留分最高的一条)→ 取小段行并做停用过滤(事后过滤,可能取不满)→ 作为又一路加进 RRF,权重 1.0。关键词路不看 `embedding_model`(换嵌入模型不影响它)。
  - 出错(超时、连接断)时与段落关键词路同样处理(K-22):丢掉这一路、继续、结果标 `keyword_degraded`。
  - 保证段落路没被改坏的三道闸:① 重构前后,段落关键词查询**编译出来的 SQL 文本逐字相同**(单测);② 同一批查询在评测库上结果逐条相同;③ 测试库上对比执行计划。
- **部分覆盖的偏差**:同一个库里只有一部分文档有问题时,有问题的文档多两路名次,会系统性地排到没问题的文档前面。评测在全覆盖下做;上线后界面在开关旁显示「N 份文档还没有生成问题,检索会偏向已生成的文档」。这是已知偏差,不是 bug(R5)。
- 融合之后的一切不变:去重、重排、门槛、折成父段看的都是小段自己的文本。给模型看的检索结果文本不变,不显示问题。结果对象的 `recall_source` 多一种取值 `question`,命中测试里显示是哪个问题命中的。
- **不改**每轮探针、库画像校准:它们量的是「段落向量离查询多近」。

**⑤ 没有重排分的时候不用问题路**

问题行是模型写的,可能把别的段拉进来;挡住它的是重排(看段落正文)和 4a 的门槛(看重排分)。这两样都不在时,问题路不能参与排序:

| 情况 | 什么时候知道 | 处理 |
|---|---|---|
| 这次检索的重排关着(库设置 / 调用方覆盖),或平台没配重排模型 | 召回之前 | 不查问题表 |
| 重排是不给分数的模型(聊天模型当重排用) | 召回之前(看重排器类型) | 不查问题表 |
| 重排调用失败 / 回空 | 重排之后 | 去掉问题路**重新融合**(排名表都还在内存里,纯计算),再走去重与后续步骤;结果标 `question_leg_dropped` |
| 重排只回来一半:正文视图失败,带标题视图有顺序、没有分数(`orch/tools/knowledge.py:1015-1026,1061-1071`);没有分数的段直接过门槛(`orch/tools/knowledge_threshold.py:55-62`) | 重排之后 | 从排好的顺序里**去掉只靠问题路进来的小段**,其余顺序不动;同样标 `question_leg_dropped`。这一格比今天略差:被去掉的段占过重排候选的名额。单测钉住 |

「问题路」指问题向量路和问题关键词路两路,规则对两路一起生效。效果:没有重排分的检索,结果里不会有只靠问题路进来的段。开了问题开关却没开重排的库,问题路不生效 —— 设置页要在开关旁提示(过线后的界面,§3.1.7)。

**⑥ 多少钱**

> | 出错方向 | 多显示、算错 | 没用上 |
>
> 选乙。E3(FAQ 相似问法)不共用这张表(用户已定,FAQ 设计 §9.2 第 4 条)。

#### 3.1.4 离线生成(证据阶段唯一的写入口)

一个只给评测用的脚本(`tools/eval/` 下),不进产品路径:读评测库里的小段 → 调「生成核心」(提示词 + 语言判定 + 调用 + 逐行检查,一个不依赖入库流程的纯模块,过线后入库流程直接用它)→ 嵌入问题 → 写问题表。原始回答缓存在评测自己的本地缓存里(同嵌入、重排缓存的做法,`tools/eval/kb_eval.py:198-199`),重跑不重付。评测库是单租户的本地库,不碰测试 / 生产。

#### 3.1.5 边界情况(证据阶段涉及的)

| 情况 | 处理 |
|---|---|
| 一个查询同时命中段落和它的问题 | 同一个小段 id 在两路里各有名次,RRF 相加 |
| 问题写错了(这段其实没答) | 这段被拉进候选,重排看正文;评测盯「混进其他文档的比例」 |
| 库开关关着但表里有行 | 不用 |
| 多库检索,有的库开、有的没开 | 各库各自决定加不加这两路 |
| 重排关着 / 失败 | 不用问题路(⑤) |
| 关键词路出错(K-22 降级) | 段落关键词路、问题关键词路各自降级,互不影响;结果标 `keyword_degraded` |
| 文档重新入库 | 小段换了 id,旧问题行随级联消失;评测阶段重跑脚本(走缓存) |

#### 3.1.6 不做什么

- 不改段落文字、不重嵌段落、不把问题拼进段落的检索文本(那是 K-11 的路)。
- 不把问题显示给智能体;不进重排文本。
- 不做假想文档 / 查询改写、文档摘要 / 分层摘要索引(B-206 设计 §7 已否,理由不变)。
- 不改分词:中文、英文以外的语言,段落的关键词路今天就切不对,这是存量问题,要改得连段落表一起重建索引,另立项。
- 不动 `ChunkType.QUESTION` 和可检索名单。**待办(不在本批)**:那份名单的注释写「白名单」,实现是「全部减去 PARENT」(`proto/knowledge.py:281-283`),以后谁往段落表里写新类型会自动变成可检索 —— 建议单独改成真正的白名单。

#### 3.2.2 方案

**① 图片的短编号**

- `kb_answer_figures` 开着时,`knowledge_search` 和 `knowledge_read` 把结果文本里的 `〔图 9f2c41d07ab3e655〕` 显示成 `〔图 D12@9f2c41〕`:文档号 + `@` + 编号的前 **6** 位。只改显示给模型的文本,库里的段落正文不动。
- 6 位固定,不做「撞了加长」。一份文档最多 50 张图,任意两张前 6 位相同的概率约万分之一。真撞了:核对时一个短编号对上两张图 → 不认。
- 工具元数据登记本次显示过的图:`meta["figures"] = [{"ref": "D12@9f2c41", "doc_seq": 12, "figure": "9f2c41d07ab3e655", "title": …, "filename": …, "caption": "描述的前 120 个字符"}]`。不带库名和库 / 文档的内部 id。
- **不在显示时核对图是不是真存着**(§0.4)。文档作者手打一行长得像图片块的字,会得到一个编号;被引用后取图 404,界面显示「图片不存在」。它不可能显示成别的图,也读不到别的文档的图(取图时按这份文档的前缀找)。
- 没有文档号的文档(4a 已说明应为 0 份):保持原样,不可引用。

**② 回答带图(E2-甲)**

- 模型在句子后面写 `[D12@9f2c41]`。与 4a 的 `[D12#7]` 走同一个核对函数,多认一种写法(`@` 后 6~16 位十六进制):
  - **认得** ⇔ 本轮(从最后一条真实用户消息起)有工具结果登记过这张图,且这个写法只对上一张。
  - 所有图片编号都从存下来的正文里拿掉。不认得的分两类计数:`figures_unknown`(哪一轮都没显示过)、`figures_earlier_turn`(上一轮显示过)。
  - 上限见 ④。
- **图不必被模型看过才能带。** 模型的依据是文字描述,用户看到的是原图。不能看图的智能体也能带图,这一步不花模型钱。风险:描述写错时图和话对不上(R6)。
- 提示文字(英文、通用;只在开关开着、且本次结果里有图时追加;不放具体编号的例子,同 4a 的规矩;token 数未量):

```text
A passage may hold figure blocks: a marker in 〔 〕 brackets that holds a handle, followed by a
description of the picture. To show a figure to the user, write its handle in square
brackets, exactly as shown, right after the sentence it illustrates. Only handles shown in
this turn's results work, at most 3 per turn.
```

  标记里固定的「图」字是入库时写进段落正文的存量写法(`figure_markup.py:37`),分段预览和存储都按它认图(`ChunkContent.tsx:19`、`figure_storage.py:237`);改它要重写已入库的段落,本批不改,等下一次本来就要重新入库图片块的改动(如 B-301 转正)一起换成与语言无关的写法。提示文字因此只说「〔 〕 里的标记」,不引用这个字。

- 流式预览:4a 的编号扣留多认这一种写法(同一个函数)。子智能体:回传文字里把图片编号插回去,元数据带 `knowledge_figures`,父级算作本轮显示过(同 4a)。配了输出格式 / 分块正文的消息:只给图片清单,不给位置(同 4a)。

**③ 模型看图(E2-乙)—— 只在 §5.2 第 0 步过了之后做**

| 智能体 | 怎么看 |
|---|---|
| 主模型能看图(路 A) | 新工具 `knowledge_figure(figures=[…])`。工具自己不返回图(协议不允许),只返回一行回执,并在元数据里登记「要看哪几张」。每一步组装提示词时,把本轮登记过的图挂进末尾那条隐藏消息 |
| 主模型不能看图、配了看图模型(路 B) | `ask_image` 多一种来源 `figure="D12@9f2c41"`。**不支持 `region`**(§0.4) |
| 两样都没有 | 没有这个工具;提示里不提看图 |

**授权放在哪**(解析器是进程级单例,不知道是谁在要,授权不能放在它那里)

| 步骤 | 谁做 | 查什么 |
|---|---|---|
| 工具调用时 | `knowledge_figure` / `ask_image(figure=…)` | 编号 → 文档号 → 文档(按本次运行的租户查)→ 文档所在的库在这个智能体**绑定的库**里 → 文档没被停用 → 这张图在这份文档的存储前缀下。通过才登记;登记的只有 `{ref, doc_seq, figure}`,**没有库和文档的内部 id** |
| **每一步挂图时**(路 A) | 组装隐藏消息的代码 | 只读**工具名是 `knowledge_figure`** 的工具结果的元数据;对每一条按文档号把上面那串检查重做一遍。通过才**签发**图片引用。每步最多 3 条,一次批量读 |
| 取字节 | 解析器 | 只取**本进程 2 分钟内签发过**的引用;别的一律当作不存在 |

- 图片引用是第三种前缀(与现有两种并列的兄弟,不改已有的解析函数):`expert_work://kbfigure/{租户}/{库}/{文档}/{16 位编号}`。解析器在控制面实现,注入现有的分派解析器;按「各代次里找这个编号」取。
- 引用只在两处生成:路 A 每步挂图时、路 B `ask_image(figure=…)` 调用时;生成即签发,随后在**同一进程**里立刻被解析,所以签发表放进程内存、2 分钟有效就够。引用不出现在任何存下来的消息里。
- 这道签发检查不依赖「把入口数全」:就算哪个入口漏进来一条格式正确的引用,没签发过也取不到。另把两处写成测试:用户请求里带这种前缀 → 422(`cp/api/runs.py:359-361` 现有校验);`ask_image` 的 `image_ref` 参数带这种前缀 → 拒绝。
- **不进进程内缓存**(`should_cache` 对这个前缀返回否):文档删了之后,下一步的挂图检查就不过。代价是每步每张图一次对象存储读取。
- 「本轮登记过哪些图」从本轮工具结果的元数据里现算(同 4a 的办法),天然按轮清零;依赖检查点里工具元数据完整保留(4a U8,同一个未验证项)。
- 工具说明(英文,初稿;不举图的种类,免得模型只在那几种图上要图):

```text
knowledge_figure — Look at the original picture of a figure named in knowledge results, by
its handle. Use it only when the answer needs a visual detail the figure's text description
does not give. At most 3 figures per turn; each stays in view for the rest of the turn.
```

- 两段文字的跨场景检验(各写一条会读错的反例,开发集里各放一题盯着):合同库 —— 「figure」被理解成附件 / 附表,模型去找不存在的编号;代码 / 接口文档库 —— 方括号被当成数组下标或链接语法,编号写进代码块里(代码块里的不认);设备手册库 —— 「visual detail」被理解成「凡是图都要看」,该读文字描述的也去要图(对照题上「要了图」≤ 20% 这条线管它)。

**④ 三个上限,各自的单位**

| 上限 | 单位 | 怎么保证 |
|---|---|---|
| 回答带图 ≤ 3 | **一轮**里所有助手消息合计的不同图片数 | 核对函数拿得到本轮之前的消息:已经带过的图计入;超出的编号拿掉,计 `figures_over_limit` |
| 路 A 看图 ≤ 3 | **一轮**里累计登记的不同图片数 | 工具在登记前数本轮已登记的;超出的拒绝并说明「本轮已看 3 张」。**没有窗口、不能换**。费用单位:每张图在登记之后**本轮的每一次主模型调用**里各付一次 |
| 路 B 看图 ≤ 3 | **一轮**里针对库图片的 `ask_image` 调用次数;因为不支持 `region`,一次调用 = 一次看图模型调用 | 工具数本轮已有的次数;第 4 次拒绝 |

**⑤ 计费(D6:记租户)**

- 工具元数据记看了几张;加一个计数器(路 A / 路 B、成功 / 被拒 / 取不到)。
- E2-甲不产生模型费用。

              "title": "文档标题", "filename": "原文件名", "caption": "描述的前 120 个字"}],

- `figure` 是图片内容的指纹:之后取到的图是不是当时那张,比它就知道。
- `figure_marks[].at` 与 4a 的 `marks[].at` 同口径;`content_len` 对不上时只给 `figures`。
- 表格里的行内图(没有描述):`caption` 取同一段显示文本里这张图的引用块的描述;找不到就为空。

| 位置 | 变化 |

**取图接口**

- 按**消息**授权:请求只给「哪个会话、哪条消息、第几张(0~2)」;服务端从存着的消息里读 `figures[n]`,再按租户查文档、在这份文档的前缀下找这个编号。键的每一段都来自记录。
- 两个平面各一个:控制台(能看这个会话的人)、对外(同一个 API key,会话属于这个 key 的租户与用户)。路径实现时按各自现有的会话路由命名(**未验证**)。
- **顺序**:会话与消息 → 文档(存在、未停用)→ 图(在存储里)全部查完,**再**比 `ETag`。任何一步不过都是 404,不区分原因。这样删了的图不会因为浏览器手里有 `ETag` 而继续显示。(现有的分段预览取图接口是先 304 后查图,记为待办,不在本批改。)
- 404 的情况:会话已删;消息已被取代(重新生成 / 编辑后的旧回答);消息里没有这一张;文档已删 / 已停用;重新入库后没有这张图了;同租户的另一个用户(对外平面)。
- 成本:每取一张要读一次消息(检查点)。一条回答最多 3 张;同一条消息的几张图各读一次,不做批量 —— 量大了再优化(R13)。
- **对接方须知**(写进对外文档):终端用户的浏览器没有 API key,不能直接调这个接口;对接方的后端要自己中转(拿自己的 key 取图,再给自己的前端)。响应头 `private, no-cache` + `ETag` + `nosniff` + `inline`。

> 取舍:签名链接还是代理接口?签名链接转发出去谁都能看、到期前收不回,存进消息的链接会过期,对象存储还得对公网可达(**未验证**)。代理接口每次都验身份,文档删了立刻 404。选代理接口:健康资料的图,「删了就立刻看不到」比省流量重要。

> 取舍:控制台看回答里的图,要不要知识库读权限?4a 对出处原文的口径是「要」。图如果也这样,没有库权限的同事打开对话会看到一排「无权查看」,而这张图是回答的一部分、终端用户本来就看得到。按消息授权(用户 11-11 已定);与 4a 口径不同。

#### 3.2.4 界面

- 回答气泡:按 `figure_marks`,在所在段落**后面**插图片块:缩略图(最宽 320 px,点开看大图)+「来自《文档标题》」+ 描述前 120 字。用登录态请求取字节(同 `ChunkContent.tsx:52` 的做法)。
- 取不到:显示说明文字 +「图片已不存在或已变更」。
- `content_len` 对不上:图片统一放在回答末尾。
- 调试台:本次登记了几张图、三类被丢掉的编号数、本轮看了几张。
- 老对话:无变化。

#### 3.2.5 边界情况

| 情况 | 处理 |
|---|---|
| 写了本轮没显示过的编号 | 丢掉;分 `figures_unknown` / `figures_earlier_turn` |
| 多抄了几位 | 是那张图完整编号的前缀就认;少于 6 位不认 |
| 一个编号对上两张图 | 不认 |
| 一轮里先后几条回答共写了 5 张 | 前 3 张留下 |
| 检索和读文档显示了同一张图 | 按 16 位编号合并 |
| 同一张图在两份文档里 | 两个短编号,各算各的 |
| 表格格子里的行内图 | 同样给短编号;`caption` 见 §3.2.3 |
| 回答后文档重新入库,图没变 | 编号不变(前提:JPEG 编码可复现,§3.2.1),照常取到 |
| 升级图像库后重新入库 | 编号可能变 → 老回答显示「已变更」。不会显示成别的图 |
| 重新入库后图换了 / 被过滤了 / 文档删了 | 404 → 说明文字 |
| 文档在一轮中途被删(路 A) | 下一步挂图检查不过,不再挂;隐藏消息里写一行「D12@9f2c41 已不可用」 |
| 父、子智能体看图能力不同 | 各用各的路;子智能体看过的图不传给父级,父级要看得自己要(计入父级自己的 3 张) |
| 假的图片块(§① ) | 有编号、可被引用、取图 404 |
| 用户问的就是 `[D12@9f2c41]` 这串字 | 会被拿掉;已知限制(同 4a) |
| 审批暂停后恢复、响应缓存命中、触发器投递等 | 同 4a 的处理 |

#### 3.2.6 扫描页、方向、与 B-301 的分工

- **扫描页**:页面上被识别成图片的区域已裁出来、有描述、有编号,E2 一视同仁。**整页原图没有存**(从存储键只有图片编号一种推出,未逐行核),「让模型看这一页扫描件」本批不做;要做需要原文件还在 + 段落在哪一页(4a 的 A2a)+ 按页现渲染,另立项。
- **方向**:入库时已按 EXIF 转正(`figure_images.py:87`);内容本身横着的图,E2 不处理。B-301 已定稿(PR #2078):方向判断放在看图工具里(问看图模型「图里文字正不正」,过线的模型才开);知识库**新入库**的扫描页在识别前用方向小模型转正,存量不处理;**文档里内嵌的横置图片明确不修**(B-301 设计的不修清单)。
- **与 B-301 的交界**:① 内嵌图片 B-301 不转,编号不受影响;只有重新入库的扫描件,页面转正后裁出的插图字节会变、编号会变,老回答里这类图显示「已变更」。② 库图片经 `ask_image(figure=…)` 时要不要先问方向,**两边都没写**(B-301 只列了上传图和工作区图片两种来源)—— 列为 G4 开工前要对的一项(§7.3 U22)。③ G4 与 B-301 的 PR 1 / PR 3 都改 `orch/tools/vision.py` 的 `ask_image`,后合的变基。④ §5.2 题集里的 6 道横置图题单独报数、不计入判据,结果交给 B-301。

#### 3.2.7 不做什么

- 不做图片向量 / 以图搜图。
- 不自动把图塞给模型。
- 不把图放进工具结果(协议不允许)。
- 不做整页扫描件原图、方向纠正、库图片的局部放大。
- 不给签名链接;不把图片字节放进消息。
- 不做每智能体 / 每库的开关。
- 不改入库:不重新描述、不改图片块写法、不重新入库。
- 不让模型自己写图片链接。
