#### 3.1.2 方案

**名词**(全文统一):

- **小段** = `knowledge_chunk` 里 `chunk_type='text'` 的一行,是被嵌入、被检索的单位(默认最多 400 token,`proto/knowledge.py:34`)。
- **大段** = 小段所属的父段,是检索结果显示给模型的单位。
- **问题行** = 新表 `knowledge_chunk_question` 的一行:一个生成的问题 + 它的向量 + 它的关键词索引 + 它所属的小段 id。
- **每千段** = 每 1,000 个**实际发起了一次生成调用**的小段(跳过的、走缓存的不算)。

**① 给哪些小段生成**

| 情况 | 处理 | 计数 |
|---|---|---|
| 普通文字小段 | 生成 | `generated` |
| 表格切出来的小段 | **生成**(不跳过)。真实问法集里答案涉及表格的题 83 / 172(总计划 §3.4),表格行正是「X 的价格是多少」这种问法对不上原文的地方;评测单独报表格题 | 同上 |
| 正文不到 30 token(本地分词)的小段 | 跳过(没什么可问,WeKnora 的注释说这种段会让模型照抄示例) | `skipped_short` |
| 被人工停用的小段 | 跳过 | `skipped_disabled` |
| 同一份文档里文本完全相同的小段(哈希相同) | 只调一次,结果各写一份 | `cached` |
| 图片描述段(引用块) | 当普通文字处理 | — |
| 大段(父段行) | 不生成(它不被检索) | — |

**② 每段几个、怎么调**

- 每段最多 3 个问题;模型给少了不补,一个合格的都没有记 `failed`。
- **一段一次调用。** K-11 首版一次让模型写 60 段,29.4% 写成了英文、重复 2.2%;调研约 15 家实现没有一家一次写多段(B-206 设计 `…b206-kb-retrieval-loss-driven-optimization-design.md:331,336`)。一段一次的代价见 ⑦,在可接受范围。
- 上下文:文档标题、这一段的标题路径、这一段的正文;另给同一大段里前一个 / 后一个小段各最多 200 个字符,明说「只用来理解,不要就它们出题」。
- 调用参数:关思考、温度 0.2、输出上限 256 token。参数和提示词版本都进缓存键。

**③ 提示词**(通用、零租户内容;初稿,质量小测后定稿)

语言由**代码**从这段正文判定(汉字简 / 繁、假名、谚文、拉丁词),不让模型猜 —— K-11 第二版用这个办法把「语言不对」从 18.6% 降到 0.1%(总计划 §3.3)。中文段用中文提示词,其它语言用英文提示词并在最后单列语言规则、写明语言名;判不出语言(全是数字)时按文档里占多数的语言。

英文版:

```text
You write search questions for one passage of a document. Write the questions a person
would type when they need exactly what <passage> states.

<context> (may be empty) only helps you understand <passage>; ask nothing about it.

Rules:
- Each question must be answerable from <passage> alone, substantially, not by a passing mention.
- Each question stands on its own: name the thing asked about with the exact names, models,
  codes or numbers <passage> uses; no pronouns, no "this document", no "the passage".
- Phrase them the way people ask, not the way the document is written.
- No question whose answer is a single word copied from the text. No two questions with
  the same meaning.
- At most {count} questions, one per line, no numbering. Fewer is fine. If <passage> states
  nothing a person would ask about, output nothing.

Document: {title}
Section: {heading_path}
<context>{before}</context>
<passage>{body}</passage>
<context>{after}</context>

Write every question in {language_name}.
```

中文版是它的对应翻译,语言规则写「全部用简体中文 / 繁體中文」。两份提示词单独放一个文件并整文件豁免全角标点的 lint 规则(K-11 踩过:ruff 会把全角标点折成半角)。

**逐行检查**(不合格的行丢掉,不重问;一行都不剩记 `failed`):语言与判定不符;短于 6 个字符或长于 80 个字符;以代词开头(这 / 该 / 它 / this / it / the document…,词表按语言);与同段另一行规范化后相同;带编号前缀的先去前缀再查。

**④ 存储与索引**

- 新表 `knowledge_chunk_question`(§3.1.3)。问题行的向量是**问题文字本身**的向量(不拼文档标题、标题路径),用入库时钉住的同一个嵌入模型;关键词索引同样只对问题文字建。
- 问题行和这份文档的小段在**同一个事务**里换(扩 `replace_chunks`,多收一个 `questions` 参数)。问题行对小段有外键、级联删除 —— 小段被整批换掉、被人工改写、文档或库被删,问题行自动跟着没,不会留下指向不存在段落的问题。
- 段落的 `content`、`embedding`、`content_tsv`、`content_hash` **都不改**。这不是约定,是结构:生成问题的代码路径不写 `knowledge_chunk`。

**⑤ 缓存与幂等**

- 模型的原始回答按文档缓存:`knowledge_parse_cache` 新增 `kind='chunk_questions'`,键 = sha256(这段的检索文本哈希 + 前后文摘要 + 提示词版本 + 模型 + 调用参数)。读出时按当前的逐行检查重新过一遍(检查规则改了,缓存跟着生效;这是 B-209 识别缓存的既有做法,B-209 设计 §5.5)。
- 同一份文档重新入库、改切段参数重切、崩溃重试:文本没变的小段直接读缓存,**不再付生成费**;问题的向量按「问题文字哈希 + 模型」在旧问题行里找得到就沿用,找不到才嵌入。
- 缓存跟文档走:删文档即删;同一个文件传成另一份文档会再付一次(B-209 已定的代价,为了删得干净)。

**⑥ 批次、并发、重试、取消**

- 在入库的「嵌入」阶段里做,不新增入库阶段(新增阶段值会让旧版前端 / 滚动发布中的旧实例读到不认识的值)。
- 并发按模型限(与识别同一套按厂商限并发的机制);429 / 5xx / 超时指数退避,最多 3 次;其它 4xx 不重试。
- 每一批调用之前查一次取消栅栏(B-222 §8 的 `guard()`),取消后最多再花已经在途的那几次调用。
- **单段失败不让整份文档失败**:记 `failed`,文档照常 `ready`,文档行上显示「问题:已生成 N · 失败 M」;之后可「补生成」(只处理失败和没生成的,走缓存)。
- 用量:每次调用按厂商返回的 `usage` 写一行 `knowledge_ingest`(复用 `IngestUsageRecorder`),问题的嵌入走现有的 `billed_embeddings`;都进这次入库的「实际花费」。

**⑦ 模型、谁付钱、多少钱**

- 模型:平台辅助模型(与库画像同一个选择,`cp/knowledge/profile_refresh.py:104`);不让租户选。它在测试 / 生产上现在指向哪个模型**未验证**(§7.3)。下面按 `qwen3.7-flash` 的价目举例。
- 付钱:租户。入库预估多一行 `questions`(§3.1.3),与其它行一起确认。
- 每千段费用(价目取自 `mig/0169…:52-55`;token 数是按 o200k 的**估算**,未在厂商分词下量过):

| | 每次调用输入 | 每次输出 | 问题嵌入 | 每千段合计 |
|---|---|---|---|---|
| 常见 | 约 750 token(提示词约 250 + 标题路径约 30 + 正文均值约 230 + 前后文约 240)→ ¥0.15 | 约 75 token → ¥0.06 | 3 × 约 25 token → ¥0.04 | **约 ¥0.25** |
| 上限 | 1,100 token → ¥0.22 | 256 token(输出上限)→ ¥0.20 | 3 × 60 token → ¥0.09 | **约 ¥0.52** |

  正文均值 230 的来历:总计划 §3.2 的免费计数,597 份 45,293 段、输入约 1,050 万 token。
- 评测语料全量(45,775 段):约 ¥11(上限约 ¥24)。对比 K-11 第二版:生成 ¥3.36 + 全部段落重新嵌入 ¥7.00;E1 不重嵌段落。
- 预估怎么算:输入 = 本地数出来的 token × 模型换算系数(与向量化同一套);输出按「每段 3 个 × 目录里的每问题均值」,目录没填用平台缺省并标「按通用均值估」(B-222 §4.2 的既有机制,`proto/model_catalog.py:212-224` 加两个可选字段)。

**⑧ 检索怎么用问题行**

只有同时满足三条才用:平台开关开、这个库的开关开、问题行的 `embedding_model` 等于这个库当前的向量模型。任何一条不满足,检索的 SQL 和结果与今天**逐字节相同**(不查新表)。

- 每个库多两路召回:**问题向量路**(问题行按与查询向量的距离排)、**问题关键词路**(问题行的关键词索引)。每路取到的问题行折成所属小段(同一小段多个问题命中只留最好的名次),得到一个小段 id 的排名表,作为新的一路加进现有的加权 RRF(`orch/tools/knowledge.py:636,647,658`)。权重初值 1.0,与现有两路相同;评测里另试 0.5(§5.1)。
- 所属小段被停用、所属文档被停用的问题行不算(与段落召回同一口径,`pers/knowledge/sql.py:560-578`)。
- 库设置里的「向量相似度下限」同样用在问题向量路上(问题与问题之间的相似度普遍比问题与段落之间高,所以这个下限对问题路偏松;真正把关的仍是重排)。
- **融合之后的一切都不变**:去重、重排、门槛、折成父段看的都是小段自己的文本。一个只靠问题行进了候选的小段,要在重排里凭自己的正文站得住才会排到前面。
- 重排文本**默认不加问题**。「把这段的问题拼进重排文本」(WeKnora 的做法)只作为评测的一个对照臂;它会改变重排分的刻度,要上就得连 4a T3 的门槛一起重新标定。
- 结果对象上的 `recall_source` 多一种取值 `question`;命中测试和检索记录里显示「由哪个问题命中」(问题文字)。给模型看的检索结果文本**不变**,不显示问题。
- **不改**的两处直接调存储层的地方:每轮探针、库画像校准(§3.1.1 最后一行)—— 它们量的是「段落向量离查询多近」,问题行进去会改变已校准的阈值。

#### 3.1.4 已有的库:补生成(付费,先预估再确认)

- 入口:库开关打开后,文档页工具条「为已有文档生成问题」;文档行上「补生成」。
- 不重新解析、不重新切段、不动段落:读这份文档现有的小段 → 读缓存 → 没命中的才调模型 → 嵌入问题 → 只换这份文档的问题行(带代次栅栏,文档必须是 `ready` 且没有待处理的新版本,否则拒绝,同人工改段的 `document_busy`)。
- 预估:走 B-222 的同一套状态与确认(新的 `EstimateOrigin`:`generate_questions`),但这个来源**只有一行 `questions` + 问题嵌入**,撤回时什么都不用恢复(文档一直在服务)。预估本身不调模型:数小段、数缓存命中、算 token。
- 「不多花钱」的结构保证:补生成的执行器**不接**识别、看图客户端,嵌入客户端只允许嵌入问题文字;段落表在这条路径上只读。预估时数到的「缓存命中」在执行时没命中(缓存被清)→ 这一段跳过并计数,不静默多付;实际花费高出确认金额的规则沿用 B-222 §6.3(开工复核:模型变了一律退回待确认;合计涨超 20% 且至少 ¥0.01 退回)。
- 生产目前 0 个知识库(总计划主线表「发生产」行),补生成只涉及测试环境和以后的库。

#### 3.1.5 边界情况

| 情况 | 处理 |
|---|---|
| 重新入库,切段参数没变、文本没变 | 段落向量沿用(现有);问题走缓存、向量沿用;生成费 0 |
| 重新入库,文本变了的段 | 这些段重新生成(预估里算进去) |
| 改了切段参数 | 段落文本大多变了 → 大多重新生成;预估如实算 |
| 生成中途被取消 | 已生成的进了缓存;问题行没写(与段落同事务);下次不重付 |
| 模型回了空 / 全部不合格 | 记 `failed`;文档照常可用 |
| 平台辅助模型没配 / 没有价目行 | 没配:不生成,预估行标「不可用,不收费」;没有价目:标「未定价,暂不计费」(B-222 既有口径) |
| 换了平台辅助模型或提示词版本 | 缓存键变了 → 已有问题行继续用(不强制重生成);新入库的用新的。**同一个库里新旧问题并存**,行上有 `prompt_version` 可查 |
| 换了嵌入模型 | 重建时问题行一并重嵌;没重嵌完的自动不参与检索 |
| 一个查询同时命中段落和它的问题 | 同一个小段 id 在几路里各有名次,RRF 相加(这正是想要的) |
| 问题写错了(问的东西这段其实没答) | 这段会被拉进候选,但重排看的是段落正文;评测的「混进其他文档的比例」盯这个 |
| 问题里出现了文档里的敏感内容 | 问题是从段落文字来的,不比段落多暴露什么;只存在租户自己的表里,不进提示词,不给模型看 |
| 库开关关着但表里有行 | 不用;设置页显示「已有 N 个问题未启用」 |
| 多库检索,有的库开、有的库没开 | 各库各自决定加不加那两路 |

#### 3.1.6 不做什么

- 不改段落文字、不重嵌段落、不把问题拼进段落的检索文本(那就是 K-11 的路)。
- 不把问题显示给智能体(检索结果文本不变)。
- 不让租户自定义提示词、个数、模型。
- 不做假想文档 / 查询改写(B-206 设计 §7 已否:收益不稳、延迟 3 倍,对强检索器和内部术语有害)。
- 不做文档摘要 / 分层摘要索引(同上 §7:Anthropic 原话「收益很有限 / 效果低」;RAPTOR 同条件对比只 +2~5)。
- 不做「过期标记 + 一键重生成单段」的界面(B-206 设计 §6 设想过):段落一改,它的问题行就随级联没了,只显示「待生成」计数。
- 不做问题的人工编辑(那是 E3 的相似问法)。

#### 3.1.7 发布窗口

PR 顺序见 §6。两个要点:

1. 存储与检索的 PR(E1-b)合进去时表是空的、两个开关都关,检索不查新表 —— 与改动前逐字节相同。
2. 生成的 PR(E1-c)**后端与管理端一起合**:只合后端,预估里会出现旧前端不认识的 `questions` 行(旧前端遇到不认识的分项怎么显示**未验证**)。平台开关在 E1-c 合完、真栈用例过了之后才在测试环境打开;生产等 §5.1 过线。

#### 3.2.2 方案

**① 图片的短编号**

- 开关开着时,`knowledge_search` 和 `knowledge_read` 把结果文本里的 `〔图 9f2c41d07ab3e655〕` 显示成 `〔图 D12@9f2c〕`:文档号 + `@` + 图片编号的前 4 位。**只改显示给模型的文本,库里存的段落正文不动。**
- 为什么要短:模型抄 16 位十六进制串会抄错(`…document-figures-design.md:353` 的实证:三次错三次)。4 位在一份文档最多 50 张图里撞上的概率约 2%;撞上时这两张图都按 5 位显示(逐位加长到不撞为止)。
- 工具元数据里登记本次显示过的图:`meta["figures"] = [{"ref": "D12@9f2c", "doc_seq": 12, "figure": "9f2c41d07ab3e655", "title": …, "filename": …, "caption": "描述的前 120 个字"}]`。不带库名、不带任何内部 id(同 4a M8)。
- 只有「确实是这份文档存着的图」才给短编号(沿用 `confirmed_figure_ids` 的检查:文档作者自己在正文里打一行长得像图片块的字,不会变成一张图)。
- 没有文档号的文档(4a 已说明应为 0 份):保持原样显示,不可引用。
- 开关关着:显示文本与今天逐字节相同。

**② 回答带图(E2-甲)**

- 模型在需要配图的句子后面写 `[D12@9f2c]`。与 4a 的出处编号 `[D12#7]` 用同一套规则处理,只是多认一种写法(`@` 后面是 4~16 位十六进制):
  - **认得** ⇔ 本轮(从最后一条真实用户消息起)有工具结果登记过这张图。指向那张图。
  - 所有图片编号都从存下来的正文里拿掉(认得的记位置,不认得的丢掉并计数)。
  - 一条回答最多 3 张不同的图(D6);第 4 张起的编号拿掉、计入 `dropped.over_limit`。同一张图写了两次,只在第一次的位置显示。
- **图不必被模型看过才能带。** 模型的依据是文字描述,用户看到的是原图。这样不能看图的智能体也能带图,而且这一步不花任何模型钱(只多几个输出 token)。风险:描述写错时图和话对不上 —— 用户能看到原图本身就是纠错(记 R6)。
- 提示文字(英文、通用;只在开关开着、且本次结果里有图时追加到结果提示后面):

```text
A passage may hold figure blocks marked like 〔图 D12@9f2c〕 followed by a description of the
picture. To show a figure to the user, write its handle in square brackets, e.g. [D12@9f2c],
right after the sentence it illustrates. Only handles shown in this turn's results work, at
most 3 per answer; the system places the picture, so do not describe the bracket itself.
```

  (`〔图` 是入库时平台写进段落的标签,`figure_markup.py:37`,不是租户内容。token 数未量。)
- 流式预览:4a 的编号扣留规则多认这一种写法(同一个函数,预览与权威正文仍逐字一致)。
- 子智能体:与 4a 相同 —— 回传给父级的文字里把图片编号插回去,工具元数据带上 `knowledge_figures`,父级把它们算作本轮显示过的图。
- 配了输出格式的智能体、正文是分块列表的消息:照常拿掉编号、记图片清单,不给位置(同 4a)。

**③ 模型看图(E2-乙)—— 只在 §5.2 第 0 步过了之后做**

| 智能体 | 怎么看 | 上限 |
|---|---|---|
| 主模型能看图(路 A) | 新工具 `knowledge_figure(figures=["D12@9f2c", …])`。工具结果是一行文字回执(「已附上 N 张」/ 哪张取不到);图片引用登记在工具元数据里。组装本步提示词时,把**本轮**这些工具结果登记过的图(最近 3 张)挂进末尾那条隐藏消息,与已有的文档页并列、各有各的名额 | 每次调用最多 3 张;每轮同时在看的最多 3 张 |
| 主模型不能看图、配了看图模型(路 B) | `ask_image` 多一种来源:`figure="D12@9f2c"` + `question`。图由宿主取来交给看图模型;`region` 照常可用(宿主按原像素裁,同上传图) | 每轮最多 3 次针对库图片的 `ask_image`;第 4 次起工具拒绝并说明 |
| 两样都没有 | 没有这个工具;结果提示里不提「可以看图」 | — |

- **取图的权限**:编号 → 文档号 → 文档(按租户查)→ 文档所在的库必须在这个智能体绑定的库里 → 文档没被停用 → 这张图是这份文档存着的、且文档当前的段落里还提到它(同 `cp/api/knowledge_figures.py:105-123` 的口径)。不要求「本轮显示过」:智能体本来就能检索到这些段落的文字,看图不扩大它能碰到的资料范围。
- **图片引用**:新增第三种前缀(与现有两种并列的兄弟,不改已有的两个解析函数):`expert_work://kbfigure/{租户}/{库}/{文档}/{16 位编号}`。解析器在控制面实现(图的存放规则在控制面的 `figure_storage.py`,编排层不反向依赖它),注入到现有的分派解析器里。解析时再校验一次租户;按「当前代次 → 别的代次」找对象。这种引用内容寻址(编号就是内容哈希),可以进解析缓存。
- **不用状态通道**:本轮看过哪些图,从本轮工具结果的元数据里现算(与 4a 算「本轮显示过哪些段」同一个办法)。好处:天然按轮清零,下一轮不会继续为上一轮的图付 token;不用动工具状态白名单。代价:依赖检查点里工具元数据完整保留(4a U8,同一个未验证项)。
- **不自动附图**(§0.2 第 3 条)。工具说明(英文,初稿):

```text
knowledge_figure — Look at the original picture of a figure named in knowledge results
(a handle like D12@9f2c). Use it only when the figure's text description is not enough to
answer: reading a value off a chart, how parts of a diagram connect, small print. Up to 3
figures per turn.
```

- **大小**:存的图长边最多 2,000 px、JPEG;原样交给模型(各厂商自己会降采样,B-266 实测「不论图多大都压到约 1,400 输入 token」,`…b266-region-zoom.md:18`)。要看小字用 `region`(路 B)—— 路 A 的局部放大本批不做(§3.2.7)。

**④ 计费(D6:记租户)**

- 路 A:图是主模型这一步的输入,用量随主模型调用记在这个智能体、这个租户名下(现有的用量中间件);路 B:看图模型的调用由 `ask_image` 记(`vision.py:516-523`)。两条路**都不需要新的记账代码、不需要新的用量种类** —— 它们就是租户自己的智能体的模型调用,本来就计入账单。
- 为了能回答「看图花了多少」:工具元数据记 `figures_viewed`(张数);加一个计数器(按路 A / 路 B、成功 / 取不到)。用量页不加新行。
- E2-甲不产生模型费用。取图接口的流量与对象存储读取是平台成本,不计费。

**⑤ 每轮多花多少、慢多少**

| | 多花 | 慢多少 |
|---|---|---|
| E2-甲(带图) | 提示文字约 70 token(只在结果里有图时);每张图的编号约 6 个输出 token;显示改写后每张图比原来的 16 位串**少**几个输入 token | 核对是内存里的正则 |
| E2-乙 路 A | 每张图在本轮后续**每一步**的输入里各算一次:估算口径 1,300 token / 张(`tokens.py`),实测口径约 1,400(B-266)~ 2,700(B-222 校准时看图描述调用的输入最大值,`proto/model_catalog.py:786-788`,含提示词)。看 3 张、之后还有 2 步 → 约 8k~16k 输入 token | 每步多一次取图(有缓存)+ 模型处理图片的时间;未量 |
| E2-乙 路 B | 每次 `ask_image` 一次看图模型调用;入库描述同量级的调用实测每张 2.1~4.8 秒、每千张 ¥0.3~2.5(B-209 设计 §4.1,那是描述任务,问答任务**未量**) | 每次 2~5 秒量级(同上,未量) |

具体金额取决于智能体自己配的模型,不在平台价目里固定;§5.2 的评测报「每题看了几张、多了多少 token、多了多少秒」。

#### 3.2.3 数据模型 / 协议

不加表、不加列、不要迁移。

**存储**:在 4a 的 `additional_kwargs["citations"]` 里加两个可选键(4a 的 `version` 仍是 1,只增不改):

```json
{"version": 1, "content_len": 412,
 "sources": [], "marks": [],
 "figures": [
   {"ref": "D12@9f2c", "doc_seq": 12, "figure": "9f2c41d07ab3e655",
    "title": "文档标题", "filename": "原文件名", "caption": "描述的前 120 个字"}
 ],
 "figure_marks": [{"at": 120, "figure": 0}],
 "dropped": {"unknown": 0, "earlier_turn": 0, "figures_unknown": 0, "figures_over_limit": 0}}
```

- `figure` 就是图片内容的指纹(字节哈希的前 16 位):之后取到的图是不是当时那张,比这个值就知道,不用另加指纹字段。
- `figure_marks[].at` 与 4a 的 `marks[].at` 同一口径(干净正文里第几个字符之后,按码点);`content_len` 对不上时只给 `figures`、不给 `figure_marks`。
- 一条消息只有图没有出处时,`citations` 键也出现(`sources` 为空数组)。4a 写的是「既没有认得的编号、也没有丢过编号时键不出现」,这里把「编号」扩成「出处编号或图片编号」。

| 位置 | 变化 |

| 所有正文 | 不变,不出现图片编号 |
| `citations.figures` / `citations.figure_marks`(`updates` 帧、items、`/messages`,随 4a 的 `citations` 一起) | 新增可选字段 |
| 工具结果元数据 `figures` / `knowledge_figures` / `figures_viewed` | 新增可选字段 |
| 工具结果**文本**里的 `〔图 …〕` | 开关开着时从 16 位串变成短编号 —— 对接方如果解析过这段文本会受影响(可能性很低,记入更新记录) |
| 取图 | 新增一个只读接口(下) |
| 事件种类、请求参数 | 不变 |

**取图接口(给图片字节)**

- 按**消息**授权,不按知识库授权:「能看到这条回答的人,就能看到这条回答带的图」。请求只给「哪个会话、哪条消息、第几张(0~2)」;服务端从**存着的消息**里读出 `figures[n]`,再按租户查文档、拼对象键 —— 键里的每一段都来自记录,不来自请求。
- 两个平面各一个:控制台平面(登录态,能看这个会话的人)、对外平面(同一个 API key,会话属于这个 key 的租户与用户)。具体路径按各自现有的会话路由命名,实现时定(**未验证**现有路由前缀)。
- 取不到的情况一律 404、不区分原因:文档已删 / 已停用;重新入库后没有这张图了(编号对不上);消息里没有这一张。
- 响应头同现有取图接口:`private, no-cache` + `ETag`(编号)+ `nosniff` + `inline`。每次都回来校验,删掉的文档的图不会从缓存里继续显示。

> 取舍:给对接方签名链接,还是代理接口?
>
> | | 签名链接(对象存储直出) | 代理接口(本文) |
> |---|---|---|
> | 鉴权 | 链接本身就是凭证,转发出去谁都能看,到期前收不回 | 每次请求都验 key 和会话归属 |
> | 文档删了之后 | 链接到期前可能还能取(对象删了才失效) | 立刻 404 |
> | 有效期 | 要定一个;存在消息里的链接会过期,历史对话的图就坏了 | 没有有效期问题;图在就能取 |
> | 部署 | 对象存储要对公网可达;测试 / 生产的对象存储是否对外**未验证** | 走现有 API 入口 |
> | 代价 | 平台不过流量 | 图片流量过控制面(每张最多约 1 MB 量级;大小**未量**) |
>
> 选代理接口。健康资料的图,「删了就立刻看不到」比省流量重要。

> 取舍:控制台看回答里的图,要不要知识库读权限?
> 4a 定的是:看出处的**原文段落**要知识库读权限,没有的人只看到快照。图如果也这样,没有库权限的同事打开一条对话会看到一堆「无权查看」的框,而这张图是回答的一部分、终端用户本来就看得到。本文建议按消息授权(同对外平面);这是与 4a 口径不同的地方,待拍板(§7.2 第 5 条)。

#### 3.2.4 界面

- 回答气泡:按 `figure_marks` 的位置,在所在段落**后面**插一个图片块(不插在句子中间):缩略图(最宽 320 px,点开看大图)+ 一行说明「来自《文档标题》」+ 描述的前 120 字。取图用登录态请求拿到字节再显示(同分段预览现有的做法,`ChunkContent.tsx:52`)。
- 取不到图:显示说明文字 +「图片已不存在或已变更」,不显示破图。
- `content_len` 对不上:图片统一放在回答末尾。
- 调试台:工具结果旁显示本次登记了几张图、被丢掉的图片编号数(两类分开)、本轮看了几张。
- 老对话没有 `figures`:无任何变化。

#### 3.2.5 边界情况

| 情况 | 处理 |
|---|---|
| 模型写了本轮没显示过的图片编号 | 丢掉,计 `figures_unknown`(上一轮显示过的也算这类 —— 要带就重新检索 / 读) |
| 模型把 4 位编号多抄 / 少抄了几位 | 多抄:只要是那张图完整编号的前缀就认;少于 4 位不认 |
| 两张图前 4 位相同 | 显示时已加长;模型仍写 4 位而匹配到两张 → 不认,计 `figures_unknown` |
| 一条回答写了 5 张 | 留前 3 张 |
| 检索和读文档显示了同一张图 | 按 16 位编号合并,算一张 |
| 同一张图出现在两份文档里 | 两个不同的短编号(文档号不同),各算各的 |
| 回答之后文档重新入库,图没变 | 编号不变,照常取到(按文档的各代次找) |
| 重新入库后图变了 / 被过滤掉了 / 文档删了 | 404 → 界面显示说明文字和提示;**不会显示成另一张图**(编号就是内容哈希) |
| 图片描述是在 B-209 PR-2 之前入库的文档 | 没有图片块,自然没有编号;要有得「补识别」(已有功能,付费) |
| 平台没开图片描述 | 同上 |
| 路 A:要看的图取不到 | 回执里说哪张取不到;隐藏消息里不挂它 |
| 路 A:本轮先后要了 5 张 | 只有最近 3 张带像素,更早的换成一行可见文字(「D12@9f2c 已退出本轮视野,需要再调一次」)—— 同现有文档页「退役是替换不是删除」的做法 |
| 路 B:看图模型超时 / 拒答 | 现有 `ask_image` 的错误与建议原样适用 |
| 审批暂停后恢复 | 仍在同一轮,之前登记的图仍算(同 4a) |
| 响应缓存命中 | 存的是模型原始回答,命中后重新核对(同 4a U7) |
| 用户问的就是 `[D12@9f2c]` 这串字 | 会被拿掉;已知限制(同 4a) |
| 触发器投递、长期记忆、质量巡检等读正文的地方 | 正文是干净的,不用改(4a §3.1.3 的表) |

#### 3.2.6 扫描页、方向、与 B-301 的分工

- **扫描页**:页面上被识别成图片的区域已经裁出来、有描述、有编号,E2 对它们与普通图片一视同仁。**整页原图没有存**,所以「让模型看这一页扫描件本身」本批做不了。要做需要:原文件还在(`has_content`)+ 知道段落在哪一页(4a 的 A2a)+ 按页现渲染 —— 排在 4a 页码落地之后另立项。§5.2 第 0 步会数「答案在扫描页里、识别文字没答上」的题占多少,作为要不要立项的依据。
- **方向**:入库规整时已按 EXIF 方向转正(`figure_images.py:87`)。没有方向标记、内容本身是横的 / 倒的图,E2 **不处理**,原样给模型、原样给用户。这是 B-301 的范围(ROADMAP B-301 行:第 1 步「上传时转正…(知识库扫描件和文档内图片先数再定)」)。
- **对 B-301 的依赖与提醒**(不重复做,只写清接口):
  1. E2 不引入任何方向判断。B-301 定了方案之后,知识库图片在哪一步转(入库规整时 / 取图时 / 交给模型前)由 B-301 设计定。
  2. 如果 B-301 选「入库规整时转」:图片字节变了 → 编号变了 → 已有回答里的图在重新入库后显示「已变更」;描述缓存的键里含规整参数(`figure_images.py:36-38`),会重新付描述费。请 B-301 设计把这两点算进去。
  3. 如果选「取图 / 交给模型时按记录的角度转」:编号不变,E2 的取图接口和解析器各加一步旋转即可。从 E2 的角度更省事,但选择权在 B-301。
  4. §5.2 的题集里放 6 道「图是横着的」的题,**单独报数、不计入过线判据**,结果交给 B-301。

#### 3.2.7 不做什么

- 不做图片向量 / 以图搜图 / 按图片内容召回(总计划「触发」项)。
- 不自动把图塞给模型;不在每次检索后预先看图。
- 不把图放进工具结果(协议不允许,§3.2.1)。
- 不做整页扫描件原图、不做方向纠正(§3.2.6)。
- 路 A 不做库图片的局部放大(路 B 有 `region`);等真实使用里出现「主模型看不清小字」再加。
- 不给对接方签名链接;不把图片字节或 base64 放进消息。
- 不做每个智能体 / 每个库的开关:只有平台开关。看图花的是智能体自己的模型额度,与它调 `read_page` 看文档页是同一性质。
- 不改入库:不重新描述、不改图片块的写法、不重新入库。
- 不让模型自己写图片链接或 Markdown 图片语法(管理端的回答渲染本来就禁原始 HTML,4a §3.1.1)。

**步骤与花费上限**(合计上限 **¥60**,超了停下来报):

| 步 | 做什么 | 花费 |

**指标**:

| 指标 | 定义 |
|---|---|

| 排名分 | 带重排 MRR@10,按大段 |

**过线**(验收半,一次;四条全满足才算过):

1. 交付命中:可归因的变好 ≥ 2 题,且变坏 ≤ 1 题。

### 5.2 E2:「答案在图里」合成题集

**题集**(全部合成:自己画的图、自己写的文档,不含客户内容)

| 集 | 题数 | 用途 |
|---|---|---|
| 开发集(随机种子甲) | 30 | 调工具说明、提示文字;可以反复看 |
| 验收集(随机种子乙,另一批图和文档) | 60 + 20 | 60 道「答案只在图里」(六类各 10:柱 / 线图读数、流程图的连接关系、带标注的示意图、含文字的截图、表格截图、照片上的小字);20 道对照题「答案在图旁边的正文里」。最后只跑一次 |
| 横置图 | 6 | 单独报数,交给 B-301,不计入判据 |
| 扫描页 | 10 | 答案在整页扫描件里;只用于第 0 步数数 |

文档形态覆盖 PDF、Word、幻灯片各三分之一。每题标明答案在哪张图(图的内容哈希),判分用现有的按断言判 + 3 票(`tools/eval/kb_agent_judge.py`)。答题分两种智能体配置各跑一遍:主模型能看图(路 A)、主模型不能看图 + 看图模型(路 B)。

**第 0 步(总计划的前置条件;先做,约 ¥10 以内,开跑前报价)**:E2 全关,只靠现有的文字描述,跑验收集的 60 + 20 + 10 道。事先定的分流:

| 60 道图题只靠描述的正确率 | 接下来 |
|---|---|
| ≥ 85% | **E2-乙(模型看图)不做**,把数字报给用户;E2-甲(带图)照做 —— 它不靠这个数 |
| < 85% | E2-乙继续;按六类分别报,哪几类低就是看图要治的 |

第 0 步动用了验收集 —— 但它量的是**改动前**的基线(同一批题、同一把尺子,就是后面要对比的那一臂),不用它调任何东西,不算偷看。

**指标与过线**(E2-乙;验收集,每题跑两次,按题次合计并给逐题配对):

| 项 | 判据 |
|---|---|
| 图题正确率 | 比第 0 步的基线高 ≥ 15 个百分点,且逐题配对变好多于变坏、符号检验 p < 0.05。两种智能体配置**各自**要过;只有一种过就只开那一种 |
| 对照题(答案在正文) | 变坏 ≤ 1 题次;这些题上「要了图」的题次 ≤ 20%(不该看的时候少看) |
| 每轮看图张数 | 任何一题次不超过 3(硬线,程序保证,评测复核) |
| 花费与延迟 | 如实报:每题次多的输入 token、多的秒数;不设线,连同正确率一起给用户定值不值 |

**E2-甲(带图)的验收**(不靠模型看图):

| 项 | 判据 |
|---|---|
| 假图片编号进入 `figures` | **0**(硬线) |
| 一条回答超过 3 张 | **0**(硬线) |
| 带了图的回答里,图确实是答案所在的那张 | ≥ 80%(起点值,没有基线可依;要改请在看结果之前改) |
| 图题里带了图的比例 | 如实报,不设线(带不带是模型的选择) |
| 存下来的正文 / 预览 / 对外四个出口 | 不含图片编号(单测 + 真栈) |

**必须变红的对照**:

| 对照 | 做法 | 必须看到 |
|---|---|---|
| 换图 | 解析器把每张图换成**另一道题**的图(编号、描述不变) | 「只靠描述答不对」的那些题,正确率回落到不高于第 0 步的水平;带图正确率(图是答案那张)降到 5% 以下 |
| 空白图 | 解析器一律返回同尺寸的白图 | 同上第一条 |
| 注入假编号 | 给每条原始回答末尾加 3 个本轮没显示过的图片编号,重跑核对函数(离线,不调模型) | `figures_unknown` 正好多 3 × 题次;进入 `figures` 的为 0 |
| 注入第 4、5 张 | 给已带 3 张图的回答再加 2 个认得的编号 | `figures_over_limit` 多 2;`figures` 仍是 3 张 |

**只能在真栈上验的**(§6 的用例):隐藏消息里图确实挂上了、下一轮不再挂;取图接口的权限与 404;流式预览里看不到图片编号;子智能体回传后父级能带图;删文档 / 重新入库后老回答的图。

**花费估算方法**:答题单价沿用 4a §5.6 的每题次约 ¥0.96 作上限参考(图题检索内容少,通常更低),路 A 另加图片输入;(60 + 20)题 × 2 次 × 2 种配置 ×(基线 + 改动后)≈ 640 题次,上限约 ¥600 —— **偏贵**。建议先只跑一种配置(路 B,多数智能体主模型不能看图)约 ¥300,过了再补另一种;或把每题跑两次降为一次(§7.2 第 6 条)。开跑前用 `tools/eval/kb_agent_estimate.py` 出报价。
