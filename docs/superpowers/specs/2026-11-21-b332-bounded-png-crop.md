# B-332 ask_image 宿主裁图的内存有界(PNG / WebP / GIF)

- **日期**:2026-11-21 · **状态**:已实现、一轮独立审查返工完(分支 `feat/b332-bounded-png-crop`,未推送);用户 11-21 拍板见 §3。
- **读者**:开发工程师(全文)、验收执行人(§6、runbook §132)。
- **关联**:[B-322 设计](2026-11-19-b322-pathA-vision-parity-design.md) §4.1.5(控制面内存预算);B-322 PR ② `zoom_image` 会让主模型直接触发同一个裁图,所以先把它的内存收住。

## 1. 问题

`ask_image` 的宿主裁图(`region_zoom.crop_image`,经 `tools/vision.py` 的 `_crop_in_thread`)不论图多大都只占 1 个宿主解图名额,解码前也没有内存估算。JPEG 能 `draft` 缩小解码,峰值有界;PNG 不能,整张解开之后,「裁一份 → 转 RGB / 铺白底一份 → LANCZOS 缩一份」几份拷贝叠在一起。

新进程里量(`ru_maxrss` 增量,48 MP = 8000x6000,整张框):RGB 552 MiB、RGBA 1101 MiB。控制面 pod 的预算只剩约 56 MiB 余量(B-322 预算,`tools/deploy/test_parse_worker_memory_budget.py`)。一张 12 MP 的 PNG 截图在 main 上就要 144 MiB(RGB)/ 282 MiB(RGBA)。

## 2. 做法

1. **裁图本身不再叠拷贝**(`_render_box`):
   - 整张框:不复制整张;RGB / 灰度直接缩(灰度缩完再转 RGB,逐像素相同);其它颜色模式(RGBA / LA / P / 1 / I;16 / CMYK)**分条**转 RGB 并分条做 LANCZOS 的横向那一遍,拼成「输出宽 x 原高」的中间图再做纵向那一遍。Pillow 缩小本来就是先横后纵、中间 8 位,横向每一行独立,所以结果与整张转完再缩**逐字节相同**。
   - 局部框、要缩、RGB / 灰度:一步 `image.resize(目标, LANCZOS, box=原图坐标矩形)`,再 `transpose`(B-301 度数与 EXIF 方向合成一个方向值,框先换算到原图坐标,与原来 `crop_upright` 同一套映射,宽高对调的 90 / 270 度也照旧)。
   - 局部框、要缩、别的颜色模式:分条路径(同上,与 main 逐字节相同)。RGBA 不走 `resize(box=)`:Pillow 会先把整张预乘一遍(研究里量到 424 MiB)。
   - 不用缩的框:RGB / 灰度原路(`crop_upright` → `_flatten`,本来就是小块);别的颜色模式也分条转(原路在带透明的图上同时有约 5 份拷贝,横条上限 300 万像素时约 57 MiB)。
2. **只读文件头的方向**(`header_orientation`):Pillow 的 PNG `getexif()` 在文件头里没有 `exif` 时会**把整张图解开**去找文件末尾的 `eXIf` 块(48 MP RGBA 多 +184 MiB,发生在事件循环上、不占名额)。控制面上传会剥掉 EXIF,所以这几乎是每张上传 PNG。`image_size` / `exif_orientation`(以及 `_zoom_pixels`、`_wants_region_hint`、`_write_crops` 复用分支、`_reads_a_copy` 这些调用方)改成:PNG 头里没有 `exif` 就当方向 1。真正裁图时整张已经解开,仍照 `eXIf` 转。
3. **解码前估峰值**(`crop_peak_bytes(..., draftable=False, rotated=..., decoder_bytes_per_pixel=...)`):只读文件头;JPEG(`draftable=True`,默认)的估算一个字不动。按最贵的框(整张、要缩)估,模式分两类(RGB / 灰度直接缩;其它分条),转方向再加一份整张的转置拷贝。除按像素数的项之外还有:每像素 1 字节的解码余量与固定 6 MiB;**Pillow LANCZOS 的滤波系数表**(横向约 宽 x 48 字节、纵向约 高 x 48 字节,估算取 72 x (宽 + 高));**分条转 RGB 的条**(一条至少一整行,约 20 字节 / 像素);不用缩的框(横条上限下)分条转、不叠拷贝,至多两份框大小的 RGB,小于「整张要缩」那一档,不单独估。再乘现有 `PEAK_SAFETY` 1.2。前两项是审查补的:一像素高的超宽图(10,000,000 x 1)按像素数估只有 30 MiB、实际 640 MiB。
4. **闸**(`image_views.crop_slots`,`vision._crop_in_thread`):沿用 B-322 的 `slots_for`(不到 110 MiB 的一半占 1 个名额,不到 110 MiB 占 2 个,超过拒绝),走同一道宿主解图闸。JPEG 与认不出的文件仍占 1 个(行为不变);超过 6000 万像素仍由 `crop_image` 自己在解码前抛原来的 `RegionImageError`。是否转方向:文件头方向标记与 B-301 `degrees` 合成不是 1;或 PNG 头里没有 `exif` 但文件里有 `eXIf` 字样(末尾块,要解码才读得到值)—— 保守算会转。文件头里有方向 1、或与 `degrees` 合成回 1 的不算转。
5. **拒绝**:超预算在解码之前抛 `ExpectedRefusalError`(见 §7),计数 `expert_work_ask_image_crop_refused_total{reason="peak_over_budget", purpose}`(`purpose` = `region`:模型要的局部;`orientation`:问方向的候选副本)。文字如实说「图太大,无法在服务器上按原分辨率裁;没有裁」,建议不要换 `region` 重试,不带 `region` 整张看,或请用户给更小的导出 / 只截要的那一块。同样不再把模型引回必被拒的裁图:`_wants_region_hint` 对裁不了的图不加 `region='auto'` 提示;`region='auto'` 遇到拒绝时整张读一次,文字说「图太大无法放大看……不要换 region 重试」,不再说「用显式 region 重问」。

## 3. 用户决定(2026-11-21)

1. 沿用每份拷贝预算 `FULL_COPY_PEAK_BYTES` = 110 MiB 与 B-322 的名额规则;不动内存预算与 parse-worker 上限。估算超过 110 MiB 的裁图拒绝,如实告诉模型,不静默降级。
2. 非原点框可以有极小像素差:仅「要缩的局部框」用一步 `resize(box=)`;**只有整张框必须与 main 逐字节相同**。(审查返工时用户补充:贴左上角的局部框如 `[0,0,600,1000]` 与别的局部框同样处理——`resize(box=)` 在右、下边缘会读到框外一圈像素做滤波,有极小差别,不再算偏离;有回归测试。)不用缩的框也与 main 逐字节相同。
3. 「图太大,无法裁」的拒绝**不算 run 失败**(审查返工时用户定):保留指标,不进 B-105 / B-226 的失败账本,run 不会因它被标成没做完。机制见 §7。

## 7. 预期之内的拒绝与失败账本(用户 11-21 定)

`ask_image` 是**只读**工具:B-164 的 `_is_read_only_failure`(`graph_builder/builder.py`)让它所有非瞬态失败本来就不进失败账本(`unresolved_failures`),所以 B-226 的「没做完」判定与账本行为**不因本票改变**(拒绝和真正的裁图错误都不进账本)。「图太大」的拒绝在没有 `ExpectedRefusalError` 时会被分成 `unknown`,从而:计入 `expert_work_cm_tool_error_total{error_class="unknown"}`、触发深想升档(`error_signal` 取「非 transient 的失败」)、给模型的建议标签是 `unknown` 那一套。最窄的做法是沿用既有的 `GuidedTimeoutError` 先例:新增 `ExpectedRefusalError`(`tools/error_classifier.py`),分类为 `transient`、`retryable=False`、带工具给的建议。它实际改变的只有三件事:

1. 不触发深想升档;
2. 建议的标签是 `[transient]`;
3. 指标的错误类是 `transient`(不混进 `unknown` 的真错误)。

真正的裁图错误(解不开等)照旧是 `unknown`(会升档、计 `unknown`),也照旧因只读而不进账本。测试用 `vision._spec_with_short_form()` 的真实规格走 `_is_read_only_failure` 这一步断言以上行为。

已知现象:`region='auto'` 的横条在约 11~13 MP 的 RGBA PNG 上会被拒(估算按整张要缩的最贵框算),拒绝按 `purpose="region"` 计,与接缝重看(`bands=True`)的拒绝没有分开;没有单独的 `purpose` 标签,不影响行为。

## 8. 与立项决定不一致的地方(已按实际处理)

1. 「告诉模型缩小区域」不成立:PNG 不论框多大都要整张解开,估算与框无关,缩小区域会反复被拒。提示改成「不带 region 整张看 / 请用户给更小的图」。
2. JPEG 的局部框(要缩、RGB / 灰度)也走 `resize(box=)`,有同一档极小差别;整张框(B-322 候选)逐字节不变。
3. 只估 JPEG 以外的格式;JPEG 的 `ask_image` 局部裁图仍占 1 个名额、估算不随框变(没有动)。JPEG 局部框若不够 `draft` 的门槛会整张解开,这是 B-322 之前就有的口径,不在本票。
4. 末尾才有 `eXIf` 的 PNG:`image_size` / `exif_orientation` 这类只读头的函数看不到它的方向(返回 1),真正裁图时照它转;两边只对这种罕见文件不一致(复用已裁好的图时报的尺寸可能是转之前的)。整张看要不要读候选副本(`_reads_a_copy`)对这种文件用与估算相同的保守规则(`may_have_trailing_exif`):读副本,副本是真正解码、照末尾标记转正的那张。

## 9. 业界做法(调研)

- Claude Code:读图时把长边压到约 2000 px 再给模型,没有「原分辨率局部放大」这一档;
- OpenManus:截图缩到 1920x1080;
- OpenViking:按 2048 px 切片,每片独立处理,内存随片大小而不是整图大小;
- pyvips(libvips 流式、按需解码):对 PNG 能显著降峰值,但要新增原生依赖与镜像改动,与「简单需求不要大设计」不符,否决。

本票的做法与它们的共同点:内存随**输出**而不是随输入走;区别是我们保留「按原像素裁」的语义,所以仍要整张解开,靠估算 + 拒绝兜住上限。

## 10. 残余风险

- 估算按最贵的框,所以小框也会因为图大被拒;这是整张解码决定的,不是估算偏保守。横条的框那一块不用缩、实测远低于估算时也一样(估算按整张要缩)。
- 并发:同时在裁的最多两个名额(沿用 `HOST_CROP_SLOTS`),一张占 2 个的单独在算。
- **JPEG 估算随尺寸不单调(B-322 既有,B-332 没动)**:测试环境实测宽高是 8 的倍数的常见尺寸(4032x3024、6000x4000、8160x6120、9000x6700、12000x9000)不判 `too_large`,非 8 倍数的(5163x3873、5656x4243、9018x6764)会判。原因:`crop_peak_bytes` 的 JPEG 路径按 Pillow 实际的 `draft` 选档估(请求尺寸向上取整,Pillow 按「原尺寸 // 请求尺寸」选档,不整除时档位变小、解开的那份更大;代码里已有「9487 宽请求 1/4、实际 1/2」的注释),所以估算跟着真实的解码一起跳。要修只能改 `crop_image` 的 `draft` 请求(改成向下取整),那会改变 B-322 JPEG 候选 / Path B 的裁图字节,与「JPEG 逐字节不变」冲突,本票不做;只在这里写明。PNG / WebP / GIF 没有 `draft` 档位,估算随尺寸单调(测试扫过,并与相邻 8 倍数尺寸比对)。JPEG 的 `ask_image` 裁图仍占 1 个名额、不看这个估算,所以该跳变只影响 B-322 的问方向候选。
