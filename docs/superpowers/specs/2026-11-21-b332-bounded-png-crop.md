# B-332 ask_image 宿主裁图的内存有界(PNG / WebP / GIF)

- **日期**:2026-11-21 · **状态**:已实现(分支 `feat/b332-bounded-png-crop`,未推送);用户 11-21 拍板两条(见 §3)。
- **读者**:开发工程师(全文)、验收执行人(§6、runbook §132)。
- **关联**:[B-322 设计](2026-11-19-b322-pathA-vision-parity-design.md) §4.1.5(控制面内存预算);B-322 PR ② `zoom_image` 会让主模型直接触发同一个裁图,所以先把它的内存收住。

## 1. 问题

`ask_image` 的宿主裁图(`region_zoom.crop_image`,经 `tools/vision.py` 的 `_crop_in_thread`)不论图多大都只占 1 个宿主解图名额,解码前也没有内存估算。JPEG 能 `draft` 缩小解码,峰值有界;PNG 不能,整张解开之后,「裁一份 → 转 RGB / 铺白底一份 → LANCZOS 缩一份」几份拷贝叠在一起。

新进程里量(`ru_maxrss` 增量,48 MP = 8000x6000,整张框):RGB 552 MiB、RGBA 1101 MiB。控制面 pod 的预算只剩约 56 MiB 余量(B-322 预算,`tools/deploy/test_parse_worker_memory_budget.py`)。一张 12 MP 的 PNG 截图在 main 上就要 144 MiB(RGB)/ 282 MiB(RGBA)。

## 2. 做法

1. **裁图本身不再叠拷贝**(`_render_box`):
   - 整张框:不复制整张;RGB / 灰度直接缩(灰度缩完再转 RGB,逐像素相同);其它颜色模式(RGBA / LA / P / 1 / I;16 / CMYK)**分条**转 RGB 并分条做 LANCZOS 的横向那一遍,拼成「输出宽 x 原高」的中间图再做纵向那一遍。Pillow 缩小本来就是先横后纵、中间 8 位,横向每一行独立,所以结果与整张转完再缩**逐字节相同**。
   - 局部框、要缩、RGB / 灰度:一步 `image.resize(目标, LANCZOS, box=原图坐标矩形)`,再 `transpose`(B-301 度数与 EXIF 方向合成一个方向值,框先换算到原图坐标,与原来 `crop_upright` 同一套映射,宽高对调的 90 / 270 度也照旧)。
   - 局部框、要缩、别的颜色模式:分条路径(同上,与 main 逐字节相同)。
   - 不用缩的框:原路(`crop_upright` → `_flatten`),本来就是小块。
2. **解码前估峰值**(`crop_peak_bytes(..., draftable=False, rotated=..., decoder_bytes_per_pixel=...)`):只读文件头;JPEG(`draftable=True`,默认)的估算一个字不动。按最贵的框(整张、要缩)估,模式分两类(RGB / 灰度直接缩;其它分条),转方向再加一份整张的转置拷贝,再加每像素 1 字节与固定 6 MiB,乘现有 `PEAK_SAFETY` 1.2。
3. **闸**(`image_views.crop_slots`,`vision._crop_in_thread`):沿用 B-322 的 `slots_for`(不到 110 MiB 的一半占 1 个名额,不到 110 MiB 占 2 个,超过拒绝),走同一道宿主解图闸。JPEG 与认不出的文件仍占 1 个(行为不变);超过 6000 万像素仍由 `crop_image` 自己在解码前抛原来的 `RegionImageError`。
4. **拒绝**:超预算在解码之前抛 `GuidedToolError`(`ask_image` 已有的「如实告诉模型、不重试」那一类),计数 `expert_work_ask_image_crop_refused_total{reason="peak_over_budget"}`。文字如实说「图太大,无法在服务器上按原分辨率裁;没有裁」,建议不带 `region` 整张看,或请用户给更小的导出 / 只截要的那一块。**不说「缩小区域」**:整张文件不论框多小都要整张解开,换个框会再被拒(见 §7 第 1 条)。

## 3. 用户决定(2026-11-21)

1. 沿用每份拷贝预算 `FULL_COPY_PEAK_BYTES` = 110 MiB 与 B-322 的名额规则;不动内存预算与 parse-worker 上限。估算超过 110 MiB 的裁图拒绝,如实告诉模型,不静默降级。
2. 非原点框可以有极小像素差:仅「要缩的局部框」用一步 `resize(box=)`;整张框与不用缩的框与 main 逐字节相同。

## 5. 现在装得下什么(4:3 画幅,估算 ≤ 110 MiB)

| 格式 / 模式 | 1 个名额(≤ 55 MiB) | 能裁(2 个名额,≤ 110 MiB) | 转 90 度能裁 |
|---|---|---|---|
| PNG RGB / RGBA | 约 4 MP | 约 13 MP(4032x3024 手机截图估算 103 MiB,装得下) | 约 7 / 6 MP |
| PNG 灰度 L | 约 13 MP | 约 35 MP | 约 23 MP |
| PNG 调色板 P / GIF | 约 10 MP | 约 28 MP | 约 8 MP |
| PNG 16 位灰度 | 约 7 MP | 约 20 MP | 约 8 MP |
| WebP | 约 1 MP | 约 4 MP | — |
| 48 MP 任何 RGB / RGBA | — | 拒绝 | 拒绝 |

比立项时预计的「RGB ≤ 18 MP、RGBA ≤ 10 MP」:RGB 低(估算含 1.2 安全系数与每像素 1 字节余量,实测 12 MP RGB 才 73 MiB),RGBA 高(分条后不再有整张的 RGBA 拷贝)。

## 6. 验证

`services/orchestrator/tests/test_b332_bounded_crop.py`:整张框 x 8 种 EXIF 方向 x 4 个度数 x 8 种颜色模式,与 main 的 `crop_image`(`_b332_main_region_zoom.py`,main 该文件的原样拷贝,进程内比对,不依赖平台的 JPEG 字节哈希)逐字节相同;局部框(非 RGB / 灰度)同样逐字节相同;RGB / 灰度的局部缩小尺寸相同、像素差有界(均值 < 0.5、最大 ≤ 32,截图类合成图);B-301 接缝横条并集框;RGBA / LA / 带透明 P 铺白底;B-322 JPEG 候选(L / RGB / CMYK x 8 方向 x 4 度数)逐字节不变、JPEG 估算与 main 相同;估算 ≥ 实测;超预算在解码前拒绝(用只有文件头的假 PNG,解码就会失败)、占名额数、指标。`test_b322_crop_image_unchanged.py`:`_cap_pixels` 被取代已删,`_crop_open_image`、`crop_upright` 改成钉新哈希,其余 main 上的定义仍逐字不变。

## 7. 与立项决定不一致的地方(已按实际处理)

1. 「告诉模型缩小区域」不成立:PNG 不论框多大都要整张解开,估算与框无关,缩小区域会反复被拒。提示改成「不带 region 整张看 / 请用户给更小的图」。
2. 「原点框逐字节相同」只对**整张框**成立。贴左上角的局部框(如 `[0,0,600,1000]`)在 RGB / 灰度且要缩时,`resize(box=)` 在右 / 下边缘会读到框外一圈像素做滤波,有极小差别(与非原点框同一档)。要让它也逐字节相同就得先裁一份整块,内存回到 main 的量级,与目标冲突。
3. JPEG 的局部框(要缩、RGB / 灰度)也走 `resize(box=)`,有同一档极小差别;整张框(B-322 候选)逐字节不变。
4. 只估 JPEG 以外的格式;JPEG 的 `ask_image` 局部裁图仍占 1 个名额、估算不随框变(没有动)。JPEG 局部框若不够 `draft` 的门槛会整张解开,这是 B-322 之前就有的口径,不在本票。

## 8. 业界做法(调研)

- Claude Code:读图时把长边压到约 2000 px 再给模型,没有「原分辨率局部放大」这一档;
- OpenManus:截图缩到 1920x1080;
- OpenViking:按 2048 px 切片,每片独立处理,内存随片大小而不是整图大小;
- pyvips(libvips 流式、按需解码):对 PNG 能显著降峰值,但要新增原生依赖与镜像改动,与「简单需求不要大设计」不符,否决。

本票的做法与它们的共同点:内存随**输出**而不是随输入走;区别是我们保留「按原像素裁」的语义,所以仍要整张解开,靠估算 + 拒绝兜住上限。

## 9. 残余风险

- PNG 末尾才有的 `eXIf` 块(罕见):文件头里看不到方向,估算按「不转」算,实际转的话多一份整张拷贝(估算的 1.2 系数只盖一部分)。PNG 头部带 `eXIf` 与 B-301 的 `degrees != 0` 都按「转」估。
- 估算按最贵的框,所以小框也会因为图大被拒;这是整张解码决定的,不是估算偏保守。
