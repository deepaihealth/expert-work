# B-267 绑了知识库却去搜网:让智能体先查自己的知识库

日期:2026-11-03 · 状态:设计稿,待用户拍板(只写方案,不动代码)

## 1. 问题

测试环境会话 `b9cadbf4-…`:智能体 `test-agent`(glm-5.3,自己的提示词 3 个字符,即为空)绑了 1 个知识库「轻天下」
(10 份文档已入库,其中就有《大国食养》,94 段提到它),同时有 `web_search`。用户问「大国食养谁写的」,模型调了
1 次 `web_search`(查询「《大国食养》作者 书」)后直接作答,知识库检索记录为 0。用户追问「你有哪些工具」时模型
能列出 `knowledge_search`,说明工具在、只是没选它。

模型做选择时能看到的只有两段工具说明:

- `knowledge_search`:「Search the tenant's knowledge base for information relevant to a query…」——没说库里有什么。
- `web_search`:「Use for current events, facts you're unsure about, or any external lookup」——「某书谁写的」正好像外部事实。

另外:只绑 1 个库时平台不展示知识库目录(`knowledge_catalog.MIN_CATALOG_BASES = 2`);没有任何平台规则说「先查知识库」。

**为什么评测没发现**:知识库评测智能体 `eval-kb` 的提示词里写着「回答前先用 knowledge_search 检索」,且不能上网——
「提示词为空 + 同时能上网」这个组合从没测过。

**影响面**:对接方大多不会在提示词里写「先查知识库」(平台原则:平台补默认,不让对接方去配),所以凡是绑了知识库
又开了上网搜索的智能体都可能这样。答案碰巧网上有时还能对;只在内部资料里的内容(内部制度、自编教材、产品参数)就会
答错或说查不到。

## 2. 业界怎么做(调研摘要)

| 做法 | 代表 | 要点 |
| --- | --- | --- |
| 每轮自动先查 | 扣子默认「自动调用」、Dify 对话 / 工作流的知识检索节点、WeKnora 非智能体模式、NotebookLM、Claude Projects(知识小时整份放进上下文) | 不漏,但每轮有成本、无关段落会干扰 |
| 平台规则 + 说清库里有什么,模型自己决定 | 微软 Copilot Studio(每个知识源要写描述)、亚马逊 Bedrock(知识库的「何时使用」说明)、Glean(先企业知识再网络)、WeKnora 智能体模式、PageIndex | 便宜;成败在「说清有什么」 |
| 只靠工具说明 | OpenAI GPTs / file_search | 社区长期反映「只有被明确要求才查知识」,通用解法是在指令里写「总是先查知识文件」 |

最完整的是 WeKnora(本地有源码):每轮在用户消息旁附上已绑知识库的名称、文档数、**大模型根据文档自动生成的画像**
(一句话概述、5–10 个主题、3–5 个典型问题),外加平台规则——「绑了知识库时,即使问题看起来像常识也先查;画像和
标题只是示例,不能证明库里没有」「本地证据缺失或需要最新信息时再上网;不要把私有内容发到外部搜索」。

Dify 曾经只靠知识库描述让模型选库,后来因为「太依赖模型怎么理解描述」逐步淘汰。

**关键判断(用户 11-03 指出)**:只列名称、文档清单甚至画像,都说明不了库里具体有什么——人名、书名、编号这种「长尾
实体」只有拿问题去库里搜一下才知道。所以规则和画像管「大方向」,真正兜底的是第 3 步的轻量探测。

## 3. 方案:三步,按顺序做,每步对照测

### 第 1 步 平台规则 + 单库也展示目录(最便宜,大概率就修好这次)

- **`knowledge_search` 的工具说明加规则**(只有绑了知识库的智能体能看到,符合「提示词跟着能力走」):
  > The bound knowledge base holds the tenant's own documents. Search it before answering any question about a topic,
  > person, product, document or term — including ones that read like general knowledge — unless the message is small
  > talk or cannot involve the documents. A name or description of the knowledge base does not show everything it
  > contains, so it cannot rule out an answer.
- **同时有 `web_search` 时**,在 `web_search` 说明(或平台段)加一句:
  > When a knowledge base is bound, search it first; use web_search when its results do not state the fact asked, or the
  > question needs current or external information. Do not put document content into web queries.
- **只绑 1 个库也展示目录**(名称 + 管理员写的描述);`bases` 参数仍只在 2 个以上时出现。
- 平台文本英文、零租户内容;不改对接方提示词。
- 代价:每轮约 80 个 token;泛泛的常识问题可能多查一次知识库(约 1–2 秒)。

### 第 2 步 自动知识库画像

- 入库时为每份文档生成一句话概述与关键词(或复用已有的文档级信息);库级画像 = 大模型基于这些汇总生成
  `{概述 ≤60 字, 主题 5–10 个, 典型问题 3–5 个, 文档类型}`,要求「只写汇总能支撑的内容」。
- 文档增删后合并触发刷新(防抖);画像进构建缓存指纹,变了才失效。
- 1 个库和多个库都在目录里展示画像;仍注明「目录不是证据,没列出不代表没有」。
- **费用要进入库前的预估与确认**(B-222 拍板:无论费用大小都要用户确认才开始)。
- 风险:画像过时、编出主题、库多时提示词变长 → 只用汇总生成、限条数、按租户数据围起来。

### 第 3 步 每轮轻量探测(真正解决「库里有什么」)

- 每轮用「最新一条用户消息 + 简短上文(处理『他还写过什么』这类指代)」在已绑的库里做一次**关键词 + 向量**检索,
  不重排、不调大模型(几十毫秒)。
- **命中时只给提示,不塞段落**:在本轮平台段(B-162,追加到最后一条消息,不进缓存的系统提示)加一句
  「知识库 K1 中有 N 段与本条消息相关的内容,回答前请用 knowledge_search 查看」;没命中什么都不加。
- 阈值**按库校准**(例如该库对随机问题得分的 90 分位,或罕见词关键词命中),不用全局常数——不同厂商、不同语料的
  向量分数不可比。
- 本轮模型已经调过 `knowledge_search`、或消息很短 / 是闲聊时不探测。
- 记录「探测命中 / 模型是否去查」,便于观察。
- 误命中的代价最多是多查一次,不会答错;不把段落直接塞给模型(我们之前实测过塞段落会让编造变多)。

### 不做

- 每轮把检索段落直接塞给模型(干扰、编造变多、注入面变大)。
- 再加一层大模型做分流(多一次调用,分流本身会错)。
- 把网络搜索并进知识库工具(改变 `web_search` 语义,有私有内容外泄风险)。

## 4. 验证

新建评测智能体 `eval-kb-route`:**提示词为空**,绑 1 个合成知识库,同时有 `web_search`(能做确定性替身就用替身,
否则注明联网带来的波动)。合成语料(中文,零租户内容):一本虚构书(虚构作者 / 出版社 / 编号)、内部制度(带数字)、
产品手册、内部操作流程、常见问答、一份用租户自己措辞写的公共主题文档、一份与公开事实故意不一致的「内部版」。

| 类别 | 例子 | 期望 |
| --- | --- | --- |
| C1 只有库里有 | 「《虚构书》谁写的」「内部制度第 N 条的额度」 | 先查知识库,答案来自库 |
| C2 库里和网上都有 | 公共主题的定义 | 先查知识库 |
| C3 两边不一致 | 内部版数值 | 答库里的版本,可注明差异 |
| C4 只有网上有 / 时效性 | 今天的新闻 | 可不查库;不编 |
| C5 闲聊 | 「你好」「你是谁」 | 不调工具 |
| C6 追问指代 | 先问书,再问「那他还写过什么」 | 第二轮也查库 |
| C7 隐私 | 任意 | 上网搜索的关键词里不出现库内专有内容 |

每类 8–12 题,共约 50 题,每个版本跑 3 遍(1 遍的差异是噪声)。判据看工具调用轨迹:第一个调用的工具、是否查过库、
闲聊是否多查、搜网关键词是否带库内内容,以及答案对错与编造。

顺序:**先在当前 main 上跑基线** → 第 1 步对照 → 第 2 步对照 → 第 3 步对照。每轮开跑前先报费用给用户。

## 5. 待拍板

1. 第 1 步规则的措辞是否接受「即使看起来像常识也先查」——代价是常识问题会多查一次。
2. 第 2 步的入库费用按 B-222 进入库前确认;已入库的老库是否补生成画像(一次性费用,按库数报)。
3. 第 3 步默认开启还是按智能体开关:平台原则是默认开、开关只用于收窄;建议默认开,给「关闭探测」的收窄开关。
4. 评测里的 `web_search` 用替身还是真联网。
5. 上线顺序:三步各自一个 PR、各自发测试,还是第 1 步先单独上(它最便宜、见效最快)。

## 6. 拍板(11-03)

全按推荐:① 接受「即使看起来像常识也先查」;② 老库补生成画像,跑之前按库数报费用;③ 每轮探测默认开,只给「关闭」开关;
④ 评测里 `web_search` 用固定结果替身(测试环境不改代码做不到时,基线用真搜索,以轨迹指标为主);⑤ 三步都进 11-03 批次的
一个 PR(`docs/superpowers/specs/2026-11-03-batch-b267-b273.md`),评测只测「基线」与「三步做完」两版。
