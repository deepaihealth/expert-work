## 1. 背景

总计划 §2.3 的来由:对照 WeKnora、RAGFlow 两个仓库盘点后,我们缺四样「可用」层面的东西。

| 缺什么 | 现在用户会遇到什么 | 我们现在的状态(已验证) |
|---|---|---|
| 第三方不能直接查库 | 对接方想在自己的页面里做「搜一下知识库」,只能发起一次完整的智能体对话 | 知识库全部接口都在控制台平面,拒绝 API key:六个路由模块都挂了 `console_only()`(`api/knowledge.py:540`、`knowledge_logs.py:164`、`knowledge_passages.py:315`、`knowledge_maintenance.py:145`、`knowledge_estimates.py:131`、`knowledge_figures.py:54`) |
| 表格只能当文字读 | 问「三月一共多少单」「哪个型号卖得最多」,智能体只能读到几段表格文字,算不全 | xlsx 逐格读成 Markdown 表格(`control_plane/knowledge/office_xlsx.py:53-75`),再按行切段、每段重复表头(`knowledge/chunking.py:1483-1533`);没有任何结构化存储 |
| 没法问「库里有什么」 | 问「一共几份文档」「有没有叫某某的文件」,智能体只能搜内容碰运气 | `knowledge_read` 能按文件名找文档,但最多列 10 个候选、没有总数、不能翻页(`tools/knowledge_read.py:66,260-290,398-428`) |
| 多轮追问 | 「那价格呢」这类追问,检索词里可能还留着「它」 | 明确不设独立改写步,靠一条提示词规则 + 一个计数器(`graph_builder/outgoing_reference.py:7-9,49-58,131-137`);没有量过错误率 |

### 2.2 读下来最该记住的四点

1. **两家的「模型写 SQL」都靠拦截名单兜底,而且各有窟窿**:WeKnora 用 Postgres 的解析器去检查要在 DuckDB 上跑的语句,进程内引擎没有内存上限和超时;RAGFlow 只有两个引擎强制只读。名单是补不完的。我们换一条路:模型的文字不进引擎。
2. **两家都只在「非智能体」流程里做多轮改写**。智能体模式下检索词是模型看着全部历史写的,它们也没有再加一步。这是 R4「先测」的主要依据。
3. **WeKnora 的空白名单 = 全部**,这个默认值对我们是反面教材:一把发给对接方的 key 默认能查全租户的库。
4. **两家的对外检索都没有限流和计量**。每次检索要调一次嵌入、可能调一次重排,用的是平台的额度;不限流等于给对接方一个免费的嵌入 + 重排服务。

#### 3.1.2 方案

**四项已拍板的推荐(B-175 §9,原文)与本文怎么落**:

| # | 题 | 原推荐 | 本文 |
|---|---|---|---|
| 1 | 开放 API 定位变更与第一期范围 | 「第一期只开『只检索』档」 | 列库 + 检索;不含读全文(§0.2 第 2 条) |
| 2 | 对外路由前缀 | 「锁定前缀收紧为 `/v1/knowledge/`,对外用 `/v1/knowledge-bases`」 | 照做。锁定自查的前缀表里把 `/v1/knowledge` 改成 `/v1/knowledge/`;现有控制台路由都在 `/v1/knowledge/` 下面,自查范围不变 |
| 3 | 知识库是否拆出独立权限资源 `knowledge` | 「拆」 | 拆;三个角色的权限和今天借用 `manifest` 时**完全一样**,是一次不改变行为的改名 |
| 4 | API key 授权模型 | 「能力 × 库白名单 × 默认拒绝」 | 照做;另加每库一个「允许对外」开关(B-175 §8.2 原文已有) |

**接口**(信封、分页、报错都按现有对外约定):

| 方法 + 路径 | 需要的能力 | 做什么 |
|---|---|---|
| `GET /v1/knowledge-bases` | `kb:read` | 列出这把 key **被授权且对外开关开着**的库:`name`、`description`、`document_count`(可检索的文档数)。`limit`(1~200,默认 50)+ `offset` + `total` |
| `POST /v1/knowledge-bases:search` | `kb:search` | 在指定的库里检索,只返回段落,不生成回答 |

**检索请求**:

| 字段 | 类型 | 说明 |
|---|---|---|
| `query` | 字符串,1~2,000 字符 | 必填。上限取检索记录能存的长度 |
| `knowledge_bases` | 库名数组,1~20 个 | 必填;每一个都必须是这把 key 有 `kb:search` 授权的库。不提供「不填 = 全部」 |
| `top_k` | 整数 1~20 | 可选;不填按 4a T5 的规则(这些库的「返回条数」设置取最大,封顶 20) |
| `user_id` | 字符串 | 可选;对接方自己的终端用户标识,只用于检索记录,不影响授权。按现有 `ext:` 规则规范化 |

请求体不接受租户;多余的字段按现有约定报 422。

**检索返回**(`data`):

```json
{"results": [
   {"content": "这一段的文字",
    "knowledge_base": "库名",
    "scores": {"rerank": 0.83, "vector": 0.61},
    "source": {"ref": "D12#7", "doc_seq": 12, "chunk_indexes": [7, 8],
               "title": "文档标题", "filename": "原文件名",
               "heading_path": ["第三章", "3.2 退货"],
               "locator": [{"type": "pdf", "page": 14}],
               "fingerprint": "9f2c41d07ab3e655"}}
 ],
 "status": "ok",
 "degraded": {"rerank": true},
 "unsearched_knowledge_bases": []}
```

- **一条结果是什么**:和智能体看到的一条结果是同一个东西 —— 一个大段的文字(4a §3.1.1 第一行)。`source` 就是 4a 的出处对象,由同一个函数生成,字段、含义、指纹算法都相同;没有页码时没有 `locator` 键。接口返回的是整段文字,所以没有 4a 的 `partial`。
- **顺序就是相关度顺序**。`scores` 里的数只保证在**这一次请求内部**可比;4a 已查明目录里的重排模型没有一个声明分数可以跨请求比较(4a §0.2 第 4 条)。对外文档写明「不要拿它和固定数值比」。没有重排时没有 `rerank` 键。
- `status`:`ok` / `no_results` / `below_threshold`(候选都没过库的相关度门槛);后两种 `results` 为空。不返回 4a T3 的文档标题清单(那是给模型看的工具结果,不属于检索接口)。
- `degraded`:只在降级时出现(重排失败退回召回顺序、嵌入失败只用关键词等),键与检索器已有的标志一一对应(`tools/knowledge.py:1169-1174`)。
- 结果与智能体一致:同一个库、同一个查询、同样的条数,接口返回的段落和顺序,与智能体工具、命中测试(不覆盖参数时)**相同** —— 三者调的是同一个 `search_detailed`。这一条进真栈用例。

**三道闸,按顺序**:

| 顺序 | 检查 | 不过 |
|---|---|---|
| 1 | key 的档位(至少 `read`)→ 角色有 `knowledge:read` | 403 `FORBIDDEN`(现有行为) |
| 2 | 请求里的每个库:这把 key 对它有所需能力的授权,且库存在于本租户 | 404 `KB_NOT_FOUND`。「不存在」「是别的租户的」「没授权」返回**一模一样**的响应,不透露库是否存在。有一个不过,整个请求不过(不悄悄少搜) |
| 3 | 库的「允许对外」开关 | 403 `KB_API_DISABLED`(只有已被授权的 key 才走得到这一步,不泄露存在性) |

对这个库有 `kb:read` 却没有 `kb:search` 的 key 调检索:403 `CAPABILITY_REQUIRED`。

**这把 key 能查哪些库**:只有授权表里明确列出的库。新建的 key 一条授权都没有 → 列库返回空、检索任何库都是 404。租户内新建的库不会自动出现在任何 key 的授权里。

**授权怎么管**(控制台,管理员):

- 「API 密钥」页:创建 / 编辑 key 时勾选知识库能力和库。改授权需要 `api_key:write`(只有 admin 有,`rbac.py:82`)。
- 库的设置页:「允许通过开放 API 检索」开关,默认关。改它同样要 `api_key:write` —— 这是「让 API key 能碰到这个库」的决定,不是普通的库设置。
- 授权的增删、开关的改动都写审计(B-175 §6.10)。
- **轮换**:新 key 行在同一个事务里复制旧行的全部授权(否则轮换后新 key 一个库都查不了);旧行的授权保留到它失效。**吊销 / 删除**:授权行随 key 行级联删除。**删库**:该库的授权行级联删除。

**限流**(两层都生效):

1. 现有的租户级限流(所有请求共用)。
2. 新增一个「知识库检索」专用桶,按租户:默认容量 10、每秒回补 5(可在平台设置里改,可按租户覆盖,走现有覆盖机制)。超了返回 429 `RATE_LIMIT_EXCEEDED`,`dimension: "kb_search"`,带 `Retry-After`。
   - 为什么比 B-175 写的「20 RPS」低:每次检索要调平台的嵌入接口,开了重排的库还要调重排;这些厂商额度是全平台的智能体共用的。先保守,有对接方提再调。

**用量与谁付钱**(§7.2 第 6 条待拍板;下面是建议方案):

- 每次检索**都记用量**:新的用量类别 `knowledge_open_api`,记在调用方租户名下,`agent_name` 留空。查询嵌入的 token 取厂商返回值(现有的嵌入用量接收机制,`llm/embedder.py:63-80`)。
- 重排:用聊天模型重排的那条路沿用现有机制记 token;专用重排接口那条路今天哪里都不记,本期在检索记录里记「重排了多少个候选」,token 级用量是已有缺口,不在本期补(§7.3)。
- 一期**不向租户收费**(和智能体运行里的检索同一口径:平台成本),靠专用限流封顶。这不是「没有成本」:成本记在 `knowledge_open_api` 下,运营用量页按类别能看到;某个租户的量长期顶着限流跑,再定价。

**检索记录**:每次检索写一行,来源 `open_api`(枚举已有);`actor_id` 记服务账号 id;`flags` 里记 key 的前缀(不是密钥)和规范化后的 `user_id`(有才记)。写法照命中测试(包一个记录范围)。管理端的检索记录页已经认得这个来源。

**报错**(新增三个错误码,其余沿用):

| 码 | 状态 | 什么时候 |
|---|---|---|
| `KB_NOT_FOUND` | 404 | 库不存在或这把 key 无权访问 |
| `KB_API_DISABLED` | 403 | 库没开「允许对外」 |
| `CAPABILITY_REQUIRED` | 403 | 对这个库的授权里没有这次操作需要的能力 |
| `INVALID_REQUEST` | 422 | 字段不合法(现有) |
| `RATE_LIMIT_EXCEEDED` | 429 | 两层限流(现有码,新 `dimension`) |
| 503 | — | 平台没配嵌入模型(同命中测试,`api/knowledge.py:1409-1413`),用对外信封 |

检索本身的降级(重排挂了、嵌入挂了)不是错误:200 + `degraded`。

**版本与文档**:

- 路径在 `/v1` 下;以后加可选字段不算破坏。
- 对外文档新增一页「知识库检索」(列库、检索、三道闸、分数怎么用、出处对象、限流);`auth.md` 的「Key 只能访问…」一句补上 `/v1/knowledge-bases`;`errors.md` 加三个码和新的 `dimension`;`changelog.md` 发布时记一条「新增接口」(按 `changelog.md:9-13` 属于新增,不需要提前通知)。
- 侧边栏配置同步(`docs-site/.vitepress/config.*`)。

**平台开关**:`kb_open_api`,默认关。关的时候两条对外路由返回 404(和没有这个功能一样),控制台里不显示授权勾选和库开关。

#### 3.1.4 边界情况

| 情况 | 处理 |
|---|---|
| 请求里同一个库名写了两次 | 去重后照常 |
| 库名大小写 / 首尾空格 | 精确匹配,不规范化(库名在清单接口里原样给出) |
| 授权了但库被删了 | 授权行已级联删除 → 404 |
| 授权了的库里一份可检索的文档都没有 | 200,`status: no_results` |
| 多个库里有的开了对外、有的没开 | 整个请求 403 `KB_API_DISABLED`,`message` 里列出没开的库名(调用方对它们都有授权,可以看见名字) |
| key 在宽限期内(已轮换的旧 key)| 照常,授权仍在 |
| 员工登录凭证调这两个接口 | 403(`external_only()`) |
| 跨租户:A 租户的 key 写 B 租户的库名 | 按本租户找库,找不到 → 404,与「不存在」相同 |
| 没有文档号的文档(4a §3.1.2:应为 0)| `source.ref` 没法给;这一条结果不返回并计数进检索记录的 `flags`。上线前数一次(4a U6 同一件事) |
| 查询里有 NUL 字节 | 422(现有的 `reject_nul`) |
| 检索超时 | 走现有的 504 处理;检索记录里是 `error` |
| 4a 还没合 | `source` 的生成函数在 4a 的 A0 / A1a 里。R1 的对外路由 PR 排在它们之后;授权与权限两个 PR 不受影响 |

#### 3.1.5 不做什么(一期)

- 读文档全文 / 分段列表、文档列表(§7.2 第 5 条)。
- 内容管理(上传、删除、改元数据、改分段、任务查询)、回调。
- MCP、Dify 等第三方协议适配。
- 请求里覆盖检索参数(方法、门槛、重排开关、过滤条件、查询改写)。
- 按终端用户的权限过滤(`user_id` 只进记录)。
- 向租户收费。
- 顺带清理读文档工具元数据里已经对外可见的内部 id(§3.1.1 倒数第二行):要先数清谁在用这些字段,单独处理(§7.2 第 12 条)。

#### 3.2.2 方案

**哪些文件**:`.xlsx` 和 `.csv`。Word / PDF 里的表格**不做**:它们的表头、合并格、跨页断开都不可靠,读成数据错的比对的多;这些表格继续当文字检索。

**一张表是什么**:xlsx 的一张工作表 = 一张表;一个 csv 文件 = 一张表。表头的认法与现有 Markdown 解析**用同一段代码**(同一个「去空行 → 可选标题行 → 表头行」),保证智能体在段落里看到的列名和表格工具里的列名一致。

**每张表存什么**:

| | 内容 |
|---|---|
| 表 | 属于哪份文档、第几张(从 1 起)、工作表名、标题(有才有)、行数、列清单 |
| 列 | 位置、表头文字(空表头叫 `column_3` 这样的名字;重名的加后缀)、类型(`number` / `date` / `text`)、非空格数、不是数的格数(数值列才有)、取值范围(数值 / 日期列的最小最大)、不同取值个数不超过 20 的文本列给出全部取值 |
| 行 | 行号(原表里的行号,从 1 起)、两份数组:`cells` 是每格**显示出来的文字**(与段落里一致),`vals` 是每格的**带类型的值**(数 / 日期的标准写法 / 文字 / 空) |

- **类型怎么定**(程序算,不调模型):xlsx 看格子本身的类型;csv 全是文字,按固定写法试着读成数(可带正负号、小数点、千分位逗号、末尾 `%`)或日期(`YYYY-MM-DD` 等几种固定写法)。一列里非空格有八成以上读得成数,这一列就是 `number`,读不成的那些格在 `vals` 里是空、并计入「不是数的格数」。八成是起点值,由评测校(§7.3)。
- **百分比**:`vals` 里存显示出来的那个数(61.12),列说明里标明是百分比。这样工具算出来的和智能体在段落里读到的是同一个数。
- **数值的精度**:`vals` 用原始值(不按显示格式四舍五入),百分比除外。

**大小限制**(起点值;§7.2 第 3 条):

| 限制 | 值 | 超了怎么办 |
|---|---|---|
| 每张表行数 | 50,000 | 这张表不存成数据(文档照常入库、照常能检索);文档上标记「表格数据:因过大未生成」 |
| 每张表列数 | 200 | 同上 |
| 每份文档的格子总数 | 1,000,000 | 同上,整份文档都不存 |
| 每份文档的表数 | 50 | 只存前 50 张 |

**怎么存 —— 取舍一:三种存法**

| | 甲:每张表建一张真的 Postgres 表 | 乙:进程内 DuckDB(WeKnora 的做法) | 丙:Postgres 里的 JSONB 行(本文选) |
|---|---|---|---|
| 表结构 | 租户上传什么就建什么表;列名是租户文字 | 查询时现从原文件建表 | 两张固定的表,列数据放在 JSON 数组里 |
| 租户隔离 | 靠表名和授权,出错就是跨租户 | 进程内共用一个库,靠表名区分(WeKnora 的物理表名就是文档 id 拼的,两个会话加载同一份文档可能互相删表 —— 调研结论) | 和段落表同一套:每行带租户 id + 行级策略 + 查询条件里的租户 |
| 迁移 / 备份 / 删除 | 动态建表不在迁移工具里;删文档要删表 | 不落库,每个副本各装各的,没有预热 | 普通的行;外键级联删 |
| 新依赖 | 无 | 新增一个本地库;装扩展要联网(WeKnora 启动时装两个扩展,`container.go` 已核) | 无 |
| 资源 | 数据库管 | 在控制面进程里吃内存和 CPU;WeKnora 没设上限 | 数据库管;语句超时 |
| 查询能力 | 完整 SQL | 完整 SQL | 我们提供什么就有什么(统计、排序、筛选) |
| 性能 | 最好 | 好 | 5 万行的 JSON 聚合要扫全表;够不够用**未测**(第 0 步) |

选丙。理由:隔离、删除、备份、多副本都和现有的段落表同一套,不引入「动态建表」和「进程内引擎」两类新风险;查询能力只要统计、排序、筛选,用不到完整 SQL。

**谁写查询 —— 取舍二:模型写 SQL,还是模型填条件**

| | 模型写 SQL | 模型填结构化条件(本文选) |
|---|---|---|
| 注入 | 靠解析 + 拦截名单。WeKnora 的名单是事后一条条补的(读文件函数那一段的注释就是在补洞);它用 Postgres 的解析器查 DuckDB 的语句,两种语法不一致的地方就是缝 | **结构上不存在**:模型给的只有「第几列 / 哪个操作 / 什么值」。查询语句由平台从固定的片段里拼,列的位置和值都作为参数传,模型写的任何字符都不会成为语句的一部分 |
| 只读 | 靠检查语句类型 | 平台只会拼出 SELECT;另外放在只读事务里 |
| 跨表 / 跨租户 | 靠表名白名单、强行并上过滤条件(RAGFlow 的做法) | 表由平台按「本租户 + 智能体绑定的库 + 文档号」解析出来,模型给不了别的表 |
| 模型会不会用 | 模型写 SQL 很熟 | 自定义的参数形状,模型可能填错 —— **未验证**,由统计题评测和三家模型冒烟来量(§5) |
| 表达能力 | 强(连接、子查询、窗口) | 弱;一次只能查一张表 |
| 填错了怎么办 | 数据库报错,不同引擎说法不同 | 平台校验,报错里列出可用的列名和类型 |

选「填条件」。如果评测显示模型填不好(§5.2 的红线不过),后备是「让模型写一小段 SQL 子集,平台解析成同一套条件再执行」—— 模型的文字仍然不进引擎,安全性质不变;那时再加解析库(§7.2 第 1 条)。

**工具**:`knowledge_table`,只读。只在「平台开关开着 + 智能体绑定的库里至少有一张已存的表」时注册;否则智能体的工具清单与今天逐字节相同。

参数:

| 参数 | 说明 |
|---|---|
| `table` | 必填。`D12`(文档 12;只有一张表时就是那张)或 `D12#T2`(文档 12 的第 2 张表) |
| `where` | 可选,最多 8 条,全部同时满足。每条:列、操作(等于 / 不等于 / 大于 / 大于等于 / 小于 / 小于等于 / 包含 / 属于一组值 / 为空 / 不为空)、值 |
| `group_by` | 可选,最多 3 列 |
| `aggregate` | 可选,最多 5 个。函数:计数 / 去重计数 / 求和 / 平均 / 最小 / 最大;除计数外要指定列 |
| `order_by` | 可选,最多 2 个:按某列或某个统计结果,升 / 降 |
| `select` | 可选:明细模式下返回哪些列(表超过 20 列时必填) |
| `limit` | 可选,默认 20,最多 100 |

- **只给 `table`、别的都不给** = 看表结构:这份文档有哪些表;每张表的列(名字、类型、非空数、范围或取值清单)、行数、前 3 行样例。
- 列可以用表头文字指(不分大小写、忽略首尾空格),也可以用位置(`column_3`)。
- 文字比较:等于 = 去掉首尾空格、不分大小写后相同;包含 = 字面子串。数值列用 `vals` 比;日期按标准写法比。对文本列求和 / 平均:报错,报错里给出各列的类型。
- **结果**:
  - 明细:一张 Markdown 表(用 `cells`,即显示的文字),每行带原表行号。
  - 统计:每组一行。
  - 结果上方一行平台写的说明:`[D12#T1]`、符合条件的行数 / 总行数、求和或平均时跳过了多少个不是数的格。行数永远给准确值,即使只显示了前 `limit` 行。
  - 文件名、工作表名、表头、格子内容都是租户文字,放 `content`;说明行和提示放 `notice`。
  - 结果文字有字符上限(与检索结果同一个上限,`tools/knowledge_results.py:27`),超了截断并说明。

**工具说明里写什么**(平台文本,英文,通用):什么时候用(要数个数、求和、平均、最大最小、排序、按条件筛表格文件里的行);先不带条件调一次看表结构;结果里的行号是原表行号;表里如果有合计行,它们也算在内。

**智能体怎么知道哪份文档是表**:

- 检索结果里,来自「有表格数据的文档」的那一条,标头后面多一个标记(例:`[D12#7] 文件名 · table data: D12`)。只在开关开着且该文档有表时出现;其余情况检索结果逐字节不变。文档有没有表,记在文档行的一个新列上,检索本来就要读文档行(`tools/knowledge.py:901-905`),不多一次读库。
- R3 的文档清单里同样标出。

**执行时的保护**:

| 保护 | 做法 |
|---|---|
| 只读 | 只读事务;平台只拼 SELECT |
| 超时 | 事务内设语句超时 3 秒;超时返回「查询太慢,请缩小条件」的工具错误 |
| 结果大小 | 永远带 LIMIT;分组最多算 1,000 组 |
| 并发 | 每个进程同时最多 4 个表格查询(占的是主库连接) |
| 租户 | 查询条件里带租户 id 和表 id;表 id 由平台从「本租户、智能体绑定的库、文档号」解析;行级策略兜底 |
| 文档状态 | 只查「能被检索到」的文档:已就绪、没被停用(和 `knowledge_read` 同一口径,`tools/knowledge_read.py:14-17`) |

**入库**:解析阶段(进程池里)多跑一步「读成表格数据」;写库和写段落在**同一个事务**里、受同一个代数围栏保护 —— 重新入库时段落和表格数据一起换,不会出现「段落是新的、表是旧的」。表格数据这一步出错(文件 openpyxl 读不了、超过大小限制):文档照常入库,只是没有表格数据,原因记在文档上。

**对入库估价与确认(B-222)的影响**:没有。这一步不调任何模型:读表格数据的模块不拿任何模型客户端(嵌入、识别、看图都不给),想调也调不了 —— 是结构上保证的,不是约定。估价单不多一行。代价是入库多一次读工作簿的时间和内存(**未测**,第 0 步量)和数据库存储。

**已有的表格文件**:手工跑一次补算命令(照 `backfill_profiles.py` 的先例):先空跑,只打印数字(多少文档、多少张表、多少因过大 / 没有原文件 / 读不了而跳过);`--apply` 才写。只做「取原文件 → 读成表格数据 → 写表」,不切段、不嵌入;命令的这条路径同样不拿任何模型客户端。没有保留原文件的文档跳过;有新上传在等的文档,按当前生效的那一版原文件算。

**已有的表格段落**:原样保留,继续参与检索(按名字、按某一行的内容找东西仍然靠它们)。不生成 WeKnora 那种「整表摘要」段落(要调模型、要花钱);以后 E1(每段生成问题)做了再看要不要。

**平台开关**:`kb_table_data`,默认关。

| 窗口 | 开关关 | 开关开 |
|---|---|---|
| 存储 PR 合了、工具 PR 没合 | 入库不写表格数据;补算命令可以手工跑(只在本地栈 / 测试环境验证用) | 入库写表格数据;没有工具,智能体无感知 |
| 工具 PR 合了 | 不注册工具、检索结果无标记 | 有表的智能体看到工具和标记 |
| 出处 PR 没合 | — | 表格结果的编号 `[D12#T1]` 在 4a 的核对里**不认得**,会被从回答里拿掉(4a 的规则:不认得的编号丢掉、句子保留)。能用,只是没有来源角标 |

测试环境在工具 PR 过了真栈用例后开;生产等统计题评测过线(§5.2)再开。

#### 3.2.4 边界情况

| 情况 | 处理 |
|---|---|
| 表头不在第一行(上面有几行说明) | 认错表头:列名会是说明文字。看表结构时有样例行,模型有机会发现;工具不纠正。评测里放这种表,数字如实报 |
| 一张工作表里放了几块表 | 当成一张表,中间的空行已去掉,列对不齐。同上 |
| 合计行 / 小计行混在数据里 | 照算在内,求和会重复。工具说明里提醒;评测里放这种表 |
| 合并单元格的类别列 | 值已往下抄(现有解析的行为),分组能用 |
| 表头重名 / 空表头 | 重名加后缀,空的叫 `column_N` |
| 一列里数和文字混着 | 八成以上是数 → 数值列,其余格跳过并在结果里报跳过了几个;不到八成 → 文本列,不能求和 |
| 带单位的数(`12 元`) | 读不成数 → 文本。不猜单位 |
| 公式格 | 取缓存的计算结果(现有解析同);没有缓存值的是空 |
| 日期 | 存标准写法;带时间的保留时间 |
| 超过大小限制 | 不存成数据,文档标记原因;检索不受影响 |
| csv 编码不是 UTF-8 | 沿用现有解析的编码判断;读不了就没有表格数据 |
| openpyxl 读不了的 xlsx | 没有表格数据(Markdown 那条路仍由 MarkItDown 兜底) |
| 文档重新入库后表的张数变了 | 整批替换;旧回答里的 `D12#T2` 指纹对不上,界面提示已变更 |
| 模型给了不存在的列 / 不支持的操作 | 工具报错(平台文字)+ 可用列清单(租户文字,放 `content`) |
| `where` 的值里写了 SQL 片段 | 就是一个普通的值,按字面比较(单测专门钉住) |
| 模型用 `D12` 但文档有 3 张表 | 返回表结构清单,让它指定 `#T` 几 |
| 文档不在智能体绑定的库里 / 是别的租户的 | 「没有这份文档」,与不存在同一个说法 |
| 查询超时 | 工具错误,建议缩小条件;不重试 |
| 子智能体 | 随 `knowledge` 配置继承;受同一个平台白名单约束 |
| 没有保留原文件的旧文档 | 补算跳过;重新上传后才有 |

#### 3.2.5 不做什么

- Word / PDF / 幻灯片里的表格;`.xls` / `.tsv`(现在本来就不支持入库)。
- 模型写 SQL;跨表连接;一次查多张表;子查询;窗口函数;「或」条件(用「属于一组值」覆盖常见情况)。
- 用模型生成表格摘要 / 列说明;用模型从散文里抽字段(K-15 原方案)。
- 修改数据、导出整表。
- 开放 API 里查表格(R1 一期只检索)。
- 画图。

#### 3.2.6 依据

| 结论 | 支持 | 反对 / 风险 | 状态 |
|---|---|---|---|
| 表格题靠读文字答不好 | 切段后每段只有几十行;B-206 引的外部说法「枚举和聚合应该变成查询」(B-206 设计 §5.4 K-15) | 我们自己没有量过表格统计题的正确率 | **未验证**(§5.2 的改动前一臂就是量它) |
| JSONB 行够用 | 行数封顶 5 万;只做单表扫描 | 没测过耗时 | **未验证**(第 0 步) |
| 模型能填对条件 | 参数少、有表结构可看、报错给列清单 | 两家都选了让模型写 SQL;自定义形状各厂商差异未知 | **未验证**(§5.2 + 冒烟) |
| 不调模型也能把表结构讲清 | 列名、类型、范围、样例都是程序算的 | WeKnora 用模型写列说明,可能对「列名看不出意思」的表更有用 | **未验证** |
| 入库不多花钱 | 这一步的模块不拿模型客户端 | — | 设计保证;单测钉「构造时没有模型客户端参数」 |
| 表头认法与段落一致 | 同一段代码 | csv 走 MarkItDown,它的表头认法与我们 xlsx 的不一定相同 | xlsx 已验证;csv **未验证** |

#### 3.3.2 方案

**工具**:`knowledge_list_documents`,只读。和 `knowledge_search` / `knowledge_read` 一起注册(同一个门:有 `knowledge` 配置),外加平台开关 `kb_list_documents`(默认关)。

| 参数 | 说明 |
|---|---|
| `name` | 可选。文件名或标题里包含这段文字的文档(字面、不分大小写)。不填 = 全部 |
| `bases` | 可选,只在绑了两个以上库时出现:`K1`、`K2` …(与 `knowledge_search` 同一套代号、同一个校验函数)。不填 = 全部绑定的库 |
| `order` | 可选:`number`(默认,按文档号从小到大)或 `newest`(新上传的在前) |
| `page` | 可选,从 1 起 |
| `limit` | 可选,默认 20,最多 50 |

- **默认按文档号排**:新文档的号最大,排在最后,所以翻页过程中有人上传文件,前面的页不会错位。WeKnora 是新的在前,翻到一半有新上传就会漏一条 / 重一条。「最新的是哪份」用 `order: newest`。
- **列哪些文档**:能被检索到的 —— 已就绪、没停用(与按名找、读文档同一口径)。还在处理 / 失败的不列,但结果的说明行里给出个数。
- **每一行**:`D12 · 文件名 · 标题(与文件名不同才有)· 库代号 · 上传日期 · 段数 · table data(有表格数据才有)`。文件名超过 120 个字符截断。
- **说明行**(平台文字):这一页是第几到第几份、**准确的总数**、涉及哪几个库、还有没有下一页、处理中 / 失败的各几份。
- 零结果分两种说:这个名字没有匹配;库里没有文档。
- 翻过头:说明总数和最后一页是第几页。
- 文件名、标题是租户文字,放 `content`;说明行放 `notice`。

**工具说明**(平台文本,英文,通用):看库里有什么、数一共几份、按名字找文档时用;每一行的文档号可以交给 `knowledge_read`;清单只说明有哪些文档,不是任何内容的依据 —— 要引用内容先读。

**与 `knowledge_read` 按名找的关系**:

- `knowledge_read` 不变:名字唯一时直接打开,这条快路留着。
- 它的候选清单超过 10 个时的「… and more」一行,在列文档工具已注册的构建里改成指向 `knowledge_list_documents`(只多一句平台文字)。没注册时逐字节不变。
- 两处的「包含」是同一个存储层匹配规则,不会出现「这边找得到、那边找不到」。

**出处**:清单里的 `D12` 是只有文档号的编号,按 4a 的规则不能当出处(4a §3.1.2)。答前核对里,清单结果**不算**「本轮显示过段落」。

**存储**:新增一个方法 —— 多个库、名字过滤、两种排序、偏移 + 条数、返回总数;内存 / SQL 两套实现。

#### 3.3.3 协议 / 迁移

没有迁移、没有新字段。工具元数据:`{"status", "total", "page", "limit", "shown", "refs": ["D12", …]}`,不带内部 id、不带库名(库用代号)。

**跟着变的地方**:工具注册(`tools/assembly.py:476-501`);隐式工具名清单(`agent_spec.py:1408-1418`);大结果外置的豁免清单(`tools/overflow.py:124-126`);管理端工具时间线的显示名;评测答题循环的工具清单;`knowledge_read` 的那一行提示(`knowledge_read.py:417-418`)。子智能体随 `knowledge` 配置继承。

每次模型调用多付的 token:一段工具说明 + 参数定义。**没量**(估计 120~160,o200k_base);实现时量出来写进 PR 说明;各厂商分词冒烟时看。

#### 3.3.4 边界情况

| 情况 | 处理 |
|---|---|
| 库里上千份文档,模型想全列 | 每页最多 50,它得一页页翻;说明行第一页就给了总数,问「一共几份」不用翻 |
| `name` 里有 `%`、`_` | 按字面匹配(存储层已转义,`base.py:546-547` 的约定) |
| `name` 超长 | 截到与 `knowledge_read` 参数相同的上限 |
| 选了不属于本智能体的库代号 | 与 `knowledge_search` 同一个报错(`knowledge_catalog.py:342-376`) |
| 绑定的库都不存在 | 与 `knowledge_read` 同一个报错(`knowledge_read.py:231-233`) |
| 没有文档号的文档 | 那一行用文件名代替编号(与 `knowledge_read` 候选清单同,`knowledge_read.py:415`);应为 0 |
| 两份文档同名 | 各列一行,文档号不同 |
| 旧的清单结果在长对话里被压缩 | 走通用的旧结果处理,不做专门的「可找回引用」(清单随时可以重列) |

#### 3.3.5 不做什么

- 按内容关键词列出相关文档(K-13 原方案)。留作后续:它要解决的「找全」类问题,B-206 的证据是「文档找得更全但答对的反而少」,必须配逐篇核对;等 R3 上线后看「找全」类题还丢多少再定。
- 按元数据 / 标签 / 时间范围过滤;文档摘要。
- 列出停用的、处理中的文档的名字。
- 把文档清单放进系统提示词(会破坏提示词缓存,`knowledge_catalog.py:15-17` 已说明)。

#### 3.4.2 测量设计

**量什么**(单位写死):

- 一次**试验** = 一个指代明确的用例跑一遍中、被判据检查的那一轮。
- **外发指代错误** = 这一轮里有成功的 `knowledge_search` 调用,但所有调用的参数里都没有出现该指对象的名字(`query_named = 0`)。
- **外发指代错误率** = 外发指代错误的试验数 ÷ 这一轮有成功检索调用的试验数(`query_named` 为 0 或 1 的)。这一轮没有检索的试验不进分母,单独报个数(模型可能凭上一轮的结果直接答了,那不是检索词的问题)。
- 同时报两个辅助数:**指错对象率**(回答层面:答成了另一个候选的事实)、参数里**残留指示词**的试验数。
- 歧义题(4 条)不进这个指标:它们的正确做法是追问,和检索词补全无关。

**怎么跑**:

- 集:`r01`~`r13` 里指代明确的 9 条 + 能读到参数的全部(以脚本输出的分母为准;r14 不看参数)。
- 每个用例重复 **5 次**(同题两次结果约一半会变,总计划 §2.3)。分母约 45~50 次试验。
- 模型:平台默认答题模型跑全量;GLM / DeepSeek / Qwen 里另外两家各跑同样的全量(三家各一份数字,不合并)。
- 前置:#2066(外发参数规则)已发到测试环境(总计划 R4 的依赖)。
- 读数的地方:`behavior_coref.py` 的汇总输出;外发指代错误率用它已有的 `query_named` 字段算,本批给脚本加一行直接打印这个比率和分母(§6 的 M0)。
- 花费:开跑前按当时的记录报价,用户说「跑」再跑。

**事先定死的判据**(看结果之前不许改;对平台默认模型的那一份数字判,另外两家的数字只作参考并如实报):

| 结果 | 结论 |
|---|---|
| 外发指代错误率 ≥ 10%,**或** 指错对象率 ≥ 6% | **做**:进入 §3.4.3 的选型 |
| 外发指代错误率 ≤ 4%,**且** 指错对象率 ≤ 2% | **不做**:R4 关闭,只保留现有规则和计数器 |
| 介于两者之间 | 不下结论:把集扩到 30 条指代明确的用例(合成),再量一次,仍按这张表判 |
| 分母不到 30 次试验 | 这次测量作废(模型大多没检索),先查用例 |

**证明这个指标咬得住**(离线重算,不花钱;任一条不成立,测量作废、先修指标):

| 对照 | 做法 | 必须看到 |
|---|---|---|
| 换成用户原话 | 把每次试验的检索参数换成那一轮用户的原始追问(里面是「它」「那个」) | 错误率 ≥ 90% |
| 换成点了名的 | 把参数换成判据里的对象名 | 错误率 = 0 |
| 换成另一个候选的名字 | 把参数换成判据里别的候选名 | 错误率 = 100%(名字写了,但不是该指的那个) |

第三条对照今天会**不过**:现在的判据只看「该指对象的名字有没有出现」,不看「有没有出现别的候选」—— 所以 M0 里顺带把「参数里只写了别的候选」单独归一类、算作错误。

**标定与验收分开**:这次测量本身不调任何参数,不存在标定。如果结果是「做」,现有 14 条用例降为开发集(可以对着它调措辞 / 阈值),另造一份同样九类指代对象的留出集做验收。

#### 3.4.3 两种做法的草图(**暂缓**,数字出来再定)

| | 甲:带条件的独立改写 | 乙:加强现有规则(工具侧退回一次) |
|---|---|---|
| 做法 | `knowledge_search` 执行前,如果启发式判断检索词里还有指代词,用辅助模型看最近几轮对话把检索词改写成自带主语的,再搜;改写失败用原词 | 同样的启发式命中时,工具不搜,返回一条平台文字的提示「检索词里还有指代,请写出名字后重试」;同一轮只退回一次,第二次不管写成什么都照搜 |
| 多花什么 | 命中时多一次辅助模型调用(钱 + 几百毫秒) | 命中时多一步主模型调用;不命中零成本 |
| 参考 | WeKnora / RAGFlow 的改写都在非智能体流程里,对象是用户原话;用在「模型写的检索词」上没有先例 | 没有先例;与平台「规则写在参数上」的现有方向一致 |
| 启发式误伤时 | 改写一个本来没问题的词,可能改坏 | 多走一步;第二次照搜,不会卡死 |
| 改错对象 | 辅助模型看的历史比主模型少,可能指错,而且比主模型更隐蔽 | 仍由主模型决定指谁 |
| 可观测 | 检索记录里要同时记原词和改写后的词 | 记「退回过一次」 |

两种都只在启发式命中时才动,所以都依赖启发式的准头(现在只当仪表盘信号用)。真要做,第一步是给计数器补上分母,在测试环境看命中率和误伤。

#### 3.4.4 不做什么

- 测量结果出来之前不写任何产品代码。
- 不把「当前对象」交给对接方传(11-05 用户已否决作为主方案,ROADMAP B-206)。
- 不为每次检索无条件加一次改写调用。

| 检索结果标头多一个表格标记 | 只在 R2 开关开、文档有表格数据时 | 工具结果文本的变化,不是字段变化 |

深护智康的对接不需要改代码。

### 4.2 已有的库、文档、key

- 已有的 key:一条知识库授权都没有,调新接口得到空清单 / 404。行为与「没有这个功能」相同。
- 已有的库:对外开关默认关。
- 已有的表格文档:没有表格数据,直到跑补算;在那之前智能体看不到表格工具(按「库里有没有表」门控)。
- 权限资源拆分:三个角色能做的事不变。**带条件的角色绑定**如果有按 `manifest` 资源收窄来管知识库的,拆分后会失效 —— 上线前数一次(§7.3)。

### 4.3 每轮多花多少 token(都只在对应开关开着时)

| 位置 | 多多少 | 什么时候付 |
|---|---|---|
| `knowledge_list_documents` 的说明 + 参数 | 没量(估 120~160) | 绑了库的智能体的每次模型调用;在可缓存的前缀里 |
| `knowledge_table` 的说明 + 参数 | 没量(估 250~350,参数多) | 只有库里有表格数据的智能体 |
| 检索结果的表格标记 | 每条约 8 | 只有来自表格文档的结果 |
| 没绑库的智能体 | 0 | — |
| 绑了库、库里没有表的智能体 | 只有列文档那一项 | — |

### 4.4 时延与资源

- R1:一次检索 = 现有检索的耗时;多一次读授权(按 key id 的主键范围查)。
- R2:查询 ≤ 3 秒(超时即止);入库多一次读工作簿(没量)。
- R3:一次带总数的分页查询。
- R4:无。

### 4.5 回滚

三个开关(`kb_open_api`、`kb_table_data`、`kb_list_documents`)各自关掉即回到改动前。迁移只加不改,不用回滚数据。权限资源拆分没有开关:它不改变行为,出问题按普通缺陷修。

### 5.1 哪些靠评测、哪些靠真栈用例

### 5.2 R2 统计题

**资料**:合成工作簿 6 份 + csv 2 份,分成两组:

| 组 | 用途 | 内容 |
|---|---|---|
| 开发组(3 份 xlsx + 1 份 csv,10 题) | 写工具、调说明、调「八成」阈值时可以反复看 | 订单明细(约 2,000 行)、库存、考勤;含一张规整表、一张带合计行的、一张带标题行和合并类别列的 |
| 验收组(3 份 xlsx + 1 份 csv,20 题) | 只在最后跑;开发期间不看逐题结果 | 另一批主题(合成);同样覆盖:规整表、合计行、合并格、百分比列、数字文字混合列、两张工作表表头相同、表头不在第一行 |

**题型**(验收组 20 题):计数 5、求和 / 平均 5、最大最小与排序 4、分组统计 4、带条件的明细 2。每题有唯一的标准答案(数或一组名字),由一段独立的脚本从原文件算出来(不经过我们的表格存储 —— 否则是自己给自己判)。

**判分**:程序比对,不用判分模型(数值允许千分之一的误差;名字集合要求相同)。所以这部分只有答题的钱。

**两臂**:改动前(只有检索和读文档)/ 改动后(加表格工具)。每题跑两次。

**另加点查护栏 10 题**:同一批表格文件上的「某一行的某个值是多少」。这类题靠检索就能答,用来看加了工具和标记之后有没有变差。

**红线(事先定,看结果之前可以改,之后不行)**:

| 指标 | 线 |
|---|---|
| 验收组统计题,改动后两次合计 | ≥ 32 / 40 题次答对(80%) |
| 改动后比改动前 | 至少多 12 题次 |
| 改动前两次合计 | ≤ 20 / 40;**高于这个数说明题太容易,这套题作废重出** |
| 点查护栏,改动后比改动前 | 少答对不超过 1 题次(20 题次里) |
| 答案里的数不是从工具结果来的(模型自己算 / 编) | 如实报个数;> 4 题次则不开生产,先查 |
| 「规整表」子集(约 10 题)改动后 | ≥ 18 / 20 题次。不规整的表(合计行、表头不在第一行)单独报,不设线 |

**必须变红的对照**(不花钱,离线或单测):

| 对照 | 做法 | 必须看到 |
|---|---|---|
| 打乱标准答案 | 把标准答案在题目之间轮换一位,重算分数 | ≤ 2 / 40 |
| 标准条件直接执行 | 给每道题手写一份正确的查询条件,不经模型直接交给工具 | 20 / 20 与标准答案一致。不一致 = 工具或存储有错,评测作废先修 |
| 条件里塞 SQL | `where` 的值是一段带引号、分号、注释符的文字 | 当普通值处理:0 行或字面匹配;表的行数前后不变;没有数据库报错 |
| 别的租户的表 | 用租户 A 的身份查租户 B 的文档号 | 「没有这份文档」 |
| 没绑定的库里的表 | 文档在本租户、但不在智能体绑定的库里 | 同上 |
| 超时 | 合成一张顶到行数上限的表 + 把超时调到极小 | 返回超时错误;连接归还 |
| 关掉开关 | 同一构建 | 工具清单、检索结果与改动前逐字节相同 |

**三家模型冒烟**:GLM / DeepSeek / Qwen 各跑开发组 10 题一次,只看「参数填得合不合法」(被工具拒绝的调用占比),不设线,如实报;某一家明显差(拒绝率 > 30%)时触发 §7.2 第 1 条的后备讨论。

**第 0 步(不花模型钱,开工先做)**:合成一张 50,000 行 × 30 列的表写进测试库,量四种查询(全表计数、按一列分组求和、带两个条件的筛选 + 排序、去重计数)各 20 次的耗时。判据事先定:第 95 百分位 ≤ 1 秒 → 行数上限用 50,000;超过 → 把上限降到耗时达标的行数,或加表达式索引后重量。同时量一份 20 MiB 的 xlsx「读成表格数据」这一步的耗时和子进程内存峰值,只记录、不设线。

### 5.3 R3 列文档题

- 资料:一个合成库 60 份文档(超过一页),另一个 8 份;文件名有规律可查(合成的型号、月份)。
- 10 题:一共几份(单库 / 两库各 1)、有没有叫某某的(有 / 没有各 1)、名字里带某段文字的有哪几份 2、最新上传的是哪份 1、第 41~45 份是什么 1、某个库里有几份 1、名字相近的两份分别是什么 1。
- 程序判分(数相等、名字集合相同)。两臂、每题两次。

| 指标 | 线 |
|---|---|
| 改动后两次合计 | ≥ 18 / 20 |
| 改动前两次合计 | ≤ 6 / 20;高于则题太容易,作废重出 |
| 回答里出现库里不存在的文件名 | **0**(硬线) |
| 对照:打乱标准答案 | ≤ 1 / 20 |
| 对照:关掉开关 | 工具清单与改动前逐字节相同 |

**护栏(R2 + R3 一起)**:多了工具会不会带偏普通问答。从普通集的有答案题里固定抽 20 题,开 / 关两个开关各跑两次(80 题次),看编造和误拒:各自不比关着的一臂多超过 1 题次。抽哪 20 题在看任何结果之前定(按题号排序取前 20)。

### 7.1 风险

### 7.2 需要用户定的

| # | 问题 | 选项 | 本文的建议 |
|---|---|---|---|
| 1 | 表格查询由谁来写 | ① 模型填条件(按哪列筛、怎么分组、算什么),平台拼查询;② 模型直接写 SQL,平台检查后在内嵌的 DuckDB 上跑(WeKnora 的做法) | ①。模型写的字不进数据库,不存在注入;代价是只能做单表的统计、排序、筛选。评测不过线再考虑「模型写一小段 SQL、平台翻译成 ① 的条件」 |
