### 0.3 这一批治不了的

- R2 只对规整的表可靠(第一行是表头、一行一条记录)。不规整的表由程序标出来并在结果里提醒,但数可能不对。
- DuckDB 官方自己写明:执行不受信任的 SQL「本质上不安全」,建议在操作系统层面再隔一层。本文做了数据库层能做的限制,并把执行放进一个没有密钥的独立容器;剩下的风险是「限制被绕过时,这一次装进去的表可能被发到外面」(§3.1.4)。
- R3 回答「库里有哪些文档」,不回答「哪些文档讲了某件事」。

#### 3.1.2 存什么、怎么进 DuckDB

**哪些文件**:`.xlsx` 和 `.csv`。Word / PDF 里的表格不做。**一张表** = 一张工作表或一个 csv 文件。xlsx 的表头认法与 Markdown 解析用同一段代码、同一次打开工作簿。

**入库时**(现有的解析进程里,不调任何模型,**不用 DuckDB**):读出每张表的列和行 → 定类型 → 写成一份**压缩的 CSV 字节**存进数据库的一列,旁边存表的说明。

| 存的东西 | 内容 |
|---|---|
| 表的说明(JSON) | 属于哪份文档、第几张、SQL 里的表名、工作表名、标题、行数、列清单、前 3 行样例、内容哈希、「疑似不规整」的原因 |
| 每列 | 物理列名(`c1`…`cN`)、给模型看的列名(规范化后的表头)、原表头、类型、非空数、不是数的格数、数值 / 日期列的最小最大、取值不超过 20 种的文本列的全部取值 |
| 数据(字节) | 每行一条,列顺序 `_row`(原表行号)、`c1`…`cN`;空值是空串;数和日期写成标准写法 |

**查询时的固定步骤**(执行容器里,§3.1.3):① 把这次要查的几张表的字节写进容器自己的内存盘目录;② 按说明里的类型**显式指定每列类型**把它读成表(不让 DuckDB 自己猜);③ 为每张表建一个视图,把 `c1`…`cN` 起成给模型看的列名;④ 删掉文件;⑤ 关访问、锁配置(§3.1.4);⑥ 执行模型的 SELECT;⑦ 整个库丢弃。第 ①~④ 步需要本地文件访问,所以关访问必须在它们之后。

| 存法 | 结论 | 理由 |
|---|---|---|
| **压缩 CSV 字节存数据库的一列 + 说明里带类型**(本文选) | 选 | 最简单:写的一侧只用标准库,入库路径和主进程都不需要 DuckDB;原文件字节本来就是这么存的,删除、备份、多副本都跟着数据库走 |
| Parquet 字节(第 4 版) | 否 | 仓库里没有能写 Parquet 的库,只能让入库进程也导入 DuckDB;而读的一侧同样要先落成临时文件,没省什么 |
| 结构化行存 Postgres,查询时逐行读出再灌进去 | 否 | 一次查询要把最多 100 万格从 JSON 行转一遍;行表只对「平台拼 Postgres 查询」有用(附录 B 第二档) |
| 查询时从原文件现读(WeKnora) | 否 | 每次重新解析工作簿;表头和类型没落下来 |

物理列名用 `c1`…`cN` 而不用表头文字,有两个好处:表头只在视图定义里出现一次(平台生成,带引号转义);附录 B 的退路(平台拼语句)可以只引用 `c1`…`cN`,语句里不出现任何租户文字。

**大小上限**(前四项用户 11-11 已定):每张表 50,000 行、200 列;每份文档 1,000,000 格、50 张表;单格最长 2,000 字符(超出截断并计数);一张表的字节(压缩前)最多 64 MiB。超了不存成数据(文档照常入库、检索不受影响),文档上记原因。一次查询最多装 3 份文档的表、合计不超过 2,000,000 格。数据那一列按需加载、不许顺带读出(与原文件字节那一列同样的写法,`persistence/models/knowledge.py:156-158`)。

**类型怎么定**(程序算,不调模型)。xlsx 里本来就是数值 / 日期类型的格子直接用,没有歧义;下面的规则只管**以文字形式存的值**(csv 的全部格子、xlsx 里的文本格),先做全半角归一再判:

| 读成 | 接受的写法(只有这些) |
|---|---|
| 数 | 可带正负号的整数或小数(小数点是 `.`);科学计数法;千分位逗号且每组恰好三位(`1,234,567.8`);末尾带 `%`(存显示出来的数,列说明标明百分比) |
| 日期 | 年在最前的写法:`2026-03-04`、`2026/03/04`、`2026.03.04`、`2026年3月4日`,后面可带 `时:分(:秒)` |
| 文本(安全降级,不猜) | 带货币符号或代码、带单位、括号表示负数、带「万 / 亿 / k / M」等量级后缀、空格作千分位、月份名、只有年月 |
| 文本,并在列说明里标「有两种读法,未转换」 | 日 / 月谁在前分不清的日期(`03/04/2026`);逗号后不是三位的数(`1,5` 可能是小数逗号);整列带点的值都是「点后恰好三位」(`1.234` 可能是千分位点);同一列里几种写法混着 |

- 一列的非空格八成以上读得成数 → 数值列,读不成的格是空值并计数;否则文本列。有前导零或超过 15 位的一律当文字(不带前导零的短编号挡不住,已知限制)。
- 读成文本不丢信息:模型看得到列类型和样例,需要时可以在 SQL 里自己转换(工具说明要求它说明做了转换)。
- 公式格取缓存结果。隐藏的工作表 / 行 / 列照读。DuckDB 里的类型:数值列 `DOUBLE`(全是整数时 `BIGINT`)、日期 `DATE` / `TIMESTAMP`、其余 `VARCHAR`。

**程序标「疑似不规整」**(只标记,不纠正;标了的表照样能查,每次结果都提醒):表头行三成以上为空或重名;数据第一行全是文字而下面的列大多是数;数据中间有全空的行(在现有解析删空行**之前**判,`office_xlsx.py:94-100`)或「除一两格外全空」的行;数据中途出现整行文字而这些列大多是数;csv 的表头与 MarkItDown 认的不一致。表尾合计行标不出来(已知限制)。

#### 3.1.3 在哪跑

控制面 pod 现在的限额是内存 4 GiB、CPU 1 核(`infra/k8s/base/control-plane/deployment.yaml:77-83`),常设的内存预算测试已经把这 4 GiB 算满(`tools/deploy/test_parse_worker_memory_budget.py:66-68`);主进程的环境里有全部密钥(`deployment.yaml:36-39`)。所以:

| 选项 | 结论 | 理由 |
|---|---|---|
| 控制面主进程里 | 否 | 一条失控的语句拖住整个副本;出了绕过,拿到主进程的全部内存 |
| 控制面容器里的子进程 | 否(只用于本地开发) | 内存预算已满,加不进去;子进程和主进程同一个系统用户,能读到主进程的环境变量(进程初始化时清掉自己的环境变量挡不住这一点) |
| **同一个 pod 里的独立容器**(本文选,测试与生产都用) | 选 | 自己的内存与 CPU 限额,不动控制面的预算;不注入任何密钥和配置;与主容器不共享进程视图,读不到主进程的环境;只读根文件系统 + 一小块内存盘 |
| 单独的 pod(可用网络策略禁出网) | 本期不做 | 要多一套服务发现和调用鉴权;同 pod 容器已消掉「读到密钥」这个主要威胁 |
| 智能体沙箱 | 否 | 不是每个智能体都开了,冷启动十几秒 |

**执行容器**:同一个镜像、另一个启动命令;内存限额 1.5 GiB、CPU 1 核;不挂任何密钥、不注入控制面的配置;以另一个非特权用户运行、去掉全部权限;根文件系统只读;一块内存盘(上限 256 MiB)放临时文件。主容器通过两个容器共享的一个本地套接字文件调它:进 = 几张表的字节 + 说明 + SQL;出 = 行或错误。容器里的服务对每个请求起一个**一次性的工作进程**(超时就杀这一个,不连累别的);同时最多 2 个,DuckDB 每个 1 线程、内存上限 512 MiB。

**同 pod 容器挡不住的**:它和主容器共用网络,所以「禁出网」靠的是 DuckDB 的设置(§3.1.4 第 2 层)而不是网络策略;它能连到本机上控制面的端口,但那些接口都要凭证,而它没有任何凭证。服务账号令牌要不要挂、怎么只对这个容器不挂,**未验证**(V7)。

**本地开发**(没有 k8s):同一段执行代码以子进程方式跑,只为开发方便,不是一种部署形态。

多副本:每次查询自带数据、用完即毁,副本之间没有共享状态。

#### 3.1.4 隔离与安全

分五层,前一层破了后一层还在。DuckDB 设置项的名字以官方「Securing DuckDB」页为准;我没装没跑,**逐项在第 0 步的安全对照里验证**。

| 层 | 做法 | 挡什么 | 依据 / 状态 |
|---|---|---|---|
| 1 库里只有该看的 | 每次查询新建内存库;平台按「本租户 + 智能体绑定的库 + 模型点名的文档号 + 文档可服务 + 没有停用或改过的段」解析出表(这个判断与取字节在**同一次读库**里完成),只把这些表交给执行容器 | 跨租户、跨库、读被停用的内容 | 设计保证;与 WeKnora「全局一个库 + 表名白名单」相反 |
| 2 关掉文件和网络 | 装完表、删掉文件之后,依次:临时目录等带路径的设置指到内存盘里一个固定的空目录;`enable_external_access = false`(官方:同时挡住读写文件、`ATTACH`、`COPY`);扩展的自动安装、自动加载设为关;Python 接口的「把变量名当表名」(替换扫描)关掉;最后 `lock_configuration = true`。官方写明安全设置「只能收紧不能放开」。关掉之后算不下的语句能不能往盘上溢出**未验证** —— 目标是不能,靠 `memory_limit` 报错 | 读写文件、把路径或网址当表名、联网、装扩展、改回设置 | 官方文档;设置名、顺序、行为**未实测** |
| 3 只许单条 SELECT | 用 DuckDB 自己的解析结果判:恰好一条、类型是 SELECT(`extract_statements` 与 `StatementType`);**执行的是解析出来的那个语句对象,不把原字符串再交给引擎**。不用正则,不用别的数据库的解析器。解析在已经锁死的连接上、在一次性工作进程里做(官方问题单报告过解析阶段会对 `PRAGMA` 参数求值) | 多语句、写操作、`PRAGMA` / `SET` / `CALL` / `PREPARE` / `EXECUTE` / `EXPLAIN ANALYZE` / `INSTALL` / `ATTACH` / `COPY` 作为语句 | 官方 Python 接口文档;行为**未实测** |
| 4 限额 | `memory_limit` 512 MiB、1 线程;软超时 5 秒调 `interrupt()`,硬超时 8 秒**杀掉那个一次性进程**(官方问题单报告过 `interrupt` 不一定停得下来);结果用「取前 N+1 行」读,最多 200 行、每格 500 字符、合计 1 万字符;SQL 最长 4,000 字符 | 笛卡尔积、无限递归、`range` 造大表、巨大字符串、超大结果 | 内存类由 `memory_limit` 报错;算不完的由杀进程兜底 |
| 5 容器 | §3.1.3:没有密钥、另一个用户、只读根文件系统、自己的内存与 CPU 限额 | 前四层被绕过之后还能拿到什么 | 部署配置;D2 的真栈用例验 |

**SELECT 里还能做的事**:元数据函数(列出表、列出设置)看到的只有这个临时库 —— 表就是那几张,设置里的目录是内存盘里那个固定的空目录,没有密钥。带副作用的表函数(开日志、落检查点之类)和「把一段字符串当语句执行」的函数,在锁定配置和关掉外部访问之后应当无效或无害,**逐个列进安全对照**(§5.2),哪一个没被挡住就按 §3.1.7 走退路。

**报错怎么回给模型**:① 语句不合规(多条、不是 SELECT、超长):固定的平台文字。② 按异常类别白名单 —— 解析、绑定、目录(找不到表或列)、类型转换 —— 才把 DuckDB 的原文放进 `content`,并附上可用的表和列。③ 其余一切(访问被拒、内存、超时、内部错误):固定的平台文字,不带原文。

**谁能让模型写出恶意 SQL**:任何能对智能体说话的终端用户,以及任何能往知识库放文件的人(表格的单元格里可以藏指令)。所以模型写的 SQL 一律当不受信任的输入。

**剩余风险,正面写**:DuckDB 官方明说「执行不受信任的 SQL 本质上不安全」。如果第 2 层被绕过:执行容器里没有密钥可读,但它能出网(同 pod 共用网络),能把**这一次装进来的表**(本来就是这个智能体有权看的)发到外面;它拿不到别的租户的数据,也拿不到平台的密钥。上线后 DuckDB 出了绕过类的安全公告:先关开关,升级并重过安全对照后再开。

#### 3.1.5 工具与模型看到的东西

**工具** `knowledge_table`,只读。只在「平台开关开着 + 智能体绑定的库里至少有一张已存的表」时注册。

| 参数 | 说明 |
|---|---|
| `documents` | 必填,1~3 个文档号(`D12`) |
| `sql` | 可选。不给 = 看表结构;给 = 执行这一条 SELECT |

- **看表结构不装数据、不进执行容器**:直接从表的说明里取 —— SQL 里的表名、工作表名、行数、每列给模型看的列名(已带双引号,可以直接抄)、类型、非空数、范围或取值清单、前 3 行样例、不规整提醒。
- **表名**:`d12_t1`(文档 12 的第 1 张表)—— 纯 ASCII、可预测、与出处编号 `D12#T1` 对得上。
- **列名**:用原表头(中文照用),一律要求写在双引号里。规范化:去首尾空格、连续空白并成一个、去掉双引号和控制字符、最长 60 字符;空表头叫 `column_3`;重名(不分大小写 —— DuckDB 的标识符不分大小写)加 `_2`、`_3`;另有固定列 `_row`。
- **工具说明与全部固定文字**的英文原文在 §3.4。要点:什么时候用;先看表结构;单条 SELECT;列名加双引号;文本列要算就显式转换并说明;行列互换用分组和条件聚合(透视语句会被展开成多条而被拒);结果有行数上限;可能有合计行。
- **注册条件是「库里有表格文件」,不是「表像数据」**:很多 xlsx 是问答表、清单、话术表。不为此加判断机制;对「列全是文本」的表,看表结构的结果里多一句提示(§3.4),并在护栏里专门量这类库有没有被带偏(§5.3)。
- **结果**:一张 Markdown 表(租户文字,放 `content`)+ 说明行(平台文字,放 `notice`):用到的表的编号、返回了多少行 / 是否截断、不规整提醒、被挡下的文档及原因。
- **写错了**:报错回给模型,模型可以改了再调;同一轮连续 3 次执行失败后,工具改为只返回平台文字「先看表结构,或换一种问法」,不再执行。
- **智能体怎么知道哪份文档是表**:检索结果的 `notice` 里多一行,列出本次结果里哪些文档号有表格数据(取自文档行的 `table_count`,检索本来就读文档行,`tools/knowledge.py:901-905`)。不改结果正文和标头。R3 的清单同样处理。
- **并发**:每次运行同时最多 1 个表格查询(同批并行的排队);每个租户在每个副本上同时最多 1 个;每个副本同时最多 2 个;等不到超过 2 秒返回「稍后再试」。

**停用 / 改过的段(用户已定)**:文档里只要有一段被停用(手工的,或系统连带停的)或被手工改过,这份文档的表**不装进这次的库**,结果的说明行写明是哪份、哪种原因;手工新增的段不算。恢复办法是把那一段恢复启用 / 撤销修改;**重新上传恢复不了**(重新入库会把停用和修改带到新版本)。文档详情页同样说明。

**出处**(`#T` 方案仍成立):用到的每张表登记一个出处,编号 `D12#T1`;对象沿用 4a 的形状,多 `"kind": "table"`、没有 `chunk_indexes`、`heading_path` 是 `[工作表名]`、`fingerprint` 是表内容的哈希。「用到了哪些表」:优先用 DuckDB 的接口从语句里取表名(**未验证**);取不到就把这次装进去的表都登记。只看表结构不登记出处。4a 的识别函数要多认 `#T`(§4.5)。

#### 3.1.6 入库、补算、数据模型

- **入库**:写表格数据和写段落在同一个事务、同一个围栏里。清空旧数据不受开关控制(每次重新入库都清);写入新的才看开关。读不了、超限不影响文档入库,原因记在文档上。入库这一步不调任何模型、不用 DuckDB,估价单不变。
- **补算**(用户已定:免费):手工命令,先空跑只打印数字,`--apply` 才写。写的事务里锁住文档行再比一次:启用、有在服务的段、代数没变、原文件哈希没变,才写。在解析进程池里跑、一次一份(读原文件吃内存)。没有保留原文件的文档跳过。
- **已有的表格段落**原样保留,继续检索。
- **迁移**(一个):新表 `knowledge_table`(`id`、`tenant_id`、`kb_id`、`document_id` 外键级联删、`table_index`、`sql_name`、`sheet_name`、`title`、`row_count`、`columns`、`sample_rows`、`content_hash`、`irregular`、`data` 字节);`knowledge_document` 加 `table_count`(默认 0)、`table_data_note`(可空)。只加不改。读表的查询一律带租户条件;行级策略照现有表的写法加,但不把它当兜底。

**跟着变的地方**:写段落的存储方法(两套实现);删文档 / 删库 / 租户清理(靠外键级联,各加断言);入库流程与评测用的本地入库路径(`ingestion.py:545-702`);文档协议对象、控制台文档接口与详情页;工具注册、隐式工具名清单(`agent_spec.py:1408-1418`)、大结果外置豁免清单(`tools/overflow.py:124-126`)、外发工具清单(`outgoing_reference.py:45`);构建缓存的键(「绑定的库里有没有表」,先例 `tools/knowledge_catalog.py:313-325`);检索结果的 `notice`;管理端工具时间线;评测答题循环(现在每题最多 3 次检索、3 次读文档、8 轮,`tools/eval/kb_agent_answer.py:33-37`:表格工具单独计数、最多 4 次,总轮数提到 10);部署清单(执行容器)。

#### 3.1.7 这条路相对「模型填条件」多出来的风险与成本,以及退路

| 多出来的 | 具体 |
|---|---|
| 新依赖 | `duckdb`:MIT 许可;PyPI 上有 Python 3.12 的预编译包,Linux x86-64 约 24 MB、arm64 约 22 MB(2.0.0 的数字,各版本不同);进控制面镜像(执行容器用的是同一个镜像),**只在执行容器的代码里导入**;解开后占多少**未验证**。版本钉死到具体小版本,升级要重过安全对照。不装任何扩展、运行时不联网 |
| 执行不受信任的 SQL | §3.1.4 的五层;剩余风险写在那一节末尾 |
| 多一个容器 | 每个控制面副本多 1.5 GiB 内存、1 核的限额;部署清单多一段;发布和健康检查多一个对象 |
| 审查面变大 | 每次升级 DuckDB、每加一种能力都要重过安全对照;所以安全对照做成常设测试 |
| 模型写错语句 | 方言不熟会多走几步;四家模型写 DuckDB 方言的能力**未验证** |

**退路**(事先定好):

| 什么不过 | 退到哪 |
|---|---|
| 安全对照里有任何一条「该拒的没拒」,且在钉住的版本上修不了 | **附录 B 第一档**:数据、DuckDB、执行容器都留着,但模型不再写 SQL —— 模型填条件,平台拼出只含 `c1`…`cN` 的语句再执行 |
| 第 0 步探针不达标:先把每表行数上限降到 10,000 再量;**仍不达标**,或新依赖进不了镜像 | **附录 B 第二档**:数据改存 Postgres 行、平台拼 Postgres 查询,不用 DuckDB、不要执行容器 |
| 某一家模型写的语句长期大比例被拒 | 不退:那一家的智能体多走几步;如实报 |

#### 3.1.8 边界情况与不做什么

| 情况 | 处理 |
|---|---|
| 表头不在第一行、两行表头、一张工作表几块表、小计行 | 标「疑似不规整」,每次结果提醒;数可能不对 |
| 模型用了不存在的表或列 | DuckDB 的绑定错误 + 可用的表和列 |
| 模型写了第二条语句、写操作、读文件、联网 | 第 3 层或第 2 层拒绝;固定的平台文字 |
| 查询超时 / 内存超限 | 固定的平台文字「请缩小范围或先聚合」;被杀的只是这一次的一次性进程 |
| 文档不在绑定的库里 / 是别的租户的 | 「没有这份文档」,与不存在同一说法 |
| 模型点了 3 份文档,其中 1 份被挡 | 另外 2 份照装;说明行写明被挡的那份和原因 |
| 重新入库后表变了 | 旧回答里的编号指纹对不上,界面提示「表格已变更」 |
| 子智能体 | 随 `knowledge` 配置继承;不能单独关 |

**不做**:Word / PDF / 幻灯片里的表格;任何写操作;装扩展;读外部文件或网址;跨租户 / 跨库的表;用模型生成表格摘要或抽字段;导出整表;画图。

#### 3.1.9 依据

| 结论 | 支持 | 反对 / 风险 | 状态 |
|---|---|---|---|
| 表格题靠读文字答不好 | 切段后每段只有几十行 | 没量过 | **未验证**(§5.2 改动前一臂) |

| `bases` | 可选,绑了两个以上库时才有:`K1`、`K2`(与 `knowledge_search` 同一套代号和校验)。目录外的库(超过 20 个时)没有代号,只能在不填时被列到 |
| `order` | 可选:`number`(默认,文档号从小到大)或 `newest`(文档号从大到小;文档号按首次上传递增,重传不变) |
| `after` | 可选:上一页最后一个文档号。不用页码 —— 文档号唯一且递增,用它当游标,中途有人上传、删除、停用都不会让后面的页错位 |
| `limit` | 默认 20,最多 50 |

- **列哪些文档**:「启用且有在服务的段」的文档。这个判断做成**一个存储层方法**,`knowledge_list_documents`、`knowledge_table`、按名找三处共用(按名找现在只看启用,改成同一个判断后,一份从没入库成功的文档不会再出现在候选里 —— 行为变化很小,写进 PR 说明)。重新入库中的文档有旧版在服务,照列,总数不抖动。
- 每一行:`D12 · 文件名 · 标题(不同才有)· 库代号 · 上传日期 · 段数`。文件名超过 120 字符截断。
- 说明行(平台文字):这一页多少份、符合条件的**准确总数**、涉及哪些库、下一页用的 `after` 值、哪些文档号有表格数据(R2 开着时)、还没入库成功的文档数。
- 零结果分两种说:名字没有匹配;库里没有文档。
- 工具说明与固定文字的英文原文在 §3.4。
- **出处**:清单里的 `D12` 只有文档号,按 4a 的规则不能当出处;清单结果不算「本轮显示过段落」。
- `knowledge_read` 的候选清单超过 10 个时那一行,在本工具已注册的构建里多一句指向本工具(平台文字);没注册时逐字节不变。

#### 3.2.3 协议 / 迁移

没有迁移。工具元数据 `{"status", "total", "shown", "next_after", "refs"}`,不带内部 id 和库名。新增一个存储方法(多库、名字过滤、游标、总数;两套实现)。

**跟着变的地方**:工具注册;隐式工具名清单;大结果外置豁免清单;外发工具清单(`name` 也是外发参数);管理端工具时间线;评测答题循环;`knowledge_read` 那一行提示;按名找改用共用判断。

每次模型调用多付的 token:**没量**(估 120~160);实现时量出来写进 PR。

#### 3.2.4 边界情况

| 情况 | 处理 |
|---|---|
| 上千份文档 | 每页最多 50;第一页的说明行就有总数 |
| 选了不属于本智能体的库代号 / 绑定的库都不存在 | 与 `knowledge_search`、`knowledge_read` 同一个报错 |
| 没有文档号的文档(应为 0) | 用文件名代替编号,排在最后,不能当游标 |
| 同名文档 | 各列一行 |
| FAQ 库 | 见 §4.5 |
| 旧清单结果被压缩 | 走通用处理,不做专门的可找回引用(V13) |

#### 3.2.5 不做什么

按内容关键词聚合文档(K-13 原方案);按元数据 / 标签 / 时间过滤;文档摘要;列出停用文档的名字;把文档清单放进系统提示词(破坏提示词缓存,`knowledge_catalog.py:15-17`)。

#### 3.2.6 依据

|---|---|---|---|
| 需要这个工具 | 目录只有分档数,按名找最多 10 个 | 这类问题占多少没数过 | 现状已验证;需求量**未验证** |
| 多一个工具不带偏别的题 | — | 工具越多越容易乱用 | **未验证**(§5.3 护栏) |

#### 3.3.2 测量设计

9 条用例、每条重复几次,结果会被一两条用例左右,说明不了问题。所以:

**用例**:新造 **30 条指代明确**的合成用例(**至少 8 条是英文或中英混合的对话**;九类指代对象都有,且分散在互不相干的领域;每条的前文里至少有两个同类候选;追问必须检索才能答 —— 答案不在上一轮的结果里;每条的对象名带常见的别写法,例如日期的几种写法)。现有 9 条降为**开发集**,只用来调判据脚本,不进判定。

**一次试验**怎么算错。前提两条:这一轮有成功的 `knowledge_search` 调用;这一轮所有检索词里,要么没有该指对象的名字(复数指代要求**全部**名字都在),要么写的是别的候选的名字。在这个前提下分两类,分开报:

- **甲类(答错对象)**:回答里出现的是另一个候选的事实。
- **乙类(漏答)**:回答里既没有该指对象的事实、也没有别的候选的事实 —— 没搜到、或答「资料没写」。检索词没补全最常见的后果是这一类,也正是改写能治的。

主模型自己想错了对象、但检索词写得明明白白的,两类都不算 —— 那种错改写治不了。

**按用例计,不按试验计**:每条用例跑 5 次;5 次里有 2 次以上算错(甲、乙合计)的,这条用例记为「稳定出错」。这一轮没有检索的试验不计;一条用例有效试验不到 3 次的,不进分母。

**判错的试验全部人工过一遍**(最多 150 条,多数应为 0)再下结论 —— 防字面匹配的误判。

**事先定死的判据**(看结果之前可以改,之后不行):

| 结果 | 结论 |
|---|---|
| 稳定出错的用例 ≥ 4 条(约 13%;甲、乙合计) | **做**:进入 §3.3.3 的选型 |
| 稳定出错的用例 ≤ 1 条 | **不做**:R4 关闭,保留现有规则和计数器 |
| 2~3 条 | 不自动下结论:把这几条的对话明细(标明甲类还是乙类)摆给用户定 |
| 进分母的用例不到 20 条 | 测量作废(模型多数没检索),先改用例 |

**模型**:只用平台默认答题模型跑(30 × 5 = 150 次多轮对话)。另外两家厂商不在本次范围;结论是「做」时,在验收阶段再各跑一遍。**结论的适用范围**:只对平台默认模型成立;中文和英文分开报数,哪种语言的用例不足 8 条有效,就写明结论对那种语言不成立。

**证明指标咬得住**(离线重算,不花钱;任一条不成立则测量作废、先修脚本):

| 对照 | 做法 | 必须看到 |
|---|---|---|
| 检索词换成用户原话 | 每次试验的检索词换成那一轮的原始追问,回答换成另一个候选的事实 | 每条用例都判错 |
| 检索词换成点了名的 | 检索词换成对象名(含别写法),回答不动 | 没有一条判错 |
| 检索词换成另一个候选的名字 | 同上,回答换成那个候选的事实 | 每条都判错(新用例都有别的候选,这条对照处处有定义) |

**标定与验收分开**:开发集(旧 9 条)调脚本;新 30 条只用于这次判定。结论是「做」时,这 30 条降为开发集,另造留出集做验收。

#### 3.3.3 两种做法的草图(**暂缓**)

| | 甲:带条件的独立改写 | 乙:工具侧退回一次 |
|---|---|---|
| 做法 | 检索词里还有指代词(启发式)时,用辅助模型看最近几轮把它改写成自带主语的,再搜;失败用原词 | 同样命中时,工具不搜,返回平台文字「检索词里还有指代,请写出名字后重试」;同一轮只退回一次 |
| 多花什么 | 命中时多一次辅助模型调用 | 命中时多一步主模型调用 |
| 参考 | 两家的改写都在非智能体流程里;用在「模型写的检索词」上没有先例 | 没有先例;与「规则写在参数上」的现有方向一致 |
| 风险 | 辅助模型看的历史少,可能改错对象且更隐蔽 | 启发式误伤时多走一步,不会卡死 |

两种都依赖启发式的准头,而它现在只有中文(量词 + 指示词)和英文代词两套规则(`outgoing_reference.py:60-84`),别的语言的对话永远不会命中 —— 真要做,这两种草图都只对中文和英文有效,要么先补语言,要么写明限制。第一步是给计数器补分母。

#### 3.3.4 不做什么

测量结果出来之前不写任何产品代码;不把「当前对象」交给对接方传(11-05 已否决);不为每次检索无条件加一次改写调用。

### 3.4 平台文字原文与跨场景检验

下面是这一批新增的、会被模型读到的全部平台文字。不带任何示例表名、列名、领域词;`D12`、`K2` 是平台自己的编号写法(现有工具说明里已在用);花括号里是程序填的编号和数字。实现时逐字用这些文本,改动要重过评测。

**`knowledge_table` 的说明**:

```text
Run one read-only SQL query over the spreadsheet documents of the knowledge bases knowledge_search searches. Use it when the answer has to be computed from many rows: counting, totals, averages, ranking, filtering by a condition, grouping by a period or a category, or combining several sheets. For what one row or one piece of text says, use knowledge_search or knowledge_read. documents takes one to three document references (D12). Call it without sql first: the result lists each table of those documents with its SQL name, its row count, three sample rows and its columns (name, type, value range or distinct values). Then pass sql: a single SELECT statement in DuckDB SQL over those tables. Write every column name in double quotes exactly as listed. A column typed as text holds text even when its values look like numbers, dates or amounts; convert it in SQL only if the question needs a computation on it, and say in your answer that you converted it. To turn rows into columns, use GROUP BY with conditional aggregates. A result shows at most 200 rows, so aggregate in SQL instead of reading rows. A table may hold subtotal or total rows; leave them out when you add values up. Only what a query returned is evidence: the structure of a table alone is not.
```

参数:`documents` —— `One to three document references, e.g. D12.`;`sql` —— `A single SELECT statement in DuckDB SQL. Omit it to see the tables and their columns.`

**`knowledge_list_documents` 的说明**:

```text
List the documents of the knowledge bases knowledge_search searches: reference, file name, title and upload date of each, and the exact total. Use it to see what the knowledge bases hold, to count documents, or to find a document by part of its file name or title. name keeps the documents whose file name or title contains that text, compared literally and ignoring case. Documents are listed by document number; pass the last reference of a result as after to get the next ones. A reference from the list can be passed to knowledge_read. The list says which documents exist, not what they say: read a document before stating anything about its content.
```

参数:`name` —— `Text the file name or title must contain.`;`bases` —— 沿用 `knowledge_search` 的原文;`order` —— `number (default, oldest first) or newest.`;`after` —— `The last reference of the previous result, e.g. D12.`;`limit` —— `Documents per result (default 20, at most 50).`

**固定文字**(都放 `notice` 或报错,不混租户文字):

| 用在哪 | 原文 |
|---|---|
| 检索结果里有表格文档(R2 开着) | `[table data: {refs} are spreadsheet documents; knowledge_table can count, total, sort or filter their rows]` |
| 列文档结果的说明行 | `[documents {first}-{last} of {total} in {bases}; next: after={ref}]`;没有下一页时没有后半句;有表格文档时再加上一行同上的 `[table data: …]`;还没入库成功的:`[{n} more documents are not ready and are not listed]` |
| 列文档零结果 | `[no document name contains that text]` / `[these knowledge bases hold no documents]` |
| `knowledge_read` 候选超过 10 个时多的一句 | `knowledge_list_documents lists every match.` |
| 表格查询结果的说明行 | `[tables used: {refs}; {n} rows returned]`;截断时 `[tables used: {refs}; first 200 rows of a longer result]` |
| 表疑似不规整 | `[{ref} may not be one regular table: its header row or its blocks are unclear. Check the sample rows before relying on totals]` |
| 表的列全是文本 | `[every column of {ref} is text: it is a list of text entries, not numeric data. knowledge_search usually answers questions about it; use SQL on it only to count or filter entries]` |
| 列看着像数或日期但写法有两种读法 | 列类型处写 `text (values look like numbers or dates in a format that can be read two ways; not converted)` |
| 文档的表不可查(有段被停用 / 被改过) | `[the table data of {ref} is not available: a passage of this document was switched off]` / `[… was edited]`,后接 `[knowledge_search and knowledge_read show its current text]` |
| 没有这份文档(不存在、别的租户、没绑定的库,同一句) | `no document {ref} in this agent's knowledge bases` |
| 文档没有表格数据 | `document {ref} has no table data` |
| 语句不合规 | `[nothing was run: pass exactly one SELECT statement]` |
| 访问被拒及其它不带原文的错误 | `[the query could not be run: files, network access and settings are not available here]` |
| 超时或内存超限 | `[the query was stopped: it took too long or needed too much memory. Add a condition, or aggregate instead of returning rows]` |
| 连续 3 次失败 | `[not run: three queries in a row failed in this turn. Look at the table structure again by calling without sql, or answer with what you have and say what could not be computed]` |
| 排队超过 2 秒 | `[the table service is busy; make this call again in a moment]` |

**跨场景检验**(拿六种不相干的表过一遍,每种写一条「这段文字会被怎么读错」;挡不住的如实写):

| 场景 | 哪句、怎么读错 | 现在的措辞挡不挡得住 |
|---|---|---|
| 订单 / 流水 | 「leave total rows out」:表里有一**列**叫合计,模型把这一列排除 | 写的是 rows;挡得住多数,残留靠看样例行 |
| 人员排班(日期横着排成列的交叉表) | 「grouping by a period」:模型按日期分组,而日期其实是列名 | 入库时这类表会被标不规整,不规整提示要求先看样例行;「rows into columns」那句不适用于反方向,残留 |
| 设备 / 库存台账 | 「convert it in SQL」:模型把序列号、资产编号这类文本列转成数去算 | 限定为「only if the question needs a computation on it」;短编号被误判成数值列时挡不住(§3.1.2 已知限制) |
| 问卷 / 工单(大段文字) | 「filtering by a condition」:问「大家怎么评价某件事」,模型去写 `LIKE` 而不是检索 | 说明第三句把「一行或一段文字说了什么」指回检索;全是文本列的表另有提示。按类别数回答数是正当用法,所以提示写的是 usually |
| 问答表 / 话术表 | 每次检索的 `[table data: …]` 提示把模型引去查表,而答案就在检索到的那一段里 | 提示只说能 count / total / sort / filter;残留用护栏里「答案在文字型表格里」的 8 题量(§5.3) |
| 测量 / 检验记录(带单位) | 「values look like numbers」:`12 mg` 这样的列是文本,模型不转换就比较大小,得到按字典序的结果 | 说明写明文本列「holds text」并要求转换时说明;模型不转换就比较的情况挡不住,列类型在表结构里是明示的 |

## 4. 对现有行为的影响与兼容

### 4.1 对接方

已有接口不变。R2 / R3 开关开了且智能体用到时,工具调用事件里会出现两个新的工具名,出处里会出现表格这种新形状;对外文档里没找到「工具名是开放集合」的明文(V10),按「已有枚举新增取值」提前通知 —— 新工具名由 L1、D2 各自写进更新记录,表格出处由 D3 写。深护智康的对接不需要改代码。

### 4.2 已有的库与文档

已有的表格文档在补算之前没有表格数据,智能体看不到表格工具。按名找文档改用「可服务文档」的共用判断后,从没入库成功的文档不再出现在候选里(§3.2.2)。

### 4.3 每轮多花多少 token(只在对应开关开着时)

| 位置 | 多多少 | 谁付 |
|---|---|---|
| `knowledge_list_documents` 的说明 + 参数 | 没量(估 120~160) | 绑了库的智能体的每次模型调用;在可缓存前缀里 |
| `knowledge_table` 的说明 + 参数 | 没量(估 180~260) | 只有库里有表格数据的智能体 |
| 检索结果的表格提示行 | 约 10 | 只有结果里有表格文档时 |
| 模型写的 SQL、看表结构的结果 | 每次查询几百 | 只在用到时 |
| 没绑库的智能体 | 0 | — |

### 4.4 资源与回滚

- R2:一次查询 = 主进程读出几张表的字节、经本地套接字交给执行容器、装载、执行,硬上限 8 秒;每个控制面副本多一个容器(1.5 GiB、1 核)。入库不多读文件。R3:一次带总数的查询。
- 回滚:两个开关各自关掉即回到改动前;迁移只加不改。`duckdb` 和执行容器都在 D2 里,回退 D2 即去掉。

### 4.5 与 FAQ 库(4c E3)、4c 图片编号的交界(规则:谁后合谁补)

## A.2 方案

**四项已拍板的推荐(B-175 §9 原文)怎么落**:

| # | 原推荐 | 本文 |
|---|---|---|
| 1 | 「第一期只开『只检索』档」 | 列库 + 检索 |
| 2 | 「锁定前缀收紧为 `/v1/knowledge/`,对外用 `/v1/knowledge-bases`」 | 照做;收紧单独放在 P1,改前改后自查覆盖的控制台路由数必须相同 |
| 3 | 知识库拆出独立权限资源:「拆」 | 拆;三个角色的权限与今天借用 `manifest` 时逐格相同 |
| 4 | 「能力 × 库白名单 × 默认拒绝」 | 照做;另加每库「允许对外」开关(B-175 §8.2 原文已有) |

**接口**:

| 方法 + 路径 | 能力 | 做什么 |
|---|---|---|
| `GET /v1/knowledge-bases` | `kb:read` | 列出这把 key 被授权且对外开关开着的库:`name`、`document_count`。`limit`(1~200,默认 50)+ `offset` + `total` |
| `POST /v1/knowledge-bases:search` | `kb:search` | 在指定的库里检索,只返回段落 |

检索请求:`query`(1~500 字符)、`knowledge_bases`(库名数组,1~20 个,每个都要有 `kb:search` 授权;不提供「不填 = 全部」)、`top_k`(1~20;不填按 4a T5 的规则)。请求体不接受租户。

检索返回(`data`):

```json
{"results": [
   {"content": "这一段的文字", "knowledge_base": "库名",
    "scores": {"rerank": 0.83, "vector": 0.61},
    "source": {"ref": "D12#7", "doc_seq": 12, "chunk_indexes": [7, 8],
               "title": "文档标题", "filename": "原文件名",
               "heading_path": ["第三章", "3.2 退货"],
               "locator": [{"type": "pdf", "page": 14}],
               "fingerprint": "9f2c41d07ab3e655"}}],
 "status": "ok", "truncated": false,
 "degraded": {"rerank": true}, "unsearched_knowledge_bases": []}
```

- **一条结果** = 一个大段的文字,和智能体看到的一条结果是同一个东西。`source` 就是 4a 的出处对象,由同一个函数生成。
- **大小上限**:全部 `content` 合计最多 60,000 字符;超了从排名最低的丢起,`truncated: true`。
- **与智能体工具的关系**:同样的库、查询、条数,智能体工具显示的编号序列是接口返回序列的**前缀**(工具另有 1 万字符的显示预算,会少显示低位结果);命中测试(不覆盖参数时最多 50 条)与接口之间也是前缀关系。
- `scores` 只保证在**这一次请求内**可比(4a §0.2 第 4 条);没有重排时没有 `rerank` 键。对外文档写明不要拿它卡固定数值。
- `status`:`ok` / `no_results` / `below_threshold`(候选都没过库的相关度门槛)。
- `degraded`:只在降级时出现(重排失败退回召回顺序、嵌入失败只用关键词)。`unsearched_knowledge_bases`:授权通过、但这一次两条召回路都失败的库;有结果时 200 并列出,一条结果都没有时 503。
- 文档号是全租户递增的:只被授权一个库的对接方,能从文档号看出这个租户文档总量的量级。4a 的编号就是它,本文接受(启动时拍板(A.9))。

**三道闸**(一条联表查询一次判完,不让「不存在」比「没授权」少一次查询):

| 顺序 | 检查 | 不过 |
|---|---|---|
| 1 | key 档位(至少 `read`)→ 角色有 `knowledge:read` | 403 `FORBIDDEN`(现有) |
| 2 | 请求里每个库:本租户存在,且这把 key 对它有任一能力的授权 | 404 `KB_NOT_FOUND`。不存在、别的租户的、没授权,响应**逐字节相同**。有一个不过整个请求不过 |
| 3a | 对这些库都有本次操作需要的能力 | 403 `CAPABILITY_REQUIRED` |
| 3b | 这些库的「允许对外」开关都开着 | 403 `KB_API_DISABLED`,`message` 列出没开的库名(调用方对它们有授权,看得见名字) |

几种不过同时出现时按表里的顺序报第一种。新建的 key 一条授权都没有:列库为空,检索任何库都是 404。新建的库不会自动出现在任何 key 的授权里。

**授权怎么管**(控制台,只有 admin:`api_key:write`):密钥页勾选能力和库;库设置页的「允许通过开放 API 检索」开关。增删改都写审计。

- **授权按轮换链生效**:授权不存在某一把 key 的行上,而是存在「这条轮换链的第一把 key」名下;轮换出来的新 key 记着链头。所以轮换不用复制授权,改一次对链上所有还有效的 key(含宽限期内的旧 key)立即生效。
- 吊销不删授权行(key 行本来就不删);链上没有有效 key 时,这些授权没人用得到。删库时该库的授权行级联删除。

**成本与额度**(先算账,再定规则):

| 项 | 数 | 依据 |
|---|---|---|
| 一次检索送重排的候选 | 50~100 个,每个最多 3,000 字符 + 查询 | `tools/knowledge.py:293,487-490` |
| 最坏一次的重排量(「中文 1 字约 1 token」「查询 500 字符」都是按中文资料估的口径,**R1 启动时按当时的语料和价目重估**) | 100 ×(3,000 + 500)字符,再加「只看正文」那一路的 20 个候选 ≈ 42 万字符;按中文 1 字约 1 token 计 ≈ 42 万 token | 双视图(`tools/knowledge.py:104-105`) |
| 重排单价 | 仓库价目里没有重排模型的行;按 B-206 设计里写的 ¥0.5 / 百万 token 估 | **未验证**,P3 开工前按生产价目表重算 |
| 最坏一次 | 高估值约 ¥0.21;按现有的单次重排上限(12 万 token,超了会裁候选)约 **¥0.1**。嵌入那一次不到 ¥0.001。「用聊天模型重排」的配置(`usage_metering.py:38-40`)没算 | 目录注释里的整次上限(`protocol/model_catalog.py:837`);`llm/rerank.py:143-152` |
| 一般一次 | 段落 500 字左右、查询 50 字:约 ¥0.03 | 估算 |
| 每租户每天最坏 | 日上限 1,000 次:高估 ¥210,按现有上限约 **¥100**;一般约 ¥30 | — |
| 不设日上限会怎样 | 每 key 每秒 1 次 = 一天 8.6 万次,最坏约 ¥1.8 万 / key / 天 | 所以必须有日上限 |

规则(都在通过三道闸**之后**才扣;没授权的请求只受现有租户大桶限制,它们不花嵌入和重排的钱):

1. **每 key 限速**:容量 5、每秒回补 1。超了 429 `RATE_LIMIT_EXCEEDED`,`dimension: "kb_search"`。同租户的两个对接方互不挤占。
2. **每租户日上限**:默认 1,000 次 / 滚动一天。走现有的**配额服务**,加一个维度 `kb_search_count_1d`(与已有的「30 天上传次数」同一种做法:容量 = 上限、按「上限 ÷ 一天」慢慢回补,`protocol/quota.py:57-62`;配额检查本来就是故障时拒绝)。要补一处:现有次数配额在租户没有这一维度的配置行时不生效(`api/external_artifacts.py:325`),本维度没有配置行时必须用平台默认值。超了 429 `RATE_LIMIT_EXCEEDED`,`dimension: "kb_search_count_1d"`。
3. 每 key 限速用现有限流接口(只有令牌桶,`ratelimit/base.py:37-48`);后端报错时**拒绝**(503)。没配 Redis 的部署是进程内计数、每个副本各数各的,只适合本地开发(V19)。
4. **一把 key 能用光全租户的日额度**:每秒 1 次,约 17 分钟就是 1,000 次,同租户别的对接方当天就查不了。本期不做每 key 的日份额(配额服务按租户记);这个后果在 启动时拍板(A.9)交给用户定。
5. 429 用对外信封,自己实现(现有的专用桶先例抛的是控制台形状的错误,不能照搬)。

**用量**:每次检索记一行,新类别 `knowledge_open_api`,记在调用方租户名下。查询嵌入的 token 取厂商返回值(现有机制,`llm/embedder.py:63-80`);专用重排接口的 token 今天哪里都不记,本期只在检索记录里记「重排了多少个候选」。一期**不向租户收费**(与对话内检索同口径);成本在运营用量页按类别看得到,上限由日上限封住。是否改为收费启动时拍板(A.9)。

**检索记录**:每次写一行,来源 `open_api`;`actor_id` 记服务账号 id,`flags` 记 `api_key_id`。不含任何终端用户标识,所以不需要新的清除路径;按保留期清理。

**报错**:新增三个码 `KB_NOT_FOUND`(404)、`KB_API_DISABLED`(403)、`CAPABILITY_REQUIRED`(403);新增两个 `dimension`;其余沿用(字段不合法或含 NUL 字节 422 `INVALID_REQUEST`;检索超时走现有的 504;没配嵌入模型 503,同命中测试 `api/knowledge.py:1409-1413`)。

**文档与通知**:对外文档新增一页「知识库检索」;`auth.md:48` 的「Key 只能访问…」补上新前缀;`errors.md` 加码和 `dimension`。更新记录的分类表里没有「新增接口」这一类(`changelog.md:9-13`),本文按**提前通知**处理:先以「待发布」列出,再发布。

**平台开关** `kb_open_api`,默认关。**路由始终挂载**;关着时处理函数直接回 404 信封(与「没有这个功能」一样),控制台不显示授权勾选和库开关。这样锁定自查、对外自查在默认配置下就能看见并覆盖这两条路由。

## A.3 数据模型 / 迁移

一个迁移:

- 新表 `api_key_knowledge_grant`:`grant_root_id`(链头 key 的 id,外键,**级联删** —— 删服务账号时 key 行会被删)、`kb_id`(外键,级联删)、`tenant_id`、`capability`(`kb:search` / `kb:read`)、`granted_by`、`granted_at`;主键(`grant_root_id`, `kb_id`, `capability`)。写入时校验链头 key、库、授权行三者同租户;读取的联表查询三张表都带租户条件。
- `api_key` 加可空列 `grant_root_id`(轮换时填:旧行有就沿用,没有就填旧行的 id)。一把 key 的**有效链头** = 这一列有值取它,否则取自己的 id。
- `knowledge_base` 加列 `api_access_enabled`,默认假。

只加表加列,老代码不读它们。**租户隔离靠查询条件本身**:行级策略照现有表的写法加上,但运行期是否强制以 ROADMAP 的记录为准(「接受单层隔离首发」,`docs/superpowers/ROADMAP.md:113`),本文不把它当兜底。

| 权限拆分 | 三个角色 × 全部知识库路由的允许 / 拒绝表,拆分前后逐格相同 |

**必须变红的对照**(单测):去掉一条对外路由的 `external_only()` → 对外自查失败;把对外路由挂到控制台路由器上 → 自查失败;某条路由不声明能力 → 能力自查失败;授权判断改成「为空 = 全部」→ 默认拒绝的测试失败;轮换不写链头 → 轮换链测试失败;知识库路由里写回 `manifest` → 测试失败。

# 附录 B:R2 的退路 ——「模型填条件」(第 3 版的方案,压缩保留)

用户 11-11 选了「模型写 SQL」。本附录是 §3.1.7 的退路,触发条件写在那里。第二档的完整文字(存储、语句形态、保护、边界情况)在 PR #2076 的提交 `02e9a55bd` 的 §3.2,合并后仍可从该 PR 的提交历史里找到。

**共同点**:入库读表、定类型、标不规整、大小上限、补算、停用 / 改过段的处理、出处编号 `D12#T1`、工具名与开关,两条路相同。区别只在「谁写查询」和(第二档)「数据放哪」。

**模型填什么**:

| 参数 | 说明 |
|---|---|
| `table` | `D12` 或 `D12#T2` |
| `where` | 最多 8 条,同时满足:等于 / 不等于 / 大于 / 大于等于 / 小于 / 小于等于 / 包含 / 属于一组值(最多 50 个)/ 为空 / 不为空;单个值最长 200 字符 |
| `group_by` / `aggregate` / `order_by` / `select` / `limit` | 最多 3 列分组;最多 5 个统计(计数、去重计数、求和、平均、最小、最大);最多 2 个排序;明细最多 20 列;默认 20 行、最多 100 |

只给 `table` = 看表结构。做不了:按月 / 季分组、计算列、分组后筛选、每组前 N、「或」、跨表。

**安全性质**:模型给的只有「哪一列、哪个操作、什么值」。拼语句的函数不接收任何字符串,只接收形状(枚举值和个数);列位置和值都作为参数传;语句写成两层(内层给列起固定别名 `f1…f8`、`g1…g3`、`a1…a5`、`s1…s20`,外层只引用别名分组排序),所以语句文本的集合是有限的、与模型输入无关。每种片段各有单测。

| 档 | 数据放哪 | 在哪执行 | 什么时候用 |
|---|---|---|---|
| 第一档 | 不变 | 平台拼出的语句仍在执行容器的 DuckDB 里执行;语句只引用物理列名 `c1`…`cN` 和固定别名,不含任何租户文字和模型文字,§3.1.4 的第 2~4 层不再承压 | 安全对照不过 |
| 第二档 | 改存 Postgres:`knowledge_table_row`(`table_id`、`tenant_id`、`row_number`、`cells` 显示文字数组、`vals` 带类型的值数组) | Postgres:只读事务、语句超时 3 秒、每条语句由同一个函数加租户和表的条件;每运行 1 个、每进程 4 个 | DuckDB 本身用不了(性能、依赖) |

**退回后评测的变化**:「进阶问法」一组从设线改回「不设线、单独报」;安全对照换成「条件值里塞 SQL 片段 → 当普通值」「换任意列名和值 → 语句文本不变」两条;其余的线不变。
