### 0.3 这一批治不了的

- R2 只对规整的表可靠(第一行是表头、一行一条记录)。不规整的表由程序标出来并在结果里提醒,但数可能不对(§3.2.4)。
- R2 的查询只有单表的筛选、分组、统计、排序。按月分组、计算列(单价 × 数量)、分组后再筛、每组前几名、「或」、跨表合计都做不了;评测里单独量这一类丢多少(§5.2)。
- R1 一期不做别家平台的协议适配(如 Dify 的外部知识库协议)。
- R3 回答「库里有哪些文档」,不回答「哪些文档讲了某件事」。

#### 3.1.2 方案

**四项已拍板的推荐(B-175 §9 原文)怎么落**:

| # | 原推荐 | 本文 |
|---|---|---|
| 1 | 「第一期只开『只检索』档」 | 列库 + 检索 |
| 2 | 「锁定前缀收紧为 `/v1/knowledge/`,对外用 `/v1/knowledge-bases`」 | 照做;收紧单独放在 P1,改前改后自查覆盖的控制台路由数必须相同 |
| 3 | 知识库拆出独立权限资源:「拆」 | 拆;三个角色的权限与今天借用 `manifest` 时逐格相同 |
| 4 | 「能力 × 库白名单 × 默认拒绝」 | 照做;另加每库「允许对外」开关(B-175 §8.2 原文已有) |

**接口**:

| 方法 + 路径 | 能力 | 做什么 |
|---|---|---|
| `GET /v1/knowledge-bases` | `kb:read` | 列出这把 key 被授权且对外开关开着的库:`name`、`document_count`。`limit`(1~200,默认 50)+ `offset` + `total` |
| `POST /v1/knowledge-bases:search` | `kb:search` | 在指定的库里检索,只返回段落 |

检索请求:`query`(1~500 字符)、`knowledge_bases`(库名数组,1~20 个,每个都要有 `kb:search` 授权;不提供「不填 = 全部」)、`top_k`(1~20;不填按 4a T5 的规则)。请求体不接受租户。

检索返回(`data`):

```json
{"results": [
   {"content": "这一段的文字", "knowledge_base": "库名",
    "scores": {"rerank": 0.83, "vector": 0.61},
    "source": {"ref": "D12#7", "doc_seq": 12, "chunk_indexes": [7, 8],
               "title": "文档标题", "filename": "原文件名",
               "heading_path": ["第三章", "3.2 退货"],
               "locator": [{"type": "pdf", "page": 14}],
               "fingerprint": "9f2c41d07ab3e655"}}],
 "status": "ok", "truncated": false,
 "degraded": {"rerank": true}, "unsearched_knowledge_bases": []}
```

- **一条结果** = 一个大段的文字,和智能体看到的一条结果是同一个东西。`source` 就是 4a 的出处对象,由同一个函数生成。
- **大小上限**:全部 `content` 合计最多 60,000 字符;超了从排名最低的丢起,`truncated: true`。
- **与智能体工具的关系**:同样的库、查询、条数,智能体工具显示的编号序列是接口返回序列的**前缀**(工具另有 1 万字符的显示预算,会少显示低位结果);命中测试(不覆盖参数时最多 50 条)与接口之间也是前缀关系。
- `scores` 只保证在**这一次请求内**可比(4a §0.2 第 4 条);没有重排时没有 `rerank` 键。对外文档写明不要拿它卡固定数值。
- `status`:`ok` / `no_results` / `below_threshold`(候选都没过库的相关度门槛)。
- `degraded`:只在降级时出现(重排失败退回召回顺序、嵌入失败只用关键词)。`unsearched_knowledge_bases`:授权通过、但这一次两条召回路都失败的库;有结果时 200 并列出,一条结果都没有时 503。
- 文档号是全租户递增的:只被授权一个库的对接方,能从文档号看出这个租户文档总量的量级。4a 的编号就是它,本文接受(§7.2 第 3 条)。

**三道闸**(一条联表查询一次判完,不让「不存在」比「没授权」少一次查询):

| 顺序 | 检查 | 不过 |
|---|---|---|
| 1 | key 档位(至少 `read`)→ 角色有 `knowledge:read` | 403 `FORBIDDEN`(现有) |
| 2 | 请求里每个库:本租户存在,且这把 key 对它有任一能力的授权 | 404 `KB_NOT_FOUND`。不存在、别的租户的、没授权,响应**逐字节相同**。有一个不过整个请求不过 |
| 3a | 对这些库都有本次操作需要的能力 | 403 `CAPABILITY_REQUIRED` |
| 3b | 这些库的「允许对外」开关都开着 | 403 `KB_API_DISABLED`,`message` 列出没开的库名(调用方对它们有授权,看得见名字) |

几种不过同时出现时按表里的顺序报第一种。新建的 key 一条授权都没有:列库为空,检索任何库都是 404。新建的库不会自动出现在任何 key 的授权里。

**授权怎么管**(控制台,只有 admin:`api_key:write`):密钥页勾选能力和库;库设置页的「允许通过开放 API 检索」开关。增删改都写审计。

- **授权按轮换链生效**:授权不存在某一把 key 的行上,而是存在「这条轮换链的第一把 key」名下;轮换出来的新 key 记着链头。所以轮换不用复制授权,改一次对链上所有还有效的 key(含宽限期内的旧 key)立即生效。
- 吊销不删授权行(key 行本来就不删);链上没有有效 key 时,这些授权没人用得到。删库时该库的授权行级联删除。

规则(都在通过三道闸**之后**才扣;没授权的请求只受现有租户大桶限制,它们不花嵌入和重排的钱):

1. **每 key 限速**:容量 5、每秒回补 1。超了 429 `RATE_LIMIT_EXCEEDED`,`dimension: "kb_search"`。同租户的两个对接方互不挤占。
2. **每租户日上限**:默认 1,000 次 / 滚动一天。走现有的**配额服务**,加一个维度 `kb_search_count_1d`(与已有的「30 天上传次数」同一种做法:容量 = 上限、按「上限 ÷ 一天」慢慢回补,`protocol/quota.py:57-62`;配额检查本来就是故障时拒绝)。要补一处:现有次数配额在租户没有这一维度的配置行时不生效(`api/external_artifacts.py:325`),本维度没有配置行时必须用平台默认值。超了 429 `RATE_LIMIT_EXCEEDED`,`dimension: "kb_search_count_1d"`。
3. 每 key 限速用现有限流接口(只有令牌桶,`ratelimit/base.py:37-48`);后端报错时**拒绝**(503)。没配 Redis 的部署是进程内计数、每个副本各数各的,只适合本地开发(V19)。
4. **一把 key 能用光全租户的日额度**:每秒 1 次,约 17 分钟就是 1,000 次,同租户别的对接方当天就查不了。本期不做每 key 的日份额(配额服务按租户记);这个后果在 §7.2 第 1 条交给用户定。
5. 429 用对外信封,自己实现(现有的专用桶先例抛的是控制台形状的错误,不能照搬)。

**用量**:每次检索记一行,新类别 `knowledge_open_api`,记在调用方租户名下。查询嵌入的 token 取厂商返回值(现有机制,`llm/embedder.py:63-80`);专用重排接口的 token 今天哪里都不记,本期只在检索记录里记「重排了多少个候选」。一期**不向租户收费**(与对话内检索同口径);成本在运营用量页按类别看得到,上限由日上限封住。是否改为收费见 §7.2 第 1 条。

**报错**:新增三个码 `KB_NOT_FOUND`(404)、`KB_API_DISABLED`(403)、`CAPABILITY_REQUIRED`(403);新增两个 `dimension`;其余沿用(字段不合法或含 NUL 字节 422 `INVALID_REQUEST`;检索超时走现有的 504;没配嵌入模型 503,同命中测试 `api/knowledge.py:1409-1413`)。

#### 3.1.3 数据模型 / 迁移

一个迁移:

- 新表 `api_key_knowledge_grant`:`grant_root_id`(链头 key 的 id,外键,**级联删** —— 删服务账号时 key 行会被删)、`kb_id`(外键,级联删)、`tenant_id`、`capability`(`kb:search` / `kb:read`)、`granted_by`、`granted_at`;主键(`grant_root_id`, `kb_id`, `capability`)。写入时校验链头 key、库、授权行三者同租户;读取的联表查询三张表都带租户条件。

#### 3.2.2 方案

**哪些文件**:`.xlsx` 和 `.csv`。Word / PDF 里的表格不做(表头、合并格、跨页都不可靠),继续当文字检索。

**一张表** = xlsx 的一张工作表,或一个 csv 文件。xlsx 的表头认法与 Markdown 解析用同一段代码,并从**同一次**打开工作簿的结果里同时派生 Markdown 和表格数据(不多读一遍文件)。csv 用我们自己的读法读表格数据;它与 MarkItDown 认的表头是否一致**未验证**(V3),不一致的 csv 标为不规整。

**每张表存什么**:

| | 内容 |
|---|---|
| 表 | 属于哪份文档、第几张、工作表名、标题、行数、列清单、内容哈希、「疑似不规整」的原因(可空) |
| 列 | 位置、表头文字(空表头叫 `column_3`;重名加后缀)、类型(`number` / `date` / `text`)、非空数、不是数的格数、数值 / 日期列的最小最大、取值不超过 20 种的文本列的全部取值 |
| 行 | 原表行号;`cells`(每格显示出来的文字,与段落一致)、`vals`(每格带类型的值:数 / 日期标准写法 / 文字 / 空) |

**类型怎么定**(程序算,不调模型):

- 每格先按固定写法试着读成数(正负号、小数点、千分位逗号、末尾 `%`)或日期。xlsx 里存成文本的数字同样这么读。
- 一列的非空格八成以上读得成数 → `number`;读不成的格在 `vals` 里是空,计入「不是数的格数」。八成是起点值(V4)。
- **看起来像编号的不算数**:有前导零或超过 15 位的,一律当文字。不带前导零的短编号(部分订单号、工号)挡不住,会被当成数值列;记为已知限制。
- 百分比:`vals` 存显示出来的数(61.12),列说明标明是百分比。其余数值用原始值,不按显示格式四舍五入 —— 所以对「显示成两位小数」的列求和,可能和把段落里看到的数加起来差一点;结果说明行会写明「按未四舍五入的值计算」。
- 公式格取缓存的结果;整列都没有缓存值时,列说明里标出来。
- 隐藏的工作表 / 行 / 列照读(与现有段落一致)。

**程序标「疑似不规整」**(只标记,不纠正;标了的表照样能查,但每次结果的说明行都会提醒):

| 信号 | 说明 |
|---|---|
| 表头行有三成以上是空的或重名 | 多半表头不在这一行,或是两行表头 |
| 数据第一行全是文字,而它下面的列大多是数 | 多半是第二行表头 |
| 数据中间有全空的行(在现有解析删掉空行**之前**判,`office_xlsx.py:94-100`),或「除一两格外全空」的行 | 多半是一张工作表里放了几块表,或有小计行 |
| 数据中途出现整行都是文字、而这些列大多是数 | 多半是第二块表的表头 |
| csv 的表头与 MarkItDown 认的不一致 | — |

**大小上限**(起点值,§7.2 第 5 条):每张表 50,000 行、200 列;每份文档 1,000,000 格、50 张表。超了不存成数据(文档照常入库、检索不受影响),文档上记原因。

**取舍一:怎么存**

| | 每张表建一张真的数据库表 | 进程内 DuckDB(WeKnora) | Postgres 的 JSON 行(本文选) |
|---|---|---|---|
| 表结构 | 租户传什么建什么,列名是租户文字 | 查询时现从原文件建 | 两张固定的表 |
| 租户隔离 | 靠表名,出错就是跨租户 | 进程内共用一个库 | 与段落表同一套:查询条件里带租户 |
| 迁移 / 备份 / 删除 | 动态建表不在迁移工具里 | 不落库,每个副本各装各的 | 普通的行;外键级联删 |
| 新依赖 | 无 | 一个本地库,装扩展要联网 | 无 |
| 资源 | 数据库管 | 吃控制面进程的内存和 CPU | 数据库管;语句超时 |
| 性能 | 最好 | 好 | 要扫全表,够不够**未测**(第 0 步) |

选第三种:隔离、删除、备份、多副本都和段落表同一套,不引入「动态建表」和「进程内引擎」两类新风险。

**取舍二:谁写查询**

| | 模型写 SQL | 模型填条件(本文选) |
|---|---|---|
| 注入 | 靠解析 + 拦截名单,名单补不完 | 结构上不存在(见下) |
| 跨表 / 跨租户 | 靠表名白名单、强行并条件 | 表由平台解析出来,模型给不了别的表 |
| 模型会不会用 | 很熟 | **未验证**(§5.2 + 三家冒烟) |
| 表达能力 | 强 | 弱:单表的筛选、分组、统计、排序 |

选「填条件」。评测不过线时的后备:模型写一小段 SQL 子集,平台解析成同一套条件再执行,模型的文字仍不进引擎。

**查询语句的形态(写死,实现不许偏离)**:

- 内层:从行表里取出需要的列,每列起**固定别名**(筛选列 `f1…f8`、分组列 `g1…g3`、统计列 `a1…a5`、明细列 `s1…s20`);列的位置和比较的值全部作为参数;租户 id 和表 id 的条件由**同一个函数**加在每条语句上。
- 外层:只引用这些别名做 `WHERE` / `GROUP BY` / 统计 / `ORDER BY` / `LIMIT`。(直接写「按第几列分组」并把列位置当参数传,数据库会报错;这样分两层就不需要把任何列位置拼进语句。)
- 所以语句的文字只取决于「几个筛选、各是哪种操作、几个分组、哪几种统计、排序方向」这些**形状**。实现上:拼语句的函数**不接收任何字符串**,只接收形状(枚举值和个数);列位置参数显式标成整数类型。每种片段各有单测,另有一条钉住「换任何列名和值,语句文本不变」「每条语句都带租户和表的条件」。

**工具** `knowledge_table`,只读。只在「开关开着 + 智能体绑定的库里至少有一张已存的表」时注册。

| 参数 | 说明 |
|---|---|
| `table` | 必填。`D12`(只有一张表时就是那张)或 `D12#T2` |
| `where` | 最多 8 条,同时满足。操作:等于 / 不等于 / 大于 / 大于等于 / 小于 / 小于等于 / 包含 / 属于一组值(最多 50 个)/ 为空 / 不为空。单个值最长 200 字符 |
| `group_by` | 最多 3 列 |
| `aggregate` | 最多 5 个:计数 / 去重计数 / 求和 / 平均 / 最小 / 最大 |
| `order_by` | 最多 2 个:某列或某个统计结果,升 / 降 |
| `select` | 明细模式下返回哪些列(最多 20 列;表超过 20 列时必填) |
| `limit` | 默认 20,最多 100 |

- 只给 `table` = 看表结构:有哪些表;每张表的列、行数、前 3 行样例、不规整的提醒。
- 列用表头文字指(不分大小写、去首尾空格)或用位置名。文字的「等于」不分大小写;「包含」是字面子串。对文本列求和 / 平均:报错并给出各列类型。
- 结果:明细是一张 Markdown 表(显示的文字 + 原表行号);统计是每组一行。**说明行**(平台文字):编号 `D12#T1`、符合条件的行数 / 总行数(准确值)、跳过了多少个不是数的格、「按未四舍五入的值计算」、不规整提醒。结果文字上限同检索结果(1 万字符)。
- 租户文字(文件名、工作表名、表头、格子)放 `content`;说明行放 `notice`。

**智能体怎么知道哪份文档是表**:检索结果的 `notice`(平台文字区)里多一行,列出本次结果里哪些文档号有表格数据。**不改结果正文和标头**(标头里拼的是租户的文件名,往后面加标记可以被文件名伪造)。只在开关开着且有这样的文档时出现。「哪些文档有表」取自文档行的 `table_count`,检索本来就要读文档行(`tools/knowledge.py:901-905`),不多一次读库。R3 的清单同样处理。

**执行时的保护**:

| 保护 | 做法 |
|---|---|
| 只读 | 只读事务;平台只拼 SELECT |
| 超时 | 事务内语句超时 3 秒;超时返回工具错误「请缩小条件」 |
| 结果大小 | 永远带 LIMIT;分组最多 1,000 组 |
| 并发 | 每次运行同时最多 1 个表格查询(同批并行的排队执行);每进程同时最多 4 个,等不到槽超过 2 秒就返回「稍后再试」的工具错误 |
| 租户 | 表由平台从「本租户 + 智能体绑定的库 + 文档号」解析;每条语句带租户 id 和表 id |
| 文档状态 | 文档「启用且有在服务的段」才可查(§3.3.2 的同一个存储层判断) |
| 停用 / 改过的段 | 这份文档里只要有一段被停用(手工停的,或重新入库时系统因「对不上原来那段」而连带停的,`persistence/models/knowledge.py:293-296`)或被手工改过(`:297`),它的表**整份不可查**,工具和文档详情页都说明是哪种原因。手工**新增**的段不算(它不在原文件里)。理由:表格数据来自原文件,停掉或改掉的内容在表里还是原样。**恢复办法是把那一段恢复启用 / 撤销修改;重新上传恢复不了** —— 重新入库会把手工的停用和修改带到新版本(`knowledge/ingestion.py:884-900`) |

**入库**:写表格数据和写段落在同一个事务、同一个围栏里。**清空旧表格数据不受开关控制**(每次重新入库都清);写入新的才看开关。所以开关关着期间重新入库,旧表会被清掉,不会出现「段落是新的、表是旧的」。这一步出错(读不了、超限)不影响文档入库,原因记在文档上。

**对估价与确认(B-222)的影响**:没有。读表格数据的模块不拿任何模型客户端(嵌入、识别、看图都不给)—— 结构上调不了。

**已有的表格文件**:手工跑补算命令(先例 `knowledge/backfill_profiles.py:11-14`):先空跑只打印数字;`--apply` 才写。落库的条件:读原文件时记下文档的代数和原文件哈希,写的那个事务里锁住文档行再比一次 —— 文档启用、有在服务的段、代数没变、哈希没变,才写;否则跳过并计数。这样补算不会和并发的重新入库互相覆盖。没有保留原文件的文档跳过。读原文件吃内存(入库有过「大文档主进程峰值 +147 MiB」的记录),所以补算在解析进程池里跑、一次一份。

**已有的表格段落**:原样保留,继续检索。不生成「整表摘要」段(要调模型)。

**平台开关** `kb_table_data`,默认关:

| 窗口 | 关 | 开 |
|---|---|---|
| D1 合了、D2 没合 | 入库只清不写 | 入库写表格数据;没有工具,智能体无感知 |
| D2 合了 | 不注册工具、检索结果无提示行 | 有表的智能体看到工具和提示行 |
| D3 没合 | — | 回答里的 `[D12#T1]` 在 4a 的核对里不认得,会被拿掉(句子保留);能用,只是没有来源角标 |

#### 3.2.3 数据模型 / 协议 / 迁移

一个迁移:`knowledge_table`(`id`、`tenant_id`、`kb_id`、`document_id` 外键级联删、`table_index`、`sheet_name`、`title`、`row_count`、`columns`、`content_hash`、`irregular`);`knowledge_table_row`(`table_id` 外键级联删、`tenant_id`、`row_number`、`cells`、`vals`);`knowledge_document` 加 `table_count`(默认 0)、`table_data_note`(可空)。只加不改;回滚 = 关开关。

**跟着变的地方**:

| 写 / 读的地方 | 变化 |
|---|---|
| 写段落的存储方法(两套实现) | 同事务清 / 写表格数据 |
| 删文档、删库、租户清理 | 靠外键级联;三处各加断言 |
| 入库流程与评测用的本地入库路径(`ingestion.py:545-702`) | 带上表格数据 |
| 文档协议对象、控制台文档接口与详情页 | 两个只读字段 |
| 工具注册、隐式工具名清单(`agent_spec.py:1408-1418`)、大结果外置豁免清单(`tools/overflow.py:124-126`) | 加 `knowledge_table` |
| 构建缓存的键 | 「绑定的库里有没有表」要进键(先例:库目录指纹 `tools/knowledge_catalog.py:313-325`) |
| 检索结果的 `notice` | 加提示行 |
| 外发参数规则 | 新工具的 `where` 值也是离开对话的参数,工具名加进外发工具清单(`outgoing_reference.py:45`) |
| 管理端工具时间线、评测答题循环的工具清单 | 加新工具。评测循环现在每题最多 3 次检索、3 次读文档、8 轮(`tools/eval/kb_agent_answer.py:33-37`):列文档和表格查询各自单独计数、各最多 3 次,总轮数提到 10 |

**出处**:表格结果登记一个出处,编号 `D12#T1`。对象沿用 4a 的形状,差别:多 `"kind": "table"`;没有 `chunk_indexes`;`heading_path` 是 `[工作表名]`;`locator` 是 `[{"type": "sheet", "sheet": "…"}]`;`fingerprint` 是表内容的哈希。一个编号 = 这张表;同一轮查几次是同一个出处。只看了表结构(没查数据)不登记出处。4a 的识别函数要多认 `#T` 这种写法(§4.6)。界面:角标点开显示工作表名、列、行数、本轮对这张表的全部查询条件;指纹对不上提示「表格已变更」。

#### 3.2.4 边界情况

| 情况 | 处理 |
|---|---|
| 表头不在第一行、两行表头、一张工作表几块表、有小计行 | 程序标「疑似不规整」,每次结果都提醒;数可能不对。评测单独设线(§5.2) |
| 合计行在表尾 | 程序标不出来(它不是「几乎全空」的行)。工具说明提醒;评测里放这种表 |
| 合并的类别列 | 值已往下抄,分组能用 |
| 数和文字混着的列 / 带单位的数 | 八成规则;带单位读不成数 |
| 超过大小上限 / csv 编码读不了 / openpyxl 读不了 | 没有表格数据,记原因;检索不受影响 |
| 重新入库后表的张数变了 | 整批替换;旧回答里的编号指纹对不上 |
| 模型给了不存在的列 / 不支持的操作 | 工具报错 + 可用列清单 |
| `where` 的值里写了 SQL 片段 | 普通的值(单测钉住) |
| 文档不在绑定的库里 / 是别的租户的 | 「没有这份文档」,与不存在同一说法 |
| 子智能体 | 随 `knowledge` 配置继承;平台白名单带了 `knowledge_search` 就连带得到新工具,不能单独关 |

#### 3.2.5 不做什么

Word / PDF / 幻灯片里的表格;模型写 SQL;跨表、子查询、「或」、计算列、按月 / 季分组、分组后筛选、每组前 N;用模型生成摘要或抽字段;修改 / 导出;开放 API 里查表格;画图。

#### 3.2.6 依据

| 结论 | 支持 | 反对 / 风险 | 状态 |
|---|---|---|---|
| 表格题靠读文字答不好 | 切段后每段只有几十行 | 没量过 | **未验证**(§5.2 改动前一臂) |
| JSON 行够用 | 行数封顶;单表扫描 | 没测耗时;宽表取一列要整行解压 | **未验证**(第 0 步两种形状) |
| 模型能填对条件 | 参数少、有表结构、报错给列清单 | 两家都让模型写 SQL | **未验证** |
| 语法够用 | 统计 / 排序 / 筛选是总计划写的范围 | 常见问法里有一批做不了(§0.3) | **未验证**(语法外题组) |

#### 3.3.2 方案

**工具** `knowledge_list_documents`,只读。与另两个知识库工具同一个门注册,外加平台开关 `kb_list_documents`(默认关)。

| 参数 | 说明 |
|---|---|
| `name` | 可选。文件名或标题里包含这段文字(字面、不分大小写) |
| `bases` | 可选,绑了两个以上库时才有:`K1`、`K2`(与 `knowledge_search` 同一套代号和校验)。目录外的库(超过 20 个时)没有代号,只能在不填时被列到 |
| `order` | 可选:`number`(默认,文档号从小到大)或 `newest`(文档号从大到小;文档号按首次上传递增,重传不变) |

- `knowledge_read` 的候选清单超过 10 个时那一行,在本工具已注册的构建里多一句指向本工具(平台文字);没注册时逐字节不变。

**跟着变的地方**:工具注册;隐式工具名清单;大结果外置豁免清单;外发工具清单(`name` 也是外发参数);管理端工具时间线;评测答题循环;`knowledge_read` 那一行提示;按名找改用共用判断。

#### 3.4.2 测量设计

9 条用例、每条重复几次,结果会被一两条用例左右,说明不了问题。所以:

**用例**:新造 **30 条指代明确**的合成用例(九类指代对象都有;每条的前文里至少有两个同类候选;追问必须检索才能答 —— 答案不在上一轮的结果里;每条的对象名带常见的别写法,例如日期的几种写法)。现有 9 条降为**开发集**,只用来调判据脚本,不进判定。

**一次试验**怎么算错。前提两条:这一轮有成功的 `knowledge_search` 调用;这一轮所有检索词里,要么没有该指对象的名字(复数指代要求**全部**名字都在),要么写的是别的候选的名字。在这个前提下分两类,分开报:

- **甲类(答错对象)**:回答里出现的是另一个候选的事实。
- **乙类(漏答)**:回答里既没有该指对象的事实、也没有别的候选的事实 —— 没搜到、或答「资料没写」。检索词没补全最常见的后果是这一类,也正是改写能治的。

主模型自己想错了对象、但检索词写得明明白白的,两类都不算 —— 那种错改写治不了。

**按用例计,不按试验计**:每条用例跑 5 次;5 次里有 2 次以上算错(甲、乙合计)的,这条用例记为「稳定出错」。这一轮没有检索的试验不计;一条用例有效试验不到 3 次的,不进分母。

**判错的试验全部人工过一遍**(最多 150 条,多数应为 0)再下结论 —— 防字面匹配的误判。

**事先定死的判据**(看结果之前可以改,之后不行):

| 结果 | 结论 |
|---|---|
| 稳定出错的用例 ≥ 4 条(约 13%;甲、乙合计) | **做**:进入 §3.4.3 的选型 |
| 稳定出错的用例 ≤ 1 条 | **不做**:R4 关闭,保留现有规则和计数器 |
| 2~3 条 | 不自动下结论:把这几条的对话明细(标明甲类还是乙类)摆给用户定 |
| 进分母的用例不到 20 条 | 测量作废(模型多数没检索),先改用例 |

**模型**:只用平台默认答题模型跑(30 × 5 = 150 次多轮对话)。另外两家厂商不在本次范围;结论是「做」时,在验收阶段再各跑一遍。

**证明指标咬得住**(离线重算,不花钱;任一条不成立则测量作废、先修脚本):

| 对照 | 做法 | 必须看到 |
|---|---|---|
| 检索词换成用户原话 | 每次试验的检索词换成那一轮的原始追问,回答换成另一个候选的事实 | 每条用例都判错 |
| 检索词换成点了名的 | 检索词换成对象名(含别写法),回答不动 | 没有一条判错 |
| 检索词换成另一个候选的名字 | 同上,回答换成那个候选的事实 | 每条都判错(新用例都有别的候选,这条对照处处有定义) |

**标定与验收分开**:开发集(旧 9 条)调脚本;新 30 条只用于这次判定。结论是「做」时,这 30 条降为开发集,另造留出集做验收。

#### 3.4.3 两种做法的草图(**暂缓**)

| | 甲:带条件的独立改写 | 乙:工具侧退回一次 |
|---|---|---|
| 做法 | 检索词里还有指代词(启发式)时,用辅助模型看最近几轮把它改写成自带主语的,再搜;失败用原词 | 同样命中时,工具不搜,返回平台文字「检索词里还有指代,请写出名字后重试」;同一轮只退回一次 |
| 多花什么 | 命中时多一次辅助模型调用 | 命中时多一步主模型调用 |
| 参考 | 两家的改写都在非智能体流程里;用在「模型写的检索词」上没有先例 | 没有先例;与「规则写在参数上」的现有方向一致 |
| 风险 | 辅助模型看的历史少,可能改错对象且更隐蔽 | 启发式误伤时多走一步,不会卡死 |

两种都依赖启发式的准头;真要做,第一步是给计数器补分母。

#### 3.4.4 不做什么

测量结果出来之前不写任何产品代码;不把「当前对象」交给对接方传(11-05 已否决);不为每次检索无条件加一次改写调用。
