# B-315 结构化输出：表单视图支持多层结构编辑

日期：2026-11-18 · 状态：设计待确认

## 1. 问题

智能体配置页的「结构化输出」只认「一层平铺的字段」：每个字段只能是文字、数字、是/否，或者文字 / 数字列表，而且不能带任何限制。只要多一点东西，整块就只剩一句「已配置（复杂结构）——请到 YAML 视图编辑」，结构看不到，也改不了。

健管师就是这种情况。它的输出结构是：

| 字段 | 类型 | 限制 |
|---|---|---|
| `messages` 回复消息 | 文字列表 | 最多 4 条；每条 1～300 字，不能全是空白 |
| `media` 素材编号 | 整数列表 | 最多 3 个、不重复；每个 ≥ 1 |

它没有更深的嵌套。被判成「复杂」，是因为用了条数、长度、格式、不重复、最小值这些限制，还有「整数列表」这个类型。别的客户的智能体还常有「列表里每项是一个对象」的结构，比如 `[{标题, 链接}]`。

## 2. 目标 / 不做

**做**
- 表单视图按层级显示结构化输出，并且能增、删、改。
- 字段类型：文字、数字、整数、是/否、对象（下面再挂字段）、列表（每一项可以是以上任意一种，包括对象和列表）。
- 每个字段能设：名字、类型、必填、说明、可选值（文字 / 数字类型）。
- 常用限制：
  - 文字：最短 / 最长字数、格式（正则）；
  - 数字 / 整数：最小值、最大值；
  - 列表：最少 / 最多几项、不重复。
- 层级最多 5 层。超过 5 层的部分只读显示。

**不做**（这些写法照样能用，只是在表单里只读显示，要去 YAML 视图改）
- 「几选一 / 全满足」类结构（`oneOf` / `anyOf` / `allOf`）、引用（`$ref` / `$defs`）、`const`、一个字段允许多种类型（如 `["string","null"]`）、`patternProperties`、条件结构（`if/then/else`）。
- 不改后端，也不改 YAML 视图。

## 3. 怎么做

**数据模型**（`form_model.ts`）
- 把 JSON Schema 读成一棵「字段树」，每个节点记：名字、类型、必填、说明、可选值、限制、子节点（对象）或列表项（列表）。
- 碰到第 2 节「不做」里的写法，**只把这一个节点**标成「只读」，原样保存它的原始内容；同级和上级的其他字段照常可编辑。
  - 现在的做法是只要有一处不认识，整块就全部只读。改成按节点只读，影响范围最小。
- 节点上的说明类附加信息（`title`、`default`、`examples`、`$comment`）原样保留，表单不显示，写回时也不丢。
- 写回时：
  - 对象节点保留原来的 `additionalProperties`；新建的对象默认写 `false`；
  - 不改动的字段写回后和原来完全一样，字段顺序也不变。
  - **核心保证：只读不改时，「读进来再写回去」的结果和原文一字不差。**

**界面**（`OutputSchemaEditor.tsx`）
- 用可展开的树形表格展示，每行是一个字段：名字、类型、必填、说明，以及一个「限制」按钮。点按钮弹出小面板，按类型显示能设的限制。
- 对象 / 列表行可以「加子字段」。列表行下面固定挂一个「每一项」子行，用来定义列表里每项的类型。
- 只读节点灰显，注明「这部分用了表单不支持的写法，请到 YAML 视图改」。
- 名字校验沿用现有规则（同一层不能重名、不能为空），出错时在行内标红。

**严格模式提示**
`strict: true` 时，部分模型厂商要求「每层的字段都必填、不允许多余字段」。这时如果有非必填字段，表单在字段旁显示提醒，但不拦保存。理由是平台在其他调用路径上会自己校验，而厂商规则也在变化。

## 4. 测试与验收

- **单元测试**（vitest）：
  - 「读进来再写回去」一字不差：健管师的结构；含对象列表、5 层嵌套、只读节点、附加信息的样例各一个。
  - 每类限制的读写各一条。
  - 每条断言都要能失败：先在实现里故意改坏一处，确认这条测试会变红。
- **组件测试**：加字段、加子字段、改类型（会清掉不适用的限制）、删字段、只读节点不能编辑、名字校验。
- **e2e**：现有的结构化输出用例要能跑过；再加一条「健管师结构：在表单里把 messages 的最多条数从 4 改成 3 → 切到 YAML 视图，看到 maxItems: 3」。
- **测试环境验收**：打开健管师配置页，结构能看到，改一处限制保存后生效，再改回去。

## 5. 工作量与风险

- 前端约 2～3 天，含测试。只改 admin-ui，不改后端，不改数据库。
- 风险是写回时把手写的配置改坏，靠 §3 的核心保证和对应测试兜住。
- 一个 PR。按老规矩：先独立审查，没有中危以上的问题再开 PR；合并前跑全量；测试环境验收通过才算完成。
