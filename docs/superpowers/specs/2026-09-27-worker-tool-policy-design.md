# 子智能体工具边界设计(B-122)

- 状态:方向已拍板(2026-09-27),本文待审
- 关联:B-37 子 Agent 上下文继承(`2026-08-28-worker-context-inheritance-design.md`,其 §2.5「写操作应留主线」)、B-35 PR-4(worker 撞审批软拒)、产物清单契约(`_child_run.py` 记录器下传)
- 原则拍板人:项目负责人(2026-09-27 会话)

## 一、问题

### 1.1 实证

测试环境 2026-09-27,ai-health-plan 回归(run `d1bb9bc7`):员工要求「派一个子智能体专门设计版式方案」。
子智能体把设计稿写进 `layout_design.md` 后,**自己调 `save_artifact` 把它登记成了产物**。
这次交付因此多出一个中间稿,除方案 JSON 与 docx 外对接方也会收到它。
该 Agent 提示词里的三条禁令(不渲染成品 / 不改 `style/` / 不调写操作 MCP)都没覆盖这件事。

同一个 Agent 的 MCP 工具清单里有 `cpwx_send_text_to_customer`、`cpwx_send_text_to_group`(给客户、群发企微消息)。
按现在的平台行为,它派出的子智能体**拿得到这两个工具**,拦着它的只有提示词里一句禁令。

### 1.2 根因:子智能体继承父的全部工具,边界全靠各 Agent 自己写提示词

- `synthesize_worker_spec`(`control_plane/subagent_runtime.py`)继承父的 `spec.tools`,只剥 `manage_task`。
- `save_artifact` 是**基础能力**(`orchestrator/tools/assembly.py` `BASE_CAPABILITY_BUILTINS`),接线齐了就自动注册,子智能体也不例外。
- 子智能体登记的产物会进**父 run 的交付清单**:`_child_run.py` 把父的产物记录器原样下传给子代。这是当初刻意的设计,注释原文:「子代登记的产物同属本 run 的交付物,漏传会让委派干活的 run 清单缺项」。
- 平台生成的子智能体提示词(`_worker_system_prompt`)只讲三件事:你是临时助手、结果回给主助手、大块产出写文件。**哪些事不该做,一句没有。**
- B-37 §2.5 定过「写操作应留主线」,但只写进了文档,平台从未执行。父侧委派块里有一句 "Never delegate writes",可子智能体手里的写工具照样齐全。

结果:每个开了子智能体的 Agent,都要由写提示词的人自己想到并写出禁令。而写提示词的人(运维、对接方)不一定知道 `save_artifact`、MCP 写工具是什么。

### 1.3 这不是一家的问题

测试环境实查(2026-09-27):

| 项 | 数量 |
|---|---|
| Agent 总数 | 10 |
| 开着子智能体(默认开) | 10 |
| 子智能体能用 `save_artifact` | 10(基础能力,全员) |
| 接了 MCP | 4(深护智康 4、高德 1) |
| 带自我进化类工具(记忆 / 行为补丁 / 技能起草) | 6 |
| 配了静态子 Agent | 0 |

## 二、业界做法(2026-09-27 读源码)

读了 hermes-agent 与 openclaw 的源码,两家做法一致的地方就是本设计的主干。

| 维度 | hermes-agent | openclaw |
|---|---|---|
| 禁用清单 | 写死 `DELEGATE_BLOCKED_TOOLS`:`delegate_task`、`clarify`、`memory`、`send_message`、`cronjob_manage`;**不可配** | 写死 `SUBAGENT_TOOL_DENY_ALWAYS`:`gateway`(改配置/自升级)、`agents_list`、`session_status`、`cron`、`sessions_send`;运维可额外增禁或放开,默认不设 |
| 往外交付 | 只有最终小结回父;没有子代直接交付文件的通道 | 结果由平台转给父,**父用自己的口吻告诉用户**;子代没有登记附件的通道 |
| 永久改变自己 | 禁记忆、定时;技能编辑没禁 | 禁定时、改配置;记忆、技能没禁(只是不给子代看记忆) |
| 外部写操作 | 不按读写裁工具;MCP `readOnlyHint` 只用于「不受信任的服务器」决定是否审批,主子一视同仁;**子代遇审批默认自动拒绝** | 不按读写裁工具,不读 MCP 标注;提示词写「不对外发消息,除非任务明确指定对象」 |
| 改工作区文件 | 不禁;做了并发保护(同文件加锁、被兄弟子代改过就拒绝覆盖),可选独立工作区副本(默认关) | 不禁 |
| 子代提示词 | 平台写死:专注子代;小结写清做了什么、发现什么、**创建或改了哪些文件**;父侧写「子代小结是自述,告诉用户前自己核实」 | 平台写死:「你**不是**主 Agent」「不和用户对话」「不对外发消息」「不建定时任务、不留持久状态」 |

**共识**:
1. 边界由平台写死、默认生效,不让配置者去记。
2. 交付只经父。
3. 子代不改会留到以后的东西。
4. 子代提示词由平台生成。

**两家都没做、本设计做的**:按读写裁 MCP 工具。
原因是我们的外部写操作主要走 MCP,比如发企微消息、建用药计划,性质等同于 hermes 禁掉的 `send_message`。

**两家都没做、本设计也不做**:禁止改工作区文件(见 §5)。

## 三、设计原则(拍板)

沿用 B-37 §三,并补两条:

1. **平台缺口先改默认,不设计成让配置者去配。**
   > 「不可能所有人都记得要写『不得调用 save_artifact 登记产物』,运维人员可能连 save_artifact 是什么都不知道。」
   >
   > —— 项目负责人,2026-09-27
2. **能从结构上禁的就不给工具**:模型看不到的工具,比提示词写十遍「不得调用」可靠。禁不了的才写进平台提示词。
3. **分析不局限于一个 Agent**:每条规则都要在「任意 Agent」上成立。
4. **只管动态子智能体(`spawn_worker`)**,静态子 Agent(`spec.subagents`)不动。静态子 Agent 是被单独配置、单独部署的完整 Agent,有自己的负责人;而且目前没有 Agent 在用。
5. **主 Agent 零变化。** 主 Agent 的写工具自动审批单独立项(§5)。

## 四、方案

### 4.1 判定「这是子智能体构建」:进程内标志,不改 manifest

在 `ToolEnv`(`orchestrator/tools/assembly.py`)上加一个进程内字段 `worker_policy: bool = False`。
`make_worker_build_fn` 构造 `worker_tool_env` 时置 `True`;孙级子智能体复用同一个 `_build`,自动带上。
静态子 Agent 走 `make_child_agent_builder`,另有自己的 ToolEnv,不受影响。

**不在 AgentSpec 上加字段**。`extra="forbid"` 让新字段成为回滚坑(B-61 的教训:回滚到旧版本时,存量 spec 里的新字段会被拒)。

所有边界判定集中在一个新模块 `orchestrator/tools/worker_policy.py`,这是唯一的规则来源:
- 禁用工具名集合;
- MCP 与 http 的判定函数;
- 回滚阀读取。

### 4.2 A 类:往外交付 → 子智能体不给

| 工具 | 为什么 |
|---|---|
| `save_artifact` | 登记即进父 run 的交付清单(§1.2)。子智能体写文件照常,登不登记由主助手定 |
| `ask_for_approval` | 向人发起审批 = 和用户交互。子智能体里本就走不通(B-35 PR-4 会整个停下软拒),不如不给,省一轮白跑 |

`save_artifact` 是基础能力,**光从 `spec.tools` 里剥不够**。`build_tool_registry` 注册基础能力时要按 `worker_policy` 跳过它。

**推翻的旧决定**:产物记录器下传(`_child_run.py`)的初衷是「委派干活的 run 清单别缺项」。
改后,子智能体产出的文件由主助手登记。§4.6 的父侧提示词明确告诉主助手:子智能体写的文件在你登记之前不算交付物。
记录器下传的代码保留,给静态子 Agent 用,只是动态子智能体不再有登记入口。

### 4.3 B 类:永久改变 Agent 自己 → 子智能体不给

`author_skill`、`refine_skill`、`fork_skill`、`propose_skill_to_tenant`、`note_behavior_patch`、`clarify_tool_usage`、`remember`、`manage_task`(已剥,原位保留)。

理由:用完即弃的临时助手,不该把「我的发现」永久写进这个 Agent 以后的行为,没人把关。
这些工具只在 spec 声明时注册,所以在 `synthesize_worker_spec` 里按 `worker_policy.py` 的集合剥掉即可。
`manage_task` 继续在这里剥,因为它还牵涉构建硬闸(BUG-19b)。

### 4.4 C 类:外部写操作 → 子智能体只拿只读的

**MCP**:
- `_materialize_tool_defs`(`orchestrator/tools/mcp.py`)把 SDK `Tool.annotations.readOnlyHint` 读进 `MCPToolDef`,新增字段 `read_only: bool | None`,没标为 `None`。
- `register_mcp_tools` 增加参数 `read_only_only`。为 `True` 时只注册 `read_only is True` 的工具,**没标注的一律当写,不给**。
- `_register_mcp` 在 `worker_policy` 下传 `True`。

影响:
- 深护智康 MCP 已在 2026-09-27 发标注(仓库 `deep-ai-health-mcp-service` `f365a1e`,已合 master 与 dev,**待部署**)。部署后 31 个查询工具子智能体照常可用,9 个写工具子智能体拿不到。
- 高德地图等不发标注的第三方服务,子智能体整台拿不到,由主助手自己查。这是保守的代价,真有需要再加白名单(本期不做)。
- B-61 参数绑定的「绑定落空」判定(B-65)在子智能体构建里**不能把被过滤掉的工具当成「服务器没有这个工具」**,否则会对配置者报假告警。实现时,被策略过滤的工具计入「存在」。

**http 工具**(**新增决策点,请审**):
- http 工具支持 `GET/POST/PUT/PATCH/DELETE/HEAD/OPTIONS`(`orchestrator/tools/http.py`),只按主机名单管控,不按方法。
- POST、PUT 这些就是对外写操作,和 MCP 写工具同性质。
- 建议:子智能体里只允许 `GET/HEAD/OPTIONS`,其余方法返回明确的拒绝信息(「子智能体不能对外写,请交回主助手」)。
- 方法在调用时才知道,所以这里是**调用时拒绝**,不是不给工具。

### 4.5 D 类:改工作区文件 → 不禁,要求报告

两家都没禁。硬禁「不能改启动前已存在的文件」会误伤正常用法,比如「派子智能体去改这份草稿」。
改为:子智能体提示词要求**小结末尾列出创建或修改过的全部文件**(§4.6)。主助手一眼能看出有没有碰不该碰的。

各 Agent 的业务约定文件(如 ai-health-plan 的 `style/`)仍由它自己的提示词保护,平台无从知道哪些文件是「规矩」。

### 4.6 平台自动插入的提示词

**子智能体侧**:在 `_worker_system_prompt` 现有三段之后追加,英文,与现有文案同风格。要点:

- 你不是主 Agent,不直接面对用户;最终消息只交给主 Agent。
- 有些工具是**有意不给你的**:登记交付物、发消息及其他对外写操作、改 Agent 的记忆/技能/定时任务。这些留在主 Agent。**不要想办法绕过**(例如用 bash 或 exec_python 发外部请求),任务需要时在最终消息里说明。
- 最终消息末尾列出你创建或修改过的每个文件(路径 + 一句话)。

**主 Agent 侧**:在 `_WORKER_DELEGATION_BLOCK` 追加。要点:

- 子智能体的最终消息是它的**自述**,用它的结论或转告用户之前先核实(打开它列出的文件)。
- 子智能体写的文件**在你用 save_artifact 登记之前不是交付物**。
- 子智能体失败、结果不可用或说缺某个工具时,**这部分你自己接手做完**,不要中断任务。

**`spawn_worker` 工具说明**同步改:
- 现在写着「Workers carry the same tool set as you — including MCP tools — and can fetch data on their own」,改为「子智能体有读类工具(含只读 MCP),可以自己查数据;不能写、不能交付」。
- 与 §4.2~4.4 保持一致,否则说明会对模型说假话。

### 4.7 可观测

子智能体构建时打一条结构化日志 `worker_policy.applied`,只记计数、不记内容:剥掉的内置工具数、过滤掉的 MCP 工具数(区分「标为写」和「没标注」)、http 是否受限。
「子智能体为什么拿不到某工具」因此可查,不会静默。

### 4.8 运维回滚阀

环境变量 `EXPERT_WORK_WORKER_TOOL_POLICY`,默认开。关掉后 `worker_policy` 恒为 `False`,**两侧**都回到现状、逐字节一致:
- 子智能体侧:工具表与提示词;
- 主 Agent 侧:委派块与 `spawn_worker` 说明。

主 Agent 侧也要跟着回退,否则父侧会告诉模型「子智能体不能登记产物」,而子智能体实际上又能登记了,说明与行为对不上。
它和 B-37 的 `inherit_skills` 阀同一形态:运维在事故时用,不是面向配置者的开关。

## 五、不做什么(及理由)

| 方案 | 不做的理由 |
|---|---|
| **主 Agent 的写工具自动审批** | 主 Agent 一碰审批就暂停等人。深护智康经 API 调用,能否处理暂停未核实,贸然开启可能卡住现有流程。测试环境近 60 天主对话零次调用这 9 个写工具,生产未查。**单独立项**:先核对接方能否处理审批暂停 |
| **禁止改工作区既有文件** | 两家都没做;会误伤「改这份草稿」类正常委派。用报告替代(§4.5) |
| **配置者可调的禁用清单** | 违背原则 1。openclaw 虽有增禁/放开口子,默认也是不设;真有 Agent 需要放开再加 |
| **静态子 Agent 同步收紧** | 它们是单独配置的完整 Agent,有自己的负责人与提示词;目前零使用。等有人用再评估 |
| **没标注的 MCP 按工具名猜读写** | `get_`/`list_` 前缀猜测不可靠,猜错一次就是把写工具交出去 |
| **子智能体里遇审批改为逐次拒绝(hermes 式)** | 现有「整个停下软拒」已满足「写留主线」;且写工具已从源头拿掉,审批路径基本走不到 |

## 六、影响面与风险

- **所有开了子智能体的 Agent**(测试环境 10 个):子智能体不再能登记产物。原先依赖子智能体登记产物的委派,交付清单会缺项,直到主 Agent 按新提示词自己登记。**这是本设计最大的行为变化**,验收重点盯它。
- **接深护智康 MCP 的 Agent**:部署带标注的 MCP 之前,所有深护智康工具都是「没标注」,子智能体一个都拿不到,查数据只能靠主助手。**上线顺序:深护智康 MCP 先部署,再发本设计**,否则子智能体会短暂失去读数据的能力。
- **高德 MCP**:子智能体整台失去。
- **ai-health-plan 提示词**:平台做完后,「不调写操作 MCP」「不渲染或生成最终成品」两条可删(后者由不给 `save_artifact` 兜住:渲染出文件不登记就不是交付物);`style/` 保护保留。**删除另行执行,不在本设计的代码改动里。**
- **token**:子智能体提示词增加约 600 字符,父侧约 400 字符;工具数减少,工具说明反而变短。
- **回滚**:§4.8 阀门。

## 七、验收

**必须看行为,不问模型「你有没有这个工具」**(同 B-37 §七)。

单测层(每条断言都要变异自证:改坏实现 → 红 → 还原 → 绿):
1. 子智能体构建的工具表里没有 `save_artifact`、`ask_for_approval` 与 §4.3 全部工具;主 Agent 构建不受影响。
2. 静态子 Agent 构建不受影响(仍有 `save_artifact`)。
3. `MCPToolDef.read_only` 取自 `readOnlyHint`:`True`/`False`/缺省三种。子智能体只注册 `True` 的;主 Agent 全注册。
4. 子智能体里 http 的 `POST`(及其余写方法)被拒、`GET` 放行;主 Agent 不受影响。
5. 子智能体构建里,被策略过滤掉的 MCP 工具上的 `arg_bindings` 不报「绑定落空」。
6. 子智能体提示词含 §4.6 三条;父侧委派块含三条;`spawn_worker` 说明不再写「same tool set」。断言锚点用实现独有的短语(B-37 教训:锚点撞上既有文案会直接绿)。
7. 回滚阀关闭时,子智能体的工具表与提示词、主 Agent 的委派块与 `spawn_worker` 说明,都与改动前逐字节一致。
8. 孙级子智能体同样受限。

真栈层(测试环境,深护智康带标注的 MCP 部署之后):
9. ai-health-plan 让员工明确要求「派子智能体做版式设计」。子智能体的事件流里**没有** `save_artifact` 调用,交付物清单里**没有**中间稿;主助手登记了成品。
10. 同上,子智能体调得到深护智康的只读工具(真调用一次,例如 `form_list_by_project`),工具表里没有 `cpwx_send_*`。
11. 主 Agent 普通出方案,行为与改动前一致:工具数不变,产物正常。
12. 让子智能体做一件需要对外写的事,例如「顺便把方案发给客户」。事件流里看不到写工具调用,最终消息说明需要主助手处理,主助手接手或向员工说明。
