## 0. 一句话结论

Dify 用 17 个大模型节点把「判断意图 → 抽字段 → 写表单 → 回答」拆成流水线;迁过来后**由一个主模型(qwen4-max,能看图、不开思考,已定)按需调工具**完成全部工作。质量不靠节点数,靠三层分工:**「该不该做」写进系统提示词,「怎么填参数」写进工具说明,「必须成立的规矩」(提前 10 分钟、循环最长 30 天、化验单按月合并、累积字段只追加、他人编码不能删、按来源消息防重复)交给深护 MCP 服务端硬性执行**;客户档案、方案摘要、今日饮食、现有提醒由模型在话题与健康有关时调一次「客户资料精简版」工具取齐(每轮最多一次,11-17 定);需要同事接手时调转人工工具;不用技能、不用子智能体;开长期记忆;输出走 02 的固定结构。Expert Work 平台只改一处(固定值下拉,04 §4.1),另有三处平台行为要先实测延迟与开销(§4.1)。

## 1. 现状:Dify 现在怎么做(带出处)

### 1.1 一轮里发生什么

客户一句话进来,Dify 依次做(节点 id@DSL 起始行,全部读 DSL 确认):

1. 拉企微聊天记录(HTTP 1770115147110@9007)→ 格式化成 2 / 6 / 30 条三份(1770115347090@9067;员工一方记 assistant,其余记 user;只留文字;历史为空记作「第一次对话」)。
2. 取东八区当前时间(1749797377062@2600,手算 +8 小时,带星期)。
3. 并行预取:客户基础信息、健康方案(markdown 格式)、系统表单清单、基础信息表单字段,存在会话变量里缓存 120 秒 / 300 秒(1750138761896 等四个判断 + 四个工具节点);附件:图片交豆包看图转文字(1748596441157@2523,失败走 qwen3.8-flash 1789984456617@10149),PDF 每份交 claude-sonnet-5 逐页转录(1789716769814@9219),其它文档走文档提取器(1789725942172@9399)。
4. **每轮都查一次客户的提醒列表**(1768788146742@8730 → 1768788302269@8788),然后才进意图分析。
5. 意图分析(17519660545350@4215,qwen3.7-max,温度 1)输出 7 个 0/1 标志:新增提醒 / 删除提醒 / 个性化方案 / 课程 / 天气 / 快递 / 其它。
6. 按标志并行走分支:课程 → 直接发固定话术(17519707698140@4489);要个性化方案且**客户没有健康方案** → 发方案推广固定话术(1761366371168@5278 → 1761366470891@5346);新增提醒 → 抽提醒要素(1751532976185@3454)→ 调 `/add-notify`;删除提醒 → 抽要删的提醒(1768787117123@8448)→ 调删除接口;天气 / 快递 → MCP Agent(1752317953920@4640)。
7. 有 customer_code 时再并行三路:判断要不要改档案 → 抽字段 → 写基础信息表单;判断要不要上报健康数据 → 选表单 → 逐表抽字段 → 写表单(化验单另走一条按月合并的支路);按客户问的时间范围查表单 + 查今日饮食。
8. 健管师主节点(1761372447236@7273,qwen3.8-max,不思考,json_object,温度 0.7)输出 `{answer, attachments}`;主节点返回空才跑备用节点(17636269089180@8001,qwen3.6-plus,提示词相同,多一段 goods_info);都空则发兜底「不好意思,我刚才开小差了呢……」。
9. 首次对话时,在主回复之外**另发一条**补问基础信息(1761376427497@7661 判断缺哪些 → 1761376653874@7752 生成补问)。

一轮里要调几次模型:有 customer_code 的普通一轮至少 5 次(意图 1 + 改档案判断 1 + 上报判断 1 + 查询范围 1 + 主回复 1),发了图 / PDF 再加看图 / 转录,设提醒、写表单、化验单再加 1~3 次。

### 1.3 与本文有关的已知缺陷(都读 DSL 确认)

- 提醒成功全凭模型说:`/add-notify`、删除接口的响应不检查,抽取节点自己先写好「成功回复」(1761364113150@5147、1768788541394@8962)。
- 「已有提醒列表」从不给健管师:合并代码要求「没有新增结果且没有删除结果」才附上列表(1761365452094@5216 的拼接条件),而两个结果变量每轮都会被赋成「未新增提醒 / 未取消提醒」,条件永远不成立。
- 写入与主回复并行,本轮写了什么健管师看不到;一轮可能发出 2~3 条、顺序不定(课程 / 推广 / 首轮补问与主回复并行发)。
- 改档案的两个节点只看图片转写,不看 PDF 转写(1761366806397@5459、1761367072328@5602 的输入只有 `give_ai_image_output`)。
- 化验单「按月合并」是按**上传当月**合并(节点名固定取当前年月,1789742130208 规则 8;只取最近 1 条记录比对月份,1789740294859@9466 `page_size: 1`、1789740487772@9524),不是按采样日期。
- 提醒抽取的示例 3 自己算错了终止时间(首次 1 月 24 日 + 30 天写成 2 月 19 日,1751532976185 示例 3),模型照着学会出错。
- 推广话术没有限频(会话变量 `send_hp_promotion_time` 声明了没人用);环境变量 `need_multi_agent` 声明了没人用;`goods_info` 只有备用节点用。
- 看图有一条几乎走不到的支路(「提取图片 URL」代码节点出错才走,1761358449308@4709 → 1761358646107@4801),它的提示里有一条业务规则:绿色液体 / 粉末、包装上有「助糖」字样的认作「助糖 3 号」。主路径的看图提示里没有这条。

## 2. 目标与不做什么

**目标**

1. DSL 里每一条必须保留的业务规则,在新配置里都有去处(§3.3),并且每类至少一条可执行验收(§7)。
2. 修掉 §1.3 里与智能体有关的缺陷:提醒 / 写表单以工具真实结果为准再回复;现有提醒随客户资料工具一并返回,需要时就看得到;一轮只出一份结构化结果。
3. 普通一轮的延迟与花费不高于 Dify(§3.6 给估算,07 实测)。
4. 开长期记忆(已拍板),并说清它与私聊 / 群聊会话的关系。

**不做什么**

- 不在本文定工具的最终接口(04)、输出字段名(02)、会话切分与调用字段(01)、补消息(03)、知识库内容(05)。
- 不做快递查询(已拍板)。
- 不做平台级内容安全审核(平台没有,本文只列风险,§6)。
- 不在 v1 用技能、子智能体、动态子智能体(§3.5)。
- 不碰生产;配置书写好后,生产按清单重建由用户执行(已拍板)。

## 3. 设计

### 3.1 先走三个真实场景

**场景一:普通问答。** 客户私聊发「中午吃了一碗牛肉面,血糖会不会高」。本轮时间写在客户消息首行(01 §3.3.1)。主模型读到:系统提示词(规则)+ 记忆召回 + 本会话最近的对话。话题和健康有关,它先调一次「客户资料精简版」拿到档案、方案摘要、今日饮食、现有提醒;判断这是饮食咨询,不是上报血糖(没有血糖值),但「中午吃了牛肉面」是饮食数据,餐次按消息时间推断为午餐,调一次「上报健康数据」写进饮食记录,工具返回成功,然后输出 `["牛肉面主要是精白面,升糖会比较快……", "下次可以……"]`、视频编号空。业务方取回结果按气泡发出。模型调用 3 次。客户如果只是说「早上好」,不查资料,1 次。

**场景二:血糖 + 设提醒。** 客户下午 3 点在群里发「血糖 9.6 正常吗,以后每天晚上 9 点提醒我泡脚」,前后没提吃饭。主模型:血糖只有值,时段按消息时间和上下文推不出来 → 先不上报,问是空腹还是饭后(换成清晨 5 点发的「血糖 6.1」,就直接按空腹记,不问);泡脚提醒信息齐全 → 调「设提醒」,参数是事件时间「今天或明天 21:00」、循环「每天」,提前量不填(服务端默认 10 分钟)。服务端算出首次 20:50、终止日期 = 首次 + 30 天,写库、进延迟队列,返回首次时间与终止日期。主模型据此回复「已设好,每天 20:50 提醒你 9 点泡脚,先到 12 月 17 日,到时可以再续」,并在同一条回复里问血糖测量时段。客户下一句「晚饭后两小时测的」→ 主模型补齐两要素,调「上报健康数据」写血糖。

**场景三:化验单照片。** 客户发两张化验单照片 + 「帮我看一下」。图片随本轮进入主模型(主模型能直接看图),业务方同时把这两张图的原始地址作为本轮变量交给平台。主模型读出各项指标:先调「录化验单」,参数是指标、数值、单位、参考范围、采样日期;附件地址由平台按绑定自动填(模型不抄长链接)。深护服务端找到这位客户本月的化验记录:有就合并、附件追加,没有就新建;只含元数据没有指标就拒绝。然后主模型回复解读要点(不诊断、不荐药),数值看不清的明确说哪项没看清、请客户补拍。

三个场景共同的变化:**模型先做事、拿到工具的真实结果,再说话**;一轮只出一份结果,由业务方按顺序发。

**长度估算**:静态部分约 10,000~11,500 字,按 1 token ≈ 1.5 个汉字粗估约 7~8 千 token(Dify 主节点提示词本身约 10,300 字,另外 16 个节点合计约 69,000 字,§10)。客户资料不在提示词里,调客户资料工具时作为工具结果进来(≤ 8000 字)。另有平台追加段(防注入说明、工具使用要求、知识库目录)与工具定义(深护 MCP 11 个工具 + 天气 1 个,粗估 4~7 千 token),每次模型调用的固定开销合计约 1.2~1.6 万 token。

**为什么提醒时间换算、字段类型写进工具说明而不是系统提示词**:①模型正是在填参数那一刻读工具说明,规则离用的地方最近;②规则和执行它的服务端在同一处维护,改接口时一起改,不会两边对不上;③同一个工具将来给别的智能体用,规则跟着走;④系统提示词因此短一半,省的是每一次调用的 token。系统提示词只留判断类规则(该不该设、缺信息先问、怎么向客户说结果)。

**模板里的两个坑(读代码确认)**:平台对没传的变量填空串,`trusted: false` 的变量还会套上防注入围栏 —— 所以 `| default('…')` 对这些变量**不起作用**,围栏后的空串在 `{% if %}` 里也算真(`prompt_render.py:78-80, 243-248`)。因此:①分支只用 `trusted: true` 的变量(`customer_code`、`is_first_contact`、`self_introduction`)判断;`self_appellation` / `self_introduction` 是运营在深护后台配的,不是客户输入,所以声明为 `trusted: true`,`{% if self_introduction %}` 才能正确判断空值;②给默认值写成 `{{ x or '默认' }}`,不用 `default`。(原来「本轮资料类变量必填、没有内容传『无』」一条,随客户资料改走工具作废。)

**化验单识读的质量风险**:化验单是小字号密集表格、常有反光和倾斜,读错一个数值就会写错档案。处理(11-17 定):①不建标注对照集、不跑模拟测试;后面工程师真实测试时重点看化验单读数准不准,明显不如 Dify 就切到路径 B(只改配置);②提示词要求看不清就说,不猜;③服务端只收有指标的记录。

**合规提醒**:Dify 现在把客户的病历 PDF 发给境外模型服务转录,涉及健康类敏感个人信息出境(推断:按节点用的模型判断,调用走哪个地域未核)。**已定(11-17):迁移后全部用境内模型,PDF 不再交境外模型**,这个问题随之去掉。

**其它**:语音由业务方转成文字后再进来(平台不收音频);平台每轮最多 8 张图,Dify 现取最后 10 个附件,超出部分 01 定怎么处理;图片作为会话的一部分会在后续轮次里被反复带上,直到被裁掉(推断,`multimodal.py` 用引用存图、每次调用时取字节),07 实测它对 token 的影响。

### 3.9 长期记忆

**配置**:开 `memory.long_term`,用平台默认值 —— 每轮召回 5 条、注入上限 2000 token、召回后复核开(多一次辅助模型调用,与本轮其它准备工作并行)、结束后后台提炼写回(不挡回复)。B-300 上生产是前提(已拍板)。

**和会话的关系**:记忆按(租户, user_id)存。user_id = 客户(已拍板,`wx:{项目}:cus:{客户编号}`),会话也已拍板为「客户 + 智能体」一段:同一位客户的私聊和他所在的每个群共用一段会话(始终一段、不按空闲换新,01 §3.4.3),也共用一份记忆 —— 这正好符合「群聊也是客户与智能体一对一」。每轮来自私聊还是群聊写在 input 首行(01 §3.3.1)。会话负责「这几天聊了什么」,记忆负责跨会话的「这个人是谁、有什么习惯和计划」(如下周出差、不吃香菜、女儿备孕)。**结构化健康数据的权威来源仍是深护表单**,提示词写明记忆与档案冲突时以档案和客户本轮说的为准(节 D)。

**要知道的风险**:

1. 群里客户谈到家人(「我妈血糖 9.6」),提炼可能记成客户本人的事实。平台「按服务对象分开存」在记忆总计划第 4 步,还没做(`2026-11-13-memory-master-plan.md` 步 4);v1 靠提炼本身的判断,07 放一条专门用例。
2. 事实类记忆在同一 user_id 的所有智能体之间共享(记忆总计划 §G11,`memory.py:1200-1202`)。客户 user_id 只给本智能体用、前缀与员工侧不同(01),所以不会串。
3. 补进会话的消息(03)没有「用户原话」标记,第一次提炼看不到它们,03 已在处理(03 已拍板放最后做,之前会话里只有 AI 参与过的对话)。
4. 每轮记忆复核多一次辅助模型调用,有延迟与花费,07 记录。
5. 私聊和群共用一段会话,群里的回复可能提到客户在私聊里说过的内容(健康数据、隐私)。已拍板(11-17)提示词先**不加**「群里不主动提健康数据和隐私」这类规则,业务侧需要时再加。

### 5.3 输出结构(以 02 为准)

本文对 02 的要求(02 已拍板):①一条回复一般拆 1~3 个气泡(上限以 02 为准,02 定为 4),**允许 0 个**(消息不是对智能体说的时候不回);②视频编号是数组,最多 3 个,取值做成编号表的枚举,模型编不出表外编号。固定话术不单设字段,模型按节 O 把原文写进 `messages`。示意(字段名以 02 为准):

```json
{
  "messages": ["牛肉面主要是精白面,升糖会快一些。", "下次可以先吃半碗青菜再吃面,面量减到三分之二。"],
  "videos": []
}
```

平台会把模型这段原文存进会话,下一轮模型看到的是自己上一轮的整段结构(共享背景所述,本文未复核);补进会话的真人回复是纯文字。两种混在一起不影响理解,但 07 要观察模型会不会因此偶尔输出纯文字(平台会带着结构要求重试)。

### 5.4 工具说明里必须写的内容(交给 04)

| 工具 | 说明里要写 |
|---|---|
| 设提醒 | 提醒语是到点原样发给客户的一句话:口语、带 emoji、写具体钟点、不写「今天 / 明天」(R28);钟点换算表(R29);事件时间填客户说的事件发生时间,提前量不填则默认 10 分钟,「准时」填 0,客户指定就按指定(R30);「X 分钟 / 小时后」用分钟数参数,不自己算钟点(R31);只说日期默认 09:00(R32);循环类型与间隔、最小单位小时(R34);循环首次填下一个对应时间点(R35);一句多个提醒可一次传多条(R38);返回值里的时间才是准的,回复客户以返回值为准 |
| 查 / 删提醒 | 列表里的「提醒时间」已减去提前量,客户说的通常是事件时间(R39);删多条须带「客户已确认」,只有客户在**上一轮**看过清单并明确确认后才能带(R40);只能用列表里的短编号(R41) |
| 改档案 | 字段按编码写(先查字段拿编码与选项);年龄与糖龄是两个字段;称呼只在客户明说怎么称呼时写;常住地址即所在地;其他健康状况即有什么病(R45、R46);累积字段只写新增内容,服务端会追加并标日期(R47);选项题只能填选项里的(R50);数值按字段单位换算(R52) |
| 上报健康数据 | 表单要求的情境(血糖时段、餐次、测量时间)先按消息时间和上下文推断,推不出再问(R54、R74);饮食只写食物(R57);一条消息里重复的量合并或带时间(R75);日期时间字段不填由服务端取当前时间;附件不用填,平台自动带 |
| 录化验单 | 有采样日期填采样日期(R60);每项填数值、单位、参考范围上下限(按原报告);最多 70 项(R62);总结只摘异常与结论(R58);附件不用填 |
| 查表单 | 日期只填 `YYYY-MM-DD`;默认近 7 天含今天、「最近 X 天」含今天、自然周从周一起、本月 / 上月按日历、具体某天起止同日、结束不晚于今天(R64) |

## 6. 异常与边界

| 情况 | 会怎样 | 处理 |
|---|---|---|
| 客户没建档(`customer_code` 为空串) | 模板走「未建档」分支;误调档案类工具 → 服务端按「未建档」拒绝(04 §6.3) | 提示词说明;回复照常 |
| 客户资料工具失败或超时 | 模型拿到错误 | 照常回答能答的部分,不编档案数据;需要数据的事如实说这次没查到 |
| 工具失败(含深护 MCP 会话过期报 400、平台只在 404 时重连 —— 共享背景所述,本文未复核,04 处理) | 模型拿到错误 | 节 E:不说已办成;写操作平台不自动重发,服务端防重复(04) |
| 本轮写入后再查资料 | 工具每次现查 | 看得到刚写的值;写入结果以写工具返回为准 |
| 转人工后客户追问(「在吗」) | 临时接管标志随客户开口被删,AI 照常被调用 | 节 R:说正在确认、稍后回复,不回答已交出去的问题 |
| 转人工配了「本轮不回」,模型仍写了回复 | 发送前检查按临时接管标志拦下(04 §3.10) | 提示词要求输出空;标志是第二道保险 |
| 一条消息里两遍同样的量 | 两次写入来源消息相同,第二次被当成重复 | 节 K:合成一条或分别带时间(R75) |
| 结构化输出不合格 | 平台带结构要求重试,仍不合格 run 失败 | 02 的兜底 |
| 主模型厂商故障 | 切备用模型;同厂商整体故障时都失败 | 02 的兜底;跨厂商备用 v1 不加(§9 第 2 条) |
| 到时限 | 80% 时被要求收尾,到点停调工具、按已有信息作答;正在进行的那一步不打断,收尾多出约 10~45 秒(推断,01 §3.7) | 300 秒内覆盖化验单轮;07 实测 |
| 消息不是对智能体说的(群里客户对别人说话) | 回复 0 个气泡 | 业务方不发也不发兜底(02);对比 Dify:空回复会触发「开小差」兜底话术 |
| 客户问自己是不是在和机器人聊 | 已定口径(R78) | 不主动提;认真问到时不否认有 AI 协助,不自称真人;是否适用《人工智能生成合成内容标识办法》(2025-09-01 施行)待法务确认 |
| 一轮发来超过 8 张图 | 平台只收 8 张 | 01 |
| 午夜前后的「今天」 | 以 input 首行的本轮时间为准 | 业务方按东八区格式化(01 §3.3.1) |
| 化验单是上个月采样、这个月上传 | 按上传当月合并(与 Dify 一致) | §9 第 11 条 |
| 记忆里有旧值(如旧体重) | 召回后可能与档案冲突 | 节 D:以档案与本轮为准 |
| 客户诱导查 / 改别的客户 | 身份参数是绑定值,模型改不了 | 01 / 04;§7 有一条用例 |
