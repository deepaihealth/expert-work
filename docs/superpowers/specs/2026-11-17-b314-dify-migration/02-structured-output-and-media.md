## 0. 一句话结论

智能体每轮只交一个固定格式的 JSON:**几条文字(`messages`)+ 要发的素材 id(`media`,深护智能体素材表里的运动视频等,05 §3.3)**。课程、健康方案推广这两段固定话术写进系统提示词规则,由智能体按给定原文原样放进 `messages`(推广只发给还没有健康方案的客户,由智能体调深护 MCP 查方案判断),业务方只负责发,不限频。平台按配置的格式校验,不合格让模型重写,还不合格这一轮就算失败;业务方在这一轮结束后取回 JSON、自己再解析一遍,按素材 id 查深护智能体素材表、校验后取链接,拼成**一个**发送任务交给数字人服务按现有方式发(清洗、真人接管检查、间隔、@ 人都不变)。任何一步失败,客户收到兜底话术;被新消息打断、被真人接管、模型判断不该回,则什么都不发。素材链接、发送节奏全部在业务方,模型碰不到。平台不用改。

## 1. 现状:Dify 现在怎么做(带出处)

### 1.1 健管师节点输出什么

- 健管师大模型节点(`1761372447236`@7273)开了 JSON 模式加结构化输出,固定输出两个字段:[确认]
  - `answer`:字符串,全部文字回答,外加「非运动视频类链接(小程序、网页)」;
  - `attachments`:字符串数组,**只放运动视频 mp4 的完整链接**,最多 3 个,客户没明确要视频时必须是空数组,「仅使用『运动视频』中提供的链接,不得自行编造和篡改链接」。
- 视频链接从哪来:环境变量 `sport_video` 是一张 41 行的 Markdown 表(动作名 + 视频 CDN 上的 mp4 链接,路径是百分号编码的中文文件名,不带查询串),整张表塞进提示词,模型自己从表里抄链接。[确认]
- 失败兜底链:主节点失败重试 3 次,还失败就输出空串 → 改跑备用节点(`17636269089180`@8001,另一个模型,同样的提示词)→ 合并节点(`1763627024726`@8248)取两者里有结果的那个 → 判断 `answer` 是否为空(`1763627083496`@8305)。[确认]

### 1.2 结果怎么送到客户手里

Dify 不把结果交回给调用方去发,而是**自己反过来调用数字人服务** `POST {agent_call_back_url}/receive-answer`(主回复 `17613774900740`@7901),请求体是字符串模板拼出来的 JSON:

```
{
  "answer": "{{合并节点.answer}}",
  "file_link_list": {{合并节点.attachments}},
  "room_conversation_id": "...", "employee_pad_userid": "...", "customer_pad_userid": "..."
}
```

数字人服务收到后:[确认]

1. 若带了 `invoke_token` 且该轮已被取消,丢弃(`agent-callback.service.ts:130-163`)。**但 Dify 的回调请求体里从来没有 `invoke_token`**,这道检查对 Dify 回调永远不生效;dk 侧的注释也写明了「dify 回调不带 invoke_token,先不做」(`pc-send-task.service.ts:188`)。
2. pad 通道:入 `send-agent-answer-queue`,无重试(`agent-callback.service.ts` 同处);dk 通道:写 PC 发送任务表,一个接收对象一行(`pc-send-task.service.ts:133-185`)。
3. 发送处理器(`send-agent-answer.processor.ts:409-772`):
   - `answer_text` 是字符串 → 一个气泡;是数组 → 每个元素一个气泡(:419-428)。**Dify 传的是字符串,所以现在一轮正文永远只有一个气泡**,模型按提示词用空行分的段都挤在这一个气泡里。
   - 每条文字先清洗:只去掉 `#` 和 `*`,保留 http(s) 链接原样,把裸 `小程序://` 补成 `#小程序://`(`answer-text-clean.util.ts`)。**没有长度限制,也不按空行拆分。**
   - `file_link_list` 按链接的扩展名分类:`.png/.jpg/.jpeg` 发图片,`.mp4` 发视频,其余一律当文件发(:434-447)。扩展名用的是 Node 的 `path.extname(整条链接)`,链接带查询串时取到的是 `.mp4?xxx`,**签名链接会被当成文件发**(本地实测确认)。
   - 发送前查人工接管:群级标志、客户级临时标志 `HUMAN_HAS_ANSWERED_…` 命中就整批不发(:470-505);dk 在 PC 端领任务那一刻再查(`pc-send-task.service.ts:432-454`)。
   - 顺序固定为:全部文字 → 图片 → 视频 → 文件;文字之间等 2~5 秒,媒体之间等 1~3 秒(:589、:608、:636 起)。群聊且开了「回复需要 @」时只有第一条文字 @ 客户(:556-571)。
   - 媒体逐条 try/catch,一条失败不影响后面;**文字没有**:任何一条文字发送抛错,后面的文字和全部媒体都不发了(:571、:587、:607 直接 await,错误落到 :770 的总 catch)。
   - 每发出一条,都把发送回执推给消息同步队列并带 `is_digital_human: 1`(:88-108 等)。

意图分析节点之后、健管师节点之后各有几条**并行**支路,每条支路都会**单独**回调一次 `/receive-answer`:[确认]

| 支路 | 触发条件 | 发什么 | 出处 |

## 2. 目标与不做什么

**目标**

1. 一轮回复 = 业务方的**一个**发送任务,里面每条消息的内容和先后顺序都是确定的。
2. 模型只决定「说什么(含按提示词原样输出的固定话术)、发哪几个素材」。素材链接、发送节奏、接管判断全部在业务方,模型看不到也改不了。
3. 失败、超时、取不到、解析不了 → 客户一定收到兜底话术;被打断、被真人接管、模型判断这轮不该回 → 什么都不发。
4. 每条发出(以及该发没发)的消息都带上「来自哪一轮」,交给 03 登记(03 已拍板放最后做;之前先打进项目服务日志,01 §5.4)。
5. 尽量复用数字人服务现有发送逻辑;Expert Work 平台不改。

**不做**

- 不让模型写素材链接;主回复不让模型调 MCP 发消息工具(理由见 §3.9,已拍板)。
- 智能体主动找客户说话(业务方或平台定时发起一轮):这次迁移不做,后面再加(已拍板 11-17);到点提醒照旧由数字人服务发,不受影响。
- 链接卡片、小程序卡片、语音消息:现有发送通道不支持(§1.2),本次不加;小程序入口先不发(已拍板 11-17,05 待拍板 7)。
- 客户发来的图片 / 文件怎么进智能体:在 01。
- 补消息、发送登记表的结构与对账:在 03。本文只规定发送侧要交出什么。
- 41 条运动视频怎么录进深护新建的智能体素材表、标签和说明怎么写:在 05。本文只规定 `media` 字段和业务方的校验、发送。
- 系统提示词全文:在 06。本文只给「输出格式」那一节。
- v1 不让智能体给客户发它自己生成的文件(已拍板 11-17,待拍板 7)。

## 3. 设计(先走一遍真实场景,再列规则)

### 3.1 走一遍:客户问一句,到客户手机上出现几条消息

下面时间都是示意。

**18:42:05** 客户在私聊里发:

> 今天晚饭吃了一碗米饭和红烧肉,饭后两小时血糖 9.6,高吗?有没有饭后能做的运动视频?

**18:42:13** 数字人服务攒满 8 秒、没有新消息,拿到这个客户的锁,生成本轮令牌 `T1`,调项目服务(调用字段、会话、幂等见 01)。

**18:42:13 ~ 18:42:31** 项目服务向 Expert Work 发起一轮。智能体读档案、把血糖记进表单(工具见 04);客户明确要了视频,它调一次深护 MCP `material_list` 拿到本智能体可用的全部素材清单,挑了两个标着「低强度」、说明里写着适合饭后做的,组织回答。它最后交出的**原文**是:

```json
{
  "messages": [
    "饭后两小时 9.6 是偏高了一些,一般建议控制在 7.8 以下。",
    "这顿米饭加红烧肉,主食和油都偏多。下次米饭可以减到半碗,多配一份绿叶菜。",
    "吃完歇半小时再动一动,对压住饭后血糖有帮助,给你两个能跟着做的动作😊"
  ],
  "media": [1205, 1218]
}
```

**18:42:31** 平台检查这段原文:是一个 JSON 对象,两个字段都在,`messages` 3 条、每条不超 300 字,`media` 是不超过 3 个、不重复的整数 —— 合格。这段原文作为这一轮的「最终回答」存进会话;流里先推出一个 `channel=final` 的 `item.done`,事件流再以 `end`(状态 `success`)收尾。

**18:42:32** 项目服务:

1. 从流里那条本轮 `channel=final` 的 `item.done` 拿到上面那段原文(字符串);流断过、续上后直到 `end` 都没收到 final 时,改查对话条目按 `run_id` 找(§3.4)。
2. 去掉可能有的 \`\`\`json 围栏,解析成对象,按宽松规则再查一遍字段。
3. `1205`、`1218` 逐个查深护素材表:存在、同项目、属于本智能体(或全项目通用)、启用、没删除 → 取链接;两个的 `media_type` 都是视频,按视频发。
4. 拼成发送载荷交回数字人服务(01 新入口的返回,§5.4):

```json
{
  "outcome": "reply",
  "run_id": "R1",
  "answer_text": ["饭后两小时 9.6 是偏高了一些……", "这顿米饭加红烧肉……", "吃完歇半小时再动一动……"],
  "answer_origins": ["reply", "reply", "reply"],
  "file_link_list": ["https://<视频CDN主机>/no_logo_sport_video/<动作A>.mp4", "https://<视频CDN主机>/no_logo_sport_video/<动作B>.mp4"],  // 由素材库查出
  "file_origins": ["reply_video", "reply_video"]
}
```

**18:42:32** 数字人服务确认 `T1` 没被取消,把载荷放进现有发送队列(带上 `run_id`、`T1`、每条的来源)。

**18:42:32 ~ 18:42:46** 发送处理器照旧工作:先查真人接管(没有)→ 清洗 → 发第 1 条 → 等 2~5 秒 → 第 2 条 → 第 3 条 → 视频 1 → 等 1~3 秒 → 视频 2。每发出一条,就上报「这条企微消息属于 R1、来源是 reply / reply_video」(登记见 03)。

**客户手机上看到**:3 条文字气泡,接着 2 个视频。

同一个问题放在今天的 Dify 上:正文是 1 个长气泡(三段用空行隔开),后面跟 2 个视频;如果这句话还被判成了别的意图,客户可能先收到一段固定话术、再收到正文。迁移后固定话术由模型自己写进 `messages`(§3.6),和正文在同一个任务里、顺序确定。

**反例:模型第一次没按格式写。** 假设模型最后直接写了一段文字「饭后两小时 9.6 是偏高了一些……」而不是 JSON。平台本地检查不通过,会把「你上一条不合格:不是合法 JSON,请只输出符合 health_manager_reply 格式的 JSON」连同格式要求发给模型重写一次(这次不给工具);重写合格,就用重写的结果,前面那段不合格的文字**不进会话**;还不合格,再纠正最多 2 次;仍不合格,这一轮以失败结束。项目服务看到失败,给客户发兜底话术。客户这边的差别只是多等了几秒,或收到一句「开小差」。

### 3.2 输出格式:为什么是这两个字段

| 字段 | 一句话 | 为什么这样设计 |
|---|---|---|
| `messages` | 要发的几条文字,一条一个气泡,按顺序 | 数字人服务本来就支持 `answer_text` 传数组、一个元素一个气泡(§1.2),只是 Dify 一直传字符串。让模型直接给数组,业务方原样塞进 `answer_text`,发送代码一行不用改,还顺手解决了「一大坨文字一个气泡」 |
| `media` | 深护智能体素材表里素材的**短 id**(整数),最多 3 个 | 模型只给 id,业务方查素材库校验、取链接、按类型放进发送载荷;发送代码基本不用改。为什么不让模型写链接、为什么不再用编号枚举见 §3.5.1 |

**刻意对齐现有发送契约 `{answer_text: string|string[], file_link_list: string[]}`**:数字人服务的清洗、真人接管检查、@ 人、间隔、pad 与 dk 两条通道,全部挂在这个契约上(§1.2)。新格式和它一一对应(`messages` → `answer_text`;`media` 查素材库取链接后 → `file_link_list`),业务方中间只有一层很薄的翻译,发送侧不需要为迁移重写。唯一**不**对齐的地方是故意的:不让模型直接产出 `file_link_list`(链接)。

**考虑过、没加的字段**

- 固定话术标记(原设计的 `fixed_reply`):11-17 拍板不要。课程、健康方案推广的话术写进系统提示词,由模型按原文放进 `messages`(§3.6)。
- 首轮要问的基础信息:不单独设字段。首轮补问本质上就是「再发一条短消息」,放进 `messages` 的最后一条即可,顺序天然确定,也省掉 Dify 里那一次额外的模型调用。模型需要知道「这是不是第一次和这个客户聊」,由数字人服务每轮传 `is_first_contact`(已拍板,待拍板 6)。
- 「这轮不回复」:不单独设字段,`messages`、`media` 都为空就表示这轮不发(已拍板,待拍板 5)。
- 转人工、提醒、上报数据:这些是动作,走 MCP 工具(04),不放进回复格式。

### 3.3 平台怎么保证格式(以及它不保证什么)

配置项 `spec.output_schema` 填一段 JSON Schema(§5.1)。平台的实际行为(读代码确认,出处见 §10):

1. **只管最后那条回答。** 模型中途调工具的那些步骤完全不受约束;只有「不再调工具的那条回答」要过检查。
2. **模型第一次写回答时,平台并不把格式要求发给它。** 平台为了不妨碍中途调工具,第一次调用不带格式;模型能不能一次写对,全靠系统提示词里写清楚格式(§5.3)。写对了,零额外开销。
3. **第一次不合格 → 带着格式要求重写一次**(这次不给工具,附上「哪里不合格」);重写的结果仍不合格,再纠正最多 2 次。最坏情况一轮的收尾要调 4 次模型,所以 §7 要盯「需要重写的比例」。
4. **全部不合格 → 这一轮失败**(状态 `error`)。不合格的那些内容都不进会话。
5. **合格 → 存进会话的是模型写的原文字符串**,不是平台解析后的对象;原文外面可能套着 \`\`\`json 围栏。平台解析出的对象只在内部用,**对外接口(条目、历史消息、事件流)都不给**,业务方要自己解析。
6. **下一轮模型看到的就是自己上一轮的那段 JSON 原文**(包括素材 id 和它写进 `messages` 的固定话术)。好处是它知道自己上轮发过哪个素材、哪段话术;但它**看不到**业务方实际发出的链接、兜底话术——这些不在 JSON 里,要靠 03 的补消息补进会话。
7. **平台守卫可能把回答整个换掉。** 输出安全检查默认开着,回答里出现类似密钥或数据外带的写法时,平台把回答换成一段固定的英文拒答文字。这段文字**不是 JSON**,业务方解析必然失败 → 走兜底。正常健管对话几乎碰不到,但业务方必须处理。
8. 格式检查按 JSON Schema 2020-12 在平台本地做,`maxLength`、`enum`、`pattern`、`uniqueItems` 都生效,与模型厂商无关。

### 3.4 业务方怎么取回、怎么解析、失败怎么办

**取回:流里拿 `channel=final`,拿不到再按轮次查条目。**(按推荐定 11-17,与 01 §3.8 / 01 待拍板 11 一致。)

- 平台没有「同步返回 JSON」的调用方式;事件流的 `end` 只给状态、产物清单、用量,不给正文;webhook 不带正文、也晚约 15 秒。所以用流式 + 条目模式(`stream_format: items`)发起:收尾时平台对最后一段正文补发一个 `item.done`,`channel` 为 `final`;取本轮(`run_id` 相同)最后一个 `type=assistant_message`、`channel=final` 的条目的 `content`。`end` 是判断结果的唯一依据。
- 流断了用 `events?since_seq=` 续上;续上的那条连接不一定补发 final(01 待拍板 11),所以续不上、或**直到 `end` 都没收到 final**,就调 `GET /v1/agents/{code}/sessions/{session_id}/items?user_id=…&limit=3`,在 `items` 里找 `run_id` 等于本轮、`type` 为 `assistant_message`、`channel` 为 `final`、`tombstone` 不为 true 的那条,取 `content`。
- `limit` 的单位是「轮」不是「条」;按 `run_id` 过滤,而不是盲取最新一条,避免拿错轮。
- **不要用事件流里的逐字预览(`token` / `item.delta`)拼正文**:平台第一次那段不合格的回答也会被逐字推出来,它不是最终回答。
- 项目服务已有的客户端方法够用:发起 `startRunStream`、续流 `consumeRunStream`(`expert-work-sse.ts:195`)、取条目 `listSessionItems`、取消 `cancelRun`(`expert-work-client.ts:420-449、489、572`)。漏掉 `end` 的补救沿用项目服务现有的巡检做法(见 01)。

**按 `end` 的状态分别处理**

| `end.status` | 处理 |
|---|---|
| `success` | 取 final → 解析 → 发 |
| `incomplete`(碰到步数等限制,平台让模型收尾) | 同 `success`:有能解析的 final 就发,模型的收尾话会如实说明没做完 |
| `error` | 发兜底 |
| `interrupted` | 是业务方自己因新消息取消的 → `cancelled`,不发,等合并重跑;其它原因(智能体被下线、租户停用)→ `offline`,不发不兜底、告警(01 §3.9) |
| `paused`(等人工审批) | 本智能体不配审批;万一出现,取消这一轮 + 发兜底 |
| 业务方等待超过上限仍无 `end` | 取消这一轮 + 发兜底;上限 360 秒(01 §3.7) |

**解析(宽进严出)**

1. 流里没收到 final、查条目也没有 → 隔 1 秒再查条目,最多 2 次;仍没有 → 兜底(原因 `no_final`)。查条目这条退路的前提:平台部署开着会话历史存储,否则条目接口永远是空的(平台文档注明)。
2. 去围栏:**只有整段被 \`\`\`json … \`\`\` 包住时**才剥,规则与平台一致。
3. `JSON.parse`;失败 → 兜底(`not_json`,平台守卫换掉回答时就是这条)。
4. 宽松检查:`messages` 必须是字符串数组(去掉空白条目);`media` 缺了当 `[]`、里面不是整数的丢掉;多出来的字段忽略。`messages` 不是数组 → 兜底(`bad_shape`)。平台已经严格校验过,业务方这里宽松,是为了智能体配置后来加字段时业务方不用同步改、也不会因此全线兜底。
5. 素材 id 查深护智能体素材表、校验、取链接(§3.5.1)。
6. 两样都为空 → 这轮静默(`silent`),不发任何东西,记一条日志。
7. **任何情况下都不把 final 原文直接发给客户。**

**日志**:只记 `run_id`、结果(reply / silent / fallback)、兜底原因、原文长度、选中的素材 id、丢弃的素材 id 个数;**不打印回答正文和客户原话**(深护现有日志把聊天正文大量打到标准输出,见 08)。

### 3.5 多媒体

#### 3.5.1 运动视频等素材:模型只给素材 id,业务方查深护智能体素材表(05 评审 11-17 定)

**为什么不让模型写链接**

- 链接是一长串百分号编码的中文文件名。模型照抄长串经常抄错一两个字符,抄错的链接要么打不开,要么(更糟)被当成别的文件发出去;Dify 提示词里专门写「不得自行编造和篡改链接」,就是因为出过这种事。
- 链接会变:换 CDN、换无水印版本、改成带签名的链接。写死在提示词里,每变一次都要改智能体。
- 素材 id 可以机器核对(存不存在、是不是本项目、是不是给本智能体用的、启用没有、删没删),链接核对不了。
- 一个短 id 比一行链接短得多,也不会抄错。

**素材从哪来**:深护为智能体新建的素材表 `t_project_agent_material`(表名待深护确认;每行有 `agent_code`、`media_type`、`url`、`description`、`tags`、`status`;05 §3.3)。41 条运动视频按现有 CDN 链接录进去(不重新上传),标签(「低强度 / 坐姿 / 器械」)和说明(要领 / 适合人群 / 禁忌)帮模型按客户情况挑。

**模型怎么挑**:只有客户**明确**要视频 / 素材时,调深护 MCP `material_list`(04 §5.12)。它返回本项目里给本智能体用(或全项目通用)、启用的**全部**素材:短 id(表主键)、名称、类型、标签、说明的前一段(要领 / 适合人群 / 禁忌,可能为空);不给链接、不按关键词搜(关键词搜会漏同义词,全量清单不会漏)。模型按客户情况挑最多 3 个放进 `media`;没有合适的就只给文字建议,并直说暂时没有。客户没要就不调工具,`media` 为空。

**业务方怎么接**(解析完 JSON 之后、交回数字人服务之前,§3.1 第 3 步):对每个 id 查素材表 —— 存在、同项目、`agent_code` 等于本智能体或为空、`status = 1`、没删除 → 取链接,按 `media_type` 发(视频 → 视频消息;图片 → 图片;`file` / `audio` → 文件);不满足的丢掉并记日志;**文字一定照发**。每轮记下选了哪些 id、丢了几个,方便抽查。

**链接本身的要求**:现在发送侧按整条链接的扩展名分类(§1.2),素材链接的扩展名要和类型一致、不带查询串(现有 41 条都是 `.mp4`、无查询串)。将来有不一致的素材(如签名链接),先把发送侧改成按业务方给的类型分类(§4 数字人服务第 3 条)。

**为什么换掉原来的「编号表 + 输出枚举」**:素材增删不用重新发布智能体;唯一来源在深护智能体素材表,不用三份(提示词目录、枚举、编号→链接表)来回同步;提示词省掉约 400~500 token 的视频目录。代价:格式约束只能限「整数、最多 3 个、不重复」,不在允许范围里的 id 由业务方丢弃,而不是平台当场让模型重写 —— 文字照发,只是少了素材。

#### 3.5.2 智能体生成的文件

- 智能体用沙箱写出文件、登记成「产物」后,平台在 `end` 的 `artifacts` 里列出清单。下载产物要带平台的 API key(`GET /v1/agents/{code}/artifacts/download`),客户和企微都拿不到这个 key,所以**不能**把平台下载地址直接发出去,也不能让模型在文字里写这个地址。
- 正确做法照搬方案生成助手:项目服务按清单的名字和版本下载 → 存进深护 OSS → 得到以原文件名(带扩展名)结尾的公网链接 → 放进 `file_link_list`,数字人服务按扩展名发图片或文件。项目服务已有通用实现 `AgentArtifactService.landAll`(下载 → `expert-work-artifact/{项目}/{run}/{文件名}` → 公网链接)。
- **v1 不开**(已拍板 11-17,待拍板 7):Dify 的健管师从来不给客户发生成的文件,迁移不需要它;深护对「生成物发客户」现有的规矩是**员工先审核**(方案 / 报告生成器,`artifact-review.ts`),健管师直发等于绕过这条规矩。v1 做法:提示词禁止生成文件;万一 `end.artifacts` 非空,项目服务**不发给客户**,只记日志。
- 已知风险(超出威胁模型,只列不做):深护 OSS 桶是公共读(`oss-url.ts` 头注),存进去的文件拿到链接即可下载。

#### 3.5.3 小程序、网页

发送通道不支持链接卡片和小程序卡片,只能写在文字里:

- 只有知识库或工具结果里**原样出现**的网页 / 小程序链接才能写进 `messages`,原样照抄,不许自己拼。
- 清洗时 http(s) 链接原样保留,裸 `小程序://` 自动补 `#`(企微只认带 `#` 的),这些都是现有逻辑。
- 现有知识资料(Dify 的 `company_info`,约 2600 字)里没有网页链接,但服务一节末尾有一条小程序短链(`#小程序://…`,与 `goods_info` 重复,05 §1.1)。短链不进知识库、不让模型写;**小程序入口先不发**(已拍板 11-17,05 待拍板 7)。将来若要发小程序 / 网页,照素材的办法录进智能体素材表、让模型只输出 id,别让模型抄链接。

### 3.6 固定话术(课程、健康方案推广)

**已拍板(11-17)**:不用单独的输出字段。两段话术的规则和原文写进系统提示词(06 节 O),由智能体自己判断、把原文**原样**作为单独一条放进 `messages`;业务方只负责发,**不限频**(发送频率先不管)。

| 话术 | 什么时候发(沿用 Dify 意图分析的口径) | 谁判断 |
|---|---|---|
| 课程 | 客户明确问课程、培训、讲座、学习班、训练营、直播课这类信息;只问运动建议、运动视频不算 | 智能体按提示词 |
| 健康方案推广 | 客户明确要求定制**跨一段时间**(一周、一个月、三个月……)的系统性健康方案,**且客户还没有健康方案**;普通建议、单次指导不算 | 智能体按提示词;「有没有方案」由智能体看 `profile_get_brief` 返回的方案摘要判断(04 §5.7、06 节 O;每轮最多查一次),查询失败按「不发推广」处理 |

**提示词里要讲清楚**(06 节 O):

- 话术原文一字不改、单独一条,放在正文之后;正文简短回应客户的问题,不在聊天里写完整的周期方案。
- 现在两段原文都写「添加【本群群主】」,私聊里不通顺;深护运营给私聊、群聊各一版,模型按 input 首行的「私聊 / 群聊」选(01 §3.3.1)。
- 话术原文由运营维护,写在配置书里(05 §3.6 的交付文件,「先改交付文件、再按它进控制台」);改话术要重新发布智能体。

**顺序**:正文 → 话术 → 素材,都在同一个发送任务里(§3.7),不用改发送代码。

**会话里的样子**:话术原文就在模型这一轮的 JSON 里,下一轮模型看得到自己发过什么;它是这一轮输出的一部分,来源记 `reply`,03 补消息时按本轮输出跳过,不另补。

**代价**:话术原文每轮都在系统提示词里(两段私聊 + 两段群聊,约几百 token);模型可能改写原文或漏查方案,靠 §7 用例 5、6 和 07 的测试用例清单盯;不限频时同一客户反复问会反复收到。

### 3.7 兜底话术与发送规则

**兜底话术**(已拍板 11-17):沿用 Dify 原文「不好意思,我刚才开小差了呢,你能再说一下吗?」,**写死在项目服务代码里**(11-17 定,不存库、不按项目配);由项目服务拼进 `answer_text` 返回 `outcome: fallback`(§5.4)。

| 情况 | 发兜底? |
|---|---|
| 这一轮失败 / 超时 / 取不到 final / 解析不了 | 发 |
| 被新消息打断(业务方自己取消的) | 不发,等合并重跑 |
| 真人接管中 | 不发(兜底也是普通消息,发送处理器照样拦) |
| 模型判断这轮不回(两样都为空) | 不发 |

兜底话术来源标 `fallback`。限频(已拍板 11-17):同一聊天窗口 10 分钟最多发一次,私聊和各群分开计(私聊按「员工企微号 × 客户企微号」,群按群,键见 01 §5.4);超过不再发、只记日志。超过时只记日志,v1 不另外提醒员工(11-17 定,待拍板 8)。

**发送规则全部沿用数字人服务现有实现**,只补两处:

| 项 | 现在 | 迁移后 |
|---|---|---|
| 气泡拆分 | 数组一个元素一个气泡;Dify 传字符串所以只有一个气泡 | 模型直接给数组,一条一个气泡 |
| Markdown 清洗 | 去 `#`、`*`,保留链接,补 `#小程序://` | 不变;提示词也禁止 Markdown |
| 长度 | 发送侧没有任何限制,只有提示词说 20~120 字 | 格式约束里每条最多 300 字、最多 4 条,超了平台让模型重写;提示词仍按 20~120 字引导 |
| 间隔 | 文字 2~5 秒,媒体 1~3 秒(pad);dk 由 PC 端自己控 | 不变 |
| 顺序 | 同一任务内:文字 → 图片 → 视频 → 文件;但一轮拆成多个任务,任务之间不定序 | **一轮只有一个任务**,顺序完全确定 |
| 真人接管 | 发送前查(pad)/ 领任务时查(dk) | 不变 |
| 群聊 @ | 第一条文字 @ 客户 | 不变 |
| 文字发送失败 | 后面的文字和媒体全不发了 | 改为像媒体一样逐条容错,一条失败不影响后面;失败的不自动重发(pad 可能其实已发出,重发会重复) |

### 3.8 发送侧要为 03 做的事

具体登记表和对账规则在 03,发送侧只负责交出信息:

1. 发送任务带上 `run_id`、`invoke_token`,以及每条的来源:`answer_origins`(与 `answer_text` 一一对应,取值 `reply` / `fallback`;固定话术由模型写进 `messages`,来源就是 `reply`)、`file_origins`(与 `file_link_list` 一一对应,取值 `reply_video` / `reply_image` / `reply_file`,按素材的 `media_type`)。
2. 每条**真正发出**的消息,上报 `{run_id, 来源, 通道, 企微消息标识, 发出时间}`。pad 的消息标识在发送回执里(现在推给同步队列的 `meesage_data` 就有);dk 用发送任务 id,PC 回报发出后再与会话存档对上。
3. **没发出**的也要上报 `{run_id, 来源, 结果}`,结果与 03 `:undelivered` 的 `reason` 用同一套取值:`human_took_over`(被真人接管拦下)/ `send_failed`(发送失败)/ `cancelled`(发送前发现本轮已取消)/ `other`;v1 项目服务只把它打进日志(带 run_id,run 表不加列,01 §5.4),03 时再落表。03 靠它知道「会话里有这段回答,但客户没收到」。
4. 哪些算「某一轮的输出、由业务方发出」(补消息时跳过):来源为 `reply`、`reply_video`、`reply_image`、`reply_file` 且已发出的(固定话术在 `reply` 里)。`fallback` 的原文不在模型的 JSON 里,按「其它消息」补进会话。03 已拍板放最后做,本节的上报在 03 之前只进项目服务日志,用于发送统计和排查。

### 3.9 主回复由谁发:业务方发 vs 智能体调 MCP 发消息工具

**已拍板(11-17):方案 A**。

**方案 A**:业务方等这一轮结束,取回 JSON,自己发(就是 §3.1 那条路)。
**方案 B**:给智能体开深护 MCP 的 `cpwx_send_text_to_customer` / `cpwx_send_text_to_group`,让它在这一轮里自己调工具把话发出去。

| 场景 | A:业务方发 | B:智能体调 MCP 发 |
|---|---|---|
| **被打断**:客户先发「血糖 8.5」,10 秒后补一句「早上吃了包子」 | 第一轮还在想,被取消,什么都没发出;合并两句重跑,客户收到一份把包子考虑进去的回答。第一轮哪怕已经写完、还没发,业务方发前检查到已取消也会丢掉 | 第一轮可能已经调工具把「8.5 偏高」发出去了,取消收不回;第二轮再答一遍。客户收到两段内容重叠、前一段没考虑包子的回答 |
| **漏调 / 多调**:模型把回答写得很好,但忘了调发送工具;或者重试时调了两次 | 不存在这个问题:最终回答一定由代码发出且只发一次 | 漏调 → 客户什么都收不到,业务方还不知道;多调 → 客户收到两遍。PC 通道还明说「返回 sent=false 不是失败,不要重复调用」,模型很容易误判 |
| **真人接管**:员工 1 分钟前刚手动回了客户 | 发送处理器发前查到接管标志,AI 不说话 | MCP 发送工具里**没有**任何接管检查(读代码确认),AI 会插话盖过真人。要用 B 得先在 MCP 侧补这道检查 |
| **发视频** | 素材 id 查素材库取链接,按类型发成视频消息 | MCP 发送工具只收文字(`content` 1~2000 字),发不了视频、图片、文件 |
| **发给谁** | 收件人由数字人服务按这条消息的来源定,模型碰不到 | 收件人是工具参数,必须用平台的参数绑定钉死,否则客户在聊天里诱导模型给别的客户发消息——正是威胁模型要防的事 |
| **格式与节奏** | 清洗、2~5 秒间隔、群里 @ 客户都是现成的 | MCP 发送不清洗 Markdown、不控间隔;群 @ 要模型自己填成员 |
| **花费** | 回答写完即止 | 每发一次多一轮工具调用,多花 token、多几秒 |
| **方案 B 唯一的好处** | — | 一轮里能分几次发(先发一句、查完再发);但健管师提示词本来就禁止「稍等,我查一下」这类占位话术 |

**选 A 的理由**:用 B 要先给 MCP 发送补接管检查、媒体能力、收件人绑定,还解决不了打断收不回和漏调,而 A 这些都是现成的。这也与 04「不放行 `cpwx_send_*`」一致。

**主动 / 定时消息的边界**(智能体主动找客户说话:这次迁移不做,后面再加,已拍板 11-17;下面留作那时的起点)

- 已有的「提醒」:到点由数字人服务的延迟队列原样发出,不经过智能体,不受本文影响。
- 由**业务方**定时发起的一轮(例如每天早上让健管师看一眼昨天的血糖、写一句关心):业务方同样在等这一轮的结果,**走同一条 A 路径**即可,不需要 MCP 发送工具。这是共享背景里说的「最稳:业务方自己定时调 runs」。
- 只有由**平台**触发器或智能体自建定时任务发起的一轮,才没有业务方在等结果,这时只能让智能体调 MCP 发。将来要做,先给 MCP 发送补接管检查、用参数绑定钉死收件人和员工,并单独评估。

## 5. 接口与数据结构

### 5.1 智能体配置里的格式约束

```yaml
spec:
  output_schema:
    name: health_manager_reply
    json_schema:
      type: object
      additionalProperties: false
      required: [messages, media]
      properties:
        messages:
          type: array
          maxItems: 4
          items:
            type: string
            minLength: 1
            maxLength: 300
            pattern: "\\S"          # 至少有一个非空白字符
        media:
          type: array
          maxItems: 3
          uniqueItems: true
          items:
            type: integer
            minimum: 1           # 深护智能体素材表主键;存在性由业务方查库保证,不做枚举
```

数字(4 条、300 字、3 个素材)是建议值,工程师按 07 的测试用例清单测过后再调。

### 5.2 字段说明

| 字段 | 类型 | 必填 | 含义 | 约束 | 示例 |
|---|---|---|---|---|---|
| `messages` | 字符串数组 | 是 | 发给客户的文字,一个元素一个气泡,按发送顺序;固定话术(课程、方案推广)按原文单独占一条(§3.6) | 0~4 条;每条 1~300 字、不能全是空白;纯文本不用 Markdown;一条里不用空行分段;与 `media` 都为空 = 这轮不说话(已拍板,待拍板 5) | `["饭后两小时 9.6 是偏高了一些……", "下次米饭可以减到半碗……"]` |
| `media` | 整数数组 | 是 | 要发的素材 id(`material_list` 返回的短 id),跟在文字后面发 | 0~3 个、不重复;只有客户明确要视频 / 素材时才非空;不在允许范围的由业务方丢弃 | `[1205, 1218]`,不要时 `[]` |

### 5.3 系统提示词「输出格式」一节(草稿)

```
# 输出格式(必须遵守)
你的最终回复只能是一个 JSON 对象,前后不要有任何文字,也不要加代码块标记:
{"messages": [...], "media": [...]}

messages:要发给客户的几条消息,按发送顺序排。
- 一条讲一件事,一般 1~3 条,每条 20~120 字为宜,最多 4 条、每条不超过 300 字。
- 纯文本,不用 Markdown;不要在一条里用空行分段,要分段就拆成两条。
- 群里明显不是对你说的话,messages 和 media 都输出 [],表示这一轮不回复。私聊必须回复;唯一例外:本轮调了转人工、工具结果说「本轮不用写回复」时,messages 和 media 都输出 []。
- is_first_contact 为 "1"(你和这位客户之间还没有过文字消息)时,调客户资料工具看档案缺不缺称呼/年龄/身高/体重/常住城市/其他健康状况;
  缺就在最后单独加一条 30 字以内的询问,一次问完;城市只问到市,不问详细住址;客户已经说过的不问。
- 需要发课程介绍或健康方案推广话术时(规则见「固定话术」一节),把给定原文一字不改、单独作为一条放在正文后面。

media:只有客户明确要视频或资料时才填。先调 material_list 拿到全部可发素材,按客户情况(年龄、关节、血压等)挑最合适的,最多 3 个,填它们的 id;其余情况一律 []。
- 不要在 messages 里写链接,也不要写「点击链接」;素材会自动跟在文字后面发出。
- 清单里没有合适的,就只给文字建议,并直说暂时没有这个内容的视频。

链接:只有知识库或工具结果里原样出现的网页、小程序链接才能写进 messages,原样照抄,不要自己拼。

```

### 5.7 解析步骤(伪代码)

```
final = 流里本轮 type == "assistant_message" 且 channel == "final" 的最后一个 item.done
若到 end 仍无 final:
    items = listSessionItems(session_id, limit=3)
    final = items 中 run_id == 本轮 且 type == "assistant_message" 且 channel == "final" 且 !tombstone 的最后一条
    若仍无:重试 2 次(间隔 1 秒),仍无 → fallback("no_final")
text = 整段被 ```json … ``` 包住 ? 取中间 : 原文
obj = JSON.parse(text)                            失败 → fallback("not_json")
若 obj 不是对象 或 obj.messages 不是数组 → fallback("bad_shape")
messages = obj.messages 里非空白的字符串
media    = (obj.media 是数组 ? obj.media 里的整数 : []) 去重,取前 3
逐个查素材表:存在 且 同项目 且 (agent_code = 本智能体 或 为空) 且 status = 1 且 未删除 → 取链接与 media_type;否则丢弃(日志记个数)
若 messages、media 都为空 → silent
否则 → reply(answer_text = messages, file_link_list = 素材链接, file_origins = 按类型)

fallback(原因):这个聊天窗口的限频键 SET NX EX 600 成功 → answer_text = [兜底文案];否则 answer_text = [](只记日志)
```

## 6. 异常与边界

| 情况 | 平台怎么做 | 业务方怎么做 | 客户看到 |
|---|---|---|---|
| 模型第一次没写成 JSON | 带格式要求重写,合格就用 | 正常取回 | 正常回复,稍慢几秒 |
| 重写后仍不合格 | 这一轮失败 | 兜底 | 兜底话术 |
| 守卫把回答换成拒答文字 | 最终回答是一段英文、不是 JSON | 解析失败 → 兜底 | 兜底话术 |
| 业务方等待超时 | — | 取消这一轮 + 兜底 | 兜底话术。迟到的回答留在会话里、客户没收到,由 03 处理(03 之前属已知缺口,01 §3.11) |
| 新消息打断 | 这一轮被取消 | 不发,合并重跑 | 一份覆盖两句话的回复 |
| 回答已生成、发送前发现被取消 | — | 不发,上报 `cancelled` | 同上;会话里那段回答没送达,由 03 处理 |
| 真人接管中 | — | 发送处理器整批不发(含兜底),上报 `human_took_over` | AI 不说话 |
| 两样都为空 | 正常结束 | 不发,记 `silent` | 没有消息 |
| `messages` 为空但有素材 | 正常结束 | 照发素材 | 只有视频(少见,提示词要求素材必须配文字) |
| 素材 id 不存在 / 别的项目 / 别的智能体 / 已停用或删除 | 平台只查是整数,能通过 | 丢弃并记日志,正文照发 | 文字照常,少了视频 |
| 正文说「给你发了视频」但 `media` 为空 | 无从发现 | 无从发现 | 文字说有视频但没有;靠工程师按 07 的清单测试发现 |
| 素材链接带查询串或扩展名与类型不一致 | — | 现在会被当文件发 | 收到文件而不是视频;按 §4 数字人第 3 条修 |
| 模型改写了话术原文,或没查方案就给已有方案的客户发了推广 | 无从发现 | 无从发现(不限频、不拦) | 话术走样或被错推广;靠 §7 用例 5、6 和 07 的测试用例清单发现 |
| 某条文字发送失败 | — | 改造后后续照发;记 `send_failed`,不自动重发 | 少一条 |
| 流里没收到 final,条目接口也暂时取不到 | — | 重试 2 次后兜底 | 兜底话术 |
| 部署没开会话历史存储 | 条目接口恒为空 | 流里拿到 final 的照常;要退回查条目的那些轮只能兜底 | 偶发兜底;上线前必须确认 |
| 本轮以 `incomplete` 结束 | 让模型收尾,收尾话也要过格式检查 | 有能解析的 final 就发 | 模型如实说明没做完的回复 |
| `end.artifacts` 非空 | — | v1 不发客户,记日志 | 无 |
| 模型在正文里写了链接 | — | 原样保留 | 带链接的文字 |
| 下一轮模型看到的上下文 | 自己上一轮的 JSON 原文(含它写的固定话术) | 03 落地后兜底话术补进会话;之前(已拍板 03 放最后)模型看不到它 | — |
| 长期记忆提炼 | 看到的助手发言是 JSON 原文 | — | 影响见记忆相关文档(推断:文字都在 `messages` 里,事实照样能提炼) |
