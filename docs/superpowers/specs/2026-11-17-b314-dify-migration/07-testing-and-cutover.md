## 0. 一句话结论

测试和评估由工程师做(11-17 定):助手把 01~06 的全部验收点整理成一份**测试用例清单(Excel)**,工程师在测试环境用测试客户逐条跑;不再做真实对话回放评测,也不做生产影子运行。上线后按员工分步切换:先 1~2 位配合的员工,头 3 天员工每天抽查 AI 回复,有问题立即把这条绑定切回 Dify;再到约 20% → 约 50% → 全部,每步至少 3 天、指标不达标不往下走。切换期间两边并存:有的绑定走 Expert Work、有的走 Dify,一个企微号(一条绑定)同一时间只绑一个智能体(`is_expert_work`)。全部切完稳定 14 天停 Dify 调用密钥,再 30 天删除应用。粗估 6~10 周到全部切完。已拍板(11-17):先交 v0 到测试环境做基础测试;03 人机混合放到最后,切换不等它,之前的已知缺口见 01 §3.11。

## 1. 现状:Dify 现在怎么做(带出处)

**为什么要逐项测。** Dify 里的「健管师」是 127 个节点的流程,其中 17 个大模型节点、1 个智能体节点各管一件事:意图分析给 7 个开关、提醒要素提取有 24 个示例、改档案 / 上报健康数据 / 化验单各有一个专门的提取节点,最后才由「健康管理师」节点写回复(DSL 节点 `17519660545350` 意图分析、`1751532976185` 提取新增提醒的要素、`1761367072328` 提取需更新客户的信息、`1761370867047` 提取待提交的表单数据、`1789742130208` 提取待提交的化验单数据、`1761372447236` 健康管理师;节点类型计数:llm 17、agent 1、http-request 12)。迁移后这些都合进一个智能体:一次对话里模型自己决定查什么、写什么、怎么回。合并后可能出现「回复写得好但忘了记血糖」「提醒时间算错」这类回退,所以每类动作都要有验收行。

**今天有什么可以拿来做基线:**

| 东西 | 现状 | 出处 |
|---|---|---|
| Dify 每轮的输入与回答 | 只在 Dify 自己的日志里;深护库里没有单独存 | 推断 |
| 消息表里哪条是 AI 发的 | pad 消息表没有「AI 发的」列,同一条消息只存一行;dk 只有 10 分钟的临时标记 | 共享背景 §四(sync-pad-message.processor.ts:599-627 读代码确认) |
| 每轮调用记录 | `t_project_ai_agent_invoke_log` 只记「提前退出」和出错的轮次,**正常完成的轮次不记、也不记耗时** | invoke-agent.processor.ts:205-229 写库(读代码确认) |
| 员工 × 智能体绑定 | pad 通道:`t_project_employee_cpwx_pad_relation.agent_code`;dk 通道:`t_project_employee_cpwx_pc_relation`;智能体本身(请求地址、密钥、回复时段、群开关)在 `t_project_ai_agent` | pad-source.adapter.ts:72-95;dk-source.adapter.ts:68-86;TProjectAiAgent.ts(读代码确认) |

所以切换前要先给调用记录加三列(走哪边、是否正常完成、耗时),攒两周 Dify 基线(§5.2)。

## 2. 目标与不做什么

**目标**
1. 01~06 的每个验收点都在测试用例清单里有一行,工程师在测试环境逐条跑过。
2. 写操作(提醒、档案、健康数据、化验单、转人工)在测试环境真写一遍、核对条数和字段码。
3. 切换按员工逐步来,任何一个员工都能单独、几分钟内切回 Dify,切回后提醒和表单数据不受影响。
4. 上线后有按员工的监控和明确的回滚线。
5. 有明确的「什么时候停 Dify」的条件和步骤。

**不做什么(11-17 定)**
- 不做真实对话回放评测(约 215 条脱敏对话、回放项目、模型判官、`b314_*` 评测脚本、600~800 元评测费、授权 / 脱敏 / 标注都不做)。测试和评估由工程师做。
- 不做生产影子运行(影子字段、影子队列、影子密钥、影子对比表、影子期记忆隔离都不做)。用更慢的首批切换代替(§3.7)。
- 不做「新智能体失败就自动改用 Dify 回这一轮」:失败发兜底话术,失败多就把这位员工切回(§6 第 3 条)。
- 平台侧人员(含助手)不碰生产;生产上的操作由用户 / 深护运维执行。

## 3. 设计(先走一遍真实场景,再列规则)

### 3.1 一条验收用例怎么跑(场景)

> 清单第 12 行:「本轮时间 05:10,测试客户 A 私聊发『血糖 6.1』」,期望「直接按空腹写一条血糖记录,不问是不是空腹」,看哪里「表单提交表里测试客户 A 新增 1 条,字段码 = 空腹血糖、值 6.1」。

1. 工程师用测试员工的企微号、测试客户 A 的企微号,在 05:10 前后发这条消息(或在调试台按清单给的 input 首行时间发)。
2. 看回复:没有问「是空腹吗」,口语短句,无 Markdown。
3. 看数据:测试库里查 A 的表单提交,只看条数和字段码,不打印数值以外的客户信息。
4. 在清单这一行填「过 / 不过」、日期、测试人;不过的写现象,附平台 run 编号,交回对应模块的负责人。

### 3.2 测试用例清单(Excel,助手交付)

- **交付物**:一份 Excel(`测试/健管师迁移测试用例.xlsx`),放在 05 §3.6.2 的本地交付文件夹 `B-314健管师交付/` 里,不进 git。助手从 01~06 的验收节和本文 §3.6 汇总,每个验收点一行。
- **谁跑**:工程师,在测试环境,用测试客户(合成数据)。测试和评估都归工程师(11-17 定)。
- **每行的列**:见 §5.1。核心三件:怎么触发、什么算过、去哪看(看数据库只看条数、字段码、时间,不打印客户原话)。
- **过闸**:清单里标「闸门」的行全过、其余行不过的都有结论(修 / 接受 / 下一版),才进生产上线。
- **改了提示词或工具**:受影响的行重跑;改动大时整张重跑。

### 3.8 切换:按员工逐步切,每个都能单独切回

**切换单位**是一条「员工 × 智能体」绑定(pad 通道一行 `t_project_employee_cpwx_pad_relation`,dk 通道一行 `t_project_employee_cpwx_pc_relation`)。做法(用户 11-17 定,见 01 §4):两张绑定表各加字段 `is_expert_work`(默认 0);**切过去 = 置 1(Expert Work 上的智能体编码与这条绑定的 `agent_code` 相同,且 `t_project_expert_work_config` 里该项目这一行 `adapter_type='wecom_chat'`、`enabled=1`、`api_key` 已填),切回 = 置 0**。`agent_code` 仍指向 Dify 那一行,回复时段、群开关、自称、自我介绍继续从那一行读,不需要复制或比对。`t_project_expert_work_config` 对应行 `enabled=0` 时,该项目全部绑定退回 Dify(紧急总开关)。数字人服务每条消息都现查绑定(`pad-source.adapter.ts:80-95` 直接查库),改完下一条消息就生效。

### 3.10 回滚步骤(单个员工,目标 5 分钟内)

1. 把这条绑定的 `is_expert_work` 置 0(深护运维,一条语句;语句模板放切换手册);全项目紧急回退则把 `t_project_expert_work_config` 对应行 `enabled` 置 0。
2. 正在跑的新智能体轮次:取消(平台取消接口,尽力而为);已经拿到结果但还没发的,不发。
3. 确认:下一条客户消息走 Dify(调用记录里的「走哪边」列)。
4. 不用迁数据:新智能体加的提醒仍在同一张表和队列里,到点照发,Dify 能查能删(§3.6 回滚兼容);写的表单 Dify 能读;Dify 每轮拉历史,能看到切换期间的聊天。
5. 再切过去时:03 落地后新智能体靠补消息拿到 Dify 期间的聊天;03 之前看不到 Dify 期间的聊天,长期记忆里也没有,这段只靠 MCP 现查兜(已知局限)。
6. 记录:谁、何时、为什么切回,写进切换手册的台账。

### 3.11 Dify 下线时机

条件:全部绑定已切换,且连续 14 天没有回滚、没有未关闭的严重问题。步骤:
1. 停用 Dify 应用的调用密钥(应用和日志保留,便于查旧问题)。
2. 停用后 30 天,导出需要留档的日志后删除 Dify 应用(这时 08 里「Dify 密钥进了 user 字段」的问题随之失效)。
3. 同时在两家后台作废 DSL 里那两把第三方密钥(天气改用平台级 MCP、快递不做,见 08)。
4. 删掉 Redis 里 `AGENT_CONVERSATION_ID_CACHE_*` 这类 Dify 会话键。
5. 如果深护已按 08 的建议加了网关规则,撤掉给 Dify 出口地址的放行(08 S1)。
6. 项目服务里只给 Dify 用的调用代码,下一个版本删除。

## 6. 异常与边界

1. **首批员工的客户遇到问题**:员工每天抽查;发现「回错客户 / 越医疗边界」当场切回,其余问题记台账、修完再继续。
2. **同一客户被两位员工服务,一位切了一位没切**:长期记忆按客户共享(`user_id` = 客户),没切的那位走 Dify 不读记忆;没有冲突,只是那一侧没有记忆。一个企微号同一时间只走一个智能体。
3. **新智能体失败时不自动改用 Dify 回这一轮(11-17 定)**:失败前可能已经写了一半(提醒加了、回复没出来),这时再让 Dify 跑一遍,Dify 会再加一次提醒。失败就发兜底话术(02),失败多就把这位员工切回。
4. **群里多个客户**:每个客户各自一条会话、各自的身份,切换按员工整体切,群里所有客户一起切。
5. **切换那一刻有正在跑的 Dify 轮次**:让它跑完照发;下一条消息才走新智能体,03 落地后补消息会带上 Dify 那条回答(03 之前看不到)。
6. **Dify 基线不够两周**:调用记录三列上线晚了,基线天数少;监控先按已有天数比,报警线用 §3.9 的绝对数(成功率)兜底。
