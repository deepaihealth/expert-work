- **防**:

## 1. 现状:Dify 现在怎么做(带出处)

先走一遍最严重的一条。

> 有人拿到了数字人服务的公网地址(企微回调、Dify 调用都要从外面进来,地址并不保密)。他翻到接口文档里的示例,发现请求头 `x-from-source` 填某个固定值就能绕过签名和登录。于是他:

## 3. 设计(逐项:场景、证据、修法、优先级、工作量)

归属四类(11-17 定):**迁移需要**(07 切换前置条件第 7 条只含这一类)、**开发约定**(迁移新代码要遵守的规矩,不单列任务)、**随 Dify 下线 / 归 03**、**深护安全待办**(不属于 B-314,深护另行排期)。下面各节的证据和修法保留,供深护排期时用。

### 3.1 S1 调试豁免来源值 = 无鉴权

**场景**:见 §1。

**证据补充**:
- 数字人服务的签名守卫一见到这个来源值就删掉签名参数直接放行(`sign.guard.ts:34-38`);登录守卫对三个来源值直接放行(`auth.guard.ts:37-48`)。两个守卫都注册成全局守卫(`app.module.ts:258-270`),所以覆盖**所有**路由,不只是回调 / 历史 / 提醒:还包括 `agent-callback`(接收回复、转人工、加提醒)、`agent-callback-dk`(同上,dk 通道)、`message/get-history-message`、`ai-notify`(查 / 删提醒)、`tag`、`pad-relation`。
- 项目服务同样(`auth.guard.ts:102` 走 `allowSource`,`:108-125` 三个来源值直接放行;`sign.guard.ts:35-39`)。Dify 用它调了项目服务的读表单、**写表单**(DSL 节点 `1789742880167` 提交用户化验单数据,路径 `/api/form/set-form-field-values`)、读图片接口。
- 这个来源值是深护服务之间互相调用的事实标准:27 个深护仓库的代码里出现了这个请求头名(按文件计数,不含依赖目录)。所以**不能直接删掉判断**,否则内部调用全断。
- 数字人服务前面有 nginx(`src/config/white-list.ts:15` 注释:测试环境的服务名前缀由 nginx 剥掉)。

**修法(三步)**:
1. **止血(建议深护尽快独立做)**:在公网入口(nginx / 负载均衡)上,对带 `x-from-source` 且取值为那几个豁免值的请求,只放行内网来源和 Dify 的出口地址,其余一律 403。内部服务改用内网地址互相调用(多数本来就是,要逐个确认)。Dify 停用后撤掉 Dify 的放行(07 §3.11 第 5 步)。
2. **换成服务密钥(深护安全待办)**:每个调用方一把密钥,放请求头 `x-service-key`,被调方按「调用方 → 密钥摘要 + 允许的路由前缀」核对(常数时间比较;做法参照数字人服务已有的 `PcTaskAuthGuard`,`white-list.ts:9-12` 注释:共享 key + Bearer + 常数时间比较,没配 key 全拒)。上线分两段:先「只记录不拦」一周,看清还有谁在用旧来源值;再改成拦。
3. **删掉旧判断(深护安全待办)**:所有调用方切完后,删掉守卫里按来源值放行的分支和接口文档里的示例值。

**归属(11-17 定)**:**深护安全待办**,不属于 B-314。Expert Work 只带密钥调深护 MCP,MCP 直接写库、投队列(提醒、表单、转人工都是),回复由项目服务取回后交数字人服务内部发送,Expert Work 不调数字人服务或项目服务的任何接口(01 / 02 / 04),所以 S1 不影响迁移,迁移也不依赖它先修。
**建议**:这个问题今天就在生产上。第 1 步网关止血一天内能做完(0.5~1 人天:配规则、确认 Dify 出口地址、确认内部调用走内网、验收),建议深护尽快独立去做;第 2 步换服务密钥(6~10 人天)、第 3 步删旧判断(1 人天)按待办排期。

### 3.2 S2 跨域放开 + 带凭据

**场景**:员工登录着深护后台,又打开了一个恶意网页;网页用脚本向深护接口发跨域请求。`origin: true` 会把任何来源原样回写进允许头,`credentials: true` 允许带 cookie,于是网页能以员工身份读写。

**证据**:数字人 `src/main.ts:41-48`、项目服务 `src/main.ts:79-83`。实际能不能利用取决于会话 cookie:两边的会话 cookie 都没设 `sameSite`(`src/config/session.ts:7`),现代浏览器默认按 Lax 处理,跨站的脚本请求不会带上它;登录令牌走 `x-auth-token` 请求头,别的网站拿不到。所以**目前风险低**(推断:取决于员工用的浏览器版本)。

**修法**:允许的来源改成配置里的后台域名清单;会话 cookie 显式设 `sameSite: 'lax'`、生产 `secure: true`。
**归属**:深护安全待办。**工作量**:每个服务 0.5 人天。

### 3.3 S3 Dify 应用密钥进了 user 字段、Redis 键、日志、调用日志表

**场景**:某位能看日志的同事(或日志服务的第三方账号)在日志里看到形如「密钥_客户 id」的字符串。拿这个密钥加任意客户 id 调 Dify 的对外接口,能列出该客户的会话和消息 —— 即全部客户的健康对话;还能以深护的名义调用应用、消耗额度。

**证据**:
- 数字人服务把智能体行的 API 密钥拼进 Dify 的 user:`src/service/dify.service.ts:74`(`${agent_key}_${customer_pad_userid}`);密钥来自 `invoke-agent.processor.ts:841`(`binding.ai_agent.api_key`)。
- Redis 键名:会话缓存 `AGENT_CONVERSATION_ID_CACHE_${user_code}`(`dify.service.ts:208-219`,永不过期);同一客户锁的键也是「密钥_客户 id」(`invoke-agent.processor.ts:633`)。
- 调用日志表:调用出错时把整个请求体(含 `agent_key`)存进 `t_project_ai_agent_invoke_log.request_payload`(`invoke-agent.processor.ts:205-229` 写库、`:920` 传入)。
- 项目服务:Redis 轮次状态的值里有 `user`(`src/modules/agent/agent.service.ts:811`、`:894`),发给 Dify 的 `user`(`:822`、`:905`);请求日志中间件把整个请求体(含 `user_code`)写进日志队列或日志文件(`src/middleware/logger.middleware.ts:37-50, 64-80`)。

**修法**:
1. **新链路不重犯(开发约定,随 01)**:调 Expert Work 的 `user_id` 用 01 定的「前缀 + 项目 + 客户」格式,不含任何密钥;Redis 键、锁键同理。
2. **Dify 链路不改,随 Dify 下线失效**:Dify 停用密钥、删除应用(07 §3.11 第 1~2 步)后,这把密钥就没用了;同时删掉 `AGENT_CONVERSATION_ID_CACHE_*` 键、清空调用日志表里的 `request_payload` 列。
3. 如果 Dify 下线晚于预期(§9.5 已定先不改),再考虑先把 Dify 的 user 改成「智能体编码_客户 id」的摘要。

**归属**:第 1 步是开发约定(01 的 `user_id` 本来就不含密钥,§5.4);第 2、3 步随 Dify 下线 / 深护安全待办(Dify `user` 字段不改,§9.5)。**工作量**:第 1 步含在 01 里;第 2 步 0.5 人天;第 3 步 1 人天(如要做)。

### 3.4 S4 `.env` 类配置文件被 git 跟踪

**场景**:任何能访问代码仓库(阿里云 Codeup)的人、任何一台克隆过仓库的电脑,都有生产数据库、Redis、对象存储、企微、Dify 等的连接信息(推断:按文件名和常见用法推断,没打开内容)。人员离职、电脑丢失、仓库权限配错,都会直接变成生产密钥泄露。

**证据(只核实「是否被跟踪」,没打开内容)**:`git ls-files` 显示 34 个深护仓库跟踪了 `.env` 类文件。本次迁移涉及的 6 个:数字人服务、项目服务、深护 MCP、pad 消息同步、pad 回调、会话存档,都跟踪 `src/.env`、`src/.env.production`、`src/.env.test`(会话存档另有 `.env.example`)。生产配置文件的提交历史:项目服务 62 次、数字人服务 16 次、深护 MCP 4 次。

**修法**:
1. **新密钥不进 git(开发约定,§5.4)**:给 Expert Work 用的深护 MCP 密钥、项目服务调 Expert Work 的密钥,只放部署时注入的位置(集群密钥 / 配置中心),不写进任何被跟踪的文件。
2. **轮换(深护安全待办)**:深护负责人本地打开这些文件,列出其中属于密钥的项,按「生产先、测试后」逐个在源头轮换。轮换完的旧值即使留在 git 历史里也没用了。
3. **停止跟踪(深护安全待办)**:每个仓库 `git rm --cached` 这些文件、加进 `.gitignore`;保留一个只有变量名、没有值的 `.env.example`;部署改为注入。
4. **历史不重写**(§9.2)。

**归属**:第 1 步是开发约定(§5.4);第 2、3 步深护安全待办。
**工作量**:第 1 步 0.2 人天;第 2 步视密钥数量 2~3 人天(要协调各系统停机窗口,粗估);第 3 步 34 个仓库约 3~5 人天(改部署方式为主,粗估)。

### 3.5 S5 客户隐私与健康建议大量打进日志

**场景**:排查问题的同事(或日志平台上的任何账号)在日志里能直接看到客户姓名、每条聊天原文、语音转写、AI 给的健康建议、提醒内容。日志通常保留更久、看的人更多、权限更松。

**证据**:
- 数字人服务:发文字消息时打印正文(`src/libs/cpwx-pad/message.ts:24`);打印整个任务数据(`invoke-agent-message.processor.ts:448`、`invoke-agent.processor.ts:302`、`send-agent-answer.processor.ts:412`、`send-notify.processor.ts:87`);打印客户聊天列表(`invoke-agent.processor.ts:631`);打印语音转写(`invoke-agent.processor.ts:767`、`source/pad-source.adapter.ts:148`);打印提醒内容(`agent-callback.service.ts:174`);打印发送数据(`send-agent-answer.processor.ts:570`)。
- 数字人服务请求日志中间件:所有路由的请求体、响应体进日志队列或日志文件(`src/middleware/logger.middleware.ts:36-50, 60-72`;注册在 `app.module.ts:278`,`forRoutes('*')`)。**响应体只在非生产环境截断到 200 字,生产环境反而全量**(`logger.middleware.ts:70`:`length > 200 && !this.is_production` 才截断)。

**修法**:
1. **新代码不打(开发约定,§5.4)**:01 / 02 新写的「调 Expert Work、取回回答、拆成消息发出」代码,只打编号、长度、状态、耗时;请求日志中间件对这些新路由只记编号字段(照 `:38-40` 的先例)。

**归属**:第 1 步是开发约定(§5.4,上线前检查一次);第 2、3 步深护安全待办。**工作量**:第 1 步含在 01 / 02 里(0.5 人天检查);第 2 步 3~4 人天(三个服务,粗估);第 3 步运维 0.5 人天。

### 3.10 S10 限流按可伪造的 `X-Forwarded-For`

**场景**:攻击者每个请求换一个 `X-Forwarded-For` 值,限流永远不触发;或者故意填某个正常调用方的地址,把它限掉。

**证据**:数字人、项目服务 `custom-throttler.guard.ts:19, 30`:优先取请求头里的 `x-forwarded-for`,不管它是谁填的。

**修法**:应用设置信任的代理层数(Express `trust proxy`),限流用 `req.ip`;网关把 `X-Forwarded-For` 改成「覆盖」而不是「追加」。

### 3.11 S11 服务器时区没有显式设置

**场景**:如果容器跑在 UTC,回复时段判断用的「现在几点」差 8 小时(凌晨回复、白天不回),客户说「明早 8 点提醒我」被存成北京时间字符串、却按 UTC 解析,提醒晚 8 小时发。

**证据**:数字人回复时段用本地时间 `dayjs().format('HH:mm')`(`invoke-agent.processor.ts:431`);加提醒用本地时间解析触发时间字符串再算延迟(`agent-callback.service.ts:208-210`);镜像(`dockerfile:1-19`)和 `pm2.json` 都没设时区。生产今天没报这类问题,说明运行环境可能在别处设了时区(**推断**,请深护运维确认集群 / 主机配置)。

**修法**:三个服务的镜像显式设 `TZ=Asia/Shanghai`;04 新写的提醒工具解析时间时显式按东八区(不依赖服务器时区)。注意:已经在延迟队列里的提醒是按毫秒延迟排的,改时区不影响它们。
**归属**:镜像设时区属深护安全待办;04 的新提醒工具自己按东八区算(04 §3.9、§4.3),不依赖服务器时区。**工作量**:0.5~1 人天。

### 3.12 S12 pad 竞态:AI 发的消息被当成员工真人发言(功能缺陷,附带列出)

**场景**:AI 给客户分几条气泡回复。pad 平台对第一条的消息回调比数字人服务自己的「我刚发了这条」回写先到,同步服务把这条当成员工本人手打的,设了「真人已接管」标志(600 秒过期,客户再开口时就被删掉);发送处理器发后面几条前查到这个标志,剩下的气泡就不发了。如果客户在 AI 分条发送期间先开口、随后 AI 气泡的回调又把标志写上,客户这条消息会在调用闸门被拦、没人回(03 §1.3 核实,推断损害路径)。迁移后 02 把一轮回复拆成多个文字气泡,后续气泡被拦的机会比 Dify 时期(正文只有一个气泡)更多(推断)。补消息的「是否某一轮的输出」靠 03 的发送登记表判断,不依赖这个标志,所以竞态不影响补消息。

**证据**:同一条消息按 `msg_app_info` 去重,谁先到谁建行,后到的直接返回(`sync-pad-message.processor.ts:599-627`);不是数字人发的就设接管标志 600 秒(`:712-765`),客户发言时删除该标志(`:662-678`,本次复核确认);数字人服务是在发送接口返回后才把带「数字人」标记的消息丢进同步队列(`deep-ai-health-digital-human-agent/src/modules/agent-callback/send-agent-answer.processor.ts:78-99`),所以存在先后。

**修法**:细节在 03(S-3)。方向:数字人服务在调 pad 发送**之前**,对所有以「不是真人」身份发出的消息写 `AI_SENT` 标记(复用 dk 的 `ai-sent.util.ts`),同步服务在「员工本人、不是数字人」分支先查这个标记,命中就按数字人处理、不设接管标志;不论回调和回写谁先到结果都一样。SOP、用药提醒等其它以员工号发消息的服务按同一做法跟进(03 S-3)。
**归属(11-17 定)**:归 03(S-3),不在本文。已知风险:03 之前,pad 上多气泡回复的后几条可能被误拦(02 把一轮回复拆成多条后更容易触发,推断);要不要从 03 单独提前做,随 03 / 00 的排期定。**工作量**:0.5 人天(计入 03)。

## 6. 异常与边界

迁移本身:**新代码漏打了正文**(上线前按 §7 第 2 条搜一遍日志);**健管师密钥漏配或配错**(04 §7 第 6 条和保存时的绑定警告会暴露)。下面 1~7 条是深护安全待办执行时要注意的。

1. **网关止血挡住了还在走公网的内部调用**:先在网关上「只记录」一天,列出所有带豁免值的公网来源,确认都是内部服务或 Dify 后再改成拦;发现的内部服务改走内网。
2. **Dify 出口地址会变**:如果 Dify 用的是云服务、出口地址不固定,网关放行做不了 —— 这时改为给 Dify 单独发一把服务密钥(Dify HTTP 节点可配自定义请求头),只放行 Dify 用到的那几个路由。
3. **服务密钥上线时某个调用方漏改**:`log_only` 阶段会把它列出来;`enforce` 后它会收到 401,不会静默。
4. **轮换生产密钥导致短暂中断**:按「先加新、再切、后删旧」做,能同时认两把的系统先改成同时认。
5. **停止跟踪 `.env` 后有人本地还用旧文件**:`.gitignore` 生效后本地文件不受影响;部署脚本改成注入后,旧文件不再被读取。
6. **改时区影响已排队的提醒**:不会,队列里存的是毫秒延迟;只影响之后新加的。
7. **MCP 密钥范围配错导致健管师调不到工具**(做了按密钥限工具之后):测试环境先配、跑 07 的测试用例清单;生产与测试的配置差异只在项目编码和密钥。
