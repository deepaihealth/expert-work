# B-314-08 深护侧安全整改

> 所属:B-314 Dify「健管师」迁移(总览:00-overview.md)。状态:草稿 v1,待逐个过。

## 0. 一句话结论

深护数字人服务和项目服务的**所有接口**,只要请求头里带一个写死在代码里的「来源」值就不验签名、不验登录,等于对知道这个值的任何人敞开(能让员工企微号给任意客户发消息、读任意客户聊天、改任意客户健康档案);迁移前必须先在网关上把它拦住,同时把深护 MCP 的密钥白名单补上、限定范围,修好 pad 竞态,并作废 Dify 导出文件里的两把第三方密钥。其余(配置文件进 git、日志打印隐私、限流可绕、时区)迁移同期做。

### 威胁模型

- **防**:
  1. 外部未授权的人访问深护接口(知道接口地址和那个来源值就能调)。
  2. 客户在企微里诱导智能体查 / 写别的客户的数据。
  3. 密钥、客户隐私外泄到日志、Redis、数据库日志表、git 仓库、在人手里流转的导出文件。
  4. 同一笔写操作被执行两次(写操作本身的防重复归 04,本文只管入口)。
- **不防**:Expert Work 与深护的系统管理员、员工(可信);能登录深护服务器 / 数据库的运维。
- **只列不做**(超出威胁模型):内部人员故意查看日志;Dify 平台运营方能看到 Dify 日志;拒绝服务攻击;服务器本身被入侵。

## 1. 现状:Dify 现在怎么做(带出处)

先走一遍最严重的一条。

> 有人拿到了数字人服务的公网地址(企微回调、Dify 调用都要从外面进来,地址并不保密)。他翻到接口文档里的示例,发现请求头 `x-from-source` 填某个固定值就能绕过签名和登录。于是他:
> 1. 调「接收回复」接口,指定某位员工和某个客户,内容写一段钓鱼链接 —— 员工的企微号就把这段话发给了客户,客户以为是自己的健管师发的。
> 2. 调「取历史消息」接口,把任意客户的聊天记录一页页拉走。
> 3. 调「加提醒」「删提醒」接口,给客户塞定时消息或删掉吃药提醒。
> 4. 换到项目服务,调「写表单」接口,改掉任意客户的血糖记录和档案。

这不是推测出来的漏洞,而是 Dify 今天就在这么用:DSL 里全部 12 个 HTTP 节点都用这个来源值做「鉴权」(Dify 的 api-key 方式,请求头名 `x-from-source`),其中包括写表单。

## 2. 目标与不做什么

**目标**
1. 迁移切换前,外部拿不到「调试豁免值 = 万能钥匙」;深护 MCP 生产环境没有「任意密钥都能进」的可能,每把密钥只能碰它该碰的项目和工具。
2. 迁移新增的密钥(给 Expert Work 用的 MCP 密钥、项目服务调 Expert Work 的密钥)从第一天起不进 git、不进日志。
3. 迁移新写的代码(项目服务调 Expert Work、取回回答)不把聊天正文和回答打进日志。
4. 存量问题(git 里的配置文件、各服务日志、限流、时区)排进迁移同期,有清单、有验收。

**不做什么**
- 不在本文里设计新的写工具和防重复(归 04)、补消息与 pad 竞态的具体修法(归 03)。
- 不重写 git 历史(理由见待拍板 9.2)。
- 不打开、不复述任何 `.env` 文件的内容;要轮换哪些项,由深护负责人本地打开后自己列。

## 3. 设计(逐项:场景、证据、修法、优先级、工作量)

优先级三档:**迁移前必须**(切第一个员工之前完成,是 07 切换前置条件第 7 条)、**迁移同期**(与迁移并行做,不卡切换)、**之后**。

### 3.1 S1 调试豁免来源值 = 无鉴权

**场景**:见 §1。

**证据补充**:
- 数字人服务的签名守卫一见到这个来源值就删掉签名参数直接放行(`sign.guard.ts:34-38`);登录守卫对三个来源值直接放行(`auth.guard.ts:37-48`)。两个守卫都注册成全局守卫(`app.module.ts:258-270`),所以覆盖**所有**路由,不只是回调 / 历史 / 提醒:还包括 `agent-callback`(接收回复、转人工、加提醒)、`agent-callback-dk`(同上,dk 通道)、`message/get-history-message`、`ai-notify`(查 / 删提醒)、`tag`、`pad-relation`。
- 项目服务同样(`auth.guard.ts:102` 走 `allowSource`,`:108-125` 三个来源值直接放行;`sign.guard.ts:35-39`)。Dify 用它调了项目服务的读表单、**写表单**(DSL 节点 `1789742880167` 提交用户化验单数据,路径 `/api/form/set-form-field-values`)、读图片接口。
- 这个来源值是深护服务之间互相调用的事实标准:27 个深护仓库的代码里出现了这个请求头名(按文件计数,不含依赖目录)。所以**不能直接删掉判断**,否则内部调用全断。
- 数字人服务前面有 nginx(`src/config/white-list.ts:15` 注释:测试环境的服务名前缀由 nginx 剥掉)。

**修法(三步)**:
1. **止血(迁移前必须)**:在公网入口(nginx / 负载均衡)上,对带 `x-from-source` 且取值为那几个豁免值的请求,只放行内网来源和 Dify 的出口地址,其余一律 403。内部服务改用内网地址互相调用(多数本来就是,要逐个确认)。Dify 停用后撤掉 Dify 的放行(07 §3.11 第 5 步)。
2. **换成服务密钥(迁移同期)**:每个调用方一把密钥,放请求头 `x-service-key`,被调方按「调用方 → 密钥摘要 + 允许的路由前缀」核对(常数时间比较;做法参照数字人服务已有的 `PcTaskAuthGuard`,`white-list.ts:9-12` 注释:共享 key + Bearer + 常数时间比较,没配 key 全拒)。上线分两段:先「只记录不拦」一周,看清还有谁在用旧来源值;再改成拦。
3. **删掉旧判断(之后)**:所有调用方切完后,删掉守卫里按来源值放行的分支和接口文档里的示例值。

**优先级**:第 1 步迁移前必须;第 2 步迁移同期;第 3 步之后。
**工作量**:第 1 步 0.5~1 人天(配网关规则、确认 Dify 出口地址、逐个确认内部调用走内网、验收);第 2 步 6~10 人天(27 个仓库里的调用方逐个换,粗估);第 3 步 1 人天。

**迁移后**:Expert Work 不调数字人服务的任何接口(回复由业务方取回再发,提醒 / 表单 / 转人工走深护 MCP,见 01 / 02 / 04),所以第 1 步不会挡住迁移后的链路。

### 3.2 S2 跨域放开 + 带凭据

**场景**:员工登录着深护后台,又打开了一个恶意网页;网页用脚本向深护接口发跨域请求。`origin: true` 会把任何来源原样回写进允许头,`credentials: true` 允许带 cookie,于是网页能以员工身份读写。

**证据**:数字人 `src/main.ts:41-48`、项目服务 `src/main.ts:79-83`。实际能不能利用取决于会话 cookie:两边的会话 cookie 都没设 `sameSite`(`src/config/session.ts:7`),现代浏览器默认按 Lax 处理,跨站的脚本请求不会带上它;登录令牌走 `x-auth-token` 请求头,别的网站拿不到。所以**目前风险低**(推断:取决于员工用的浏览器版本)。

**修法**:允许的来源改成配置里的后台域名清单;会话 cookie 显式设 `sameSite: 'lax'`、生产 `secure: true`。
**优先级**:之后。**工作量**:每个服务 0.5 人天。

### 3.3 S3 Dify 应用密钥进了 user 字段、Redis 键、日志、调用日志表

**场景**:某位能看日志的同事(或日志服务的第三方账号)在日志里看到形如「密钥_客户 id」的字符串。拿这个密钥加任意客户 id 调 Dify 的对外接口,能列出该客户的会话和消息 —— 即全部客户的健康对话;还能以深护的名义调用应用、消耗额度。

**证据**:
- 数字人服务把智能体行的 API 密钥拼进 Dify 的 user:`src/service/dify.service.ts:74`(`${agent_key}_${customer_pad_userid}`);密钥来自 `invoke-agent.processor.ts:841`(`binding.ai_agent.api_key`)。
- Redis 键名:会话缓存 `AGENT_CONVERSATION_ID_CACHE_${user_code}`(`dify.service.ts:208-219`,永不过期);同一客户锁的键也是「密钥_客户 id」(`invoke-agent.processor.ts:633`)。
- 调用日志表:调用出错时把整个请求体(含 `agent_key`)存进 `t_project_ai_agent_invoke_log.request_payload`(`invoke-agent.processor.ts:205-229` 写库、`:920` 传入)。
- 项目服务:Redis 轮次状态的值里有 `user`(`src/modules/agent/agent.service.ts:811`、`:894`),发给 Dify 的 `user`(`:822`、`:905`);请求日志中间件把整个请求体(含 `user_code`)写进日志队列或日志文件(`src/middleware/logger.middleware.ts:37-50, 64-80`)。

**修法**:
1. **新链路不重犯(迁移同期,随 01)**:调 Expert Work 的 `user_id` 用 01 定的「前缀 + 项目 + 客户」格式,不含任何密钥;Redis 键、锁键同理。
2. **Dify 链路不改,随 Dify 下线失效(之后)**:Dify 停用密钥、删除应用(07 §3.11 第 1~2 步)后,这把密钥就没用了;同时删掉 `AGENT_CONVERSATION_ID_CACHE_*` 键、清空调用日志表里的 `request_payload` 列。
3. 如果 Dify 下线晚于预期(见待拍板 9.5),再考虑先把 Dify 的 user 改成「智能体编码_客户 id」的摘要。

**优先级**:第 1 步迁移同期;第 2 步之后。**工作量**:第 1 步含在 01 里;第 2 步 0.5 人天;第 3 步 1 人天(如要做)。

### 3.4 S4 `.env` 类配置文件被 git 跟踪

**场景**:任何能访问代码仓库(阿里云 Codeup)的人、任何一台克隆过仓库的电脑,都有生产数据库、Redis、对象存储、企微、Dify 等的连接信息(推断:按文件名和常见用法推断,没打开内容)。人员离职、电脑丢失、仓库权限配错,都会直接变成生产密钥泄露。

**证据(只核实「是否被跟踪」,没打开内容)**:`git ls-files` 显示 34 个深护仓库跟踪了 `.env` 类文件。本次迁移涉及的 6 个:数字人服务、项目服务、深护 MCP、pad 消息同步、pad 回调、会话存档,都跟踪 `src/.env`、`src/.env.production`、`src/.env.test`(会话存档另有 `.env.example`)。生产配置文件的提交历史:项目服务 62 次、数字人服务 16 次、深护 MCP 4 次。

**修法**:
1. **新密钥不进 git(迁移前必须)**:给 Expert Work 用的深护 MCP 密钥、影子密钥(07)、项目服务调 Expert Work 的密钥,只放部署时注入的位置(集群密钥 / 配置中心),不写进任何被跟踪的文件。
2. **轮换(迁移同期)**:深护负责人本地打开这些文件,列出其中属于密钥的项,按「生产先、测试后」逐个在源头轮换。轮换完的旧值即使留在 git 历史里也没用了。
3. **停止跟踪(迁移同期)**:每个仓库 `git rm --cached` 这些文件、加进 `.gitignore`;保留一个只有变量名、没有值的 `.env.example`;部署改为注入。
4. **历史不重写**(待拍板 9.2)。

**优先级**:第 1 步迁移前必须;第 2、3 步迁移同期(越早越好,不卡切换)。
**工作量**:第 1 步 0.2 人天;第 2 步视密钥数量 2~3 人天(要协调各系统停机窗口,粗估);第 3 步 34 个仓库约 3~5 人天(改部署方式为主,粗估)。

### 3.5 S5 客户隐私与健康建议大量打进日志

**场景**:排查问题的同事(或日志平台上的任何账号)在日志里能直接看到客户姓名、每条聊天原文、语音转写、AI 给的健康建议、提醒内容。日志通常保留更久、看的人更多、权限更松。

**证据**:
- 数字人服务:发文字消息时打印正文(`src/libs/cpwx-pad/message.ts:24`);打印整个任务数据(`invoke-agent-message.processor.ts:448`、`invoke-agent.processor.ts:302`、`send-agent-answer.processor.ts:412`、`send-notify.processor.ts:87`);打印客户聊天列表(`invoke-agent.processor.ts:631`);打印语音转写(`invoke-agent.processor.ts:767`、`source/pad-source.adapter.ts:148`);打印提醒内容(`agent-callback.service.ts:174`);打印发送数据(`send-agent-answer.processor.ts:570`)。
- 数字人服务请求日志中间件:所有路由的请求体、响应体进日志队列或日志文件(`src/middleware/logger.middleware.ts:36-50, 60-72`;注册在 `app.module.ts:278`,`forRoutes('*')`)。**响应体只在非生产环境截断到 200 字,生产环境反而全量**(`logger.middleware.ts:70`:`length > 200 && !this.is_production` 才截断)。
- 项目服务请求日志中间件同样记全量请求体、响应体(`src/middleware/logger.middleware.ts:37-50, 64-80`);已经有一个接口只记客户编号和请求编号的先例(`:38-40`),说明这条路走得通。
- pad 消息同步:打印整条消息数据(`sync-pad-message.processor.ts:279`)。

**修法**:
1. **新代码不打(迁移前必须)**:01 / 02 新写的「调 Expert Work、取回回答、拆成消息发出」代码,只打编号、长度、状态、耗时;请求日志中间件对这些新路由只记编号字段(照 `:38-40` 的先例)。
2. **定日志规矩并改存量(迁移同期)**:可以打的 —— 项目 / 员工 / 客户编号、消息 id、类型、长度、状态、耗时、错误码;不可以打的 —— 姓名、聊天正文、语音转写、回答正文、提醒内容、健康数值、整个请求体 / 任务数据。按上面证据逐处改;请求日志中间件改成「按路由白名单记字段」,并修掉生产不截断的反逻辑。
3. **存量日志清理(之后)**:按定下的保留期(待拍板 9.3)清理已有日志和日志队列落的表。

**优先级**:第 1 步迁移前必须;第 2 步迁移同期;第 3 步之后。**工作量**:第 1 步含在 01 / 02 里(0.5 人天检查);第 2 步 3~4 人天(三个服务,粗估);第 3 步运维 0.5 人天。

### 3.6 S6 深护 MCP:白名单为空即全放行;密钥能读写任意项目

**场景**:如果生产的 `AGENT_KEYS` 没配(或某次发布把它弄丢了),任何人只要能连到 MCP 地址,随便填一个 `x-agent-key` 就能用全部 45 个工具,包括跨客户查询和以员工身份发企微消息的工具。即使白名单配了,拿到任意一把合法密钥的人也能在请求里填任意项目、任意客户:密钥通道下身份参数原样信任。

**证据**:
- `mcp-auth.ts:82-89`:有 `x-agent-key` 时,只有「白名单非空且不在里面」才拒绝,白名单为空就直接放行;白名单来自环境变量(`src/config/app.ts:9`)。
- 密钥通道的身份来自请求头和参数:`mcp-auth.ts:46-54`(项目、公司取自请求头);`bind-employee-context.ts:15, 37, 54` 三个绑定函数对密钥通道都原样返回入参,不覆盖项目 / 员工。
- 生产当前是否为空:**未核实**(配置在 `.env` 文件里,按规矩不打开),请深护负责人确认。

**修法(迁移前必须)**:
1. **生产缺密钥就不启动**:生产环境 `AGENT_KEYS` 为空时服务启动失败(而不是放行)。
2. **每把密钥带范围**:配置从「密钥列表」改成「密钥摘要 → 名字、允许的项目、允许的工具、是否影子」(§5.2)。密钥通道下,请求里的项目不在允许范围就拒;工具不在允许清单就不列出也不让调。给 Expert Work 健管师的密钥只放 04 定的那十来个工具,测试 / 生产各一把。07 的影子密钥用同一套配置(`shadow: true`)。
3. 平台侧照 00 已拍板:每个工具用平台绑定(`arg_bindings`)把项目 / 客户 / 员工钉死,模型看不到也改不了;这一层防「客户诱导」,本条防「密钥外泄」,两层都要。
4. 加固(之后,00 已定为可选):服务端核对「这个客户确实属于这个员工 / 项目」。

**优先级**:1~3 迁移前必须;4 之后。**工作量**:1.5~2.5 人天(含测试)。

### 3.7 S7 MCP 未预料的异常原文返回给模型

**场景**:某个工具查库时报错,错误原文(可能含 SQL 片段、表名、内部地址,甚至别的行的数据)原样回给模型;模型在企微里对客户说「系统提示:……」,或者被人用来试探内部结构。

**证据**:`mcp-error.ts:32-44`:不是已知业务错误时,把 `err.message` 原样放进返回给模型的 `message`。

**修法**:未预料的异常对模型只返回「服务暂时出错,请稍后再试」+ 一个错误编号;原文连同错误编号记在服务端日志(按 §3.5 的规矩,不含客户数据)。已知业务错误(参数不对、找不到客户等)照旧给提示和建议动作。

**优先级**:迁移前必须(迁移后这些工具直接面对客户对话)。**工作量**:0.5 人天。

### 3.8 S8 Dify HTTP 节点关闭证书校验

**现状**:DSL 全部 12 个 HTTP 节点 `ssl_verify: false`。Dify 到深护这段路上如果有人做中间人,能读写客户数据。

**迁移后不再适用**:这些 HTTP 节点随 Dify 一起下线;Expert Work 连深护 MCP 用默认的证书校验(平台源码里没有关闭证书校验的写法,`git grep` 无命中)。**带来一个前置要求**:深护 MCP 的测试 / 生产域名必须有有效的公网证书,否则平台连不上 —— 不要为此让平台关校验。

**修法**:迁移前确认深护 MCP 两个环境的证书有效;Dify 下线前如果证书本来就有效,可以顺手把这 12 个节点的校验打开(几分钟)。
**优先级**:之后(随 Dify 下线消失)。**工作量**:0.1 人天。

### 3.9 S9 Dify 导出文件里的明文第三方密钥

**场景**:Dify 导出的 DSL 文件被当作普通资料发来发去(聊天、邮件、下载目录),里面 MCP 地址的查询参数就是地图服务(高德)和快递查询服务(快递100)的密钥。拿到文件的人就能用深护的额度调这两家服务。

**证据**:DSL 节点 `1752317953920`(MCP Agent)第 4661、4663 行。

**修法**:
1. **立即轮换(迁移前必须)**:在两家后台作废旧密钥、生成新密钥,更新 Dify 里这个节点(Dify 下线前天气还要用)。
2. **迁移后作废**:天气改用平台级地图 MCP(00 已拍板),快递不做,Dify 下线后两把新密钥一起作废。
3. **限制文件流转**:DSL 导出文件按密钥同等对待,不进 git、不发群;迁移结束后删除各处副本(包括本次调查用的那份,由用户决定何时删)。以后 Dify 里的密钥放「密钥类型」的环境变量,导出时不带出。

**优先级**:第 1、3 步迁移前必须;第 2 步之后。**工作量**:0.5 人天。

### 3.10 S10 限流按可伪造的 `X-Forwarded-For`

**场景**:攻击者每个请求换一个 `X-Forwarded-For` 值,限流永远不触发;或者故意填某个正常调用方的地址,把它限掉。

**证据**:数字人、项目服务 `custom-throttler.guard.ts:19, 30`:优先取请求头里的 `x-forwarded-for`,不管它是谁填的。

**修法**:应用设置信任的代理层数(Express `trust proxy`),限流用 `req.ip`;网关把 `X-Forwarded-For` 改成「覆盖」而不是「追加」。
**优先级**:迁移同期。**工作量**:0.5 人天。

### 3.11 S11 服务器时区没有显式设置

**场景**:如果容器跑在 UTC,回复时段判断用的「现在几点」差 8 小时(凌晨回复、白天不回),客户说「明早 8 点提醒我」被存成北京时间字符串、却按 UTC 解析,提醒晚 8 小时发。

**证据**:数字人回复时段用本地时间 `dayjs().format('HH:mm')`(`invoke-agent.processor.ts:431`);加提醒用本地时间解析触发时间字符串再算延迟(`agent-callback.service.ts:208-210`);镜像(`dockerfile:1-19`)和 `pm2.json` 都没设时区。生产今天没报这类问题,说明运行环境可能在别处设了时区(**推断**,请深护运维确认集群 / 主机配置)。

**修法**:三个服务的镜像显式设 `TZ=Asia/Shanghai`;04 新写的提醒工具解析时间时显式按东八区(不依赖服务器时区)。注意:已经在延迟队列里的提醒是按毫秒延迟排的,改时区不影响它们。
**优先级**:迁移同期(04 的新提醒工具必须显式)。**工作量**:0.5~1 人天。

### 3.12 S12 pad 竞态:AI 发的消息被当成员工真人发言(功能缺陷,附带列出)

**场景**:AI 给客户分几条气泡回复。pad 平台对第一条的消息回调比数字人服务自己的「我刚发了这条」回写先到,同步服务把这条当成员工本人手打的,设了「真人已接管」标志(600 秒过期,客户再开口时就被删掉);发送处理器发后面几条前查到这个标志,剩下的气泡就不发了。如果客户在 AI 分条发送期间先开口、随后 AI 气泡的回调又把标志写上,客户这条消息会在调用闸门被拦、没人回(03 §1.3 核实,推断损害路径)。迁移后 02 把一轮回复拆成多个文字气泡,后续气泡被拦的机会比 Dify 时期(正文只有一个气泡)更多(推断)。补消息的「是否某一轮的输出」靠 03 的发送登记表判断,不依赖这个标志,所以竞态不影响补消息。

**证据**:同一条消息按 `msg_app_info` 去重,谁先到谁建行,后到的直接返回(`sync-pad-message.processor.ts:599-627`);不是数字人发的就设接管标志 600 秒(`:712-765`),客户发言时删除该标志(`:662-678`,本次复核确认);数字人服务是在发送接口返回后才把带「数字人」标记的消息丢进同步队列(`deep-ai-health-digital-human-agent/src/modules/agent-callback/send-agent-answer.processor.ts:78-99`),所以存在先后。

**修法**:细节在 03(S-3)。方向:数字人服务在调 pad 发送**之前**,对所有以「不是真人」身份发出的消息写 `AI_SENT` 标记(复用 dk 的 `ai-sent.util.ts`),同步服务在「员工本人、不是数字人」分支先查这个标记,命中就按数字人处理、不设接管标志;不论回调和回写谁先到结果都一样。SOP、用药提醒等其它以员工号发消息的服务按同一做法跟进(03 S-3)。
**优先级**:迁移前必须(多气泡回复让它更容易触发)。注意 03 整体已拍板放最后做,这一项要从 03 里单独提前做。**工作量**:0.5 人天(数字人服务自己发的消息,计入 03 S-3;其它服务跟进另计)。

## 5. 接口与数据结构

### 5.1 服务间调用密钥(S1 第 2 步)

请求头:`x-service-key: <该调用方的密钥>`、`x-service-name: <调用方名字>`。

被调方配置(部署时注入,不进 git):

```json
{
  "callers": {
    "robot-service": { "key_sha256": "<摘要>", "routes": ["/api/message/"] },
    "dify-legacy": { "key_sha256": "<摘要>", "routes": ["/api/agent-callback/", "/api/agent-callback-dk/", "/api/message/", "/api/ai-notify/"] }
  },
  "mode": "log_only"
}
```

`mode`:`log_only`(只记录谁还在用旧来源值,不拦)→ `enforce`(拦)。比较用常数时间。

### 5.2 深护 MCP 密钥范围(S6)

```json
{
  "<密钥摘要>": {
    "name": "expert-work-jgs-prod",
    "projects": ["<项目编码>"],
    "tools": ["profile_get_brief", "form_get_latest_field_values", "form_save_customer_values", "reminder_create", "..."],
    "shadow": false
  },
  "<另一把密钥摘要>": {
    "name": "expert-work-jgs-prod-shadow",
    "projects": ["<项目编码>"],
    "tools": ["..."],
    "shadow": true
  }
}
```

规则:生产环境此配置为空 → 启动失败;请求的项目不在 `projects` → 拒;工具不在 `tools` → 不列出、不让调;`shadow: true` → 写工具只记不写(07 §3.7)。工具清单以 04 为准。

### 5.3 MCP 未预料异常的返回

```json
{ "code": 9999, "category": "internal", "message": "服务暂时出错,请稍后再试", "error_id": "<随机编号>" }
```

服务端日志:`error_id` + 工具名 + 错误原文(不含客户数据)。

### 5.4 日志规矩

| 可以打 | 不可以打 |
|---|---|
| 项目 / 员工 / 客户编号、消息 id、轮次令牌、平台运行编号 | 姓名、昵称、群名 |
| 消息类型、长度、条数 | 聊天正文、语音转写、回答正文、提醒内容 |
| 状态、耗时、错误码、错误编号 | 健康数值、档案字段值 |
| 字段码 | 整个请求体、整个任务数据、任何密钥或带密钥的字符串 |

## 6. 异常与边界

1. **网关止血挡住了还在走公网的内部调用**:先在网关上「只记录」一天,列出所有带豁免值的公网来源,确认都是内部服务或 Dify 后再改成拦;发现的内部服务改走内网。
2. **Dify 出口地址会变**:如果 Dify 用的是云服务、出口地址不固定,网关放行做不了 —— 这时改为给 Dify 单独发一把服务密钥(Dify HTTP 节点可配自定义请求头),只放行 Dify 用到的那几个路由。
3. **服务密钥上线时某个调用方漏改**:`log_only` 阶段会把它列出来;`enforce` 后它会收到 401,不会静默。
4. **轮换生产密钥导致短暂中断**:按「先加新、再切、后删旧」做,能同时认两把的系统先改成同时认。
5. **停止跟踪 `.env` 后有人本地还用旧文件**:`.gitignore` 生效后本地文件不受影响;部署脚本改成注入后,旧文件不再被读取。
6. **改时区影响已排队的提醒**:不会,队列里存的是毫秒延迟;只影响之后新加的。
7. **MCP 密钥范围配错导致健管师调不到工具**:测试环境先配、跑 07 的写操作验收;生产与测试的配置差异只在项目编码和密钥。

**9.2 git 历史里的 `.env` 要不要重写历史删掉?**
- 选项 A:只轮换、停止跟踪,不重写历史。
- 选项 B:重写全部 34 个仓库的历史。
- 推荐 A。理由:轮换后旧值失效,重写历史收益很小;重写要所有人重新克隆、所有分支重建,协调成本高;已经被克隆走的副本也删不掉。如合规有明确要求再做 B。

**9.3 日志保留多久、存量怎么清?** 推荐:应用日志 30 天、日志队列落的表 30 天;改造完成后一次性清理更早的。理由:排查问题很少需要 30 天前的明细;越久越多越危险。

**9.4 MCP 密钥范围要不要同时限项目和工具?** 推荐两者都限。理由:限项目防「一把密钥读全部项目」,限工具防「拿健管师的密钥去调发企微、跨客户查询」;配置同一处,成本几乎一样。

**9.5 Dify 链路的 user 字段要不要现在就改?**
- 选项 A:不改,Dify 下线后删应用即失效。
- 选项 B:现在就改成摘要。
- 推荐 A,前提是 Dify 在 3 个月内下线;若下线时间推迟到更晚,改选 B。理由:改 user 会让 Dify 侧会话全部断开重来,而 Dify 不久就下线。

**9.6 服务端核对客户归属(加固)什么时候做?** 推荐迁移之后。理由:平台绑定已让模型改不了身份参数,范围限定后密钥泄露的影响也收窄;归属核对要给每个工具补校验,工作量不小,不该卡迁移。
