## 0. 一句话结论

收消息、攒消息、打断、各道闸、真人接管、发送这些全留在数字人服务,逻辑基本不变;只把「项目服务调 Dify」换成「项目服务调 Expert Work 的 `POST /v1/agents/{code}/runs`(stream + 条目模式)」,由项目服务等这一轮结束、取出最终回复交回数字人服务直接入发送队列(不走 MCP 发消息,已拍板)。user_id = `wx:{项目}:cus:{客户编号}`(已拍板);会话 = 客户 + 智能体一段,私聊和各群共用,**始终一段、不按空闲换新**,成本靠调低压缩门槛控制(已拍板);每轮时限 300 秒;Idempotency-Key 用本批企微消息身份组;新消息打断旧轮时调 `:cancel`,旧轮结果一律不发;失败 / 超时发兜底话术,同一聊天窗口 10 分钟最多一次。新链路里不出现任何 Dify 应用密钥。

### 1.2 现在链路里与本文相关的毛病

- **密钥到处都是**:Dify 应用密钥拼进了 Dify 的 `user`(`dify.service.ts:74`)、会话缓存的 Redis 键(`:209, :218`)、同客户锁的 Redis 键(`invoke-agent.processor.ts:633`)、发起失败时写进调用日志表的请求体(`:841` 放进 payload,`:920` 落表)。
- **打断的兜底不生效**:`receive-answer` 靠 `invoke_token` 判断「这轮已被取消就丢弃」(`agent-callback.service.ts:138-144`),但 Dify 回调的请求体里没有 `invoke_token`(DSL @7913-7917 只有 answer / file_link_list / room_conversation_id / employee_pad_userid / customer_pad_userid),所以这道兜底对 Dify 的回答从来没起过作用;dk 通道用 `invoke_token` 做发送防重(`agent-callback-dk.service.ts:63`)同样拿到的是空值。
- **会话无限长**:Dify 会话永不过期、私聊群聊共用;Dify 自己每轮只取最近 30 条历史,所以成本没爆,但迁到 Expert Work 后会话内容会一直累积(见 §3.4)。
- **失败时客户什么都收不到**:项目服务抛错时数字人服务只记日志,本批消息照样从缓存里删掉(`invoke-agent.processor.ts:913-922, 963-966`)。
- **入参里一半没用上**:数字人服务每轮传 17 个 inputs(dk 再多 1 个 `source`)(`invoke-agent.processor.ts:844-866`),Dify 开始节点只声明了 12 个,其中 `employee_name`、`customer_name` 声明了但整个工作流没引用;`self_appellation`、`has_referral_human` 等根本没声明(DSL 1748585795560@2374-2471)。

## 2. 目标与不做什么

**目标**

1. 客户在企微里发消息,到收到回复,体验不变或更好:不多发、不漏发、被打断的旧回答不发。
2. 调用链里不出现任何 Dify 应用密钥;Expert Work 的 API key 只留在项目服务。
3. 每个客户一个终端用户(长期记忆按客户共享),每个客户 × 智能体一段会话(私聊和各群共用),每次送进模型的上下文有上限(压缩门槛),成本可控。
4. 网络抖动、进程重启时重试不产生第二轮,也不重复扣费。
5. 按智能体逐个切换、随时能切回 Dify。

**不做什么**

- 不改收消息、攒消息、各道闸、真人接管、发送队列本身的逻辑(只改调用目标和锁键)。
- 不改企微收发通道(pad / dk)。
- 提示词、回复格式、兜底话术的文字不在本文(见 02);补消息字段和未送达回报的平台实现不在本文(见 03);工具、身份绑定、深护 MCP 不在本文(见 04)。
- 主动 / 定时触达不在本文。
- 不用 queue 模式、不用 webhook(webhook 不带正文和 user_id、晚约 15 秒,共享背景)。

## 3. 设计(先走一遍真实场景,再列规则)

### 3.1 走一遍:一条私聊消息从发出到收到回复

> 客户 A 在私聊里给健管师企微号 E 发消息。下面的时间都是东八区。

1. **14:31:05** 客户 A 发「早上空腹血糖 6.8」;14:31:20 又发了一条语音「今天早饭吃了两个包子」;14:31:40 发一张早餐照片。
2. 数字人服务照旧把三条攒进「E × A × 私聊」这一批,每来一条就把 8 秒计时器重置。14:31:48 计时到,开始处理。
3. 各道闸照旧过一遍(绑定、回复时段、开关、有效期、真人刚回过没有……)。同客户锁的键改成不含密钥的 `invoke_lock:{项目}:{智能体}:{客户号}`,抢到锁。
4. 语音照旧转成文字。数字人服务看到 E 绑定的智能体标记为「走 Expert Work」,于是调项目服务新入口 `/agent/invoke-digital-human-ew`,带上本批三条消息(每条带企微消息身份、类型、文字或 OSS 链接、发送时间)和身份字段。
5. 项目服务:
   - 查余额(照旧);
   - 算 user_id = `wx:{项目}:cus:{客户编码}`;
   - 查会话映射表:「智能体 × 客户 A」这一格(私聊和 A 所在各群共用)已有会话,续用(不按空闲换新,§3.4.3);只有这一格还没有会话(A 第一次走本智能体)时,才先调 `POST /v1/agents/{code}/sessions` 建一段、写进映射表;
   - 下载那张照片,按文件头判断是 JPEG,带 `session_id` 上传,拿到 `upload_id`;
   - 拼 input:首行「[本轮时间 2026-11-17 14:31 周二 · 私聊]」(会话不分窗口,首行注明本批来自私聊还是群聊),后面每条消息一行、带发送时间;
   - 按本批消息身份算 Idempotency-Key;
   - `is_first_contact` 照数字人服务传来的值转给平台(E 与 A 之间从没有过文字消息才是 "1",§3.3.2);A 第一次走本智能体(映射表里原来没有这一格)时,03 落地后按 03 带上「最近的企微消息」做衔接,03 之前不带(已知缺口,§3.11);
   - 发 `POST /v1/agents/{code}/runs`(`mode: stream`、`stream_format: items`),从响应头拿到 run_id,写进轮次状态(供取消用)和 run 台账。
6. 平台跑这一轮:召回客户 A 的长期记忆(私聊和群里说过的都在),按需调深护 MCP 查档案、写健康数据,最后给出回答。项目服务在流里收到 `item.done`(`type=assistant_message`、`channel=final`),再收到 `end`(`status=success`)。
7. 项目服务按场景扣康豆(口径见 §3.8),把最终回复按 02 解析(视频编号换链接),按 §5.1 返回 `outcome: "reply"` 和 `answer_text[]`、`file_link_list[]` 及各自来源。
8. 数字人服务确认这一轮没被标成「取消中」,按通道入发送队列(pad 进 `send-agent-answer-queue`,dk 进 `pcSendTaskService.enqueueAnswer`,防重种子用 run_id)。发送前的真人接管检查照旧。
9. 发送结果(发出 / 被真人接管拦下 / 发送失败)记到 run 台账;没发出去的,按 03 报「未送达」(03 推荐当场单独调接口报;03 之前没有这个接口,属已知缺口,§3.11)。

**打断的那一版**:如果 14:32:10(第 6 步还在跑)客户 A 又发「对了,昨晚睡得不好」——

- 数字人服务照旧:把轮次状态置为「取消中」,调项目服务取消入口;项目服务按 invoke_token 找到 run_id,调 `POST /v1/agents/{code}/runs/{run_id}:cancel`,并让第 5 步那个还在等的请求立刻返回 `{outcome: "cancelled"}`;
- 不管这一轮最后是 `interrupted` 还是抢先跑完的 `success`,结果一律不发;如果它已经生成了最终回答,台账记为「未送达」,按 03 报;
- 8 秒防抖后,数字人服务用「新消息」再触发一轮,同一段会话、新的 Idempotency-Key。旧那批客户消息怎么带见 §3.6。

### 3.3 请求字段怎么填

#### 3.3.1 `input`:本批客户的话 + 本轮时间

本轮时间只用这一种做法(按推荐定 11-17,§9 第 7 条):06 不另传 `current_time` 变量、不另加【MM-DD HH:mm】前缀。

- 首行写本轮时间,精确到分钟、带星期,东八区显式计算(深护服务的容器没设时区,共享背景;项目服务可复用 `src/libs/timezone-date.ts`);同一行注明本批来自「私聊」还是「群聊」(已拍板会话不分私聊 / 群,模型要靠这一行知道这句话在哪儿说的;群名不写,群名可被成员改)。
- **本轮时间取本批最后一条客户消息的发送时间**,不取「现在」。理由:① 重试时请求体必须一字不差(§3.5),取「现在」会让重试变成 422;② 「10 分钟后提醒我」本来就该从客户说话那一刻算。两者相差的只是防抖的几秒到几十秒,等锁最坏时 10 分钟,可接受。
- 之后每条消息一行,行首带 `HH:mm`;语音转写的行标「(语音转文字)」,让模型知道可能有错字;图片 / 文件那一行写「(图片)」「(文件 xxx.pdf)」,内容本身走 `files`。
- 去掉 @ 的做法照旧(`removeAtMentions`)。
- 只有附件没有文字时,不再塞「帮我看一下」——input 里本来就有「(图片)」那一行。

**为什么时间放 input、不放系统提示词变量**(核实结果,读代码确认):

- 平台自己只注入**日期**:构建智能体时算一次「The current date is …」放进系统提示词(`agent_factory.py:1203-1211, 1888-1908`),构建结果缓存 30 分钟(`runtime.py:452`),所以过零点后最多 30 分钟里还是昨天的日期;这段文字还叫模型「要精确时间就调 exec_python」,而健管师没有代码工具。
- 系统提示词开了模板模式后,**每一轮都用本轮 inputs 重新渲染**(`prompt_render.py:260-265`)。被模板引用的变量一变,系统提示词的字节就变,提示词缓存从第一个字起全部失效;没被引用的变量不进系统提示词,不影响缓存。所以「每分钟都变」的值不能放进被引用的变量。
- 平台每一步把计划、预警等「平台段」贴在**最后一条消息末尾**、不落库(`platform_context.py:1-35`),前面的消息不动,缓存才稳;把时间写在本轮客户消息里,同样只影响最后一段。
- Dify 现在也是把时间放在本轮「用户」消息开头(DSL @7466),行为上一致。

代价与配套:

- input 整段会被当作「客户说的话」:长期记忆第一次提炼只读 input 这一段(`runs.py:503-521`),记忆召回和知识库探测的检索词也取最新客户消息。时间行会混进去,属于少量噪声。验收里专门查(§7 第 14 条)。
- 建议这个智能体**关掉平台的日期注入**(`dynamic_context.inject_current_date: false`,`agent_spec.py:338`):每轮都有精确时间,再留一个可能滞后 30 分钟的日期只会打架;关掉后系统提示词跨天也不变,缓存更稳。提示词里写明「以本轮消息开头的时间为准」(06 节 C)。

#### 3.3.2 `inputs`:要声明哪些变量

规则(读代码确认):

- 只有系统提示词开了模板模式并声明了变量才能传;没声明的键、缺了必填的键都 422(`prompt_render.py:268-285`)。
- 上限:64 个键、单个字符串值 8192 字、整体 65536 字节(`agents.py:880-888`;对外文档 chat.md §2.7)。

#### 3.3.3 `files`:OSS 链接 → 下载 → 上传 → upload_id

平台的规矩(对外文档 chat.md §2.6,读文档确认):

- 先 `POST /v1/agents/{code}/uploads`(表单带 `user_id`、`session_id`、文件),拿 `upload_id`,再在 `files[]` 里引用。
- 按表单里声明的 Content-Type 判类型,不看后缀:图片 png / jpeg / webp / gif ≤ 10 MiB;文档 pdf / docx / xlsx / pptx / txt / md / csv ≤ 25 MiB;不收音频、视频。
- **图片必须和这一轮属于同一段会话**,所以上传时一定带 `session_id`;这也是 §3.4 要求「先建会话再跑」的原因之一。
- 每轮最多 8 张图(`settings.py:337`),超了 422 且读不到错误码;`files` 合计最多 64 项。

做法(项目服务):

1. 本批里的图片 / 文件消息按发送时间排序;图片只取**最后 8 张**(现在是最后 10 个,`invoke-agent.processor.ts:795-797`),文档另取(建议最多 5 份)。
2. 从 OSS 下载。只允许深护自己的 OSS 域名(配置白名单),防止链接被换成内网地址。
3. 按文件头判断真实类型,不认后缀;不在白名单里的(HEIC、老的 .doc / .xls、视频等)不上传,在 input 对应那一行写明「(客户发了一个 xxx 文件,暂时打不开)」,让模型如实说。可复用 `upload-validation.ts:13-31` 的白名单与大小检查。
4. 带 `session_id` 上传,把「会话 × 企微消息身份 → upload_id」记一份(Redis,存 1 天)。**重试或打断后重跑时复用同一个 upload_id**,不重新上传:重新上传会拿到新 id,请求体一变,同一个 Idempotency-Key 就会 422(§3.5)。
5. 会话不按空闲换(§3.4.3);只有 404 换了新会话时,图片要在新会话里重新上传(图片绑会话);文档平台允许跨会话引用(chat.md §2.6「引用别的会话上传的文档」),但为了简单也一律按新会话重传。

#### 3.3.4 `untrusted_content`:用途边界

平台规矩:最多 16 块、每块 8192 字;放在客户消息正文之后、加围栏当数据;会留在会话里;长期记忆第一次提炼只读 input 那一段,不读它(`runs.py:503-525`)。

| 放 | 不放 |
|---|---|
| 首期不用。将来接入卡片类、合并转发类、引用别人消息这类「客户转来的别人的内容」时放这里 | 客户自己说的话(要进记忆,必须在 input) |
| | 本轮时间、身份(input 首行 / inputs) |
| | 健管师一方的消息、会话外的历史(走 03 的补消息字段) |

现在数字人服务只收文字、语音、图片、文件四种(`invoke-agent.processor.ts:746-797`),卡片、转发等类型本来就丢弃,所以首期不需要这个字段。项目服务客户端也还没有这个字段(`expert-work.types.ts:42-49`),等要用时再加。

### 3.4 user_id 与会话

#### 3.4.1 user_id

- 已拍板:user_id = 客户编号,格式 `wx:{项目编码}:cus:{客户编号}`;群里没建档的发言人用 `wx:{项目编码}:ext:{企微账号}`(11-17)。
- 现有前缀(读代码确认,`expert-work-user.ts:3-29`):员工侧 `pc:{项目}:emp:{员工}`(ai-health-plan 等)、员工代客户 `pc:{项目}:emp:{员工}:cus:{客户}`、H5 里客户本人 `h5:{项目}:cus:{客户}`。
- 前缀 **`wx:`**(wx = 企微)与员工侧不撞,也不与 H5 的 `h5:` 共用(共用等于让企微健管师和 H5 里客户自用的智能体共享长期记忆,且 `h5:` 在项目服务里用于计费归属判断)。平台按(租户, user_id)隔离长期记忆,同一个 user_id 下「事实」类记忆跨该用户的所有智能体共享(共享背景),所以前缀选择就是「和谁共享记忆」的选择。
- 长度 ≤ 255、不含 NUL,沿用 `assertValidExternalUserId`。项目服务里按前缀判断「是不是客户发起」的 `isCustomerExternalUserId` 只认 `h5:`,新前缀要补(计费归属用)。
- 同一个客户的私聊和所有群用同一个 user_id,长期记忆因此共享;会话也共用一段(下一节)。
- 已知限制:群里没建档的发言人(`ext:`)之后建了档,user_id 换成 `cus:`,旧 `ext:` 下的长期记忆不会自动合并过来。

#### 3.4.2 会话键

**会话键 =(项目, 智能体, 客户)**(已拍板 11-17):同一客户的私聊和他所在的各个群共用一段会话,不分聊天窗口,也不含员工企微号。这与 Dify 现在的映射一致(Dify 的 conversation_id 粒度就是「智能体 × 客户」,`dify.service.ts:207-219`)。

由此带来的几点:

- 模型要知道每句话在哪儿说的:本批来自私聊还是群聊写在 input 首行(§3.3.1)。
- 数字人服务的攒消息、轮次状态、真人接管标志的键仍带员工企微号和群(`invoke-agent-message.processor.ts:80-117`;`invoke-agent.processor.ts:713-717`),不改;同一客户一把锁本来就跨所有群(§3.7),保证同一段会话里同时只有一轮在跑。
- 同一个客户被两个绑定同一智能体的员工号服务时,两边也共用这一段会话;人设(自称)按本轮的员工号传(`invoke-agent.processor.ts:861-862`)。
- 群聊里可能提到私聊里说过的内容;是否加「群里不主动提健康数据和隐私」这类规则,已拍板先不加,业务侧需要时再加(06)。

#### 3.4.3 什么时候开新会话

已拍板(11-17):**不做「空闲 N 小时换新会话」**。一个客户在一个智能体下始终一段会话(私聊和群共用),成本靠调低压缩门槛控制(§3.4.4)。只有两种情况开新会话:

1. 映射表里这一格还没有会话(这个客户第一次走本智能体,通常就是切换后的第一轮)。
2. 平台返回 404 `SESSION_NOT_FOUND`(例如会话在控制台被物理删除)时,映射表标记关闭、开新会话、换新 Idempotency-Key 重发一次。归档不影响续用(query.md §5.5),不会触发这一条。

另外:

- **开新会话一律先调 `POST /sessions`**,拿到 session_id 写进映射表,再上传、再跑。不靠「runs 不带 session_id 自动建」:那样带图片的第一轮做不了(图片要先绑会话),重试时请求体里有没有 session_id 也会前后不一致(§3.5)。
- **会话绑定建会话时的智能体版本号**(`thread_meta.agent_version`,`api/runs.py:1915-1960`):以后改配置只能在同一版本号上原地编辑、发布(发布即替换这一版并清构建缓存,已有会话下一轮就用新配置,`api/agents.py:2371-2425`);**不要升 `metadata.version`**,升了的话老客户的会话会一直停在旧版。
- 上线后看真实费用;贵了再考虑加回「空闲换会话」(后续可选,不在 v1)。

第一段会话开头怎么衔接:

- **长期记忆**:平台每一轮开始都会按最新客户消息召回这个客户的长期记忆(`memory.py:1250-1265`),第一轮也一样;私聊、群里沉淀下来的事实都在。会话被裁到最近 20 轮以后(§3.4.4),更早的内容也靠它衔接。
- **最近聊天**:03 落地后,这个客户第一次走本智能体时,业务方按 03 带上「会话里还没有的企微消息」——也就是最近一段聊天(条数 / 字数上限在 03 定)。这样客户说「刚才那个」时模型看得到。03 之前(已拍板 03 放最后做)会话从空开始,只靠长期记忆衔接(§3.11)。
- 工具查的东西(档案、方案)不衔接,需要时模型再查。

#### 3.4.4 成本:不切会话,靠压缩门槛封顶(粗算)

计算假设(全部是**粗估**,上线前要用测试环境实测替换,见 §8 的「先数」):

| 项 | 取值 | 依据 |
|---|---|---|
| 模型与单价 | 健管师现用 qwen3.8-max:输入 12 元 / 百万 token,缓存命中 1.5,输出 36 | 价目表迁移 0187(读代码确认);qwen4-max 为 10 / 0.5 / 30(迁移 0192) |
| 固定前缀 S | 约 1.2 万 token:健管师提示词、平台固定段、约 15 个工具的说明、召回的记忆 | 粗估 |
| 每轮留在会话里的增量 g | 约 1,500 token:客户本批、回复、「本轮输入」说明段、工具调用与结果(平台在上下文超过 3 万后会把旧轮次的大块工具结果收起,`agent_spec.py:1044-1048`)、补消息 | 粗估 |
| 每轮调模型次数 k | 3 次(约 2 次查 / 写工具 + 1 次作答) | 粗估 |
| 缓存 | 一轮里第 1 次调用不命中(客户隔几分钟到几小时才回,缓存通常已过期,推断;且每轮召回的记忆放在前缀里、结果会变);第 2、3 次调用前缀命中 | 推断 |
| 平台门槛(本智能体) | 已拍板(11-17),纯配置:`policies.tool_result_prune.absolute_cap_tokens: 40000`(先把旧的大块工具结果收成一行引用)、`policies.working_memory.max_recent_turns: 20` 与 `absolute_cap_tokens: 40000`(再裁成「第一轮 + 最近 20 轮」)、`policies.context_compression.absolute_cap_tokens: 60000`(裁完仍超才把中段交辅助模型摘要)。三道按「收起 → 滑窗 → 摘要」顺序,每次调模型前检查;平台默认三道都是 min(窗口 × 0.7, 20 万) = 20 万 | `agent_spec.py:911-1050, 1098-1108`(`origin/main` 读代码确认);窗口 100 万(`model_catalog.py`) |

于是单轮输入成本 ≈ (每次调用的输入量) × (12 + 2 × 1.5) / 100 万 元。括号里是「一轮里也完全不命中缓存」的上限 × 36 / 100 万。

| 会话里已有轮数 | 一次调用的输入量 | 单轮输入成本(元) |
|---|---|---|
| 0(第一轮) | 1.2 万 | 0.18(0.43) |
| 10 | 2.7 万 | 0.41(0.97) |
| 约 19(到 4 万) | 约 4 万 | 约 0.60(1.44) |
| 20 轮以后 | 第一轮 + 最近 20 轮,约 4.4 万(旧工具结果先被收起,实际更少) | 约 0.65(1.57) |

读法:

- 按原假设,会话超过约 20 轮后每轮输入成本稳定在约 0.65 元,**门槛封顶约 ¥0.9 / 轮**(一轮里全不命中缓存约 2.2 元),不再随会话变长而涨。主模型用 06 定的 qwen4-max(10 / 0.5),同样输入量约便宜 1/4。
- **这些数都待实测**:上线前用测试环境实测 S、g、k 替换(§8「先数」第 2 条);上线后看真实费用,贵了再考虑加回「空闲换会话」(后续可选)。
- 代价:① 到门槛后模型只看得到第一轮 + 最近 20 轮,中间的靠长期记忆;摘要触发时多一次辅助模型调用。② 平台默认一直保留会话第一轮(`working_memory.keep_first_turn`),会话不换,这一轮会是几周、几个月前的内容(§9 第 14 条)。③ 会话越长,平台读历史的接口越慢(query.md §5.3「会话越长,单次请求的开销越大」)。
- 输出(含思考)另算,不随会话长度变。

### 3.5 幂等:Idempotency-Key 怎么组、重试怎么做

平台规矩(读代码确认):

- 键在租户内唯一、永久有效,长度 1-255(`_idempotency.py:37`;`store.py:1517-1527` 查询不带时间范围)。
- 平台记的是「整个请求体 + 智能体编码」的指纹(`_idempotency.py:42-57`)。同一个键、请求体一个字不差 → 返回原来那一轮(stream 模式下重新接上原来的事件流);请求体有任何不同 → 422 `IDEMPOTENCY_KEY_REUSED`(`agents.py:1774-1781`)。
- 409 `THREAD_QUEUE_FULL` 在建 run 之前返回(`runs.py:1438-1456`),同一个键稍后重发是安全的。

组法:

```
Idempotency-Key = "dh1:" + sha256_hex( 项目 | 智能体 | session_id | 排好序的本批企微消息身份 | 代次 )
```

- **企微消息身份**:pad 用 `msg_app_info`,dk 用会话存档 msgid(与 03 的消息身份同一口径)。
- **session_id 进键**:同一批消息换了会话,必须是新的一轮。
- **代次**:默认 0。同一批消息**有意再跑一次**时加 1——典型情形:旧轮被打断后,触发打断的那条新消息又被客户撤回,重跑的那一批和被取消的那一批一模一样;不加代次,平台会把那个已经 `interrupted` 的旧轮原样还回来,客户什么都收不到。代次记在 run 台账里。
- 总长 68 字符,不含任何密钥、客户信息。

要做到「请求体一字不差」:

- 本轮时间取本批最后一条消息的时间(§3.3.1),不取当前时间。
- 附件复用已上传的 upload_id(§3.3.3)。
- 新会话先建再跑,第一次发和重试都带同一个 session_id(§3.4.3)。
- inputs 从同一批数据确定性生成;03 的补消息字段也必须按同一份「已在会话里的消息」计算(由 03 保证)。

重试语义:

| 情况 | 动作 |
|---|---|
| 网络错误、5xx、429 | 同一个键、同一个请求体重发(项目服务客户端已内建最多 2 次退避重试,`expert-work-client.ts:284-333`) |
| 项目服务进程在等待中死了 | 数字人服务这一批记失败(拿不到兜底原文,见 §3.9 末条与 §9 第 16 条);本批客户消息如果没进会话,下一轮按 03 补进去;已经生成但没发的回答按 03 报未送达 |
| 409 `THREAD_QUEUE_FULL` | 不算失败,见 §3.7 |
| 404 `SESSION_NOT_FOUND` | 换新会话、新键,重发一次 |
| 422 `IDEMPOTENCY_KEY_REUSED` | 客户端内部重试发的是同一份请求体,不会出现。出现说明请求体没做到确定性(例如跨进程重发时补消息里多了新内容):告警;代次加 1 重发一次,前一次若已生成回答按 03 报未送达 |

### 3.6 取消与打断

映射关系:

| 数字人服务现在的动作 | 迁移后项目服务做什么 |
|---|---|
| 调取消入口(带 invoke_token) | 用 invoke_token 查轮次状态里的 run_id,调 `POST /v1/agents/{code}/runs/{run_id}:cancel`(body 只有 user_id);同时让还在等这一轮的那个请求立刻返回 `{outcome: "cancelled"}`,不再等 `end` |
| 取消先于发起到达(预取消墓碑) | 照旧:发起前看到墓碑就不发;拿到 run_id 后再看一次,有墓碑立即取消 |
| 返回 cancelled 后,数字人服务记 `INVOKE_CANCELLED`、合并重跑 | 不变 |

规则:

- **被取消的轮次,结果一律丢弃不发。** 平台的取消是尽力而为:取消在两个步骤之间生效,正在生成最后一段时它会照常以 `success` 收尾,即使取消接口返回了 `stopped: true`(run-control.md §4.1)。所以判断依据是「我方是否发过取消」,不是 `end.status`。
- 数字人服务收到项目服务的回答后、入发送队列前,再看一次轮次状态;已经是「取消中」就丢弃(窗口很小,与现在一致)。
- 我方取消、但平台那一轮已经生成了最终回答的:这条回答留在会话里,客户没收到。项目服务在台账里把它记成「未送达」,按 03 报给平台(03 之前无法报,属已知缺口,§3.11)。
- 取消之前已经做完的工具调用(写了档案、设了提醒)不会回滚,留在会话里,下一轮模型看得到(共享背景)。这正好防止模型在重跑时再写一遍;服务端防重复见 04。
- 取消后项目服务不等 `end`,收尾(记 end 状态、用量)交给后台补齐(§3.8)。

打断后重跑时 input 放什么:

- 被取消的那一轮如果**已经开始执行**,它那批客户消息已经写进会话了;如果被取消时**还在排队、没开始执行**,那批话不在会话里。业务方事先不知道是哪一种。
- **03 落地后**(03 S-8):重跑的 input 只放取消之后新到的消息;被取消那一批作为补消息(`backfill`)带上,平台按企微消息身份判断它是否已在会话里,已在就跳过。两种情况那批话都只出现一次,业务方不用判断。
- **03 落地前**(已拍板 03 放最后做,这是 v1 的做法;按推荐定 11-17,§9 第 10 条):照现在的方式把合并后的整批放进 input,接受被取消的轮已开跑时会话里那批话出现两次,提示词里说明「客户的话可能因上一轮被打断而重复出现」(02 / 06)。
- **两种情况下** inputs 变量 `input_message_ids` 都放合并后的整批(含被取消那批):被取消那一轮可能已经写过数据,重跑时深护 MCP 靠来源消息重叠认出重复(04 §3.4、§6.16)。

为什么不用平台的「编辑重发」(`:edit`)替换被打断的那一轮:它会把那一轮整轮从模型视野里拿掉,包括已经做过的写操作,模型看不到就可能再做一遍;而且它要求会话里没有在跑的轮次(否则 409 `THREAD_BUSY`),要等被取消的那一轮真正停下(chat.md §2.10)。

### 3.7 排队上限、同客户锁、并发与时限

**排队上限与锁的关系**

- 平台:同一段会话里各轮依次执行,最多排 3 轮,第 4 轮 409 `THREAD_QUEUE_FULL`(chat.md §2.5)。
- 数字人服务:同一客户(跨所有群)同一时刻只有一轮在调用(锁 TTL 600 秒,`msg-cache.util.ts:22`)。
- 所以正常情况下一段会话里最多 1 轮在跑。会排起队的只有一种情形:旧轮刚被取消、还没停下,重跑的那一轮已经发起——它会收到 `queued` 事件、排在后面,前面停了自动开始,不需要业务方处理。连续多次打断时,排队中的轮次被取消会直接出队,实际很难到 3 轮。
- 真收到 409 时:不算失败、不发兜底;项目服务返回 `{outcome: "busy"}`,数字人服务按现有「抢不到锁」的路子 5 秒后重排(复用 `locked_retry` 和 600 秒总时限),Idempotency-Key 不变。
- 锁保持「跨所有群」不收窄:同一客户在私聊和群里同时跑两轮,两轮可能同时改同一份档案、同时写长期记忆,没必要冒这个险。

**并发吞吐**

- 数字人服务每个进程最多 50 个调用任务同时等待(`invoke-agent.processor.ts:299`),每个任务一直占着,直到项目服务返回。
- 每进程吞吐 ≈ 50 ÷ 平均每轮耗时。若平均 30 秒,约 100 轮 / 分钟 / 进程(粗估)。是否够用要拿现网高峰并发核对(§8「先数」)。不够就加进程,不必改并发数。
- 取消后项目服务立即返回(§3.6),被打断的轮次不会白占位置。

**时限要按智能体调小**

- 平台默认每轮最长 5400 秒(`settings.py:877`),到 80% 时让模型收尾、到 100% 时不调工具直接出回答(`agent_spec.py:1126-1140`,`end.status=incomplete`、`exit_reason=deadline`)。
- 数字人服务这边:调项目服务默认 300 秒超时(`project.request.ts:33`,只读核实)、锁和轮次状态都是 600 秒。平台还在跑、业务方已经超时,会出现「回答留在会话里但没人发」;业务方超时后锁也随之释放,下一批进来时平台那一轮可能还在跑。
- **已拍板(11-17):`policies.run_deadline_s: 300`**。平台按这一轮实际运行的秒数记(排队、等审批不算,`tools/run_clock.py:1-20`),240 秒(80%)提醒收尾,300 秒起不再给工具、让模型按已有信息写最终回答。

**到点以后还要多久(B-302 收尾,读代码确认)**

- 平台只在每一步调模型**之前**看时限(`graph_builder/builder.py:757-772`),不打断正在进行的那一步(深护 MCP 工具不看时限);到点后做**一次不带工具**的模型调用写最终回答(`builder.py:740-746, 1545-1550`);这次回答不合格式还会带格式要求重写,最多再 3 次(02 §3.3)。
- 所以平台**没有硬上限**,多出来的时间 = 到点时还在进行的那一步 + 收尾那一次调用(+ 少见的格式重写)。各自的上限:深护 MCP 单次调用平台默认最长 30 秒(`tools/mcp.py:117`);模型调用首字最长 180 秒(`stream_deadline_s` 平台下限 180,低于 180 的配置按 180,`agent_factory.py:227-236`),出字后两字之间最长 45 秒(`idle_timeout_s` 默认,`agent_spec.py:1674`),总时长不封顶。
- 正常情况下是「一个在途的工具调用(≤ 30 秒)+ 一次很短的收尾回答(几秒到十几秒)」,约 10~45 秒(推断;§7 第 16 条实测分布)。

**三层超时(建议值)**

| 层 | 值 | 说明 |
|---|---|---|
| 平台每轮时限 | 300 秒 | 已拍板 |
| 项目服务等平台 | 从发起 runs 算起 360 秒 | 300 + 60 秒收尾余量(覆盖上面的正常情况;含排队等前一轮停下的几秒)。到点主动 `:cancel`、按失败发兜底(§3.9);迟到的回答留在会话里,03 之前属已知缺口 |
| 数字人服务调项目服务新入口的 HTTP 超时 | 390 秒 | 现在默认 300 秒(`project.request.ts:33`),比前两层都短,必须改;调新入口时显式传 390000 毫秒。多出的 30 秒给项目服务建会话、下载上传附件、解析 |
| 同客户锁、轮次状态、取消标记 | 600 秒(不变) | 一次调用最长约 390 秒,加上调用前的语音转写仍在 600 秒内;等锁总时限 600 秒(`msg-cache.util.ts:22, 34`)也盖得住前一轮的 390 秒 |

- 余量不够的后果:收尾特别慢(收尾那次首字很慢、或格式重写)超过 360 秒时,项目服务先放弃,客户收到兜底,平台随后才生成的回答留在会话里。§7 第 16 条实测的收尾耗时 P99 超过 60 秒,再放宽项目服务和数字人服务两层(两层同步加,锁 600 秒前都够)。
- 06 里 `stream_deadline_s: 60` 不生效(平台下限 180,06 §3.10)。

### 3.8 结果怎么取、康豆怎么扣

**取最终回复**(按推荐定 11-17,§9 第 11 条;02 §3.4 已同步)

- 用 `stream_format: items`:收尾时平台会对最后一段正文补发一个 `item.done`,`channel` 改成 `final`(sse-events.md §3.7)。取本轮(`run_id` 相同)最后一个 `type=assistant_message`、`channel=final` 的条目。
- `end` 是判断结果的唯一依据;流断了用 `GET .../runs/{run_id}/events?since_seq=` 续上(项目服务的 `consumeRunStream` 已实现,`expert-work-sse.ts:195`)。平台对外请求在断线时不取消这一轮(`agents.py:1940`)。
- 续不上,或续上了但直到 `end` 都没收到 final(续上的那条连接不一定补发 final,§9 第 11 条),退回 `GET .../sessions/{id}/items`,**按 run_id 过滤**,不能只取 `limit=1`:正在跑的轮次不出现在里面,排在后面的轮次可能已经先结束了(query.md §5.8)。查不到隔 1 秒再查,最多 2 次,仍没有按「取不到」发兜底(02 §3.4)。
- 拿到的正文按 02 定的格式解析;解析不了发兜底;合法但 `messages`、`videos` 都为空 = 模型判断这轮不回,返回 `silent`(02 §3.4)。

**康豆**

现在 Dify 链路:按场景取固定价(文字 / 图片 / 图文),流正常结束才扣,被取消不扣,扣在发送之前(`agent.service.ts:820-847`)。项目服务里其它 Expert Work 智能体的口径不同:按用量折算,被取消的也扣(`expert-work-billing.service.ts:58-80`)。

已拍板(11-17,§9 第 5 条):沿用场景固定价,只扣拿到可用回答的轮次;取消、失败、兜底不扣。

| 本轮结果 | 扣不扣 |
|---|---|
| `success` / `incomplete`,取到可用回答 | 扣,沿用现在的场景固定价;扣在取到回答时,发送失败或被真人接管不退(与现在一致) |
| 模型判断这轮不回(`silent`,什么都不发) | 待定,推荐不扣(§9 第 15 条) |
| 取到回答但不可用,改发兜底话术 | 不扣 |
| 我方取消(`interrupted`,或取消后抢先跑完的 `success`) | 不扣 |
| `error`、超时、发起失败、409 | 不扣 |
| `paused` | 不该出现(健管师不配审批);出现按 `error` 处理并告警 |

- 扣费幂等:台账每个 run 一行,按 run_id 只扣一次(沿用现有「`charged_k_dou` > 0 即已扣」的做法)。
- 每轮的平台用量(`end.usage_by_model`,或 `GET .../runs/{id}/usage`)按价目折成成本记进台账,供核对「康豆收入 vs 模型成本」,不参与扣费。取消后不等 `end` 的轮次由后台巡检补记(照 `run-settlement.sweeper.ts` 的做法)。
- 扣谁的豆照旧:群聊按群上的合伙人,私聊按客户归属(`agent.service.ts:578-582`)。

### 3.9 失败与超时时客户收到什么

| 情况 | 平台表现 | 项目服务返回 `outcome`(§5.1) | 客户看到 |
|---|---|---|---|
| 正常 | `success`,有可用回答 | `reply` | 回复 |
| 工具失败但模型如实说了 | `success`,`completed=false` | `reply` | 回复(模型说明没办成) |
| 到时限收尾 | `incomplete`,有回答 | `reply` | 收尾回复 |
| 模型判断这轮不回(群里不是对它说的) | `success`,`messages`、`videos` 都为空 | `silent`,不发也不兜底 | 无 |
| 有结束但取不到或解析不了 | `success` / `incomplete`,没拿到 final、不是 JSON、结构不对 | `fallback` | 兜底话术 |
| 执行失败 | `error` | `fallback` | 兜底话术 |
| 等人审批(不该出现,健管师不配审批) | `paused` | 先取消,`fallback`,告警 | 兜底话术 |
| 我方取消 | `interrupted` 或抢先 `success` | `cancelled`,丢弃 | 新一轮的回复 |
| 非我方中断(智能体被下线、租户停用) | `interrupted` | `offline`,不发不兜底,告警 | 无 |
| 发起被拒:智能体下线 | 403 `AGENT_DISABLED` | `offline`,不发不兜底,告警 | 无 |
| 发起被拒:请求不合法 | 422 | `fallback`,告警 | 兜底话术 |
| 网络 / 5xx,重试用尽 | — | `fallback` | 兜底话术 |
| 排队满 | 409 | `busy`,数字人服务稍后重排 | 稍晚的回复 |
| 项目服务等满 360 秒 | 平台可能还在跑 | 先 `:cancel`,再 `fallback` | 兜底话术 |
| 康豆余额不足 | 调用前 | 照旧:不调用、不发 | 无 |

已拍板(11-17,§9 第 8 条):

- **兜底原文由项目服务拼**(文案按项目可配,缺省 Dify 原文,02 §3.7 / §5.6),放进 `answer_text`、来源标 `fallback`,返回 `outcome: "fallback"`;数字人服务按普通回复入发送队列,发送前的真人接管检查照样生效。
- **限频**:同一聊天窗口 10 分钟最多发一次兜底,私聊和各群分开计 —— 私聊按「员工企微号 × 客户企微号」,群按群(群里所有人都看得到)。项目服务拼兜底前 `SET NX EX 600`(键见 §5.4);设置不成功(10 分钟内这个窗口发过)就返回 `answer_text: []`、只记日志。平台整体故障时,不会每个客户每说一句就收一条「开小差」。
- **数字人服务调项目服务本身失败**(连不上、390 秒超时、项目服务进程挂了):拿不到兜底原文,不发、记日志并告警(与现在一致;是否改由数字人服务存一份缺省文案自己发,§9 第 16 条)。
- 兜底话术由员工企微号发出,按已拍板的人机混合规则算健管师一方的消息,03 落地后下一轮会被补进会话。
- 失败时本批客户的话没进会话的,03 落地后下一轮会按 03 补进来,不会丢;03 之前这批话不进会话(已知缺口,§3.11)。

## 6. 异常与边界

- **群里没有客户行的发言人**:现在照常回复、`customer_code` 为空(`invoke-agent.processor.ts:378-387`)。user_id 和工具身份怎么办见 §9 第 2 条。
- **客户编码变了**(客户被合并或重建):user_id 跟着变,之前的长期记忆接不上。现阶段接受,记一笔。
- **跨零点**:平台日期段已建议关闭;本轮时间以 input 首行为准。
- **图片超过 8 张**:只带最后 8 张,input 里说明「客户还发了 N 张更早的图片,这次没带上」。
- **附件下载失败 / 类型不收**:不上传,input 对应行写明打不开;不让整轮失败。
- **附件过期**:平台附件最后一次使用后保留 90 天(chat.md §2.6),缓存的 upload_id 只存 1 天,不会用到过期的。
- **取消与发送同时发生**:入队前再查一次轮次状态,剩余窗口与现在相同;真发出去了,这一轮就按已送达算,下一轮正常补消息。
- **平台在我方超时后才跑完**:那一轮的回答留在会话里没发,按 03 报未送达。
- **智能体配置改了、inputs 对不上**:422,只有 `detail` 字段;告警,发兜底。改配置前先改业务方传参。
- **平台限流 429**:客户端按 `Retry-After` 退避,最多 2 次(现有);仍不行按失败处理。
- **数字人服务并发不够**:任务在 Bull 队列里排队,表现为回复变慢,不会丢;靠加进程解决。
- **dk 通道**:发送走 `enqueueAnswer`,真人接管与显示名在 PC 端领任务时才判断(`agent-callback-dk.service.ts:55-56`),与 pad 一样无需改。

## 7. 测试与验收

每条:怎么触发 → 看哪里 → 什么算过 → 没修好时会怎样。

1. **单条私聊**:测试企微号给健管师号发一句话 → 平台 run 列表、数字人服务发送日志、台账 → 一个 run、`end=success`,客户只收到一条回复,内容与 `channel=final` 一致 → 没修好:收不到或收到两条。
2. **防抖合并**:8 秒内连发 3 条(文字、语音、图片)→ 平台对话条目 → 只有一个 run,input 里三行按时间排好、语音行带标记,图片在附件里 → 没修好:3 个 run,或图片丢失。
3. **打断**:发一句会触发查工具的话,run 进行中(看到工具调用)再发一句 → run 列表、台账 → 旧 run 被取消、客户只收到新一轮的一条回复,新一轮看得到新消息 → 没修好:收到两条回复,或旧回答被发出。
4. **取消抢跑**:构造回答已生成后才到的取消(在 `item.done final` 之后、`end` 之前取消)→ 台账 → 旧回答没发,`delivery=discarded`,(03 落地后)按 03 报了未送达 → 没修好:旧回答被发出,或下一轮模型以为客户收到了。
5. **打断后重跑不重复**(03 落地后):同第 3 条 → 新一轮的对话条目 → 旧那批客户的话在会话里只出现一次 → 没修好:同一批话出现两次。
6. **幂等重试**:让项目服务第一次发起后断网重试(或直接用同一个键、同一个请求体调两次)→ 平台 run 列表 → 只多 1 个 run,两次拿到同一个 run_id,康豆只扣一次 → 没修好:两个 run、扣两次。
7. **请求体确定性**:带图片的一批,第一次发起后模拟进程重启再重试 → 平台响应 → 不出现 422 `IDEMPOTENCY_KEY_REUSED` → 没修好:重试必挂。
8. **代次**:一批被打断后,把触发打断的消息撤回,重跑同一批 → 平台 run 列表 → 产生了新 run、客户收到回复 → 没修好:平台还回那个被取消的旧 run,客户没回复。
9. **会话不切分、门槛生效**:把映射表 `last_run_at` 改到几天前再发消息 → 映射表、平台会话列表 → 仍是同一段会话;同一测试客户连续跑 25 轮 → 每轮 `usage_by_model` → 单次调用输入量涨到约 4 万后不再随轮数涨,任何一次不超过约 6 万 → 没修好:换了新会话,或输入量一直涨。
10. **私聊与群共用会话**:客户在私聊里说一句,再到群里说一句 → 平台会话列表、对话条目 → 同一段会话、同一个 user_id,两轮 input 首行分别标「私聊」「群聊」;会话裁到最近 20 轮以后,早先在私聊里说过的合成事实(例如「我对青霉素过敏」)仍能由长期记忆召回 → 没修好:私聊和群分成两段会话,或标记缺失。
11. **user_id 不撞**:同一个客户分别经员工侧 ai-health-plan 和本链路各跑一轮 → 平台终端用户表 → 两个不同的终端用户,记忆互不出现 → 没修好:员工的提问被记成客户的事实。
12. **附件边界**:一批发 10 张图 + 一个 .heic + 一个视频 → 平台请求、对话条目 → 只带最后 8 张,不 422;另两个在 input 里写明打不开 → 没修好:整轮 422,客户收不到回复。
13. **排队满**:人为让同一会话排满(连发 4 个不同键的请求)→ 业务方日志 → 第 4 个拿到 409 后 5 秒重排成功,没发兜底 → 没修好:客户收到兜底。
14. **本轮时间**:客户说「10 分钟后提醒我喝水」→ 提醒工具收到的时间、对话条目 → 提醒时间 = 客户消息时间 + 10 分钟;另查这一轮写回的长期记忆里没有「客户说当前时间是……」这类条目 → 没修好:提醒时间错,或记忆里混进时间行。
15. **缓存命中**:同一会话连发两句、间隔 1 分钟 → 两轮 `usage_by_model` → 每轮第 2 次起的调用 `cache_read_tokens` > 0;跨轮的第一次调用有命中更好(不强求) → 没修好:成本按全价走。
16. **时限与收尾余量**:临时把 `run_deadline_s` 调到 30 秒、项目服务等待上限同步调成 90 秒(30 + 60),问一个要查多个工具的问题,重复 20 次 → `end`、台账 → `incomplete` + `deadline`,有收尾回答且被发出,项目服务没超时;记下每次「`end` 时刻 − 起跑 − 时限」,P99 不超过 60 秒(超过就按 §3.7 同步放宽两层)→ 没修好:业务方先超时,回答留在会话里没人发。
17. **失败兜底与限频**:把智能体指到一个不存在的工具服务或临时禁用 → 客户在私聊连发 3 句,同时在一个测试群里发 1 句 → 私聊只收到 1 条兜底、10 分钟内不再收到;群里也收到 1 条(各窗口分开计);兜底文字等于项目配置的文案 → 没修好:每句都收到「开小差」,或私聊发过后群里收不到。
18. **康豆口径**:分别造出 success、我方取消、error 三种结果 → 钱包流水 → 只有 success 扣了一笔,金额等于场景固定价 → 没修好:取消也扣、或 error 也扣。
19. **真人接管**:真人在企微里刚回过客户,客户再发消息 → 调用日志 → 照旧在闸门处跳过,不发起 run;run 进行中真人回复 → 回答没发,台账 `delivery=blocked_by_human` → 没修好:真人回完 AI 又插一句。
20. **密钥不出现**:跑完以上用例后,扫 Redis 键名、数字人服务和项目服务的日志、调用日志表 → 找不到 Dify 应用密钥和 Expert Work API key 的任何片段;日志里没有 input 正文 → 没修好:密钥或客户健康数据进了日志。
21. **灰度与回退**:把某条员工绑定的 `is_expert_work` 置 0(或把 `t_project_expert_work_config` 对应行 `enabled` 置 0)→ 下一条消息 → 立刻走回 Dify 原路径,Dify 会话照常续上 → 没修好:切换要发版,或 `enabled=0` 不生效。
