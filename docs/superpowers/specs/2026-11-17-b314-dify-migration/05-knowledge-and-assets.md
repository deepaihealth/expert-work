## 0. 一句话结论

Dify 里的「知识」其实只有三段写死在环境变量里的文字,每轮整段塞给模型(约 4,100–5,400 token):公司介绍(还夹着 10 位专家简介和 16 个推荐动作)、41 条运动视频链接表、一行小程序入口。迁移后:

- 公司介绍**内容全部保留**(业务方已授权,11-17),只改错别字和格式,拆成 6 篇 Word 文章放进「公司与服务」知识库,模型问到才查;回复照样按提示词的广告法、医疗用语规则说。
- 运动视频改走深护新建的**智能体素材表** `t_project_agent_material`:41 条按现有链接录进去;模型在客户明确要视频时调深护 MCP `material_list` 拿全量清单,输出素材 id,业务方查表校验后按类型发(02、04)。没有后台页,助手交建表与初始化 SQL,用户在各环境执行。
- 小程序入口、`goods_info` 不迁(小程序不需要了,11-17)。

测试→生产:平台**没有知识库或智能体的导出导入**,而且这两类接口只对登录的员工开放,对外 API key 调用直接 403 —— 所以生产只能在控制台手工重建。交付物是**文件,不进 git**:知识库 Word 文章、配置书(Word:完整系统提示词 + 控制台步骤,YAML 放附录),放在用户机器上的本地交付文件夹;数据库变更的 SQL(含素材表)放深护建库仓库 `deep-ai-health-db-design/1.5.7/project_tables/leyi/`(`2026-11-18-b314-*`)(11-18)。助手按这些文件建测试环境;用户在生产上传同样的文件、粘贴同样的 YAML、执行同样的 SQL,助手不碰生产。B-314 设计文档仍在 git。打包导出导入暂不做(11-17)。

### 1.2 怎么用的

- 没有知识检索节点。健管师节点(1761372447236)每轮把 `company_info` + `sport_video` 作为一条 **assistant 消息**塞给模型;备用节点(17636269089180)再加 `goods_info`。
- 健管师提示词里与本篇有关的规则(主、备两个节点逐字相同):
  - 2.3 广告法:禁极限词「最好、最佳、最有效、完全、彻底、根治、立竿见影、神奇、奇效、100%、绝对、终极」;禁具体时间承诺(「7 天见效」「一周改善」「立即见效」「30 天内」「马上见效」「当天改善」);改用「有助于、可能改善、逐步改善、坚持一段时间」。
  - 2.4 医疗词:禁「问诊、复诊、就诊、诊疗、坐诊、挂号、患者、病人」,分别换成「咨询、再次咨询、客户 / 用户、提供咨询服务、预约咨询」。
  - 2.5 宣传合规:不夸大效果、不用「治愈 / 根治」、不虚假承诺(如「3 天降糖 5 个点」)、客观描述、不承诺治疗效果。
  - 3.x 运动视频:只在客户**明确要视频**时发;一次最多 3 个;输出 `{answer, attachments}`,`attachments` 只放 mp4 完整链接;「仅使用运动视频中提供的链接,不得自行编造和篡改链接」。
- 回复节点把 `attachments` 原样作为 `file_link_list` 发给数字人服务的 `/receive-answer`(节点 17613774900740);数字人按扩展名把 .mp4 发成视频气泡。

### 1.3 现在的问题

1. **知识和规则互相打架**:`company_info` 写着「帮助客户实现糖尿病完全逆转或部分逆转」「效果显著」,同一轮的提示词又禁「完全」和效果承诺。两样每轮同时喂给模型。
2. **推荐动作和视频对不上**:16 个推荐动作只有 3 个在视频表里同名,另 1 个名字略有出入(多了「徒手」二字),其余 12 个没有视频。
3. **模型手抄链接**:每条链接是约 60 token 的 URL 编码串,抄错一位就是坏链接。提示词专门写了「不得编造和篡改链接」,说明出过这类问题(推断)。
4. **固定开销大**:每轮 4–5 千 token 的知识,绝大多数轮次(报血糖、报饮食)用不上。
5. **错别字与格式**:「致力千」(应为「致力于」)2 处;一本专家共识的书名缺字;一位专家的标题层级和其他人不一致;一个推荐动作名疑似笔误。

## 2. 目标与不做什么

**目标**

1. 公司 / 服务类问题由「公司与服务」知识库回答;库里保留业务方授权的原文,回复按提示词的广告法、医疗词规则说。
2. 运动视频走深护智能体素材表:模型只出素材 id,链接由业务方查库取;id 不对不会发出坏链接。
3. 测试环境建好的智能体、知识库、素材,能按同一套交付文件在生产原样重建,生产与测试内容可核对一致。
4. 以后改内容(改一句服务介绍、加一个视频)有固定流程,不会出现「测试改了生产没改」或「控制台改了交付文件没改」。

**不做**

- 不让模型输出任何链接(视频、小程序、网页)。
- 不把客户个人资料、健康方案放进知识库(这些从深护 MCP 现取,见总览)。
- 不用 FAQ 类型的库:平台目前只有「文档」一种库,FAQ、素材类型只是保留值(`knowledge.py:242-248`)。
- 第二期科普库本期不做(11-17 定,§3.5)。
- 本期不做平台打包导出导入(11-17 定,§3.6.7)。
- 不写「费用与报名」篇:Dify 也没有,报名 / 费用只出现在课程意图规则里(11-17 定,§3.4)。
- 助手不碰生产:生产操作由用户执行,助手只准备文件、清单和核对方法。

## 3. 设计

### 3.1 先走三个真实场景

**场景 A:客户问公司和效果。** 客户在企微发「你们公司在哪?真能把糖尿病逆转吗?」。平台每轮开始先拿这句话对「公司与服务」库做一次轻量探测,命中就在本轮消息末尾加一行「这个库里有相关内容,先查」。模型调 `knowledge_search`,拿到「01-公司简介与联系方式」和「03-控糖服务与逆糖服务介绍」两段(业务方授权的原文),回复地址和服务做法;效果按提示词节 G 说成「坚持饮食、运动和监测管理,有助于改善血糖」,不照搬原文里提示词禁止的绝对化说法(如「完全」)。

**场景 B:客户要动作视频。** 客户发「我膝盖不太好,有没有练腿的视频?」。模型调 `material_list`,拿到本智能体可用的全部 41 条(短 id、名称、类型、标签、说明前一段),挑了两条标着「低强度」「坐姿」、说明里写着「适合膝盖不适者」的,输出 `media: [1207, 1233]`,`messages` 里先用文字讲要点、不写链接。业务方逐个查素材表:存在、同项目、属于本智能体(或全项目通用)、启用、没删除 → 取链接,按视频发;不合格的丢掉并记日志,文字照发。

**场景 C:运营改了一句服务介绍。** 深护说「控糖服务里的直播从每月一次改成每两周一次」。助手改交付文件夹里的 `03-控糖服务与逆糖服务介绍.docx`,在配置书变更记录里记一行 → 在测试控制台重传同名文件 → 控制台显示预估费用,确认 → 等「就绪」→ 检索测试和冒烟过 → 用户在生产控制台重传同一个文件、确认 → 对照测试与生产两边的文件大小、段数一致。全程没人在控制台里直接改段落。

### 3.2 「公司与服务」知识库

#### 3.2.1 为什么进库而不是继续塞提示词

公司介绍清理后约 2,000–2,500 字。继续塞提示词,每轮固定多 1,800–3,000 token,而且改一句就要重新发布智能体、两个环境各发一次;进库后只有问到时才花 token,改内容只需重传文件,智能体不用动。用户已拍板「公司与服务」一库,这里只说明理由。

#### 3.2.2 文档怎么切

| 文件名(= 检索时的文档标题) | 放什么 | 来自原文哪节 | 备注 |
|---|---|---|---|
| `01-公司简介与联系方式.docx` | 公司做什么、服务哪些人群和人数、体验中心的位置与设施;公司全称、地址、联系电话 | 简介、规模、名称地址电话 | 内容照原文(已授权) |
| `02-服务边界与用药说明.docx` | 不具备开处方资质;用药调整要在有处方权的医生指导下进行 | 「重要说明」 | 这条同时是提示词里的行为规则;库里放一份,是为了客户问「能不能开药」时有原文可依 |
| `03-控糖服务与逆糖服务介绍.docx` | 两种服务的总述和医生团队;控糖服务的内容、周期(3–6 个月)和直播;逆糖服务的团队、周期、日常管理、7×24 小时响应 | 服务一节 | 两种服务合成一篇;用原服务名(带「逆糖」,法务已确认可用);不写「看小程序」那句 |
| `04-管理方法与管理模式.docx` | 控糖方法的来源和三个阶段、院内诊疗 + 院外管理的模式、海外逆转案例数 | 管理方法、管理模式 | 用原方法名 |
| `05-专家团队.docx` | 10 位专家:姓名、头衔、任职医院与科室、学会任职、荣誉、擅长领域 | 公司专家 | 已授权保留(§3.2.5) |
| `06-运动推荐动作.docx` | 16 个推荐运动动作,按器械分 5 组 | 运动推荐 | 客户要运动建议时的文字依据;其中有视频的 4 个也在素材表里(§3.3.6) |

另有一份 `知识库说明.docx`(放在 `知识库/` 下,**不上传**):给维护的人看,写清每篇放了什么、每段出自原文哪里、库设置和改名规矩。

切成多篇的理由(读代码确认):

- 平台把**文件名**(去掉扩展名,下划线换空格)作为文档标题,和**小节标题路径**一起拼在每段前面参与向量、关键词和重排(`protocol/knowledge.py:291-318`)。文件名和小节标题写成客户的问法,直接提高命中。
- 切块时**标题一换就断段**,一个小节不会和下一个小节混在一段里;默认每段上限 512 token、重叠 64(`chunking.py:1-35`;迁移 `0022`)。命中一段时返回它所在的「父段」(上限 1,024 token,`chunking.py:178`)。

#### 3.2.3 标题和正文怎么写

1. 每篇用 Word 的「标题 1」写一个总标题,下面用「标题 2」分小节;小节标题写成客户会问的话:「控糖服务包含哪些内容」「服务周期多长」「公司地址和客服电话」「能不能帮我开药」。平台读 Word 时认标题样式,也认大纲级别,按标题断段(`control_plane/knowledge/office_docx.py:22-29`),所以层级一定要用样式或大纲级别标出来,不能只靠加粗。
2. 每个小节控制在 300 字以内,一节只讲一件事,保证一节就是一段。
3. 正文写完整的口语短句,不用表格、不用加粗。健管师回复禁止 Markdown、限 20–120 字,原文越接近口语,模型越不容易照搬格式。
4. 客户的几种说法在正文里自然出现一次(控糖 / 血糖管理 / 糖尿病管理),帮关键词检索。
5. 除电话外不放任何长串(链接、小程序短码、编号)。

#### 3.2.8 入库费用预估与确认(读代码确认)

流程(`api/knowledge_estimates.py:1-21`;`api/knowledge.py:881-951`):

1. 上传文件 → 平台在本地解析计数**先估价,不花钱、不调模型**,文件进入「待确认」。
2. 控制台显示每个文件的预估金额;**不论金额多少都要人点确认**才开始入库(包括 ¥0.00)。确认时带上「当时看到的条数和总额」,中间有变化就拒绝、让人重看。
3. 7 天没人确认,自动撤回。
4. 同一个库里重传**字节完全相同**的文件 → 「无变化」,什么都不做;同库另一个文件已有相同内容 → 标「重复」,不解析不收费。
5. 重传同名文件 → 新版本进待确认,**旧版本继续服务**,新版本就绪后才替换(`persistence/knowledge/base.py:1091-1124`)。文档按「库 + 文件名」唯一(`models/knowledge.py:233`)。

费用组成:向量化;库画像(一次辅助模型调用)和探测校准(一组固定查询的向量化),这两项只在每轮探测的平台总开关开着时才有(`protocol/knowledge_estimate.py:59-71`)。本库 6 篇纯文字,粗估一次入库不到 ¥0.1,**以控制台显示为准**;测试、生产各付一次。

限制:单文件默认 50 MiB(`settings.py:536`,部署级可调);格式 pdf、docx、pptx、xlsx、md / markdown、txt、html / htm、csv(`parsing.py:34-36`)。本库全部用 Word(`.docx`),平台支持(`parsing.py:34-36`)。

### 3.3 运动视频:走深护新建的智能体素材表(11-17 定,取代原编号表)

原设计是「git 里一份 CSV → 提示词里的编号目录 + 输出枚举 + 给深护的编号→链接 JSON」三份同步。改成一张由深护维护的素材表后:唯一来源在深护,增删素材不用重新发布智能体,提示词也省掉约 400~500 token 的视频目录。

**为什么新建一张表**:和其它业务的素材(营销、方案生成助手等)解耦,互不影响;表里按智能体划范围(`agent_code`),以后别的智能体也能用。

#### 3.3.2 数据怎么建

- **41 条运动视频**:按 Dify 表里现有的 CDN 链接各插一行(`media_type = video`),**不重新上传**;`agent_code` 填健管师的智能体编码,即深护员工绑定上的那个 `agent_code`(06 §3.11,已定);`material_list` 钉的也是这个值。
- **标签和说明**:由深护运动教练给。原表没有任何强度信息,41 条里 21 条名字里也看不出要不要器械,补上 `tags`(如「低强度」「坐姿」「器械」)和 `description`(要领 / 适合人群 / 禁忌),模型才有依据;**空着也能上线**,没写的素材只按名称挑。

#### 3.3.3 模型怎么用

- 只有客户**明确**要视频 / 素材时,调 `material_list`(04 §5.12)。它返回本项目里 `agent_code` 等于本智能体或为空、且启用的**全部**素材,按 `sort` 排:短 id、名称、类型、标签、说明的前 60 字左右;**不给链接、不按关键词搜**(关键词搜会漏同义词,全量清单不会漏)。
- 模型按客户情况(年龄、关节、血压、器械条件)对照说明里的适合人群和禁忌,挑最多 3 个,把 id 放进输出的 `media`(02 §5.1);没有合适的就只给文字建议、直说暂时没有。客户没要就不调工具,`media` 为空。

#### 3.3.4 业务方怎么接

对每个 id:存在、同项目、`agent_code` 等于本智能体或为空、`status = 1`、没删除 → 取链接,按 `media_type` 发(视频 → 视频消息;图片 → 图片;`file` / `audio` → 文件);不满足的丢掉并记日志;**文字一定照发**。每轮记下选了哪些 id、丢了几个(02 §3.5.1、§5.7)。

#### 3.3.5 能保证什么、不能保证什么

| | 靠什么 |
|---|---|
| **能保证**:只发本项目、给本智能体用的素材 | `project_code` 由平台绑定,`agent_code` 由配置钉死,模型改不了;业务方发送前再按这两项核对 |
| **能保证**:发出去的素材一定存在、启用、没删除 | 业务方逐个查表 |
| **能保证**:不会因为关键词没对上而漏掉合适的素材 | 工具返回全量清单 |
| **能保证**:不会抄错链接 | 模型只写短 id,链接由业务方查 |
| **不能保证**:挑的是「最合适」的那几个 | 靠说明(要领 / 适合人群 / 禁忌)+ 标签 + 提示词规则 + 07 用例 + 工程师真实测试;说明写得越全越准,没写说明的只能按名称和标签挑;每轮日志记选中的 id 和丢弃个数,定期抽查 |

### 3.5 第二期:控糖 / 血压 / 血脂科普库 —— 本期不做(11-17 定)

- **为什么**:现在健康问题全靠模型自己的常识回答,口径未必和公司的控糖方法一致,也容易踩广告法和医疗边界。有一个经过审核的科普库,平台「绑了库就先查」的规则会让模型优先按库里的口径答。
- **内容从哪来**:深护已有的课程讲义、直播讲稿、营养师资料、健康方案模板里的通用部分;公开指南只做**深护自己写的摘要**,不整段搬原文(版权)。
- **口径**:与公司控糖方法一致;具体数值(血糖目标、用量)要么不写,要么写明「以医生和个人方案为准」;与客户个人健康方案冲突时以个人方案为准(这条写进提示词)。
- **谁审**:深护医学顾问 / 营养师逐篇签字;每篇开头写审核人、日期、版本、适用人群。
- **代价**:平台零开发;深护内容整理加审核约 1–2 周;每轮探测命中会明显变多(健康问题几乎每轮都有),检索次数和延迟上升,要在测试里量。

#### 3.6.3 测试环境改内容的规矩

1. **先改交付文件,再动控制台**。改 Word、YAML、SQL 都先改交付文件夹里那一份,再按它去测试控制台(或数据库)操作。控制台上不留交付文件里没有的改动。
2. **知识库只整文件重传**,不在控制台里直接编辑段落(平台有段落编辑功能,但那样改的内容不在交付文件里,重传还会被覆盖)。
3. **文件名就是标题,改名 = 新文档**。改名后要在控制台手工删掉旧名文档,否则新旧两份同时被检索到。
4. **智能体只从配置书附录的 YAML 整段粘贴**,保存草稿 → 调试台用草稿试跑 → 发布。不在表单里零散改字段。
5. 每次改动在配置书的变更记录写一行:改了哪个文件、为什么、业务方谁确认的、测试生效时间、生产生效时间(上线后补)。
6. **测试环境第一次就按生产清单搭**,边搭边修清单。上线前在测试里按清单「只核不改」走一遍,每一步的核对项都通过,清单才算定稿 —— 生产只是把测试上的步骤原样重放。

#### 3.6.6 以后的增量变更

- **只改知识库**:改 Word → 测试重传、确认、检索测试 → 配置书变更记录记一行 → 用户在生产重传同名文件、确认、核对大小和段数。智能体不用动。

#### 3.6.7 可选平台改造:智能体 + 知识库打包导出 / 导入 —— 暂不做(11-17 定)

  - 导出:控制台在智能体详情页「导出」,得到一个压缩包 —— 线上版本的配置 YAML;它引用的每个知识库的设置;每篇文档的原件(平台本来就保留原始字节,用于失败重跑,`api/knowledge.py:908-912`);依赖清单(MCP 注册名、平台 MCP 名、模型、平台技能)。**不含**任何密钥、MCP 地址、记忆、会话。

## 5. 接口与数据结构

### 5.1 素材表查询口径

表结构见 §3.3.1。`material_list` 和业务方校验共用一个口径:

```
FROM t_project_agent_material
WHERE project_code = <绑定的项目>
  AND (agent_code = <配置钉死的智能体编码> OR agent_code IS NULL)
  AND status = 1 AND deleted_at IS NULL
ORDER BY sort, id
```

业务方校验一个 id:上面的条件再加 `id = <id>`,有结果才发,按 `media_type` 发。

### 5.2 素材表 SQL 骨架(以 `deep-ai-health-db-design/1.5.7/project_tables/leyi/2026-11-18-b314-08 / 09` 两个文件为准;值均为占位)

```sql
SET NAMES utf8mb4 COLLATE utf8mb4_0900_ai_ci;
-- 1. 占位(必须填;没填时只建表、不写数据)
SET @project_code = '<填项目编码>';
SET @agent_code   = '<填健管师智能体编码>';   -- = 深护员工绑定上的 agent_code(06 §3.11)
SET @created_by   = NULL;                      -- 创建人 ID,不知道问深护(默认 0)
-- 2. 建表(已存在就跳过;DDL 隐式提交,放在事务外)
CREATE TABLE IF NOT EXISTS `t_project_agent_material` (
  `id` bigint unsigned NOT NULL AUTO_INCREMENT COMMENT '自增主键;模型输出的素材短 id 就是它',
  `project_code` varchar(80) NOT NULL DEFAULT '' COMMENT '项目唯一标识码',
  `material_code` varchar(64) NOT NULL COMMENT '素材唯一标识码 mat_xxxx,服务端生成(格式待深护确认)',
  `agent_code` varchar(80) DEFAULT NULL COMMENT '哪个智能体能用;NULL = 本项目所有智能体都能用',
  `name` varchar(120) NOT NULL COMMENT '素材名称',
  `media_type` enum('video','image','file','audio') NOT NULL COMMENT 'PDF 算 file',
  `url` varchar(1000) NOT NULL COMMENT '素材地址;不返回给模型',
  `description` varchar(1000) DEFAULT NULL COMMENT '要领 / 适合人群 / 禁忌 / 用法,可空',
  `tags` json DEFAULT NULL COMMENT '标签数组',
  `status` tinyint NOT NULL DEFAULT '1' COMMENT '1 启用 0 停用',
  `sort` int NOT NULL DEFAULT '0' COMMENT '排序,小的在前',
  `created_at` datetime NOT NULL, `updated_at` datetime NOT NULL,
  `created_by` bigint unsigned NOT NULL DEFAULT '0', `updated_by` bigint unsigned NOT NULL DEFAULT '0',
  `deleted_at` datetime DEFAULT NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_material_code` (`material_code`),
  KEY `idx_project_agent_status` (`project_code`, `agent_code`, `status`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
-- 3. 41 条运动视频(一个事务;按 material_code 判断,已存在的跳过,不恢复已停用 / 已软删的行)
--    material_code = 'mat_' + SHA1(项目编码 + 固定前缀 + 素材名称) 前 16 位十六进制
--    链接用 Dify 表里现有的 CDN 地址(不重新上传);标签是助手按动作名推断的建议,说明留空等运动教练补
INSERT INTO t_project_agent_material (project_code, material_code, agent_code, name, media_type, url, description, tags, status, sort, created_at, updated_at, created_by, updated_by)
SELECT @project_code, CONCAT('mat_', LEFT(SHA1(CONCAT(@project_code, '<固定前缀>', d.name)), 16)), @agent_code, d.name, 'video', d.url,
       NULL, d.tags, 1, d.sort, NOW(), NOW(), COALESCE(@created_by, 0), COALESCE(@created_by, 0)
FROM (SELECT '深蹲' AS name, 'https://<视频 CDN 主机>/no_logo_sport_video/<文件名>.mp4' AS url,
             '["中等强度","站姿","徒手","臀腿","膝盖负担较大"]' AS tags, 33 AS sort
      /* UNION ALL …… 其余 40 条 */) d;
```

执行前要确认的:表名、列长度(`name` 120、`description` 1000、`material_code` 64)、`material_code` 的格式、`created_by` 填什么。执行后核对条数;`description` 和 `tags` 空着不影响上线。回滚用 `09` 文件末尾注释掉的回滚段。

## 6. 异常与边界

| 情况 | 会怎样 | 怎么处理 |
|---|---|---|
| 生产没建库或库名拼错 | `knowledge_search` 报「这个智能体的知识库都不存在」;模型应如实说没法确认 | 冒烟 1–3 会暴露;清单第 7 步逐字核对库名 |
| 上传后忘了确认 | 文档停在「待确认」,7 天后自动撤回;新文件检索不到,重传的文件继续用旧版 | 清单第 8 步要求全部「就绪」才往下走 |
| 重传字节相同的文件 | 「无变化」,什么都不做 | 可以放心重跑清单第 8 步 |
| 改了文件名 | 新增一篇,旧的还在,两份都会被检索到 | 规矩第 3 条:改名同时删旧名 |
| 两环境向量模型不同 | 段数可能不同;库显示需要重建索引 | 清单第 8 步核对段数,不一致先查向量模型和切块参数 |
| 每轮探测超时(1.5 秒) | 这轮不加提示,静默跳过 | 不影响回答;模型仍可按提示词自己查 |
| 重排失败或限流 | 退回融合排序,结果带降级标记 | 库小,影响有限;检索日志能看到 |
| 每轮探测误触发 | 报数据的轮次也去查公司介绍,多一两秒,可能夹推广内容 | 工程师真实测试时观察;多了就设 `probe: false` |
| 模型给出不存在 / 别的项目 / 别的智能体 / 已停用的素材 id | 平台只查形状能通过 | 业务方丢掉并记日志,文字照发(§3.3.4) |
| 素材没录或 `agent_code` 配错 | `material_list` 返回空清单 | 模型如实说暂时没有视频、给文字建议;清单第 10 步核对条数 |
