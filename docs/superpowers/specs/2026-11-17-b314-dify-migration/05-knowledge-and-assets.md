# B-314-05 知识库、静态资料与测试→生产迁移

> 所属:B-314 Dify「健管师」迁移(总览:00-overview.md)。状态:草稿 v1,待逐个过。
>
> 本篇管三件事:Dify 里写死的「知识」迁到哪、运动视频怎么改成编号、测试环境建好的东西怎么原样搬到生产。
> 输出字段总表、固定话术、提示词正文不在本篇,本篇只给它们需要的片段和约束(见总览里讲输出契约和智能体配置的那几篇)。

## 0. 一句话结论

Dify 里的「知识」其实只有三段写死在环境变量里的文字,每轮整段塞给模型(约 4,100–5,400 token):公司介绍(还夹着 10 位专家简介和 16 个推荐动作)、41 条运动视频链接表、一行小程序入口。迁移后:

- 公司介绍**清理掉与广告法规则冲突的说法**,拆成 5–6 篇短文放进「公司与服务」知识库,模型问到才查;
- 运动视频改成**编号表**:提示词里只放「编号 + 动作名」,模型只输出编号,深护按编号换成 mp4 链接再发;
- 小程序入口**不进库、也不让模型写**,第一版**先不发**(已拍板 11-17,§9 第 7 条)。

测试→生产:平台**没有知识库或智能体的导出导入**,而且这两类接口只对登录的员工开放,对外 API key 调用直接 403 —— 所以生产只能在控制台手工重建。做法是把**所有源文件放 git**(配置书、智能体 YAML、知识库原文、视频编号表、上线清单),测试环境严格按 git 建,生产由用户按清单原样重放、助手不碰生产。打包导出导入作为可选平台改造列出,建议先手工走一遍再定。

## 1. 现状:Dify 现在怎么做

### 1.1 三个环境变量

| 变量 | 大小 | 内容(只写类别和条数) | 谁在用 |
|---|---|---|---|
| `company_info` | 2,602 字;约 1,800–3,000 token | 9 节:公司简介(服务人群、服务人数说法)、「不具备开处方资质」声明、公司全称 / 地址 / 客服电话各 1 条、规模(体验中心位置与设施)、控糖管理方法(带「逆糖」字样的方法名,三阶段)、管理模式、服务(总述 1 段,含医生团队与互联网医院;两种服务各 1 段;小程序入口 1 行)、**专家 10 位**(每位:姓名、头衔、现任或曾任医院与科室、学会任职、荣誉、擅长领域)、**运动推荐 16 个动作名** | 主节点、备用节点每轮 |
| `sport_video` | 5,781 字;约 2,300–2,450 token | Markdown 表,**41 行**「动作名 \| mp4 链接」;链接全在同一个 CDN 主机的同一目录下,文件名就是动作名的 URL 编码,无查询串、无签名 | 主节点、备用节点每轮 |
| `goods_info` | 44 字 | 一行「控糖服务和产品介绍:」+ 小程序短链(`#小程序://…`);与 `company_info` 服务一节最后一条**重复**;没有任何商品、价格信息 | 只有备用节点 |
| `need_multi_agent` | 整数 0 | 开关,不是知识 | 不迁 |

token 是用两种通用分词器数的(本地 tiktoken cl100k / o200k),模型实际分词器不同,只看量级。

### 1.2 怎么用的

- 没有知识检索节点。健管师节点(1761372447236)每轮把 `company_info` + `sport_video` 作为一条 **assistant 消息**塞给模型;备用节点(17636269089180)再加 `goods_info`。
- 健管师提示词里与本篇有关的规则(主、备两个节点逐字相同):
  - 2.3 广告法:禁极限词「最好、最佳、最有效、完全、彻底、根治、立竿见影、神奇、奇效、100%、绝对、终极」;禁具体时间承诺(「7 天见效」「一周改善」「立即见效」「30 天内」「马上见效」「当天改善」);改用「有助于、可能改善、逐步改善、坚持一段时间」。
  - 2.4 医疗词:禁「问诊、复诊、就诊、诊疗、坐诊、挂号、患者、病人」,分别换成「咨询、再次咨询、客户 / 用户、提供咨询服务、预约咨询」。
  - 2.5 宣传合规:不夸大效果、不用「治愈 / 根治」、不虚假承诺(如「3 天降糖 5 个点」)、客观描述、不承诺治疗效果。
  - 3.x 运动视频:只在客户**明确要视频**时发;一次最多 3 个;输出 `{answer, attachments}`,`attachments` 只放 mp4 完整链接;「仅使用运动视频中提供的链接,不得自行编造和篡改链接」。
- 回复节点把 `attachments` 原样作为 `file_link_list` 发给数字人服务的 `/receive-answer`(节点 17613774900740);数字人按扩展名把 .mp4 发成视频气泡。

### 1.3 现在的问题

1. **知识和规则互相打架**:`company_info` 写着「帮助客户实现糖尿病完全逆转或部分逆转」「效果显著」,同一轮的提示词又禁「完全」和效果承诺。两样每轮同时喂给模型。
2. **推荐动作和视频对不上**:16 个推荐动作只有 3 个在视频表里同名,另 1 个名字略有出入(多了「徒手」二字),其余 12 个没有视频。
3. **模型手抄链接**:每条链接是约 60 token 的 URL 编码串,抄错一位就是坏链接。提示词专门写了「不得编造和篡改链接」,说明出过这类问题(推断)。
4. **固定开销大**:每轮 4–5 千 token 的知识,绝大多数轮次(报血糖、报饮食)用不上。
5. **错别字与格式**:「致力千」(应为「致力于」)2 处;一本专家共识的书名缺字;一位专家的标题层级和其他人不一致;一个推荐动作名疑似笔误。

## 2. 目标与不做什么

**目标**

1. 公司 / 服务类问题由「公司与服务」知识库回答,库里的说法与健管师提示词的广告法、医疗词规则一致。
2. 运动视频只出编号,链接由深护换;编号错了不会发出坏链接。
3. 测试环境建好的智能体、知识库、编号表,能按一份清单原样在生产重建,生产与测试内容可核对一致。
4. 以后改内容(改一句服务介绍、加一个视频)有固定流程,不会出现「测试改了生产没改」或「控制台改了 git 没改」。

**不做**

- 不让模型输出任何链接(视频、小程序、网页)。
- 不把客户个人资料、健康方案放进知识库(这些从深护 MCP 现取,见总览)。
- 不用 FAQ 类型的库:平台目前只有「文档」一种库,FAQ、素材类型只是保留值(`knowledge.py:242-248`)。
- 第二期科普库本期不做,只列待拍板(§3.5)。
- 本期不做平台打包导出导入,只列可选方案(§3.6.7)。
- 助手不碰生产:生产操作由用户执行,助手只准备文件、清单和核对方法。

## 3. 设计

### 3.1 先走三个真实场景

**场景 A:客户问公司和效果。** 客户在企微发「你们公司在哪?真能把糖尿病逆转吗?」。平台每轮开始先拿这句话对「公司与服务」库做一次轻量探测,命中就在本轮消息末尾加一行「这个库里有相关内容,先查」。模型调 `knowledge_search`,拿到「公司简介与联系方式」和「控糖服务介绍」两段(已清理过的版本),回复地址,并说「坚持饮食、运动和监测管理,有助于改善血糖」,不说「逆转」「效果显著」。

**场景 B:客户要动作视频。** 客户发「深蹲怎么做?有视频吗?」。模型先用文字讲要点,输出 `videos: ["V33"]`(深蹲),`messages` 里没有链接。深护拿到结果,按映射表把 V33 换成 mp4 链接,发一条文字气泡 + 一条视频气泡。如果模型给了表里不存在的编号,平台按输出格式校验直接让模型重写;万一映射表里这个编号已停用,深护丢掉视频、照发文字,并记一条告警。

**场景 C:运营改了一句服务介绍。** 深护说「控糖服务里的直播从每月一次改成每两周一次」。助手改 git 里的 `控糖服务介绍.md` 并提交 → 在测试控制台把同名文件重传 → 控制台显示预估费用,确认 → 等「就绪」→ 检索测试和冒烟过 → 把这一条加进生产清单的「增量变更」→ 用户在生产控制台重传同一个文件、确认 → 对照测试与生产两边的文件大小、段数一致。全程没人在控制台里直接改段落。

### 3.2 「公司与服务」知识库

#### 3.2.1 为什么进库而不是继续塞提示词

公司介绍清理后约 2,000–2,500 字。继续塞提示词,每轮固定多 1,800–3,000 token,而且改一句就要重新发布智能体、两个环境各发一次;进库后只有问到时才花 token,改内容只需重传文件,智能体不用动。用户已拍板「公司与服务」一库,这里只说明理由。

#### 3.2.2 文档怎么切

| 文件名(= 检索时的文档标题) | 放什么 | 来自原文哪节 | 备注 |
|---|---|---|---|
| `公司简介与联系方式.md` | 公司做什么、服务哪些人群、体验中心的位置概述与设施;公司全称、地址、客服电话 | 简介、规模、名称地址电话 | 服务人数说法见清理清单第 2 条 |
| `服务边界与用药说明.md` | 不具备开处方资质;用药调整要找有处方权的医生;健康管理不替代医疗 | 「重要说明」 | 这条同时是提示词里的行为规则;库里放一份,是为了客户问「能不能开药」时有原文可依 |
| `控糖服务介绍.md` | 服务对象、周期(3–6 个月)、包含内容(专家咨询、营养方案、饮食与血糖点评、定期直播);「想了解更多可以看小程序」一句(**不放链接**) | 服务一节的总述、第 2 条、小程序那句;`goods_info` | |
| `<第二种服务>介绍.md` | 多角色服务团队的构成、周期、日常管理方式、响应安排 | 服务一节第 3 条 | 服务名带「逆糖」,文件名待 §9 第 2 条拍板;响应时间待核实(清理清单第 6 条) |
| `管理方法与管理模式.md` | 控糖方法的三个阶段(改写去掉效果承诺)、院外管理 + 营养 / 运动 / 心理多学科参与 | 管理方法、管理模式 | 方法名待 §9 第 2 条 |
| `专家团队.md` | 待拍板(§9 第 1 条);推荐先只写团队由哪几类专业人员组成 | 公司专家 | |

原文「运动推荐」一节不是公司信息,挪去运动视频编号表(§3.3)。

切成多篇的理由(读代码确认):

- 平台把**文件名**(去掉扩展名,下划线换空格)作为文档标题,和**小节标题路径**一起拼在每段前面参与向量、关键词和重排(`protocol/knowledge.py:291-318`)。文件名和小节标题写成客户的问法,直接提高命中。
- 切块时**标题一换就断段**,一个小节不会和下一个小节混在一段里;默认每段上限 512 token、重叠 64(`chunking.py:1-35`;迁移 `0022`)。命中一段时返回它所在的「父段」(上限 1,024 token,`chunking.py:178`)。

#### 3.2.3 标题和正文怎么写

1. 每篇一个 `#` 标题,下面若干 `##` 小节;小节标题写成客户会问的话:「## 控糖服务包含哪些内容」「## 服务周期多长」「## 公司地址和客服电话」「## 能不能帮我开药」。
2. 每个小节控制在 300 字以内,一节只讲一件事,保证一节就是一段。
3. 正文写完整的口语短句,不用表格、不用加粗。健管师回复禁止 Markdown、限 20–120 字,原文越接近口语,模型越不容易照搬格式。
4. 客户的几种说法在正文里自然出现一次(控糖 / 血糖管理 / 糖尿病管理),帮关键词检索。
5. 除电话外不放任何长串(链接、小程序短码、编号)。
6. 正文里不出现提示词禁止的词(下面清理清单 + §7 的禁用词扫描)。

#### 3.2.4 入库前清理清单

对照健管师提示词 2.3–2.6 节逐条过 `company_info`。我把原文用禁用词扫过一遍:「完全」1 处、「诊疗」2 处、「逆转」3 处、「逆糖」5 处、「显著」1 处、「著名」1 处、「名医」1 处;「病人」1 处是「慢病人群」的误报。

|---|---|---|---|

#### 3.2.5 真实专家姓名、任职医院放不放进库

列为待拍板(§9 第 1 条)。要考虑的事实:

- 原文 10 位专家都带真实姓名和现任 / 曾任医院。放进库,模型会在聊天里主动提名字和医院,这等于拿医生个人和医院的名义做宣传:要每位专家书面同意,任职变动后库里内容会过期,模型自己没法核实。
- 模型可能顺势说「我帮你约某某教授」—— 预约不在智能体的能力范围内,提示词又禁止承诺后续服务。
- 不放的代价:客户问「你们有哪些专家」时只能回答团队构成,不能报名字。

```yaml
    # probe: false   ← 只有 §7 用例 3 判定误触发太多时才加
```

- **按名字引用,搜索时才解析**:智能体可以先于库保存;库不存在时 `knowledge_search` 报「这个智能体配置的知识库都不存在」,不会悄悄返回空(`agent_spec.py:667-720`;`tools/knowledge.py:252`)。
- 提示词里加一句(放进健管师提示词,措辞由提示词那篇定):「客户问到公司、服务内容、地址电话、专家团队、能不能开药时,先查『公司与服务』;查不到就如实说本轮没法确认,不要编;查到的内容按回复规范改写成口语短句,不要照搬。」
- **每轮探测**(平台总开关默认开,`settings.py:204`;智能体级默认开):每轮开始用客户最新一句话对库做一次**轻量检索**(关键词 + 向量,不重排、不调模型,每库取 3 条,总时限 1.5 秒)。判定相关时在本轮消息末尾加一行「某库有 N 段相关内容,先查」;**从不把原文直接塞进去**;闲聊和很短的消息不探测(`tools/knowledge_probe.py:1-41, 81-92`)。
  - 对本智能体的风险:客户日常消息里常有「血糖」「饮食」「运动」,服务介绍里也有。关键词一侧只要同一段里有消息里的两个实词就算相关,可能在报数据的轮次里也提示「先查」,多一次检索、多一两秒,还可能把推广内容带进回复。所以要先在测试里量(§7 用例 3),再定开不开(§9 第 8 条)。

#### 3.2.8 入库费用预估与确认(读代码确认)

流程(`api/knowledge_estimates.py:1-21`;`api/knowledge.py:881-951`):

1. 上传文件 → 平台在本地解析计数**先估价,不花钱、不调模型**,文件进入「待确认」。
2. 控制台显示每个文件的预估金额;**不论金额多少都要人点确认**才开始入库(包括 ¥0.00)。确认时带上「当时看到的条数和总额」,中间有变化就拒绝、让人重看。
3. 7 天没人确认,自动撤回。
4. 同一个库里重传**字节完全相同**的文件 → 「无变化」,什么都不做;同库另一个文件已有相同内容 → 标「重复」,不解析不收费。
5. 重传同名文件 → 新版本进待确认,**旧版本继续服务**,新版本就绪后才替换(`persistence/knowledge/base.py:1091-1124`)。文档按「库 + 文件名」唯一(`models/knowledge.py:233`)。

费用组成:向量化;库画像(一次辅助模型调用)和探测校准(一组固定查询的向量化),这两项只在每轮探测的平台总开关开着时才有(`protocol/knowledge_estimate.py:59-71`)。本库 5–6 篇纯文字,粗估一次入库不到 ¥0.1,**以控制台显示为准**;测试、生产各付一次。

限制:单文件默认 50 MiB(`settings.py:536`,部署级可调);格式 pdf、docx、pptx、xlsx、md / markdown、txt、html / htm、csv(`parsing.py:34-36`)。本库全部用 `.md`。

### 3.3 运动视频编号表

#### 3.3.1 编号规则

- 格式 `V` + 两位序号(超过 99 用三位,与 02 一致):按现在表格的顺序发 V01–V41;新视频往后排(V42…)。
- **编号永不复用**:视频下架时这一行标「停用」,不删、不把编号让给新视频 —— 会话里留着模型以前输出的编号,复用会让旧记录指向别的动作。
- 不直接拿动作名当键:名字会改,还有很近的名字(深蹲 / 宽距深蹲 / 高脚杯深蹲 / 弹力带酒杯蹲),原表里还有一个名字带空格、和文件名对不上。编号短且稳定。

#### 3.3.2 字段

| 字段 | 例 | 谁填 | 进提示词? | 进深护映射? |
|---|---|---|---|---|
| 编号 | `V33` | 助手按规则发 | 是 | 是 |
| 动作名 | 深蹲 | 来自原表 | 是 | 是(日志用) |
| 器械 | 徒手 / 哑铃 / 壶铃 / 弹力带 / 弹力圈 | 深护运动教练 | 是 | 否 |
| 强度 | 低 / 中 / 高 | 深护运动教练 | 是(可选) | 否 |
| 注意人群 | 「膝关节不适慎做」 | 深护运动教练 | 可选 | 否 |
| 链接 | `https://<视频 CDN 主机>/no_logo_sport_video/<动作名>.mp4` | 来自原表 | **否** | 是 |
| 状态 | 启用 / 停用 | 深护运营 | 只列启用的 | 是 |

器械不能从名字推:41 条里 21 条名字里没写器械,其中有的其实要器械(比如高脚杯深蹲要哑铃或壶铃)。原提示词要求「有高血压选温和运动」,但原表没有任何强度信息,模型只能猜 —— 补「强度」「注意人群」两列,模型才有依据。

#### 3.3.3 放在哪:四个选项

| 选项 | 做法 | 好处 | 代价 |
|---|---|---|---|
| **A 提示词 + 输出枚举(推荐)** | git 里一份 CSV 是唯一来源;生成三样:提示词里的「运动视频目录」一节(编号 + 动作名 + 器械 + 强度)、输出格式里 `videos` 的枚举、给深护的映射 JSON | 零开发;模型挑选时看得到全表;编号写错由输出格式校验当场拦住重写 | 每轮多约 370–1,000 token(静态内容,随系统提示词一起缓存);加视频要改 CSV、重新发布智能体(两个环境各一次),同时更新深护映射 |
| B 深护 MCP 工具 | 深护 MCP 加一个只读工具,返回「编号 + 动作名 + 器械」;深护发送时用同一张表换链接 | 唯一来源在深护;加视频不动智能体 | 深护要开发新工具;要视频时多一次工具调用;输出只能按格式校验(如 `^V\d{2,3}$`),校验不了编号是否存在 |
| C 业务方每轮传入 | 深护每次调用把目录作为一个输入变量传进来,渲染进系统提示词 | 唯一来源在深护;不开发 MCP | 每轮请求都带这份目录;同样没法做枚举校验;多一个变量要在提示词里声明 |
| D 放进知识库 | 目录作为一篇文档入库 | — | **不推荐**:检索只返回前几段,模型要挑动作得看全表;表格会被切开;而且知识库返回不了视频本身 |

推荐 A:41 条一年也变不了几次,最省事;编号校验最硬。如果深护以后要自己频繁加视频、不想等智能体发布,再换 B(§9 第 5 条)。

**token 估算**(两种通用分词器的范围,只看量级):只放「编号 + 动作名」约 370–500 token;加器械、强度两列约 760–1,010 token;Dify 现在整张带链接的表约 2,300–2,450 token。

#### 3.3.4 为什么不让模型写链接

1. **抄长串必错**:每条链接是约 60 token 的 URL 编码串,错一位就是 404。平台已有同类教训写进规矩:「长串抄错一位就是 404」「地址、编码、ID 这类长串,永远不许从上下文里抄进参数」(`docs/design/agent-config-1235-addendum-b61.md:105, 122`)。原提示词专门写「不得自行编造和篡改链接」,也说明遇到过(推断)。
2. **能校验**:编号是 41 个固定值,输出格式用枚举就能挡住编出来的编号;链接没法校验真假。
3. **发错的后果**:深护按扩展名决定发视频还是发文件,坏链接到客户那里就是一个打不开的气泡。
4. **换地址不动智能体**:CDN 换域名、换文件,只改深护映射。
5. **省 token**:见上面估算。

#### 3.3.5 输出和深护侧怎么接

- 输出字段 `videos`(名字、是否必填以输出契约那篇为准):字符串数组,最多 3 个,不重复,每项必须是目录里的编号。客户没明确要视频时必须是空数组(沿用原提示词 3.1–3.2 节的判断规则)。
- 平台:输出格式校验不过 → 带着格式要求让模型重写一次,路由层再重试最多 2 次;仍不合格这一轮失败(`agent_spec.py:820-880`)。41 选 3 的选择题,连错三次的可能很小;发生了就走深护的兜底话术。
- 深护:取到结果后按映射 JSON 把编号换成链接,放进 `file_link_list`;**不认识的编号或已停用的编号直接丢掉、文字照发**,并记一条带编号的告警日志。

#### 3.3.6 谁维护

深护运营(运动内容负责人)提出增删改 → 助手改 CSV、重新生成提示词片段、枚举、映射 JSON,提交 git → 测试环境发布智能体 + 深护测试环境更新映射 → 冒烟 → 写进生产清单的增量变更 → 用户发布生产智能体,深护运维更新生产映射。三处(提示词目录、枚举、映射 JSON)条数和编号必须一致,清单里有核对步骤。

#### 3.3.7 16 个推荐动作怎么办

原「运动推荐」16 个动作里只有 3 个有同名视频,1 个名字差「徒手」二字(视为同一个),其余 12 个没视频。选项见 §9 第 6 条;推荐让深护运动教练确认这 12 个还推不推荐:推荐的进目录,标「无视频」(只用于文字建议,不进枚举);不推荐的删掉。

### 3.4 商品介绍(`goods_info`)和小程序入口

- `goods_info` 实际只有一行小程序入口,与 `company_info` 重复,**没有任何商品或价格信息**。
- 去处:「想了解更多服务可以看小程序」这句话并进 `控糖服务介绍.md`;短链本身不进库、不让模型写(理由同 §3.3.4)。
- 小程序入口:**先不发**(已拍板 11-17,§9 第 7 条;02 已取消 `fixed_reply`,原设想的「输出字段附带入口」作废)。本篇只要求库里不出现短链。`控糖服务介绍.md` 里「想了解更多可以看小程序」这句要不要留(留了客户可能追问入口而模型给不出),运营核事实时一并定。
- 两个待深护确认的事实:深护发送接口不支持小程序卡片;`#小程序://…` 这种纯文本在企微发给微信客户时能不能点开,需要深护实测(推断,未核实)。
- 价格、报名方式:Dify 里也没有。客户问到时模型只能如实说本轮没法确认。如果希望 AI 能答,深护补一篇「费用与报名方式」进库(可选,§9 第 4 条附带)。

### 3.5 可选第二期:控糖 / 血压 / 血脂科普库(全部待拍板)

- **为什么**:现在健康问题全靠模型自己的常识回答,口径未必和公司的控糖方法一致,也容易踩广告法和医疗边界。有一个经过审核的科普库,平台「绑了库就先查」的规则会让模型优先按库里的口径答。
- **内容从哪来**:深护已有的课程讲义、直播讲稿、营养师资料、健康方案模板里的通用部分;公开指南只做**深护自己写的摘要**,不整段搬原文(版权)。
- **口径**:与公司控糖方法一致;具体数值(血糖目标、用量)要么不写,要么写明「以医生和个人方案为准」;与客户个人健康方案冲突时以个人方案为准(这条写进提示词)。
- **谁审**:深护医学顾问 / 营养师逐篇签字;每篇开头写审核人、日期、版本、适用人群。
- **代价**:平台零开发;深护内容整理加审核约 1–2 周;每轮探测命中会明显变多(健康问题几乎每轮都有),检索次数和延迟上升,要在测试里量。

#### 3.6.3 测试环境改内容的规矩

1. **先改 git,再动控制台**。改 md、CSV、YAML 都先提交,再按提交后的文件去测试控制台操作。控制台上不留 git 里没有的改动。
2. **知识库只整文件重传**,不在控制台里直接编辑段落(平台有段落编辑功能,但那样改的内容不在 git 里,重传还会被覆盖)。
3. **文件名就是标题,改名 = 新文档**。改名后要在控制台手工删掉旧名文档,否则新旧两份同时被检索到。
4. **智能体只从 `manifest.yaml` 整段粘贴**,保存草稿 → 调试台用草稿试跑 → 发布。不在表单里零散改字段。
5. 每次改动在 README 变更记录写一行:改了哪个文件、为什么、谁审核(表述类改动要深护运营 + 法务)、测试生效时间、生产生效时间(上线后补)。
6. **测试环境第一次就按生产清单搭**,边搭边修清单。上线前在测试里按清单「只核不改」走一遍,每一步的核对项都通过,清单才算定稿 —— 生产只是把测试上的步骤原样重放。

#### 3.6.6 以后的增量变更

- **只改知识库**:改 md → 提交 → 测试重传、确认、检索测试 → 清单「增量」一节记一行 → 用户在生产重传同名文件、确认、核对大小和段数。智能体不用动。
- **加 / 停用视频**:改 CSV → 重新生成提示词目录、枚举、映射 → 测试发布智能体 + 深护测试映射 → 冒烟 5、6 → 生产按清单第 10–14 步。
- **改提示词或工具**:改 `manifest.yaml` → 测试保存草稿、试跑、发布 → 生产按清单第 10–12 步。

#### 3.6.7 可选平台改造:智能体 + 知识库打包导出 / 导入

- **做法**:
  - 导出:控制台在智能体详情页「导出」,得到一个压缩包 —— 线上版本的配置 YAML;它引用的每个知识库的设置;每篇文档的原件(平台本来就保留原始字节,用于失败重跑,`api/knowledge.py:908-912`);依赖清单(MCP 注册名、平台 MCP 名、模型、平台技能)。**不含**任何密钥、MCP 地址、记忆、会话。
  - 导入:上传压缩包 → 先出预检报告(目标环境缺哪些 MCP 注册、平台 MCP 是否放行、模型在不在目录、同名库是否存在以及每个文件的大小差异、同名智能体是否存在)→ 用户逐项确认 → 建库、上传文档(照样走入库估价和确认)→ 建智能体**草稿** → 用户试跑后自己发布。
- **粗估**:后端导出 2 天、导入加预检 4–5 天、控制台页面 2–3 天、测试 2–3 天,合计约 2–3 人周(粗估,未拆任务)。
- **中间方案**:一个本地脚本,用用户自己的控制台登录态(员工身份能过这组接口,API key 不能)读 git 里的文件建库、上传、展示估价等用户确认、建智能体草稿。约 1–2 天;但要处理登录凭据怎么交给脚本,生产上由用户自己跑。
- **建议**:先按清单手工走一遍生产,记下花了多久、哪一步出错。如果后面还有一批 Dify 智能体要迁,或者同一个智能体每月都要同步,再做;只迁这一个,手工清单足够(§9 第 11 条)。

## 5. 接口与数据结构

### 5.1 `exercise-videos.csv`

| 列 | 类型 | 约束 |
|---|---|---|
| `code` | 字符串 | `^V\d{2,3}$`,唯一,永不复用 |
| `name` | 字符串 | 动作名,唯一 |
| `equipment` | 枚举 | 徒手 / 哑铃 / 壶铃 / 弹力带 / 弹力圈 / 无视频 |
| `intensity` | 枚举 | 低 / 中 / 高;可空 |
| `caution` | 字符串 | ≤30 字;可空 |
| `url` | 字符串 | https,`.mp4` 结尾,无查询串;「无视频」行为空 |
| `status` | 枚举 | 启用 / 停用 |

### 5.2 提示词里的目录一节(生成样例,只列 3 行;编号按现表顺序是真的,器械、强度是示意,以深护运动教练填写为准)

```
# 运动视频目录(客户明确要视频时才用;只在 videos 里填编号,回复正文里不写链接)
V07 哑铃弯举(哑铃,低)
V27 弹力带扩胸(弹力带,低)
V33 深蹲(徒手,中)
```

### 5.3 输出格式片段(并入输出契约那篇的总 schema)

```json
{
  "videos": {
    "type": "array",
    "maxItems": 3,
    "uniqueItems": true,
    "items": { "type": "string", "enum": ["V01", "V02", "…", "V41"] },
    "description": "客户明确要运动视频时填目录里的编号,最多 3 个;否则为空数组"
  }
}
```

输出格式按 JSON Schema 2020-12 在平台本地校验(`agent_spec.py:820-880`),枚举有效。

### 5.4 `video-map.json`(交深护)

```json
{
  "version": "2026-11-17.1",
  "source_commit": "<git 提交号>",
  "videos": {
    "V33": { "name": "深蹲", "url": "https://<视频 CDN 主机>/no_logo_sport_video/<文件名>.mp4", "status": "active" }
  }
}
```

深护规则:`status != "active"` 或编号不存在 → 不发视频、文字照发、记告警(带编号和 run 编号)。

## 6. 异常与边界

| 情况 | 会怎样 | 怎么处理 |
|---|---|---|
| 生产没建库或库名拼错 | `knowledge_search` 报「这个智能体的知识库都不存在」;模型应如实说没法确认 | 冒烟 1–3 会暴露;清单第 7 步逐字核对库名 |
| 上传后忘了确认 | 文档停在「待确认」,7 天后自动撤回;新文件检索不到,重传的文件继续用旧版 | 清单第 8 步要求全部「就绪」才往下走 |
| 重传字节相同的文件 | 「无变化」,什么都不做 | 可以放心重跑清单第 8 步 |
| 改了文件名 | 新增一篇,旧的还在,两份都会被检索到 | 规矩第 3 条:改名同时删旧名 |
| 两环境向量模型不同 | 段数可能不同;库显示需要重建索引 | 清单第 8 步核对段数,不一致先查向量模型和切块参数 |
| 每轮探测超时(1.5 秒) | 这轮不加提示,静默跳过 | 不影响回答;模型仍可按提示词自己查 |
| 重排失败或限流 | 退回融合排序,结果带降级标记 | 库小,影响有限;检索日志能看到 |
| 每轮探测误触发 | 报数据的轮次也去查公司介绍,多一两秒,可能夹推广内容 | §7 用例 3 量化;超标就设 `probe: false` |
| 模型给出目录外的编号 | 格式校验不过 → 重写;连错 3 次本轮失败 → 深护兜底话术 | 概率很低;失败率进日常监控 |
| 编号在目录里但深护已停用 | 不发视频,文字照发,告警 | 下次发布把目录同步掉 |
| 客户要的动作没有视频 | `videos` 为空,文字讲要点 | 沿用原提示词「没有对应视频就给文字建议」 |
| 库里内容与客户个人方案冲突 | 模型可能按库里通用说法回答 | 提示词写明个人方案优先(提示词那篇) |
| 有人在控制台直接改了段落或 YAML | 测试与 git 不一致,生产重放时这部分丢失 | 规矩第 1、2、4 条;清单第 0 步只认 git |

## 7. 测试与验收

每条:怎么触发 → 看哪里 → 什么算过 → 没修好会怎样。

1. **禁用词扫描(静态)**
   - 触发:对 `knowledge/公司与服务/*.md` 跑一遍正则(提示词 2.3–2.4 的词 + 本库额外的「逆转、显著、著名、名医」,「逆糖」视 §9 第 2 条),「慢病人群」等已知误报列白名单。

   - 过:清理后的文件 0 命中。
   - 没修好:冲突说法进库,模型照着说。
2. **检索命中(测试环境)**
   - 触发:库的检索测试页跑 10 个问题(地址、电话、控糖服务内容、服务周期、第二种服务、能不能开药、管理方法、体验中心设施、专家、怎么了解更多)。
   - 看:检索测试结果、检索日志。

   - 触发:调试台发 20 条日常消息(报血糖、报饮食、问饮食、闲聊各 5 条)。

   - 过:≤2/20 轮出现探测提示或调了 `knowledge_search`(门槛待 §9 第 8 条确认)。
   - 没修好:日常对话变慢、回复夹公司推广 → 设 `probe: false` 后复测,并确认用例 2 的端到端问答仍能查库。
4. **端到端问答(测试环境)**

   - 深护单测:映射里删掉一个编号再喂给发送逻辑,文字照发、无视频、有告警。
   - 没修好:发出坏链接或把编号原样发给客户。
6. **测试→生产一致性**
   - 触发:生产清单第 8、10 步做完后。
   - 看:两个环境库文档列表的文件名、大小、段数、切块参数指纹;两个环境智能体 YAML 页内容与 git 里的 `manifest.yaml` 对比(平台补出来的默认字段忽略,推断)。
   - 过:文件名和大小完全一致;段数一致;YAML 除占位外无差异。
   - 没修好:生产与测试行为不同,而且查不出原因。
