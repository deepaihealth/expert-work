## 量级预估的算术（先摆出来，免得事后倒推）

## n=1 的边界

## 去查的结果：我的因果模型错了一个数量级

预测里我算的是「省掉 20,064 字符的重打 ≈ 5,016 输出 token × 18ms ≈ 90 秒」。

**实际省了约 950 秒。差 10 倍。** 原因是我只算了「少写一个文件」，没算**那个文件引发的连锁**：

基线那一次实际写了 **46,385 B**，不是 20,064：

| 写了什么 | 字节 | 那东西本来就在工作区里吗 |
|---|---|---|
| `style/render_plan.py` | 20,064 | **在**（重打） |
| `style/PLAN_STYLE.md` | 2,591 | **在**（重打，我原先漏数了这个） |
| 方案 JSON 第一遍 | 11,619 | — |
| 方案 JSON 第二遍 | 12,111 | 同一轮里又写一遍 |

而重放只写 15,944 B（JSON 一次，且比基线那份**更大**）。

**真正的机制**：`list_dir` 报 `sandbox create failed: 504` → 模型判定 `style/` 不存在 → 重建渲染脚本 → 重建版式锚 → 拿不准又把 JSON 写两遍 → 每一步都是额外的 LLM 轮次。**24 → 13 次调用，差的 11 次就是这条连锁。**

所以：**一次失败的目录探测，赔的不是一个文件，是半个 run。** 这一点在开跑前我没想到，是数据告诉我的。

所以「success 但没有产物」在这个 agent 上是**既有常态**，重放的 1/4 = 25% 低于任何一周的基线。**不是回归。**

（顺带立一条 backlog：对这个 agent 而言 `status=success` 几乎不携带「活干完了」的信息。与 B-85 ③ 同源，但那一条修的是工具失败的信号，不是交付物缺失的信号。）

## 这次还证不了什么

1. **单个 run 的归因未拆开。** 重放测的是 `621249f6 → 927087ed`，中间含 B-61/B-67 与 #1608。要单独摘出本波，必须在 `139057c8` 上再跑一臂。
2. **基线是异常值。** `7fad305b` 是 298 个 run 里第 5 长的。不过三次重放（177/235/254s）都稳定在全体均值（228s）附近或以下，而那个均值本身是**混着老代码的老均值** —— 所以「向均值回归」解释不了全部，但解释得了多少，得靠群体统计。
3. **发生率答不了。** 重打的真实发生率是 5%（279 个「文件已存在」的后续 run 里 13 个重打）。n=4 看不见 5% 的变化，只能泡一周复算。
